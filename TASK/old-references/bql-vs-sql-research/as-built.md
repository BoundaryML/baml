# Research: BQL vs SQL for the observability query surface (as-built reality)

## 0. Prior art in the repo: the decision was already made competitively
- design.md §8 (line 750): three surfaces were designed competitively — SQL over DataFusion virtual tables, a pipeline DSL, a BAML-native stdlib API — scored by three judges. DSL won human (8.5) and implementer (8) lenses; **agent lens preferred SQL (8.5)** but "conceded that the DSL's trust machinery, made mandatory, resolves SQL's worst agent hazards (silent-empty results, opt-in completeness)". The decisive implementer argument is the wasm size gate: bridge_wasm gzip ceiling **4.5 MiB** with committed baseline **4.4 MiB** (+3% delta guard) — actual figures verified in `.cargo/size-gate.toml:74-88` and `.ci/size-gate/wasm32-unknown-unknown.toml:5-7` (file 16.0 MiB, gzip 4.4 MiB). Headroom is ~100 KiB gzip; "embedding DataFusion (~2-4 MB compressed alone) is disqualifying" (design.md:750).
- The escape hatch is explicit: "sealed segments export to Parquet so DuckDB/DataFusion work *outside* the product as the unbounded-expressiveness escape hatch" (design.md:752). **Honesty check: export(format=parquet) is in the designed catalog (design.md:791) but NOT in the as-built stage list** (bql.rs:805 `STAGE_LIST` = runs, run, ctx, calls, errors, rollup, where, sort, top, stats, limit, values, get, instances, vdiff) — the escape hatch is unimplemented today. However, storage was deliberately shaped for it: sealed BCCT columns are "contiguous fixed-width little-endian arrays, 8-byte aligned, so a zero-copy Arrow `ArrayRef` view over the mmap gives Arrow interop (and Parquet export) without the Arrow container" (design.md:575).
- The cloud story is NOT anti-SQL: studio design keeps ClickHouse for hosted projections and SQLite/DataFusion locally (studio-design §6.1, lines 1184-1188, 1155-1157), but rules "Physical SQL cannot be that contract because: local and hosted storage differ; physical tables change across projection generations; tenant scope and budgets must be mandatory; BAML types, value paths, coverage, and three-valued results need domain semantics; a local Codex agent should construct a safe plan without learning private database layouts" (studio-design:422-430). design.md:849 mandates a "[launch] BQL->ClickHouse compilation of the aggregate subset" prototype with a golden diff corpus (still open: IMPLEMENTATION.md:704 "ClickHouse compilation prototype" in REMAINING P8). So SQL engines are positioned as *projection backends compiled to*, never the semantic contract.

## 1. What BQL v1 actually is (as-built, bex_query/src/bql.rs, 2558 lines)
- Pipeline of typed stages `source | transform | sink`; **set kinds implemented: RunSet, CtxSet, ValueSet, Table** (SetKind enum, bql.rs:708-714; design §8.2 specified nine kinds — CallSet, EventSet, SpawnSet, SeriesSet, DiffSet are unbuilt). Exactly two implicit coercions: RunSet→CtxSet (single-run only; multi-run fails closed with E_MULTI_RUN_CTX, bql.rs:1599-1606) and X→Table at pipeline end (bql.rs:2474-2483).
- **Stage catalog** (bql.rs:943-1362): sources `runs(last=<dur>, status=)`, `run(id=)`, `ctx()`; CtxSet transforms `calls(fn=glob)`, `errors()`, `rollup(by=fn)`, `where(<metric> <op> <value>)` (single comparison only), `sort(by=, desc|asc)`; sinks `top(k, by=)`, `stats()`, `limit(k)`; **value plane**: `values(role=[input|output|error|log], fn=glob)` → ValueSet, `get(max_bytes=64kb default, depth=32 default)` hydration sink, `instances(source=values)` exact-instance gate, `vdiff(a=,b=)` two-run output compare, `stats(by=cid)` dedupe view. Metrics: calls|total_ns|self_ns|errors|p50|p95|p99 (bql.rs:737).
- **Typed errors with machine-actionable remedies** (BqlError{code, message, remedy}, bql.rs:38-44): E_PARSE, E_UNKNOWN_STAGE, E_TYPE, E_MULTI_RUN_CTX, E_BAD_ARG, plus **E_NO_EXACT_SOURCE** at three sites: non-values instance source (bql.rs:1296-1302), `values(fn=…)` filter with no exact call→fn join (bql.rs:2328-2334, remedy "re-run with BAML_PROFILE_RAW=1 … or drop the fn= filter"), `instances()` with zero captures (bql.rs:2390-2395, remedy "opt calls in with $id = boundary.id().capture(...), arm the flight recorder, or request a bounded full trace"). E_MISSING_BLOCK exists via HydrateError (values.rs:258-264 "§8.4 fail closed: partial bytes are never decoded as whole") — surfaced per-row as `{"$unavailable": …}` in get() output (bql.rs:1940-1946).
- **Completeness footer on EVERY result** (Completeness{sealed, torn, first_ts_ns, last_ts_ns, degraded[]}, bql.rs:128-139): sealed/torn are real scan facts from segment recovery (CctFold.torn/sealed, cct.rs:53-54, set from ScanEnd Sealed/ActiveEnd/Torn at cct.rs:194-201); degraded notes include percentile mean-fallback counts (bql.rs:1431-1439), implicit RunSet→CtxSet coercion (bql.rs:1591-1596), implicit 1000-row caps (DEFAULT_ROW_LIMIT, bql.rs:30, notes at 1723-1727), empty-set explanations ("RunSet is empty: no runs matched", bql.rs:1583; "no captured values matched: capture defaults are llm_boundary…", bql.rs:2349-2352), CAS-store-unreadable fallback (bql.rs:1915-1919), budget elision counts ("N subtree(s) elided by the M-byte budget; raise get(max_bytes=...) or descend by cid", bql.rs:1949-1952). Empty results still ship the footer — the BQF1 BqlTable frame reserves row 0 as a meta row so "an EMPTY result is a 1-row frame that still carries its footer" (bqf1.rs:66-67; test bql.rs:2541-2557).
- **Budgets**: implicit 1000-row cap on materialization; get() byte budget default 64 KiB / depth 32 (bql.rs:1247-1273) with byte-size literals (64kb/4mb, lexer bql.rs:292-297, 443-464); engine wire bound DEFAULT_MAX_BYTES 4 MiB / HARD_MAX 16 MiB, native fold cache byte-budget 256 MiB LRU (engine.rs:16-21, evict_to_budget:127-141).
- **ColData::Json** (bql.rs:80-88): hydrated bodies are serialized JSON per cell — "renders as an object in JSON output, as a truncated preview in tables, as Str on the wire" (96-char preview per IMPLEMENTATION.md:632).
- **Percentiles**: folded from 16-bucket ×4-stride histograms (bucket upper bound, bql.rs:1443-1467); empty histogram degrades to mean and bumps the footer counter — degradation is counted, never silent.
- **vdiff = Merkle short-circuit**: matches calls across two runs by INPUT CID, compares output CIDs; "CID equality is the Merkle short-circuit — bodies are never fetched" (bql.rs:2074-2077).
- Consumers: `baml q` CLI (q_command.rs, 215 lines, table+json render, footer line), /api/obs WS method "bql" (obs_ws.rs; errors → Status 422 with code+remedy), studio Runs tab "Captured values" panel drives the same `values() | get(16kb)` query as the CLI (IMPLEMENTATION.md:641-651).
- **Designed-but-unbuilt** (honest deltas from §8): E_BUDGET resume cursors, snapshot pinning (--snapshot), --schema self-description, caret spans, series/delta/diff(align=fqn), lookup tables, events/dumps/health/audit/failure sources, live()/flame()/export sinks, path patterns (`>`/`>>`), multi-run ctx, boolean where-composition, get(as=Type) typed hydration (explicitly rejected with remedy, bql.rs:1241-1245), MCP tool (IMPLEMENTATION.md:652-654 REMAINING P7). `live()` streaming is NOT a BQL stage; obs_ws refuses subs on bql ("bql is not subscribable in v1", obs_ws.rs:214) — live tails come from the named fast-path subscriptions instead.

## 2. Engine properties beneath BQL, and whether a SQL executor could sit on the SAME storage
The stack: BQL executor → ObserveEngine (fold cache) → CctFold (epoch-aware fold) → SegmentSource (sans-io byte plane) → {MmapSource, SliceSource, LiveMirrorSource} → BCCT segments / CAS packs / .bamlvalue records / .bamlmeta.

**(a) Sans-io Poll/NeedData fold** (source.rs:23-44: "Queries never do IO … a view that cannot be satisfied from resident bytes surfaces as Poll::NeedData with the exact ranges, and the host fetches and retries"). This is what makes ONE engine run identically on native mmap, wasm linear memory, and HTTP Range (design §9.2: "the only model that works identically … without an async runtime in wasm"). SQL engines own their I/O and buffer managers: DuckDB has its own filesystem abstraction (duckdb-wasm reimplements async I/O inside its own engine), ClickHouse-local has none for wasm, SQLite VFS is sync. None can express "return the byte ranges you still need and let the host fetch" — you'd run the SQL engine only where its I/O model works, forking the host story the sans-io design exists to unify.

**(b) The storage is NOT tables — it's a fold input.** BCCT segments are append-only block streams (112B header, CRC'd 32B block headers, torn-tail recovery, seal-by-append; IMPLEMENTATION.md:355-360) whose semantics are: totals = last `node_total` checkpoint + deltas after it, per node, per epoch; `EPOCH_CLOSE` markers reset the node-id space; cross-epoch nodes unify by recursive ancestor-path re-interning (cct.rs:8-14, merge_epoch/resolve cct.rs:346-421 — memoized parent-chase creating (parent,function) interned nodes). A SQL executor pointed at raw block columns would see *delta rows in an epoch-local id space*, not answers. To answer `top(5, by=total_ns)` in SQL you need either: (i) a **table function / virtual table that runs this exact fold code** — i.e., you keep all the Rust and SQL only replaces the ~700-line lexer/parser/planner while adding an FFI impedance layer; or (ii) **materialization** into real tables. Materialization costs: a second copy of every run's data (vs the current zero-copy mmap + 256 MiB byte-budgeted fold cache), an ingestion/compaction pipeline (freshness lag vs the current re-fold-on-epoch-change), index maintenance, and a consistency story for torn tails and live growth (the fold's sealed/torn/first/last facts — the footer's raw material — come from the scan itself; a materialized table has no per-query provenance).

**(c) Live mirror**: same-process runs fold from the consumer's in-RAM state via `cct_live_segment` — bytes in the IDENTICAL block format, "the query code cannot tell" (source.rs:209-215); epoch = (len<<32)|crc32c because fixed-population live tails re-encode to the same length (engine.rs:396-403). obs_ws re-opens preferring live every subscription tick (obs_ws.rs:293-306, 377-386), giving ~0-latency live views *ahead of the 1s/1MiB group commit*. A SQL engine over files or materialized tables is structurally behind group commit; feeding it RAM snapshots means a per-tick ingest of the whole segment into the SQL engine — a copy per 250ms tick per subscriber.

**(d) Epoch-aware CCT fold + hist percentile folds**: the ×4-stride bucket percentile (bql.rs:1443-1467) is expressible in SQL (cumulative sum over 16 bucket columns), painfully; the mean-fallback-with-counted-degradation is a semantics choice no SQL aggregate carries. The recursive path-identity merge is expressible as a recursive CTE only after the checkpoint/delta/epoch decode — which SQL can't do without the custom reader anyway.

**(e) Budgeted CAS hydration with Merkle elision** (values.rs:299-333 + canon::decode_budgeted): values live as BLAKE3-CID canonical DAGs in packs; hydration is byte+depth budgeted, eliding whole subtrees and returning their `bamlv_1_…` CID handles for selective descent ("budget failure is a navigation hint", design §8.4.2). SQL's closest analog is `SUBSTR(json, 1, N)` — structure-destroying truncation with no descent handle. A UDF could reproduce it, but then the budget/elision semantics live in the UDF, i.e., outside SQL again.

**(f) Recognized-query fast paths share the planner**: ObserveEngine's named methods (runs/run_meta/timeline/left_heavy/top_functions/recent_calls, engine.rs:58-371) and BQL read the SAME cached CctFold via `fold()`/`names()` accessors (engine.rs:380-391); frames are LOD-bounded (coarsen_bands power-of-2 merges, left_heavy pixel-width halving, FLAG_LOD_DEGRADED; engine.rs:263-347) so "a month-long session costs the same viewport frame as a short one". A SQL surface would be a *second* execution path beside these UI paths (they can't be SQL — they're pixel-width/LOD-parameterized), forfeiting the "one engine" property (design §9.2: "both go through the same planner").

**(g) wasm-compilability**: bex_query deps are base64, bex_events, prost, rustc-hash, serde, serde_json, memmap2 behind `native` feature (Cargo.toml) — all already in the lockfile; bex_events+bex_engine check clean on wasm32-unknown-unknown (IMPLEMENTATION.md:746-751); §5.12 wasm CCT embedding emits identical segment bytes for the wasm ObserveEngine (IMPLEMENTATION.md:585-589). Values hydration is cfg-gated native-only today (values.rs:299 `#[cfg(not(target_arch = "wasm32"))]`) — a real current limitation.

**SQL-executor embedding costs (steelman-honest):**
- **DuckDB embedded**: could read Parquet *exports* zero-effort, and its Arrow interop matches the deliberately Arrow-viewable sealed columns (design.md:575). But: native static lib is tens of MB; duckdb-wasm is multiple MB compressed on its own — the total gzip ceiling for ALL of bridge_wasm is 4.5 MiB with 4.4 MiB already used. Reading the live/native format still needs a custom extension embedding the fold. Freshness: exports/materialization only; no live mirror. Maintenance: a C++ build dependency in a pure-Rust workspace with byte-frozen golden formats.
- **ClickHouse-local (chDB)**: hundreds-of-MB binary class, no wasm story — disqualifying locally; the repo's plan is the inverse direction (compile BQL's aggregate subset TO ClickHouse for cloud, design.md:849).
- **SQLite + virtual tables**: cheapest (~1 MiB amalgamation, wasm-able); virtual tables over the fold are feasible. But every table's rows still come from the Rust fold; SQLite adds no columnar exec, no typed remedy channel, no footer channel, no budget semantics — it would replace only the parser/planner (~700 of 2558 lines) while adding FFI + a second query semantics to document. Studio design does adopt SQLite — but as a rebuildable *catalog/index*, explicitly "a projection, not canonical evidence" (studio-design:281, 1030, 1131).
- **DataFusion**: the design's own scored alternative; ~2-4 MB compressed (design.md:750), pure Rust, wasm-plausible — the strongest alternative. Still needs custom TableProviders wrapping the fold; still no mandatory-footer/fail-closed channel without wrapping every result (at which point the wrapper IS the product surface and SQL is an internal detail costing megabytes).

## 3. Behavior partition: no-SQL-equivalent vs trivially-SQL
**No natural SQL equivalent (the trust contract, §8.4 "mandatory, not opt-in"):**
- Typed fail-closed E_NO_EXACT_SOURCE gating: SQL's honest answer to "no exact source" is an empty result set — precisely the "silent-empty" agent hazard the judges scored against SQL (design.md:750). BQL raises a typed error naming three remedies (bql.rs:2328-2334, 2390-2395).
- E_MULTI_RUN_CTX fail-closed coercion (bql.rs:1599-1606): SQL would silently aggregate across runs.
- Footer-on-every-result: SQL result sets have no metadata side-channel; completeness would be a second query or a convention — opt-in by construction. BQL's footer is computed from the scan facts of the blocks actually touched (sealed/torn from ScanEnd, cct.rs:194-201) and is structurally unskippable (BqlTable carries it; the wire frame reserves the meta row even for empty results, bqf1.rs:57-68).
- Byte-budgeted partial hydration returning descent handles (get() + canon::DecodeBudget elided CIDs, values.rs:315-330, footer note bql.rs:1949-1952).
- live() streaming frames: designed (§8.3) but NOT built as a BQL sink; the live property is delivered by /api/obs named-method subscriptions (250ms tick, epoch-change-only, one-in-flight, LOD-bounded ≤4 MiB frames) over the live-mirror — a push model with per-frame data-epoch stamps that SQL polling over materialized tables cannot match for same-process runs (it's ahead of group commit).
- Degradation accounting (percentile mean-fallback counted per row into the footer, bql.rs:1449-1456).
**Trivially SQL (conceded):**
- `top(k, by=m)` = ORDER BY m DESC LIMIT k; `where(metric op v)` = WHERE; `sort` = ORDER BY; `limit` = LIMIT; `rollup(by=fn)` = GROUP BY function_id with SUMs (modulo histogram-merge, which needs an aggregate UDF); `stats()` = one-row aggregate; `stats(by=cid)` = GROUP BY cid ORDER BY count DESC (bql.rs:2023-2072 is literally a hand-rolled GROUP BY); `runs(last=24h, status=x)` = WHERE over the runs table; `vdiff` ≈ JOIN a ON b USING(input_cid) with row_number for the multiset first-match semantics; `calls(fn=glob)` = LIKE/GLOB. **The as-built where() is weaker than SQL**: single comparison, no AND/OR, no expressions; sort is single-key; no cross-run aggregation, no joins, no arbitrary projections (`select()` unbuilt). An agent needing "error rate per fn across the last 20 runs" cannot express it in BQL v1 at all — SQL expressiveness is a real loss, mitigated only by the (unimplemented) Parquet export hatch and the planned ClickHouse compilation for cloud scale.

## 4. LOC / complexity honest accounting
- bex_query src total **5,062 lines**: bql.rs 2,558 (lexer ~220 + parser ~180 + planner ~660 + executor/materializers ~1,420, incl. ~70 test lines), values.rs 567 (value listing + budgeted hydration + legacy prost mirror), cct.rs 567 (THE fold), engine.rs 467, bqf1.rs 386 (wire), source.rs 270 (sans-io plane), runs.rs 221, lib.rs 26. Tests: 1,308 lines (bql.rs 911 + fold.rs 397) + inline units. Host glue: obs_ws.rs 945, q_command.rs 215. So the *entire query product* — language, planner, executor, wire format, three source backends, fold, live mirror, WS server, CLI — is ~7.5k lines of dependency-free-beyond-lockfile Rust.
- The BQL-specific increment over what any SQL approach would ALSO need (fold, sources, wire, hydration ≈ 2,000 lines) is bql.rs's ~2,500 lines. That is the honest price of the DSL: ~2.5k lines vs linking DataFusion (2-4 MB compressed, wasm-risky), DuckDB (blows the 4.5 MiB gzip ceiling outright; C++ dep), chDB (no), or SQLite (~1 MiB, but keeps all the Rust and adds FFI + a second semantics).
- Maintenance surface: BQL has zero external-engine version churn; the grammar is ~15 stages with plan-time arg validation; the TS wire decoder is ~150 lines (bqf1.rs:23). Counter-cost: every new capability (series, diff, boolean where) must be hand-built — SQL would have given them free; REMAINING P7/P8 lists confirm this backlog is real (IMPLEMENTATION.md:652-654, 702-704).
- Perf context making the custom path credible: open+first-frame 2.62 ms vs legacy 1,654.7 ms (632×, C6, IMPLEMENTATION.md ledger:808); left_heavy frame 304 B vs the measured 2.21 GB JSON wire pathology (IMPLEMENTATION.md:450-451); constant 34.3 MiB peak RSS over a 256 MiB corpus (C7, ledger:809); full e2e `baml q 'ctx() | top(5, by=total_ns)'` answers with names/percentiles/footer on a 400k-call run (IMPLEMENTATION.md:614-620).

## 5. Steelman residue (what a decision doc must not hide)
1. The agent-lens judges preferred SQL; the DSL won on trust-machinery + size-gate grounds, not expressiveness (design.md:750).
2. The Parquet/DuckDB escape hatch that justified bounding BQL's expressiveness is not yet implemented (no export stage in STAGE_LIST).
3. BQL v1's relational power is far below SQL (single-comparison where, no joins/series/diff/multi-run); the §8 design closes much of this gap but it is unbuilt.
4. The trust contract is partially delivered: footer+typed errors+budgets are real; snapshot pinning, E_BUDGET cursors, --schema, caret spans are not.
5. SQL is not banished from the architecture — it is compiled-to (ClickHouse, cloud) and used as rebuildable local projection (SQLite/DataFusion in studio design) — the actual decision is "SQL as backend, never as the semantic contract" (studio-design:422-430).
6. Values hydration is native-only today (wasm cfg-gate, values.rs:299); the wasm ObserveEngine host is REMAINING P8.
