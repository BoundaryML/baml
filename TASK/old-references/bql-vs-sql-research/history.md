# SQL-vs-BQL decision history, reconstructed from TASK/design.md

## 1. The competition, the losing designs, and §8.6 grafts

**Process** (design.md:750, §8 opening): three candidate query surfaces were "designed competitively": (a) **SQL over DataFusion virtual tables**, (b) **a purpose-built pipeline DSL** (became BQL), (c) **a BAML-native stdlib API**. Scored by three judges under three lenses:
- pipeline DSL won **human-dev lens 8.5** and **implementer lens 8**;
- **agent lens preferred SQL at 8.5** — but "conceded that the DSL's trust machinery, made mandatory, resolves SQL's worst agent hazards (silent-empty results, opt-in completeness)" (design.md:750).
- **The decisive argument was implementer-structural, not linguistic**: `bridge_wasm` ships under an enforced gzip size gate (4.5 MiB absolute ceiling in `.cargo/size-gate.toml`, 3% delta guard over a 4.4 MiB committed baseline); "embedding DataFusion (~2-4 MB compressed alone) is disqualifying, while the pipeline engine is small hand-rolled Rust over deps already in the lockfile" (design.md:750). Adversarial note for the synthesizer: this kills *DataFusion-in-wasm*, not SQL-the-language — a hand-rolled SQL subset was not scored as a fourth option; the doc does not record why "small hand-rolled SQL" wasn't considered, only "small hand-rolled pipeline DSL" vs "full DataFusion".

**Decision** (design.md:752): "one query engine (`bex_query`), one primary surface (BQL)… everything else a wrapper or an export." Driven by principle #7 "One engine, one wire… There are not two data planes" (design.md:109) — the same engine must run native + wasm for CLI, web app, playground, VSCode, MCP agents (design.md:762, §5.12:522, §9.2).

**§8.6 grafts FROM the losing designs** (design.md:844-855):
- From **SQL**: [launch] `cct_hist` histogram blocks in storage — "from SQL's `dur_hist` column" (design.md:848; implemented as block kind 9, §6.3:596, justified at :602: p95/p99 "unanswerable retroactively from sums"; also §2.5 req 2:186 and §8.3:793). The SQL design's schema thinking survived into the storage layer even though its language lost.
- From **SQL** (implicitly — the cloud aggregate path): [launch] **BQL→ClickHouse compilation of the aggregate subset**, prototyped before the cloud query API freezes, with "a golden corpus in CI diffing local vs ClickHouse results" (design.md:849). I.e., a SQL engine *is* the cloud backend; BQL is compiled to it.
- From **baml-native stdlib**: typed hydration `get(as=MyType)` / `baml obs hydrate <cid> --type T` (design.md:850), and "the layering endgame: once `bex_query` is proven, wrap it as a thin `baml.obs` stdlib module (one engine, two surfaces) — deferred, not v1" (design.md:854, OQ6:1042).
- Unattributed grafts from the judging: `failure()` evidence-bundle source (:851), parameterized query files + user lookup tables (:852), `critical_path()` typed as EventSet-in so `E_NO_EXACT_SOURCE` gates it honestly (:853), the playground 60fps viewport as a recognized-query fast path inside the same engine — "not a second API" (:855).

**Rejected from the losers**: DataFusion embedding (size gate); SQL as primary surface; the SQL design's opt-in completeness and silent-empty semantics (:750); a stdlib API as the v1 primary (deferred to wrapper); any second data plane (:109, R7:1059 kills the CctPatch→run-store plane).

## 2. Escape hatches (the design's own hedge against BQL's bounded expressiveness)

- **Parquet export = "unbounded-expressiveness escape hatch"**: "sealed segments export to Parquet so DuckDB/DataFusion work *outside* the product" (design.md:752); `export(format=jsonl|parquet)` is a v1 sink (design.md:791). Enabled structurally: BCCT columns are "contiguous fixed-width little-endian arrays, 8-byte aligned, so a zero-copy Arrow `ArrayRef` view over the mmap gives Arrow interop (and Parquet export) without the Arrow container" — "Arrow/Parquet are export codecs" ruling (design.md:575). So full SQL is deliberately available, just not *inside* the bounded product surface.
- **BQL→ClickHouse compilation** of the aggregate subset, [launch]-tagged (design.md:849), scheduled P8 (:1016) as the "forcing function" for the cloud upload protocol / ClickHouse schema (OQ5:1041). IMPLEMENTATION.md:704 still lists the "ClickHouse compilation prototype" as pending work.
- **Golden corpus diffing local vs ClickHouse in CI** (design.md:849) — the mechanism that keeps one-language/two-engines honest.
- Adversarial reading: the design concedes SQL twice — histograms adopted from SQL's schema, and the cloud tier *is* SQL (ClickHouse) with BQL as a compile-target frontend. The steelman for SQL is therefore strong at the aggregate tier; BQL's non-negotiables live in the exact/value/trust tiers (below).

## 3. Trust contract (§8.4) + typed sets (§8.2): what is language-bound vs not

**LANGUAGE-level (any language, incl. an SQL dialect, could adopt by convention):**
- Human literals `24h`, `64kb`, `yesterday` and path patterns compiled inside string literals (design.md:793).
- Self-description: `baml q --schema` one-JSON-document bootstrap + language service from the static stage registry (§8.4.6:802). SQL has information_schema; equivalent in kind.
- Empty-is-explained (§8.4.4:800) and ready-to-paste corrected queries (:799) — error-UX, not type theory.

**SCHEMA/ENGINE-level (SQL engines could enforce these too; nothing about pipelines required):**
- Completeness footer `meta = {complete, watermarks, capture_loss[], …}` "computed from the blocks the query actually touched" (§8.4.1:797) — an envelope/protocol feature. SQL result sets have no standard side-channel for it, but a wrapper could add one; the design's real claim is that it's *mandatory not opt-in* (the agent judge's concession at :750 was exactly that mandatory trust machinery neutralizes SQL's advantage).
- Bounded by construction: implicit 1000-row default limits, 64 KiB `get()` budgets, keyset cursors over decoded ULID payloads, `E_BUDGET` as a navigation hint (§8.4.2:798). Engines can impose quotas on SQL; SQL-the-language just defaults to unbounded.
- Snapshot pinning `--snapshot W` bit-identical re-runs (§8.4.5:801) — engine snapshot isolation, cf. `AS OF`.
- `E_MISSING_BLOCK` ("never decode a partial value as whole", :799) — storage-integrity, engine-level.

**Genuinely type-system-bound (the load-bearing BQL-only claims):**
- **The CtxSet/CallSet split "encodes the capture contracts in the type system"** (design.md:780): CtxSet is keyed logically by (revision_id, function-id path) over CCT delta segments; CallSet is exact instances backed *only* by recent-call ring / flight dumps / full traces (§8.2 table:766-778). "Aggregates are always available; exact instances exist only where an exact source covers the scope, and `instances(source=...)` is the honest gate — it raises `E_NO_EXACT_SOURCE` naming remedies (arm flight recorder / `@capture` / bounded trace) **instead of returning zero rows**" (:780). In SQL these are just two tables, and scanning an uncovered exact-calls table *correctly* returns empty under SQL semantics — the honest-gate behavior would violate SQL's own contract for a table scan. This directly answers the §3 capture-contract table (aggregate mode intentionally does not promise per-call data, :201) — the language's types mirror the capture modes.
- Only **two implicit coercions** (RunSet→CtxSet, X→Table, :779-780) — plan-time signature checking per stage (:766) makes aggregate/exact confusion inexpressible rather than detectable.
- `E_REVISION_MISMATCH` — ctx ids across revisions without `align=fqn` (:799) is a plan-time check encoding §4.4's "(revision_id, function_id) is the only scope in which function_id means anything" (:359); SQL would happily join function_ids across revisions.
- `E_STAGE_INPUT` / `E_UNKNOWN_FIELD` (lists valid fields for the *kind*, :799) — per-set-kind field vocabularies.
- `critical_path()` typed EventSet-in so the exact-source gate applies (:853).
- **As-built confirmation**: bql.rs implements exactly this shape — v1 ships three kinds (RunSet, CtxSet, Table) with the two coercions (bql.rs:5-7), the mandatory §8.4 footer (bql.rs:126, 202-212), `E_NO_EXACT_SOURCE` raised at plan/exec time (bql.rs:1299, 2330, 2391), fail-closed multi-run coercion (bql.rs:1560-1615).

## 4. §2 user stories that constrain the language choice

The **AI agent persona (§2.3) is the explicit sharpener**: "results must be structured and bounded (an agent cannot skim a million rows), IDs stable across queries, completeness machine-checkable before the agent commits to a conclusion, and the highest-stakes workflow — *verify my own fix* — a first-class operation" (design.md:153). Mapped to stories:
- P0 bounded paginated run index with stable ULID ids (:157) → §8.4.2 keyset cursors + §2.5 req 7 (:191, ULIDs sort by raw payload, *not* string form — cursors decode).
- P0 byte-budgeted value fetch "with child CIDs for selective descent" (:158) → `get(max_bytes)` + `E_BUDGET`-as-navigation (§8.4.2:798, §7.4:735).
- P0 Merkle short-circuit diff by CID (:160) → CID as query primitive (§2.5 req 6:190, duplicate-prompt query :831).
- P0 "Verify my own fix… with an explicit completeness verdict" via `diff` + `compare(match_io)` (:161, representative query :827-828) — a first-class stage, not a join idiom.
- P1 "Check capture completeness before trusting any conclusion — mandatory result meta footer" (:164) → §2.5 req 4: "Completeness is part of every answer… 'No data' is always distinguishable from 'no events'" (:188) → §8.4.1 mandatory footer.
- §8.7 (:859): the meta footer + fail-closed errors "are what make autonomous use safe"; agents cite `(query, snapshot)` pairs as re-verifiable evidence (§8.4.5:801).
Non-agent stories also bind: operator P0 "Trust the data: explicit loss markers, never silent truncation" (:142); the wasm hosts (VSCode/browser, §3.2:224) force the engine into wasm, which is what makes the DataFusion size argument decisive. Note the irony the synthesizer should keep: the agent persona *preferred SQL* (:750) — the agent requirements were satisfied by making trust machinery mandatory in the DSL, not by picking the agent judge's winner.

## 5. What a SQL engine would need to query this storage AT ALL (§6.x)

The storage is a custom WAL-shaped container, not tables:
- **BCCT container** (§6.2:573-581): custom `BCCT` framing, per-block CRC + commit markers, torn-tail recovery, active-tail block-scan vs sealed footer-index protocol. "The active role needs… a WAL's requirements, which Arrow IPC does not provide" (:575). SQL access requires either custom table functions/virtual-table providers per block kind (what the losing DataFusion design proposed) or materialization to Parquet (the actual escape hatch — *sealed segments only*; live/active tails have no Parquet form).
- **Delta/checkpoint/hist fold** (§6.3): current state = last kind-8 `node_total` checkpoint + kind-1 `cct_delta` rows since it (checkpoint-by-bytes cadence, :604); percentiles = fold kind-9 `cct_hist` 16×u32 bucket arrays across windows then interpolate (:596, :793). In SQL every query re-implements the checkpoint-anchored fold and array-summing aggregation (ClickHouse can, natively — hence it as the compile target; stock SQL needs UDAFs). BQL bakes the fold into the engine once.
- **node_birth parent-chase** (§4.6:386, §6.3 kind 2:590, §8.2:771): node ids are dense, **session-epoch-scoped**, restart per epoch, "meaningless outside" their session dir (:571); a CtxSet row's logical key (revision_id, function-id path) is resolved "at fold time via `node_birth` parent-chase" (:771). SQL equivalent: recursive CTE over parent_node_id *per session epoch*, then re-key to paths before any cross-epoch/cross-session GROUP BY; path patterns (`main>>handle_request>extract_*`, :793) become recursive-CTE + string matching. Boundary attribution is another indirection: delta rows carry no boundary column — join through `partition_bind` blocks (kind 5:593, ruling :567).
- **Cross-revision joins**: dictionary alignment `definition_key` + `def_content_hash`, "computed on read", no local alignment table (§4.4:353-358) — SQL needs the `.bamldict` protobuf loaded as a dimension table per revision; the design says only "the cloud materializes the definitions table at ingest" (:358) — i.e., SQL gets this *after* ETL, which is exactly the ClickHouse plan.
- **CAS value DAG** (§7.4): BLAKE3 CIDs over canonical node bytes, chunked at 128 KiB/128 entries, stored in append-only packs with fanout indexes (§6.7:641-643); hydration is byte-budgeted with child-CID handles for selective descent, `readValue` the only hydration path (:735). Bounded Merkle descent with resume cursors is not expressible as a SQL scan; it needs procedural UDFs — BQL's `get()`/`vdiff()` are these, first-class.
- **Live + wasm**: `LiveMirrorSource` reads the consumer's in-RAM active delta blocks, identical format RAM/disk (§9.2:886); the engine is **sans-io** (`Poll::NeedData{ranges}`) precisely because "this is the only model that works identically for native mmap, wasm linear memory… and HTTP Range requests, without an async runtime in wasm" (:876) — DataFusion's async scan model doesn't fit any of the three hosts.
- **Completeness accounting**: the footer is "computed from the blocks the query actually touched" (:797) — watermark blocks (kind 4:592) and marker blocks (kind 12:599) must be consulted *alongside* every data scan; a SQL engine has no mechanism to force every query to join its own scan against the watermark/loss stream.

**Summary shape for the decision doc**: SQL lost on (a) wasm binary size (the only argument called "decisive"), (b) agent-safety defaults being opt-in in SQL semantics vs structurally mandatory in typed pipelines, (c) storage that is a WAL+DAG needing engine-owned folds/descent that SQL would wrap in UDFs anyway. SQL won concessions: histogram schema in storage, ClickHouse as the cloud aggregate engine (BQL compiles to it), and Parquet/DuckDB/DataFusion as the explicit unbounded-expressiveness hatch. The genuinely non-SQL-replicable core is the typed-set encoding of capture contracts (E_NO_EXACT_SOURCE instead of empty scans) plus the mandatory per-query completeness footer.
