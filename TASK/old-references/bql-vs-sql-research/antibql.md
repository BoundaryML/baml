# Attack on the pro-BQL case: ranked objections

Verification note: I independently verified the load-bearing factual claims against repo files (cited inline). Three notable corrections to the research packet itself: (a) the size-gate file is at `baml_language/.cargo/size-gate.toml`, not `.cargo/size-gate.toml` as design.md:750 and the research both cite; (b) the doc-comment on `BqlError` (bql.rs:41) lists only 5 error codes and omits `E_NO_EXACT_SOURCE` even though it is raised at bql.rs:1299, 2330, 2391 — the flagship trust feature is already drifting from its own inline docs; (c) studio-design.md:428 contains a raw typo ("need domain semantics;g") in the very passage the decision doc will quote as the anti-SQL rationale.

## Objection 1 (strongest): The decision's provenance is unauditable, and the product's own primary persona voted for SQL

The entire "competitive bake-off" exists only as a paragraph in the winning design. design.md:750 self-reports the scores; the losing SQL design, the judge transcripts, and the rubric are confirmed absent: IMPLEMENTATION.md:25-26 — "Prior docs referenced in design Appendix B ... are NOT in the repo. TASK/design.md is the only spec." Worse, the lens that lost — agents, SQL at 8.5 — is the persona §2.3 calls the product's sharpener and §8.7 calls the reason the trust contract exists. The decision doc will cite a competition whose only record was written by the winner and whose target-user judge preferred the loser.
**Refutes it:** producing the original candidate designs/judge transcripts, or a fresh measured eval (agent task-success writing BQL-from-schema vs SQL-over-materialized-tables). Note the honest partial defense: the concession clause at design.md:750 ("the DSL's trust machinery, made mandatory, resolves SQL's worst agent hazards") is at least recorded contemporaneously.

## Objection 2: The "decisive" argument kills DataFusion-in-wasm, not SQL-the-language — a hand-rolled SQL subset was never a candidate

Verified: `baml_language/.cargo/size-gate.toml` sets `max_gzip_bytes = "4.5 MiB"` with `policy.max_delta_pct = 3.0` for `bridge_wasm`, and the committed baseline is `gzip_bytes = "4.4 MiB"` (`.ci/size-gate/wasm32-unknown-unknown.toml:7`). Real constraint, ~100 KiB headroom. But the scored SQL candidate was "SQL over DataFusion virtual tables" (design.md:750) — the size argument disqualifies the *engine*, not the *syntax*. The actual shipped alternative is ~2,558 lines of hand-rolled lexer/parser/planner/executor (bql.rs, verified line count); a hand-rolled SELECT-subset parser over the identical fold/engine would be comparable LOC and identically wasm-safe. The doc never records why "small hand-rolled SQL subset" wasn't the fourth candidate. Additionally the gate binds only `bridge_wasm` — one host — while the studio design plans native DataFusion/SQLite locally anyway (studio-design:1156), and the cloud tier compiles BQL to ClickHouse SQL (design.md:849). Calling binary size "decisive" for the whole product surface is an overreach.
**Refutes it:** an argument that the genuinely non-syntactic wins can't wear SQL syntax — i.e., that `E_NO_EXACT_SOURCE` on an uncovered scan *violates SQL's own semantics* (an empty table scan correctly returns zero rows), so a "SQL" that fail-closes isn't SQL and forfeits the familiarity dividend, which is the pro-BQL argument the doc should make *instead of* the size gate. Sentry's SnQL shows restricted-SQL-with-enforced-bounds ships at scale, so this refutation needs to engage with why SnQL-shaped wasn't chosen.

## Objection 3 (internal contradiction): The org has TWO bespoke query contracts, each claiming canonicity, mutually unaware — "BQL over SQL" is really "two proprietary languages over one standard"

Verified by grep: zero occurrences of "BQL" in `TASK/studio-design/baml-studio-design.md`; zero occurrences of "StudioQueryV1" in `TASK/design.md`. Studio locks "StudioQueryV1 is the local/hosted/agent contract | no physical SQL or formatted text dependency" (studio-design:3613) — "no formatted text dependency" arguably excludes a typed text DSL like BQL too. Studio prescribes Arrow/DataFusion for local scans (:1156); design.md disqualifies DataFusion (:750). Studio has caller-selected coverage modes, deferred scans, structured value paths; BQL has none of these. The maintained-surface inventory under "BQL over SQL" is: BQL grammar + BQF1 wire + StudioQueryV1 JSON AST + BQL→ClickHouse compiler + golden cross-engine equivalence corpus + internal SQLx/ClickHouse SQL. SQL-first collapses most of this. A decision doc that concludes "BQL over SQL" without resolving BQL-vs-StudioQueryV1 resolves the wrong dichotomy — both docs already agree raw SQL isn't the contract (design.md:750-752; studio-design:424-432, verified).
**Refutes it:** a written unification commitment with an owner — e.g., BQL's typed `PlanStage` AST becomes the serialized StudioQueryV1-shaped wire form (they are structurally compatible: both versioned typed ASTs with mandatory scope/budgets/coverage), and design.md:849's pre-freeze ClickHouse prototype as the forcing function. Without that commitment in the decision doc, the objection stands.

## Objection 4: The trust machinery that justified overruling the agent judge is mostly unbuilt

The agent-lens concession was contingent: trust machinery "made mandatory" (design.md:750). As-built, the mandatory footer is `{sealed, torn, first_ts_ns, last_ts_ns, degraded[]}` (verified bql.rs:128-141) versus the designed `{complete, watermarks, capture_loss[], sources_consulted, truncated, next_cursor, warnings, snapshot}` (design.md:797). Unbuilt and confirmed REMAINING: `--schema` self-description, snapshot pinning, MCP tool, series/delta/diff, events/dumps stages (IMPLEMENTATION.md:652-654); ClickHouse compilation prototype (IMPLEMENTATION.md:704). The Parquet export escape hatch that justified bounding BQL's algebra is also unimplemented — verified STAGE_LIST at bql.rs:805 is `runs, run, ctx, calls, errors, rollup, where, sort, top, stats, limit, values, get, instances, vdiff`; no `export`. So the decision doc would be defending BQL with features SQL was rejected for lacking — that don't exist yet either.
**Refutes it:** shipping `--schema`, snapshot pinning, MCP, and export before or alongside the doc; or scoping the doc's claims to as-built (typed errors with remedies, E_NO_EXACT_SOURCE at three sites, footer-on-empty-results via BQF1 meta row — these ARE real and verified).

## Objection 5: BQL v1's algebra is below SQL and below the product's own requirements checklist

As-built: `where()` is a single comparison — no AND/OR/expressions; single-key sort; no joins, no window functions, no cross-run aggregation, no projections. "Error rate per fn across the last 20 runs" is inexpressible. Against studio's own capability checklist: nested value-path predicates (§3 row 8, "email ends .edu") — absent; application-context/tag/user/session dimensions (§5.7) — absent from the entire data model; top-level-enum-variant value queries — absent. SQL gives all of these for free, and the flagship agent stories are *more* fluent in SQL (verify-my-fix = join on input CID; dedup = GROUP BY cid — the CAS design manufactures SQL's favorite primitive, a content-addressed join key). The stated mitigation — export to DuckDB — simultaneously (a) doesn't exist and (b) exits the trust envelope entirely, which indicts the safety rationale: the hardest queries get handed to exactly the surface (raw SQL) with none of the rails.
**Refutes it:** evidence that the bounded set covers the actual query distribution (the profiler precedent — pprof/Parca ship fixed folds, no language at all — cuts this way); plus a committed roadmap for boolean where, series/diff, and path predicates. But note the profiler precedent cuts against building a big DSL too, not just against SQL.

## Objection 6: Permanent agent-unfamiliarity and ecosystem-isolation tax

LLMs carry massive SQL priors and zero BQL priors; every session bootstraps from a schema doc (unbuilt). No Metabase/Grafana/dbt/notebook/warehouse integration, ever, except through the (unbuilt) export. Industry arc is DSL-first vendors adding SQL under customer pressure (Datadog DDSQL); studio-design itself hedges the same way ("a later tenant-dedicated SQL capability", :2805). PromQL/TraceQL succeeded as *ecosystem standards* — a network effect a single-vendor DSL won't have.
**Refutes it:** measured agent round-trip data showing typed corrected-query errors (`BqlError.remedy`, verified bql.rs:38-44) outperform SQL's silent-empty/hallucinated-column failure modes — plausible, but currently asserted, not measured. TraceQL/LogQL precedent for tree-structural operators is the strongest external support.

## Objection 7: The language debate papers over the real fault line — per-call schema vs CCT aggregates

Studio's contract assumes per-observation terminal rows; design.md's core thesis abandons per-call events (38.5 TB/day). "List recent failed observations" is unanswerable from CCT aggregates outside exact-evidence windows regardless of query language. Choosing BQL doesn't fix this; a "BQL over SQL" conclusion lets the doc claim resolution while the data-model divergence — the thing that actually determines which questions are answerable — stays open.
**Refutes it:** an explicit statement that studio's observation rows are a cloud-ingest projection of exact-window artifacts with coverage-honest gaps, i.e., BQL's CtxSet/CallSet split and studio's coverage reasons are the same contract in two vocabularies (they are — this is genuinely reconcilable, but must be written down).

## What survives the attack (so the doc isn't strawmanned)

Three pro-BQL claims verified and genuinely hard to refute: (1) fail-closed capture-contract typing — E_NO_EXACT_SOURCE with named remedies instead of empty scans is semantically incompatible with SQL table-scan contracts (bql.rs:2328-2334, 2390-2395); (2) the footer travels on every result including empty ones via the reserved BQF1 meta row — structural, not conventional; (3) the sans-io Poll/NeedData engine running identically over mmap/wasm/HTTP-Range has no off-the-shelf SQL-engine equivalent. The honest decision-doc framing is: "restricted semantic surface over a custom engine, with SQL as compile target and export format" — and the surface's *syntax* (pipes vs SELECT vs JSON AST) is the weakest-evidenced part of the whole decision.
