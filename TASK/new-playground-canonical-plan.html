New Playground Architecture

A committed design for a clean, low-entropy, performant playground that integrates with BEX tracing/profiling, preserves current user-visible functionality, and leaves room for future features without keeping legacy event reconstruction alive.

1. Executive Summary

The new playground must stop reconstructing execution semantics in TypeScript. The canonical execution state belongs in Rust, behind a RunStore keyed by RunId. The browser renders snapshots and patches. Native LSP, Node/TypeScript, Python, Go/Ruby/CFFI, and WASM are adapters around the same runtime model, not separate owners of execution state.

The design is intentionally aggressive about deletion. We do not need backwards compatibility with the current playground runtime-event protocol. The legacy browser-side RuntimeEvent decoding, span guessing, fake RunEntry model, and "attach to the only active call" heuristic should be removed before the new implementation becomes the public path. This summary is intentionally not the deletion checklist; the canonical file/symbol disposition lives in the §20 ledger.

WASM remains a supported runtime target because BAML must work in deployment environments such as Cloudflare Workers and in browser-only surfaces where no native process exists. That does not make WASM a separate architecture. WASM must implement the same run model and must be able to emit the same .bamlprof artifact format as native, returning bytes or chunks to its host instead of depending on native file IO.

Core decision: RunStore owns observable execution state. Project metadata, session settings, test catalogs, VFS/editor state, and static analysis remain outside RunStore.
Correction from review: Test discovery is not tracing and should not be forced through RunStore. Test execution is a run. The test catalog belongs to project state.

2. Design Principles

Minimal Surface Area

The browser should not receive raw profiler/protobuf details. It should receive normalized run snapshots and patches. The protocol should be small and domain-shaped.

Low Entropy

There should be one owner for execution state. Do not let Rust, websocket broadcast, the worker, and React each maintain competing run models.

Rust-Canonical State

BEX and Rust reconstruction know the runtime structure. TypeScript should render the reconstructed model, not infer call structure from spans or raw events.

Delete Legacy Paths

No backwards compatibility requirement for the old playground event protocol. Build the new path cleanly and remove legacy reconstruction before the new playground is live.

Snapshots Are Authoritative

Patches and websocket delivery are optimizations. A client must be able to recover by asking for a fresh snapshot.

Future Features Fit Naturally

Expected output, human feedback, signal events, annotations, flamegraphs, and timelines should attach as payloads or projections, not new side channels.

The current implementation uses CallId for too many meanings: cancellation, result routing, UI run identity, fetch-log correlation, input correlation, and trace correlation. The new design separates names by responsibility.

Naming rule: Do not expose proto names or profiler names in the playground API. The browser should not see process_euid, engine_id, thread_id, profiler call_id, function_id, legacy spanId, or legacy rootSpanId.

RunId Versus HostCallId Versus CallRef

The subagent correctly observed that today's native and WASM paths already pass a CallId through call setup, cancellation, input, and fetch. That is useful for migration, but it must not become the conceptual store key.

The BEX CallRef is also not RunId. It is runtime trace identity minted after execution enters the VM, when the engine has a thread and call id. A playground run must be able to exist before that root BEX call is known, so RunStore creates an opaque RunId first and attaches the later entry CallRef as the run's root trace reference.

Committed decision: RunStore is keyed by RunId. RunId and HostCallId are deliberately independent from the first implementation: no shared counter, numeric equality assumption, reversible conversion, or RunId-as-sys_types::CallId migration phase is allowed. CallRef stays an opaque trace ref attached with attach_root_trace(run_id, trace_ref).

HostCallId has no required target-neutral integer representation. The native playground adapter can construct it from sys_types::CallId(u64). The WASM bridge can construct it from an adapter-local u32 host-call id, a JS handle, or a private map entry. RunStore stores only the opaque host id inside the active adapter/session namespace; cancellation, result routing, fetch, input, and env attribution go through adapter methods rather than casts, transmute, or numeric comparison. A native value 7 and a WASM value 7 are unrelated unless the same adapter mapping explicitly says otherwise.

Allocation rule: RunStore allocates RunId. Browser clients and host adapters may allocate request ids for request/response correlation, and host adapters allocate HostCallId for runtime plumbing after RunStore has created the run. The host adapter records HostCallId -> RunId before BEX or sys_ops can emit observations. No adapter owns durable run identity, and tests should use distinct id spaces so accidental RunEntry.id == callId behavior fails loudly.

4. Three Stores and One Pipeline

The architecture should not collapse every playground feature into RunStore. The cleaner model has three state-owning stores plus one internal reconstruction pipeline that feeds RunStore.

ProjectStore

Owns language and project metadata.

  • Project list
  • Function list and function capabilities
  • Diagnostics and stale/current state
  • Test catalog and test generation
  • CFG/control-flow graph
  • Cursor context
  • Static env-var names

SessionStore

Owns editor/session-level state and host interaction settings.

  • Env values, overrides, process env import, and resolver policy
  • Connected clients
  • VFS/editor file changes
  • Build/runtime ready state
  • Editor decoration settings and session-level UI plumbing
  • Pending UI dialogs outside any run

RunStore

Owns observable execution state.

  • Run lifecycle and status
  • Run inputs and output/error/cancel state
  • Runtime call tree and timeline
  • Fetch, input, per-run env requests/resolutions, logs, tags, and custom payloads
  • Snapshots, patches, cursors, and diagnostics

Trace/Reconstruction Pipeline

Transforms raw profile events into normalized call/thread projections for RunStore.

  • Native .bamlprof reader
  • Target-neutral .bamlprof encoder
  • Native filesystem profile artifact sink
  • WASM byte/chunk profile artifact sink
  • Trace routing, unresolved-component buffering, and root-component claiming
  • Identity/edge-first reconstruction with timestamp-based timeline projection
  • Call/thread balance diagnostics
  • Timeline and flamegraph projections emitted through RunStore

Store ownership is logical ownership, not a claim that the owner always writes bytes directly. For env values, SessionStore is the only source of truth in memory and on the protocol boundary. Browser localStorage/IndexedDB, native override maps, process/shell env imports, and WASM envVars records are backing adapters, import sources, or mirrors that hydrate and update SessionStore through an explicit storage/redaction policy. UI reducers and RunStore never read those backing stores directly as authoritative env state.

The rule is simple: if it is observable state of an execution, it belongs in RunStore. This includes more than tracing, but less than the whole playground.

7. Target Architecture

The target architecture keeps host/language concerns at the edges and centralizes execution state in Rust. 

Browser UI
  renders Run snapshots and patches
  sends commands: start run, cancel run, respond to input/env

RunStoreClient
  snapshot(run_id)
  subscribe(run_id, cursor)
  list_runs(filter)
  command transport adapter

Native LSP / Node / WASM adapter
  creates ExecutionRequest
  resolves host callbacks
  maps cancellation and responses
  forwards RunStore snapshots/patches

RunStore
  owns Run lifecycle and payload state
  owns cursor stream and recovery semantics
  receives trace reconstruction results

Trace/Reconstruction
  target-neutral .bamlprof encoder
  native filesystem sink / WASM byte-chunk sink
  read_bamlprof -> ProfileEvent
  ProfileEvent -> normalized CallNode tree/timeline

BEX Runtime
  owns VM execution
  owns BEX trace identity
  emits raw profile events
  uses sys_ops for env/input/fetch/etc.

Why This Is Minimal

  • Only Rust reconstructs runtime structure.
  • Only RunStore owns execution state.
  • Only the language adapters know host-specific value conversion and cancellation APIs.
  • Only React owns view state such as selected run, selected call, filters, and collapsed UI nodes.

RunKind is derived from RunTarget and must not be stored independently beside it. The derived kind provides the default visibility, but RunVisibility is a stored per-run field. Function runs normally default to History. Preview and companion runs normally default to Scoped. Internal runs normally default to Hidden or DebugOnly. List and history APIs use RunFilter so scoped previews do not leak into normal run history unless the caller asks for that scope.

ProfileEvent is the normalized structural event consumed by live trace routing and .bamlprof replay. It is not a playground run event and must not contain RunId, HostCallId, raw target ticks, payload values, args, results, or errors. For live ingestion, process_euid, engine_id, and function-table metadata come from engine registration and the profile producer. For artifact replay, the same fields are derived from the .bamlprof header and disk event stream before reconstruction. The normalized event stream always exposes timestamp_ns.

Reconstruction is identity/edge-first. TraceThreadKey is process_euid + engine_id + thread_id, and TraceCallKey is process_euid + engine_id + thread_id + call_id. Same-thread parentage comes from CallFunction.parent_call_id. Spawned-thread causality comes from StartThread.parent_thread_id + parent_call_id. EndFunction and EndThread attach by identity, even if they arrive before the matching start record. Timestamps place nodes on the timeline and compute duration; they do not determine parentage, node identity, or run attribution.

Equal timestamp_ns values are valid. Sibling ordering in the browser is deterministic presentation order, for example by stable node id, thread id, call id, or function name; it is not runtime causality. Do not add a semantic per-thread sequence key to the initial contract unless a later feature needs exact event-tape replay or order-sensitive metadata that identity and explicit edges cannot resolve. Until such a feature exists, ambiguous same-object metadata uses a stable deterministic fallback and emits a diagnostic when needed; it must not corrupt the structural call tree.

StartRunContext is the RunStore/adapter start envelope. It exists after RunStore has allocated RunId and before BEX starts, and it carries request identity, target, project/runtime revision, time anchor, and start/cancellation guard state. RunContext is the internal execution context used by the host adapter and RunStore integration for completion, payload attribution, and trace-root attachment. FunctionCallContext.host_call_id remains separate BEX/sys-op plumbing for cancellation/result routing; it is not RunId, not trace identity, and not persisted into .bamlprof.

ThreadNodeId and CallNodeId are stable, opaque, run-local projections of TraceThreadKey and TraceCallKey. They are never derived from event order, timestamp sort position, vector index, or first-render position. Late starts/ends, replay, reconnect snapshot rebuilds, and attach_root_trace back-fill must upsert the same node id for the same trace key inside the same RunId. The browser receives only these opaque node ids and optional opaque trace handles; it cannot decode process, engine, thread, or profiler call ids from them.

Time contract: fields ending in _at_ms are Unix epoch milliseconds for history, sorting, and display. Fields ending in _at_ns are monotonic nanoseconds relative to the run's RunTimeAnchor.trace_zero_ns; they are for duration/timeline math inside one run and must not be compared across runs without the anchor.

Raw producer records may use target-local ticks only inside the profiler hot path. Native converts ticks to normalized nanoseconds at the profiling consumer/transcode boundary before building ProfileEvent or writing DiskEventV1. .bamlprof replay reads already-normalized event nanoseconds from the artifact. WASM must provide monotonic nanoseconds directly, or the host adapter must normalize its clock to the same timestamp_ns domain before events reach RunStore reconstruction. Zero, raw, or target-local ticks must never leak into ProfileEvent, Run, RunPatch, or browser snapshots.

ProfileEvent.timestamp_ns is the normalized profile-clock timestamp used for timeline placement. Reconstructors convert it to run-relative started_at_ns/ended_at_ns values by applying RunTimeAnchor.trace_zero_ns. Equal or coarse timestamps are valid and may affect only stable presentation order, not call parentage, node identity, run attribution, or payload attachment.

RunSummary.touched_functions is the RunStore-owned successor to the browser's findLatestGraphRun scan. It contains the request target when known plus every normalized CallNode.function_name observed in the reconstructed call tree, including direct and transitive calls. RunStore revises this set through snapshots and patches as reconstruction catches up. The browser must query RunFilter.call_tree_contains_function; it must not rescan raw runtime events to decide which run exercised a graph node.

RunVisibilityFilter::HistoryOnly returns only RunVisibility::History runs. Scope { scope_id } returns only runs scoped to that exact panel/session scope. IncludeHidden is for internal panes that intentionally include hidden and scoped runs, while AllForDebug is reserved for diagnostic tooling and may include DebugOnly runs.

RunRetentionPolicy is owned by RunStore. It is a product/operational policy over the single run model, not a second state owner. Active, waiting, starting, and cancelling runs must not be silently evicted by TTL, byte-budget, or count-based history GC. If capacity pressure prevents a new run from starting, RunStore rejects the start with an explicit error before half-creating a run. If capacity pressure makes an active run impossible to continue, RunStore must complete or fail it through an explicit outcome/diagnostic rather than making it disappear.

Terminal runs may be compacted or evicted according to configured count, TTL, byte, and target-specific history limits. RunSummary is the list/history surface and may survive longer than a full selected-run snapshot. Full snapshots may report SnapshotCompacted, PayloadBodiesCompacted, or Evicted instead of returning heavy bodies. GC must preserve referential correctness: snapshots and summaries must not contain payload ids, call ids, env request ids, diagnostics, or graph overlay references that point to silently removed data without an explicit compacted, truncated, or evicted marker.

Patch windows are bounded by RunRetentionPolicy.patch_window_capacity. A stale, compacted, unknown, or future cursor uses the existing runCursorExpired recovery path and requires a fresh snapshot(run_id). Transport lag does not change retention truth.

CallStatus mirrors BEX FunctionEndStatus plus Running. ThreadStatus mirrors BEX ThreadEndStatus plus Running. A bare (thread_id, call_id) tuple is never enough for durable identity outside one profile artifact. Browser-visible trace refs must be non-reversible run-local handles; the browser must never receive CallRef::encode(), ThreadRef::encode(), or the underlying process/engine/thread/call tuple as public API.

RunPatch is a revision protocol, not an append-only event log. Reconstruction may receive late profile events that revise earlier call or thread nodes after identity/edge reconstruction catches up. Clients see only normal RunPatch cursor order; they do not see unresolved router components, route reservations, or buffering internals. Trace routing contract: Raw and replayed profile events are ingested without a playground RunId. RunPatch Apply Contract

  • RunCursor is scoped to one RunId and increases monotonically for every emitted patch.
  • Every runPatch frame carries both run_id and cursor.
  • RunStore owns the current snapshot and bounded per-run RunPatchWindow.
  • Clients apply patches in cursor order and ignore duplicate (run_id, cursor) patches.
  • Clients track last applied cursor per run; a gap in one run does not invalidate another run's stream.
  • A patch is an upsert/revision over snapshot state, not an append-only delta.
  • subscribe(run_id, None) returns or sends snapshot(run_id), then streams patches after snapshot.cursor.
  • subscribe(run_id, Some(current_cursor)) attaches to live delivery.
  • subscribe(run_id, Some(retained_cursor)) replays exactly the retained missing patches in cursor order, then attaches live.
  • If after_cursor is expired, compacted, unknown, future, or otherwise unrecoverable, the server sends runCursorExpired { run_id, reason } and the client refetches snapshot(run_id).
  • tokio::broadcast::Lagged(n) may trigger resubscription, but the lag count is never the source of truth for missing run cursors.
  • RunDiagnostic is reserved for in-run domain diagnostics such as reconstruction balance violations, not transport recovery.
Recovery rule: Recovery is a RunStore subscription contract. Broadcast fan-out can drop messages, but recovery is computed from the run's retained cursor window and snapshot, never from broadcast lag alone.

Target-Specific Recovery Guarantees

  • Native LSP/websocket, same host process: browser/webview reload and websocket reconnect recover retained runs from server-side RunStore memory through listRuns, snapshot(run_id), and subscribe(run_id, cursor).
  • Native LSP/server restart: in-memory live run state is gone unless that target has explicitly implemented durable RunStore history/profile persistence. Old in-memory RunId values return an expired/missing session or run response; the UI must not show stale browser-cached snapshots as live runs.
  • Browser-only WASM without configured persistence: page reload normally destroys the worker and in-memory RunStore. The UI may show an explicit expired session/history-empty state, but not a fake live run restored from local reducer state.
  • Browser-only WASM with configured persistence: IndexedDB, browser storage, Durable Object, KV/R2, or downloaded/imported .bamlprof artifacts can back RunStore snapshots/artifacts according to the same retention, redaction, and payload-compaction rules. When policy permits env persistence, browser storage or WASM host state backs SessionStore env values through the same redaction/session policy. Those stores are adapters behind RunStore or SessionStore, not parallel env/run models read directly by UI reducers.

Function Run

1. Browser sends startRun(request_id, Function, project, generation, function_name, args) without a HostCallId.
2. RunStore allocates RunId and creates StartRunContext.
3. RunStore creates Pending run from StartRunContext.
4. Host adapter allocates HostCallId for cancellation/result plumbing.
5. RunStore attaches HostCallId to RunId and populates the HostCallId -> RunId lookup.
6. Host adapter enters BEX with RunContext and FunctionCallContext.host_call_id.
7. BEX/profile layer emits structural events into the trace router; these may arrive before root binding.
8. The adapter surfaces the entry CallRef and calls attach_root_trace(run_id, root_call_ref).
9. The trace router claims or reserves the root component, back-fills buffered events, and reconstruction upserts the call tree/timeline by stable trace-derived node ids.
10. sys_ops emit payloads: fetch/input/env/log/custom/tags.
11. The supervised host/BEX wrapper classifies result, error, cancellation, exit, host failure, or panic.
12. RunStore completes the run with exactly one RunOutcome.
13. Browser renders final snapshot.

1. Browser already has a test catalog from ProjectStore.
2. Browser sends startRun(Test, project, generation, test_name).
3. RunStore creates a Test run.
4. BEX calls testing.TestRegistry.run_test with the captured project generation.
5. All runtime payloads go through the same RunStore path.
6. TestReport is stored through the terminal RunResult.

1. Browser requests a prompt/curl/build-request preview.
2. Browser includes the requesting panel's RunScopeId.
3. RunStore creates a Preview or Companion run.
4. RunStore stores parent function + helper/companion target, not a fake history function name.
5. Visibility is Scoped { scope_id } by default.
6. Env/fetch/input/errors are still captured in RunStore.
7. The panel renders from the scoped run snapshot or a derived preview projection.

The compiler-generated companion name such as ${fn}$render_prompt may remain the internal execution target, but it is not the public history identity. History and list views see RunTarget::Preview or RunTarget::Companion; preview panes recover their own runs with RunFilter { visibility: Scope { scope_id }, kinds: [Preview, Companion], ... }.

Cancellation

1. Browser sends cancelRun(run_id).
2. If no HostCallId exists yet, RunStore marks the start guard cancelled and completes the run as Cancelled.
3. If HostCallId exists, RunStore transitions cancellable active states -> Cancelling.
4. Host adapter looks up the adapter-owned HostCallId and its target-specific backing id.
5. Host adapter calls the corresponding native or WASM cancellation primitive, including the pre-active-call registration race.
6. Pending input/env requests are resolved as cancelled/missing through RunStore.
7. BEX drains open calls innermost-first with FunctionEndStatus.CANCELLED.
8. Final runtime outcome transitions through the RunStatus precedence rule.

The host start path must check a RunStore start guard after creating the pending run, after attaching HostCallId, and before entering BEX. Before host identity exists, cancellation prevents host dispatch from allocating or starting a BEX call. After host identity exists, cancellation always routes through cancel_function_call(host_call_id); BEX's pre-cancel reservation covers the window before ActiveCallGuard registers the active call.

12. Tracing and Profiling Integration

The tracing/profiling scratchpad establishes the core BEX identity model: 

CallRef = process_euid + engine_id + thread_id + call_id

The VM owns BEX call identity. The hot path emits compact records. Headers carry metadata. Cold consumers reconstruct meaning later. The playground should reuse that architecture instead of inventing a separate browser-side span model.

Native Path

profile events
  -> ProfileEventEnvelope stream
  -> RunStore trace router
  -> component claim via attach_root_trace
  -> reconstruct claimed component by identity/edges
  -> RunSnapshot / RunPatch
same ProfileEvent stream
  -> target-neutral .bamlprof encoder
  -> filesystem ProfileArtifactSink
  -> .bamlprof header + DiskEventV1 records

WASM Path

profile events
  -> cooperative profile drain
  -> ProfileEventEnvelope stream
  -> same trace router and component-claim reconstruction path
  -> RunSnapshot / RunPatch
same ProfileEvent stream
  -> target-neutral .bamlprof encoder
  -> byte/chunk ProfileArtifactSink
  -> host persistence: R2, KV, Durable Object, response body, browser Blob, IndexedDB

Profile Artifact Requirement

Every runtime target that can execute BAML must be able to produce a valid .bamlprof artifact. Native targets may save the artifact directly to .baml/profiles. WASM targets must expose the same artifact as bytes or chunks and let the host decide where it is persisted.

The core profiler API must not require a native file path. File paths are a native sink detail. Cloudflare Workers, browser workers, and other WASM hosts need an artifact stream they can write to object storage, attach to a response, send to another service, keep in memory for a bounded run, or offer as a browser download.

Proposed Profile Reader and Live Reconstruction APIs

The clean split is that live playground state consumes ProfileEvent streams directly, while .bamlprof is an artifact sink and replay format. Do not make RunStore wait for a finished artifact in order to render live patches. Also do not make WASM pretend it has native file paths just to use the same reader.

This is a proposed API shape, not current code. Today read_bamlprof(path: &Path) is path-only and returns raw file-order DiskEventV1 values; production reconstruction does not exist yet outside the prof_gate.rs tests. The production reconstruction milestone must promote that logic into bex_events::run::reconstruct before live reconstruction APIs or TypeScript graph/timeline cutover are treated as implemented surfaces.

Native keeps the existing path-reading capability as a wrapper. WASM implements bounded byte/chunk persistence and uses the byte or reader API. Both targets feed the same reconstructor and must produce artifacts that the same reader can parse.

Required Reconstruction Rules

  • Every CallFunction should have exactly one EndFunction, or produce a diagnostic.
  • Every StartThread should have exactly one EndThread, or produce a diagnostic.
  • File order is not event order.
  • Build call/thread identity from TraceThreadKey, TraceCallKey, and explicit parent edges, not timestamps.
  • Use timestamp_ns for timeline placement, start/end times, durations, and approximate temporal ordering.
  • Equal timestamp tie behavior is presentation-only and must be deterministic without implying causality.
  • Events that arrive before their parent edge or root binding stay in bounded unresolved components until claimed, expired, or diagnosed.
  • function_id is a compact artifact-local lookup key, not a semantic hash.
  • No semantic hash computation belongs on the hot path.
  • WASM cannot depend on file IO for day-0 visibility.
  • WASM cannot depend on a background thread to drain profile data.
  • WASM profile buffers must have explicit caps, flush behavior, and backpressure or drop diagnostics.

WASM Profiling Prerequisites

WASM profiling parity is not only a byte sink. The shared structural profile path must be split away from native path and thread assumptions before profiling can be enabled on wasm32.

  • prof::pb, prost or generated protobuf dependencies, structural header/event encoding, hand encoding, and raw-record-to-DiskEventV1 transcode are dual-target shared code and covered by a wasm32-unknown-unknown build check.
  • prof::file, Path/File persistence, profile directories, native background consumer threads, and native flush_and_join remain native adapters.
  • read_bamlprof(path) stays a native convenience wrapper over shared bytes/reader parsing; read_bamlprof_from_bytes and streaming reader APIs are the target-neutral reader surface.
  • WASM uses cooperative drain/flush into a bounded byte/chunk ProfileArtifactSink with explicit caps, backpressure, truncation, and dropped-chunk diagnostics.
  • WASM engine metadata and header construction must work through a dual-target in-memory metadata registry or explicit metadata passed to the header builder; register_engine_metadata and engine_closed must not silently no-op when metadata is required for reconstruction or graph/source joins.
  • ProfConfig.enabled may stop forcing profiling off on wasm32 only after cooperative drain, nonzero monotonic timestamp_ns, metadata/header construction, shared protobuf visibility, shared transcode helpers, bytes/reader parsing, and byte/chunk sink support exist.
Current gap: The current BEX profile implementation forces profiling off on wasm32. That is not acceptable for the target architecture if Cloudflare Workers or browser-only execution can run BAML. A cooperative WASM profile drain, target-neutral .bamlprof artifact sink, shared reader, and metadata/header path are required conformance gates before any public WASM playground surface.

15. Language Adapter Pattern

Every language should follow the same pattern conceptually, but not by implementing separate stores. The adapter pattern belongs at the boundary; RunStore remains Rust-canonical. 

Language adapter
  resolves call options
  gets/clones ambient context
  maps cancellation
  encodes values
  calls Rust runtime with ExecutionRequest / RunContext
  receives typed result and optional run updates

Rust Owns

  • RunId allocation.
  • RunStore.
  • BEX trace/profile reconstruction.
  • Payload ingestion.
  • Snapshots and patches.

Language Adapters Own

  • Value conversion to and from host language types.
  • Ambient context propagation.
  • Env/options/tags/client/type overrides.
  • Host cancellation mapping.
  • Typed result casting.
  • Language-native callbacks where the SDK exposes them.

Existing Inspiration

The older SDK architecture has useful pieces:

  • TypeScript uses BamlCtxManager backed by AsyncLocalStorage.
  • Python uses contextvars plus thread-aware context tracking.
  • Generated clients resolve env, tags, client registry, collectors, cancellation, and watchers before calling Rust.
  • RuntimeContextManager carries tags, call stack, env, type-builder overrides, and client overrides.

That is inspiration for call-local context, not a durable run store. The new model should split CallContext from RunStore instead of repeating the old mixed tracing/context storage.

Node / TypeScript

The main TypeScript path should go through Node/native, not WASM. That is cleaner: Node can host the runtime session manager and expose normalized runs to the browser/webview. Node being single-threaded at the host layer simplifies delivery, but it does not remove BEX-level trace/thread identity.

Python / Go / Ruby / CFFI

SDKs do not need independent playground stores. They should be able to opt into run snapshots/events if we expose a developer-facing tracing API later, but the playground initiative should not duplicate state machines in each language.

  • playground_io.rs sends input request/resolved keyed by call_id.

Broadcast Rule

Broadcast is allowed as a delivery mechanism. It is not allowed as the state owner. If a client lags, reconnects, or starts after a run began, it must recover through RunStore.subscribe(run_id, after_cursor), retained per-run patch replay when available, or snapshot(run_id) after runCursorExpired.

18. WASM Path

WASM is a required deployment adapter. BAML must continue to run in environments such as Cloudflare Workers and browser-only surfaces where a native process cannot be assumed. The decision is not whether WASM exists; the decision is that WASM must not fork the playground architecture.

Native/Node remains the preferred host for local playground execution when it is available. WASM exists for Workers, browser-only execution, static demos, offline/client-side inspection, and other no-native-host worlds. Both paths must expose the same run model, snapshots, patches, and profile artifacts.

WASM is not a lesser playground. If the product includes a hosted "try BAML" webpage, web-only editors, or offline/browser demos, those surfaces should be able to use the playground normally through WASM. The sequencing distinction is architectural, not product-scoped: first prove the shared native/Rust reconstruction and RunStore contract, then bring WASM to conformance on that same foundation before exposing the new browser-only surface. Do not preserve the legacy worker event model as the fallback.

Utility Evaluation

WASM is useful as a deployment adapter, not as the architectural source of truth. Its strongest value is keeping BAML compilation, diagnostics, test catalog discovery, prompt rendering, curl preview, and limited browser-only execution available in contexts where a native process cannot be assumed. It is also useful for Cloudflare Workers, demos, hosted playgrounds, web-only editors, and offline/client-side inspection.

WASM is weak as the canonical playground execution path when Node/native is available. It adds a second host callback surface for fetch/env/input/cancellation, cannot rely on native file IO or background threads, and can tempt the browser back into owning execution reconstruction. The plan should therefore treat WASM as an adapter around the same Rust RunStore model, not as a parallel playground runtime.

Profile Artifact Sink

WASM must be able to save profile data, but the core runtime should define "save" as "produce a valid .bamlprof byte stream." The host decides whether those bytes become an R2 object, KV/Durable Object payload, HTTP response body, browser Blob, IndexedDB record, or downloaded file. 

trait ProfileArtifactSink {
  fn write_chunk(&mut self, bytes: &[u8]) -> Result<()>;
  fn flush(&mut self) -> Result<ProfileArtifactRef>;
}

Native implements this as a filesystem sink. WASM implements it as a bounded byte/chunk sink with explicit flush points, size limits, and drop/truncation diagnostics. The artifact format stays the same; only persistence differs by host. Native and WASM both use the shared header/event encoder and shared bytes/reader parser; native path APIs are wrappers, not the core artifact abstraction.

What To Remove

  • Legacy RuntimeEvent proto as the browser execution model.
  • Worker-side runtime event deserialization.
  • Worker-side active-call heuristic.
  • Worker-side fetch/input/env state as canonical run state.
  • Any profiler API that requires WASM to pretend it has native filesystem semantics.
WASM decision: Rebuild the WASM bridge because Workers and browser-only execution are supported runtime worlds. Do not preserve the old event architecture for compatibility, and do not let WASM become a second canonical execution-state owner.

20. Migration and Deletion

The migration should reduce entropy at each step. Avoid running the old and new execution models indefinitely.

The migration builds one final architecture in a testable internal order. Dead legacy variants can be deleted or hard-isolated early when they are not the active execution-structure source, but TypeScript graph, timeline, and runtime reconstruction must not be cut over or removed until production Rust reconstruction feeds real RunStore snapshots. The required dependency chain is schema and context contracts, production bex_events::run reconstruction, RunStore trace routing/root attachment, payload attachment through trace provenance, TypeScript snapshot consumption, browser reconstruction deletion, and then WASM conformance against the same model.

Intermediate checkpoints should prove slices of that final architecture rather than blessing throwaway product states. There is no supported public mode where the browser remains the canonical reconstructor, where WASM is the first proof of the reconstruction model, or where call-level payloads are permanently run-scoped because call reconstruction has not landed yet.

Migration source of truth: The Deletion and Rename Boundary Ledger is canonical for file/symbol disposition. The Safe Demolition Order is canonical for anchored implementation ordering. The Migration Sequence and §22 milestones are coarser planning rollups; they defer to the ledger and safe order whenever wording or granularity differs. All three views must still preserve the same hard gate: browser runtime/graph cutover waits for production Rust reconstruction and trace-routed RunStore snapshots.

Boundaries That Must Stay Intact

  • RuntimePort stays (runtime-port.ts). Replace the Worker/WebSocket implementations, never the external prop boundary. RunStoreClient is created above that port inside the playground package, so ExecutionPanelPane/MonacoEditor/App.tsx wiring does not churn while UI code still gets domain-shaped run methods. The Rust mirror is the Bex trait (bex.rs), renamed in lockstep.
  • Structural vs payload channels stay separate, joined only inside RunStore. The structural channel (.bamlprof DiskEventV1, no values) and the payload channel (args/results/errors/media/logs/fetch/input/env) never re-merge in the browser; RunId owns payloads, and call-level payloads carry internal trace provenance that resolves to CallNodeId or produces an explicit unresolved-provenance diagnostic.
  • Broadcast delivers but never owns. broadcast::channel::<WsOutMessage>(64) is demoted to RunPatch fan-out; RunStore is the single authority and a fresh subscriber recovers through a snapshot plus retained per-run patch replay when possible, or through runCursorExpired and snapshot refetch when not.
  • RunId ≠ HostCallId ≠ CallRef. RunId is opaque playground execution identity allocated by RunStore at create_run(); HostCallId is adapter-scoped cancellation/result plumbing whose backing id may be native sys_types::CallId(u64) or WASM u32/JS state; bex_events::ids::CallRef is runtime trace identity minted after execution starts and attached through attach_root_trace(run_id, trace_ref).
  • Env values in SessionStore; per-run env requests in RunStore. The override store has exactly one logical owner (SessionStore), ending the triple-ownership (playground_env.rs overrides / envAtoms.ts localStorage / wasm envVars). LocalStorage, IndexedDB, native override maps, process env import, and WASM envVars may only hydrate or persist SessionStore through policy; EnvVarRequest/EnvVarFromShell become per-run observations keyed by RunId + EnvRequestId.
  • Browser never reconstructs or decodes proto. The identity/edge-first reconstruction and timestamp timeline projection live only in Rust bex_events::run; runtime-output.ts, deserialize-event.ts, and the two RuntimeEvent.decode sites are removed.
  • File paths are native-persistence only. profile_dir/ProfileWriter::create stay behind the native ProfileArtifactSink; WASM emits the SAME .bamlprof bytes/chunks through the host_dispatch seam.
  • Value rendering + value codec stay decoupled. ResultDisplay/EventValueDisplay/result-renderers/format-value/media-values and the pkg-proto codec (encodeCallArgs/decodeCallResult) consume opaque BamlJsValue and survive unchanged; static CFG layout (convert.ts) and the ring record format (record.rs) and LSP transport (wasm_lsp.rs) are out of scope.

Safe Demolition Order

This ordered list governs migration sequencing. It is more specific than the coarse sequence and milestones below; when those rollups omit a substep or group several substeps together, this order wins.

  1. Isolate the dead RuntimeEvent channel — delete PlaygroundNotification::RuntimeEvent at its source (bex_lsp/mod.rs:167) plus its two forwarding mirrors and the never-constructed WsOutMessage::NextFunctionCallError. Removing a variant with no constructor and only forwarding match-arms is self-consistent; TS still parses but the server stops emitting.
  2. Add opaque RunId newtype in RunStore — pure addition, no callers, deliberately separate from CallRef and HostCallId.
  3. Populate the HostCallId index at startRun — every host call allocation immediately records HostCallId -> RunId before BEX/sys_ops can run. Fetch/input/env ingestion depends on this map; env must stop discarding its sys_op CallId before it can emit per-run observations.

End state: exactly one owner per concept — RunStore (Rust) allocates opaque RunIds and is the single authority for observable execution state; BEX emits structural trace identity as CallRefs, and the entry CallRef is attached to the existing run via attach_root_trace. Migration Sequence

This is a coarse rollup for planning discussions. It intentionally groups file-level work; defer to the Safe Demolition Order for exact ordering and to the ledger for exact symbols.

  1. Define the run/profile contracts: RunId, HostCallId, StartRunContext, RunContext, ProfileEvent, ProfileEventEnvelope, RunCursor, and RunOutcome. RunStore allocates RunId; raw profile events do not carry it.
  2. Promote production Rust reconstruction into bex_events::run and make the shared .bamlprof reader/encoder feed the same normalized ProfileEvent path used by live ingestion.
  3. Wire RunStore trace routing: unresolved components, route reservations, attach_root_trace, stable ThreadNodeId/CallNodeId, retained patches, and native lifecycle completion/cancellation.
  4. Attach payloads through the final model: RunId plus internal trace provenance resolves to CallNodeId; unresolved payloads are bounded pending attachments with diagnostics, not a public run-scoped payload architecture.
  5. Expose startRun, cancelRun, listRuns, snapshot, subscribe, runPatch, and runCursorExpired over the stable RuntimePort transport.
  6. Build TypeScript RunStoreClient and ExecutionStore only for transports that provide real snapshots/patches whose call tree, timeline, payload, input/env, and fetch projections come from RunStore.
  7. Cut graph, timeline, result, fetch, input, env, and log views to Run/RunPatch snapshots; TypeScript renders prepared projections and does not decode raw runtime/profile proto.
  8. Delete legacy TS runtime-event delivery, browser proto decode, active-call heuristics, and graph/runtime reconstruction once compile and grep gates prove no migrated view imports them.
  9. Bring WASM to conformance with the same RunStore, ProfileEvent, .bamlprof, and reconstruction contract before exposing the new public browser-only surface.
  10. Add normal playground breadth on the shared model: test execution as RunTarget::Test, prompt/curl preview as scoped RunTarget::Preview, hosted polish, flamegraph/profile UI, and project-state test catalog support.

21. Invariants

  • RunId is the authoritative playground execution identity.
  • RunStore allocates RunId; adapters allocate only request ids and host plumbing ids.
  • HostCallId is cancellation/result plumbing, not durable trace identity.
  • RunId and HostCallId use deliberately independent allocation from day one.
  • Every run captures the project/runtime generation it executed against.
  • Snapshots are authoritative; patches are optimization.
  • RunCursor is scoped to one run, and recovery uses RunStore snapshot plus retained per-run patch windows.
  • RunStore owns observable execution state.
  • ProjectStore owns language/project metadata.
  • SessionStore owns editor/session configuration.
  • Env backing stores such as localStorage, IndexedDB, process env import, native overrides, and WASM envVars cannot bypass SessionStore as the env value owner.
  • The browser never reconstructs BEX call structure from raw profile/proto events.
  • The browser never sees profiler internals as public API.
  • Every run can exist before its root BEX call is known.
  • Raw profile events and .bamlprof artifacts do not carry playground RunId.
  • Profile events are routed to runs only through HostCallId start attribution plus attach_root_trace component claiming.
  • ThreadNodeId and CallNodeId are stable trace-derived run-local ids, never sort positions.
  • Payloads may be held as bounded internal run-scoped pending attachments before they resolve to a stable CallNodeId; that is not a public degraded payload mode.
  • Call-level args, results, errors, and media use payloads with trace provenance; they are not structural .bamlprof data.
  • Env requests during execution are recoverable from snapshot(run_id) as RunId + EnvRequestId state.
  • Every terminal run has one final outcome.
  • Profile reconstruction can update call/thread structure but cannot infer or seal terminal RunStatus.
  • RunOutcome::Panicked is reserved for supervised host/runtime panic boundaries, not ordinary BAML-level unhandled throws.
  • Cancellation is not the same as failure.
  • After HostCallId is attached, cancelRun(run_id) must issue host/BEX cancellation; it cannot only mutate RunStore state.
  • Test catalog is not a run.
  • Test execution is a run.
  • Preview/helper execution is either hidden/internal or scoped, but still represented if it is observable.
  • No semantic hashes in the hot tracing path.
  • Every runtime target that can execute BAML can produce a valid .bamlprof artifact.
  • WASM emits profile artifacts as bytes or chunks; native file paths are not part of the core profiler API.
  • No legacy runtime event pipeline in the new public playground.

22. Milestones

Milestones are delivery rollups, not a second migration order. They preserve the same hard dependency chain as §20: production Rust reconstruction and trace-routed RunStore snapshots land before TypeScript graph/timeline/runtime cutover, and WASM parity is conformance against that shared model rather than the first proof of the architecture.

Milestone 1: Contracts and Normalization

  • Define RunId, HostCallId, StartRunContext, RunContext, RunTarget, derived RunKind, RunStatus, and RunOutcome.
  • Define normalized ProfileEvent, ProfileEventEnvelope, trace keys, component-claim vocabulary, timestamp units, cursor semantics, and runCursorExpired reasons.
  • Add project_generation or equivalent runtime revision to the execution request and run summary shape.
  • Pin the public identity boundary: browser-visible commands use RunId and request ids; raw profile events and .bamlprof do not carry playground RunId.

Milestone 2: Production Rust Reconstruction

  • Promote prof_gate.rs reconstruction logic into production bex_events::run::reconstruct.
  • Normalize live profile records and .bamlprof replay through the same ProfileEvent path.
  • Build call tree, thread tree, timeline placement, balance diagnostics, stable node ids, and late-event repair from trace identity and parent edges.
  • Keep timestamps as timing/timeline data, not as the semantic reconstruction key.

Milestone 3: RunStore Trace Routing and Native Lifecycle

  • Add RunStore create/snapshot/subscribe/complete, per-run retained patch windows, and snapshot-first subscription behavior.
  • Replace nextFunctionCall with startRun; attach HostCallId internally and populate HostCallId -> RunId before BEX/sys_ops can emit observations.
  • Implement trace routing, unresolved-component buffering, route reservations, attach_root_trace, and back-fill into stable ThreadNodeId/CallNodeId.
  • Classify native completion through RunStore.complete_run(run_id, RunOutcome) and route cancellation through the host/BEX cancellation primitive once HostCallId exists.

Milestone 4: Payload, Input, Env, Fetch, and Logs

  • Route call args, call results, call errors, media previews, fetch logs, input requests/resolutions, env requests/resolutions, logs, custom events, and tags into RunStore payload/request state.
  • Attach call-level payloads through RunId plus internal trace provenance so they resolve to stable CallNodeId when reconstruction catches up.
  • Make fetch/input/env sys_ops resolve their host call id through the HostCallId -> RunId map before writing observations.
  • Add retention, truncation, and redaction hooks for heavy or sensitive payload bodies.

Milestone 5: TypeScript Snapshot Protocol and UI Cutover

  • Add RunStoreClient and ExecutionStore over the existing RuntimePort transport boundary with the new domain-shaped typed union.
  • Expose startRun, cancelRun, listRuns, snapshot, subscribe, unsubscribe, runPatch, and runCursorExpired.
  • Render runs, graph overlays, timeline, result panel, fetch panel, logs, and input/env prompts from RunStore snapshots/patches that already include reconstructed call/thread structure.
  • Remove RunEntry as canonical state after migrated views no longer need raw runtime events.

Milestone 6: Browser Reconstruction Deletion

  • Delete browser runtime proto decoding, deserialize-event.ts, active-call heuristics, and raw runtime-event protocol messages once compile and grep gates prove there are no live imports.
  • Delete runtime-output.ts and repin its behavior as Rust reconstruction and graph-overlay tests.
  • Gut the old ExecutionPanel reducer state that modeled runs, pending input/env, fake collection runs, and fetch logs outside RunStore.
  • Keep UI-only layout, selection, navigation, and log-decoration projections as presentation code.

Milestone 7: WASM Conformance and Artifact Parity

  • Make the shared pb, profile encoder, byte/reader API, and ProfileArtifactSink usable on wasm without pretending native file paths exist.
  • Add cooperative WASM profile drain, explicit caps/drop diagnostics, and a monotonic timestamp_ns source.
  • Implement WASM start/cancel/result/error, fetch/input/env/log payload ingestion, snapshot, patch, and byte/chunk artifact output against the same RunStore contract.
  • Prove deterministic byte fixture parity where metadata is fixed, and structural reconstruction equivalence after canonicalizing target-specific header fields for real native/WASM artifacts.
  • Delete or hard-isolate the legacy WASM runtime-event path before exposing the new public browser-only surface.

Milestone 8: Normal Playground Breadth and Profiling UI

  • Move test execution to RunTarget::Test on native and WASM-supported surfaces while keeping the test catalog in ProjectStore.
  • Model prompt/curl helpers as Preview or Companion runs on the shared model.
  • Render timeline, flamegraph, and profile-derived views from the shared reconstructed model.
  • Preserve hosted/browser-only playground polish through the WASM adapter without reintroducing browser-owned execution reconstruction.

Milestone 9: Legacy Removal Audit

  • Verify no TypeScript surface imports legacy runtime-event decode, graph runtime reconstruction, active-call heuristics, or raw runtime-event protocol messages.
  • Verify baml_events.proto retirement does not remove value-codec or structural bamlprof.proto functionality.
  • Verify SessionStore, ProjectStore, and RunStore remain the only logical state owners for their domains.
  • Verify native and WASM supported surfaces use the same RunStore, ProfileEvent, .bamlprof, and reconstruction contracts.

23. Risks and Answers

Risk Answer
Too many names: RunId, HostCallId, CallRef. Expose only RunId, Run, RunPatch, CallNode. Keep the rest internal.
RunStore becomes a dumping ground. Use the observable-execution-state rule. Project/session metadata stays outside.
Test discovery gets mis-modeled as execution. ProjectStore owns test catalog and discovery diagnostics. RunStore owns only test execution; default-on profiling during discovery is suppressed or classified as hidden/internal before it can create visible run state.
Preview/helper calls pollute history. Use the RunTarget-derived kind and visibility. Store them if observable, but scope/hide them by default.
WASM forks the architecture. Rebuild WASM against RunStore, target-neutral profile events, and byte/chunk .bamlprof artifact output. Do not keep legacy runtime events as the future path.
WASM cannot save native files. Do not make file paths the abstraction. WASM produces valid .bamlprof bytes or chunks; the host persists them to R2, KV, Durable Object, response body, browser storage, or download.
Snapshots become too heavy. Use summaries for lists and full snapshots per selected run. Patches are optimization; compact old payload bodies if needed.
Secret env values leak into run snapshots. Store env request key/source/status by default. Redact values unless explicitly marked safe.
Profile event ordering is wrong. Reconstruct structure from trace identity and parent edges. Use timestamps only for timeline placement and deterministic presentation ordering.
Old and new systems both remain alive. Make deletion a milestone. Do not let the old TS runtime-event pipeline be a fallback after launch.
