# Implementation Findings

## Native live profile observer seam is intentionally narrow

The BEX profile consumer now transcodes `RawRecord` values once, writes the `.bamlprof` artifact, and publishes the same normalized `ProfileEventEnvelope` through a small in-process observer seam. Native LSP registers a `RunStoreProfileObserver` that ingests those events into the shared `InMemoryRunStore` and broadcasts resulting `RunPatch` frames, so live profile ingestion and `.bamlprof` replay now share the same normalization/reconstruction path.

Keep this seam narrow. It is a process-local fanout for target-neutral structural profile events, not a new playground protocol, not a persistence layer, and not a replacement for root trace attribution. Do not fake call-tree reconstruction from `HostCallId`, timestamps, function names, or "only active run" heuristics. `RunStore` identity/lifecycle/root-trace wiring remains the only run-routing mechanism, including the WASM cooperative drain path.

Manual testing against `/Users/rossir/dev/baml-demos` exposed a native flamegraph regression where successful `Hi()` runs wrote `.bamlprof` artifacts but the RunStore snapshot stayed at `rootCallNodeId: null` with empty `calls` and `threads`, leaving the Flame tab on `No profile yet`. The root cause was that the native profile consumer minted a separate process UUID for artifact/live envelopes while `BexEngine` minted `ProcessEuid::current()` for `CallRef`; the trace quads could never match during `component_events_for_root`. The consumer now uses `ProcessEuid::current().0`, and the same manual run now yields a non-null root call, one thread, nine call nodes (`user.paulo.Hi` plus eight `user.paulo.childFunc1` calls), and a populated Flame tab.

## Run protocol bridge uses host-call-free run arguments

The native websocket now accepts run-vocabulary read/recovery commands (`startRun`, `cancelRun`, `listRuns`, `snapshot`, `subscribe`, `unsubscribe`) and no longer carries the old direct `callFunction` execution frames. `startRun` no longer uses the browser request id as host plumbing; native allocates its own `HostCallId` before entering BEX and returns request-correlated `runStarted`.

The function/preview run argument envelope is now `argsBytes`, a length-delimited stream of `InboundMapEntry` values decoded by `bridge_ctypes::playground_run_args_to_bex_values`. It reuses the shared CFFI value codec for rich values and handles, but it does not reuse `CallFunctionArgs` and therefore cannot carry `call_id` as hidden host plumbing. Collection/debug delivery still has wrapper-level call-id compatibility only for transient discovery fetch correlation; it is not execution identity and does not feed normal run history.

## WASM RunStore adapter is RunStore-backed and in-memory

The WASM bridge now owns an `InMemoryRunStore` and emits run-vocabulary events through the playground callback. Browser-only `startRun` and `startTestRun` create real `RunTarget::Function` / `RunTarget::Test` runs, allocate `HostCallId::Wasm`, attach the host call before execution, attach the traced root call through `call_function_with_trace` / `call_test_function_with_trace`, and complete snapshots with the same base64 outbound result payload shape used by native. `cancelRun`, `snapshot`, `subscribe`, `unsubscribe`, and `listRuns` are backed by that Rust store, and the worker unwraps those WASM notifications into the same `WorkerOutMessage` stream consumed by `RunStoreClient`.

WASM env, input, and fetch sys-ops now ingest redacted RunStore observations keyed through `HostCallId::Wasm`, so final snapshots and patches can carry request/fetch payload state from Rust rather than browser-local reducers. WASM `startPreviewRun` also records `RunTarget::Preview` and executes the concrete companion function through the same Rust-owned run lifecycle. WASM `respondToInput` and `respondToEnv` now validate `RunId + requestId` through Rust `RunStore` before the worker releases the host callback promise; the callback ids are the Rust request ids, not a second browser counter. The browser-only adapter is intentionally in-memory today: without a configured durable storage adapter, reload destroys retained runs/artifacts rather than restoring browser-cached execution state as authoritative.

WASM profile production is now bridge-scoped rather than globally default-on: `ProfConfig` stays default-off on wasm until the playground bridge explicitly enables cooperative profiling, so other wasm embedders do not accumulate rings without a drain owner. `bex_events::prof::drain` provides a cooperative drainer over the crate-private ring registry, sharing the target-neutral header/event encoder and byte sink. `bridge_wasm` owns one drainer per runtime, drains after a traced function/preview/test run attaches its root trace, applies normalized profile envelopes to `RunStore`, forwards resulting `RunPatch` frames, converts drain warnings into run diagnostics, and emits retained `.bamlprof` byte chunks as `profileArtifactChunk` adapter notifications with explicit cap/drop stats. The worker forwards those artifact chunks as first-class transport notifications, while `ExecutionPanel` deliberately leaves them to the RunStore/artifact boundary instead of decoding profile bytes in React. Native file writing remains on the native consumer path; browser TypeScript still does not decode profile bytes.

The `bridge_wasm` wasm-pack tests no longer call the deleted direct `call_function` API. Their helpers now start execution through `startRun`, capture RunStore playground notifications, wait for the terminal `complete` patch, and decode the base64 outbound result from the RunStore outcome. `wasm_fs_glob` also has wasm-pack tests that assert real WASM `startRun` executions emit `profileArtifactChunk` bytes that parse via `read_bamlprof_from_bytes`, reconstruct through `bex_events::run::bamlprof`, and match the same canonical nested-call shape pinned by the native `prof_gate::native_profile_reconstructs_canonical_parity_shape` fixture. This environment does not have `wasm-pack`, so the executable Node-WASM test run is not verified here; `cargo check -p bridge_wasm --tests --target wasm32-unknown-unknown` does compile the wasm test targets and catches stale API use.

Test catalog/discovery calls now suppress profiling per `FunctionCallContext` rather than relying on hidden runs or post-hoc filtering. `collect_tests`, `TestRegistry.serialize`, `TestRegistry.expand_set`, and expansion error resend paths use `with_profile_enabled(false)`, while actual test execution remains a traced `RunTarget::Test`. `prof_gate::profile_suppressed_context_does_not_emit_records` verifies that a suppressed entry call creates no marker-bearing `.bamlprof` component even when profiling is globally enabled, and that the same function still profiles normally with the default context.

The legacy `nextFunctionCall`/`callFunction` value-returning path is now deleted from the TypeScript runtime port, worker protocol, browser worker, and native websocket adapter. Future WASM/browser-only behavior must go through `RunStore` commands; there is no direct-call fallback left for preview, normal execution, or test execution.

`bridge_wasm` no longer exports direct `nextFunctionCall`, `callFunction`, `cancelCall`, or `callTestFunction` methods in its generated WASM API surface. The Rust bridge source and regenerated `pkg-playground/wasm` artifact now expose the RunStore execution commands instead. This required auditing the generated `.wasm` export table because a d.ts-only edit would have typechecked while leaving the browser runtime on stale legacy exports.

## TypeScript execution views consume RunStore snapshots

`RunStoreClient` and `ExecutionStore` now provide a typed snapshot/patch path over the runtime transport and own patch application outside React components. Normal function execution in `ExecutionPanel` now starts through `ExecutionStore.startRun`, renders RunStore snapshots via `run-store-projections.ts`, and cancels by `RunId` rather than host-call id.

Test execution now starts through `ExecutionStore.startTestRun`, renders from `RunTarget::Test` snapshots, cancels by `RunId`, and derives sidebar test outcomes from RunStore snapshots instead of fabricating `testing.run_test` `RunEntry` rows. The legacy `callTestFunction` frame is deleted from the TypeScript worker protocol.

Test discovery no longer creates a `$collect_tests` `RunEntry` in the React panel. Collection and expansion fetch diagnostics are held in a separate `CollectionDebugState` and surfaced as project/test discovery debug UI, not as normal run history.

Native and WASM input prompts now have run-scoped `respondToInput` commands. Function/test run views project pending `InputRequested` payloads from `RunStore` snapshots, submit responses by `RunId + inputRequestId`, and ignore legacy host-call-keyed input frames during the staged transport cutover. Native and WASM env requests also have run-scoped `respondToEnv` commands with Rust-side run/request validation. The existing global API-key dialog opportunistically resolves through `RunId + envRequestId` when the matching RunStore env payload is present, and keeps the legacy `envVarResponse` fallback only for migration races/legacy surfaces.

`respondToInput` and `respondToEnv` now return RunStore-derived request outcomes (`accepted`, `alreadyResolved`, `rejectedStale`, `cancelled`, `missing`, `alreadyTerminal`) instead of treating every absent native pending waiter as generic `missing`. `cancelRun` also records cancelled input/env request payloads in the same RunStore patch that moves the run into cancellation, and native host adapters release their live waiters so stale prompts do not keep execution suspended. WASM host callbacks now use the Rust request id and de-duplicate completion through `resolve_*_request_for_run`, so run-scoped responses and direct host callback completion do not emit competing resolution patches.

`ExecutionStore` now preserves the typed `RequestCommandOutcome` vocabulary on cancel/input/env methods instead of widening the facade back to plain strings.

GraphView and `ExecutionPanel` are no longer RuntimeEvent consumers: GraphView consumes RunStore snapshot overlay data, `runtime-output.ts` plus its tests are deleted, and normal/test run cards plus collection debug no longer render decoded runtime events. The TypeScript `RuntimePort` no longer exposes `nextFunctionCall()`, and the worker protocol no longer defines `nextFunctionCall`, `callFunction`, `callFunctionResult`, `callFunctionError`, `cancelCall`, `callTestFunction`, or `clearHandles` frames. The Rust websocket `NextFunctionCall`/`NextFunctionCallResult`, `CallFunction`/`CallFunctionResult`/`CallFunctionError`, `CancelCall`, and `CallTestFunction` mirrors are deleted too. `RuntimeEvent.decode`, `deserializeRuntimeEvent`, `DeserializedRuntimeEvent`, `runtimeEventNew/Error`, `PlaygroundNotification.runtimeEvent`, `shared/deserialize-event.ts`, and the `pkg-proto` runtime-event re-export block are now deleted. Workspace grep confirms no TypeScript `RuntimeEvent`, event type, `deserialize-event`, `nextFunctionCall`, or direct `callFunction` worker-protocol references remain.

Native and WASM prompt/cURL preview now have RunStore-backed paths: `startPreviewRun` records `RunTarget::Preview { parent_function_name, helper }`, executes the concrete companion function, stores the terminal value on the hidden Run snapshot, and the UI decodes that snapshot result for the prompt/cURL tabs. The old preview fallback through `nextFunctionCall` + `callFunction` is deleted.

The old normal-run `RunEntry[]` React reducer in `ExecutionPanel` is now removed; normal function/test history renders from `ExecutionStore` Run snapshots, GraphView selects Run snapshots directly, and legacy `fetchLogNew`/`fetchLogUpdate` no longer route into a browser-owned run list. Collection debug now renders only fetch logs and expansion errors; `ExecutionPanel` has no `DeserializedRuntimeEvent`, `runtimeEvents`, `runtimeEventNew`, `callFunctionResult`, or `nextFunctionCall` handlers.

`RunEntry` itself is now deleted from `worker-protocol.ts` and from the public barrel. Grep confirms no `RunEntry` references remain in `pkg-playground`, `app-promptfiddle`, or `app-vscode-webview`.

`MetadataBadges` no longer imports the legacy `FetchLogEntry` identity shape; it accepts only `responseHeaders` and `responseBody`, which are the presentation fields it actually reads. `FetchLogEntry.callId` is deleted; the temporary legacy correlation now lives only on the `fetchLogNew` message wrapper so collection-debug buffering can associate pre-result fetch logs with `testCollectionResult.callId`. That wrapper-level `callId` should disappear when collection/debug fetch delivery is moved fully behind ProjectStore diagnostics or RunStore-backed observations.

## SessionStore now owns env values

`pkg-playground/src/session-store.ts` is the browser-side SessionStore owner for env values, shell/process imports, required-key UI metadata, localStorage hydration/persistence, and RuntimePort env mirroring. `envAtoms.ts` is now only a Jotai/React mirror over SessionStore, preserving the existing `useEnvVars(port)` hook while removing direct localStorage reads/writes and duplicate port sync from `ExecutionPanel`.

Native `PlaygroundEnvState` no longer owns the env override map directly. `playground_session.rs` holds the process-side `PlaygroundSessionStore` override mirror, and `PlaygroundEnvState` reads that mirror before falling back to process env and the run-scoped webview prompt path. Per-run `EnvRequested`/`EnvResolved` observations still go through RunStore; SessionStore owns values, not execution observations.

The wire messages are still named `setEnvVar`/`deleteEnvVar` for staged compatibility with native and WASM transports, but they now represent SessionStore mirror updates rather than an independent UI reducer owner. The WASM worker's `envVars` object remains a host-adapter mirror and must not grow new ownership logic during WASM conformance.

## GraphView now uses Rust-owned overlay data

`Run` snapshots now expose reconstructed `CallNode` values with stable ids, statuses, parentage, function names, explicit future provenance fields (`calleeSource`, `callSiteSource`, `functionOrigin`, `payloadIds`), and a Rust-owned `GraphRuntimeOverlay` snapshot/patch field. `callSiteSource` is now carried from VM/compiler source-map spans through raw `CallFunction`, `.bamlprof`, replay normalization, and live RunStore reconstruction when the caller PC has a line-table span. Normal function runs now carry the current live project generation instead of the previous hard-coded `ProjectGeneration(0)`, matching the plan's requirement that runs remember the ProjectStore snapshot key they executed against.

The canonical Rust overlay projection now exists as `bex_events::run::build_graph_runtime_overlay_from_cfg_spans(run, cfg_node_spans)`: ProjectStore can provide captured CFG node source spans, and the helper maps exact call-site spans first, then a single smallest containing CFG span, grouping one CFG node to many `CallNodeId` values and leaving unmatched, incomplete, or ambiguous calls unattached with explicit diagnostics. Rust tests pin the two plan fixtures: the same callee invoked from two distinct call sites maps to two different `CfgNodeId` values, and repeated executions of one call site group onto one CFG node. The helper never consults function names, timestamps, callee definition spans, or active-call state.

Native ProjectStore now snapshots prepared CFG graphs on successful engine rebuilds, retains a bounded set by generation, exposes `control_flow_graph_for_generation(project, generation, function_name)`, and installs a `ProjectGraphRuntimeOverlaySpanProvider` into `InMemoryRunStore`. Live native RunStore profile recomputation can therefore populate `GraphRuntimeOverlay.entries` from the run's captured `project_id + project_generation + function_name` when the retained generation is still available. If that generation has been evicted or the target has no value-free graph, the provider emits `GraphOverlayProjectGenerationUnavailable` and deliberately does not use the current-editor graph.

The current websocket `requestControlFlowGraph` path still resolves the current graph by function name across projects for the static graph view. That path must not be used as the production run-overlay join for old runs after edits.

GraphView is now cut over to the prepared overlay path: it accepts `GraphRuntimeOverlay`, `CallNode[]`, `Run.status`, and the run error message, rolls call execution states up through CFG parents, and no longer imports or receives raw runtime events. `runtime-output.ts` and its test have been deleted after a grep gate confirmed there were no remaining live imports. This intentionally drops browser-side value/image extraction from graph nodes rather than preserving it through heuristics; graph result previews should return only when RunStore has explicit call-level payload/result attachment.

The plan explicitly forbids replacing `runtime-output.ts` with browser-side function-name matching, timestamp proximity, or "next matching node" heuristics. Browser graph reconstruction is now deleted; future graph result previews should come from explicit RunStore call-level payload/result attachment, not a TypeScript-only join from `CallNode.functionName` to `CfgNode.calleeName`.

`RunStoreClient.listRuns` now accepts typed filters for `projectId`, `projectGeneration`, run `kinds`, `callTreeContainsFunction`, and visibility. The native websocket mirrors this into `RunFilter`, and `bex_events` now pins target-function `touched_functions` summaries plus project/generation/kind/function filtering. `ExecutionPanel` now selects graph snapshots from RunStore display state rather than the old React `RunEntry.runtimeEvents` scan.

`ExecutionPanel` now has compact `Trace` and `Flame` tabs backed only by RunStore `CallNode` and `ThreadNode` snapshots. Same-thread nesting comes from `CallNode.parentId`; spawned-thread roots use `ThreadNode.parentCallNodeId` as their stack parent. `ExecutionProfileView` owns the CodSpeed-lite profile UI as a lazy, memoized TypeScript projection over the selected `Run`: it builds function table rows, search-driven multi-highlight, `Function`/`Origin`/`Thread` color modes, system-frame hiding with visible-descendant reparenting, and flame depth tracks without changing RunStore, wire protocol, or Rust reconstruction. Search no longer filters blocks or table rows; it derives matching function keys and grays out nonmatches using the same highlight mechanic as row/block selection. Depth-track lane packing now preserves projection/traversal order for same-start frames instead of promoting longer sibling spans above earlier spawned siblings. The old `runToFlamegraphRows` compatibility projection was removed; tests now target the execution-profile projection builder directly. `run-store-projections.test.ts` pins same-thread call edges, spawned-thread parentage, function aggregation, search highlighting, system-frame collapse, and color-key stability. `/Users/rossir/dev/baml-demos/baml_src/ns_demo/flamegraph_fanout.baml` adds `FlameGraphFanoutDemo`, a root-to-three-branches-to-two-leaves sleep/fanout demo for visual inspection. The current view is an elapsed-time flame chart from start/end timestamps; it is not a sampled CPU flamegraph unless the profile substrate later adds CPU sample counts.

## WASM profile substrate has shared bytes and bridge-owned profiling

`bex_events::prof::encode` and `bex_events::prof::read` now hold the target-neutral `.bamlprof` header/event encoder and bytes/reader parser. Native `prof::file` remains the filesystem adapter and keeps `read_bamlprof(path)` as a wrapper, while re-exporting the old reader symbols for native compatibility. The hot `CallFunction`/`EndFunction` hand encoder is now shared by the native writer and byte/chunk sinks, and tests pin both prost parity and native-file-vs-byte-sink byte equality with fixed metadata.

`ByteProfileArtifactSink` now has an explicit bounded mode (`with_max_bytes`) that retains the artifact prefix, counts dropped bytes/chunks, and returns truncation diagnostics on `flush`. This gives the future WASM adapter a concrete backpressure/drop reporting surface instead of an unbounded in-memory buffer or silent partial artifact.

This satisfies the plan prerequisite that `prof::pb`, prost-generated types, shared header/event encoding, raw-record transcode, byte sink, and bytes/reader APIs build for `wasm32-unknown-unknown` without exposing native `Path`/`File` or background consumer threads. Profiling remains default-off for generic wasm embedders, but `bridge_wasm` explicitly enables cooperative profile capture and owns the only current wasm drain path.

After deleting browser runtime-event proto decode and adding the WASM RunStore adapter plus cooperative artifact output, `cargo check -p bridge_wasm --target wasm32-unknown-unknown`, `cargo check -p bex_events --target wasm32-unknown-unknown`, and `cargo test -p bex_events prof::drain -- --nocapture` all pass. This proves the shared profile substrate and bridge drain compile on wasm and can produce reader-compatible `.bamlprof` bytes through the same encoder contract.

`.bamlprof` replay reconstruction (`bex_events::run::bamlprof`) now consumes the shared `prof::read::BamlprofContents` type instead of the native file module, so wasm builds can parse bytes and feed the same run reconstructor. Native tests still use `prof::file::read_bamlprof(path)` as a convenience wrapper, but path IO is no longer part of the replay boundary.

Engine profile metadata now lives in a target-neutral `prof::metadata` registry. Native header construction and the cooperative WASM drain read from that registry, and both native fallback close paths and wasm `engine_closed` remove registered metadata instead of silently leaking/no-oping.

Live RunStore reconstruction now uses the same registered engine metadata as native `.bamlprof` header construction to map `function_id` to function names, function origins, and callee byte spans. Each run caches the resolved function table so later recomputation does not lose names after `engine_closed` cleans the global metadata registry. This lets live `CallNode.functionName`, `functionOrigin`, `calleeSource`, and `RunSummary.touchedFunctions` come from Rust-owned metadata instead of browser event scans.

Call-site provenance is now a Rust-owned profile field as well: the VM records the caller PC before descending into bytecode calls, inline native pairs, and sys-op/host-closure calls; `RawRecord::CallFunction` stores the source-map file id, byte span, and line when available; `.bamlprof` persists those as optional fields; and RunStore reconstruction projects them into `CallNode.callSiteSource`. Tests pin raw record roundtrips, hand-encoder/prost parity, raw-to-disk transcode, repeated same-callee calls with distinct call sites, the span-indexed overlay projection helper, provider-populated live overlays, and retained CFG cache eviction. GraphView is already cut over and `runtime-output.ts` is deleted; future graph result previews should come from explicit RunStore payload attachment, not browser reconstruction.

With TypeScript runtime-event decode/imports gone, the trailing CFFI runtime-event proto is retired too: `bridge_ctypes/types/baml_core/cffi/v1/baml_events.proto` and the generated Python `baml_events_pb2` stubs are deleted. `baml_inbound.proto`, `baml_outbound.proto`, and `.bamlprof` stay. Unrelated SDK telemetry/tracing symbols such as `BamlLogEvent` are outside this deletion.

## Known completion gaps from manual serving audit

The native `/api/ws` playground server and VS Code-hosted flow are wired. Standalone terminal serving now has a narrow project-loading path: `baml lsp --playground-via-browser --workspace <PATH>` seeds the same workspace-root discovery used by LSP `initialize`, refreshes discovered BAML projects, and opens the first discovered project in the browser when `BAML_PLAYGROUND_DEV_PORT` or `BAML_PLAYGROUND_DIR` is present. A plain `baml lsp --playground-via-browser` still only starts the LSP/server shell; without an editor client or explicit `--workspace`, it has no workspace roots to discover from.

Standalone `--workspace` serving now also runs a small filesystem poller for explicit workspace roots. This fills the gap where browser-only sessions do not receive editor `workspace/didChangeWatchedFiles` or `textDocument/didChange` notifications, and where webview `filesChanged` is local-only in the websocket runtime port. The poller watches `*.baml` and `baml.toml`, skips generated/heavy directories such as `.baml`, `.git`, `target`, `dist`, and `node_modules`, and reuses `initialize_workspace_roots` for the refresh. A manual smoke test added then deleted a temporary BAML file in `baml-demos`; the open browser moved from `Functions(19)` to `Functions(20)` and back to `Functions(19)` without reload.

The VS Code extension development path also expects packaged webview assets at `typescript2/app-vscode-ext/dist/playground/index.html`; the launch config provides `BAML_PLAYGROUND_DEV_PORT=4000` for the Rust server, but `WebviewPanel` still loads the packaged HTML from disk. Building `app-vscode-webview` and running `pnpm vscode:package:stage` produces the ignored local `dist/playground` assets and unblocks manual testing, but this is a dev-flow requirement rather than an automatic live-dev fallback.

The plan-level acceptance matrix is broader than the verified implementation. The migration has substantial coverage for RunStore ownership, TypeScript runtime-event deletion, native websocket commands, WASM compile conformance, shared `.bamlprof` bytes, and graph-overlay cutover, but not every falsifiable gate has been executed in this environment. In particular, `wasm-pack` is unavailable locally, so executable Node/WASM browser tests were not run here; browser-only durable persistence adapters are not implemented beyond the intentionally in-memory RunStore adapter; and the full VS Code-hosted manual run/reconnect flow still needs to be exercised after staging the webview assets.
