# BAML TypeScript tooling architecture

**What this adds.** Opt-in v1 tooling for importing BAML directly from TypeScript — `import { b, Resume } from './baml_src/resume.baml'` and `import { b } from 'baml:client'` — with cross-language editor support (definition, references, rename, diagnostics, completion, hover) and build integration for Vite, Rollup, Webpack, esbuild, and Bun. The direct-import `b` surface is deliberately async-only in v1. `baml generate`, the generated SDK, and every v0 surface are unchanged; the feature activates only by installing the tooling package.

**Invariant.** The compiler owns all BAML semantics. No TypeScript code parses BAML, infers a BAML type, or identifies a declaration by name-matching generated text. Non-goals for v1: no runtime-bridge ABI change, no tsserver features *inside* `.baml` documents (the native LSP owns those), no `baml-tsc` binary.

## Package boundaries

Rust, under `baml_language/`:

- `crates/baml_tooling_api` (internal): every tooling operation over a long-lived `ProjectDatabase` — saved/unsaved source snapshots, check, in-memory SDK and virtual-module emission with segment maps, definition/references/hover/completions, prepare-rename/rename, `fingerprint()`, `watch_files()`. Advertises capabilities `typescriptImports.v1` and `rename.v1`.
- `crates/bridge_ctypes`: the additive-only `baml.tooling.v1` protobuf contract (`types/baml/tooling/v1/tooling.proto`), generated into `typescript2/pkg-proto` and vendored into the published tooling package so it carries no workspace dependency.
- `sdks/typescript/bridge_tooling`: napi crate published as `@boundaryml/baml-bridge-tooling` — umbrella plus eight optional platform packages, from the `napi.targets` matrix in its `package.json`, version-stamped by `scripts/baml-language-version`. It is a thin protobuf shim over `baml_tooling_api` with no dependency edge to the runtime bridge ABI. `crates/bridge_wasm` (`src/tooling.rs`) exposes the same byte-oriented dispatcher; **parity rule:** a protocol operation is complete only when both hosts expose it in the same commit. Both hosts construct **per-instance** bridges (`new BamlToolingBridge()` on native and WASM alike): each instance owns its protocol sessions, so two clients serving the same project root (client + SSR environments, two projects in one test process) never observe each other's overlays. There is no shared process-wide session state on either host. Sessions are **explicitly released**: `close` is a protocol request like any other, so `BamlProject.dispose()` drops the compiler database and every allocation reached through it on native and WASM alike, rather than leaving a superseded session alive until GC. Closing is idempotent (`released: false` for a session that was already gone is a success, not an error) and a released project id is dead — later requests against it fail with `unknown_project` instead of silently reopening. The parity corpus dispatches `close` to both hosts and compares response bytes, so neither host can drift into leaking what the other frees.
- `sdks/typescript/sdkgen_typescript_shared`: the tooling projection is emitted by `emit_tooling_module`, reusing the canonical `translate_ty` and `SymbolPool` code paths while its mapped writer records segment maps. The `baml generate` path is unchanged, and byte parity is a CI gate.
- `crates/baml_lsp2_actions`: compiler-owned `prepareRename`/`rename` with collision validation — the gate behind `rename.v1`.

TypeScript, under `typescript2/`:

- `pkg-baml-tooling` → **`@boundaryml/baml-tooling`**, the single published package. It discovers the owning `baml.toml`, selects native then WASM unless configured, maintains source overlays and revision gates, translates segment maps, owns the disk cache and the sidecar predicate, and ships the `baml-ts-gen` bin. All host integrations are subpath entry points over shared cores: `./vite`, `./rollup`, `./webpack`, `./esbuild`, and `./bun` share one build core; `./typescript-plugin` (CJS) is the tsserver plugin. Entry points hold only lifecycle and API wiring — resolver state, sidecar policy, diagnostics, and generated artifacts live in the shared project/build core.
- `pkg-ts-tooling-e2e` (private): real bundler builds and HMR, packed-install fixtures, and a real tsserver protocol harness.

## Project discovery and ownership

Every `.baml` source is owned by the **nearest `baml.toml` walking up from the resolved import location** — never by the build's working directory. Consequences:

- A dependency installed into `node_modules` that ships its own `baml.toml` + `baml_src` owns its `.baml` files. An app importing `dep/baml_src/widget.baml` opens (or reuses) a compiler session rooted at the dependency, alongside the app's own session. Bare specifiers resolve through Node's module algorithm, so real installs and pnpm-style symlinks both land on the physical file before the walk-up begins; paths are canonicalized (`realpath`) so a symlinked `node_modules/@shared/baml` and the real `packages/shared` are the same project. **This rule applies on every host path, tsserver included:** the language-service plugin keeps one lane per owning root (the app's project plus one lazily opened session per dependency or workspace sibling), routes each virtual declaration to the session that owns the resolved source, and resolves bare specifiers host-side — the bridge deliberately rejects bare specifiers and unknown entry files with protocol errors, because Node package resolution is only possible host-side and an empty filtered module would otherwise render as a silently blank declaration. A specifier that cannot be resolved (missing package, or an `exports` map that hides the subpath) produces an error diagnostic on the import span, never an empty module.
- Projects are addressed by `projectId(root)` everywhere identity matters: virtual module ids (`\0baml:<projectId>:…`), the shared runtime module, and the disk cache directory are all per-project, so any number of projects coexist in one build without collisions or cross-talk.
- Watch events are filtered to `.baml` and the project's **exact** config path — a `basename === 'baml.toml'` pre-filter plus a canonical-path equality check against `layout().configPath`, so `mybaml.toml` or a nested `sub/baml.toml` never reaches the Rust session (which would reject it with `NonBamlPath`) — and routed to the owning project by canonical path prefix; anything else (a TSX edit under `vite dev`) never enters the compiler database, and the Rust session rejects non-BAML paths defensively on **both** of its entry points: an overlay update, and the project-open snapshot — a snapshot carrying a stray `App.tsx` fails the whole open with `NonBamlPath` and leaves no session behind, rather than half-populating the database with a file the compiler would then report as broken BAML. Watch hooks never throw out of the bundler: a rejected update is reported through `watchError` and re-surfaced by the next `load()`. A `.baml` file created after a project opened is registered with its session eagerly on first resolve (bundler hosts) or on the next overlay sync (tsserver, which also removes deleted files), and the project layout is re-fetched after every membership change.
- A consumer reading a dependency's types therefore always gets declarations compiled against the dependency's own config, not the app's.

## Projection and source maps

A `.baml` file import is an export *filter* over the compiled project (BAML compilation is project-wide); `baml:client` exports the full public client. Every entry module imports one shared internal runtime module, `\0baml:<projectId>:runtime`, so serialized bytecode occurs once per bundle rather than once per entry.

Declaration projection carries a version-1 segment map. BAML source is never transformed before compilation, so compiler spans are true source spans and no offset-delta correction exists anywhere; the only mapping needed is generated declaration ↔ BAML source. Generated offsets are UTF-16, physical BAML offsets are UTF-8 bytes. Each segment carries a compiler `symbolId`, optional overload `signatureId` (reserved; v1 BAML has no overloads), source hash, and semantic role. The tooling package verifies revision text against `sourceHashes`, builds UTF-8/UTF-16 line indexes, binary-searches generated→source over ordered segments, and scans source→generated within the file's segments. Synthetic items map to their compiler-designated owner, never an invented span; same-named symbols in different namespaces (and same-spelled type/value pairs) are disambiguated by id, never bare names. An untranslatable navigation result is dropped — a virtual filename is never returned to an editor — and rename refuses the entire operation when any location fails the map round-trip.

## Language-service features

`@boundaryml/baml-tooling/typescript-plugin` (configured in `compilerOptions.plugins`; workspace TypeScript required) creates deterministic in-memory `.d.ts` files under `/.baml/__virtual__/` and feeds unsaved editor buffers to the compiler as overlays, so the compiler always sees what the user sees. Overlay sync is per request but deliberately cheap: per-file version counters catch edits and existence checks catch deletions for known sources, while the recursive directory walk that discovers *new* files is gated on directory mtime stamps (a file or subdirectory added or removed anywhere moves its parent's stamp) — the full re-walk never runs per keystroke. **Every one of those reads goes through the host's file abstraction, never through `node:fs` directly**, at open time and on every poll alike: a source that exists only inside the host — an unsaved `.baml` buffer the user just created, or any file supplied by a WASM/in-memory host that has no process filesystem — must be discoverable, or the host abstraction is decorative. Two channels carry what a disk walk cannot see: the host's own recursive listing, compared on every poll so that a change to it *triggers* the re-walk rather than only being read inside one (a buffer the host created that nothing imports yet moves no directory stamp and registers no import target, so gating the listing behind the stamp check would strand it until a save or an unrelated disk change), and individually registered import targets (a resolved `.baml` specifier is evidence its source exists, and re-checked for existence through the host on every poll). A directory absent on two consecutive polls counts as unmoved, so an in-memory root does not force a re-walk per request. On tsserver the host listing is **not** `LanguageServiceHost.readDirectory` alone: that call is backed by the process filesystem, so a brand-new unsaved `.baml` buffer is absent from it even while the editor is serving the buffer's text. The plugin unions it with the editor's own open-file registry (`ProjectService`), and reads existence and script versions from the same union — otherwise the per-request deletion sweep, which asks whether a known source still exists, would delete the buffer discovery had just added, and edits to a buffer the TypeScript project does not own would never move a version and never reach the compiler. Absent or renamed tsserver internals degrade to the disk-only listing, never to a thrown request. Discovery changes also bump the project version: rewriting a virtual declaration is not enough on its own, because the language service keeps serving the program it already built. UTF-8/UTF-16 line indexes are built once per (file, snapshot) and cached, in a single code-point-arithmetic pass. Each feature asks TypeScript first, then translates any hit inside a virtual declaration through the segment map to a `symbolId` and a compiler query against the symbol's owning session: **definition** lands on the exact physical `.baml` token; **references** merge TS use sites with compiler `references_at`, deduped and grouped under the BAML declaration; **rename** maps the TS symbol to compiler `prepare_rename`/`rename` and is capability-gated on `rename.v1` (older bridges refuse cleanly rather than emitting untranslatable edits); **diagnostics** merge TS use-site errors with compiler diagnostics at true `.baml` spans, also attached once per affected import specifier; **completions** and **hover** are proxied from the literal declarations and augmented with compiler documentation. Renaming an import alias stays TS-local; renaming the source token crosses the boundary. The native BAML LSP remains authoritative while the cursor is inside a `.baml` document.

## Caching, invalidation, HMR

Three layers: (1) the in-process Salsa database — overlays go through `update_file` so only dependent queries recompute, and hosts send `baml.toml` through the same snapshot channel as BAML sources, keeping fingerprints identical across native and WASM without host-neutral filesystem reads; (2) a disk artifact cache keyed by tooling protocol version and `fingerprint()` (compiler version + config snapshot + target) plus per-file raw-byte content hashes, with atomic-rename writes, envelope validation on read, and single-flighted concurrent misses — bad or stale entries are misses, never errors. Entries are immutable and content-addressed, so every edit writes a new key; the cache is therefore **bounded** (default 512 entries) and pruned oldest-write-first, evicting to 75% of the cap — a concurrent `get` racing a pruned key simply misses. The bound is derived from **on-disk** state, not from a per-instance write counter: the directory is shared by every process that uses it, so each process also reconciles against it once, on its first write. An in-process counter alone would never fire for a short-lived CLI or build that writes a handful of artifacts and exits, and the directory would grow past the cap forever, one run at a time. Counting is readdir-only, so the per-process reconcile costs no stat unless the directory is genuinely over cap; pruning stays amortized (at most `PRUNE_EVERY_PUTS` entries of overshoot between prunes), and the overshoot does not grow with the number of writes, processes, or the age of the directory; (3) a per-revision projection cache on the TS side, cleared whenever the revision changes.

Build hosts watch everything `watch_files()` reports — all discovered sources and `baml.toml` — from startup. Any BAML or config change invalidates project-wide (correctness before pruning), with per-module output hashing so unchanged modules aren't re-emitted. In a dev server a failed compile keeps the last-known-good runtime loaded while diagnostics surface; a production build always fails — a watch event alone never flips a build into development mode — with errors carrying the physical BAML path and byte offset.

## Sidecars and native typechecking (`tsc` / `tsgo`)

`baml-ts-gen` emits sidecars byte-identical to the virtual declarations, so plain JS-based `tsc --noEmit` works without the plugin. `<name>.baml.ts` overrides runtime and types; `<name>.baml.d.ts` overrides declarations only; one exported predicate is shared by every host. Generated files embed the compiler fingerprint, so a stale sidecar is detected rather than silently trusted. An invalid build fails sidecar generation; the editor may retain a stale-marked last-known-good declaration alongside the current compiler error.

**Sidecar precedence is scoped to what a sidecar actually overrides, so the two workflows compose in one checkout.** A bundler needs runtime code, and only `<name>.baml.ts` has any: when it exists the build core resolves the import *to that path explicitly*, because returning "not mine" would leave the bundler resolving `./main.baml` to the literal `.baml` file (extension appending never fires for a path that already exists) and failing in its JavaScript parser. `<name>.baml.d.ts` — everything `baml-ts-gen` emits — is declarations only and therefore never suppresses build-time virtualization; a `baml-ts-gen` run for `tsc` must not break the next `vite build`. On the type side the precedence is unchanged: both forms override the plugin's virtual declaration and both are fingerprint-checked for staleness.

The Go-native TypeScript compiler (`tsgo`, now published as `typescript@latest`) does not load JS tsserver plugins, so direct `.baml` imports there need compiler support. One experimental option is **[smithersai/baml-tsgo](https://github.com/smithersai/baml-tsgo)**: following the pattern established by [Effect's TypeScript-Go fork](https://github.com/Effect-TS/tsgo) (pinned upstream submodule, minimal ordered patches, generated shims, `init()`-registered hooks), a small resolver hook maps relative `.baml` imports onto the fingerprinted `.baml.d.ts` sidecars. This is not an endorsed BAML distribution path without maintainer sign-off. The alternative is [Volar](https://volarjs.dev/): a language plugin projecting `.baml` into mapped virtual TypeScript over stock `tsc` with a `vue-tsc`-style checker wrapper — no compiler fork, but a second Node-based projection stack to keep in sync.

## Running the tests

- Rust, from `baml_language/`: `cargo test --lib`, `cargo test --package baml_tests`, `cargo test --package baml_lsp2_actions_tests`, and `cargo nextest run -p sdk_test_typescript` / `-p sdk_test_typescript_web` for SDK byte parity. Lint gates: `cargo fmt --all -- --config imports_granularity=Crate --config group_imports=StdExternalCrate` and `cargo clippy --workspace --all-targets --all-features -- -D warnings`.
- TypeScript, from `typescript2/`: `pnpm build:wasm && pnpm lint && pnpm typecheck && pnpm test && pnpm build`. **`build:wasm` is not optional** — the e2e backend-parity test compares native against WASM bytes, so a stale `pkg-playground/wasm` artifact fails it for the wrong reason.
- The `pkg-baml-tooling` unit contract suite runs against a mock backend; native/WASM agreement is proven by the e2e backend-parity corpus. `pkg-ts-tooling-e2e` covers bundler adapters, HMR, the sidecar + `tsc --noEmit` path, packed-tarball installs, execution of a real compiler-emitted runtime module, and a real tsserver over the packed plugin. Its adapter-level `builds.test.ts` drives Vite, Rollup, Webpack, and Bun through fake project factories; compiler-backed coverage comes from the esbuild enum test and the packed Vite/esbuild consumer run.
- Release stamping: `scripts/baml-language-version check` must stay green — it covers `bridge_tooling` and `pkg-baml-tooling` alongside the existing npm packages.
