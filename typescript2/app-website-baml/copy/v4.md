## 3. How it works

## Write it in BAML, deploy it, query your data, and build anything.

You write your code in BAML and deploy it. There's no tracing SDK to add and nothing to configure. Your agent uses the same CLI you do to see what happened and fix it.

### Animation

The video player from hero version 7 on `/v3`: `triage.baml` in an editor beside one terminal, with five chapters under it that show progress and seek. The terminal is an agent session, opened with "> Check on triage in production." Each chapter's title matches a column in the hero. When a chapter's query answers, the matching group in a row of four cards under the video crosses out its products, and the command that replaces them lights up under the logos: Trace (`baml query`), Dashboards (`baml query --watch`), Alerts (`baml alerts`), and Feature flags (`baml flags`). It runs for 35 seconds and loops. Under reduced motion it holds after the alert resolves.

1. **Trace.** The agent reads one slow request's calls with `baml query`, as a waterfall: `route` 1,342ms, `classify` 1,318ms, and `openai/gpt-6-luna` 1,296ms. `route`, the `classify(ticket)` call, and the client line light up with their times. Tracing is built into the runtime, so there is nothing to send to Datadog or LangSmith.
2. **Dashboards.** It watches calls per minute with `baml query --watch`, the live chart from hero version 7. Each function's call count goes up at the end of its first line. A dashboard is a query, so there is no Grafana to set up.
3. **Alerts.** `baml alerts` shows classify firing: other is 3.1% of calls, above 2%. A red alarm appears next to `function classify`. Alerts are queries too, so they replace Sentry and PagerDuty.
4. **Feature flags.** The agent says the calls labelled other are sarcastic tickets, adds a line to the prompt (marked as a diff from then on), and runs `baml flags set classify --version v44 --traffic 10%`. A query compares the two versions: other is 3.1% on v43 and 0.3% on v44. This replaces LaunchDarkly.
5. **Fix.** `baml test add classify --from-query "output_value = 'other'"` adds 31 tests from production calls, `baml test classify` returns "40 passed, 0 failed", and `baml flags set classify --version v44 --traffic 100%` ships it to everyone. A day later, `baml alerts` shows classify resolved at 0.3%, and the alarm turns green.

## 4. Language features

## The best parts of TypeScript, Rust, Go, and Python.

`triage.baml`: the same sample as `/v3`, the `Label` type, `classify`, and `route`, with one comment added over `classify`: `// 'AI function' syntax for easy extraction`. It sits in an editor window beside the four points below.

Based on the current site's "A language and toolchain for AI code" list:

- **TypeScript-like syntax.** Write unions, generics, and classes in a syntax TypeScript developers already read.
- **Rust-like correctness.** The errors a function can throw are part of its type, and `baml check` reports any it doesn't handle.
- **Fast checks and Go-like concurrency.** `baml check` type-checks 60,000 lines in about 1.4 seconds, and green threads run work concurrently with `spawn` and `await`.
- **Types that hold at runtime.** Model replies are parsed into your types, and the runtime records every call with its typed arguments and result, with no tracing SDK.

## 5. Adopt incrementally

## Start with either side of the stack.

Two cards, labelled with the side of the hero's deploy line they start from: "Build and test" and "Production".

You don't have to move everything at once.

- **Start with the language.** Write one function in BAML and call it from your Python, TypeScript, Go, Rust, Java, Swift, or C++ app through a generated client. You don't need to rewrite your app or run a separate service.
- **Start with production.** If you already send OpenTelemetry traces, send them to Boundary and query them with `baml query`. Move code into BAML when you want typed telemetry, program versioning, and better developer experience.

## Open questions

- **Feature flags.** The hero and step 4 sell them, but a search of `baml_language/crates` finds no feature flag or experiment code. Should step 4 stay, or should the column read "Coming soon"?
- **OpenTelemetry ingestion.** The call said to sell it even if it isn't built. `/v3`'s copy already notes that Boundary doesn't ingest OpenTelemetry yet. Does that need to ship before `/v4` goes live?
- **Alerts.** Step 3 assumes alerts are queries. There is no `baml alerts` command in `baml_language` today.
- **Compile speed.** Measured on November 3 on an Apple M5 Max with baml-cli 0.23.0, on generated projects of 1,000 modules: `baml check` took 1.37 s for 60,000 lines (1.72 s after a one-file edit), `go build` took 0.96 s for 74,000 lines, and a cold `cargo check` took 2.57 s for 67,000 lines. BAML only type-checks while Go builds a binary, so the page doesn't say "as fast as Go". It gives BAML's own number instead. With the build cache on, an edited `baml check` was slower than a cold one, which looks like a bug worth filing.
- **The stack's name.** Boundary is the cloud service. This draft calls the whole thing "the BAML stack" until there's a better name.

Settled: other companies' logos are fine, section 2 gets a blueprint drawing, it isn't signed, and the Calendly link is above.
