# S3 and hosted object storage

**Status:** Target v1 contract. No new Project Studio artifact/CAS uploader exists on this branch. The exact source-chunk and receipt key shapes are specified; projector-state/result key shapes are not.

## What S3 stores

### Authoritative objects

After receipt-backed acceptance, S3 is the canonical hosted authority for:

- immutable source-range artifact chunks, including canonical value/CAS-bearing chunks;
- service-authenticated commit receipts; and
- accepted source/schema snapshots when present.

Only source-chunk and receipt **key shapes** are specified below. Their byte-level envelope/receipt codecs still have explicit freeze gates.

### Derived or temporary objects

S3 may also store immutable projector state snapshots, rebuildable commitment acceleration, and temporary scan/export/query results. These objects are not accepted customer evidence, are not the sole copy of transactional truth, and may expire under their separate policies.

## Source artifact versus uploaded chunk

- **Source artifact** — exact runtime-produced file or logical value/blob artifact.
- **Source-range chunk** — one immutable record-aligned byte range of exactly one source artifact; the upload unit.
- **Derived segment/snapshot** — rebuildable acceleration produced from accepted evidence.

The cloud accepts chunks without pretending a chunk is a run. Run attachment/completion comes from explicit manifests and root identity.

## Literal source-chunk key

~~~text
artifacts/v1/
  shard=<hash-prefix>/
  tenant=<uuid>/
  project=<uuid>/
  environment=<uuid>/
  cell=<id>/
  lane=<id>/
  ledger_date=<yyyy-mm-dd>/
  stream_epoch=<uuid>/
  sequence=<u64>/
  <chunk_uuid>.bamlchunk
~~~

The server selects the key. The path supplies IAM/deletion/inventory scope and request sharding. **ledger_date** is fixed at first authorization and reused by every retry of the same chunk identity.

## Literal receipt key

~~~text
receipts/v1/
  tenant=<uuid>/
  project=<uuid>/
  ledger_date=<yyyy-mm-dd>/
  commit=<id>.receipt
~~~

A receipt is deterministic and service-authenticated. It proves which immutable manifest set was accepted and lets a PostgreSQL restore re-import commitments after the restore point.

## Keys that are not specified

Do not invent stable public trees for:

- standalone **values/<cid>** objects;
- projector state snapshots;
- commitment compaction segments;
- exports;
- temporary query/scan results;
- source/schema snapshot bodies; or
- deletion verification reports.

The current hosted value design stores canonical CAS bodies in committed pack-bearing artifact chunks. An authorized private lookup maps an opaque provider handle to object reference/offset/length. The handle representation is deferred, and no standalone CID-object key scheme is canonical.

## ArtifactChunkEnvelopeV1

The versioned envelope carries:

| Family | Fields |
|---|---|
| Protocol | protocol/schema version, artifact media type, runtime version |
| Authenticated claim to verify | tenant, project, environment, cell, lane |
| Source range | source artifact ID/generation, byte offset/length, total length when known |
| Stream | stream ID/kind/epoch/sequence, predecessor digest |
| Bounds | record count, optional time and causal-sequence bounds |
| Integrity | plaintext digest, envelope digest |
| Encoding | compression plus reserved/capability-gated application-encryption metadata |
| Evidence | capture policy, loss deltas/totals |
| Program | source/program schema references when known |

Envelope scope is advisory. Every projected row takes scope from the authorization-derived PostgreSQL artifact_chunks record. A mismatch is quarantined and security-audited.

Framing:

~~~text
magic | envelope_length | canonical CBOR envelope | encoded payload | authentication tag
~~~

### Wire freeze gate

The source material does **not** yet specify an implementable byte-level envelope or receipt codec. Before writing production bytes, freeze and golden-test:

- literal magic/version bytes;
- integer widths, byte order, and maximum envelope length;
- canonical CBOR field keys/tags, types, required/optional rules, and unknown-field behavior;
- digest algorithms/domains and exactly which bytes each digest covers;
- authentication-tag algorithm, key identity/rotation, nonce rules, and covered bytes;
- exact allowlisted Zstandard parameters;
- receipt fields, canonical encoding, signature/MAC algorithm, key version, and verification/restore rules;
- per-task streaming byte, allocation, and CPU/deadline ceilings; and
- the clock-skew policy window and **clock_skew_flagged** representation.

V1 uses TLS and provider-side encryption at rest. Application-envelope encryption and BYOK remain deferred; the reserved metadata cannot be emitted or accepted without a future negotiated capability and policy decision.

## Hard decode limits

| Item | V1 maximum |
|---|---:|
| Stored ordinary chunk | 64 MiB |
| Decoded payload | 256 MiB and at most 32× expansion |
| Records per chunk | 500,000 |
| Individual structural record | 8 MiB; larger bodies use value/blob artifacts |
| Nested decode depth | 128 |
| Sequence | zero-origin, non-wrapping u64 |
| Compression | allowlisted Zstandard settings |
| Envelope | deterministic CBOR |
| Streaming work | Explicit byte/allocation/CPU deadline per task class; numeric policy freeze required |

These are protocol safety bounds, not capture/query policy budgets. Exceeding a hard bound or failing authentication/integrity quarantines the entire chunk; no prefix is partially accepted or projected.

## Upload rules

- The host creates/fsyncs an immutable spool object before authorization when durable storage exists.
- Authorizations bind exact key, expiry, length, full-object checksum and required provider-side encryption headers.
- Chunk uploads are one PUT; multipart is forbidden for chunks at or below 64 MiB.
- Conditional create (`If-None-Match: *`) is required.
- Ingest credentials cannot overwrite or delete.
- Object key, version ID, length and checksum become immutable manifest fields.
- Caller-supplied metadata is never integrity proof.
- Presigned URLs are bearer secrets and never enter logs/browser diagnostics.

An uploaded object is not accepted evidence until PostgreSQL commits its manifest and the deterministic receipt is written and verified.

## Client reclamation watermark

Two contiguous watermarks exist per stream:

- **contiguous_committed_through** — PostgreSQL commitment;
- **contiguous_anchored_through** — verified receipt in S3.

The client-visible durability watermark is their minimum. Local spool/CAS pins are reclaimed only through that watermark; a later successful sequence cannot hide an earlier gap.

## Canonical value path

~~~text
VM value
-> trace snapshot
-> canonical BLAKE3 DAG + local pack
-> .bamlvalue capture root + manifest pin
-> source-range chunk containing the relevant artifact/pack bytes
-> accepted S3 object
-> private rebuildable handle index
-> authorized ranged GET
-> canonical decode and budgeted hydration
~~~

ClickHouse may retain an opaque handle and availability/occurrence metadata. It may not retain pack bytes, bodies, previews, decoded JSON, scalar leaves or search indexes.

## Retention

Accepted S3 artifacts and canonical CAS content are immutable and retained indefinitely by default.

Ordinary maintenance may remove:

- uncommitted orphan uploads after a race-safe grace/delete-intent workflow;
- abandoned multipart state for object types that use multipart;
- expired temporary query/export results; and
- obsolete rebuildable projections/snapshots.

It may not age/size-evict accepted customer evidence. Future customer retention windows are policy-deferred.

## Explicit erasure

1. Authorize a supported tenant/project/environment/run erasure scope.
2. Deny logical access first.
3. Cancel active queries in scope; a snapshot does not preserve revoked access.
4. Tombstone PostgreSQL authority/work.
5. Remove S3 artifacts/CAS and every derived copy/cache/export.
6. Remove/rebuild affected ClickHouse projections.
7. Address replicas and backups according to the declared policy.
8. Verify each store and record durable audit evidence.

## Provider qualification

An S3-compatible provider is not supported until real-provider tests prove:

- full-object checksums;
- conditional create;
- version binding;
- IAM scope;
- presigned expiry/header binding;
- ambiguous-response resolution;
- listing/inventory behavior;
- deletion markers and reconciliation; and
- KMS behavior.

The current legacy **tracingv2** S3 publisher uploads a different JSON/gzip trace/blob protocol. It is not the new canonical Studio artifact/CAS path and supplies no canonical object-key layout for this design.
