# COMPOSITION analysis: where queries run and compose (BQL vs SQL)

## 0. Ground truth: what was actually decided and what exists

- The decision record: three surfaces were designed competitively — "SQL over DataFusion virtual tables; a purpose-built pipeline DSL; a BAML-native stdlib API" — judged under agent/human/implementer lenses. Pipeline DSL won human (8.5) and implementer (8); **the agent lens preferred SQL (8.5)** but "conceded that the DSL's trust machinery, made mandatory, resolves SQL's worst agent hazards (silent-empty results, opt-in completeness)" (historical design.md:750, already absent when archived). Decisive implementer argument: `bridge_wasm` gzip ceiling 4.5 MiB (`.cargo/size-gate.toml:88`) vs DataFusion "~2-4 MB compressed alone" = disqualifying (design.md:750).
- Adversarial caveat: the competing design docs and judge transcripts are NOT in the repo — "Prior docs referenced in design Appendix B ... are NOT in the repo. The historical design.md is the only spec" ([IMPLEMENTATION.md](../IMPLEMENTATION.md):25-26). The 8.5/8 scores are self-reported; the decision provenance cannot be independently re-verified.
- Decision: "one query engine (`bex_query`), one primary surface (BQL) ... sealed segments export to Parquet so DuckDB/DataFusion work *outside* the product as the unbounded-expressiveness escape hatch" (design.md:752). Principle 7: "One engine, one wire ... There are not two data planes" (design.md:109).
- As-built BQL v1 (`bex_query/src/bql.rs`) is a thin slice of the §8 design: set kinds RunSet/CtxSet/ValueSet/Table of the designed nine (bql.rs:709-722; design.md:766-778); stages `runs run ctx calls errors rollup where sort top stats limit values get instances vdiff` (bql.rs:805); errors E_PARSE/E_UNKNOWN_STAGE/E_TYPE/E_MULTI_RUN_CTX/E_BAD_ARG (bql.rs:40) + E_NO_EXACT_SOURCE (bql.rs:1299). The as-built `Completeness` footer is only `{sealed, torn, first_ts_ns, last_ts_ns, degraded[]}` (bql.rs:128-139) — far thinner than the designed meta `{complete, watermarks, capture_loss[], sources_consulted, truncated, next_cursor, warnings[], snapshot}` (design.md:797). Snapshot pinning, `--schema`, cursors, MCP tool, series/delta/diff, events/dumps stages are explicitly REMAINING (IMPLEMENTATION.md:652-654). Any "BQL beats SQL" claim must acknowledge most trust machinery is designed-not-built; what IS built works end-to-end (`baml q 'ctx() | top(5,by=total_ns)'` with dict-joined names, percentiles, footer — IMPLEMENTATION.md:614-620; values pipeline `values()|get()` e2e — IMPLEMENTATION.md:621-640).
- `bex_query` deps are tiny and lockfile-resident: base64, bex_events, memmap2(opt), prost, rustc-hash, serde, serde_json (bex_query/Cargo.toml) — no SQL engine, no async runtime ("sans-io ... No tokio in core", design.md:876).

## 1. Per-surface: what BQL needs vs what SQL would need

| Surface | BQL (as designed/built) | SQL alternative would need |
|---|---|---|
| **Local CLI (`baml q`)** | bex_query linked in; schema = static stage registry compiled into the engine (design.md:802); no auth; table/JSON render (q_command.rs, IMPLEMENTATION.md:611-613) | Embedded engine (DataFusion/DuckDB, multi-MB — baml-cli is itself file-size-gated per platform, size-gate.toml) + virtual-table adapters over BCCT/bamlmeta/CAS + catalog shipping + trust contract bolted outside SQL semantics (limits/footers via query rewriting) |
| **`/api/obs` WS (studio local + Runs tab)** | JSON `{op:"query"/"bql", q}` in → BQF1 binary out; errors as Status frames with code+remedy (obs_ws.rs; IMPLEMENTATION.md:460-466,605-608) | Same wire possible, but server-side SQL parse/plan + AST rewriting for mandatory bounds; caret-span typed errors with corrected queries much harder over general SQL |
| **wasm playground/VSCode** | THE structurally decisive surface: 4.5 MiB gzip ceiling; sans-io `Poll::NeedData` is "the only model that works identically for native mmap, wasm linear memory ... and HTTP Range requests, without an async runtime in wasm" (design.md:876). CctEngine already embedded in wasm drain emitting identical segment bytes (IMPLEMENTATION.md:585-589) | DataFusion disqualified by size alone (design.md:750); also needs an async executor and mmap-shaped IO wasm doesn't have. SQL-in-wasm is not merely costly, it's gated out |
| **MCP tool (agents)** | Identical semantics to CLI; `--schema` one-JSON-doc bootstrap; footer + fail-closed errors make autonomous use safe (design.md:857-859, 802). NOT BUILT yet (IMPLEMENTATION.md:652) | Steelman: agents have deep SQL pretraining — the agent lens scored SQL highest (design.md:750). SQL costs: silent-empty results, NULL semantics absorbing unknowns, no mandatory completeness — exactly the "worst agent hazards" the DSL's mandatory trust machinery resolves |
| **Studio ONLINE (cloud)** | Studio design independently rejects physical SQL as the public contract: "Physical SQL cannot be that contract because: local and hosted storage differ; physical tables change across projection generations; tenant scope and budgets must be mandatory; BAML types, value paths, coverage, and three-valued results need domain semantics; a local Codex agent should construct a safe plan without learning private database layouts" (studio-design §6.1, :420-432). Non-goal: "arbitrary raw SQL access to multitenant physical databases" (§4.4 :251; §23.8 :2805). So even a SQL-first LOCAL choice would still force a semantic layer in the cloud — i.e., SQL-as-surface guarantees two languages | Public cloud SQL requires tenant row-level security ClickHouse doesn't robustly give, per-generation schema stability SQL can't have (semantic AST is projection-generation independent), and budget injection by rewriting |
| **ClickHouse backend** | "[launch] BQL→ClickHouse compilation of the aggregate subset, prototyped **before** the cloud query API freezes, with a golden corpus in CI diffing local vs ClickHouse results" (design.md:849). Still listed REMAINING under P8 (IMPLEMENTATION.md:704). BQL is source language, SQL the compile target — the right layering | SQL-as-surface hits dialect skew: local engine SQL (DataFusion/DuckDB) ≠ ClickHouse SQL; "which dialect is the product" has no good answer |
| **Parquet/DuckDB export** | `export(format=jsonl|parquet)` sink (design.md:791); the deliberate escape hatch: users who want SQL get full SQL, outside the product, on sealed data (design.md:752) | This IS the SQL story — conceded, scoped, and shipped as an export rather than the trust surface |
| **In-BAML (`baml.obs`)** | §8.6 layering endgame: "wrap bex_query as a thin `baml.obs` stdlib module (one engine, two surfaces) — deferred, not v1" (design.md:854). See §2 below | SQL strings inside BAML: needs the SQL engine in every BAML host including wasm (re-disqualified), returns untyped rows |

- Honest precision on the size argument: the 4.5 MiB gate binds only `bridge_wasm` (size-gate.toml:78-88). A native-only local agent could carry DataFusion — and the TENTATIVE studio design in fact plans exactly that for ITS local agent: "Arrow/DataFusion for larger scans, grouping, and Parquet interoperability" (studio §10.7 :1156; §19.7 :2313 "Local query execution ... targets SQLite/DataFusion"). So "SQL engine impossible" is strictly true only for the wasm surface; for native it was a size/complexity/one-engine choice. This is a live contradiction between the two docs the decision document should surface: the shipped local design has ONE engine on all three hosts; the tentative studio doc assumes a different local stack (SQLite+DataFusion) for the same laptop.

## 2. The in-BAML story

- Grounding — how stdlib packages are shaped: packages live at `crates/baml_builtins2/baml_std/{baml/ns_*, assert, boundary, log, reflect, testing}`; functions are declared in `.baml` with `$rust_function`/`$rust_io_function` bodies, typed `throws`, named/optional params with defaults, and classes with methods (e.g. `sys.exec(program, args?, options: ProcessOptions?) -> ShellOutput throws root.errors.Io | root.errors.Timeout`; `ShellOutput.ok(self) -> bool` — ns_sys/sys.baml). Reflection exists: `reflect.type_of<T>() -> type`, `Signature`/`Arg` classes (reflect.baml). Precedent already in-tree: **`boundary/core.baml` is already an in-BAML observability surface** — `boundary.id() -> LocalId` with `.capture(inputs?, output?, error?)` controlling value capture from inside the program.
- Three candidate shapes for "calling the query surface inside BAML":
  1. **BQL string**: `obs.query("ctx() | top(5, by=total_ns)") -> ObsTable throws ObsError` — one function, stringly-typed results (a dynamic-column table class), typed errors map 1:1 to `BqlError{code,message,remedy}` (bql.rs:39-44). The static stage registry that generates the playground language service (design.md:802) could lint embedded strings, but results don't participate in BAML's type system.
  2. **SQL string**: same stringly problem plus the engine-embedding problem in every BAML host (wasm gate again) plus no path from rows to BAML classes.
  3. **Typed stdlib API**: `baml.obs.runs(last=..).calls(fn="extract_*").top(10, by=..)`. The pipeline shape is **method-chaining-isomorphic**: `source | stage | stage` ≡ `source().stage().stage()`; stage↔method, named-arg↔BAML named/optional param. This is why the wrapper can be "thin" (design.md:854) — it is a mechanical surface mapping onto the same planner, not a second implementation. SQL's SELECT/JOIN/subquery shape has no such isomorphism; embedding it typed is a LINQ-scale compiler project.
- Type-system composition is where BAML-native decisively beats both string forms: the designed typed hydration `get(as=MyType)` "decode against the capturing revision's schema, schema-erased JSON fallback" (design.md:850) becomes, in-BAML, `values.get<Invoice>()` returning the user's OWN class — compile-checked against the current revision, with revision mismatch as a typed error. The completeness footer becomes a field on the result class; studio's `include_unknown` three-valued results (studio :513) map naturally onto BAML unions/optionals, which SQL's NULL cannot represent (NULL-in-WHERE silently collapses unknown→false — the exact silent-empty hazard named at design.md:750).
- Composition consequence: BQL-as-pipeline is the only one of the three candidates where CLI text form, wire form, and in-BAML typed form are projections of one AST over one engine. The stdlib API alone (the third losing candidate) would have had this too — but no text form for the CLI/bug-report/copy-as-BQL loop (design.md:928 "every view's underlying query is copyable ('view as BQL')").

## 3. Schema composition with studio (field mapping and join keys)

- **Join keys align, and they are compiler-owned (already landed in P1)**:
  - `boundary_id`: local ULID `BoundaryId` `baml_id_1_...` (design.md:191), written in `boundary.bamlmeta begin{boundary_id, target, source, created_ms, project_id, revision_id, capture_defaults}` (design.md:613) ⇄ studio run root attachment `boundary_id -> (process_id, engine_id, thread_id, call_id)` (studio §12.6 :1288) and Run = "root attachment and BAML `BoundaryId`" (studio :326).
  - Revision/program identity: local `RevisionId` = BLAKE3-256 over source×toolchain×options, `baml_rev_1_` (design.md:269-281, §4.3 :328-340) ⇄ studio "program snapshot ... content digest over the normalized program/source/schema inputs defined by the compiler contract" (studio :354). Same idea; the studio doc does not name the `baml_rev_1_` formula — unification requires pinning both to §4.3. Studio adds deployment/build/release as separate optional dimensions (studio :354).
  - Function identity: local `definition_key` ("function:user.Extract") is "THE cross-revision join key" + `def_content_hash` change hints (design.md:291-296, :353-359) ⇄ studio `ProgramSchemaManifestV1` "stable definition key, FQN" (studio :1321). Same key, explicitly.
  - Call identity: local CallSet key `(run_id, thread_id, call_id)` (design.md:772) ⇄ studio ClickHouse row provenance "run/boundary/process/engine/thread/call identity" (studio §23.2 :2695).
  - CCT paths: cloud re-keys under `(tenant, revision_id, path_dict_id, path_id)` with parent-chase recovery (design.md:386) — the local node-id epoch-locality is already designed for cloud re-keying.
- **Mismatches one-language-over-both must absorb**:
  - Studio's observation kinds `model_attempt`/`tool_invocation`/`resource_operation` (studio :306-316) have no local set kind; local LLM data is per-call `LlmCallMeta` rolled into CCT counters, with streaming and retry-flag gaps documented (IMPLEMENTATION.md:296-304). Studio's per-attempt taxonomy (including failed attempts, studio :312) is richer; BQL would need an ObservationSet/AttemptSet kind or a lossy attempts→calls mapping.
  - **CID-as-primitive tension**: local BQL makes CID a query primitive (`stats(n=count(), by=cid)` for duplicate prompts — design.md:830-831, built: bql.rs StatsByCid :1155) but hosted multitenant explicitly rules "Raw SHA-256 of short values is not a safe general equality index. Equality search uses no token or a tenant-keyed versioned HMAC" (studio §23.5 :2767). A federated `by=cid` over cloud-indexed data violates the hosted indexing policy; it must run per-tenant (HMAC space) or against object-storage bodies.
  - Wire: local BQF1 columnar frames (design §9.3 :894); studio REST/JSON + "optional Arrow IPC later" (studio :2190-2193). Language ≠ wire, but a federated client needs both decoders.
- **Which language degrades better when half the schema is remote**: the semantic-pipeline side, structurally. (a) The sans-io engine already reads remote bytes — HTTP-Range `CacheSource` "open a shared boundary dir from a URL" (design.md:886, :936) — a degenerate federation with zero language change. (b) The designed footer carries `sources_consulted` + per-source watermarks (design.md:797), i.e., partial-source honesty is IN the result contract; SQL has no standard partial-failure semantics for federated tables — a missing remote shard is either an error or silently absent rows. (c) Projection-generation churn (studio :427) breaks physical-SQL queries but not semantic ASTs. Counterweight: BQL today has zero federation code, and StudioQueryV1 was invented independently of BQL — **the real risk is TWO semantic languages** (BQL text + StudioQueryV1 JSON) plus internal ClickHouse SQL plus external Parquet SQL, eroding "one engine, one wire" (design.md:109). They are unifiable — BQL's pipeline AST can serialize to/lower onto a StudioQueryV1-shaped semantic query (both are versioned typed ASTs with mandatory scope/budgets/coverage) — but no document currently commits to that unification; design.md:849's pre-freeze ClickHouse prototype is the only forcing function, and it is unbuilt.

## 4. Local footer vs studio coverage: same idea?

- Same genus — mandatory structured trust envelope on every result, "not a generic warning banner ... structured data used by the UI, CLI, Codex skill, tests, and automation" (studio :414); "mandatory, not opt-in" (design §8.4 :795) — different axes:
  - Local (designed): **evidence-plane completeness** — `{complete, watermarks, capture_loss[], sources_consulted, truncated, next_cursor, warnings[], snapshot}` computed "from the blocks the query actually touched" (design.md:797). As-built: `{sealed, torn, ts-range, degraded[]}` (bql.rs:128-139).
  - Studio: **fact-universe accounting** — `eligible/examined/matched/unknownByReason + durableWatermark + projectionWatermark` (studio :388-396, :546-556) with modes `strict_complete | best_effort | include_unknown` (studio :507-515).
- Mapping: local `capture_loss[]` reasons ⊂ studio's reason vocabulary, which already anticipates the local ones — "capture lost", "artifact truncated or corrupt" (= torn), "not indexed", "delayed projection" (studio :400-412); local `watermarks` ≈ `durableWatermark`; `projectionWatermark` is cloud-only (locally "disk is the database" — design.md:872 — there is no projection to lag); local snapshot pinning ("`--snapshot W` re-runs any query bit-identically", design.md:801) generalizes to studio's immutable evidence barrier for scans (studio :2111) and cursor-bound projection generation + durable watermark (studio :559).
- Modes: BQL has no coverage-mode parameter; its equivalent of `strict_complete` is plan-time fail-closed typing (`E_NO_EXACT_SOURCE` gating instances/exact stages — design.md:780, built bql.rs:1299) — stronger where it applies, narrower in scope. A `coverage=` argument on BQL is an additive fit.
- **Verdict on one trust envelope across a federated local+cloud query: constructible.** Union shape: per-source entries `{source, durable_watermark, projection_watermark?, sealed/torn, capture_loss[]}` + merged `unknownByReason` + a compound snapshot (local segment-set pin + cloud evidence barrier/generation). Studio's reason list is a superset of local's; local's reproducibility pin is stronger than studio's. Neither side's envelope is expressible as a SQL result set — both teams independently invented mandatory non-SQL envelopes, which is itself the strongest single piece of evidence that the query surface must own trust semantics SQL does not have.

## 5. Verdict material per deployment shape

- **(a) Local-only**: BQL, decisively. Shipped and working (IMPLEMENTATION.md:614-651); engine fits the wasm gate; trust contract native; O(pixels) responses (design.md:106); SQL power users get Parquet export → DuckDB (design.md:752). SQL-as-surface fails the wasm surface outright and duplicates the engine natively.
- **(b) Studio-online-only**: a semantic query layer regardless — studio's own §6.1 rules out physical SQL for tenancy/budgets/generations/three-valued-coverage reasons even with no local component. The open question in (b) is BQL-text vs StudioQueryV1-JSON, which are complementary forms (human/agent text vs machine wire), not rivals. Steelman for SQL here: the BI ecosystem (Grafana/Metabase/dbt) speaks SQL, and studio itself leaves the door open — "A later tenant-dedicated SQL capability requires independent database roles/policies, quotas, and audit" (studio :2805) — deferred, not denied.
- **(c) Federated local+cloud**: the strongest case FOR the BQL architecture and simultaneously its least-built part. Requirements: one planner splitting per source, "associative merge state" for cross-cell/cross-source aggregates (studio §19.7 :2311), per-source trust envelopes (§4 above), shared compiler-owned join keys (§3, landed). SQL federation would require schema identity both sides (false: BCCT segments vs ClickHouse projections) and cannot carry coverage. Mechanisms that exist today: HTTP-Range CacheSource (remote read), shared keys, BQF1. Missing: BQL→ClickHouse compiler ([launch] graft, unbuilt — design.md:849, IMPLEMENTATION.md:704), federation planner, unified envelope.
- **(d) User-BYO-warehouse**: SQL wins and the design concedes it by construction — Parquet/JSONL export is the sanctioned exit (design.md:752, :791; studio POST /v1/exports :2249) with the explicit boundary that projections/exports "cannot replace the artifact and semantic contracts" and are "not canonical evidence" (studio :256-259). Honest limitation to state: the trust envelope does not travel with a Parquet export — completeness/coverage would need to be materialized as sidecar tables/columns, or the export consumer simply loses the contract.

## 6. Additional adversarial-honesty items for the decision doc

- The agent-lens SQL preference (8.5) is on the record in the shipped design (design.md:750); the mitigations that answer it (`--schema` self-description, MCP tool, snapshot citations) are the exact parts still unbuilt (IMPLEMENTATION.md:652-654). The built mitigations are typed errors-with-remedy and the mandatory (thin) footer.
- The studio doc is explicitly TENTATIVE with decision labels (§0.1-0.2) and P-1 "must not require ... PostgreSQL, S3, SQS, or ClickHouse" (studio :204-208) — its DataFusion/SQLite local-agent stack (§10.6-10.7) predates/parallels the shipped bex_query reality and would be superseded by it under "one engine" (design.md:109); the decision doc should reconcile this explicitly rather than let two local stacks coexist on paper.
- The §8 design says the losing stdlib-API candidate survives as the layering endgame (design.md:854) and the losing SQL candidate survives twice: as the ClickHouse compile target (design.md:849) and as the Parquet/DuckDB export (design.md:752) — i.e., the shipped architecture is "BQL as the trust-bearing surface, SQL as a backend target and an export format", not "no SQL anywhere".
- Conformance discipline exists on both sides and should be merged: local golden corpus diffing local-vs-ClickHouse results in CI (design.md:849) ⇄ studio "semantic query conformance corpus must return the same normalized result and coverage locally and hosted" (studio §10.7 :1159).
