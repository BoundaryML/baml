# Research: baml-studio-design.md (all 3958 lines read) vs the query-language decision

Doc identity: historical `studio-design/baml-studio-design.md` (already absent when this corpus was archived), whose header claims "**Status:** Canonical implementation design, **Date:** 2026-07-27" (lines 3-4) — i.e. it *self-describes* as authoritative ("When this document disagrees with an older file, this document wins", line 30), but it predates the historical `design.md` (2026-07-30; also absent) and per the task framing is the TENTATIVE cloud Studio design. This matters for §5 conflicts below: both documents claim to own the query contract.

## 1. The semantic query contract (§6, lines 418-620)

**§6.1 "Why Studio uses a semantic query" (lines 420-433)** — the doc's own anti-SQL argument, verbatim reasons why "Physical SQL cannot be that contract":
1. local and hosted storage differ (SQLite/DataFusion vs ClickHouse);
2. physical tables change across projection generations;
3. tenant scope and budgets must be mandatory (can't trust callers to add WHERE tenant_id);
4. BAML types, value paths, coverage, and three-valued results need domain semantics;
5. "a local Codex agent should construct a safe plan without learning private database layouts."
The chosen unit: "The public query unit is `StudioQueryV1`, a versioned semantic AST" (line 434). Note carefully: this is NOT a pipeline DSL and not a text language at all — it is a **declarative JSON AST with SQL-shaped semantics** (select/where/orderBy/groupBy/measures/limit) minus SQL syntax.

**§6.2 Query shape (lines 438-479)**: JSON with `version, from, to, source, select, where {and:[{field,op,value}]}, orderBy, limit, coverage`. Schema supports: sources = observations/runs/events/values/logs/coverage/rollups; typed scalar fields; canonical BAML value paths; boolean filter composition; grouping+aggregates (`measures` with `count`, `quantile p:0.95` — Appendix C line 3860-3866); stable sorting+cursors; field projection; explicit or bounded-default time range; coverage mode; "row, byte, time, and scan-cost budgets" (line 478).

**§6.3 Canonical value paths (lines 483-506)**: "Dotted strings are ambiguous. Paths are structured" — role (input/output), argument by ordinal or name, segments (field / union arm / map key / list wildcard). JSON form `{"role":"input","argument":{"name":"request"},"segments":[{"field":"customer"},{"field":"email"}]}`. "Each path has a canonical encoding and scoped digest. Display strings are derived and never used as the authoritative key" (line 505).

**§6.4 Coverage modes (lines 509-515)**: `strict_complete` (structured coverage error unless every eligible fact evaluated), `best_effort` (matches + unknown counts/reasons), `include_unknown` (three-valued `true/false/unknown(reason)`). "The mechanism is locked. The default mode in the human UI remains a product decision" (line 515); §17.5 (2093-2100) recommends best_effort for humans, strict_complete for gates; open question Q6 (3670-3676).

**§6.5 Explain before execute (lines 517-534)**: every backend implements `query explain` returning normalized query, required datasets/fields, interactive-vs-deferred-scan classification, estimated eligible artifacts/rows/bytes, expected coverage limitations, chosen execution path, enforced budgets, "no physical credentials or unsafe SQL" (line 534).

**§6.6 Stable response envelope (lines 536-559)**: `{schemaVersion, query:{normalizedHash}, data, nextCursor, coverage:{status,eligible,examined,matched,unknownByReason,durableWatermark,projectionWatermark}, diagnostics}`. "A cursor binds scope, query hash, sort key, semantic schema version, projection generation when hosted, durable watermark, and expiry. It is opaque to callers" (line 559).

**§5.8 Coverage concept (lines 384-414)**: reason taxonomy — not emitted / capture disabled / omitted by policy / redacted / capture lost / artifact missing / truncated-corrupt / unsupported version / not indexed / expired / delayed projection. "Coverage is not a generic warning banner. It is structured data used by the UI, CLI, Codex skill, tests, and automation" (line 414). §23.7 (2773-2791) gives the non-overlapping precedence ladder so totals reconcile.

**§7 Natural language via local Codex (lines 563-620)**: "Studio does not need an embedded LLM to answer natural-language questions correctly." Flow: question → inspect capabilities + query schema → construct StudioQueryV1 → `query explain` → execute bounded → inspect coverage → fetch runs/values/source → cited narrative (570-578). §7.1 CLI primitives (584-595): `capabilities`, `schema query`, `query explain`, `query run`, `observations show`, `runs show/graph/profile`, `values read`, `source show` — all `--format json`. **§7.3 (615-619), the integration-boundary claim**: "The Codex skill never generates ClickHouse SQL or parses human-formatted terminal tables. It generates `StudioQueryV1` and consumes versioned JSON responses. This also allows other agents, scripts, editor integrations, and future natural-language interfaces to share the same contract." Locked decision table repeats it: "`StudioQueryV1` is the local/hosted/agent contract | no physical SQL or formatted text dependency" (line 3613) — note "formatted text dependency" arguably cuts against a *text* DSL too, not just SQL.

## 2. Studio's data model (§5.x, lines 265-414; analytical §16, §22-23)

- **Artifact (§5.1, 267-282)**: canonical = `.bamlprof`, `.bamlvalue`, content-addressed blobs, source/schema snapshots, run/root attachments, completion manifests, commit receipts. "A ClickHouse row, SQLite row, Parquet export, or browser snapshot is a projection, not canonical evidence" (line 281).
- **Event (§5.2, 284-288)**: one immutable runtime/adapter fact; several events may describe one operation; not the default browsing row.
- **Observation (§5.3, 289-318)**: user-facing operation assembled from facts; fields: stable identity, kind+schema version, containing run, parent/root correlation, start/end, state+outcome, function/provider/tool/resource identity, value/metadata refs, evidence+coverage state, provenance. Kinds capability-versioned: `run`, `baml_call` (current artifacts), `model_attempt`, `tool_invocation`, `resource_operation` (post provider-branch). Unknown kinds → `unsupported_observation_kind` coverage, never dropped (line 318).
- **Run (§5.4, 320-341)**: causal graph rooted in a root attachment + `BoundaryId`; explicitly "not defined by timestamps"; independent state axes (execution/structural/value/integrity/projection/retention — §26.1, lines 2979-2991). Cross-process = related runs with correlation links, not merged (Q2, 3639-3644).
- **Program snapshot (§5.5, 342-359)**: content digest over normalized source/schema; deployment/git/release are separate alias dimensions (PG `program_snapshots` + `program_snapshot_aliases`, 2479-2492). Maps closely to design.md's `revision_id`/`source_snapshot_id` (§4.2-4.3) — the concepts are compatible, names differ.
- **Effective schema (§5.6, 360-367)**: TypeBuilder-modified schemas need runtime-emitted digest+overlay; "Studio does not reverse-engineer a runtime schema from returned values"; until then, partial coverage. design.md has no effective-schema concept at all.
- **Application context (§5.7, 369-380)**: bounded indexed tags; reserved `user_id`/`session_id`; freezes at observation start. design.md has nothing comparable (no tag dimension in CCT or BQL v1).
- **Coverage (§5.8)** — see above.
- **Analytical shapes (§16)**: `ObservationSummaryV1` vs `ObservationDetailV1` logical split (1800-1812, locked); `observations_active_v1` bounded rebuildable active index (1813-1836); `observations_terminal_v1` immutable row-per-observation with full field list (1839-1889); run-detail datasets (1892-1906); rollups recomputed post-watermark, never insert-triggered (2024-2037).
- **ClickHouse tables (§23.3, 2703-2726)**: observations_active/terminal, runs, calls, threads, graph_edges, operation_events, function_definitions/parameters, call_inputs/outputs/errors, captured_values, value_nodes, logs, capture_losses, engine_liveness, run_dataset_coverage, path_coverage, function_rollups_1m, projection_visibility, projection_integrity_conflicts. "Only named semantic serving views are queryable by the API" (2728).
- **Value indexing (§23.5, 2749-2767)**: capture (none/summary/exact) independent from index (top_level/allowlisted_paths/full_scalar_bounded); exact bodies stay in object storage; "Raw SHA-256 of short values is not a safe general equality index. Equality search uses no token or a tenant-keyed versioned HMAC" (2767) — a direct caution against naive CID-equality search in a multitenant setting (design.md's CID-as-query-primitive is single-tenant local, so not contradictory, but the cloud path must not reuse raw CIDs as equality tokens).
- **Relation to local CCT design**: the studio model is **per-call/per-event shaped** (calls_v1, one terminal row per observation, value_nodes rows). design.md's model is **aggregate-CCT shaped** (one row per unique calling context per 250ms window; exact calls exist only in the 4096-slot recent ring, flight dumps, and opt-in full trace — design.md §8.2 CallSet "exact instances... flight dumps, full traces ONLY"). Studio-design assumes per-call structural events remain the canonical artifact (`.bamlprof` structural records, §5.1); design.md §1 explicitly abandons "one disk event per call" (1.69 GB / 38.5 TB/day measurement, design.md line 99). This is the deepest schema-level divergence: a Studio `baml_call` observation list ("list recent failed observations") is unanswerable from CCT aggregates alone except at context granularity or within the exact-evidence windows.

## 3. Part III+ storage/upload/cloud-query/SQL/warehouse/export findings

- **Hosted stack (§13.2, 1433-1448)**: Terraform, ECS/Fargate, S3 canonical artifacts, SQS Standard pointers, PostgreSQL control, **ClickHouse Cloud** analytical projections, static TanStack SPA, OIDC. Explicit non-dependencies: Kubernetes, Lambda (backend), Kafka, Kinesis, Redis, SNS, EventBridge, ClickPipes, browser-held DB credentials (1446).
- **Authorities table (§11.1, 1181-1189)**: S3+receipts = exact evidence; PostgreSQL = control/correctness; SQS = replaceable pointers "never evidence"; ClickHouse = rebuildable projections; SQLite control/catalog local. Invariant 9 (1200): "One semantic implementation. Local, hosted, offline, CLI, browser, and Codex adapters share reconstruction and query semantics."
- **Local analytical execution (§10.7, 1150-1159)**: direct Rust for point reads; SQLite for discovery; **Arrow/DataFusion for larger scans**; "cached Parquet only as a rebuildable acceleration format"; conformance corpus must match locally and hosted. (Conflicts with design.md §8, which disqualifies DataFusion in wasm on size-gate grounds — see §5.)
- **Hosted query execution (§19.7, 2298-2314)**: PG resolves scope/generation → "semantic validator injects scope, time, fields, coverage, and budgets" → point reads route to owning cell → project-wide analytics run "bounded ClickHouse subqueries per cell" → API merges "only typed partial aggregates or ordered cursors" (associative merge state, composite cursors). Never streams high-cardinality scans through PG.
- **SQL bans**: §4.4 non-goals: "arbitrary raw SQL access to multitenant physical databases" (line 252); "ClickHouse, Parquet, OTLP, or SQLite as canonical evidence" (256). §23.8: "Hosted multitenant v1 exposes no arbitrary raw SQL. A later tenant-dedicated SQL capability requires independent database roles/policies, quotas, and audit" (2805) — i.e. tenant SQL access is contemplated as a *possible later capability*, not v1. §19.6: errors "never include... database SQL" (2294). Internal SQL discipline §24.2 (2819-2829): SQLx checked macros, "User text never enters SQL syntax."
- **BYO-warehouse**: **absent**. No BYO-warehouse or customer-warehouse-sync story anywhere. The nearest things: (a) Parquet/OTLP export — P-1 CLI `baml studio export PATH --format json|jsonl|parquet|otlp` (1060), with "OTLP export is an explicitly lossy interoperability projection... does not make OTLP or the evolving OTel Profiles model canonical" (1066) and "Adapters and exports may interoperate with OTel/Parquet" (259); (b) P1 "richer exports" (237) / "advanced export" (§18.6, Phase 1 line 3581); (c) Enterprise = customer-managed PostgreSQL/ClickHouse/S3 endpoints (§29.2, 3269-3280) — customer *hosts* the same stack, not a warehouse integration.
- **Deferred scans (§18, 2104-2122)**: interactive queries exceeding index/byte/time limits are rejected or promoted to audited, cancellable, separately-queued scans over retained artifacts through the shared decoder — the mechanism for unindexed nested-path queries. design.md/BQL has no scan concept (bounded-by-construction instead).
- **Conformance (§31.2, 3384-3392)**: every StudioQueryV1 fixture runs against in-memory reference evaluator, local SQLite/DataFusion, hosted ClickHouse; compare normalized rows/order/cursors/aggregates/coverage; three-valued behavior tested.

## 4. Query-capability checklist a query language must satisfy (from §2-§3)

From §3's question table (165-186) and §2.1 workflows (100-163):
1. List/filter recent observations by: status/terminal outcome, function, observation kind, provider, model, environment, release, tag, user/session context, time range (§2.1 "Find what went wrong"; §3 rows 1, 9).
2. Sort by duration; drill from list into run timeline/flame; inclusive vs self time; provider-attempt and tool timing (§2.1 "Understand a slow execution").
3. Bounded aggregate queries + drill-down: "Which function became slower after a deployment?" needs function identity × program/deployment dimensions × timing, cohort comparability reporting (§3 row 3; §2.1 "Compare behavior" — latency, failure-rate, token, cost, output-shape changes across functions/providers/models/releases/environments/snapshots).
4. Value-shape queries on summaries: "outputs whose top-level enum variant is Rejected" — indexed semantic query with schema/capture/index coverage (§3 row 7).
5. Nested value-path predicates: "values where request.customer.email ends in .edu" — interactive if indexed, deferred scan otherwise (§3 row 8; §17.2).
6. Application-context queries: all work for user 123 / session abc; "absent context is different from a user with no activity" (§3 row 9).
7. Point reads: exact value for a call (availability reason on miss), run graph/profile/source/logs (§3 rows 10; §7.1).
8. Usage/cost aggregation from emitted facts only, with provider-omitted usage as explicit unknowns (§3 rows 5; §17.3).
9. Coverage on every answer; "never converts 'no matching indexed row' into 'definitely no matching execution'" (line 186); three-valued results.
10. Explain-before-execute with cost estimate and scan classification (§6.5).
11. Budgets: row/byte/time/scan-cost, mandatory scope/time bounds (§6.2, §23.8).
12. Stable cursors + versioned envelope; capability/schema discovery for agent bootstrap (§6.6, §19.5).
13. Identical semantics local and hosted (invariant 9; §31.2).
14. Honest absence: "fact not emitted" for CPU/wait time etc. (§3 last rows).
15. Distinguish app failure from missing telemetry / delayed projection / redaction (§2.1).

## 5. AGREE / CONFLICT: studio-design vs historical design.md (+ as-built BQL)

**Neither document knows the other's query language.** grep confirms zero occurrences of "BQL" or "pipeline" query in studio-design.md; zero occurrences of "StudioQueryV1"/"semantic query" in design.md. Each defines its own contract and each claims canonicity (studio line 3/30/3613 vs design.md title "Canonical Design" + §8 "Decision: one query engine... one primary surface (BQL)"). design.md is 3 days newer and is what shipped (IMPLEMENTATION.md:597 "BQL v1 LANDED", bex_query/src/bql.rs).

AGREEMENTS (strong):
- **Both reject raw SQL as the public surface, for overlapping reasons.** design.md §8 (line 750): SQL lost on agent hazards ("silent-empty results, opt-in completeness") and the decisive wasm size gate (DataFusion ~2-4 MB compressed vs 4.5 MiB gzip ceiling). studio §6.1 (426-432): storage divergence, projection-generation churn, mandatory tenancy/budgets, domain semantics, agent safety without private layouts. Studio adds multitenant arguments design.md never needed (tenant scope, generations); design.md adds the binary-size argument studio never considered.
- **One engine / one contract everywhere**: design.md principle 7 "One engine, one wire" ≈ studio invariant 9 + §7.3 integration boundary.
- **Mandatory completeness with every answer**: design.md §8.4 footer `{complete, watermarks, capture_loss[], sources_consulted, truncated, next_cursor, warnings, snapshot}` ≈ studio §6.6 coverage `{status, eligible, examined, matched, unknownByReason, watermarks}`. Same philosophy ("Empty is explained" / "A zero-match result with unknowns is not a trustworthy negative answer", studio 2073), different vocabularies — reconcilable by mapping.
- **Fail-closed typed errors**: BQL `E_NO_EXACT_SOURCE/E_MISSING_BLOCK/...` with remedies (design §8.4.3; bql.rs:40,1299) ≈ studio §19.6 typed error codes incl. `coverage_incomplete`.
- **Explain**: BQL `--explain`/`explain()` sink ≈ studio `query explain` (studio's is richer: cost estimates, scan promotion).
- **Agent-first NL architecture**: both put the LLM outside the deterministic query layer; agent constructs typed queries, checks completeness, cites re-verifiable evidence (design §8.7 MCP + `(query, snapshot)` pairs ≈ studio §7 Codex + normalizedHash/coverage).
- **Parquet/Arrow as export/acceleration only, never canonical** (design §6.2 ruling line 575, §8 escape hatch; studio 256, 281, 1158).
- **ClickHouse as the hosted analytical backend with a local↔hosted golden conformance corpus**: design §8.6 "[launch] BQL→ClickHouse compilation of the aggregate subset, prototyped before the cloud query API freezes, with a golden corpus in CI" ≈ studio §31.2 conformance across reference/SQLite-DataFusion/ClickHouse.
- **Local-first, no cloud required** (design principle 6 ≈ studio P-1 §4.1).
- **Content/program identity**: revision_id/source_snapshot_id/definition_key (design §4) ≈ program snapshot digest + aliases (studio §5.5, 2479); ULID BoundaryId ≈ studio run/BoundaryId.

CONFLICTS (adversarially honest):
1. **Representation**: StudioQueryV1 = declarative versioned JSON AST (SQL semantics, no syntax); BQL = human-typed pipeline text DSL. Studio's locked decision even excludes "formatted text dependency" (3613). BQL text must be parsed (lexer/AST in bql.rs); studio argued agents should emit ASTs directly. Counterpoint for the decision doc: BQL ships `--schema` self-description + typed corrected-query errors (design §8.4.6), and the AST-vs-text gap is a serialization detail — BQL's planner produces a typed `PlanStage` pipeline (bql.rs:753) that could be exposed as the AST.
2. **Underlying evidence model**: studio assumes per-call/per-event canonical artifacts and one terminal row per observation; design.md's core thesis is that per-call disk events are the disease (38.5 TB/day) and replaces them with CCT aggregates + bounded exact windows. Studio's "list recent failed observations" (per-call) has no complete backing store in the CCT design — BQL encodes this as the CtxSet/CallSet type split and `E_NO_EXACT_SOURCE` (design §8.2); studio encodes the analogous honesty as coverage reasons. Reconcilable in philosophy, irreconcilable in schema without one side moving.
3. **Nested value paths**: studio §6.3 structured canonical paths + indexed value_nodes + deferred scans are a core requirement (§3 row 8). BQL v1 has no path predicate at all (values(role, fn-glob)/get/vdiff only, bql.rs:805; IMPLEMENTATION.md:630); design.md's answer is CID equality + bounded hydration with child-CID descent — a different primitive. Gap in BQL vs studio's capability checklist item 5.
4. **Coverage modes**: studio has caller-selected strict_complete/best_effort/include_unknown; BQL has one behavior (always-on footer; caller inspects). No strict-mode error in BQL. Minor, additive.
5. **Deferred scans & budgets**: studio's interactive/scan promotion, scan-cost estimation, and row/byte/time/scan budgets vs BQL's bounded-by-construction (default 1000 rows, 64 KiB get, byte-budgeted caches). BQL has no long-running-scan story.
6. **DataFusion**: studio prescribes Arrow/DataFusion for local large scans (1156); design.md disqualifies DataFusion (wasm size gate) and hand-rolls (750). Not strictly contradictory (studio's DataFusion is native-agent-side) but they made opposite bets on the same component.
7. **Governance**: studio says StudioQueryV1 is "Locked" as *the* local/hosted/agent contract (3613); design.md says the cloud query API is *not frozen* and BQL→ClickHouse is its forcing function (§8.6, phase P8 line 1016, OQ line 1041). Whoever writes the decision doc must state which contract governs the cloud surface.
8. **Application context / tags / user-session dimensions**: required by studio (§5.7, Q3), absent from design.md's data model and BQL v1 entirely.
9. **Observation abstraction**: studio's kind-versioned observation (model_attempt, tool_invocation...) has no BQL analogue; BQL's sources are runs/ctx/dumps/trace/health/audit. design.md's LlmCallMeta covers a subset of model_attempt facts (model, tokens, error flags — design §5.4) but no attempt/tool taxonomy (consistent with studio's own note that those await the provider branch, §9/P0-B).

As-built BQL v1 ground truth (bex_query/src/bql.rs): stages = "runs, run, ctx, calls, errors, rollup, where, sort, top, stats, limit, values, get, instances, vdiff" (bql.rs:805); errors E_PARSE/E_UNKNOWN_STAGE/E_TYPE/E_MULTI_RUN_CTX/E_BAD_ARG (bql.rs:40) + E_NO_EXACT_SOURCE (bql.rs:1299); Completeness footer {complete, sealed, torn, first/last_ts_ns, degraded[]} (bql.rs:129-141); DEFAULT_ROW_LIMIT 1000 (bql.rs:30); BQF1 frame emission (bql.rs:165). Not yet built: MCP tool, series/delta/diff align=fqn, studio query box (IMPLEMENTATION.md:652).

## Synthesis-relevant net takeaways
- The strongest steelman for "why not SQL" is that BOTH independent design efforts — the local one (design.md §8, competitive 3-judge bake-off where SQL won only the agent lens) and the cloud one (studio §6.1, five structural reasons) — rejected raw SQL, for partially disjoint reasons (wasm size + agent trust locally; tenancy/generations/budgets/layout-privacy in the cloud). SQL survives only as: (a) export escape hatch (Parquet → DuckDB/DataFusion outside the product, design 752), (b) a possible later audited tenant-dedicated capability (studio 2805), (c) internal implementation detail (SQLx/ClickHouse behind the semantic layer).
- The real open fault line is not SQL-vs-not-SQL (both agree) but text-pipeline-DSL (BQL) vs declarative-JSON-AST (StudioQueryV1), and per-call observation schema vs CCT aggregate schema. Any decision doc should note these are the alternatives actually in tension, and that BQL's typed plan + --schema self-description + BQL→ClickHouse compilation prototype (design §8.6) is the stated reconciliation path.
