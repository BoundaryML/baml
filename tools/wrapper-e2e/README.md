The shared wrapper conformance suite is written in BAML. It starts real Rust or packed BAML wrappers in isolated homes, uses an independently compiled configurable `baml-cli` stub, and serves real release manifests and archives over a loopback HTTP server. The fixture helper only prepares OS resources and serves requests; it never invokes the wrapper or installs a managed toolchain for an installation test.

Run `python3 tools/wrapper-e2e/run` from the repository root. This builds an independent compiler, pack host and stub, snapshots both Rust self-update variants, packs both BAML self-update variants, and runs identical scenarios against all four candidates. It reports PASS, FAIL or SKIP for each scenario and implementation and returns nonzero on any failure. `--filter S12` selects IDs by substring. `--target <triple>` also builds the wrappers and pack host for that platform while retaining an independent native compiler/test runtime.

For a prebuilt candidate, use `--no-build --candidate '{"label":"baml","command":["/absolute/path/to/baml"],"self_update":true}'`. Repeat `--candidate` to compare implementations or pass a command prefix in `command`. Adapters pass arguments unchanged and do not repair fixtures. Each scenario has a descriptive function and an adjacent `test` entry in a behavior file under `baml_src/` (for example, `selection.baml`, `installation.baml`, or `telemetry.baml`). These entries expose the same scenarios to `baml test` using the environment variables set by the runner. `scenarios.baml` registers the stable catalog IDs and their callbacks; `harness.baml` owns candidate iteration, fixture/server cleanup, capability exclusions, and shared assertions. To add a scenario, write its setup, invocation, and assertions in the relevant behavior file, add its adjacent `test` entry, and register the callback. Scenario functions do not branch on catalog IDs.

Each fixture starts in an unpinned `project/` with global default `0.11.0`. Versions `0.11.0`, `0.12.0`, and `0.13.0` are already installed; canary is recorded at `0.11.0` and nightly at `0.12.0`. Local stubs identify themselves as `L1` under the project root and home, and `L2` under the nested working directory and outside the project. Tests change this baseline explicitly before invoking a candidate.

Release gates use `--release-artifacts <downloaded-artifacts-dir> --target <triple> --wrapper-version <version>` to test the exact uploaded Rust and BAML archives. The runner requires every variant shipped for that target in `release/platforms.json`, stages each archived executable unchanged, and fails on missing or ambiguous archives. The harness, compiler, and fixture stub are still built independently. Run `python3 -m unittest discover -s tools/wrapper-e2e -p 'test_*.py'` to check staging for tar/zip archives, shipped variants, and invalid archive contents.

Scenario IDs follow the wrapper test catalog: S covers precedence and discovery, L covers local paths, I covers installation and recovery, M covers management, V covers version reporting, E covers configuration/state errors, and W covers wrapper replacement. R covers JSON resolution, U covers passive freshness and offline retry throttling, and D covers human-readable errors. T covers independent wrapper PostHog events, opt-out, delivery retries, queue recovery, and operation outcomes; candidates enable this capability with `"posthog": true`. F adds argument rejection and stdio regression cases, including simultaneous large stdin/stdout/stderr transfers and non-UTF-8 bytes. Every delegation checks the full new invocation list, identity, argument array, cwd and direct-CLI guard. Installation assertions check release requests and installed metadata. Management assertions check selection changes and subsequent launches.

Windows paths, suffix handling and replacement run on Windows. Symlink tests require privileges on Windows and are explicitly excluded there. POSIX permissions are tested on POSIX. Self-update cases are selected by the candidate's build capability; replacement always operates on a fixture copy. I20 requires a binary built for an unsupported host and is explicitly excluded from the supported-target matrix. The platform resolver's unsupported-target unit tests cover its diagnostic. All release targets, including both Linux libc variants and both Windows architectures, are scheduled by `.github/workflows/wrapper-e2e.yaml` using the repository platform contract.

All fixture invocations disable telemetry by default with `DO_NOT_TRACK=1`. Telemetry scenarios explicitly opt in only against the fixture's loopback capture server. Harness/compiler builds also opt out. Capture assertions cover both wrapper implementations and self-update variants without contacting production PostHog.
