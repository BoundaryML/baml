Testing tool calling for gpt realtime: baml vs native

Two real gpt-realtime-2.1 sessions over the Realtime WebSocket API, fed the same microphone audio and the same text. They differ in exactly one place: who turns your words into a tool call.

This page shows the recorded runs. The live side-by-side arena needs a long-lived WebSocket server, so it runs locally: npm start in tools/experiments/benchmarking-realtime/server, then open http://localhost:8788.

The setup

The native lane is the setup most realtime apps ship. Tools are declared as JSON schemas in session.update, and the voice model itself picks a tool and extracts the arguments while it talks.

The baml lane gives the voice model a single tool, delegate(request), and prompts it to pass the utterance through verbatim; spelled-out letters, fractions and all. A BAML function then does the tool selection as one structured decode into a typed union, and the tools themselves run in the BAML VM:

// brain/baml_src/thinker.baml
function DecideAction(history: string, request: string, now_iso: string)
    -> GetWeather | LookupOrder | SetTimer | CreateCalendarEvent | SendMessage | Answer {
  client Thinker  // claude-sonnet-4-6
  prompt #"
    Order IDs are precise alphanumerics: normalize to uppercase, keep dashes.
    Timer durations must be converted to whole seconds.
    Calendar events: resolve relative dates against {{ now_iso }}.
    {{ history }} {{ request }} {{ ctx.output_format }}
  "#
}

function handle(history: string, request: string, now_iso: string) -> ToolOutcome {
  execute(DecideAction(history, request, now_iso))  // runs the chosen tool in the VM
}

The executors are shared (the native lane's function calls are routed into the same BAML functions), so any difference between the panes is purely tool selection and argument extraction. Everything lives in two small projects:

brain/baml_src/
  types.baml     the action union (weather, orders, timer, calendar, message, answer)
  thinker.baml   the Thinker client + DecideAction + handle()
  tools.baml     executors: open-meteo weather, order DB, timers, calendar, contacts
  tests.baml     deterministic executor tests (baml test)

server/src/
  relay.ts       one WebSocket per lane; delegate vs native session config
  compare.ts     the benchmark harness below (three suites)
  index.ts       the live arena + the dual-session bridge

Every turn from both lanes, in the arena and in the benchmark harness, is logged to a Convex database (experiments/turns) with the raw args, executor payload, and latency.

What the runs showed

BAML went 25/25 across the base, hard, adversarial, and ultra suites. Native went 23/25, and its two misses are the interesting part. One was argument extraction on confusable phonetics: "queue five are six…" lost the Q. The other was an indirect location: "where the golden gate bridge is" got passed to the weather tool as a literal city name. Native is also about twice as fast per turn, since there's no second model hop. That's the trade. The ultra suite (compound dose math, unit conversion, phonetic drug codes) ended 6/6 for both lanes; the one native stumble we caught there, refusing to call the tool on an ambiguously phrased phonetic request, didn't repeat on a clean rerun, so we don't count it.
