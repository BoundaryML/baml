Telemetry Bench

We wrote the same four small programs in BAML and in Python, traced them with Boundary Cloud (BCS), Pydantic Logfire, Datadog and plain OpenTelemetry, and measured what each one sends, stores, costs and loses.

Short version

What we found

    The setup

    Same program, four ways to watch it

    Each app runs in a fresh process against a fake model server on the same machine, so the network and the model never add noise. The four apps grow in size: hello (no model), classify (yes/no about a document), extract (pull an invoice into a class) and agent (two model calls and a tool, where the first reply attempt fails with a 503 and is retried).

    BAML

    function Classify(text: string) -> bool {
  client: Model
  prompt: `
    Is this document an invoice?
    Reply with only true or false.
    ${text}
  `
}

    Tracing setup: none. Set BOUNDARY_API_KEY and every LLM call is recorded with its inputs, output and raw HTTP exchange.

    Python + Logfire

    import logfire
logfire.configure(service_name="bench")
logfire.instrument_openai()

@logfire.instrument()
def classify(text):
    reply = ask(f"Is this document an invoice? ...\n{text}")
    return reply.strip() == "true"

    Datadog looks much the same (LLMObs.enable plus @workflow). Plain OpenTelemetry needs its own exporter, provider and decorator.

    Bytes on the wire

    BAML records the whole exchange, so it sends more

    BAML records every model call's raw HTTP request and response next to the function's inputs and output. The others record less by default: Logfire keeps function arguments and the chat messages but not return values, and OpenTelemetry's OpenAI instrumentation keeps no message text on spans at all. Logfire and OpenTelemetry also gzip what they send; Datadog and BAML send it uncompressed. Pick a document size to see bytes sent per call. Why Logfire's numbers move so much is explained further down.

    Repeated input is nearly free on the wire

    BCS stores content by hash. Ten identical 100 KiB calls sent from BAML versus for ten different ones. Logfire's gzip gets part of that saving ( vs ). Datadog sends uncompressed JSON, about 207 KB per call either way. The bill does not shrink: BCS counts every reference.

    Deep dive · Logfire's payload

    Why Logfire's byte counts swing so much

    The same 10 KiB prompt cost Logfire 2.2 KB per call in our first run and 15.9 KB in the second. Neither number was a measuring error. We decoded every export Logfire sent and found that three things decide its size: how many copies of the prompt each call carries, how far apart those copies sit in the export, and how well the text compresses.

    1. Each call carries the prompt twice

    A traced classify call becomes two spans. The function span records the argument, and the model span records the chat messages, which contain the same document after the instruction line. About 2 KB of metadata comes on top: a JSON schema for the attributes, the message template, tags and code location.

    A third copy appears only for a span that is still open when an export fires. Logfire then sends a "pending" placeholder with the arguments. That happened to 2 of 22 spans in most of our runs and to none at 100 KiB.

    2. gzip only looks back 32 KB

    Logfire gzips each export. gzip saves bytes by pointing back to text it has already seen, but only within the last 32 KB. The export groups spans by instrumentation scope, so all the model spans come first and all the function spans after them. The two copies of one prompt end up several spans apart. The diagram shows one export holding ten 10 KiB calls.

    Real exports split the ten calls over two requests, but the effect is the same: with ten different 10 KiB prompts, the copies were 43 to 83 KB apart and gzip paid for both. At 1 KiB some copies land inside the window, which is why the red line starts lower. When every call sends the same prompt, each copy has an identical neighbor one span back, and gzip makes it almost free, until the document reaches 32 KiB and the neighbor falls out of the window. The chart shows how many gzipped copies of the prompt each call costs.

    The y-axis divides bytes sent per call by the size of one gzipped document. The dashed line recompresses the same exports with lzma, whose window is 8 MB: it finds the duplicates at every size. Our first run varied only a short suffix on one document, so at 1 and 10 KiB it measured the cheap case.

    3. Prose compresses, random characters don't

    Our main tests use random characters, the worst case for gzip, so text can't hide size. Real prompts are mostly prose. We reran the comparison with English text from Python's documentation, which gzips to about a third of its size. Logfire and OpenTelemetry sent about half as much. Datadog and BAML send uncompressed, so they didn't change.

    What this means

    • Expect the gap to be wider with real prompts. With 10 KiB of prose, BAML sends about Logfire's bytes per call, against 2.5× with random characters.
    • Repeated context is cheap only when it is small. A fixed system prompt or few-shot block under about 10 KiB costs Logfire almost nothing on the wire after the first call. From 32 KiB it costs full price every time.
    • None of this changes Logfire's bill. Logfire charges per record, two per classify call at any size. It does matter for network egress and for Logfire's soft guideline of about 5 KB per span: the model span holds the whole prompt.
    • BCS's bill doesn't move either. BCS bills uncompressed captured bytes, so prose and random characters bill the same ( vs for ten 10 KiB calls).
    Cost

    Who is cheapest depends on the shape of your data

    The three products bill different things. BCS bills captured data by the gigabyte, and spans are free. Logfire bills per span or log record. Datadog LLM Observability bills per model call. Move the sliders to match your app. The defaults are our measured classify app with a 10 KiB document.

    Prices are the published list prices on 7 November 2026, after free tiers: BCS Starter $4/GB, Logfire $2 per million records, Datadog LLM Observability $3.50 per 10,000 LLM spans. Logfire does not charge by size, but says it may email customers whose spans average over about 5 KB; most of the spans here are bigger. Datadog also has a $160/month minimum, and APM spans for non-model steps are billed separately. Measured billed bytes come from replaying BCS's billing rules over the exact upload bodies.

    Scenario · a support chatbot

    A long chat resends the whole conversation every turn

    We built the same support bot in BAML and in Python: a 4 KB system prompt, a customer message each turn, an order-lookup tool on every other turn, and a 600-character answer. Like every chat app, it sends the entire conversation to the model on each call. We played conversations of 1 to 50 turns through each platform, one fresh process per conversation, with a mock model that takes 1 second per call. BAML's uploads went to the real BCS.

    What BCS caches

    Batching decides what gzip can reuse

    Each call's history is the previous call's history plus one turn, so a compressor that still sees the earlier copy can skip most of it. gzip sees only the last 32 KB of the same export. OpenTelemetry exports every 5 seconds, about five calls at a time here, so it skips repeats until the conversation passes 32 KB around turn 20, then pays for every call in full. Logfire exports every half second, one call at a time, and also sends a "pending" copy of each span still open at export time, so it sends about as many bytes as the prompts themselves. BCS and Datadog don't compress.

    What BCS can and can't cache

    BCS stores what it captures as content-addressed pieces: a piece's ID is a hash of its bytes, so the same bytes always get the same ID, and the BAML client skips uploading a piece it already uploaded in the same process. Whether a value gets its own piece depends on its kind and size. Anything smaller is written inside its parent and is uploaded again with every new copy of the parent.

    Captured valueGets its own piece whenReused on a later call?
    Text: a string, image data, a byte arrayit is 16 KiB or more (16,384 bytes)Yes, when the same text is captured again in the same process. A 20 KB file the agent read, a big system prompt or a photo is uploaded once.
    An object: one message, a list of messagesit encodes to 64 KiB or more, not counting text already cut outOnly if it is unchanged. A message list that gains a turn is different bytes, so the whole list is a new piece every call.
    The raw HTTP request sent to the modelalways, as one string (once it reaches 16 KiB)No. It holds the whole conversation as one JSON text, so it is new every call. Messages inside it are not separate pieces.

    What this means for a chat

    • 1,000 small messages: no cache hits. No message reaches 16 KiB, so each call uploads the full history again as one new piece. Our 100-turn long chat, about 100k tokens, shows this below.
    • A few big messages: those are cached. Each message of 16 KiB or more is uploaded once; later calls only reference it. The small messages around it are still uploaded every call.
    • The HTTP request is never cached. BCS keeps the raw request so you can see exactly what was sent, and that copy costs a full upload every call.
    • Only within one process. A second process uploads the same photo again, and BCS's server didn't report it as already stored.
    • Caching saves upload bandwidth, not money. Billing counts each call's input and request at full size, cached pieces included.

    When BCS's cache does help: images and big prompts

    BCS's cache works on large pieces. A string of 16 KiB or more, such as an image's data or a long document, becomes its own stored piece, and the BAML client uploads each piece only once per process. We reran the 20-turn chat twice more: once with a 150 KB photo attached before the first message, which stays in the conversation, and once with a 20 KB system prompt.

    Bigger conversations: 100k and 500k tokens

    Two longer conversations, sized in tokens at about 4 characters per token. The coding agent reads one source file per turn, cycling through ten sizes from 3 KB to 150 KB, and keeps every file in the conversation. The long chat has 1.5 KB customer messages, 2.5 KB answers and no tools. A hatched part means a cache hit.

    A fast process can exit before its traces are uploaded

    Our first run used a model that answered instantly, so a 50-turn conversation finished in about a second with megabytes still queued. The BAML CLI waits only 5 seconds for uploads at exit (btel_bcs's delivery shutdown_timeout, not changed by --shutdown-timeout). It printed ShutdownTimeout, and 15 of 44 uploads never reached BCS. With a realistic 1-second model, uploads kept pace and nothing was lost. Batch jobs, replays and tests that make many fast calls are the ones at risk.

    Retries

    In the agent app, every first model attempt fails with a 503 and is retried. BAML recorded all 30 HTTP attempts in 10 runs, failures included. Logfire and Datadog recorded 20 model spans for the same 30 requests, because the OpenAI SDK retries inside a single instrumented call.

    What gets stored

    Logfire's default scrubbing hides ordinary support tickets

    Logfire replaces any recorded value that contains words like password, session or secret. It replaces the whole value, not just the word. We sent ten ordinary tickets through a traced function and read back what Logfire stored for its argument.

    The model-call span in the same trace kept the full text every time, because chat messages are on Logfire's safe list. So the ticket is still stored. It just disappears from the function span you would search. BAML never redacts unless you mark a field with @trace.redact.

    Learnings and next steps

    Where BCS wins, where it loses, and how it could pull far ahead

    BCS already leads on

    • Setup: 0 lines of tracing code, against 10 for Logfire and Datadog and 28 for OpenTelemetry.
    • Speed: a whole BAML process (start, 51 calls, upload, exit) takes 150 ms and 61 MB. Python with no tracing takes 744 ms; with Datadog, 1.9 s.
    • Losses: 0% of traces lost on SIGTERM and 2.8% on kill -9, where OpenTelemetry lost about 40%. No spans dropped in a burst where OpenTelemetry and Logfire dropped 69%.
    • Spans are free: 8,200 spans billed 445 bytes.
    • Search: a trace is searchable 5.8 s after exit, against 15 s for Logfire and 38 s for Datadog.
    • Fidelity: the raw HTTP request and every retry are kept, and nothing is scrubbed unless you ask.

    BCS loses on

    • Big prompts: each call is billed about twice its prompt, once as the function input and once as the raw request.
    • Long conversations: bytes grow with the square of the turns. A 50-turn chat costs $22,728 per million conversations, against $352 on Logfire.
    • Caching: only pieces of 16 KiB or more, only within one process, and never on the bill.
    • Short processes: about 55 KB of program definitions are uploaded by every process.
    • Exit: uploads still queued 5 s after shutdown starts are dropped, whatever --shutdown-timeout says.
    • Settings: the Python bridge ignores BAML_TELEMETRY, and http_bodies = false can't be set at run time.

    The big lever: BAML owns the runtime, so it can record what happened instead of copying bytes

    LLM traces are mostly repeats. In the 48-turn coding agent the model received about 100 MB, but everything in the conversation fits in its last request, about 2 MB, and most of that is files the agent read from disk. Logfire and Datadog sit outside the program: they patch an SDK and see each call as an opaque blob of text, so all they can do is ship it. BAML is the language and the VM. It knows where every value came from, so it can record each new piece of information once and describe everything else as a reference or a recipe.

    1. Store each piece once, and bill it once. BCS already stores content by hash. Billing stored pieces instead of captured bytes passes the cache on to the customer. On its own this helps only when large pieces repeat.
    2. Record history as deltas. The VM knows that call 40's history is the same list as call 39's plus one push. It can record "previous list + this message" without hashing or copying the history again, and give every value that has already been captured a reference, whatever its size. No 16 KiB threshold, and capture cost grows with the new turn, not the conversation.
    3. Derive the request instead of storing it. The raw HTTP request is a pure function of the prompt template, the inputs and the client settings, all of which BCS already has. Store a receipt instead: template ID, input references, settings and a hash of the exact bytes sent. BCS re-renders the request on read and checks the hash; if rendering ever disagrees, the client falls back to sending the raw bytes. The parsed output is likewise derived from the raw response.
    4. Reference content BCS already has. The runtime sees where data enters the program. A file read with baml.fs.read, an image, a system prompt or a RAG document is the same in thousands of conversations, so it is stored once per project, keyed by its hash, and every conversation points to it. A coding agent reading a repository then pays for each file version once, not once per call.

    The chart applies these steps to the conversations we measured. Steps 2 and 3 only pay off together: deltas alone leave a full-size raw request every call, and a request receipt alone points at history that is new every call.

    Projections from measured sizes, not measurements of a built system. Step 1: the bytes BAML actually uploaded (each stored piece once, cut as today), or today's bill if lower. Step 2: every raw request at full size plus one copy of the conversation (its final request). Step 3: one copy of the conversation plus 200 bytes of references per call.     Why this beats the competition, not just today's BCS

    Logfire and Datadog can't follow, because they don't own the program. An SDK hook sees a request string, not the list it was rendered from, and can't know that a tool result came from a file the platform already holds. So they will keep shipping every repeat, and their customers keep paying for the bandwidth even when the bill counts records instead of bytes. The same knowledge makes BCS better, not just cheaper: a call can be shown as what changed since the last one, any call can be replayed exactly from its receipt, and a production conversation can be forked at turn 23 with a different prompt to make an eval.

    Price is the other half. Logfire charges $2 per million records whatever their size, and asks for spans near 5 KB on average; the agent's spans are megabytes, so its list price may not hold for this workload. With steps 1–3, BCS at $4/GB is already 4–77× cheaper than Datadog on these conversations and about even with Logfire on the support chat, but up to 18× above Logfire on the others. Step 4, which needs the runtime, brings it level with Logfire's list price on three of the four conversations (about 1.1× below), while keeping the whole conversation rather than a scrubbed summary. The long chat stays 4.4× above, because its 2.5 KB messages are all new text: a per-byte price at $4/GB still charges for genuinely new information. To pull clearly ahead of Logfire on cost, the per-GB price has to come down as well, which bytes stored once make easier to afford.

    More improvements, by impact

    1. Share pieces across processes. A support bot's system prompt, a product photo or a RAG document is the same in a million conversations. Let the server answer "already stored" for pieces of any process in the project, and bill them once. A 20 KB system prompt over a million conversations would go from 20 GB to 20 KB. Today a second process re-uploads the identical photo, and BCS reported 0 objects already stored.
    2. Compress uploads. BAML sends uncompressed bytes. gzip shrank English prompts by about 60% for Logfire and OpenTelemetry; zstd with a per-project dictionary would do better. This cuts upload time and storage, not the billed bytes, since queries read the decompressed values. On a laptop it matters: the 48-turn agent pushed 113 MB of uploads through the developer's own connection.
    3. Make definitions free after the first upload. The 55 KB of program definitions are already content-addressed. If the server confirms it has them, a one-call process uploads about 1 KB instead of 55 KB, which is what serverless functions and CLI tools pay today.
    4. Lose nothing at exit. Honor --shutdown-timeout (or wait until the queue drains), spool unsent uploads to disk so kill -9 and network failures lose nothing, and resend on the next start. BAML already loses the least of any stack; this would make it zero.
    5. Fix the settings gaps. Make the Python bridge read BAML_TELEMETRY, and make http_bodies a run-time setting.
    6. Show what's new in each call. Once BCS knows that call 40's history is call 39's history plus one turn, the UI can show each call as a diff: the new message, the new tool result, the model's answer. No other platform can do this, because they ship each call as an opaque copy.
    Method

    How we measured

    • Each run is a fresh process. Run order is shuffled so one stack never always goes first.
    • A local relay sits between each SDK and its backend and records every request body exactly as sent. In hosted runs it also forwards to the real service, and every request was accepted.
    • BCS billed bytes are computed by replaying BCS's billing rules (logical_bytes_approx_v1) over the upload bodies. The Billing page then showed exactly the predicted change: 5,457 spans and 34 MB.
    • Python stacks are set up the way each vendor's docs describe: Logfire 5.4, ddtrace 4.16 (LLM Observability, agentless), OpenTelemetry SDK 1.45 with opentelemetry-instrumentation-openai-v2, OpenAI SDK with max_retries=1.
    • The model is a local fake that answers instantly, so speed numbers show tracing cost only. A real model call takes hundreds of milliseconds, which dwarfs every difference on this page except process startup.
    • Test documents are random printable characters, so compression can't hide size. The Logfire deep dive also uses English prose: unique lines from Python's own docstrings, with words that trigger Logfire's scrubbing removed.
    • Everything (code, raw results, a running log) is in research/telemetry-benchmarks/.
