NATIVE V0: BAML -> RUST, RUNNING INSIDE BEX VM
==============================================

0. Premise

The interpreter decides at runtime, on every operation, what a compiler can
decide once: which opcode comes next, whether an operand is an int, where a
local lives. Native code is those decisions made at compile time. That is the
speedup. Everything else here is plumbing so compiled code is
indistinguishable from bytecode to the things that observe a running
function: callers, the GC, the exception unwinder, and telemetry.

Rule for v0: every BAML feature keeps working. A function is compiled when it
needs nothing the VM has to provide mid-body (it never suspends). Everything
else stays bytecode, with identical semantics, in the same program.


1. The unit: one Function object, two bodies

    Function.native_body: Option<NativeBody>     runtime-only, borsh(skip)

The native body is a field on the bytecode Function, not a new FunctionKind.
FunctionKind::Native means "hidden builtin" (no frame, NATIVE_DEFAULT_MODE =
Hidden, $trace rejected); reusing it would hide user functions from
observability. The kind stays Bytecode, so everything keyed on it (telemetry
mode, $trace, reflection) is unchanged, and the bytecode stays populated so
one artifact runs with or without the native build.

Open: the bytecode body is authoritative for every observer except
execution. The debugger steps bytecode that does not run.


2. Loading

attach_native_bodies runs after attach_builtins and before compact code is
prepared. The generated module's table is

    CompiledEntry { object, name, arity, body }

keyed by object index: the identity the generated code already depends on (it
bakes callee and class indices in). Name and arity are repeated and checked,
so a table from another build is refused at load instead of running against
the wrong objects. Bodies were first bound by Function.name, which is display
metadata and may repeat; that was the wrong identity.


3. Calls and frames

Every call of a compiled function gets a BytecodeFrame, as in bytecode. A
frame is the unit of five things: the MAX_FRAMES depth limit, GC rooting of
the callee, the stack trace, the unwinder's walk, and telemetry completion.

  VM -> compiled     the call funnel's Bytecode arm: telemetry entry and the
                     frame push as for bytecode, then the body runs in place
                     of the bytecode and finish_bytecode_frame (Return's
                     epilogue) completes it.
  compiled -> compiled
                     compiled_rt::call_compiled. Telemetry off: push a frame
                     with no telemetry (a struct push), call the body directly
                     (LLVM can inline it), pop. Telemetry on: through the call
                     funnel, so records, call paths and $trace are exactly the
                     bytecode ones.

An earlier version called small functions ("folded", under 64 statements, no
loop) as plain Rust calls with no frame, for speed. That removed all five
frame properties at once: recursion skipped the depth limit (wrong results,
then a native stack overflow that aborts the process), traces lost frames,
and small functions vanished from default telemetry by a size heuristic
nobody chose. Measure first: if the frame push matters, keep it and make
telemetry the only optional part.

While a body runs, cur_pc and every compiled frame's faulting_pc hold
NATIVE_BODY_PC, a value no exception-table range covers, so the unwinder never
starts a bytecode handler inside a compiled frame. Consequence: traces show
the line of the function's last line-table entry, raise evidence classifies
compiled raises as unknown, and calls out of compiled code record that
sentinel as caller_pc (call-path ids differ from an all-bytecode run). Open:
on the error path, set cur_pc to the bytecode pc of the same MIR statement
(outside every try range when the block has no unwind), or give compiled code
its own source-site coordinate.

The call fast path (call_specialize) skips callees with a native body; a
bytecode loop calling a compiled leaf pays the general funnel. Open.


4. The runtime surface

bex_vm::compiled_rt is the API generated code uses. It composes the
interpreter's semantic primitives (Value::try_int and tagged checked
arithmetic, resolve_index, binop/cmpop, the panic constructors), so results,
messages and exceptions match.

The interpreter's dispatch arms keep their own hand-tuned shape. Routing them
through these helpers measurably slowed pure bytecode (A/B against the merge
base, telemetry off: fields +28%, index_sum +14%, arith +10%), and forcing
inlining made it worse: run_compact is one giant function whose register
allocation depends on every arm. Any change to run_compact needs an
interpreter benchmark, not just the corpus.


5. Errors

    CompiledBody = fn(&mut BexVm, &[Value]) -> Result<Value, Box<VmError>>

Bodies return the VM's own error. A throw keeps its throw kind and context end
to end; internal errors keep their own variant. Bodies first used the builtin
signature (NativeCallResult), whose error type has no context: the conversion
dropped it, and YieldToCall was a variant compiled code could never produce.

catch: a block with an unwind edge matches on Err and calls compiled_rt
catch(error, depth). That builds the error's baml.errors.Context exactly as
the unwinder would (the BEP-042 rules, factored into in_flight_context), with
every frame between the throw and the handler still on the stack, then pops
the frames compiled callees left above the catching function, completing
their telemetry with the error outcome. The handler gets the value and the
real context, so catch (e, ctx) works and a rethrow carries the original
context. An internal error is not catchable and propagates.

Open: a new throw inside a compiled handler body does not take the handled
error as its cause (the cause walk reads bytecode handler tables). Compiled
catches record no raise evidence.


6. Generated code

One Rust function per admitted BAML function. Locals typed from MIR: int is
i64, float is f64, bool is bool, everything else Value. A parameter with a
default stays Value until MIR's OmittedArg test. Unboxing a Value into a
scalar is checked (compiled_rt::expect_int ...); a mismatch is a checker hole,
reported as an internal error, never read as zero.

Every operand that is not an atom is bound to a temporary before use, so no
call's arguments contain another call. Control flow is rebuilt from the
dominator tree (structure.rs). Open: MIR comes from structured source; if the
builder's loop annotations survive optimization, consuming them is smaller.

String literals load the program's compile-time string object, as bytecode
does, instead of allocating per evaluation.


7. Memory and GC

HeapPtr is a raw pointer and the collector moves objects, but it runs only
when every VM has returned its heap permit (await, sys op, spawn, the
early-yield poll). A compiled body runs under the permit, so nothing moves
while it holds pointers. Results are Values on the eval stack. Same contract
as every builtin.

Consequence: a compiled function has no safepoints. A long loop delays every
other thread that wants a collection, and an allocating loop grows Gen0 until
it returns. The fix is a body that can save its live Values in its frame's
stack slots and return to the run loop: the state machine below.


8. Admission

Admission is one fixpoint over two facts: the body generates (every construct
in it is supported), and every user function it calls is admitted. Generation
is the only judge of the first fact, so nothing half-supported is emitted.
(An earlier version rejected in three places and rechecked callers once,
which could leave a caller calling a dropped function.)

Supported beyond scalars and control flow: arrays, class fields, class/enum
literals and tests (non-generic), catch, calls to admitted functions, calls
to non-yielding builtins, generic builtins when every type argument is static
(a primitive or an array of primitives; e.g. Array.push, to_string), and
for-in over an array: compiled as an index walk with the semantics
baml.iter.ArrayIterator documents (array by reference, length re-read every
step, Done at the end).

Stays bytecode: await, spawn, sys ops and LLM calls; calls to bytecode
functions (stdlib BAML included: string templates call baml.String.from,
json.to_string calls to_json); function values, closures, interface dispatch
other than array iteration; user generic functions; runtime type templates,
map literals and indexes, enum variant literals, bigint; trace hooks; calls
with omitted or named arguments made from compiled code.


9. Performance: what caps it

Gone inside a compiled function: opcode dispatch, eval-stack traffic, tag
checks on statically typed scalars. Remaining, the same price bytecode pays:

  array/map access    one CAS acquire + release per access (LazyBiasedMutex).
                      The real cost is the ordering barrier: LLVM cannot hoist
                      a length read or bounds check out of a loop.
  instance fields     acquire/release on AtomicValueSlot.
  pointer stores      write barrier.
  floats in the heap  boxed.
  per-job floor       ~24us of engine work per host call before any BAML
                      runs; no in-VM design removes it.

These are VM decisions made for spawn and GC; they speed up both backends
when changed (lock elision when no spawn is live, unboxed int/float arrays).
Measured with locks on aarch64: fib(32) 4.4x, array loops ~1.8x.


10. The next step: resumable bodies

Almost everything in the "stays bytecode" list needs one thing: a compiled
function that can hand control back to the VM and resume. The body returns a
request (Return, Call, Throw, Yield/Await) after saving its live Values in its
frame's locals region (already reserved and rooted by the call funnel); the
VM pushes callee frames, parks for await, collects, and resumes the body at a
saved block. That covers await, spawn, LLM calls, calls into bytecode,
callback builtins, function values, GC safepoints in long loops, and catch
across a suspension. Functions that cannot suspend keep the direct call.
