Overview

What is TIR?

TIR = Typed Intermediate Representation

TIR is the core type-checking phase of the BAML compiler. It takes an untyped expression tree from earlier stages and produces a fully-typed, verified representation with:

  • A type for every expression
  • Name resolution for all identifiers
  • Exhaustiveness checking for pattern matches
  • Exception inference across the call graph
  • Flow-sensitive type refinement
Key insight: TIR operates per-scope — each function body, lambda, or block is analyzed independently. This enables fine-grained incremental recomputation via Salsa: editing a lambda body only re-checks that lambda, not the entire file.

Type Checking

Bidirectional Type Checking

Two modes of operation that work together for maximum inference power

Synthesis (Bottom-up) ↑

Infer the type of an expression from its structure, without any expected type.

// infer_expr(expr) → Ty

let x = 42      // synthesize: 42 → int
let y = x + 1   // synthesize: int + int → int
let z = [1,2,3] // synthesize: → List<int>

Checking (Top-down) ↓

Verify an expression matches an expected type, pushing context downward.

// check_expr(expr, expected_ty)

let x: string = 42   // check 42 against string → ERROR
let f: int → bool =  // push return type down
  (n) => n > 0        // infer n:int from context
Why bidirectional? Pure bottom-up requires annotations everywhere. Pure top-down can't infer without context. Bidirectional gets the best of both: synthesize when types are locally obvious, check when context is available. src/builder.rs implements this by switching between infer_expr and check_expr as it walks the tree.

Analysis

Flow-Sensitive Type Narrowing

Types refine based on control flow — implemented in src/narrowing.rs352 lines 

function process(x: string | null) {

  // x is string | null here

  if (x != null) {
    // x narrowed to string ✓
    return x.length
  }

  // x narrowed to null ✓
  // (inverse narrowing in else branch)
  return 0
}

Null Checks

if (x != null) narrows T? to T in the then-branch and to null in the else-branch.

Early Return Narrowing

If the then-branch diverges (returns/throws), the rest of the function sees the narrowed type from the else-path.

Evolving Containers

Empty [] is EvolvingList(Never). Each .push(x) widens the element type. On read, it freezes to List<T>.

Patterns

Pattern Exhaustiveness Checking

Ported from rustc's usefulness algorithm — src/exhaustiveness.rs4327 lines + src/pattern_lowering.rs58 lines 

match status {
  Status.Active  => "running",
  Status.Paused  => "paused",
  // ⚠ Missing: Status.Stopped
  // TIR reports: "non-exhaustive match
  //   missing: Status.Stopped"
}

match status {
  Status.Active  => "running",
  Status.Paused  => "paused",
  Status.Stopped => "stopped",
  // ✓ Exhaustive — all variants covered
}

Step 1: Lower Patterns

AST patterns are deconstructed into constructor + sub-patterns. Status.Active becomes Ctor(Variant("Active"), []).

Step 2: Build Matrix

All arms form a pattern matrix. Each row is one arm, columns are sub-pattern positions.

Step 3: Usefulness Check

For each possible constructor, specialize the matrix. If any constructor has no matching row, the match is non-exhaustive.

Step 4: Witness Construction

Missing cases are reconstructed into human-readable patterns for the diagnostic message.

Exceptions

Exception Inference (BEP-007)

Two-pass call graph analysis in src/throw_inference.rs548 lines + src/throws_analysis.rs270 lines

Two-Pass Algorithm

Pass 1: Direct Throws

Scan each function body for throw expressions and direct calls. Build a set of directly-thrown types.

Pass 2: Transitive Propagation

Walk the call graph. Each callee's throw set propagates to the caller — unless the callee has a declared throws clause, which acts as a firewall.

// throws IoError (declared = firewall)
function readFile(path: string)
    throws IoError {
  ...
}

// TIR infers: throws IoError
// (transitive from readFile)
function loadConfig() {
  let data = readFile("config.json")
  return parse(data)
}

// This function catches IoError
// TIR verifies: no escaping throws
function safeLoad() {
  try {
    return loadConfig()
  } catch (e: IoError) {
    return defaults()
  }
}
Performance

Salsa-Powered Incrementality

Per-scope inference means surgical recomputation on edits

✓

✓
infer_scope_types(helper_fn) — cached
✗
infer_scope_types(lambda_42) — recompute

✓

Per-Scope Granularity

Each function, lambda, let, and block gets its own ScopeId. Salsa tracks dependencies at this level, so only the changed scope (and its dependents) recompute.

Arena-based IDs

ExprId and PatId are indices into an arena (ExprBody). This avoids pointer chasing and makes equality checks cheap — critical for Salsa memoization.

Demand-Driven

Queries are lazy: resolve_class_fields only runs when someone asks for it. Unused code never gets type-checked unless explicitly requested.

Deep Dive

Type Normalization & Cycle Detection

The largest analysis module handles alias expansion, structural comparison, and recursive types — src/normalize.rs1990 lines + src/cycle_detector.rs50 lines

Type Alias Resolution

Expands aliases to StructuralTy for comparison. type StringList = List<string> becomes the structural form so StringList and List<string> are equivalent.

Cycle Detection (Tarjan's SCC)

Identifies strongly-connected components in the type graph. Guarded cycles (through a class indirection) are valid: class Node { next: Node? }. Unguarded cycles are errors: type A = B; type B = A;

Equirecursive Subtyping

Recursive types are compared co-inductively: assume A <: B, then verify the assumption holds at each unfolding. Uses a set of assumptions to break infinite recursion.

// Valid: guarded cycle through class
class LinkedList {
  value: int
  next: LinkedList?  // ✓ guarded by Optional
}

// Invalid: unguarded cycle
type Loop = List<Loop>  // ✗ infinite expansion

// Co-inductive subtype check:
//   LinkedList <: LinkedList?
//   1. Assume LinkedList <: LinkedList?
//   2. Check fields:
//      value: int <: int  ✓
//      next: LinkedList? <: LinkedList?
//        → hits assumption, stops  ✓
//   3. Assumption validated ✓

PackageInterface

The fully-resolved typed contract of a package:

  • All exported classes with field types
  • All exported enums with variants
  • All exported functions with signatures

Design

Key Design Patterns

Salsa Queries

All major computations are #[salsa::tracked] functions. Inputs change → only dependent queries recompute. The database (dyn Db) threads through every call.

Arena Allocation

Expressions and patterns live in arenas (ExprBody). ExprId is a cheap index — no heap allocation per node, cache-friendly traversal, and trivial equality.

Span-Free Errors

TirTypeError carries no source location. The ExprId or PatId provides identity; the diagnostic layer maps back to spans via the AST. Keeps the type checker location-agnostic.

Co-inductive Reasoning

Recursive types use assumption sets: assume the property holds, verify at each step. If the assumption is never violated, it holds by co-induction. Guards against infinite loops.

Demand-Driven

Nothing computes eagerly. resolve_class_fields only runs when a field access is type-checked. Dead code is never analyzed unless the LSP requests it.

Firewall Pattern

Declared throws clauses act as firewalls in exception inference. They stop transitive propagation, creating a clean contract boundary between caller and callee.

Concept

Two Modes: Synthesis vs Checking

The builder switches between two modes as it walks the expression tree. Every function call uses both.

Synthesis (infer_expr) ↑

Type info flows leaves → root. Compute the type from sub-expression types alone. No expected type — the expression itself tells you what it is.

// "What type IS this?"
42       → Literal(42, Fresh)
x + 1    → int (from operand types)
format  → (int)→string (lookup)
Used when: no contextual type available, variable lookups, operator results, callee resolution.

Checking (check_expr) ↓

Type info flows root → leaves. An expected type is passed down from the parent. Verify that the expression conforms, and push context into sub-expressions.

// "Does this MATCH the expected type?"
42 vs int       → ✓ (Literal <: int)
42 vs string    → ✗ TYPE MISMATCH
"hi" vs string  → ✓ (Literal <: string)
Used when: type annotations, function arguments (vs param types), return expressions (vs declared return type).
Note: The tree walk is always recursive (parent → children). “Direction” refers to type information flow, not traversal order. In format(42): synthesize callee type ↑ (int) → string, then check argument 42 ↓ against int, then synthesize return type ↑ string. The two modes interleave within a single call expression.
