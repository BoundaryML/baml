# Compiler and runtime benchmarks

Every bench target is a `harness = false` binary that skips itself under a
debug profile. All but `cache_profile` are [divan](https://docs.rs/divan)
benches, run with `cargo bench`:

```bash
cargo bench -p baml_tests --bench compiler_benchmark          # one bench target
cargo bench -p baml_tests --bench runtime_benchmark -- vm_     # filter by name
```

## Bench targets

| target | crate | measures |
|---|---|---|
| `syntax_benchmark` | `baml_compiler2_ast` | lex, parse and CST→AST lowering, each stage in isolation, on inputs from a 7k-line file up to 8.5 MB. The budget for the syntax-layer rebuild: never slower at any size, lowering faster. |
| `compiler_benchmark` | `baml_tests` | whole-pipeline compile (parse → HIR → TIR → MIR → emit) of an empty project (fixed overhead) and of the full `baml_src/` project. |
| `package_compile_benchmark` | `baml_tests` | `reflect.Package.compile` cold cost, and dispatch-cost parity between a runtime-compiled package and the same loop compiled into the host image (compare the 0- and 100k-iteration medians). |
| `runtime_benchmark` | `baml_tests` | VM execution of compiled bytecode. Every bench is generated by `build.rs` from the speedtest workloads under `tools/speedtest/workloads/`; edit a workload, not this file. Not run in CI; benchmarks are run locally. |
| `call_overhead` | `baml_tests` | runtime call and structured-logging overhead. |
| `telemetry_overhead` | `baml_tests` | per-call telemetry cost: each scenario runs with recording off and on; overhead is `(on − off) / CALLS` from the two medians. |
| `cache_profile` | `baml_tests` | hardware cache and instruction counters for the VM (darwin-kperf on macOS, `perf stat` on Linux). Not a divan bench: `cargo build --bench cache_profile --profile profiling`, then run the binary under `sudo`; see its header doc. |

## Reading results

divan prints `fastest / slowest / median / mean` per benchmark, and a
throughput line when the benchmark declares a byte counter. Compare medians:
sample noise on a laptop is easily ±10%, so only call something a regression
when it moves well outside that at *every* input size.
