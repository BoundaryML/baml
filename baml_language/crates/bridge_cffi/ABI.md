# BAML bridge C ABI

The public contract is [`include/baml_cffi.h`](include/baml_cffi.h). A dynamic
bridge resolves only `baml_get_api_v1`, validates the returned prefix, and uses
the function pointers in `BamlApiV1`. The legacy top-level exports remain for
existing in-tree integrations but are not part of the recommended loader
contract.

## Authoritative source and regeneration

Rust declarations in [`src/api.rs`](src/api.rs), together with the recursively
referenced `#[repr(C)]`/fixed-representation types, are authoritative. Pinned
`cbindgen` 0.29.0 and [`cbindgen.toml`](cbindgen.toml) deterministically generate
the checked-in header.

Regenerate it with exactly:

```sh
cargo test -p bridge_cffi --test header_generation regenerate -- --ignored --exact
```

Normal `cargo test -p bridge_cffi` runs two drift checks: the generated bytes
must exactly equal the checked-in header, and two consecutive generations must
be byte-for-byte identical. Updating Rust declarations without regenerating the
header therefore fails CI.

Generation is supplemented, rather than trusted alone, by strict compiled C11
and C++17 assertions. They verify enum widths and discriminants, every public
structure's size/alignment, every field offset and order, every table field's
named function-pointer type, the getter signature, and the complete original V1
prefix size. The Rust integration test executes the C layout probe and compares
every reported value with `size_of`, `align_of`, and `offset_of` on the same CI
architecture.

## V1 evolution

`abi_version` identifies this table contract; the UTF-8 value returned by
`version` identifies the BAML product release. They are intentionally separate.

V1 is append-only. Existing fields cannot be reordered, removed, retyped, or
given new semantics. A new field may only be appended. Consumers must test that
`struct_size` reaches the end of a field before reading it. The header's
`BAML_API_V1_MIN_SIZE` and `baml_api_v1_is_compatible` validate the original V1
prefix, accept unknown larger tables, and reject truncation. The C and C++ smoke
consumer executes all three cases before calling `version`.

An incompatible change requires a separately designed ABI version; there is no
`BamlApiV2` without such a change.

## Consumer audit

Audit baseline: `origin/canary` at `bd55eab8ba5b80a20b0d44293386a04c94f89c70`,
including merged PR #4041, plus the read-only Go reference worktree supplied for
this milestone.

### New-graph Python and Node.js bridges

`sdks/python/rust/bridge_python` and `sdks/nodejs/bridge_nodejs` link the Rust
`bridge_cffi` crate directly. They do not dynamically load the cdylib and do not
duplicate C layouts or calling conventions. Their direct Rust calls include
runtime construction, cancellation, media/handle helpers, bridge registration,
host callbacks, and test-only seed helpers. No foreign-layout, calling-
convention, or buffer-ownership mismatch was found. They do not consume
`BamlApiV1` because there is no dynamic C boundary between these Rust crates.

### Canary `sdks/go/bridge_go`

This older experimental Go bridge dynamically resolves individual top-level
symbols: `version`, `create_baml_runtime`, `destroy_baml_runtime`, `free_buffer`,
`call_function`, `register_callback`, `cancel_function_call`,
`baml_handle_clone`, `baml_handle_release`, `__testonly_seed_function_ref`,
`flush_events`, `register_host_dispatch_callback`,
`register_host_release_callback`, and `complete_host_call`.

Its duplicated `Buffer`, result callback, host dispatch/release callbacks,
status values, and handle signatures otherwise match the current Rust ABI, but
two cancellation/call-ID correctness problems are material:

- `CancelFunctionCallFn` declares a `uint32_t` ID while bridge_cffi accepts a
  `uint64_t`; this is a function-signature mismatch.
- It passes a callback-routing ID to cancellation and does not populate the
  distinct protobuf `CallFunctionArgs.call_id`. bridge_cffi rejects that zero
  engine call ID before starting the call, and cancellation cannot target the
  intended engine call.

The old bridge is also Unix-specific (`dlfcn.h`/`-ldl`). Fixing these issues in
isolation would not produce a valid V1 consumer: it also depends on the legacy
source-file constructor and test symbols. Its migration is intentionally left
to the separate Go work, rather than partially rewriting SDK behavior in this
shared ABI milestone.

### Read-only Go reference worktree

The reference `sdks/go/baml_go/native_unix.go` and `native_windows.go` have the
same `BamlApiV1` field order, widths, status returns, bridge-info layout, and
platform C calling convention as the canonical header. They correctly resolve
only `baml_get_api_v1`, reject a short table, accept a larger table, allocate a
real `uint64_t` engine call ID, encode it in `CallFunctionArgs`, and cancel that
same ID.

One declaration should be corrected when that branch adopts this header:
`BamlResultCallback` uses mutable `int8_t *content`, while Rust and the public
header provide borrowed read-only `const int8_t *content`. This does not change
the machine calling convention, but it is a source-level signature mismatch.
The worktree also manually duplicates every declaration and omits the explicit
Windows macro strategy; both disappear when it includes `baml_cffi.h`.

### C, C++, C#, and legacy engine consumers

No existing C, C++, or C# consumer of the new `bridge_cffi` library exists on
the audited canary tree. The added smoke programs are therefore the first
standalone C and C++ consumers.

Repository paths under `engine/language_client_cffi`,
`engine/language_client_go`, and `languages/rust/baml-sys` target the separate
legacy native library. Their direct-symbol declarations are not compatible with
`BamlApiV1` and must not be pointed at a new-graph `bridge_cffi` artifact without
a deliberate migration.

The intentionally omitted legacy bridge_cffi operations are
`create_baml_runtime` (source-file initialization), `destroy_baml_runtime`
(no-op), `invoke_runtime_cli` (stub), `flush_events` (no-op), and the two
`__testonly_seed_*` helpers. V1 instead exposes bytecode initialization and all
production handle/media/host-callback operations.

No table field was found to pass a Rust-only layout or unwind across C. Raw
pointers still require the validity documented in the header; host callbacks
must not throw/unwind; and an unexpected panic aborts rather than crossing the
boundary. V1 has no shutdown/unregistration operation, so a loader must keep the
library resident while buffers, handles, callbacks, or asynchronous work remain.
