Description:
    ## Summary

    Adds an `llm_providers` SDK-test fixture that rebuilds a BAML v0 user's 28 leaf LLM clients on the v1 stdlib clients, then drives one plain call and one streamed call through each from Python.

    Providers covered:
    - **AWS Bedrock** (11): `aws.BedrockClient` with a static IAM key pair. Covers Claude with adaptive and budgeted thinking, Nova, and GLM.
    - **Bedrock Mantle** (3): `openai.ResponsesClient` with a bearer key and prompt-cache options passed through `request_body`.
    - **Azure AI Foundry** (5): `openai.ResponsesClient` with the key in an `api-key` header.
    - **Google AI Studio** (6): `google.GeminiClient` with `thinkingLevel`.
    - **Vertex Gemini** (1): `google.VertexClient`, authenticated from `GOOGLE_APPLICATION_CREDENTIALS_CONTENT`.
    - **Vertex Model Garden** (2): `openai.GenericClient`. The OAuth token is minted from the same service account unless `VERTEX_ACCESS_TOKEN` is set.

    Fallback chains and retry policies are out of scope; only the leaf clients are tested.

    ## Test modes

    - **Keyless (default, runs in CI):** each client's request is rendered with placeholder credentials, and the test asserts the URL plus provider-specific body fields such as thinking, effort, temperature, max tokens and prompt-cache settings.
    - **Live:** set `BAML_LIVE_PROVIDER_TESTS=1` and run with keys from the `dev-llm-provider-tests` Infisical environment:
      ```
      BAML_LIVE_PROVIDER_TESTS=1 infisical run --env=dev-llm-provider-tests -- \
        cargo nextest run -p sdk_test_python_pydantic2 llm_providers::pytest
      ```
      In live mode, a missing key fails the test instead of skipping it.

    ## v1 gaps found while porting

    - `aws.BedrockClient` does not implement `ai.stream.StreamingClient`, so the Bedrock stream cases are marked strict xfail.
    - The Bedrock `access_key_id`, `secret_access_key` and `region` fields are plain strings, not `ai.Credential`, so they can't be `env.NAME` refs in a `client X = ...` declaration. The fixture builds its clients inside functions to work around this.
    - No v1 client has an equivalent of `connect_timeout_ms` or `idle_timeout_ms`, and the Bedrock and Gemini clients have no request or time-to-first-token timeouts.

    ## Followup

    - `VertexLlama4ScoutRouter` sets `max_tokens 4096`, which is not in the user's v0 config. Vertex's Llama 4 Scout MaaS endpoint returns 500 (plain) / 400 (streamed) without it, so the v0 client likely fails today and falls through its fallback chain. Marked `FOLLOWUP` in `providers.baml`.

    ## Test plan

    - [x] `sdk_test_python_pydantic2 llm_providers` (ruff, pyright, pytest): 30 keyless tests passed, 56 live cases skipped
    - [x] typescript, typescript_web, rust, go, java and cpp `llm_providers` + `fixture_manifest`
    - [ ] swift: setup fails locally because of a broken Xcode install; the error is unrelated to this change, so CI covers it
    - [x] live run for the 7 Gemini-based clients and Vertex Llama/Qwen (plain and streamed)
    - [ ] live run for Azure, Bedrock Mantle and Bedrock, once their keys and base URLs are in `dev-llm-provider-tests`
