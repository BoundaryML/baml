# Evaluation — Deployment shapes (server / browser / edge / durable)

The scenario: one provider layer must run unchanged in four homes, where the home dictates (1) where the secret comes from, (2) which transports survive, and (3) who holds the long-lived key. The adversarial question is whether the proposal's "provider = class, options = fields, client = function" model absorbs those divergences, or just relocates them.

## (a) What the proposal reuses unchanged

- **`client` is a function ⟹ "which home" is a function call.** This is the single biggest win and it costs nothing new. `ServerChat()`, `EdgeChat()`, `IamChat(region)` are three zero-/one-arg functions over the *same* `OpenAIChat` class. The application's `Analyze(text, who: Provider)` is written once and parameterized on the provider. No `@providers:` map, no per-home config schema. Reused verbatim from §3.
- **Options dissolve into fields ⟹ "where the secret comes from" is a constructor argument.** `env.OPENAI_API_KEY` vs `env.PLATFORM_OPENAI_BINDING` is a different *expression in the client body*, not a different provider. §4 carries this with no addition.
- **The ephemeral-key pattern is just a provider factory.** "Server mints a session-scoped token the browser uses" maps directly onto §3's "a client is a function returning a Provider." `SessionMint.for_browser` is an ordinary function that does I/O and returns an `OpenAIRealtime` whose `auth` is the minted token. The proposal predicted this shape (dynamic selection, factories) without anticipating this use, and it lands cleanly.
- **Combinators wrap unchanged for the cron home.** `ServerChat().with_retry(5) .fallback_to(IamChat(...))` reads identically to every other scenario; the "nobody is watching, retry hard" posture is pure §6 combinator stacking. The provider body never learns it's in a cron job.
- **Realtime's pass-in `io: Channel` (§3, OQ2)** is exactly right here: the durable-object and browser homes hand in a socket-backed channel at the `.live` call; the edge home simply never gets that far.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface Credential { authorize(request) -> request }`** — net-new capability-shaped type. The proposal's `ChatModelOptions` models `api_key: string?` as a *read-interface field*. That is insufficient here: the whole scenario is that auth is sometimes a static string, sometimes a signed IAM chain resolved per-request, sometimes a minted token with an expiry. Folding all three behind one `authorize` is the move that lets `OpenAIChat`'s body be byte-identical across homes. Tied to: the `interface`/`implements` primitive.
2. **`class IamCredential` with a `$rust_io_function authorize`** — net-new host boundary. Cloud-IAM signing genuinely cannot be expressed in pure BAML; it needs the platform credential chain. Tied to: the `$rust_io_function` bridge (OQ7).
3. **`class EphemeralToken { value, expires_at_unix }`** — net-new type carrying an *expiry the provider enforces*. `authorize` throws on a stale token. Tied to: `throws`/`catch` + a `baml.sys.now_unix()` host call.
4. **`function host_can_hold(transport) -> bool`** — net-new host primitive. The runtime must answer "can this home hold a socket?" so a provider refuses an unviable transport up-front. There is no existing primitive for "what deployment am I." Tied to: a new `$rust_io_function`.
5. **`baml.map.insert`, `baml.sys.now_unix`, `baml.str.to_int`, and the `baml.llm.*_body` request builders** — small host/std helpers assumed present; only `host_can_hold` and `now_unix` are conceptually new.

## (c) Where it is awkward, leaky, or unresolved

- **The home is a runtime fact, but the proposal offers no compile-time home guarantee — directly engages OQ5.** `host_can_hold` returns a `bool` checked at runtime; `IamCredential.authorize` throws at runtime when no chain exists. The proposal *cannot* express "this client is browser-safe" as a type. The closest it gets is `BrowserVoice(minted: OpenAIRealtime)` — but nothing stops an app author from writing `OpenAIRealtime { auth: BearerKey { value: env.SECRET }, transport: "webrtc" }` and shipping it to a browser bundle. **The proposal has no answer to the single hardest requirement in this scenario — secret hygiene under bundlers** (background "What's hard"). A leaked key is a *build-time* property; the proposal's whole model is runtime existentials. This is the most honest failure: a `BearerKey` constructed in browser-targeted code is a leak, and nothing in the type system prevents it. You would need a build-toolchain taint check that lives entirely outside this proposal.

- **`auth: Credential` is an existential, so the IAM-in-browser failure is late.** `IamChat("us-east-1")` typechecks and constructs fine in a browser; it only fails when `authorize` throws because the chain is absent. Engages OQ5 again: capability/credential viability is a runtime `match`/`throw`, never a static guarantee. The proposal accepts this tradeoff elsewhere; here it's sharper because the failure is a security-relevant misconfiguration, not a missing feature.

- **The factory boundary is a convention, not a guarantee — engages OQ3.** `SessionMint.for_browser` *promises* not to leak the server key by returning a provider whose `auth` is only the token. But that's discipline, not a checked property: the function could just as easily put a `BearerKey` in the returned provider. The proposal's "client is a function" gives us the factory shape for free but no way to mark a function's *return* as "free of server secrets." OQ3 asks whether the request side wants more structure than `baml.http.Request`; the answer this scenario surfaces is orthogonal — what's missing is a *provenance* type on credentials, which the proposal does not have.

- **Transport viability is encoded inside one provider, which doesn't compose.** `OpenAIRealtime.run` checks `host_can_hold(self.transport)`. Good — but a `Fallback` combinator that forwards `Realtime` (§6) would route to a realtime member without re-checking transport viability per member, and the proposal's combinator "claims every capability it forwards" rule means `.live` compiles on a fallback whose only realtime member can't hold a socket here. The failure still surfaces (the member throws), but the combinator can't *prefer* a viable member because viability isn't part of the type — it's a `bool` discovered by calling. Same OQ5 root cause.

- **`Realtime requires Provider` (OQ1) is mildly awkward for `OpenAIRealtime`.** We had to give it a best-effort single-turn `call` (`$rust_io_function`) purely to satisfy the `requires`. In the edge home that `call` would itself need a socket and would be just as unviable as `run`, but nothing flags that — a caller doing `Analyze(text, BrowserVoice(p))` (plain `.call`, not `.live`) on edge gets a confusing socket failure from a path that looks like ordinary HTTP.

## (d) Verdict: **Workable-with-additions**

The proposal absorbs the *structural* divergences of this scenario remarkably well: because a client is a function and options are fields, "four homes" reduces to "four small functions over one provider class," and the ephemeral-key pattern falls straight out of provider factories — arguably the cleanest fit of any scenario. The additions it needs (`Credential` as an interface, `host_can_hold` as a host primitive) are natural and ride existing machinery. But it cannot express the two things this domain most wants as *guarantees* rather than runtime hopes: **server-authoritative secret hygiene** (a key must not cross into a client bundle — a build-time, taint property the runtime-existential model has no vocabulary for) and **transport viability as a typed precondition** (OQ5). Those are real, security-relevant gaps, not cosmetic ones, so this is firmly "workable with additions" — and one of those additions (bundle taint-checking) lives outside the proposal's stated scope entirely.
