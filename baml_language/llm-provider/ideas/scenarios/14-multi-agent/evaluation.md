# Evaluation — Multi-agent (handoffs, sub-agents-as-tools, deterministic orchestration)

Adversarial read: does "Provider is the base, capabilities `requires Provider`, client is sugar" actually carry multi-agent, or does it leak?

## (a) What the proposal reuses unchanged

- **An agent *is* a Provider (the marker).** The whole reason this scenario is tractable is the load-bearing idea #1: a router, a leaf specialist, a deterministic pipeline, and a combinator are all just `Provider` — and under the marker spine that means only "composable", not "has `call`". `Agent` is a thin record around the existential `Provider` — no new "agent kind". Each node then claims the *capability it actually does* (`Tools` for the loop, `HttpProvider` for the value-producing combinators), and a `Handoff` claims neither a faked `call` nor anything but its real `Tools` loop.
- **`Tools` (the loop seam) is reused verbatim.** Handoff and sub-agent-as-tool are both expressed entirely through `begin`/`step`/`submit`/`run_tools` and the `ToolCall`/`ToolResult` correlation seam. The per-provider wire divergence (Anthropic id-correlation vs Gemini's missing ids) stays *inside* each provider's `Tools` impl, exactly as §7 promised — `Handoff` never sees a wire format. That is the portability claim paying off: `usage.baml` swaps Anthropic for Gemini at a leaf with no change to the combinator.
- **`client` == `function -> Provider`** lets `SupportDesk()`, `WriterPipeline()`, `ResearchFanout()` be one-expression factories, and lets the whole graph chain `.with_retry(2).cached(...)` for free because every node returns a `Provider` (idea #3 + the combinator default-methods of §6).
- **Combinator-as-Provider** (§6) is the template `Handoff`/`Sequential`/`Parallel`/ `Loop` copy: plain non-generic class, `implements` forwards by runtime delegation.
- **`Parallel`'s fan-out reuses shipped structured concurrency unchanged.** Fanning the branches out is a list of `spawn`s and the join is `await baml.future.all(...)` — BEP-034 (`baml_std/baml/ns_spawn`, `ns_future`) is a first-class *language* feature, not a host scheduler primitive, so `Parallel.call_with` expresses concurrent fan-out with zero net-new surface. `baml.future.all` even gives the right failure semantics for free: on the first branch's `CallError` it cancels the losers before re-throwing (swap to `all_complete` if a branch has side effects that must finish). Concurrency is *not* a gap this scenario has to flag.
- **Deterministic orchestration is "plain functions"** as §5/§7 assert. `Sequential`/ `Parallel`/`Loop` produce a value, so they `implements HttpProvider` (which owns `call`/`call_with` under the marker spine — [`../../provider-as-marker.md`](../../provider-as-marker.md)); the app's `Foo(args)` companion matches `HttpProvider.call` and calls them as ordinary functions. This is the cleanest third of the scenario.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Agent` record** — ties to idea #1 (Provider) + §7 (`Tool`). Needed because a handoff/sub-agent must carry routing metadata (`name`, `description`, `tools`) *beside* the Provider. The proposal's `Provider` has no name/description; the router needs both to synthesize `transfer_to_*` and tool descriptors.
- **`Handoff` combinator + provider-swap inside `submit`** — extends §6's combinator pattern and §7's `Tools`. New mechanic: `submit` does not return a tool result, it *re-`begin`s* a different provider. The proposal never contemplated a Tools impl whose transcript spans multiple underlying providers.
- **`Threading` interface with `History` / `Shared`** — net-new, no proposal primitive covers it. The background's "two threading models that don't mix" is made a *type the author must pick*. `History.Carry = PromptAst`, `Shared.Carry = map<string,unknown>` — and because `Carry` is an associated type, the incompatibility is enforced: you cannot feed a `Shared` agent a `History` carry.
- **`agent_as_tool` / `AgentTool`** — adapter `Provider -> Tool`, ties to §7's `Tool`
  + `ExecutionContext.dispatch`. Net-new: a `ctx.child(name)` for an **isolated** nested dispatch table (the "without polluting main context" property). §7 only proposed `dispatch` + `emit`; nesting is new.
- **`baml.agent.*` host seams** — `pending_transfer`, `partition_transfers`, `set_pending`, `extend_carry`, `coerce<T>`, `root_ctx`. These are the graph plumbing that can't be pure BAML. `coerce<T>` in particular (existential -> T at a deterministic seam) is a smell — see (c).
- **`baml.llm.concat_prompts` / `truncate_prompt` / `inject_vars`** — net-new prompt algebra. The proposal treats `PromptAst` as fully opaque; history-threading *requires* concatenating and truncating it, which the opaque type doesn't expose.
- **Two handoff-domain `ToolError` classes** — `HandoffDepthExceeded { max_depth }` and `NoSuchHandoffTarget { to_name }`. These are NOT net-new *interfaces*: both `implements baml.errors.ToolError` (the existing capability channel), with all three classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) returning `false` — they are pure orchestration faults, not transport or parse faults. The handoff loop is genuinely a `Tools` capability, so reusing `ToolError` is correct and no new `baml.errors.<Cap>Error` interface is warranted. The only capability-negotiation failure (`router/target has no Tools`) reuses `baml.errors.Unsupported` verbatim.

## (c) Where it is awkward, leaky, or unresolved

- **OQ #5 (capability `match` over an existential) is load-bearing and stressed hard.** Every node does `match (provider) { let tp: Tools => ... }`. Handoff calls it on `t.active` at *every* `step`/`submit`, and `Agent.run` calls it too. If runtime interface-membership over an existential isn't supported, the entire scenario collapses. Worse: a handoff target that *isn't* a `Tools` provider fails at `submit` time, mid-conversation, after the router already transferred — a late, ugly runtime error the type system can't prevent. Under the new error model that late failure is a `baml.errors.Unsupported` (it implements all four capability interfaces, so it is legal on the `ToolError` channel `submit` declares); the app catches it by its concrete type, but the *timing* — mid-conversation — is unchanged.
- **OQ #1 (does every capability `requires Provider`) is now *resolved* as "marker", and the swap is honest about it.** When Handoff swaps to a target, it must `begin` the target's `Tools` transcript. A target that is only an `HttpProvider` (a leaf with no tools, which under the marker spine owns `call` but not the loop) cannot be transferred to *as a router target* — we throw `baml.errors.Unsupported` at the swap. Under the OLD spine this was the "degenerate `call` forced onto everything" complaint; now there is no forced `call` to lean on, and the failure is stated plainly: a handoff destination needs the `Tools` loop, and a provider that only does `HttpProvider.call` does not have it. The marker framing makes this *correct* rather than a missing-base-method gap.
- **The provider-swap abuses `Tools.submit`'s contract.** `submit` is specified as "feed tool results, get the next transcript". We instead route a control signal (`set_pending` + empty results) through it to trigger a swap. That works only because we *also* override `run_tools`. A naive caller using the *default* `run_tools` would feed `transfer_to_*` straight into `ctx.dispatch`, which has no handler — silent misroute. So `Handoff` is **not** drop-in under the default loop; it secretly requires its own `run_tools`. That's a real leak in the §7 abstraction: the loop vocabulary (`T | ToolCalls`) has no "control call" channel, so we smuggle one through the transcript via host functions (`pending_transfer`/`set_pending`).
- **`PromptAst` opacity vs history threading.** §2/§7 make `PromptAst` opaque on purpose. But `History.thread` must concatenate and truncate it, forcing net-new `concat_prompts`/`truncate_prompt`. The background's "grows unbounded, blows the context window, rarely a truncation policy" is exactly here — and the proposal gives no handle on the prompt to *implement* a policy without new host functions. This is unresolved: opacity and history-threading are in tension.
- **`coerce<T>` / existential narrowing in deterministic combinators.** `Sequential.call<T>` runs children as `run<unknown>` then `coerce<T>(last)`. The generic `T` flows in from the caller, but children produce `unknown` (each agent has its own output type), so we launder through `unknown` and re-narrow. This is the proposal's `T`-generic threading working *against* us: a typed pipeline whose intermediate types differ has no place to live, so we erase to `unknown`. ADK's `output_schema`-per-step has no clean BAML analogue here.
- **Two threading models genuinely don't compose — and the proposal can't make them.** We surfaced that as a `Threading` *choice*, which is honest, but it means a `Shared`-written sub-agent and a `History`-written one cannot be mixed in one `Handoff` (one `threading` field, one `Carry` type). The proposal offers no bridge; neither do the SDKs, so this is faithful, not a regression — but it is *unsupported* to mix them, and that should be said plainly.
- **Depth cap is app-authored, not enforced.** `max_depth` is just a field we check. Nothing in the type system or `Tools` contract prevents a combinator author from omitting it (the default loop has no notion of handoff depth). Same footgun the background names; the proposal neither helps nor hinders.
- **Routing accuracy is unaddressable by types** (expected). "Do not answer directly" lives in the router prompt; if the router answers instead of calling `transfer_to_*`, `step` returns `T` and we return it. No mechanism — model behavior, out of scope for the interface model. Worth stating because it's a primary failure mode and the proposal offers nothing.
- **Observability across the graph** (OQ-adjacent, §7's `emit`): events/costs must bubble through every `submit`/swap and every nested `ctx.child`. We thread `ExecutionContext`, but nothing guarantees a child's emits reach the root stream; `ctx.child` would have to forward emits. Left unresolved here.
- **The error model has no cross-capability channel, so the deterministic combinators box `ToolError` into `UnknownError`.** This is the sharpest tension the new model surfaces *here*. `Agent.run` declares the `ToolError` channel (it runs a tool loop), but `Sequential`/`Parallel`/`Loop` `implements HttpProvider` (their `call`/`call_with` ride the `CallError` channel that `HttpProvider` owns under the marker spine). A `ToolError` is an *independent* interface, not a sub-type of `CallError`, so when a child agent fails mid-loop inside `Sequential.call`, that `ToolError` is foreign to the enclosing channel and must be normalized — we route it through a trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CallError>(e, "…") }`. But the boxing does **not** destroy the error: `with_message` annotates the `UnknownError` *in place* (its third arm) and leaves the original thrown value untouched in `.data`, so a `HandoffDepthExceeded` or a `Refused` that happened three levels deep inside a `Sequential` step still reaches the app *intact inside the box* — re-asserting `from<baml.errors.ToolError>(e)` (or `from<HandoffDepthExceeded>(e)`) at any later layer where that type is in scope pulls the *same* concrete error back out, its `is_*` classifiers intact, however many capability boundaries it crossed. What is actually lost is the **static** story: the consumer's channel is `baml.errors.CallError | baml.UnknownError`, which does not advertise that a `ToolError` is recoverable inside the box, so recovery is by *speculative* `from<T>` probing rather than type-directed — the compiler can't tell the author "a depth-exceeded fault can reach you here." That is exactly P2 (capability-as-runtime-promise) applied to the error channel: precision is recoverable at runtime, not statically guaranteed. And the recovery is **always explicit, never transparent** (settled, not an open question): a `catch (e) { let c: baml.errors.ToolError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `ToolError`), so that arm never fires on it — to reach the inner fault the author must `baml.UnknownError.from<baml.errors.ToolError>(e)` inside the `UnknownError` arm. So the cost is firm, not conditional: a plain catch across this boundary only ever sees `CallError` or `UnknownError`, and the down-stack classifier is reachable only by code that already knows to probe for it. The flip side (`Agent.run`'s degrade arm matches `HttpProvider` and calls `h.call` on the `CallError` channel, then must box *that* into `ToolError`) shows the asymmetry is bidirectional. A multi-agent graph mixes capabilities by construction, so this boxing is on the common path, not the edge. The rules-4 promise ("combinators declare the same channel, no variance gymnastics") holds only *within* a capability; across capabilities the only join point the model gives is `UnknownError`, which preserves the error's data but not its *static* type — so a graph keeps the recovery path but loses the compile-time signal that it is needed exactly where it most wants it.
- **Concrete handoff errors survive an existential `Tools` handle, but only because the catch is a runtime match.** `SupportDesk()` is a `client`, so the app holds the existential `Provider`/`Tools`, not a `Handoff`. The static error type of `.run_tools` is `baml.errors.ToolError | baml.UnknownError`, yet the app can still `catch` `HandoffDepthExceeded` by its concrete type (a runtime refinement, per rule 5). This is the model working as designed — but it means the depth-cap and bad-target failures are *invisible in the signature*: nothing tells an app author those two concrete errors are reachable. The classifier triad (`is_network_error`/`is_rate_limit`/`is_parse_error`) is also a poor fit for orchestration faults — all three are `false`, so an app that only triages by classifier silently lumps a depth-exceeded run in with "some other ToolError", and must know to match the concrete class to react to it.

## (d) Verdict: **Workable-with-additions**

The base model carries multi-agent further than expected: agents-are-providers and the `Tools` seam make deterministic orchestration genuinely *clean* and make leaf portability (Anthropic↔Gemini) real, with the wire divergence correctly trapped inside each provider. But two of the three patterns need real additions and one real abuse. Handoff requires a `Tools` impl whose transcript spans providers and *smuggles a control signal* (the swap) through `submit` because the `T | ToolCalls` loop vocabulary has no control channel — that is a genuine gap in §7, not just new classes. History-threading collides with `PromptAst` opacity, forcing net-new prompt algebra the proposal deliberately withheld. The capability `match` (OQ #5) is on the hot path and pushes all routing/destination-capability errors (now `baml.errors.Unsupported`) to runtime, mid-conversation. The new per-capability error channels are a clean fit *within* a capability — handoff faults are honest `ToolError`s, negotiation faults reuse `Unsupported` — but a multi-agent graph crosses capabilities (an `HttpProvider.call` combinator wrapping a `Tools`-driven agent), and the model's deliberately-disjoint `CallError`/`ToolError` channels have no join but `UnknownError`, so the deterministic combinators box typed tool failures into the escape hatch on the common path. The boxed error is not destroyed — it survives in `UnknownError.data` and is recoverable via an explicit `from<ToolError>` probe (`catch` does *not* auto-unwrap — a plain `let c: ToolError =>` arm never matches the box) — but the *static* signal is lost: the channel no longer advertises that a tool failure is reachable, so recovery is by convention (you must know to probe), a runtime promise (the P2-analog). None of this is unsupported, but "the loop is a capability" needs a control-call channel, the prompt needs a thread/truncate surface, and the error model needs to pin down the cross-capability contract (given that `catch` is settled as no-auto-unwrap, channel-union vs. opaque-box) before handoff is first-class rather than smuggled — so a graph's cross-capability precision is statically discoverable, not merely runtime-recoverable.
