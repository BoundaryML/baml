# Evaluation — Observability (spans, cost, wire-vs-UI message)

Adversarial read: does the Provider/capability/`client`-sugar model actually express auto-instrumented tracing across calls, streams, and agent loops — with cost attribution, usage normalization, and the wire-vs-UI message split?

## (a) What the proposal reuses unchanged

- **The combinator layer carries tracing verbatim.** `Traced` is a plain non-generic class that wraps a `Provider` and forwards capabilities by runtime delegation — structurally identical to `Retry`/`Fallback`/`Cache` in §6. No new mechanism: open a span, call `inner`, close it. Chaining (`with_retry().fallback_to().with_traced()`) reads outside-in for free because every combinator returns a `Provider`.
- **Capability forwarding via `match` on the existential** (§5). `Traced.stream`, `Traced.run_tools`, and `Traced.usage_attrs` all `match (self.inner)` on the capability they need and degrade or error in the `_` arm — exactly the negotiation pattern the proposal already uses. Usage normalization is just another optional capability (`UsageReporting requires Provider`) discovered by the same `match`.
- **The tool loop nests for free.** Because we don't have to reimplement threading — `begin`/`step`/`submit` stay inside the provider (§7) — `Traced` only wraps the *seam*: a child span per `step`, the parent span per `begin`. The `T | ToolCalls` shape is untouched.
- **`ExecutionContext.dispatch`** is the documented hook (§7) where per-tool spans belong; `TracingContext` is an ordinary `implements ExecutionContext`.

## (b) Net-new surface it must add (tied to a primitive)

- **`baml.obs` host seam** (`obs_start` / `obs_finish` / `obs_event` / `obs_now`) → new `$rust_io_function` host primitives. The exporter (OTel/Langfuse) is native; there is no pure-BAML way to open a span. Justified — it's a genuine host boundary, like `baml.http.send`.
- **`ExecutionContext.emit(name, attrs)`** → this is the event surface the proposal *flags as net-new in §7* ("`ExecutionContext` … needs … an event-`emit` surface"). We made it concrete: a point-event onto the current loop span. Ties directly to Open Question #7's territory (host-backed control surfaces).
- **`UsageReporting requires Provider`** + the normalized `Usage` record → a new optional capability interface. The proposal has no usage concept at all today; `call<T>` returns only `T`. This is the single biggest gap: **usage is out-of-band from the typed return**, so it must be a side-channel capability the combinator pulls *after* the call (`last_usage()`), which is stateful and racy (see (c)).
- **`Traceable.with_traced`** default method → strictly we cannot edit the canonical `Provider` interface, so the fluent method lives on a sibling `Traceable requires Provider`. This works but means `.with_traced` is NOT inherited by *every* provider the way `with_retry` is unless `Traceable` is folded into `Provider`. Minor, but it's net surface.
- **`WireMessage` / `UiMessage` / `UiPart` + `MessageView`** → new types. The proposal models prompts as the opaque `baml.llm.PromptAst` and outputs as `T`; it has **no message-history type at all**, so the wire-vs-UI distinction has nowhere to live in the current model. This is net-new and load-bearing.
- **`TracedStream` implementing a `baml.llm.StreamLike`** → the conventions give `baml.llm.Stream<TStream,TFinal>` as opaque, but to close a span on the *last* item we need to interpose on `next()`. That presumes a `StreamLike` interface with `next() -> Item | StreamDone` (mirroring `Iterator`). If `Stream` is truly opaque, span-on-last-byte is **not expressible** — see (c).

## (c) Where it is awkward, leaky, or unresolved

- **Usage is a stateful side-channel, and that's a real leak.** `call<T>` returns `T` and nothing else, so `Traced` reads `inner.last_usage()` *after* the call returns. That only works if the provider stashes the last response on `self` (note `OpenAI.last_response_body()` — a `$rust_io_function` reaching into mutable provider state). Under a `Fallback` or concurrency this races: which call's usage? The honest fix is for `call` to return usage *with* the value (e.g. `call<T> -> Traced<T>` carrying `{ value, usage }`), which the proposal does not do. **This is the scenario's sharpest stress on the base interface.**

- **Open Question #4 (`parse` input is the full `Body`).** Usage normalization actually wants to read the *Body*, not re-fetch a stashed string — the tokens live in the same `Response` that `parse<T>` consumes. The clean design threads usage out of `parse`, but `parse<T>(from: Body) -> T` has no second return. So QO#4's "the seam is `Body`" is right, but the seam is **write-only toward `T`** — usage falls out the bottom. This is the same leak as above, seen from the codec side.

- **Streaming spans + Open Question #5.** Closing a span on the last byte requires interposing on the stream, which requires the stream to be a matchable interface (`StreamLike.next -> Item | StreamDone`) and value-level reflection to re-wrap it. That's exactly QO#5 ("runtime membership testing needs the concrete type at runtime"). If `baml.llm.Stream` stays a fully opaque `$rust_type`, the combinator can only trace *start* and *whole-buffer* fallback — **native streaming spans are unsupported**. Our `TracedStream` assumes the interface exists; that assumption is the cost.

- **Agent-loop span ownership is split awkwardly.** The parent loop span is opened in `Traced.begin` (or by the app in `run_research`), but the default `run_tools` in §7 returns `T` directly with no place to *close* the parent. We had to **override `run_tools`** in `Traced` just to close the span on the value arm — duplicating the canonical loop body. So "we reuse the default loop" is only half true: the moment you need a span that brackets the whole loop, you reimplement the loop. The proposal's loop has no `on_complete`/`finally` hook.

- **Two emit paths, one loop.** Per-tool spans come from `TracingContext.dispatch` (app side), per-turn spans from `Traced.step` (combinator side). They nest under the *same* parent only because the app and the combinator agree on the parent `SpanId` out-of-band. There is no typed channel that carries "the current parent span" through `run_tools`; we smuggle it via `TracingContext` fields. A real implementation wants an ambient context (`ExecutionContext` carrying the span stack), which pushes more onto QO#7.

- **Wire-vs-UI has no home in the model.** Because prompts are opaque `PromptAst` and there's no message-history type, the rich/lean split is entirely app-authored types with no compiler awareness. Nothing *enforces* that the model only ever sees `wire_from_ui` output; an app can hand a `UiMessage` straight into a prompt and leak reasoning/PII. The proposal cannot give a compile-time guarantee here — same family as "capability is a runtime promise."

- **Redaction-before-export is policy, not type.** `export_messages` is a bool field; nothing stops a provider body from logging the raw prompt before the combinator redacts. PII safety is convention, not enforced by the seam.

## (d) Verdict: **Workable-with-additions**

Tracing-as-a-combinator is a genuinely good fit: `Traced` slots beside `Retry`/`Cache` with no new machinery, capability forwarding handles call/stream/ tools uniformly, and per-tool spans land naturally on `ExecutionContext.dispatch`. The model absorbs the *structure* of observability cleanly. But two additions are mandatory and one is a real wart. Mandatory: a `UsageReporting` capability + a normalized `Usage` type (the proposal has no usage concept), and a matchable `StreamLike` so spans can close on the last byte (QO#4/#5). The wart: usage being out-of-band from `call<T>`'s return forces a stateful `last_usage()` side-channel that races under fallback/concurrency — the right fix is a richer return (`{ value, usage }`) the base interface doesn't currently offer. And the wire-vs-UI split, plus PII redaction, live entirely in app-authored types with no compile-time guarantee — expressible, but unenforced. Workable, with those additions and an honest acknowledgment that cost attribution wants to ride *with* the value, not chase it afterward.
