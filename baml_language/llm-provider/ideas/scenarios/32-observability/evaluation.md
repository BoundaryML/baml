# Evaluation — Observability (spans, cost, wire-vs-UI message)

Adversarial read: does the Provider/capability/`client`-sugar model actually express auto-instrumented tracing across calls, streams, and agent loops — with cost attribution, usage normalization, and the wire-vs-UI message split?

## (a) What the proposal reuses unchanged

- **The combinator layer carries tracing verbatim.** `Traced` is a plain non-generic class that wraps a `Provider` and forwards capabilities by runtime delegation — structurally identical to `Retry`/`Fallback`/`Cache` in §6. No new mechanism: open a span, call `inner`, close it. Chaining (`with_retry().fallback_to().with_traced()`) reads outside-in for free because every combinator returns a `Provider`.
- **Capability forwarding via `match` on the existential** (§5). `Traced.stream`, `Traced.call`/`Traced.call_with`, and `Traced.run_tools` `match (self.inner)` on the capability they need and degrade or error in the `_` arm — exactly the negotiation pattern the proposal already uses. Under provider-as-marker, `call`/`call_with` are NOT on the base `Provider` (a bare marker); they are the `HttpProvider` capability, so `Traced` declares `implements HttpProvider` and `Traced.call_with` `match`es `self.inner` for `let h: HttpProvider` and forwards `h.call_with` (erroring `Unsupported` for a pure-realtime/harness inner). Usage is still not a *separate* capability: it is a *sidecar of the call itself*, projected from `HttpProvider.call_with` (`m => m.usage()`) in the same codec pass — so once the inner is matched as `HttpProvider`, the `Fallback`/`Retry` chain underneath carries the sidecar for free (the winner's view).
- **The tool loop nests for free.** Because we don't have to reimplement threading — `begin`/`step`/`submit` stay inside the provider (§7) — `Traced` only wraps the *seam*: a child span per `step`, the parent span per `begin`. The `T | ToolCalls` shape is untouched.
- **`ExecutionContext.dispatch`** is the documented hook (§7) where per-tool spans belong; `TracingContext` is an ordinary `implements ExecutionContext`.

## (b) Net-new surface it must add (tied to a primitive)

- **`baml.obs` host seam** (`obs_start` / `obs_finish` / `obs_event` / `obs_now`) → new `$rust_io_function` host primitives. The exporter (OTel/Langfuse) is native; there is no pure-BAML way to open a span. Justified — it's a genuine host boundary, like `baml.http.send`.
- **`ExecutionContext.emit(name, attrs)`** → this is the event surface the proposal *flags as net-new in §7* ("`ExecutionContext` … needs … an event-`emit` surface"). We made it concrete: a point-event onto the current loop span. Ties directly to Open Question #7's territory (host-backed control surfaces).
- **Usage rides `call_with` + `ResponseMeta`, not a bespoke companion (the P1 fix applied).** This scenario originally invented a `UsageReporting requires Provider` capability whose `last_usage()` pulled the token counts off a *stashed* response after the call returned — the canonical bespoke `Wrapper<T>` companion the value+sidecar model exists to delete. It is now gone. `Usage` is a dimension of the normalized `ResponseMeta` interface (`function usage(self) -> Usage`), normalized **lazily** inside each provider's concrete `OpenAIResponse` / `AnthropicResponse` (the same per-key divergence, same `meta_of(body)` seam). The combinator reads it by projecting over the inner provider's **`HttpProvider.call_with`** (matched as `let h: HttpProvider`; `call_with` is the request/response capability, not a base-`Provider` method) (`m => m.usage()`) in the *same codec pass* that produced the value — so it is no longer a stateful side-channel, and a `Fallback` forwards it (winner's view) instead of racing a stash. **P1 is resolved-with-mechanism here for the usage sidecar:** `call_with` + `ResponseMeta`. The residual is no longer "usage is out-of-band and racy" but the narrower, honest ones in (c).

- **Tuples `(T, U)` are the required net-new language surface.** `call_with` returns a tuple, and the combinator projects *two* things in one pass — the caller's `U` **and** the `Usage` it needs for the span — by nesting them: `m => (project(m), m.usage())`, returning `(T, (U, Usage))`, then destructuring `let (u, usage) = both`. So this scenario exercises both first-class tuple **types** and tuple **destructuring** (`let (value, both): (T, (U, Usage)) = …`). This is the shared dependency the value+sidecar model flags as REQUIRED (also used by the streaming folds); if tuples are rejected the fallback is a named `Output<T,U> { value, extra }` struct, at an ergonomic cost. Also net-new on the same grain: **closures-as-method-params** (`project: (ResponseMeta) -> U`) and the `meta_of(body) -> ResponseMeta` codec seam.
- **`MeteredTools requires Tools` sibling capability interface** → net-new. The per-turn usage projection (`meta(t) -> ResponseMeta`) is the tool-loop analog of `meta_of(body)`, but it CANNOT live on the canonical `Tools` interface (we cannot edit it), and it must NOT be folded into `call_with` (the loop step is a sentinel sum, `step -> T | ToolCalls`). So it is a sibling extension — same shape as `Traceable requires Provider` — declared in its own `implements MeteredTools` block on the provider, matched for (`let t: MeteredTools`) by the combinator, and degraded (`Unsupported`) when absent. This is the price of keeping the per-turn-usage projection callable through a typed value without widening either `Tools` or `call_with`.
- **`baml.errors.UsageError` and the `*UsageMissingError` classes are DELETED.** They were the error surface of the bespoke `last_usage()` companion — a classified "made a call but stashed no body" channel. With usage projected out of the same body `parse<T>` consumed, there is no separate fetch to fail: a malformed body surfaces on the existing `CallError` channel like any other parse failure. This removes the net-new `<Cap>Error` interface the old version had to justify, and retires the honest counter-pressure that it was *dead weight* (the only consumer discarded every usage error anyway). Net error surface for this scenario drops to zero.
- **`Traceable.with_traced`** default method → strictly we cannot edit the canonical `Provider` interface, so the fluent method lives on a sibling `Traceable requires Provider`. This works but means `.with_traced` is NOT inherited by *every* provider the way `with_retry` is unless `Traceable` is folded into `Provider`. Minor, but it's net surface.
- **`WireMessage` / `UiMessage` / `UiPart` + `MessageView`** → new types. The proposal models prompts as the opaque `baml.llm.PromptAst` and outputs as `T`; it has **no message-history type at all**, so the wire-vs-UI distinction has nowhere to live in the current model. This is net-new and load-bearing.
- **`TracedStream` implementing a `baml.llm.StreamLike`** → the conventions give `baml.llm.Stream<TStream,TFinal>` as opaque, but to close a span on the *last* item we need to interpose on `next()`. That presumes a `StreamLike` interface with `next() -> Item | StreamDone` (mirroring `Iterator`). If `Stream` is truly opaque, span-on-last-byte is **not expressible** — see (c).

## (c) Where it is awkward, leaky, or unresolved

- **Usage-as-stateful-side-channel is RESOLVED (was the scenario's sharpest stress).** The previous version had `call<T> -> T` returning nothing else, forcing `Traced` to read `inner.last_usage()` *after* the call off a response stashed on `self` — racy under `Fallback`/concurrency. The value+sidecar model's `HttpProvider.call_with` removes the race: `call_with<T,U>(prompt, m => m.usage()) -> (T, Usage)` carries the usage *with* the value out of one codec pass, so there is nothing to stash and nothing to re-fetch. This is exactly the "richer return (`{ value, usage }`)" the old (d) verdict said the request/response interface should offer — it now does, as a tuple (on `HttpProvider`, the capability that owns request/response — the bare `Provider` marker carries no `call`). The remaining honest residuals are narrower:
  - **Fallback aggregate has no slot — winner's view only.** `project` runs over **one** `ResponseMeta`, the winner's. Tokens burned on members that failed first (you paid for them) have nowhere to go; the span sees the winning call's usage, not the chain's. Same aggregate-provenance gap as the error side; it is *not* the old race, just the cost of the product shape.
  - **The tool-loop per-turn usage rides a `MeteredTools requires Tools` extension, not `call_with`.** `Tools.step` returns `T | ToolCalls` — a sentinel **sum**, which the partition explicitly keeps OFF `call_with` (a paused/branching turn has no single `T` to pair). So per-turn usage cannot be projected through `call_with` inside the loop. Because we cannot edit the canonical `Tools` interface, the `meta(t) -> ResponseMeta` projection lives on a *sibling* `interface MeteredTools requires Tools` (exactly as `with_traced` lives on `Traceable requires Provider`) — a value typed as the base `Tools` cannot call `.meta()`, so the combinator binds `let t: MeteredTools` in its `begin` match, stores `owner_tools: MeteredTools` on the transcript, and degrades (`Unsupported`) when the inner tool loop can't report per-turn usage. It exposes the last turn's normalized response on the *same* `ResponseMeta` grain, keeping the mechanism uniform without pretending `call_with` covers the sum-shaped loop step.

- **Open Question #4 (`parse` input is the full `Body`) — now answered by `meta_of`.** Usage lives in the same `Response` that `parse<T>` consumes; the codec exposes a *second* projection off that body via `meta_of(from: Body) -> ResponseMeta` (the canonical `HttpProvider` seam). So the body is no longer **write-only toward `T`**: `call_with` runs `parse<T>(body)` and `project(meta_of(body))` over the one body in one pass. QO#4's "the seam is `Body`" is right, and `meta_of` is the second exit the old version was missing.

- **Streaming spans + Open Question #5.** Closing a span on the last byte requires interposing on the stream, which requires the stream to be a matchable interface (`StreamLike.next -> Item | StreamDone`) and value-level reflection to re-wrap it. That's exactly QO#5 ("runtime membership testing needs the concrete type at runtime"). If `baml.llm.Stream` stays a fully opaque `$rust_type`, the combinator can only trace *start* and *whole-buffer* fallback — **native streaming spans are unsupported**. Our `TracedStream` assumes the interface exists; that assumption is the cost. With the value+sidecar model, the *usage* half of the streaming span is uniform: the terminal `StreamDone` carries the normalized `ResponseMeta` (the streaming analog of `meta_of(body)`), so `done.meta.usage()` projects the end-of-stream tokens on the same grain as `call_with` — no separate stashed-body fetch.

- **Agent-loop span ownership is split awkwardly.** The parent loop span is opened in `Traced.begin` (or by the app in `run_research`), but the default `run_tools` in §7 returns `T` directly with no place to *close* the parent. We had to **override `run_tools`** in `Traced` just to close the span on the value arm — duplicating the canonical loop body. So "we reuse the default loop" is only half true: the moment you need a span that brackets the whole loop, you reimplement the loop. The proposal's loop has no `on_complete`/`finally` hook.

- **Two emit paths, one loop.** Per-tool spans come from `TracingContext.dispatch` (app side), per-turn spans from `Traced.step` (combinator side). They nest under the *same* parent only because the app and the combinator agree on the parent `SpanId` out-of-band. There is no typed channel that carries "the current parent span" through `run_tools`; we smuggle it via `TracingContext` fields. A real implementation wants an ambient context (`ExecutionContext` carrying the span stack), which pushes more onto QO#7.

- **Wire-vs-UI has no home in the model.** Because prompts are opaque `PromptAst` and there's no message-history type, the rich/lean split is entirely app-authored types with no compiler awareness. Nothing *enforces* that the model only ever sees `wire_from_ui` output; an app can hand a `UiMessage` straight into a prompt and leak reasoning/PII. The proposal cannot give a compile-time guarantee here — same family as "capability is a runtime promise."

- **Redaction-before-export is policy, not type.** `export_messages` is a bool field; nothing stops a provider body from logging the raw prompt before the combinator redacts. PII safety is convention, not enforced by the seam.

- **The error model forces `Traced` to carry THREE distinct channels, and the span-close catch is where they meet.** Under the per-capability model `Traced.call` / `Traced.call_with` declare `baml.ExtendUnknownError<baml.errors.CallError>`, `.stream` `StreamError`, and `.begin/.step/.submit/.run_tools` `ToolError`. (It used to be FOUR — usage carried its own `UsageError`; folding usage onto `call_with` over the `CallError` channel removes that one.) A *cross-cutting* combinator like tracing has to repeat the whole channel matrix even though its only job is "open span, forward, close span." More pointedly, every span-close happens inside a `catch (e) { _ => … throw baml.UnknownError.with_message<CapErr>(e, …) }`. That is correct, and it does *not* lose the cause: `with_message<CapErr>` returns a known `Refused` / rate-limit unchanged on the in-channel arm, and on the foreign arm it boxes the original into `baml.UnknownError` — whose `.data` still holds the thrown value untouched, recoverable later via `from<InnerErr>`. So the concrete error survives the span-close either way; what the span-close catch does *not* do is re-advertise the inner typed error on the outer channel — recovery downstream is by speculative `from<T>` probing, not a static signal (the P6 / P2-analog). The one genuine pitfall is author discipline: if the combinator instead minted a *fresh* `LlmClient { message: "traced call failed" }` (discarding `e` entirely rather than boxing it), the original cause would be gone — nothing in the type system forces routing through `with_message` rather than a fresh error. So "close the span on failure" is the spot where an author can drop the cause by hand, but the canonical `with_message` path preserves it; the cost is a missing *static* signal, recoverable at runtime, not an erased error.

- **Per-field absence is a runtime promise (P2, localized to metadata).** The model's `Supported<T> = T | Unsupported` makes "this provider CAN'T produce logprobs/citations" a *typed* absence rather than a `null`. This scenario only reads `usage()`, which every response can produce, so it returns `Usage` directly (no `Supported`). But the moment the span wanted, say, `reasoning()` or `citations()`, *which* dimensions a given client actually supports is still answered at runtime (an `Unsupported` value or a `match` miss), never by the static type of the client — the same P2 "capability is a runtime promise," now localized to a metadata field. Not introduced here; inherited from the model.
- **The dead-weight `UsageError` channel is gone (the old counter-pressure to rule 4 retired).** The previous version minted `baml.errors.UsageError { is_network_error, is_missing }` plus concrete `*UsageMissingError` classes for the bespoke `last_usage()` companion — then the only consumer (`Traced.usage_attrs`) discarded *every* usage error, classified or not, so the carefully-typed channel was information no caller read. Folding usage onto `call_with` + `ResponseMeta` deletes that whole channel: usage now rides the value's own `CallError` channel (a malformed body is just a parse failure), so there is no novel `<Cap>Error` to justify and no dead classifier. The honest residual it illustrated — "one `<Cap>Error` per novel capability is cheap to declare but can be dead weight" — no longer applies *to usage*, because usage was never a separate capability; it was a sidecar of the call.

- **Concrete provider errors travel through an existential, then get thrown away by the wrong layer.** `Traced.inner` is the existential `Provider`, so a member's concrete `OpenAiRateLimitError` arrives at `Traced.call` only as `baml.errors.CallError | baml.UnknownError`. That is *recoverable* at the app's `catch` (runtime refinement), which is the model's whole promise — but the combinator's failure `catch` runs *first* and only closes the span before re-raising. If a future `Traced` wanted to, say, emit a different span status for rate-limits vs refusals, it would have to runtime-`match` the existential error inside its own catch, re-deriving concreteness the model deliberately deferred. Tracing is the first combinator that has a *reason* to inspect the error it's forwarding, and the existential makes that a `match`, not a field read.

## (d) Verdict: **Workable-with-additions**

Tracing-as-a-combinator is a genuinely good fit: `Traced` slots beside `Retry`/`Cache` with no new machinery, capability forwarding handles call/stream/ tools uniformly, and per-tool spans land naturally on `ExecutionContext.dispatch`. The model absorbs the *structure* of observability cleanly, and the value+sidecar model resolves what used to be its sharpest wart. **P1 is resolved-with-mechanism for the usage sidecar:** `call_with<T,U>(prompt, m => m.usage()) -> (T, Usage)` over a lazy `ResponseMeta` (normalized per-provider in `OpenAIResponse`/`AnthropicResponse`, exposed via the `meta_of(body)` codec seam) replaces the bespoke `UsageReporting`/`last_usage()` companion. Usage now rides *with* the value out of one codec pass — no stateful stash, no fallback race — which is exactly the "richer return (`{ value, usage }`)" the earlier verdict asked for, delivered as a tuple. The mandatory net-new surface narrows to: **tuples `(T, U)` + destructuring** (REQUIRED — the projection returns `(T, (U, Usage))` and we destructure it; shared with the streaming folds), closures-as-method-params, and a matchable `StreamLike` so spans can close on the last byte (QO#4/#5, now with `StreamDone` carrying `ResponseMeta`). The honest residuals are smaller and inherited, not introduced: the Fallback aggregate carries only the **winner's** `ResponseMeta` (the tokens you paid for on failed members have no slot); per-field absence (logprobs/citations/reasoning) stays a **runtime promise** via `Supported<T>`/`match`-miss (P2); the escape hatch for a provider-only raw field rides OQ5 wrapper-transparency; and the *sum*/*stateful* round-trips stay on their own mechanisms — the tool-loop's per-turn usage rides a small `MeteredTools requires Tools` sibling extension (so a `Tools`-typed value can't reach `.meta()` — the combinator binds `MeteredTools` and degrades when absent) because `step -> T | ToolCalls` is a sentinel sum, not a `call_with` product. The remaining warts are unchanged: the wire-vs-UI split plus PII redaction live entirely in app-authored types with no compile-time guarantee — expressible, but unenforced. On errors specifically: the per-capability `baml.ExtendUnknownError<CapErr>` model survives a cross-cutting combinator fine — `Traced` just declares each forwarded capability's channel — and the channel count drops from four to three now that usage no longer needs a `UsageError`. The canonical span-close `catch` routes the original error through `baml.UnknownError.with_message<CapErr>`, which *preserves* it: in-channel errors pass through unchanged and foreign ones are boxed into `baml.UnknownError` with `.data` holding the original, recoverable downstream via `from<InnerErr>`. What is lost there is only the *static* signal — the outer channel does not advertise which inner classified errors are recoverable in the box, so a down-stack rate-limit is reachable by speculative `from<T>` probing rather than by the type (the P6 / P2-analog). And recovery is explicit, never transparent: a plain `catch (e) { let c: baml.errors.CallError => … }` arm tests the runtime type of `e` *itself*, but a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it — the author must explicitly `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm to pull the inner error back out. The only way to genuinely lose the cause is author error — minting a *fresh* error that discards `e` instead of using `with_message` — which nothing typed forbids.
