# Scenario 32 — Observability: spans, cost, wire-vs-UI message

A colleague reading this wants to know whether the Provider/capability model can express "see every model call and tool call as a trace, know its token cost, and ship it to my backend." The answer here: tracing is a `Traced` **combinator** that wraps any `Provider` (beside `Retry`/`Cache`), opening a span per call and forwarding `call`/`stream`/`tools` by the same runtime `match` the proposal already uses. Usage rides the **value+sidecar model** (`call_with` + `ResponseMeta`): the token counts come back *with* the answer out of one codec pass (`m => m.usage()`), normalized lazily per-provider, so there is no stateful `last_usage()` side-channel and a `Fallback` forwards the usage instead of racing a stash — the P1 fix applied. The interesting friction is below the seam — span nesting across an agent loop needs the loop to expose a completion hook, native streaming spans need a matchable `StreamLike` (whose `StreamDone` now carries the end-of-stream `ResponseMeta`), and the wire-message (lean, what the model sees) vs UI-message (rich, persisted + redacted) split has no home in the current model and is added here as app-authored types. `implement.baml` is the std-lib surface (combinator, `ResponseMeta`/`Usage`, `Cost`, message types, `TracingContext`); `usage.baml` shows two divergent providers (OpenAI vs Anthropic usage encodings) wrapped with one `.with_traced(...)` line.
