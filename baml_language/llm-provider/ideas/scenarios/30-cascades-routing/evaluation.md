# Evaluation — Model cascades & semantic routing

Adversarial read of the proposal against the three shapes from `background/05-cross-cutting.md → ## ◆ Model cascades & semantic routing`: cheap-first escalate-on-confidence, classifier/semantic routing, and judge-gated escalation.

## (a) What the proposal reuses unchanged

- **Routing is `client` sugar, full stop.** The headline shape — "a classifier decides which tier per request" — is *literally* a function returning a `Provider` (proposal §3). `RoutedByClassifier(q)` in `usage.baml` takes the request text and returns `Full()` or `Mini()`. No combinator, no new interface. This is the cleanest fit in the whole set: the proposal's central claim ("clients are functions, so they select dynamically") *is* semantic routing.
- **Combinators wrapping a `Provider`** (§6). `Cascade`, `JudgeGated`, `SemanticRouter` are plain non-generic classes with a `Provider` (marker) field, in the exact mold of `Fallback`/`Retry`. Because they do request/response routing, they `implements HttpProvider` (the capability that owns `call`/`call_with` under [`../provider-as-marker.md`](../provider-as-marker.md)) and forward `call_with`'s projection to whichever member answers, so usage/cost is not dropped. They return `Provider`, so they chain (`Answer6`'s `Layered`).
- **Fluent combinator factories on the `Provider` marker** (the `Iterator.map` pattern). We added `escalate_to` / `judged_by` next to `with_retry` / `fallback_to` with no new machinery — and these factories are *exactly* the kind of member the marker hosts (it carries no interaction, only combinator factories).
- **Capability negotiation by `match`** (§5). `Cascade.call` (now an `HttpProvider` method) `match`es its cheap member for `ConfidenceProvider` and degrades when absent, and `match`es each routed-to member for `HttpProvider` before calling it — the same runtime membership test the proposal uses for `Streaming`. Under the marker model the *basic* call is itself such a match: a `Provider`-typed field has no `call` until you match it to `HttpProvider`.
- **`throws`/`catch`, `for`/`match`, static-class functions, `$rust_io_function` at host boundaries** — all reused verbatim.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface ConfidenceProvider requires Provider` + `class Scored<T>`.** Tied to: `HttpProvider.call<T>` returns a *bare* `T`. A cascade needs `(value, confidence)`. Rather than widen `call` for every `HttpProvider`, confidence is a new capability that `requires Provider` (the marker) and adds its own `call_scored` method. This is genuinely net-new — the spine has no notion of a signal riding alongside the answer. It is, however, *shaped* exactly like an existing capability (`requires Provider`, negotiated by `match`), so it costs the proposal nothing structurally — only a new interface a std lib must ship. It slots cleanly into the marker model: `ConfidenceProvider` is just another interaction surface a provider may or may not own, exactly like `HttpProvider`/`Streaming`/`Realtime`. **Error channel:** `call_scored` is a producing call, so it declares the call-path channel `baml.ExtendUnknownError<baml.errors.CallError>` — *not* a net-new `baml.errors.<Cap>Error`. A scored call can fail in exactly the ways `call` can (HTTP non-2xx, parse, refusal); reusing `CallError` is correct and avoids a redundant interface. The cost of that reuse is examined in (c).
2. **Concrete provider call-errors:** `OpenAiHttpError { status }` / `AnthropicHttpError { status }`, each `implements baml.errors.CallError` with `is_rate_limit -> status == 429`. These replace the old single-channel `throw` of a per-provider error with a `message: "… http failed"`. Foreign `Io`/`Timeout` out of `baml.http.send` and any SAP failure in `parse` are normalized through the canonical trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CallError>(e, "…") }` — the deliberately-thrown `*HttpError` passes through that catch unchanged because `with_message<CallError>` returns a known `CallError` as-is.
3. **`Cascade`, `JudgeGated`, `SemanticRouter` combinators + `Verdict` / `Exemplar` types.** Tied to: §6 combinators. Net-new classes, but no net-new *kind* of thing. They `implements HttpProvider` (call/call_with live there now) and declare the **same** `baml.ExtendUnknownError<baml.errors.CallError>` channel as the providers they wrap (rule 4: no narrow/widen/forward) — including `Cascade.call_scored`, which forwards its members' `CallError` channel verbatim, and each combinator's `call_with`, which forwards the projection to the member that answers so the sidecar survives the routing decision (the P1 fix).
4. **Two combinator factories on the `Provider` marker** (`escalate_to`, `judged_by`). Tied to: §6's "combinators as default methods". Adding to the marker is a real extension surface — every provider in the world inherits them — but it is the *only* kind of member the marker carries, so it does not re-privilege any interaction.
5. **Host primitives** (genuine `$rust_io_function`/host boundaries):
   - `baml.llm.logprob_mean_confidence(text) -> float` — the OpenAI-only signal.
   - `baml.llm.render_judge(prompt, candidate) -> PromptAst` — rubric prompt.
   - `baml.llm.nearest_exemplar_tier(prompt, Exemplar[]) -> string` — embedding KNN.
   - `baml.telemetry.emit(event, attrs)` — needed to make silent regressions *non*-silent (see (c)).

## (c) Where it is awkward, leaky, or unresolved

- **The confidence signal is a runtime promise, and that is the leak.** `SmartAnswerAnthropic` in `usage.baml` (`Haiku().escalate_to(Opus(), 0.72)`) **compiles and looks identical** to the OpenAI cascade, but Haiku has no logprobs, so its `call_scored` returns `confidence: 1.0, source: "none"` and the cascade *never escalates* — it silently degrades to "always cheap". This is precisely the background's "quality regressions are silent" hazard, and the proposal's runtime-capability model **amplifies** it: there is no type-level way to say "this cascade requires a *calibrated* confidence source." This engages **Open Question 5** (capability `match` over an existential): membership (`is ConfidenceProvider`) is testable at runtime, but *quality of implementation* (real logprobs vs. a stub returning 1.0) is not a capability the type system can see. The honest mitigation is social/observability — `source: "none"` plus a `telemetry.emit("cascade.no_signal")` — not a compile error. A reviewer should weigh whether that is acceptable.
- **`ConfidenceProvider` for Anthropic is a forced lie or a forced extra field.** Anthropic's `call_scored` has two bad options: (i) return `1.0/"none"` (our choice — never blocks, demands the app use a `Judge` instead), or (ii) bake a `certainty: float` field into *every* answer schema and parse it back out — which mutates `T`, the user's type, behind their back. Neither is clean. The proposal gives no place for "this capability exists but is degraded"; you get a binary `implements` or not. We chose to `implements ConfidenceProvider` anyway so the cascade `match` succeeds, but that makes the degraded path *look* supported. Arguably Anthropic should **not** implement `ConfidenceProvider`, and the cascade's `_` arm should fire — but then the app author who wrote `escalate_to` gets a no-op cascade with no warning either. Lose-lose; the proposal does not adjudicate it.
- **The router-is-a-call cost is invisible in the type.** `JudgeGated.call` issues *three* model calls worst-case (cheap + judge + strong) and `classify_ difficulty` adds a call before every generation. The proposal models each as an ordinary `HttpProvider.call`, which is correct — but nothing surfaces the cost multiplier. A `Cascade` and a single `OpenAI` are the same type to the app (both the `Provider` marker, both `HttpProvider` once matched); the 3× billing risk lives entirely in the body. This is inherent to "everything is a Provider" and is not unique to this scenario, but cascades make it sharp.
- **`escalate_to` widening the `Provider` marker is a real commitment.** Adding cascade-specific factories to `interface Provider` means *every* provider — including a subprocess harness or an image model — inherits `escalate_to`. That is fine semantically (it just builds a `Cascade`), and under the marker model it is *consistent*: combinator factories are the marker's whole purpose, so a harness inheriting `escalate_to` is no stranger than it inheriting `with_retry`. But it is still interface bloat; the alternative (free functions / a separate `Cascadable` interface) fragments the fluent surface. The proposal's §6 already accepts this tradeoff for `with_retry`; cascades inherit the same unresolved question of *how many* combinators belong on the marker. (Note this is the one place a harness/realtime-only provider still gains a method it can't meaningfully *use* — but `escalate_to` only *builds* a `Cascade`; it never forces a `call`, so the marker model's "no degenerate interaction" property is intact.)
- **Cross-provider routing re-imports the normalization burden.** `Layered` cascades OpenAI → Anthropic → Anthropic. Each `call<T>` re-encodes the same schema four different ways (the `build_request` divergence from §2). The cascade combinator is clean precisely because it never looks inside — but the background's "the router must speak every backend's wire shape" cost is real and lives in each provider's `build_request`, not in the cascade. The proposal *contains* it correctly; it does not *eliminate* it.
- **The error model has no vocabulary for the failure that actually matters here — and that is new under the per-capability channels.** The whole point of a cascade is the confidence *signal*, yet `call_scored` reuses `baml.errors.CallError`, whose only classifiers are `is_network_error` / `is_rate_limit` / `is_parse_error`. "I produced an answer but could not produce a calibrated signal" is none of those — and in this design it is not even an *error*: Anthropic's degraded `call_scored` *succeeds* with `confidence: 1.0, source: "none"`. So the silent-regression leak from the first bullet has an error-model twin: the one condition a cascade author would want on a typed channel (`UncalibratedSignal`) is deliberately modeled as a successful return, precisely so the `match` doesn't fall to the `_` arm. We considered minting a net-new `baml.errors.ConfidenceError` with an `is_uncalibrated()` classifier and having Anthropic *throw* it — but that would make `escalate_to` over a no-logprob backend a hard failure rather than a no-op, which is a different (and arguably worse) silent-vs-loud tradeoff than the background already flags. The five-rule model is honest about *transport/domain* errors and says nothing about *signal quality*; reusing `CallError` is correct under the rules and still leaves the load-bearing failure mode uncatchable. That is OQ5 reappearing on the error channel, not just the capability `match`.
- **Concrete-error precision survives behind a combinator, but *which tier* threw does not — and combinators are the whole scenario.** `OpenAiHttpError` carries `status: int`; an app holding a bare `OpenAI` could catch it concretely. Every `usage.baml` client returns the existential `Provider` *through* a `Cascade` / `JudgeGated` / `SemanticRouter`, each of which `implements HttpProvider`, whose `call`/`call_with` channel is the interface `baml.errors.CallError | baml.UnknownError`. Here that channel never changes — the cascade combinators stay on `CallError` (rule 4: same channel as the providers they wrap), so a `*HttpError`, being a `CallError`, rides the shared channel unboxed and a plain `catch` arm matches it concretely. Boxing into `baml.UnknownError` is *not* a structural consequence of crossing a combinator: it happens only at a boundary into a *different* capability's channel and *only for an error that does not implement that destination interface* — and even that is avoidable, because `implements` is a Rust-like trait relation that admits external impls in both directions. A channel author who wants an upstream `CallError` to flow through their net-new `OuterErr` channel typed declares `implements OuterErr for <UpstreamCallError>` (or a blanket `implements OuterErr for baml.errors.CallError`) alongside the channel; then the crossing stays typed and a plain `let o: OuterErr =>` arm catches it. So minimizing boxing is a **coverage convention**, not a wall: either side of the boundary can supply the `implements` rows. The residual is narrow — *if* a row is missing (the convention is unenforced; a forgotten row surfaces as a type error at the first `_` arm, not a silent gap), a crossing still boxes, but the error is *not* destroyed: `UnknownError.data` holds the original untouched and re-asserting `from<CallError>(e)` pulls the same concrete error back out, classifiers intact. Recovery across an un-covered boundary is then **always explicit** — `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm — because a boxed error *is* a `baml.UnknownError` (a plain `let c: baml.errors.CallError =>` arm never fires on it; `catch` does not auto-unwrap), and the `OuterErr | baml.UnknownError` channel does not advertise that a `CallError` is reachable in the box. That is the static signal degrading to a runtime promise (the P2-analog on the error channel) in the un-covered case only, not the data going away. What the cascade *additionally* cannot tell the app is *which tier* threw: a `baml.errors.CallError` with `is_rate_limit() == true` out of `Layered` could be Mini, Haiku, Mini-as-judge, or Opus, and the channel carries no tier breadcrumb. That is a distinct loss — loss of *aggregate provenance* (the combinator surfaces one member's error and never records which of its members it was), independent of boxing and not recovered by any `implements` row, since the error's identity and classifiers survive regardless. For routing specifically, "which model failed" is operationally as important as "what failed," and the per-capability channel does not carry it — while "what failed" stays typed across a covered crossing, and recoverable by an explicit probe across an un-covered one.
- **Not engaged but worth noting:** Open Questions 2–4, 6, 7 are about Body / SAP / harnesses and are orthogonal here. **OQ1 ("does realtime/harness need a degenerate `call`?") is now resolved** by the marker model — no provider here fakes a `call`; the combinators that *do* answer requests own a real `call`/`call_with` via `implements HttpProvider`, and the only universal member every provider inherits is the combinator factory set, which never forces an interaction. The only OQ this scenario stresses is **5**, and it stresses it hard.

## (d) Verdict: **Workable-with-additions**

The *mechanics* are clean: routing falls directly out of `client`-as-function (the single best demonstration of §3 in the set), and cascade/judge are textbook §6 combinators. The proposal absorbs the structure with one new capability interface and a `Scored<T>` carrier — both perfectly in-pattern. What it cannot do is the thing the background says actually matters: **guarantee a meaningful confidence signal**. Because capability membership is a runtime `match` over an existential `Provider`, a cascade built on a backend without logprobs compiles, reads identically, and silently never escalates — the exact "silent quality regression" failure mode, now *enabled* by the type model rather than caught by it. That is not a defect in cascades specifically; it is OQ5 biting. The model is usable and idiomatic, but a serious deployment needs additions the proposal does not specify: a `source`-aware contract, telemetry to de-silence regressions, and ideally a way to demand a calibrated signal at the type level (which today means dropping the `client` sugar and returning a concrete `ConfidenceProvider`).
