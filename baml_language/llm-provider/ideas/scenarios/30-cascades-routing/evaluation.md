# Evaluation — Model cascades & semantic routing

Adversarial read of the proposal against the three shapes from `background/05-cross-cutting.md → ## ◆ Model cascades & semantic routing`: cheap-first escalate-on-confidence, classifier/semantic routing, and judge-gated escalation.

## (a) What the proposal reuses unchanged

- **Routing is `client` sugar, full stop.** The headline shape — "a classifier decides which tier per request" — is *literally* a function returning a `Provider` (proposal §3). `RoutedByClassifier(q)` in `usage.baml` takes the request text and returns `Full()` or `Mini()`. No combinator, no new interface. This is the cleanest fit in the whole set: the proposal's central claim ("clients are functions, so they select dynamically") *is* semantic routing.
- **Combinators wrapping a `Provider`** (§6). `Cascade`, `JudgeGated`, `SemanticRouter` are plain non-generic classes with a `Provider` field, in the exact mold of `Fallback`/`Retry`. They return `Provider`, so they chain (`Answer6`'s `Layered`).
- **Fluent default methods on `Provider`** (the `Iterator.map` pattern). We added `escalate_to` / `judged_by` next to `with_retry` / `fallback_to` with no new machinery.
- **Capability negotiation by `match`** (§5). `Cascade.call` `match`es its cheap member for `ConfidenceProvider` and degrades when absent — the same runtime membership test the proposal uses for `Streaming`.
- **`throws`/`catch`, `for`/`match`, static-class functions, `$rust_io_function` at host boundaries** — all reused verbatim.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface ConfidenceProvider requires Provider` + `class Scored<T>`.** Tied to: the base `Provider.call<T>` returns a *bare* `T`. A cascade needs `(value, confidence)`. Rather than widen `call` for everyone, confidence is a new capability. This is genuinely net-new — the spine has no notion of a signal riding alongside the answer. It is, however, *shaped* exactly like an existing capability (`requires Provider`, negotiated by `match`), so it costs the proposal nothing structurally — only a new interface a std lib must ship.
2. **`Cascade`, `JudgeGated`, `SemanticRouter` combinators + `Verdict` / `Exemplar` types.** Tied to: §6 combinators. Net-new classes, but no net-new *kind* of thing.
3. **Two default methods on `interface Provider`** (`escalate_to`, `judged_by`). Tied to: §6's "combinators as default methods". Adding to the base interface is a real extension surface — every provider in the world inherits them.
4. **Host primitives** (genuine `$rust_io_function`/host boundaries):
   - `baml.llm.logprob_mean_confidence(text) -> float` — the OpenAI-only signal.
   - `baml.llm.render_judge(prompt, candidate) -> PromptAst` — rubric prompt.
   - `baml.llm.nearest_exemplar_tier(prompt, Exemplar[]) -> string` — embedding KNN.
   - `baml.telemetry.emit(event, attrs)` — needed to make silent regressions *non*-silent (see (c)).

## (c) Where it is awkward, leaky, or unresolved

- **The confidence signal is a runtime promise, and that is the leak.** `SmartAnswerAnthropic` in `usage.baml` (`Haiku().escalate_to(Opus(), 0.72)`) **compiles and looks identical** to the OpenAI cascade, but Haiku has no logprobs, so its `call_scored` returns `confidence: 1.0, source: "none"` and the cascade *never escalates* — it silently degrades to "always cheap". This is precisely the background's "quality regressions are silent" hazard, and the proposal's runtime-capability model **amplifies** it: there is no type-level way to say "this cascade requires a *calibrated* confidence source." This engages **Open Question 5** (capability `match` over an existential): membership (`is ConfidenceProvider`) is testable at runtime, but *quality of implementation* (real logprobs vs. a stub returning 1.0) is not a capability the type system can see. The honest mitigation is social/observability — `source: "none"` plus a `telemetry.emit("cascade.no_signal")` — not a compile error. A reviewer should weigh whether that is acceptable.
- **`ConfidenceProvider` for Anthropic is a forced lie or a forced extra field.** Anthropic's `call_scored` has two bad options: (i) return `1.0/"none"` (our choice — never blocks, demands the app use a `Judge` instead), or (ii) bake a `certainty: float` field into *every* answer schema and parse it back out — which mutates `T`, the user's type, behind their back. Neither is clean. The proposal gives no place for "this capability exists but is degraded"; you get a binary `implements` or not. We chose to `implements ConfidenceProvider` anyway so the cascade `match` succeeds, but that makes the degraded path *look* supported. Arguably Anthropic should **not** implement `ConfidenceProvider`, and the cascade's `_` arm should fire — but then the app author who wrote `escalate_to` gets a no-op cascade with no warning either. Lose-lose; the proposal does not adjudicate it.
- **The router-is-a-call cost is invisible in the type.** `JudgeGated.call` issues *three* model calls worst-case (cheap + judge + strong) and `classify_ difficulty` adds a call before every generation. The proposal models each as an ordinary `Provider.call`, which is correct — but nothing surfaces the cost multiplier. A `Cascade` and a single `OpenAI` are the same type (`Provider`); the 3× billing risk lives entirely in the body. This is inherent to "everything is a Provider" and is not unique to this scenario, but cascades make it sharp.
- **`escalate_to` widening the base interface is a real commitment.** Adding cascade-specific defaults to `interface Provider` means *every* provider — including a subprocess harness or an image model — inherits `escalate_to`. That is fine semantically (it just builds a `Cascade`), but it is interface bloat; the alternative (free functions / a separate `Cascadable` interface) fragments the fluent surface. The proposal's §6 already accepts this tradeoff for `with_retry`; cascades inherit the same unresolved question of *how many* combinators belong on the base.
- **Cross-provider routing re-imports the normalization burden.** `Layered` cascades OpenAI → Anthropic → Anthropic. Each `call<T>` re-encodes the same schema four different ways (the `build_request` divergence from §2). The cascade combinator is clean precisely because it never looks inside — but the background's "the router must speak every backend's wire shape" cost is real and lives in each provider's `build_request`, not in the cascade. The proposal *contains* it correctly; it does not *eliminate* it.
- **Not engaged but worth noting:** Open Questions 1–4, 6, 7 are about Realtime / Body / SAP / harnesses and are orthogonal here. The only OQ this scenario stresses is **5**, and it stresses it hard.

## (d) Verdict: **Workable-with-additions**

The *mechanics* are clean: routing falls directly out of `client`-as-function (the single best demonstration of §3 in the set), and cascade/judge are textbook §6 combinators. The proposal absorbs the structure with one new capability interface and a `Scored<T>` carrier — both perfectly in-pattern. What it cannot do is the thing the background says actually matters: **guarantee a meaningful confidence signal**. Because capability membership is a runtime `match` over an existential `Provider`, a cascade built on a backend without logprobs compiles, reads identically, and silently never escalates — the exact "silent quality regression" failure mode, now *enabled* by the type model rather than caught by it. That is not a defect in cascades specifically; it is OQ5 biting. The model is usable and idiomatic, but a serious deployment needs additions the proposal does not specify: a `source`-aware contract, telemetry to de-silence regressions, and ideally a way to demand a calibrated signal at the type level (which today means dropping the `client` sugar and returning a concrete `ConfidenceProvider`).
