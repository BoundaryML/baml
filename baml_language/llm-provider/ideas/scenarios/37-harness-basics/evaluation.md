# Evaluation — What a harness is + driving it

Adversarial read of whether the proposed `Provider`/capability model expresses a *driven* subprocess harness (Claude Code / Pi / Flue) cleanly. Updated for provider-as-marker (`Provider` is a bare marker; `call`/`call_with` belong to `HttpProvider`; a harness has neither and exposes only its real interactions, `Realtime.run` + `Tools`).

Background: `background/06-harnesses.md → ## 2. ★ Driving a harness`.

---

## (a) What the proposal reuses unchanged

- **`Provider` as a marker, no `HttpProvider`, no `call`.** This is the scenario the marker model was designed for, and it lands cleanest of all: a harness's transport is a subprocess, so it does HTTP request/response NEVER — and under provider-as-marker it is no longer forced to fake a `call` to satisfy a base. `ClaudeCode` carries no `implements Provider { call }` block at all; it IS a `Provider` (marker) automatically because `Realtime`/`Tools`/`ControlPlane` all `requires Provider`. "A harness is a `Provider` with no `HttpProvider` and no `call`" is true with zero new surface. (provider-as-marker.md §2, §4.)
- **`Realtime` for the steerable session — the harness's *real* interaction.** The canonical `Realtime.run(prompt, io) -> Transcript` *is* the entry point. The caller hands in the `Channel` (pass-in); the provider drives it. The one-shot/stateful distinction from the SDK table (`query()` vs `ClaudeSDKClient`) is NOT a `call`-vs-`run` split anymore — both are `run`: the "one-shot" is simply `run` over a throwaway channel with a do-nothing driver, run to completion. One method shape, no degenerate `call`.
- **`client → function ... -> Provider` sugar.** `CodeAgent()` is config-only; `sandbox`/`permission_mode`/`model` are ordinary bound fields, exactly like `model` on a chat client. Dynamic selection (`Coder(trust)`) is a plain `if`.
- **Combinator forwarding.** `ResilientCoder()` = `CodeAgent().fallback_to(PiCoder()).with_retry(2)` works because `Fallback` forwards `Realtime` by runtime delegation (§6). A harness composes like any other provider.
- **The capability `match` for `.live`.** `Build`'s desugaring is the verbatim `Foo$live` pattern from §5 — `match (p) { let r: Realtime => ..., _ => throw }`. No honest fallback for a session, exactly as the proposal says.
- **`Tools` for host-owned dispatch.** `BuildWithMyTools` reuses `run_tools<T>`/`begin`/`step`/`submit` unchanged; the harness's subprocess loop *is* the opaque `Transcript`, and `ToolCall.id` stays opaque.

## (b) Net-new surface it must add (each tied to a primitive)

1. **Concrete `InEvent`/`OutEvent` unions** (`implement.baml` §2) — tied to the canonical `Channel` interface. `Channel` is in the cheat-sheet, but its `InEvent`/`OutEvent` are abstract there. A harness must *instantiate* them with the real control-plane vocabulary (`Steer`, `FollowUp`, `Interrupt`, `SetModel`, `SetPermMode`, `RewindFiles`, `StopTask`, `EndSession` / `TextDelta`, `TurnDone`, `RewindResult`, …). This is the central modeling claim: **the control plane is data over one duplex method, not a method per verb.** Without it, `Realtime` would have to grow `interrupt()`, `setModel()`, `rewindFiles()` … and stop being one interface.
2. **`Sandbox` / `PermissionMode` enums** — tied to "options dissolve into provider fields" (§4). These are bespoke `ClaudeCode` fields. Trivial, but net-new types.
3. **`ControlPlane` capability** (`interface ControlPlane requires Realtime`) — tied to the capability-interface primitive. Net-new because plain `Realtime` can't say *which* OutEvents a provider honors, and a voice model and a coding harness are both `Realtime`. `supported_verbs() -> type[]` uses the first-class `type` + `reflect.type_of`. This is the harness analogue of the `Tool { parameters: type }` net-new flag in §7.
4. **`GuardedChannel`** — a `Channel`-shaped combinator. Net-new but built entirely from existing primitives (`reflect.type_of_value` + the membership check). It is the driver-side enforcement that an OutEvent is in the negotiated verb set before it hits the subprocess.
5. **`reflect.type_of_value(data) -> type`** — a value→type reflection used by `GuardedChannel.send`. The cheat-sheet lists `reflect.type_of<T>()` (static) and `TypeValue.implements`; runtime *value* reflection is implied by the capability `match` (Open Q5) but is here used on a closed data union, not an interface. Flagged as a host primitive the proposal must confirm.
6. **Per-capability error channels, no `type Error`.** Under the new error model each fallible method declares its own capability channel — and because a harness has no `call`, it has NO `CallError` surface: `run` uses `…<RealtimeError>`; `begin`/`step`/`submit` use `…<ToolError>`. There is no per-provider `type Error` and no `baml.errors.LlmClient`. The harness adds two concrete error classes — `HarnessSpawnError` (a subprocess-bridge failure, classified `is_network_error -> true`, implementing RealtimeError + ToolError because a spawn can fail on *either* of the two entry points) and `Refused` (the canonical refusal shape, on RealtimeError/ToolError so a mid-session/mid-tool-loop decline is the same typed value). Note the marker revision *shrank* this surface: pre-revision both errors also implemented `CallError` for the degenerate one-shot `call`; dropping `call` drops that channel cleanly. Every host (`$rust_io_function`) body gets a trailing `catch (e) { _ => throw baml.UnknownError.with_message<CapErr>(e, "…") }` to normalize foreign subprocess/IO failures into the universal wrapper. The capability-negotiation `_` arms in `usage.baml` (`DriveBuild`, `BuildWithMyTools`) throw `baml.errors.Unsupported`, which implements all four capability interfaces and so is legal on every channel.

## (c) Where it is awkward, leaky, or unresolved

- **OQ1 (must every provider carry a `call`?) — RESOLVED to "no," and this scenario is the cleanest proof.** Pre-revision we wrote a `ClaudeCode.call<T>` that spawned a *fresh* subprocess and parsed a final answer — a "best-effort spawn-and-die" that was a degenerate stand-in for the real, long-lived `run`. Under provider-as-marker that block is GONE: `Provider` is a bare marker, `call` is an `HttpProvider` capability, and a harness simply does not claim it. The class IS a `Provider` via `Realtime`/`Tools`/`ControlPlane` `requires Provider`. The old awkwardness ("`.call` and `.live` are nearly unrelated programs forced onto one class") evaporates because there is now exactly ONE program — the driven session — and the "one-shot" is that same `run` over a throwaway channel. No dishonest method, no unrelated second implementation.

- **Open Q2 (how does `io` surface at the call?) — the leak is real.** The proposal says `io` "appears only on the capability companion, never the plain `Foo(args)` call." But a harness driver is *mostly* `io` manipulation — see `DriveBuild`, where the entire body is `io.on`/`io.send` and `r.run` is the last line. The `client`-sugar function (`Build`) can declare `io: Channel` in its signature, but then the interesting logic (negotiation, the steer/rewind sequence) does **not** live in the generated companion at all — it lives in a hand-written `DriveBuild`. So for harnesses the `.live` companion is a thin shell and the real program is the driver loop the author writes by hand. The sugar buys less here than for chat/voice. Q2's "acceptable as-is" is true but hollow for this scenario.

- **Open Q3 (the request side is HTTP-specific) — confirmed, and it's the clean part.** A harness sidesteps `HttpProvider` entirely; there is no `build_request`. So "HTTP is a capability, not the base" is exactly right and this scenario is the proof. No new request-side associated type is needed *for the harness* — but note the harness's "request" (the subprocess spawn spec: argv, env, sandbox flags) is fully hidden inside `$rust_io_function` with no analogue to `Inspectable`. You cannot preview what a harness will run.

- **Open Q5 (capability `match` over an existential) — stretched.** The scenario leans on it twice: once for `Realtime` membership (canonical) and once, harder, in `GuardedChannel.send`, which matches a *data value* against a set of `type` values. That needs value-level reflection (`type_of_value`) and `type` equality (`ty == allowed`). The proposal only commits to interface-membership `match`; equality of reified `type` values for closed unions is an extra ask.

- **Open Q7 (host-backed bodies) — load-bearing and unresolved in detail.** Every interesting method here is `$rust_io_function`: `run` and the three `Tools` methods (there is no `call` — the harness drops it under provider-as-marker). The proposal asks "is an `implements` block with native bodies the supported bridge boundary?" — for harnesses the answer must be yes or the whole scenario is vapor. The subtle part the proposal does NOT address: `run`'s host body has to land mid-flight `Steer`/`Interrupt`/`SetModel` at a safe boundary (background §2 "What's hard"). That race lives entirely below the BAML seam, which is correct, but it means the *honesty* of "the control plane is just messages" depends on a host implementation BAML can't constrain.

- **The control plane's errors live OUTSIDE the error model — and that is the scenario's deepest tension.** The new model says every fallible capability throws `baml.ExtendUnknownError<CapErr>`, and `Realtime.run` duly declares `…<RealtimeError>`. But a *driven* session reports most of its failures NOT by throwing — it `io.send`s a `SessionError { message }` **InEvent** up the channel (see `DriveBuild`'s `io.on` handler). That is plain data, not a thrown error: it never touches `RealtimeError`, never hits `is_network_error()`, and never bubbles to a `catch`. So the harness has *two parallel error surfaces* — thrown `RealtimeError | UnknownError` for failures that abort `run`, and `SessionError`-as-data for failures the session survives — and the error model only governs the first. A driver that wants uniform handling has to bridge them by hand. This is honest (a long-lived session genuinely has recoverable in-band failures), but it means "the error model is uniform per capability" is only half-true for `Realtime`: the *interesting* harness failures are deliberately modeled as channel data, by design, to stay recoverable.

- **`GuardedChannel.send` rejects on `baml.errors.Io`, not a capability error — a deliberate downgrade.** When the guard blocks an unsupported verb it `throw baml.errors.Io { message: … }`, because `Channel.send`'s canonical channel is `baml.errors.Io` (it is not a capability method). So "you sent `RewindFiles` to a harness that does not support it" is, at the type level, indistinguishable from a real socket failure on the channel — neither is a `RealtimeError`, neither carries `is_network_error()`. The new per-capability model does not reach `Channel`, so the control-plane's own guard violations fall back to the coarse `Io` channel. We could mint a `ControlPlaneError` capability interface for this, but `ControlPlane`'s only method (`supported_verbs`) is infallible, so there is currently no capability channel to attach it to — the verb-rejection error has no natural home in the four-interface taxonomy.

- **A concrete error implementing two interfaces, surfaced through an existential, is never caught concretely here.** `HarnessSpawnError` implements RealtimeError AND ToolError so one class covers spawn failures on both of the harness's entry points (post-revision there is no `call`, so no CallError variant). But every consumer in `usage.baml` holds the harness through `client` sugar (the existential `Provider`) and the companions throw the *interface* channel. So an app can catch `baml.errors.RealtimeError` and ask `is_network_error()`, but to branch on `HarnessSpawnError` *concretely* it must name the `claudecode` package's class — re-introducing exactly the provider coupling the existential was meant to hide. The model permits the concrete catch (runtime refinement); the harness's config-only-client ergonomics quietly discourage it.

- **Server-authoritative / hidden state — plainly unsupported at the type level.** Two things the model cannot express:
  1. **Compile-time guarantee that a verb is supported.** `supported_verbs()` is a *runtime* list; `GuardedChannel` rejects unsupported verbs at runtime (`throw baml.errors.Io`). There is no way to make "this harness supports `RewindFiles`" part of the type — and worse, even within one provider it's *data-dependent* (`ClaudeCode` in `Local` sandbox drops rewind). No type system could capture that; it is inherently runtime. The proposal's "drop the sugar for compile-time precision" escape hatch does **not** help, since the variability is in a *field value*, not the static type.
  2. **Session identity / "continue" state.** The background flags folding stateless+stateful into one entry with a `continue` flag as "leaky." Our model avoids the flag: there is one entry point, `Realtime.run`, and the "one-shot" is just `run` with a do-nothing driver — so stateless and stateful are the *same* method differing only in whether the caller steers. That is a genuine win (no `continue` flag, no degenerate `call`) — but it also means there is no first-class *session handle*. `run` owns the session for its whole duration; you cannot get a session, stash it, and resume it across separate top-level calls. The handle the TS SDK returns (a `Query` you hold) has no representation; you hold the `Channel` instead, and only for the lifetime of one `run`.

## (d) Verdict

**Workable-with-additions.**

The `Provider`-as-marker claim is the cleanest thing in the whole proposal here: a harness genuinely *is* a `Provider` (the marker) without faking any `call`, its single real interaction is `Realtime.run` (the "one-shot" is just `run` with a do-nothing driver), and combinators compose harnesses for free. The marker revision specifically resolved OQ1 for this scenario — the degenerate spawn-and-die `call` is gone, not papered over. The decisive modeling bet — **control plane as a closed `OutEvent`/`InEvent` union over the single handed-in `Channel`, rather than a method per verb** — pays off and keeps `Realtime` from metastasizing. The additions it forces are modest and principled (concrete event unions, a `ControlPlane` capability advertising verbs via first-class `type`, a guard combinator). What it cannot do is give any *compile-time* guarantee about the control surface — verb support is runtime, sometimes field-dependent — and it has no first-class resumable session handle (you hold the `Channel` for one `run`, not a `Query` you can stash). For driving a harness those are acceptable limitations, not blockers; hence Workable-with-additions rather than Clean.
