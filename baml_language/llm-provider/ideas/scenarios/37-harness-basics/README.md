# 37 — What a harness is + driving it

A harness (Claude Code, Pi, Flue) is the payoff of the provider-as-*marker* model: it has NO `call` (no `HttpProvider`, no `build_request`) because its transport is a *subprocess*, not HTTP — it is a `Provider` only in the marker sense (composable, the type `client` returns), and what it can DO is per-capability. Its real interaction is `Realtime.run(prompt, io)` for the long-lived steerable session, where the caller hands in a `Channel` and *drives* the harness rather than calling it; the "fresh session, run to completion" one-shot (Python `query()`) is just `run` over a throwaway channel, not a separate `call`. It also adds `Tools` so the host can own tool dispatch. The whole control plane — interrupt / setModel / setPermissionMode / rewindFiles / steer / followUp / stopTask — is modeled as a closed `OutEvent`/`InEvent` union sent over that one channel, not as a method per verb; `sandbox`/`permission_mode`/`model` are bound config fields. `implement.baml` builds the providers, the `ControlPlane` capability, and a `GuardedChannel`; `usage.baml` shows the config-only clients, the `.live` companion, a full driver loop, and two divergent harnesses (Claude Code with rewind, Pi without); `evaluation.md` stresses it.
