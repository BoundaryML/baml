# Evaluation — dataset / task / scorer / runner

Adversarial read of whether the proposed provider/client/capability model expresses an eval harness cleanly. The eval loop is dataset + task + scorer(s) + runner; the twist is that *the task under test and the LLM-judge scorer are both providers*, so the proposal's spine is doing double duty.

## (a) What the proposal reuses unchanged

- **The task under test is already a `function -> Provider`.** The proposal makes `SupportReply(q)` literally `function … { client().call<string>(render_prompt(q)) }`. So the eval runs the *exact* production code path — no separate "eval mode" client, no re-plumbing. The runner takes the task as a plain function value `(TInput) -> TOutput`; the proposal's "clients are functions" thesis (§3) is what makes that a one-liner.
- **The LLM-judge is just another `Provider`.** `JudgeScorer.score` does `self.judge.call<Verdict>(prompt)` — the same `call<T>` seam as any task, with `T = Verdict` SAP-parsed. "Everything is a provider" (§1) means a judge needs no special category; it's a chat model you point at a rubric.
- **The embedding scorer reuses `call<T>` with `T = float[]`.** An embeddings model is a `Provider` whose output type is a vector. No new interface — the generic `T` in `call<T>` (§2) absorbs it. Determinism is free (no sampling).
- **Cross-family judging falls out of provider values.** The background demands the judge be a *different family* than the task to dodge self-preference. Here that's just `JudgeModel()` returning `Anthropic` while `SupportModel()` returns `OpenAIChat` — two provider values, no harness-level multi-provider machinery.
- **`service_tier: "flex"` dissolves into a provider field (§4).** An eval sweep has no user waiting, so the cheap async tier is the right knob; it's a field on `OpenAIChat`, not a runner option.
- **Capability negotiation via `match` (§5)** is reused verbatim for reading the determinism fingerprint: `match (self.task_provider) { let d: Deterministic => … }`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **A `Scorer<TInput, TOutput>` interface** — one method `score(case, output) -> Score`. Tied to the proposal's one-method-interface pattern (the `Iterator`/ `Provider` template). This is *library* surface, not a language change: it's ordinary `interface`/`implements` + the typed `throws` channel. The proposal has no scorer concept because scoring isn't a provider concern — but it composes the proposal's primitives without extending the language.
2. **A `Deterministic requires Provider` capability** — `fingerprint(self) -> RunFingerprint`. Tied to the capability model (§1) and the "options are fields" rule (§4). This is the scenario's sharpest *fix* to the proposal: `seed` is NOT a universal field, because OpenAI has it and Anthropic/Gemini do not. Modeling `seed` as a plain field (which §4 would suggest) lets you construct an `Anthropic` with a `seed` it silently drops. Promoting "reproducibility availability" to a capability interface is the honest model — and it's exactly the proposal's own pattern, applied to a divergence the proposal's field-dissolution rule would have papered over.
3. **A separate `PairwiseScorer` interface** — `compare(input, a, b) -> Score`. Tied to nothing in `Scorer`. A pairwise judge scores a *pair*, not a single output, so it genuinely does not fit `Scorer<TInput, TOutput>`. This is a real shape divergence the single-output interface cannot absorb; it needs its own interface and its own runner path. The runner in `implement.baml` only handles `Scorer`; pairwise lives in usage code (`compare_prompts`) as a hand-rolled loop.
4. **The eval data vocabulary** — `Case`, `CaseSource`, `Score`, `RunFingerprint`, `TaskRun`, `RunReport`, `Trace`. Plain library data classes. None touch the language; they're the runner's nouns.
5. **`RunFingerprint` + the runner's "is this pinned?" check** — tied to the `Deterministic` capability. The background's core CI worry ("a red build means the *change* regressed, not that sampling drifted") needs the harness to *record* the seed/system_fingerprint and refuse to interpret an unpinned run. That recording has no home in the proposal until `Deterministic` exists.

## (c) Where it is awkward, leaky, or unresolved

- **Open Question 5 (capability `match` over an existential) is load-bearing.** The runner reads the determinism fingerprint via `match (task_provider) { let d: Deterministic => … }`. If value-level reflection can't test interface membership on an existential `Provider`, the runner can't distinguish a seedable backend from a temperature-only one, and the whole "pin the run / detect drift" story collapses. OQ5 asks us to "confirm" runtime membership testing works; this scenario stakes the determinism-recording on a yes.

- **The proposal cannot give a COMPILE-TIME determinism guarantee.** Because `client SupportModel()` returns the existential `Provider`, "is this client reproducible?" is a *runtime* `match`, not a type. The escape hatch (§3, §5: drop the sugar, write `function … -> OpenAIChat`) would make `Deterministic` part of the type — but then the runner is no longer provider-agnostic; it would have to be written against the concrete type, defeating the point of a reusable runner. So a CI author cannot get a *compile error* for "you tried to gate an eval on an unpinned, seedless provider." The best the model offers is a runtime field on `RunReport` (`fingerprints`) the author must remember to inspect, plus a half-hearted `gate` that throws only if *every* case errored. **A compile-time "this eval is reproducible" guarantee is unsupported in this model**, and for a CI gate that's exactly the guarantee you'd want.

- **Self-preference and judge-drift are NOT enforceable — only conventional.** The mitigations (judge ≠ task family; pin the judge model id) live in *app convention*: `JudgeModel()` happens to be Anthropic while `SupportModel()` is OpenAI, and the pin is just a string field. Nothing in the model *prevents* an author from pointing `JudgeScorer.judge` at the same `OpenAIChat` as the task, reintroducing self-preference. Both `judge` and `task_provider` are the existential `Provider`, so the harness cannot even runtime-`match` "are these the same family?" — provider *family/identity* is not a capability, and there's no reflection surface for it. The model expresses the judge perfectly but gives the *anti-bias structure* no teeth.

- **Position bias forces a SECOND interface, fracturing the runner.** `PairwiseScorer` can't be a `Scorer`, so the clean "runner runs a list of scorers" story splits: single-output scorers go through `Runner.run`, pairwise comparison is a separate hand-rolled loop (`compare_prompts`). That's not the proposal's fault — it's inherent to pairwise eval — but it means the harness is two runners, not one, and the proposal offers no unifying abstraction.

- **Score-stability-vs-reality is a methodological hole the model can't close.** Pinning `temperature: 0` and `seed: 7` (provider fields) makes CI stable but tests the model in a mode users never see (they get sampled output). The model lets you *set* these fields cleanly, but it cannot express "score the distribution, not one draw" without a multi-sample scorer the runner doesn't have. Reproducibility and realism are in tension and the harness picks reproducibility silently.

- **`Deterministic.fingerprint` doing an I/O probe is a smell.** OpenAI's `system_fingerprint` is only known *after* a call, so `openai_system_fingerprint` is a `$rust_io_function` that fires a probe request before the sweep. A "read my config" method that secretly makes a network call is leaky; the honest alternative (capture the fingerprint from the first real response and reconcile) doesn't fit the "record once up front" runner shape.

- **Engages Open Question 1 indirectly.** OQ1 asks whether every capability should `requires Provider` / refine `call`. `Deterministic requires Provider` is a clean fit (a seedable thing is-a provider). But note it's a *read-only* capability — it adds no new interaction shape, just metadata about how `call` behaves. The proposal has no category for "capability that describes `call` rather than extends it," so it sits a little oddly next to `Streaming`/`Tools`/`Realtime`, which all add *methods*.

## (d) Verdict

**Workable-with-additions.**

The core of an eval harness lands beautifully on this model: the task under test *is* a `function -> Provider`, the LLM-judge *is* another `Provider` you `call<Verdict>`, the embedding scorer *is* `call<float[]>`, and cross-family judging *is* just two provider values — all reused unchanged, with excellent app-author ergonomics (a task function, a list of scorer values, one `.gate(0.95, baseline)`). The net-new surface (`Scorer`, the data vocabulary, the `Deterministic` capability) is mechanical library code that composes the proposal's own primitives, and `Deterministic`-as-a-capability is actually a *better* model of the seed divergence than the proposal's "seed is a field" rule would give. What the model genuinely *cannot* do is the part a CI gate most wants: a **compile-time guarantee that an eval is reproducible** (the existential `Provider` makes "is this seedable?" a runtime `match` at best, and the concrete-type escape hatch breaks the reusable runner), and it gives the **judge anti-bias structure no teeth** — judge≠task-family and judge-pinning are convention, unenforceable because provider identity/family isn't a capability the model can reflect on. Pairwise judging also fractures the runner into two paths. None of these is fatal — they are documentable, and the additions are small — but they are real holes: the proposal expresses *what an eval does* cleanly while leaving *the guarantees an eval exists to provide* (reproducibility, unbiased grading) as runtime hopes rather than typed facts.
