# Evaluation — dataset / task / scorer / runner

Adversarial read of whether the proposed provider/client/capability model expresses an eval harness cleanly. The eval loop is dataset + task + scorer(s) + runner; the twist is that *the task under test and the LLM-judge scorer are both providers*, so the proposal's spine is doing double duty.

## (a) What the proposal reuses unchanged

- **The task under test is already a `function -> Provider`.** The proposal makes `SupportReply(q)` literally `function … { match (client()) { let h: HttpProvider => h.call<string>(render_prompt(q)), … } }` — the companion-as-match desugar, where `call` is matched for on `HttpProvider` (the marker `Provider` carries no interaction). So the eval runs the *exact* production code path — no separate "eval mode" client, no re-plumbing. The runner takes the task as a plain function value `(TInput) -> TOutput`; the proposal's "clients are functions" thesis (§3) is what makes that a one-liner.
- **The LLM-judge is just another provider you `call`.** `JudgeScorer.score` does `self.judge.call<Verdict>(prompt)` on a `judge: HttpProvider` field — the same `call<T>` seam as any task, with `T = Verdict` SAP-parsed. Under the marker model `call` is an `HttpProvider` capability, so a judge is precisely an `HttpProvider`; it needs no special category, it's a chat model you point at a rubric.
- **The embedding scorer reuses `call<T>` with `T = float[]`.** An embeddings model is an `HttpProvider` whose output type is a vector (`embedder: HttpProvider`). No new interface — the generic `T` in `HttpProvider.call<T>` (§2) absorbs it. Determinism is free (no sampling).
- **Cross-family judging falls out of provider values.** The background demands the judge be a *different family* than the task to dodge self-preference. Here that's just `JudgeModel()` returning `Anthropic` while `SupportModel()` returns `OpenAIChat` — two provider values, no harness-level multi-provider machinery.
- **`service_tier: "flex"` dissolves into a provider field (§4).** An eval sweep has no user waiting, so the cheap async tier is the right knob; it's a field on `OpenAIChat`, not a runner option.
- **Capability negotiation via `match` (§5)** is reused verbatim for reading the determinism fingerprint: `match (self.task_provider) { let d: Deterministic => … }`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **A `Scorer<TInput, TOutput>` interface** — one method `score(case, output) -> Score`. Tied to the proposal's one-method-interface pattern (the `Iterator`/ `Provider` template). This is *library* surface, not a language change: it's ordinary `interface`/`implements` + the typed `throws` channel. The proposal has no scorer concept because scoring isn't a provider concern — but it composes the proposal's primitives without extending the language. **Net-new error channel:** scoring is NOT call/stream/tools/realtime, so it gets its own capability-error interface `baml.errors.EvalError` (one classifier, `is_inapplicable()`), and `score` declares `throws baml.ExtendUnknownError<baml.errors.EvalError>`. Two concrete EvalErrors land on it: `ScorerInapplicable` (reference-based scorer with no `case.expected` → `is_inapplicable() == true`) and `EvalGateFailure` (the CI gate's regression verdict, raised by `Runner.gate`). When a scorer drives a `Provider` (`JudgeScorer`, `EmbeddingScorer`), that provider's `CallError` reaches the scoring channel — and whether it stays typed is a *coverage convention*, not a wall. Because BAML `implements` is a Rust-like trait relation that admits external impls, the `EvalError` author can write, alongside the channel, `implements baml.errors.EvalError for baml.errors.CallError` (local trait, foreign type) — and then a judge `Refused` / rate-limit rides the `EvalError` channel as its *typed* self, caught concretely, no box. Absent that row a crossing falls back to `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.EvalError>(e, "…") }` and the `CallError` boxes — but `with_message` leaves the original untouched in `.data`, recoverable via an explicit `from<baml.errors.CallError>` probe. So a judge refusal or rate-limit only loses its *static* visibility when the `implements` row is missing; the data always survives.
2. **A `Deterministic requires Provider` capability** — `fingerprint(self) -> RunFingerprint`. Tied to the capability model (§1) and the "options are fields" rule (§4). This is the scenario's sharpest *fix* to the proposal: `seed` is NOT a universal field, because OpenAI has it and Anthropic/Gemini do not. Modeling `seed` as a plain field (which §4 would suggest) lets you construct an `Anthropic` with a `seed` it silently drops. Promoting "reproducibility availability" to a capability interface is the honest model — and it's exactly the proposal's own pattern, applied to a divergence the proposal's field-dissolution rule would have papered over.
3. **A separate `PairwiseScorer` interface** — `compare(input, a, b) -> Score`. Tied to nothing in `Scorer`. A pairwise judge scores a *pair*, not a single output, so it genuinely does not fit `Scorer<TInput, TOutput>`. This is a real shape divergence the single-output interface cannot absorb; it needs its own interface and its own runner path. The runner in `implement.baml` only handles `Scorer`; pairwise lives in usage code (`compare_prompts`) as a hand-rolled loop.
4. **The eval data vocabulary** — `Case`, `CaseSource`, `Score`, `RunFingerprint`, `TaskRun`, `RunReport`, `Trace`. Plain library data classes. None touch the language; they're the runner's nouns.
5. **`RunFingerprint` + the runner's "is this pinned?" check** — tied to the `Deterministic` capability. The background's core CI worry ("a red build means the *change* regressed, not that sampling drifted") needs the harness to *record* the seed/system_fingerprint and refuse to interpret an unpinned run. That recording has no home in the proposal until `Deterministic` exists.

## (c) Where it is awkward, leaky, or unresolved

- **Open Question 5 (capability `match` over an existential) is load-bearing.** The runner reads the determinism fingerprint via `match (task_provider) { let d: Deterministic => … }`. If value-level reflection can't test interface membership on an existential `Provider`, the runner can't distinguish a seedable backend from a temperature-only one, and the whole "pin the run / detect drift" story collapses. OQ5 asks us to "confirm" runtime membership testing works; this scenario stakes the determinism-recording on a yes.

- **The proposal cannot give a COMPILE-TIME determinism guarantee.** Because `client SupportModel()` returns the existential `Provider`, "is this client reproducible?" is a *runtime* `match`, not a type. The escape hatch (§3, §5: drop the sugar, write `function … -> OpenAIChat`) would make `Deterministic` part of the type — but then the runner is no longer provider-agnostic; it would have to be written against the concrete type, defeating the point of a reusable runner. So a CI author cannot get a *compile error* for "you tried to gate an eval on an unpinned, seedless provider." The best the model offers is a runtime field on `RunReport` (`fingerprints`) the author must remember to inspect, plus a half-hearted `gate` that throws only if *every* case errored. **A compile-time "this eval is reproducible" guarantee is unsupported in this model**, and for a CI gate that's exactly the guarantee you'd want.

- **Self-preference and judge-drift are NOT enforceable — only conventional.** The mitigations (judge ≠ task family; pin the judge model id) live in *app convention*: `JudgeModel()` happens to be Anthropic while `SupportModel()` is OpenAI, and the pin is just a string field. Nothing in the model *prevents* an author from pointing `JudgeScorer.judge` at the same `OpenAIChat` as the task, reintroducing self-preference. `judge` is an existential `HttpProvider` and `task_provider` an existential `Provider` marker, so the harness cannot even runtime-`match` "are these the same family?" — provider *family/identity* is not a capability, and there's no reflection surface for it. The model expresses the judge perfectly but gives the *anti-bias structure* no teeth.

- **Position bias forces a SECOND interface, fracturing the runner.** `PairwiseScorer` can't be a `Scorer`, so the clean "runner runs a list of scorers" story splits: single-output scorers go through `Runner.run`, pairwise comparison is a separate hand-rolled loop (`compare_prompts`). That's not the proposal's fault — it's inherent to pairwise eval — but it means the harness is two runners, not one, and the proposal offers no unifying abstraction.

- **Score-stability-vs-reality is a methodological hole the model can't close.** Pinning `temperature: 0` and `seed: 7` (provider fields) makes CI stable but tests the model in a mode users never see (they get sampled output). The model lets you *set* these fields cleanly, but it cannot express "score the distribution, not one draw" without a multi-sample scorer the runner doesn't have. Reproducibility and realism are in tension and the harness picks reproducibility silently.

- **A judge/embedder `CallError` crossing the scorer boundary stays typed *if* the `EvalError` author adds one `implements` row; otherwise it boxes (data intact) — the residual cost is the unenforced convention, not an erasure.** Under the new model the channel is per *capability*, not per provider. A `JudgeScorer` IS-A scorer, so its method declares `baml.errors.EvalError`; the judge model it calls declares `baml.errors.CallError`. These are independent interfaces — but because BAML `implements` is a Rust-like trait relation with external impls in both directions, the `EvalError` author can declare, in their own package, `implements baml.errors.EvalError for baml.errors.CallError` (local trait, foreign type). With that row a judge `Refused` (a safety decline on the candidate output — highly meaningful: the judge wouldn't grade it) and a judge `OpenAiRateLimitError` (retry-and-rescore!) ride the `EvalError` channel as their *typed* selves, caught concretely at the runner, **no box** — so this boxing is a *coverage convention*, not a structural wall, and either side of the boundary can supply the row. Where the row is *missing*, the crossing falls back to `baml.UnknownError.with_message<baml.errors.EvalError>(e, …)` and boxes — but even then nothing is destroyed: `with_message` annotates the box *in place*, so `.data` still holds the original `CallError` untouched, and the runner can pull the concrete error back out by re-asserting `from<baml.errors.CallError>(e)` — classifiers (`is_rate_limit()`/`is_network_error()`) intact, however many boundaries it crossed. So the retry/skip distinction *is* recoverable at runtime either way. The only thing the missing-row path loses is the **static** story: the runner's channel is `EvalError | baml.UnknownError`, which does not advertise that a recoverable rate-limit or refusal can be hiding in the box — recovery is then by *speculative* `from<CallError>` probing, never type-directed, so the compiler can't tell the runner author "a judge rate-limit can reach you here." This is exactly **P2** (capability = runtime promise) applied to the error channel. And in that path the recovery is **explicit, never transparent** (settled): a `score(...) catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it — to pull the inner `CallError` back out the runner must explicitly `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm. So when the row is absent, a plain `catch` across the scorer boundary only ever sees `EvalError` or `UnknownError`; provenance is preserved and recoverable, but only by code that already knows to probe for it. The residual cost over the single `LlmClient` channel is therefore narrow: nothing *forces* the `EvalError`-for-`CallError` row, so a forgotten row degrades a typed, exhaustive triage signal into a runtime probe — an unenforced convention, not an irreducible erasure.

- **`Deterministic.fingerprint` doing an I/O probe is a smell.** OpenAI's `system_fingerprint` is only known *after* a call, so `openai_system_fingerprint` is a `$rust_io_function` that fires a probe request before the sweep. A "read my config" method that secretly makes a network call is leaky; the honest alternative (capture the fingerprint from the first real response and reconcile) doesn't fit the "record once up front" runner shape.

- **OQ1 is now resolved, and this scenario is a clean witness.** OQ1 (does every capability need a degenerate `call`?) is closed as **no** by the marker model: `Provider` carries no interaction, and each capability adds only its own surface. `Deterministic requires Provider` is a textbook fit — a seedable thing *is-a* `Provider` (the marker) and adds *only* `fingerprint`, with no fake `call` to satisfy a base contract. The scenario never had to forge a degenerate `call` for `Deterministic`, the embedder, or the judge: `call` lives on `HttpProvider`, matched/typed exactly where request/response actually happens. The one residual oddity is benign — `Deterministic` is a *read-only* capability (metadata about how `HttpProvider.call` behaves) rather than a new interaction shape, so it reads a little differently from `Streaming`/`Tools`/`Realtime`, which add *methods*; but under the marker model that's just "a capability is whatever surface it owns," and read-only metadata is a legitimate surface.

## (d) Verdict

**Workable-with-additions.**

The core of an eval harness lands beautifully on this model: the task under test *is* a `function -> Provider` (whose body `match`es `HttpProvider` for the `call`), the LLM-judge *is* another `HttpProvider` you `call<Verdict>`, the embedding scorer *is* an `HttpProvider` you `call<float[]>`, and cross-family judging *is* just two provider values — all reused unchanged, with excellent app-author ergonomics (a task function, a list of scorer values, one `.gate(0.95, baseline)`). The marker revision *helps* here: there is no degenerate `call` to forge anywhere (OQ1 closed), and `Deterministic` lands cleanly as a read-only capability on the bare marker. The net-new surface (`Scorer`, the data vocabulary, the `Deterministic` capability) is mechanical library code that composes the proposal's own primitives, and `Deterministic`-as-a-capability is actually a *better* model of the seed divergence than the proposal's "seed is a field" rule would give. What the model genuinely *cannot* do is the part a CI gate most wants: a **compile-time guarantee that an eval is reproducible** (the existential `Provider` makes "is this seedable?" a runtime `match` at best, and the concrete-type escape hatch breaks the reusable runner), and it gives the **judge anti-bias structure no teeth** — judge≠task-family and judge-pinning are convention, unenforceable because provider identity/family isn't a capability the model can reflect on. Pairwise judging also fractures the runner into two paths. The new per-capability error model adds a small, real cost here: a `Scorer` needs its own `baml.errors.EvalError` channel (clean enough), and a judge model's `CallError` — a refusal, a rate-limit — stays typed across the scorer boundary only if the `EvalError` author writes one external `implements baml.errors.EvalError for baml.errors.CallError` row (legal because BAML `implements` is a Rust-like trait relation with external impls; with the row, the `CallError` rides the `EvalError` channel typed, caught concretely, no box). That makes the boxing a *coverage convention*, not a wall — either side of the boundary can supply the row. Where the row is forgotten the crossing boxes, but even then the error survives (its data sits untouched in `.data`, recoverable via an explicit `from<CallError>` probe — a plain `catch` arm never auto-unwraps the box, so `let c: CallError =>` never matches it); the only loss is that the runner's channel no longer *advertises* it, so the retry/skip classification a judge-backed eval wants degrades to a runtime promise the author must speculatively and explicitly probe for. None of these is fatal — they are documentable, and the additions are small — but they are real holes: the proposal expresses *what an eval does* cleanly while leaving *the guarantees an eval exists to provide* (reproducibility, unbiased grading) as runtime hopes rather than typed facts.
