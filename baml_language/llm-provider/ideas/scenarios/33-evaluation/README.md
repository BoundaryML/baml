# 33 — Evaluation (dataset / task / scorer / runner)

This scenario stress-tests the provider/client/capability model against an eval harness: measuring whether prompts, models, and pipelines actually work. The payoff is that the model already speaks most of the nouns — the **task under test is a `function -> Provider`** (so the eval runs the production code path), the **LLM-judge is just another `Provider`** you `call<Verdict>`, the **embedding scorer is `call<float[]>`**, and cross-family judging (to dodge self-preference) is simply two provider values. The harness adds a small library layer on top: a `Scorer` interface, the eval data vocabulary (`Case`/`Score`/`RunReport`), and — the one real *fix* to the proposal — a `Deterministic` **capability** that models the seed divergence honestly (OpenAI has a seed, Anthropic/Gemini do not) instead of pretending `seed` is a uniform field. Read `implement.baml` for the library side, `usage.baml` for the app side (task + golden/production dataset + scorer stack + CI gate), and `evaluation.md` for where it leaks: no compile-time reproducibility guarantee, and judge anti-bias is convention without teeth.
