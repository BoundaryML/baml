# Evaluation — Provider diversity & gateways

Adversarial read of whether the proposed model expresses provider diversity (base_url proxies, prefix routing, registries, auth-shape divergence, the lowest-common-denominator trap) cleanly. The background's headline goal is "call many models, possibly through a proxy or gateway, without rewriting per provider, and switch models by changing a string." This is the scenario the proposal was practically *designed* for — "clients are functions that return a Provider" is the whole story — so the interesting question is where it still leaks.

## (a) What the proposal reuses unchanged

- **`client` = `function … -> Provider` IS prefix routing.** `Registry.resolve(spec)` is an ordinary function that `match`es a string prefix and constructs a provider; `client Smart(spec) { Registry.resolve(spec) }` wraps it. LiteLLM's `completion(model="anthropic/…")` and Vercel's `createProviderRegistry(...)` both collapse into this with *zero* new machinery — the §3 sugar plus a `match` on a string. `client:` accepting any Provider-typed expression (proposal §3) is what lets `client: Registry.resolve(spec)` and `client: Smart(spec)` work verbatim. This is the cleanest single mapping in the whole scenario set.
- **`base_url` + `headers` as provider fields** is precisely "options dissolve into provider fields" (§4). An OpenAI-compatible proxy is `OpenAIChat` with a different `base_url` and `auth` — no subclass, no new codec. The named constructor `OpenAIChat.compatible(...)` is the existing `from_shorthand`/ `from_model` static-factory pattern (§6), reused intact.
- **One `HttpProvider` codec, N endpoints.** `build_request` interpolates `self.base_url` into one URL template; `send`/`parse` are unchanged. The four structured-output encodings still live inside `build_request<T>`/`parse<T>` (carried over from scenario 02), so a Groq call and an OpenAI call share a body.
- **The portability claim lands.** `Extract(bio)`'s function body is byte-for-byte identical across OpenAI / Groq / Ollama / Claude / Gemini / Bedrock; only the `client:` line changes. This is the model's best showing and it is real.
- **Combinators wrap a Provider.** `RoundRobin` is a plain non-generic class that `implements HttpProvider` and forwards `call`/`call_with` to the picked pool member, exactly the `Fallback` template from §6 — load-spread across same-shape backends with no provider changes. It does NOT redefine the inherited combinator factories (`with_retry`/`fallback_to`/`cached`); those ride in via `HttpProvider requires Provider`.
- **The existential return type is the *mechanism* of portability.** `Registry.resolve` returns the bare marker `Provider`; that erasure is what lets one function accept any backend. The proposal's §5 framing ("capability — *including the basic call* — is a runtime promise because `client` returns the existential `Provider` marker") is not a wart here — it is the feature. The companion for the value path `match`es the resolved marker for `HttpProvider` and calls `call`; the marker itself promises nothing.
- **The per-capability error channel survives N divergent backends with no per-provider error type.** Every codec's `build_request`/`send`/`parse` declares the SAME `baml.ExtendUnknownError<baml.errors.CallError>` regardless of whether the wire shape is OpenAI, Anthropic, or Gemini — there is no associated `type Error` per provider, so the registry can erase three concrete classes to one `Provider` *and* their three concrete HTTP errors (`OpenAiHttpError`, `AnthropicHttpError`, `GeminiHttpError`) all collapse to the single `baml.errors.CallError` interface at the catch. A LiteLLM-style `ExtractMany` triages every backend's failure through one `is_rate_limit()` without naming a provider. This is the error-model's flat-union claim paying off exactly where diversity is maximal.
- **A non-2xx is a typed `CallError`, not a stringly message.** Each provider raises a concrete `<Provider>HttpError { status }` whose `is_rate_limit()` encodes that backend's overload signal (OpenAI/Gemini 429, Anthropic *also* 529). The app branches on the classifier without a status-code table. Foreign `baml.errors.Io`/`Timeout` from `baml.http.send` is normalized once per codec via a trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CallError>(e, "<provider> send failed") }` — the breadcrumb names which backend the gateway routed to.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Auth` interface + four variant classes (`BearerAuth`, `ApiKeyHeaderAuth`, `QueryKeyAuth`, `SigV4Auth`, `GcpOAuthAuth`).** Tied to the provider-field rule (§4) and the `interface`/`implements` machinery. The proposal says auth is a provider field but never shows that the *shape* of auth diverges structurally (a header vs a URL rewrite vs a full-request signature). Modeling it as a small `apply(request) -> request` interface is the honest absorption: a field whose *type* is `Auth`, dispatched at `build_request` time. This is genuinely new surface, but it is built ON the spine, not a patch to it.
- **`baml.cloud.sigv4_sign` / `baml.cloud.gcp_access_token`** — host functions for cloud-IAM auth. Tied to the host-boundary rule (`$rust_io_function`). Bedrock/ Vertex have no static credential header; signing reads the ambient credential chain and HMACs the canonical request. This is irreducibly a host concern and the proposal's §4 "auth shape" bullet hand-waves it ("cloud IAM (SigV4/OAuth), not a bearer key at all") — this scenario shows it costs two host functions and an `Auth` variant that *mutates the whole request*, not just a header.
- **Header-bag merge is *not* net-new — it is ordinary `Map` mutation.** Tied to the transport/ envelope discussion (§4). The proposal asserts headers are merged "outside the per-provider arm," but for a *gateway* the routing header is part of provider identity, so the merge happens *inside* `build_request`. There is no `baml.map.merge`; the codecs copy `self.headers` into a fresh `map<string, string>` (iterate `.keys()` + `.get`/`.set`) and `.set("content-type", …)`, and each `Auth.apply` `.set`s its header(s) onto `request.headers`. All real stdlib `Map` methods — no addition.
- **Prefix splitting is real `string` method work, not a primitive.** The registry splits `spec` on the FIRST `/` with `spec.index_of("/")` + `spec.substring(...)` — `before`/`after` were invented spellings. The only subtlety (model-id namespacing) is that only the first `/` is the routing key (openrouter/bedrock ids contain more slashes), which a single `index_of` cut captures while `.split("/")` would over-split.
- **`Registry` resolver class** — net-new *library* code, but built entirely from `match` + named constructors. No new primitive; it earns its place as the thing the background calls "a `ModelProvider.get_model(name) -> Model` resolver."
- **`Normalized` + `Escape`** — net-new library classes encoding the LCD trap and its hatch. `Normalized` is a combinator that *narrows* (forwards only `call`); `Escape.as_streaming` is a `match` back up to a capability. Both reuse §5/§6 machinery; new code, no new primitive.
- **`KVCounter` (`next_mod`) host primitive** — atomic cursor for round-robin. Tied to the host-boundary rule. Round-robin needs mutable shared state, which a pure provider field cannot hold; this is a genuine (small) host addition.

## (c) Where it is awkward, leaky, or unresolved

- **The registry cannot promise a capability — OQ-5 head-on (and now even the basic call is negotiated, not guaranteed).** `Registry.resolve` returns the bare marker `Provider`, which under the marker revision promises *no* interaction at all — not even `call`. `RoutedExtract` reaches `.call` only because its value companion `match`es the resolved marker for `HttpProvider` and finds one (every backend the registry constructs happens to be an `HttpProvider`); the marker itself does not advertise it. The moment the app wants `.stream` on a routed client, it must likewise `match` the resolved value back to `Streaming` at runtime (`Escape.as_streaming`) and accept a runtime failure for backends that lack it. There is no way to write "this registry only ever yields streaming providers" — or even "...yields callable providers" — as a type. The escape hatch (`function … -> ConcreteHttpProvider`) recovers precision but *destroys routing* — a concrete return type names one provider, so you cannot route by string and keep the capability statically. **You choose: route-by-string OR static capability, never both.** This is the documented cost of `client`-as-sugar (§5), and provider diversity is exactly where it bites hardest, because routing is the whole point. OQ-5 ("confirm value-level reflection supports `match (provider) { let h: HttpProvider => … }` / `let s: Streaming => …`") is load-bearing: the entire registry-plus-capability story — including the basic call — is unsound if runtime interface membership over the marker is not supported. (Note the marker revision *removes* the old OQ-1 complaint outright: there is no longer a degenerate `call` forced onto every provider, so the registry's existential narrows to "which capabilities are present," with `call` simply one of them — see (d).)

- **The lowest-common-denominator trap is *expressible* but not *enforced*.** `Normalized` makes "request/response only" explicit and honest — under the marker revision it `implements HttpProvider` (and forwards `call` *and* `call_with`, so usage/cost survives the normalization layer), deliberately exposing no other capability. Good. But nothing stops an app author from skipping `Normalized` and calling `.stream` on a registry-resolved provider that happens to support it for OpenAI and throws for Ollama. The model gives you a way to *say* "lowest common denominator" but no way to *check* that a given call stays within it. The background calls "designing the escape hatch as hard as designing the common surface"; here the escape hatch (`Escape.as_streaming`) is clean, but the *common surface* has no compile-time floor — it is convention, not a type. A truly portable function is one the author *disciplines* to the `HttpProvider` surface only; the compiler will not enforce it.

- **Per-attempt / per-request overrides have nowhere to live (§4 tension).** A gateway caller often wants a one-off header or model override on a single call ("this request, add `x-trace-id`"). Because the header bag and base_url are *provider construction fields*, a per-call override means constructing a new provider per call — fine for the registry path (it constructs anyway) but awkward when you hold a long-lived `client`. The proposal deleted the per-call options bag (§4); gateways are precisely where people reach for it. There is no `call(prompt, overrides)` seam, so per-request gateway knobs round-trip through "build a fresh provider," which is more allocation and ceremony than the Python `default_headers` vs per-request `extra_headers` split the background shows.

- **Auth-as-`apply(request)` quietly assumes a fixed build→auth ordering.** SigV4 must sign *after* every header and the body are final; `QueryKeyAuth` must run before any signature would (it mutates the URL). The codec calls `self.auth.apply` as the last step of `build_request`, which is correct for these five, but the model has no way to express ordering constraints between auth and other request mutations. A combinator that adds a header *after* `build_request` (the §4 "transport envelope wraps the provider" story) would silently invalidate a SigV4 signature — and nothing in the type system catches it. **Signing and the "headers live at the combinator layer" rule are in direct, unenforced conflict.** This is a real soundness gap the proposal's §4 split does not acknowledge.

- **The error channel re-creates the LCD trap, one layer down — and the registry hides it.** Portability collapses three concrete HTTP errors to `baml.errors.CallError`, which is the *point* — but it also means the only failure surface an app holding a `Registry.resolve(spec)` result can rely on (for the call path it negotiates via `HttpProvider`) is the three classifier bits (`is_network_error`/`is_rate_limit`/`is_parse_error`). The instant an app wants a provider-specific signal — Anthropic's `retry-after`, OpenAI's `x-request-id`, a 529-vs-429 distinction — it must `catch` the *concrete* `AnthropicHttpError`, which the registry's existential makes a runtime gamble: the concrete error is not destroyed (it arrives intact and a concrete `catch` arm is a legal runtime refinement, per error-model rule 5), but the existential channel does not *advertise* which concrete errors can reach the catch, so the arm only fires for the backends the string happened to route to. **Just as `Normalized` narrows capabilities to the `HttpProvider` (request/response) surface statically, the existential narrows the *static* error surface to the `CallError` classifiers; the typed-error story has the same route-by-string-XOR-static-precision tension as the capability story, and it is *less* visible because there is no `Normalized`-shaped marker for "you have no static guarantee which concrete error type you'll see."** The classifiers are a genuine lowest-common-denominator on the *statically-known* error surface, not just the call side — the concrete signal is recoverable at runtime, just not type-directed.
- **Crossing a capability boundary forces a manual error re-route the model does not automate.** `StreamIfPossible` resolves a provider on the *call* channel (`Registry.resolve` → `CallError`, incl. the `UnknownProviderError` which implements `CallError` only) and then streams on the *stream* channel. Because `UnknownProviderError` is not a `StreamError`, the body must hand-write a `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.StreamError>(...) }` to launder the resolve failure into the enclosing capability's channel — boxing it into `UnknownError` in the process. This does *not* destroy it: `with_message` annotates the `UnknownError` *in place*, so `.data` still holds the original `UnknownProviderError`, and a later `from<UnknownProviderError>(e)` (or `from<CallError>(e)`) at any layer where that type is back in scope pulls the *same* concrete error back out, classifiers intact. The provider HTTP errors dodge the box entirely because they were *authored* to implement both `CallError` and `StreamError`; a domain error that implements only one capability interface cannot flow into a sibling capability's channel *statically* — it rides the box and is recovered by speculative `from<T>` re-assertion. What is actually lost is the **static** story: the enclosing `StreamError | UnknownError` channel does not advertise that a resolve-time `CallError` is recoverable inside the box, so the compiler cannot point the author at it — exactly the P2 capability-as-runtime-promise tension applied to the error channel. The "one channel per capability" rule is clean within a capability; for the very common "resolve-then-stream" / "resolve-then-tool-loop" composition it relies on this box-and-re-assert round-trip, with no static signal that the round-trip is needed. (And the round-trip is *not* optional: `catch` is settled as a runtime is-a test on `e` *itself*, so a plain `catch (e) { let c: baml.errors.CallError => … }` arm never fires on the box — the value is a `baml.UnknownError`, which does not implement `CallError` — and the re-assertion is the only way back to the inner error. So the recovery is firm but always explicit: the manual `with_message` laundering and the `from<…>` probe are both load-bearing, never dissolved by an auto-unwrapping catch.)
- **`Escape.as_streaming` returns `baml.errors.Unsupported`, which means the streaming-negotiation failure and a mid-stream transport failure are now the same static type.** `Escape.as_streaming` lives on the `StreamError` channel and throws `baml.errors.Unsupported` (legal, since `Unsupported` implements all four interfaces). Good — but the app catching `s.stream(...) catch (...)` now sees a `StreamError` channel that mixes "this backend can't stream at all" (`Unsupported`, a static capability fact knowable before any byte) with "the stream died at token 400" (a real `StreamError`). They demand opposite responses (pick a different backend vs. resume/retry), and only a concrete-type `match` on `baml.errors.Unsupported` separates them. The classifier interface has no `is_unsupported()`, so the negotiation-vs-runtime distinction is invisible to a classifier-only consumer.
- **Server-authoritative routing state cannot be modeled (out of reach, stated plainly).** LiteLLM's `Router` does least-busy / latency-based routing with a circuit-breaker (`allowed_fails`, `cooldown_time`) — decisions that depend on *live, cross-call* state the server owns. `RoundRobin` fakes a slice of this with a `KVCounter`, but health-aware routing needs shared mutable state and out-of-band health signals that a stateless `HttpProvider.call<T>(prompt) -> T` has no place to carry. The model can express *static* fan-out (a `Provider[]` pool); it cannot express a *stateful, self-adjusting* router without smuggling all the state behind a `$rust_type` handle, at which point the routing logic is host code, not BAML. (Reliability scenario owns the deep version; flagged here because gateways are where it surfaces.)

## (d) Verdict: **Clean**

This is the scenario the proposal models best, and it earns a Clean verdict on its core claim. "A proxy is the same provider with a different base_url," "auth shape is a provider field," and "prefix routing / a registry is an ordinary function returning a Provider" all fall out of the spine with *no patches to the model* — only ordinary library code (`Registry`, `Auth` variants, `Normalized` — the header-merge and prefix-split are plain `Map`/`string` methods, not additions) and honest host boundaries (`sigv4_sign`, `gcp_access_token`, an atomic counter). The portability headline — one function body across six divergent backends, switch by changing a string — is delivered directly by `client`-as-sugar plus the existential `Provider` return, and the lowest-common-denominator trap is expressible (`Normalized` picks the `HttpProvider` request/response surface and forwards both `call` and `call_with`, dropping no usage) with a clean typed escape hatch (`Escape.as_streaming`). It is *not* downgraded to Workable-with-additions because every addition is library/host surface that builds ON the primitives rather than amending them. The per-capability error model holds up here too: dropping the old per-provider `type Error` for one `baml.ExtendUnknownError<baml.errors.CallError>` channel is what lets the registry erase three divergent codecs *and* their three concrete HTTP errors to a single classifier interface, so a LiteLLM-style batch triages every backend the same way. The honest caveats are the ones the proposal already owns and states: a registry cannot give a *compile-time* capability guarantee (OQ-5 — route-by-string XOR static capability, and under the marker revision this now extends to the basic `call`, which is itself a negotiated `HttpProvider` capability rather than a guaranteed base method; the old OQ-1 "degenerate `call` forced onto every provider" is *resolved* by the marker, not a live caveat), and two things sit genuinely outside the model — per-request override knobs (deleted with the options bag in §4) and server-authoritative, health-aware routing state. The error model adds three of its own, of a piece with the capability tension: the existential narrows the *static* concrete-error surface to the `CallError` classifiers (an LCD on the statically-known error side — the concrete error is still recoverable at runtime, but with no `Normalized`-shaped marker to flag that the static guarantee is gone); a resolve-then-stream composition has no static story for moving a `CallError`-only domain error into the `StreamError` channel except boxing it through `UnknownError` (the error survives in `.data`, recoverable via an explicit `from<T>` probe — `catch` is settled as no-auto-unwrap, so a plain `let c: CallError =>` arm never fires on the box and the re-assertion is the only way back to the inner error — but the channel does not advertise it, so recovery is by convention rather than type-directed: a runtime promise, the P2-analog); and routing capability-negotiation failures (`baml.errors.Unsupported`) through the same `StreamError` channel as live transport failures collapses a knowable-up-front fact and a mid-stream fault into one static type. Those are real, but they are the documented edges of the design, not failures of this scenario; within its stated scope the model expresses provider diversity cleanly.
