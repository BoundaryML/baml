# Evaluation — Within-run history + sessions

Adversarial read: does the marker-`Provider` + capabilities model (see `../provider-as-marker.md`: `Provider` is a bare marker; `call`/`call_with` belong to `HttpProvider`) express a stateful transcript cleanly, or does it leak?

## (a) What the proposal reuses unchanged

- **The capability pattern itself.** `Conversational requires Provider` is a textbook application of idea (2): a new interface that refines the base. Nothing about the pattern had to be extended — same `requires`, same default method, same interface-membership `match` in the companion.
- **`build_request → http.Request` as the divergence sink.** The proposal's §1–§2 claim that per-provider wire encoding belongs inside the provider is exactly what lets system-prompt placement (in-array vs top-level) and message grammar (flat vs nested content blocks) live inside `build_chat` with zero shared-layer leakage. The four structured-output encodings reappear here verbatim: `response_format` for OpenAI, forced-tool for Anthropic.
- **Combinator-as-wrapper.** `Windowed` / `Summarizing` are the `Fallback`/`Retry` shape from §6 — a plain class that wraps a `Provider`, re-exposes the capability, and delegates. Windowing is "Iterator.map over the transcript." No new machinery.
- **The `.chat` companion's negotiation** is the §5 `match`-or-error pattern, used in its "error" mode (a one-shot `call` cannot honestly fake conversational memory), exactly like `.live`.
- **Static no-self constructors** (`Session.new`, `Session.ephemeral`, `MemoryStore.new`) reuse the `ArrayIterator.new` idiom.

## (b) Net-new surface it must add (each tied to a primitive)

- **A transcript grammar: `Role`, `Turn`, `Block` union** (`TextBlock`, `ToolUseBlock`, `ToolResultBlock`, `ReasoningBlock`). Tied to: the `type`/tagged-union primitive. The proposal has `ToolCall`/`ToolResult` for the *live* loop but nothing for the *persisted* transcript. This union is genuinely new surface — the transcript is a first-class value the app holds, distinct from the provider-opaque `Tools.Transcript` (§7), which is deliberately opaque and non-persistable.
- **`Conversational` capability interface** (`build_chat`/`chat`/`to_user_turn`/ `to_assistant_turn`/`send_chat`/`parse_chat`). Tied to: `interface … requires Provider`. Net-new because `HttpProvider.call<T>(prompt)` takes only the *new* turn; threading prior turns + persisting both sides is a strictly larger contract. (Both `Conversational` and `HttpProvider` `requires` the same `Provider` marker; they are sibling capabilities, neither built on the other's method.)
- **`Session` + `SessionStore` 4-method protocol** (`load`/`save`/`append`/`clear`). Tied to: `interface`/`implements` and a host-held `$rust_type` cell. Net-new because the proposal has no notion of state that survives a `call` — every provider in the proposal is stateless between calls.
- **`MemoryStore`** as the default `$rust_io_function`-backed store. Tied to: the §7 host-backed-`implements` boundary (Open Question 7).
- **Serializing the assistant turn** uses the real `baml.json.to_string<T>` (canonical JSON for a typed value) — *not* a net-new `sap.to_string`. To persist the assistant turn we serialize a structured `T` back into the transcript; the stdlib already provides this as `baml.json.to_string<T>`, so no new primitive is needed here.
- **No net-new JSON/array helpers.** The request bodies are built from native `map<string, json>` / `json[]` literals serialized with `baml.json.stringify`, and responses are read with `baml.json.from_json<Envelope>` + field access. List/string work uses the real `Array`/`String` methods (`.push`, `.length()`, `.concat`, `.slice`, `.join`) and `baml.math.max`. These are all existing stdlib surface, not additions.
- **A NET-NEW capability-error interface: `baml.errors.SessionError`** (classifier `is_store_unavailable`). Tied to: the error model's rule that *any capability beyond call/stream/realtime/tools gets its own `baml.errors.<Cap>Error` interface*, declared on its methods as `baml.ExtendUnknownError<baml.errors.SessionError>`. Session persistence is exactly such a capability — the `SessionStore` 4-method protocol and `Session.{history,record,reset}` are the only methods in any scenario so far whose failures are neither a call nor a stream nor a tool loop. Net-new surface the proposal's error model must admit. The concrete `StoreUnavailableError` implements *both* `SessionError` and `CallError`, which is what lets a store fault ride the call-path channel of `chat` without forcing `chat` to declare a second error type.

## (c) Where it is awkward, leaky, or unresolved

1. **The Session is a hand-passed parameter, not part of the client.** A client is sugar for `function Name(args) -> Provider` (idea 3) — it is *config-only and stateless by construction*. So the conversation's identity (`session`) cannot ride on the client; it must be threaded as an argument to every `.chat` call. This is the honest consequence of idea (3) but it means "a stateful chat" is two things the app must keep paired (a client + a Session), where the mental model is one thing (a conversation). The proposal gives us no place to bind them.

2. **OQ1 — RESOLVED by the marker model; the old "misleading inherited `call`" complaint no longer applies.** The prior version of this evaluation flagged that `Conversational requires Provider` *inherited* a forgetful base `call`, so `Terse().call<string>(p)` would silently do a stateless one-shot beside the remembering `chat`. Under `../provider-as-marker.md` that footgun is gone at the root: `Provider` is a bare marker with **no** `call`, so a *pure* conversational provider inherits nothing that forgets — a conversation-only client cannot be `.call`-ed at all (the `.call` companion's `_` arm throws `Unsupported`). `call` is now a *separate* `HttpProvider` capability you must opt into. In this scenario `OpenAIChat`/`AnthropicChat` happen to implement **both** `HttpProvider` and `Conversational` (they are genuine request/response models that *also* thread a transcript), so `.call` and `.chat` do coexist on the same value — but that coexistence is now an explicit choice the provider made by implementing two sibling capabilities, not an inheritance the marker forced. The residual footgun is milder and self-inflicted: a model that wants *only* conversational semantics simply omits `implements HttpProvider`. The base/refinement leak the old note described does not exist, because there is no base method to refine.

3. **Open Question 3 (request side is HTTP-specific) resurfaces, doubled.** `build_chat` returns `baml.http.Request`, so a non-HTTP conversational provider (a harness that holds its own transcript, e.g. Claude Code, §8) cannot implement `Conversational` as written — it would have to model history through `Realtime.run`'s channel instead. That's a real fork: **server-authoritative / harness-held transcripts and client-held transcripts do not share this interface.** The proposal cannot express "the transcript lives on the server" (OpenAI `previous_response_id`, Anthropic server-side context editing) through `Conversational` at all — that is a *different* provider whose `Session` would carry an opaque server handle, not a `Turn[]`. We model only the client-held case. Stated plainly: **server-authoritative state is unsupported by this interface and needs its own.**

4. **The `Block` union is a normalization bet that will leak.** The background warns the Responses API uses *typed items* that round-trip the response's `output` straight back into `input`, and that reasoning blocks are echoed by some providers and dropped by others. Our `Block` union is a lowest-common-denominator grammar; the moment a provider emits an item shape not in the union (a Responses `reasoning` item with provider-specific fields, a cache-control marker), `to_assistant_turn` lossily flattens it to text and reasoning continuity silently degrades — the exact failure the background calls out. A faithful model would make `Turn.blocks` provider-opaque, but then windowing/summarizing (which must *read* turns) can't introspect them. There is a genuine tension between a portable transcript and a faithful one, and the model does not resolve it — it picks portable.

5. **`chat`'s persistence is not transactional.** The default method records `[user_turn, assistant_turn]` after a successful parse. If the process dies between the model response and `session.record`, the turn is lost; if `record` half-applies, the transcript desyncs. The 4-method store protocol has `append` but no compare-and-swap / version, so concurrent `.chat` calls on the same Session id race. The proposal offers no concurrency primitive; this is left to the store impl and is under-specified.

6. **Open Question 5 (capability `match` over an existential).** `Ask$chat` relies on `match (p) { let c: Conversational => … }` succeeding at runtime for a value returned as the existential `Provider`. Same dependency as every other scenario, but here it gates *all* memory, so if value-level reflection over `Conversational` is not supported the feature is dead, not degraded.

7. **The error model forces a cross-capability collision that the per-capability channels don't natively resolve.** `chat` is a *call-path* method, so its channel is `baml.ExtendUnknownError<baml.errors.CallError>`. But `chat` internally calls `session.history()` / `session.record()`, whose channel is the net-new `baml.ExtendUnknownError<baml.errors.SessionError>`. Two *different* capability channels meet inside one method, and the error model gives no merge operator — `CallError` and `SessionError` are independent interfaces, not a hierarchy. We resolve it the only way the model allows: a single concrete class (`StoreUnavailableError`) that `implements` **both** interfaces, so a session fault is *also* a `CallError` and is therefore legal to throw on `chat`'s channel. That works, but it is a load-bearing convention, not a guarantee: nothing in the type system *forces* a session error raised on the call path to also be a `CallError`. A `SessionStore` impl that throws a `SessionError`-only class would fail to typecheck *directly* on `chat`'s channel — but it does not vanish: rule 3's trailing `with_message<baml.errors.CallError>(e, …)` boxes it into `baml.UnknownError`, which is legal on the channel, and because `.data` holds the original untouched a later layer where `SessionError` is back in scope recovers the *same* concrete error via `from<baml.errors.SessionError>(e)` — classifiers intact. So the typed session fault survives the crossing; what does *not* survive is the **static** signal. `chat`'s declared channel is `baml.errors.CallError | baml.UnknownError`; it does not advertise that a `SessionError` can be reached inside the box, so a consumer recovers it only by *speculatively* probing `from<SessionError>`, never by following the type — the P2 (capability-as-runtime-promise) story applied to the error channel. The two repairs that *would* restore the static signal both re-introduce surface the model meant to delete: widen `chat`'s channel to `baml.errors.CallError | baml.errors.SessionError` (a *composed* capability needs a *union* of capability channels, which the canonical table does not enumerate), or make `StoreUnavailableError` `implement` both interfaces by hand (the multi-implements route). The clean per-capability model is clean only for *leaf* capabilities; the moment one capability's default method drives another's store, the cross-capability precision is recoverable at runtime but no longer typed — and recovery is **explicit, never transparent**: a plain `catch (e) { let c: baml.errors.SessionError => … }` arm is a bare is-a test on `e` *itself*, and a boxed fault *is* a `baml.UnknownError` (which does not implement `SessionError`), so that arm never fires on it. To pull the session error back out the author must explicitly `baml.UnknownError.from<baml.errors.SessionError>(e)` inside the `UnknownError` arm — `error-model.md`'s unwrap rule is settled, so the cost is firm: a plain catch across the boundary only ever sees `CallError` or `UnknownError`, and the down-stack `SessionError` is reachable only by code that already knows to probe for it.

8. **`StoreUnavailableError.is_network_error → true` is a lie of convenience.** To make a store fault triageable by a `CallError`-shaped consumer (`if (c.is_network_error()) retry()`), we mapped `is_store_unavailable` onto `is_network_error`. But a Postgres deadlock or a missing-session is *not* a network error — the classifier vocabulary of `CallError` (network / rate-limit / parse) has no cell for "your durable store is down," so we borrow the nearest-fitting bool. This is the general hazard of rule 4's "reuse the classifiers": when a novel capability's failure taxonomy doesn't line up with the core three classifiers, the concrete error either lies (as here) or answers `false` to all of them and becomes invisible to interface-level triage — recoverable only by catching the concrete type. The new `is_store_unavailable` classifier exists precisely because the core trio couldn't express the distinction; that it had to be added is the evidence that the classifier set is capability-specific, not universal.

## (d) Verdict

**Workable-with-additions.** The transcript-as-memory baseline maps cleanly onto a new `requires Provider` capability, and the two genuinely divergent providers (OpenAI in-array system + flat messages; Anthropic top-level system + nested content blocks with id-correlated tool_result) are absorbed entirely inside `build_chat`, which is the proposal's whole thesis working as advertised. Windowing and summarizing fall out as ordinary wrappers. The additions are real but disciplined: a `Turn`/`Block` grammar, a `Session` + 4-method `SessionStore`, a `Conversational` interface, and — under the new error model — a net-new `baml.errors.SessionError` capability-error interface plus a `StoreUnavailableError` that implements both it and `CallError` so a store fault can ride the call-path channel of `chat`. (Transcript serialization and request/response JSON ride existing stdlib surface — `baml.json.to_string`/`stringify`/`from_json` and the `Array`/`String` methods — not new primitives.) The model is *not* clean on two fronts the background forces into view: (1) idea (3)'s stateless-client rule means the Session can never be part of the client, so a "conversation" is permanently two paired values; and (2) server-authoritative / harness-held transcripts (Responses `previous_response_id`, Anthropic server-side context editing) are simply not expressible through this `http.Request`-shaped interface and require a separate provider — which the proposal's §8 harness story hints at but this capability does not deliver. The earlier third front — OQ1's "forgetful `call` sitting beside the remembering `chat`" — is **resolved** by the marker model (`../provider-as-marker.md`): `Provider` carries no `call`, so a pure-conversational provider inherits no forgetful method; `OpenAIChat`/`AnthropicChat` expose `.call` only because they explicitly *also* implement `HttpProvider`, a deliberate sibling-capability choice rather than an inherited footgun.
