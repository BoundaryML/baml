# Evaluation — Durable execution

Adversarial read: does the provider/capability/combinator model express record-once-replay-forever durability, and where does it leak?

## (a) What the proposal reuses unchanged

- **The `Cache` combinator shape, verbatim.** `Durable` is `Cache` with a different key (a step coordinate, not a prompt hash) and a different store (the engine's step log, not a generic KV). It is a plain non-generic class that wraps `inner: Provider` (the bare marker) and `implements HttpProvider` — the capability that owns `call`/`call_with` under the marker-`Provider` revision (`../provider-as-marker.md`) — exactly the spine's `Cache { inner, store }`. The proposal's claim that "orchestration lives in combinators that wrap a Provider" holds: durability is orchestration, and it rode in as a combinator forwarding one capability, with no new language surface. The combinator factories (`with_retry`/`cached`/`durable`) are inherited via `requires Provider` on the marker, so `Durable` is itself composable.
- **The fluent combinator method.** `p.durable(log, coord)` is `DurableExt`, an interface `requires Provider` adding one default method — the same `Iterator.map` pattern as `with_retry`/`cached`. `Claude().durable(...).call<Intent>(...)` reads like every other chain.
- **`client` = function returning Provider.** Because `Claude()` is literally a function returning the existential `Provider`, the workflow body can reach the bare provider and wrap it. No special "durable client" kind was needed — the sugar already gives an expression of provider type.
- **Host-backed `implements` blocks.** The three engine adapters (`TemporalStepLog`/`DbosStepLog`/`InngestStepLog`) are `implements StepLog` with `$rust_io_function` bodies — the same bridge boundary as `PrimitiveClient` and the harness in §8 (Open Question 7). Swapping engines is swapping the `StepLog` value, which matches the background's "swap the adapter, not the agent."
- **`throws`/`catch` and interface-membership `match`.** The replay/first-run fork is a `match (prior) { let hit: string => …, null => … }`; the agentic variant gates `Tools` with the standard capability `match`.
- **The per-capability error channel, verbatim.** `Durable.call` declares `baml.ExtendUnknownError<baml.errors.CallError>` exactly like the `HttpProvider.call` it forwards — there is no per-combinator error type and no widening. Foreign failures are normalized once at a trailing `} catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CallError>(e, …) }`, and because `with_message<CallError>` returns any value that *is* a `CallError` unchanged, the inner provider's typed errors (a rate-limit, a `Refused`) — and the step-log `Io`, since `baml.errors.Io` implements `CallError` — all pass straight through the wrapper to the workflow as their typed selves; only a genuinely foreign value (a host panic, unmapped JSON) actually lands as `baml.UnknownError`. `DurableDispatch.dispatch` does the same on the `baml.errors.ToolError` channel, and the agentic variant's capability-negotiation `_` arm throws `baml.errors.Unsupported` (legal on the tool channel because `Unsupported` implements every capability interface). The "combinators declare the same channel" rule is what lets `Durable` wrap an existential `Provider` without knowing or restating its concrete error types.
- **The value+sidecar `call_with`, forwarded (the P1 fix).** Because `Durable` now `implements HttpProvider`, it owns `call_with<T,U>` alongside `call`. It does not drop the sidecar: it `match`es `self.inner` for `HttpProvider` and forwards the projection to the inner provider's own `call_with`, so usage/cost/logprobs the live call produces still reach the workflow's `project`. The record/replay determinism guard rides `call`; the sidecar path forwards rather than fabricating a recorded `ResponseMeta` — the combinator stays honest (it forwards a member's `call_with`, it does not invent fake codec methods).

## (b) Net-new surface it must add

| Net-new | Tied to which primitive | Why it's unavoidable |
|---|---|---|
| `interface StepLog` (`recorded`/`record`/`deterministic_now`) | A new **host capability interface** at the bridge boundary (OQ7). | The engine's step log is server-authoritative state BAML cannot model in pure BAML; it must be an existential the adapter supplies. |
| `class StepCoord { run, step }` | A new **host primitive / value type**. | Durability is keyed by the *workflow coordinate*, a concept absent from the provider model (which keys only by prompt). |
| `class Durable` combinator | Builds on the **`Cache` pattern**, but is genuinely new. | Cache keys by prompt and may legitimately miss; `Durable` keys by coordinate and a *miss-then-prompt-change is an error*, not a re-fetch. |
| `baml.llm.prompt_fingerprint(PromptAst) -> string` | New host function on the **opaque `PromptAst`**. | The determinism guard needs to compare prompts across replay; PromptAst is opaque so only the host can hash it. |
| `durable_encode<T>/decode<T>`, envelope helpers | New host functions over the **generic `T`** + `parse` seam. | Recording happens at the wire layer so a schema edit re-parses the *same bytes* instead of re-sampling — this needs a T-aware serializer the runtime owns. |
| `class DurableDispatch` wrapping `ExecutionContext.dispatch` | Builds on the **`Tools`/`ExecutionContext` seam** (§7, already flagged net-new). | Idempotent tool execution is where the dangerous side effects live; it needs the step log inside `dispatch`, which means `ExecutionContext` must be wrappable. |
| `interface baml.errors.DurabilityError` (`is_non_determinism`/`is_step_log_error`) + `class NonDeterministicReplay` | A new **capability-error interface** in `baml.errors`, alongside `CallError`/`StreamError`/`ToolError`/`RealtimeError`. | Durability is a net-new capability whose characteristic failure (a replay that sees a changed prompt) is neither network, rate-limit, nor parse — none of the existing classifiers describe it, so it needs its own interface. `NonDeterministicReplay` implements **both** `CallError` (it surfaces on the call path so callers triaging by `is_network_error()`/… still see it) and `DurabilityError`. |

The honest count: the *combinator mechanism* and the per-capability error channel are reused, but durability drags in an entire host-state primitive (`StepLog` + `StepCoord`), a prompt fingerprint the provider model never anticipated, AND a new `baml.errors.DurabilityError` interface for the determinism-violation failure mode. These are real additions, not sugar.

## (c) Where it is awkward, leaky, or unresolved

- **The record/replay boundary is at the wrong layer, and the model can't say so.** Correctness demands recording the *wire response* (so replay re-parses the same bytes) — but `Durable.call` forwards `self.inner.call<T>(prompt)`, which hands back the *already-parsed* value `T`. We record `durable_encode<T>(answer)` after parsing, which is fine until the output schema `T` changes between runs: then replay decodes stale bytes into the old shape, never re-parsing under the new schema. To record at the response layer we'd have to drive `HttpProvider`'s `send`/`parse` seam directly (`send` returns `Body`) and forward `inner` as a concrete `HttpProvider` rather than the bare `Provider` marker — but then the combinator is no longer transport-agnostic and can't wrap a harness or a `Fallback`. Forwarding the `HttpProvider.call` capability is too narrow to express "record the response, replay the parse," which the background calls the central correctness issue. **This is OQ3/OQ4 biting:** the request/response seam (`send`/`parse`) is HTTP-specific, so a combinator that forwards `call` across the existential marker can only see the post-parse `T`.

- **Capabilities don't compose with replay, and the type system happily lies.** `Durable` forwards only `HttpProvider` (request/response). A streamed call has no replayable result — you cannot resume half a token stream from a step log — so we deliberately do not implement `Streaming`/`Realtime`/`Tools` on `Durable`. Good, and under the marker revision this is the *honest* shape: `Durable` claims exactly the one capability it forwards and nothing else, with no degenerate `stream`/`run` to fake. But this means `Claude().durable(log, c).stream(...)` does not type-error; capability is a *runtime promise* (§5), so it compiles and only fails when the `Foo.stream` companion `match`es `Durable` against `Streaming`, misses, and degrades to buffering an `HttpProvider.call` — which *does* match `Durable` (it implements `HttpProvider`), so the buffer-as-stream path runs the durable `call` rather than re-sampling around it. The subtler hazard is the reverse: a plain `Foo(args)` value companion that degrades a `Streaming`-only client by draining its stream cannot run through `Durable` at all, since `Durable` is not `Streaming`. The model gives no compile-time way to say "this combinator is call-only." **OQ5** (capability `match` over the existential) is exactly why the guarantee can't be static.

- **Idempotency stays the author's burden — the model can't enforce it.** The background is blunt: at-least-once means the framework *will* re-run a step, and making the *effect* once-only is application work. `DurableDispatch` records after the side effect, so the crash-after-effect/before-record window still double-charges unless the *tool's own* idempotency key dedupes downstream. The proposal cannot close this — there is no place in `HttpProvider.call` or `Tools.dispatch` to express "this effect is idempotent under key K" as a checked property. We pass `key` by convention into `charge_card`; nothing in the type system ties it to the coordinate. This is a genuine *cannot-express*, not an awkwardness.

- **Determinism rules are unchecked.** §4 forbids wall-clock/rng/direct-I/O in the replayed body. We provide `deterministic_now` on `StepLog`, but nothing *stops* a workflow author from writing `baml.sys.now()` in `BillingWorkflow` directly. BAML has no effect system to mark a function "replay-safe," so the determinism contract is documentation, exactly as it is in Temporal's Python SDK. The provider model neither helps nor hurts here.

- **A determinism violation rides the call channel typed, but its real classification lives on a second interface the channel doesn't advertise.** A determinism violation is a *durability* failure, but `Durable.call` declares `baml.ExtendUnknownError<baml.errors.CallError>` — that is the channel `HttpProvider.call` owns, and the whole point of a forwarding combinator is to pass it through unchanged. So `NonDeterministicReplay` `implements` `CallError` (to be throwable here, caught concretely with **no box**) *and* `DurabilityError` (its real classification) — a clean two-interface impl, not a forced widening. The friction is purely the classifier *vocabulary*: its three `CallError` classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) all answer `false`, because the `CallError` vocabulary has no word for "the replayed body changed." A workflow author catching `baml.errors.CallError` to drive retry/backoff will see this error, find every classifier false, and have no *in-`CallError`-vocabulary* signal that retrying is futile (the body changed; re-running won't help). To branch correctly they `catch` the concrete `NonDeterministicReplay` *or* the `DurabilityError` interface — both legal arms, since the error implements both, and neither boxes. What they *cannot* do is read the durability signal off the declared `CallError` channel: a caller holding only the existential `Provider` and catching the declared channel sees the value typed but classifies it as a generic `CallError`, because the static channel does not advertise that `DurabilityError` is also reachable. The gap is **discoverability of the second classification on a shared channel, not expressibility** — the error stays typed and concretely catchable; what's missing is a static hint that `is_non_determinism` is worth probing. **This is the dual of the (c) capability-composition leak:** capabilities are a runtime promise, and so is the second error-interface a value carries on a shared channel.
- **The read-vs-write step-log distinction the engine needs for retry policy is carried but never surfaced as a classifier — the data survives, but the channel doesn't advertise it.** The old code threw distinct messages for "step log read failed" vs "step log write failed". Under the new model the foreign step-log `Io` is *not* lost: `baml.errors.Io` already implements all four core capability interfaces (including `CallError`), so the trailing `with_message<CallError>` catch returns the `Io` **unchanged** — it rides the `CallError` channel as its typed self, *not* boxed into `baml.UnknownError`. A consumer can catch `let io: baml.errors.Io =>` directly and a read-vs-write predicate on it still answers. (Only a *genuinely foreign* step-log failure — a host panic, an unmapped JSON shape that is not a `baml.errors.Io` — would box into `UnknownError`; there the original survives in `.data` and a re-assertion `from<Io>(e)` at any later layer where `Io` is back in scope pulls the concrete value back out.) A durable engine genuinely treats a *read* failure (transient, safe to replay) differently from a *write* failure (the step may have committed — re-running risks a double effect), and that information is recoverable — what is missing is the **classifier-vocabulary** signal: `CallError`'s classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) say nothing about read-vs-write, so an author triaging *by the `CallError` interface* gets no word for the distinction, and the declared channel `baml.errors.CallError | baml.UnknownError` doesn't hint that an `Io` carrying it is even reachable. If we wanted that distinction as a statically discoverable, classifier-driven property we'd add it cheaply: declare, in the durability package, `implements baml.errors.DurabilityError for baml.errors.Io` (external impl — local trait, foreign type) so a step-log `Io` *also* answers `is_step_log_error`, or mint a `StepLogError implements DurabilityError` for the bespoke case — one `implements` row either way, not a per-callsite rewrite. (And the boxed-recovery rule is settled, not open: when something *does* box, a `catch (e) { let io: ... => … }` arm is a plain is-a test on `e` itself, and a `baml.UnknownError` is not an `Io` — so the arm never fires on the box; recovery there is never transparent, the author must `from<Io>(e)` by hand inside the `UnknownError` arm.) The model loses neither the value nor the type — it only declines to *force* a read-vs-write classifier onto a channel that doesn't natively carry one.

- **The step coordinate is hand-threaded.** `run` and the per-step `step` name are passed as ordinary parameters and assembled into `StepCoord` literals in the body. A wrong/duplicated `step` name silently aliases two steps' caches — a determinism violation we can only catch via the prompt fingerprint, not prevent. Real engines auto-assign a monotonic step id from execution position; expressing that would need the runtime to inject the coordinate, which the pure-function `client` model has no hook for. **OQ2-adjacent:** like the live `io` channel, the coordinate is execution-time state the config-only client can't carry, so it leaks into the function signature.

## (d) Verdict

**Workable-with-additions.** The combinator spine carries durability gracefully — `Durable` is `Cache` with a coordinate key, engine adapters are `StepLog` implementations, and engine-swapping is value-swapping, which is the right shape. The per-capability error channel rides along just as cleanly: `Durable.call` forwards `baml.ExtendUnknownError<baml.errors.CallError>` unchanged, the step-log `Io` (which implements `CallError`) and the inner provider's typed errors pass through the wrapper as their typed selves, and only a genuinely foreign value normalizes through the one trailing `UnknownError` catch. But it leans on substantial net-new host surface (`StepLog`, `StepCoord`, `prompt_fingerprint`, T-aware record/replay codec, plus a new `baml.errors.DurabilityError` interface) that the provider model never anticipated, and it hits two things the model genuinely *cannot* express: (1) recording at the wire-response layer while staying transport-agnostic — forwarding the `HttpProvider.call` capability across the existential marker only exposes the parsed `T`, so a mid-run schema change replays stale bytes (OQ3/OQ4); and (2) a compile-time guarantee that a durable provider is call-only or that a tool effect is idempotent — capability is a runtime promise (OQ5) and BAML has no effect system. The error model is *not* a third such limit: a determinism violation that *is* a durability failure but rides the `CallError` channel `Durable.call` inherits stays fully typed — `NonDeterministicReplay` implements both `CallError` and `DurabilityError` (a clean two-interface impl, no box, caught concretely on either arm); what's lost is only *discoverability* on the shared channel — its three `CallError` classifiers answer false (the `CallError` vocabulary has no word for non-determinism) and the declared channel doesn't advertise that `DurabilityError` is also reachable, exactly the same runtime-promise shape as capability negotiation. The central correctness property (record-and-replay, never re-sample) *is* expressible and reads cleanly; the sharp edges are the layer of the recording and the absence of static guarantees — limits of the proposal's shape, with the error model adding only a discoverability convention, not a wall.
