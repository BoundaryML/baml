# Evaluation — Durable execution

Adversarial read: does the provider/capability/combinator model express record-once-replay-forever durability, and where does it leak?

## (a) What the proposal reuses unchanged

- **The `Cache` combinator shape, verbatim.** `Durable` is `Cache` with a different key (a step coordinate, not a prompt hash) and a different store (the engine's step log, not a generic KV). It is a plain non-generic class that `implements Provider` and wraps `inner: Provider` — exactly the spine's `Cache { inner, store }`. The proposal's claim that "orchestration lives in combinators that wrap a Provider" holds: durability is orchestration, and it rode in as a combinator with no new language surface.
- **The fluent combinator method.** `p.durable(log, coord)` is `DurableExt`, an interface `requires Provider` adding one default method — the same `Iterator.map` pattern as `with_retry`/`cached`. `Claude().durable(...).call<Intent>(...)` reads like every other chain.
- **`client` = function returning Provider.** Because `Claude()` is literally a function returning the existential `Provider`, the workflow body can reach the bare provider and wrap it. No special "durable client" kind was needed — the sugar already gives an expression of provider type.
- **Host-backed `implements` blocks.** The three engine adapters (`TemporalStepLog`/`DbosStepLog`/`InngestStepLog`) are `implements StepLog` with `$rust_io_function` bodies — the same bridge boundary as `PrimitiveClient` and the harness in §8 (Open Question 7). Swapping engines is swapping the `StepLog` value, which matches the background's "swap the adapter, not the agent."
- **`throws`/`catch` and interface-membership `match`.** The replay/first-run fork is a `match (prior) { let hit: string => …, null => … }`; the agentic variant gates `Tools` with the standard capability `match`.

## (b) Net-new surface it must add

| Net-new | Tied to which primitive | Why it's unavoidable |
|---|---|---|
| `interface StepLog` (`recorded`/`record`/`deterministic_now`) | A new **host capability interface** at the bridge boundary (OQ7). | The engine's step log is server-authoritative state BAML cannot model in pure BAML; it must be an existential the adapter supplies. |
| `class StepCoord { run, step }` | A new **host primitive / value type**. | Durability is keyed by the *workflow coordinate*, a concept absent from the provider model (which keys only by prompt). |
| `class Durable` combinator | Builds on the **`Cache` pattern**, but is genuinely new. | Cache keys by prompt and may legitimately miss; `Durable` keys by coordinate and a *miss-then-prompt-change is an error*, not a re-fetch. |
| `baml.llm.prompt_fingerprint(PromptAst) -> string` | New host function on the **opaque `PromptAst`**. | The determinism guard needs to compare prompts across replay; PromptAst is opaque so only the host can hash it. |
| `durable_encode<T>/decode<T>`, envelope helpers | New host functions over the **generic `T`** + `parse` seam. | Recording happens at the wire layer so a schema edit re-parses the *same bytes* instead of re-sampling — this needs a T-aware serializer the runtime owns. |
| `class DurableDispatch` wrapping `ExecutionContext.dispatch` | Builds on the **`Tools`/`ExecutionContext` seam** (§7, already flagged net-new). | Idempotent tool execution is where the dangerous side effects live; it needs the step log inside `dispatch`, which means `ExecutionContext` must be wrappable. |

The honest count: the *combinator mechanism* is reused, but durability drags in an entire host-state primitive (`StepLog` + `StepCoord`) and a prompt fingerprint that the provider model never anticipated. These are real additions, not sugar.

## (c) Where it is awkward, leaky, or unresolved

- **The record/replay boundary is at the wrong layer, and the model can't say so.** Correctness demands recording the *wire response* (so replay re-parses the same bytes) — but `Durable` wraps `Provider`, whose only method is `call<T> -> T`, the *already-parsed* value. We record `durable_encode<T>(answer)` after parsing, which is fine until the output schema `T` changes between runs: then replay decodes stale bytes into the old shape, never re-parsing under the new schema. To record at the response layer we'd have to wrap `HttpProvider` (`send` returns `Body`) instead of `Provider` — but then the combinator is no longer transport-agnostic and can't wrap a harness or a `Fallback`. The base `Provider` is too narrow to express "record the response, replay the parse," which the background calls the central correctness issue. **This is OQ3/OQ4 biting:** the request/response seam is HTTP-specific, so a transport-agnostic combinator can only see the post-parse `T`.

- **Capabilities don't compose with replay, and the type system happily lies.** `Durable` forwards only `Provider`. A streamed call has no replayable result — you cannot resume half a token stream from a step log — so we deliberately do not implement `Streaming`/`Realtime`/`Tools` on `Durable`. Good. But this means `Claude().durable(log, c).stream(...)` does not type-error; capability is a *runtime promise* (§5), so it compiles and only fails when the companion `match`es `Durable` against `Streaming`, misses, and falls back to `.call` (buffering) — silently re-sampling the buffered call **without** going through the durable path at all, because the fallback calls `p.call` on the *inner*, not the wrapper. The model gives no compile-time way to say "this combinator is call-only." **OQ5** (capability `match` over the existential) is exactly why the guarantee can't be static.

- **Idempotency stays the author's burden — the model can't enforce it.** The background is blunt: at-least-once means the framework *will* re-run a step, and making the *effect* once-only is application work. `DurableDispatch` records after the side effect, so the crash-after-effect/before-record window still double-charges unless the *tool's own* idempotency key dedupes downstream. The proposal cannot close this — there is no place in `Provider.call` or `Tools.dispatch` to express "this effect is idempotent under key K" as a checked property. We pass `key` by convention into `charge_card`; nothing in the type system ties it to the coordinate. This is a genuine *cannot-express*, not an awkwardness.

- **Determinism rules are unchecked.** §4 forbids wall-clock/rng/direct-I/O in the replayed body. We provide `deterministic_now` on `StepLog`, but nothing *stops* a workflow author from writing `baml.sys.now()` in `BillingWorkflow` directly. BAML has no effect system to mark a function "replay-safe," so the determinism contract is documentation, exactly as it is in Temporal's Python SDK. The provider model neither helps nor hurts here.

- **The step coordinate is hand-threaded.** `run` and the per-step `step` name are passed as ordinary parameters and assembled into `StepCoord` literals in the body. A wrong/duplicated `step` name silently aliases two steps' caches — a determinism violation we can only catch via the prompt fingerprint, not prevent. Real engines auto-assign a monotonic step id from execution position; expressing that would need the runtime to inject the coordinate, which the pure-function `client` model has no hook for. **OQ2-adjacent:** like the live `io` channel, the coordinate is execution-time state the config-only client can't carry, so it leaks into the function signature.

## (d) Verdict

**Workable-with-additions.** The combinator spine carries durability gracefully — `Durable` is `Cache` with a coordinate key, engine adapters are `StepLog` implementations, and engine-swapping is value-swapping, which is the right shape. But it leans on substantial net-new host surface (`StepLog`, `StepCoord`, `prompt_fingerprint`, T-aware record/replay codec) that the provider model never anticipated, and it hits two things the model genuinely *cannot* express: (1) recording at the wire-response layer while staying transport-agnostic — the base `Provider` only exposes the parsed `T`, so a mid-run schema change replays stale bytes (OQ3/OQ4); and (2) a compile-time guarantee that a durable provider is call-only or that a tool effect is idempotent — capability is a runtime promise (OQ5) and BAML has no effect system. The central correctness property (record-and-replay, never re-sample) *is* expressible and reads cleanly; the sharp edges are the layer of the recording and the absence of static guarantees, both of which are pre-existing limits of the proposal rather than new failures.
