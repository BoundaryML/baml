# Scenario 45 — Durable execution

A workflow that survives crashes, restarts, and long waits: on recovery the engine replays the body, skipping completed steps and resuming the unfinished tail. The hard part for an LLM workflow is that a replayed step must reproduce its result, but a model call is nondeterministic — so the model call inside a durable step must be **recorded-and-replayed, never re-sampled**. This scenario expresses that as `Durable`, a `Cache`-shaped combinator keyed by a `(run, step)` coordinate over the engine's own step log, with engine adapters (Temporal / DBOS / Inngest) as `StepLog` implementations and an idempotent `DurableDispatch` for side-effecting tool calls. `Durable` forwards the request/response capability — under the marker-`Provider` revision (`../provider-as-marker.md`) it `implements HttpProvider` (which owns `call`/`call_with`), not the bare `Provider` marker. `implement.baml` is the library code; `usage.baml` is the billing workflow an app author writes; `evaluation.md` stresses where even `HttpProvider`'s post-parse `call<T>` is too narrow to record at the wire layer and where determinism and idempotency can only be conventions, not guarantees.
