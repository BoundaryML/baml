# Evaluation — Cost & tokens + batch / async inference

Adversarial read of whether the proposed model expresses metering, budgeting, and the batch lifecycle cleanly. It does not — metering needs a new return-value seam the base `Provider` structurally cannot carry, and batch is server-authoritative state the existential `Provider` cannot promise.

## (a) What the proposal reuses unchanged

- **`service_tier` dissolves into provider fields (§4).** OpenAI's `flex`/`priority` and Anthropic's `auto`/`standard_only` are bespoke fields on the two classes, with *different value sets* and no shared blob. The pricing "processing mode" axis lands with zero friction — `pricing_mode()` reads the field and maps it to a `PricingMode`. This is the cleanest part.
- **Per-provider usage normalization is exactly the four-encodings pattern.** The background's three usage vocabularies are the cost analog of the four structured-output encodings the proposal already pushes inside `build_request`. `usage_from(raw) -> Usage` lives inside each provider's `implements Metering`, per the rule "what can't be written once for all providers stays in the provider." OpenAI's `prompt_tokens`/`completion_tokens` vs Anthropic's `input_tokens`/`output_tokens` + `cache_creation`/`cache_read` map cleanly.
- **Budget is a Provider, so it composes via the combinator pattern (§6).** `Budget` wraps an inner `Provider` and forwards `.call`/`call_metered` by runtime delegation — identical in shape to `Fallback`/`Retry`/`Cache`. Because it is a `Provider`, `Budget { inner: Fast().fallback_to(Claude()) }` works and the inner Fallback's model swaps still flow through one accumulator (the model is read off `Metered<T>.model`, not assumed).
- **Batch reuses the background-jobs handle pattern (scenario 27) verbatim.** `BatchHandle<T>` (opaque id + `owner` + count), `BatchState` mirroring server-authoritative status, `run_batch` as a default over `submit/poll/download` — these are the `Job<T>` / `await` shapes already validated for async lifecycles. The `custom_id` rejoin is the same "correlation id the loop never interprets" discipline as `ToolCall.id` (§7).
- **`throws`/`catch` + interface-membership `match`** carry the whole "is this provider Metering / Batch?" negotiation and the budget-exceeded abort.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`Metered<T>` — a (value, usage) pair.** Tied to the base `Provider.call<T> -> T`. This is the irreducible gap: `call` returns `T`, and there is *no field on the return* to hang usage on. Every metering feature descends from this one missing pair. The proposal never models a side-channel on the result.
2. **The `Metering` capability** (`call_metered` + `usage_from`). Tied to the capabilities-as-`requires Provider` mechanism. It is a genuine capability — not a delivery refinement — because (unlike `Streaming`) you cannot fabricate usage from a `.call` that didn't report it. So its companion `match` *errors* on the `_` arm rather than degrading (proposal §5's "different shape" branch).
3. **`RawBody` + `ChatMetering`.** Tied to `HttpProvider`'s `parse<T>`. To parse BOTH the value and the usage from one body without re-issuing the request, the metering default needs the raw body text that `parse<T>` consumes. `parse<T>` takes the typed `Body` but hands back only `T`; usage lives in the same bytes, so we add a `body_text(Body) -> string` seam. This is a real wart: the value and usage seams are not unified.
4. **`Usage` / `PriceTable` / `PriceRow` / `Cost` / `PricingMode`.** Tied to nothing in the proposal — pure new vocabulary. `Usage.add` is the load-bearing op for fan-out summing; `PricingMode` makes batch/flex/priority a *multiplier* rather than a parallel table.
5. **`BudgetCell { _cell: $rust_type }` — mutable host state.** Tied to nothing in the proposal, and the central conflict (see (c)). The running total must be shared across a fan-out tree; the `client -> function -> Provider` sugar cannot own mutable state, so the accumulator is a host cell threaded by hand.
6. **The `Batch` capability + `BatchRequest`/`BatchResult<T>`/`BatchHandle<T>`/ `BatchState`/`BatchCounts`.** Tied to the capability mechanism. Batch is many-prompts, server-side, separate-rate-pool, unordered-with-rejoin — none of which the single-prompt `call<T>` shape can express, so it earns its own interface with its own lifecycle.
7. **Host JSON/IO seams** (`baml.json.*`, `openai_upload_jsonl`, `anthropic_create_batch`, `baml.sys.now_ms`, `to_float`, `fmt_usd`). Tied to `baml.http`/host boundaries. JSONL assembly and file upload are genuinely host-level; the normalization arithmetic above them is pure BAML.

## (c) Where it is awkward, leaky, or unresolved

- **Metering breaks the base contract — Open Question 1 directly.** OQ1 asks whether every capability should `requires Provider` (a best-effort `.call`) or whether some should stand alone. Metering is the sharpest case *against* the uniform answer: `Metering requires Provider` gives a metered provider a plain `.call` that **silently discards** the usage it just measured. The information exists and is thrown away on the base path. The honest model would make `call` itself return richer data, or make metering a wrapper that *replaces* `.call` — but the proposal's "call<T> -> T is irreducible" forbids both. We chose the capability route and accept that `.call` is the lossy convenience.

- **The Budget needs mutable cross-call state, and the `client` sugar forbids it — Open Question (implicitly 3, the request-side/statelessness assumption).** A `client` is `function(args) -> Provider { body }`; a function cannot own a mutable accumulator that persists across the many calls of a fan-out tree. So `Budgeted` is a plain `function` taking a `BudgetCell` argument, NOT a `client`, and the cell is constructed imperatively in `TriageRun`. The proposal's headline ergonomic ("the app author writes one line") does not hold for budgeting: the app must construct a cell, thread it, and read it back. This is the same gap `RoundRobin` hit in scenario 29 — combinators that accumulate state are second-class citizens of the sugar.

- **Reasoning tokens leak through normalization — and the leak is invisible.** The background flags hidden-but-billed reasoning as a hard problem. Our `Usage` has a `reasoning_tokens` sub-field, and OpenAI fills it from `completion_tokens_details.reasoning_tokens`. But **Anthropic does not itemize reasoning** (it folds it into `output_tokens`), so `Anthropic.usage_from` sets `reasoning_tokens: 0` even when extended thinking ran. Cost is still correct (output rate already bills it), but any app that *reports* "you spent N reasoning tokens" silently under-reports on Anthropic. The normalized field is a lie of omission on half the providers — and nothing in the type system warns you. This is a fundamental floor: you cannot normalize a number a provider refuses to send.

- **Capability is a runtime promise — no compile-time "this client can meter / batch" — Open Question 5.** Because `client` returns the existential `Provider`, `Classify.metered(...)` and `ScoreBacklog(...)` can only `match` at runtime and *throw* if the provider is not `Metering`/`Batch`. An app that wires a non-batch client to an offline cron job gets a runtime `Unsupported`, not a compile error. The escape hatch (drop the sugar, write `function ScoreBacklog(...) -> Provider`... still existential; you'd need a concrete `-> Anthropic` return to make `Batch` static) defeats the portability the whole design is selling. OQ5's "runtime membership testing" is load-bearing here and it is strictly weaker than what a cost-sensitive batch pipeline wants.

- **Server-authoritative batch state cannot be modeled, only mirrored.** `Batch` exposes `poll_batch -> BatchState`, but the proposal has no notion of state the *server* owns and the client merely reads. We mirror the lifecycle enum verbatim (like scenario 27), which works, but there is no language-level guarantee that our `BatchStatus` stays in sync with the provider's, and the 24h-window/`Expired`/partial-results semantics live entirely in host functions the type system can't see. The proposal is silent on durable, externally-owned state; we bolt it on.

- **Pre-flight counting drift is unaddressed and arguably unaddressable here.** The background notes pre-flight token estimates drift (tokenizer per model, images/tools). Nothing in this model lets you get an *authoritative* count before sending — `usage_from` only runs on a *response*. A `count_tokens` capability would be yet another `requires Provider` interface, and it would still be per-provider and still an estimate for some. We did not add it; it would be net-new surface #8 with the same runtime-promise weakness as the rest.

## (d) Verdict

**Workable-with-additions.** The combinator and capability machinery genuinely absorb the *shape* of this scenario: usage normalization sits inside providers like the structured-output encodings, `Budget` composes as a Provider, and batch reuses the background-jobs handle pattern cleanly. But the additions are not cosmetic. Metering forces a new return-value pair (`Metered<T>`) that exposes the base `call<T> -> T` as too narrow (OQ1), and the load-bearing Budget-over-a-tree requires mutable host state that the `client` sugar structurally cannot hold, demoting budgeting from a one-line client to a hand-threaded function. The reasoning-token leak and the runtime-only capability promise (OQ5) are real floors the proposal cannot raise. It works, but only by adding one new capability, one new combinator-with-host-state, and one new result type — and by accepting that "what did this cost" is a best-effort, runtime-negotiated answer rather than a guaranteed one.
