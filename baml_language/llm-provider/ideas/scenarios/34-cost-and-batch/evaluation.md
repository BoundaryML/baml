# Evaluation — Cost & tokens + batch / async inference

Adversarial read of whether the proposed model expresses metering, budgeting, and the batch lifecycle cleanly. The metering half is now **resolved with a named mechanism**: usage is a *product sidecar* (value AND metadata), so it rides the `call_with` + `ResponseMeta` seam owned by the `HttpProvider` capability (`value-sidecar-model.md`; the marker `Provider` carries no interaction method, so `call`/`call_with` live on `HttpProvider` — `../provider-as-marker.md`) — no bespoke `Metered<T>`/`call_metered` companion, and no silent drop under Fallback. What stays genuinely separate is what was *never* P1's problem: **budgeting** is a SUM/stateful round-trip (a running total over many calls, against mutable host state — not one response's sidecar), and **batch** is server-authoritative state where the handle *replaces* the answer (a `submit -> handle` lifecycle, not `(T, U)`). Those two keep their own mechanisms; the cost arithmetic and money/batch error channels are unchanged.

## (a) What the proposal reuses unchanged

- **`service_tier` dissolves into provider fields (§4).** OpenAI's `flex`/`priority` and Anthropic's `auto`/`standard_only` are bespoke fields on the two classes, with *different value sets* and no shared blob. The pricing "processing mode" axis lands with zero friction — `pricing_mode()` reads the field and maps it to a `PricingMode`. This is the cleanest part.
- **Usage is a product sidecar — `call_with` + `ResponseMeta`, not a bespoke companion.** The prior draft invented `Metered<T> { value, usage, model, tier }` and a parallel `call_metered<T> -> Metered<T>` capability to carry it. The value+sidecar model retires both: usage is "value AND metadata," so it rides `HttpProvider.call_with<T,U>(prompt, project) -> (T, U)` (the request/response capability's value+sidecar method, sibling to `call`), projecting `m.usage()` off the normalized `ResponseMeta`. The app matches its client's provider for `HttpProvider` and writes `h.call_with(text, m => m.usage())`, destructuring `(Ticket, Usage)`. Crucially, because `call_with` lives on the SAME capability as `call`, **Fallback/Retry/Cache forward it** — the winning member's usage is no longer silently dropped (the exact bug the inherited-`.call`-over-`Metered` companion had). This is the direct P1 resolution for the metering pile.
- **Per-provider usage normalization is exactly the four-encodings pattern — now inside `ResponseMeta`.** The background's three usage vocabularies are the cost analog of the four structured-output encodings. The normalizer is the `usage()` body inside each provider's `implements ResponseMeta` (`OpenAIResponse.usage()` / `AnthropicResponse.usage()`), normalizing the SAME wire response `parse<T>` consumed, LAZILY — a caller who projects only `m.usage()` parses nothing else. OpenAI's `prompt_tokens`/`completion_tokens` vs Anthropic's `input_tokens`/`output_tokens` + `cache_creation`/`cache_read` map cleanly across two `ResponseMeta` impls, proving portability. The two pricing-specific dimensions (which model actually served, which tier) ride a small **external-impl interface `MeteredMeta`** reached by `match (m) { let mm: MeteredMeta => ... }` — the proposal §7 "novel dimension by runtime match" pattern, the same fork as `Grounded`.
- **Budget is a Provider, so it composes via the combinator pattern (§6) — and it sources usage by *projecting* `call_with`.** `Budget` wraps an inner `Provider` and forwards `.call`/`call_with` by runtime delegation — identical in shape to `Fallback`/`Retry`/`Cache`. It charges by projecting each sub-call's `(usage, model, tier)` off the inner provider's `call_with` (read via `MeteredMeta` + `ResponseMeta.usage()`), so `Budget { inner: Fast().fallback_to(Claude()) }` works and the inner Fallback's model swaps still flow through one accumulator (the model is read off the projected `ResponseMeta`, **not** off a fixed config and **not** off a bespoke `Metered<T>`). Budget is NOT itself converted to a sidecar — a running total across the tree is mutable state, not one response's `(T, U)` — so it stays a hand-threaded combinator (see (c)).
- **Batch reuses the background-jobs handle pattern (scenario 27) verbatim.** `BatchHandle<T>` (opaque id + `owner` + count), `BatchState` mirroring server-authoritative status, `run_batch` as a default over `submit/poll/download` — these are the `Job<T>` / `await` shapes already validated for async lifecycles. The `custom_id` rejoin is the same "correlation id the loop never interprets" discipline as `ToolCall.id` (§7).
- **`throws`/`catch` + interface-membership `match`** carry the "is this provider Batch?" negotiation, the basic-call/`call_with` `HttpProvider` match, and the budget-exceeded abort. (There is no separate "is this provider Metering?" negotiation — usage is not its own capability; any `HttpProvider` answers `m.usage()` via `call_with`, matched by the same `HttpProvider` arm the basic call uses, so usage is never separately `Unsupported`.) Under the per-capability error model the budget-exceeded abort is a *typed channel*: `BudgetExceeded` is a concrete class (carrying `tenant`/`spent_usd`/`limit_usd`) the app catches by its concrete type, exactly like a `Refused` — money problems are not strings. `WrongBatchOwner` is the same idea for batch: a Fallback member's id handed to the wrong provider is a concrete `BatchError`, not a generic failure.

## (b) Net-new surface it must add (each tied to a primitive)

1. **Tuples `(T, U)` + destructuring — REQUIRED.** Tied to `call_with<T,U>(...) -> (T, U)`. The whole value+sidecar carrier is a tuple: `Cheap().call_with(text, m => m.usage())` returns `(Ticket, Usage)`; `Budget.charge_one` returns `(T, Charge)`; `Budget.call_with` projects `(Charge, U)` in one pass to bill AND return the caller's sidecar without a second request. This is the net-new language surface this scenario most depends on — flagged in `value-sidecar-model.md §6` and shared with the streaming folds (scenario 04), so it is a *shared* dependency, not bespoke to metering. (A named `Output<T,U>` struct is the fallback if tuples are rejected, at an ergonomic cost.)
2. **`call_with` + `ResponseMeta` (the `HttpProvider` sidecar seam) — replaces the bespoke companion.** Tied to the `HttpProvider` capability (the marker `Provider` carries no interaction; `call`/`call_with` live on `HttpProvider` — `../provider-as-marker.md`). `call_with<T,U>(prompt, project) -> (T,U)` and the `ResponseMeta` interface (with `usage()`) are the canonical mechanism for *every* request/response product sidecar; this scenario just supplies the per-provider `usage()` normalizers and one external `MeteredMeta` dimension. NOT net-new to *this* scenario — it is the shared P1 resolution — but it is what made `Metered<T>`/`call_metered`/`RawBody`/`ChatMetering` (four bespoke types/seams the prior draft added) **disappear**. Closures-as-method-params (`project: (ResponseMeta) -> U`) and `Supported<T>` ride along from the same model.
3. **`MeteredMeta` external-impl interface** (`served_model` + `tier`). Tied to the proposal §7 external-impl pattern. The two pricing dimensions beyond canonical usage are added as a small interface each `*Response` implements and a Budget reaches by `match (m) { let mm: MeteredMeta => ... }` — exactly like `Grounded`. This is the only genuinely new *response* surface metering adds, and it is one interface, not a parallel companion method.
4. **`Usage` / `PriceTable` / `PriceRow` / `Cost` / `PricingMode`.** Tied to nothing in the proposal — pure new vocabulary (the cost arithmetic, unchanged by the rewrite). `Usage.add` is the load-bearing op for fan-out summing; `PricingMode` makes batch/flex/priority a *multiplier* rather than a parallel table.
5. **`BudgetCell { _cell: $rust_type }` — mutable host state.** Tied to nothing in the proposal, and the central conflict (see (c)). The running total must be shared across a fan-out tree; the `client -> function -> Provider` sugar cannot own mutable state, so the accumulator is a host cell threaded by hand.
6. **The `Batch` capability + `BatchRequest`/`BatchResult<T>`/`BatchHandle<T>`/ `BatchState`/`BatchCounts`.** Tied to the capability mechanism. Batch is many-prompts, server-side, separate-rate-pool, unordered-with-rejoin — none of which the single-prompt `call<T>` shape can express, so it earns its own interface with its own lifecycle.
7. **Host transport seams** (`openai_upload_jsonl`, `openai_download_output`, `anthropic_create_batch`, `anthropic_stream_results`, `to_float`, `fmt_usd`). Tied to `baml.http`/host boundaries. JSONL file upload and the batch result fetch are genuinely host-level. Everything *above* them is real stdlib, NOT net-new: usage normalization decodes the wire body with `baml.json.from_json<OAIWire>` / `<AntWire>` into a typed class and reads fields; batch JSONL/inline bodies are built from native `map<string, json>` / `json[]` literals serialized with `baml.json.stringify`; the per-line results are decoded with `baml.json.from_json<OAIBatchLine>` / `<AntBatchLine>`; `requests.length()`, `rows.keys()`, `lines.join("\n")`, `n.to_string()`, `"$" + s` concat, `baml.sys.sleep`, `baml.sys.now_ms`, and `baml.log.info` are all the real spellings (no `Response.json_path`, no `baml.json.{obj,arr,str_at}`, no `baml.sys.{log,sleep_ms}` — those were invented). The cost arithmetic is pure BAML.
8. **Two net-new capability-error interfaces: `baml.errors.MeteringError` and `baml.errors.BatchError`.** Tied to the per-capability error model (`error-model.md`). Note the rewrite *narrowed* `MeteringError`: it is no longer the "metered call" channel (usage now rides `call_with` and fails on the canonical `CallError` channel like any `.call`) — it is the **money / budget** channel only, covering `PriceTable.cost` on a stale table and the Budget combinator's ceiling-blown abort. `BatchError` is unchanged (the submit/poll/download lifecycle). Each is declared as the channel `baml.ExtendUnknownError<baml.errors.<Cap>Error>`, shaped like `CallError` but with capability-specific classifiers: `MeteringError.is_budget_exceeded()` / `is_unknown_price()`, `BatchError.is_wrong_owner()` / `is_partial_failure()`. The concrete classes are `UnknownPriceError`, `BudgetExceeded` (implements both `MeteringError` *and* `CallError`, because it surfaces on `Budget.call`/`Budget.call_with` too), and `WrongBatchOwner`. Because `implements` is a Rust-like trait relation that admits external impls, the new-channel author makes upstream errors legal on these channels by writing one row each — `implements baml.errors.MeteringError for baml.errors.Unsupported`, `implements baml.errors.BatchError for baml.errors.Unsupported`, and the same for any `CallError`-bearing transport error it wants to flow through typed — declared alongside the channel in `implement.baml`. This is the error-model surface this scenario forces the proposal to add: two interfaces plus their coverage rows, not a structural reshaping.

## (c) Where it is awkward, leaky, or unresolved

- **Metering does not break any contract — P1 is resolved with a mechanism for the usage sidecar, and the marker resolves OQ1 underneath it.** The prior draft's sharpest complaint (OQ1: `Metering requires Provider` gives a metered provider a `.call` that *silently discards* the usage it measured) **dissolves twice over**: (1) usage is a product sidecar, so the `HttpProvider` capability ships `call_with<T,U>(prompt, project) -> (T,U)` alongside `call` to carry it; and (2) under the marker revision (`../provider-as-marker.md`) there is no degenerate `call` forced onto anything — `call`/`call_with` belong to `HttpProvider`, matched by the companion, and a realtime/harness client simply has no `call` to fake. `.call` is still the lossy 90% path by choice for a request/response client, but the usage is one tuple-projection away on the SAME capability, and — because `call_with` lives on that capability beside `call` — Fallback/Retry/Cache **forward** it instead of degrading to zero usage. No bespoke `Metered<T>`, no `call_metered`, no `RawBody`/`ChatMetering` re-fetch seam. This is the P1 "value+sidecar" pile settled (`value-sidecar-model.md`), and OQ1 is now closed as "no" (the old "degenerate/dishonest `call`" complaint is moot).

- **Honest residual #1 — the Fallback aggregate is the winner's view only.** `project` runs over **one** `ResponseMeta`, the member that won. The tokens burned on members that failed first (you paid for them) have nowhere to go; the product shape carries the winner's usage, not the chain's. A Budget over a Fallback therefore under-counts a failed-then-retried sub-call. This is the same aggregate-provenance gap the error side has, not new — `value-sidecar-model.md §8.2`.

- **Honest residual #2 — per-field absence is a runtime promise (P2, localized to metadata).** `MeteredMeta` (model/tier) is reached by a runtime `match`; a provider whose response is not `MeteredMeta` is discovered at run time (`priced=false`, refused), never by the static type of the client. `Supported<T>` makes "this provider can't itemize reasoning" typed, but *which* dimensions a given client carries is still answered at runtime. Same P2 the rest of the model has — `value-sidecar-model.md §8.3`.

- **Honest residual #3 — the escape hatch rides OQ5 wrapper-transparency.** A projection that reaches for a provider-only raw field, `m => match (m) { let o: OpenAIResponse => o.wire().usage, _ => default }` (decoding the body with `baml.json.from_json<OAIWire>` and reading a field — the real read move, no invented `Response.json_path`), silently misses when `m` is a framework wrapper (a `FrameworkMeta`/`CacheMeta`) around the `OpenAIResponse` rather than the response itself — the same occlusion as `UnknownError` boxing a concrete error and `Fallback` hiding its member. The `MeteredMeta` match in `Budget.charge_of` rides the *same* OQ5 keystone (value-level `match` through wrappers). Metadata does not escape OQ5 — `value-sidecar-model.md §8.1`.

- **The Budget needs mutable cross-call state — a SUM/stateful round-trip, NOT a `call_with` sidecar.** This is exactly the case the value+sidecar partition leaves off `call_with`: `(T, U)` carries *one* response's metadata, but a budget is a *running total over many calls* against a mutable cell, plus a ceiling-blown abort — there is no single response whose sidecar that is. So Budget stays a hand-threaded `Provider` combinator: it *consumes* `call_with` (projecting each sub-call's usage/model/tier) but is not *expressed as* one. And the `client` sugar forbids the state it needs — a `client` is `function(args) -> Provider { body }`, and a function cannot own a mutable accumulator that persists across the fan-out tree. So `Budgeted` is a plain `function` taking a `BudgetCell` argument, NOT a `client`, and the cell is constructed imperatively in `TriageRun`. The proposal's headline ergonomic ("the app author writes one line") does not hold for budgeting: the app must construct a cell, thread it, and read it back. This is the same gap `RoundRobin` hit in scenario 29 — combinators that accumulate state are second-class citizens of the sugar.

- **Reasoning tokens leak through normalization — and the leak is invisible.** The background flags hidden-but-billed reasoning as a hard problem. Our `Usage` has a `reasoning_tokens` sub-field, and `OpenAIResponse.usage()` fills it from `completion_tokens_details.reasoning_tokens`. But **Anthropic does not itemize reasoning** (it folds it into `output_tokens`), so `AnthropicResponse.usage()` sets `reasoning_tokens: 0` even when extended thinking ran. Cost is still correct (output rate already bills it), but any app that *reports* "you spent N reasoning tokens" silently under-reports on Anthropic. The normalized field is a lie of omission on half the providers — and nothing in the type system warns you. This is a fundamental floor: you cannot normalize a number a provider refuses to send.

- **Batch capability is a runtime promise — no compile-time "this client can batch" — Open Question 5.** (This used to read "meter / batch"; metering is no longer a capability — any `HttpProvider` answers `m.usage()` via `call_with`, matched by the same `HttpProvider` arm the basic call uses, so there is no separate metering negotiation and nothing to throw `Unsupported` on for usage. Only batch — and, under the marker, the basic `HttpProvider` match itself — still negotiate.) Because `client` returns the existential `Provider`, `ScoreBacklog(...)` can only `match (p) { let b: Batch => ... }` at runtime and *throw* if the provider is not `Batch`. An app that wires a non-batch client to an offline cron job gets a runtime `baml.errors.Unsupported` (whose canonical definition implements only the four *core* capability-error interfaces; making it legal on the `BatchError` channel is one external `implements baml.errors.BatchError for baml.errors.Unsupported` row — a local-trait/foreign-type impl this scenario's channel author writes at the top of `implement.baml`, exactly the coverage convention the error model prescribes, not a reach-back that re-opens any gap), not a compile error. The escape hatch (drop the sugar, write `function ScoreBacklog(...) -> Provider`... still existential; you'd need a concrete `-> Anthropic` return to make `Batch` static) defeats the portability the whole design is selling. OQ5's "runtime membership testing" is load-bearing here and it is strictly weaker than what a cost-sensitive batch pipeline wants. (Metering's own runtime-promise residual — *which* response carries `MeteredMeta` — is the P2-analog noted under "honest residual #2," but it never *blocks a call*: usage always projects.)

- **Server-authoritative batch state cannot be modeled, only mirrored.** `Batch` exposes `poll_batch -> BatchState`, but the proposal has no notion of state the *server* owns and the client merely reads. We mirror the lifecycle enum verbatim (like scenario 27), which works, but there is no language-level guarantee that our `BatchStatus` stays in sync with the provider's, and the 24h-window/`Expired`/partial-results semantics live entirely in host functions the type system can't see. The proposal is silent on durable, externally-owned state; we bolt it on.

- **Cross-capability channel mismatch is a coverage convention, not a structural wall — and where a row is missing the data still survives.** The usage carrier no longer crosses a channel (it rides `call_with` on the `CallError` channel and stays there), but the money and batch paths still cross: `Budget.charge_one` calls the inner provider's `call_with` (which declares `CallError`) but itself declares `MeteringError`; `Budget.call`/`Budget.call_with` forward `MeteringError` as `CallError`; `download_batch` forwards `CallError`/`MeteringError`-bearing errors on `BatchError`. Whether an error boxes when it crosses is entirely a question of coverage: `baml.UnknownError.with_message<MeteringError>(e, …)` matches the **runtime value**, so it passes through *untouched* any error that implements `MeteringError`, and boxes only an error that does **not**. Because `implements` is a Rust-like trait relation admitting external impls, the channel author closes that crossing by declaring, alongside `MeteringError` in `implement.baml`, `implements baml.errors.MeteringError for <the upstream transport error>` (local trait, foreign type) — or, more simply, by having transport errors implement all four common interfaces the way the canonical `Refused`/rate-limit errors do. With that row a classified network failure rides the `MeteringError` channel as its typed self, caught concretely, **no box**, `is_network_error()` reachable by a plain `catch` arm. The residual is only the *unenforced* part of the convention: nothing **forces** the row, so a crossing the author forgot to cover still boxes. When it does, the box is not a grave: `UnknownError.data: unknown` holds the original untouched, so re-asserting `from<CallError>(e)` at any later layer where `CallError` is back in scope pulls the *same* concrete error back out — `is_network_error()` intact. Because `with_message` annotates an existing `UnknownError` *in place* (its third arm) rather than re-wrapping, `.data` always holds the original however many boundaries it crossed, so one re-assertion recovers it. The same is true at `Budget.call` (forwards `MeteringError` as `CallError`; a `MeteringError` that is *not* also a `CallError`, e.g. `UnknownPriceError`, stays typed iff `implements baml.errors.CallError for UnknownPriceError` is declared, else boxes and `from<MeteringError>(e)` recovers it) and at `download_batch` (one `implements baml.errors.BatchError for …` row per upstream type keeps each typed). So when a row *is* missing, what's lost is the **static** story, not the data: the outer channel reads `MeteringError | UnknownError`, which does not advertise that a `CallError` is recoverable inside the box, and recovery is by *speculative* `from<CallError>` probing rather than type-directed — the analog of P2 applied to a crossing the author chose not to cover. Recovery in that case is **always explicit, never transparent** (settled in `error-model.md`): a `catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it; to reach the inner `CallError` the author must `baml.UnknownError.from<baml.errors.CallError>(e)` *inside* the `UnknownError` arm. The clean answer is the external impl, which keeps the crossing typed and the static signal intact for every covered error, not just hand-declaring `BudgetExceeded implements CallError` one error at a time. A genuinely foreign value (a host panic, unmapped batch JSON) has no inner typed error to admit, so for *those* the `UnknownError` escape hatch is doing exactly its job.

- **The new capability classifiers don't generalize, and that is a smell.** `CallError`'s three classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) are genuinely cross-provider. But `MeteringError.is_budget_exceeded()` and `is_unknown_price()`, and `BatchError.is_wrong_owner()` / `is_partial_failure()`, are capability-*idiosyncratic* — they describe *our* combinator's and *our* lifecycle's failure modes, not a provider-neutral taxonomy. A second metering implementation with a different cost model might never set `is_unknown_price`. So the "triage without knowing the concrete class" promise is weaker for these net-new interfaces than for `CallError`: the useful information is in the concrete `BudgetExceeded`/`WrongBatchOwner`, and the interface classifiers risk being a checklist of one design's special cases rather than a stable contract. This is the honest cost of letting every new capability mint its own error interface.

- **Pre-flight counting drift is unaddressed and arguably unaddressable here.** The background notes pre-flight token estimates drift (tokenizer per model, images/tools). Nothing in this model lets you get an *authoritative* count before sending — `ResponseMeta.usage()` only runs on a *response*. A `count_tokens` capability would be yet another `requires Provider` interface, and it would still be per-provider and still an estimate for some. We did not add it; it would be net-new surface #8 with the same runtime-promise weakness as the rest.

## (d) Verdict

**Workable-with-additions — and P1 is resolved-with-a-mechanism for the metering half.** The combinator and capability machinery genuinely absorb the *shape* of this scenario: usage normalization sits inside providers' `ResponseMeta` like the structured-output encodings, `Budget` composes as a Provider (a marker), forwarding request/response via `implements HttpProvider`, and batch reuses the background-jobs handle pattern cleanly. The headline change from the prior draft: usage is a **product sidecar**, so it rides the `HttpProvider` `call_with` + `ResponseMeta` seam — there is no bespoke `Metered<T>`/`call_metered`/`RawBody`/`ChatMetering`, the OQ1 "lossy/degenerate `.call`" complaint dissolves (usage is one tuple-projection away on the request/response capability, *forwarded* by Fallback/Retry/Cache instead of dropped; and under the marker revision there is no `call` forced onto non-request/response providers to be degenerate in the first place — OQ1 closed as "no"), and the net-new surface metering adds shrinks to **tuples `(T,U)`** (required, shared with streaming), the shared `call_with`/`ResponseMeta` mechanism, and one external `MeteredMeta` dimension. What stays genuinely separate is what was never P1's problem: **budgeting** is a SUM/stateful round-trip (a running total over many calls against mutable host state — not one response's `(T,U)`), so it remains a hand-threaded combinator the `client` sugar cannot hold; and **batch** is server-authoritative state where the handle *replaces* the answer, so it keeps its `submit -> handle` lifecycle. The reasoning-token leak (a number Anthropic refuses to send) and the runtime-only *batch* capability promise (OQ5) are real floors the proposal cannot raise. So it works by adding one stateful combinator and one server-lifecycle capability — and by accepting that the usage sidecar is settled (resolved-with-mechanism), while the Fallback aggregate is the winner's view only, per-field absence stays a runtime promise (P2), and the provider-raw escape hatch rides OQ5 wrapper-transparency (the three honest residuals from `value-sidecar-model.md §8`). The per-capability error model layers cleanly on top (two new `*Error` interfaces, concrete `BudgetExceeded`/`UnknownPriceError`/`WrongBatchOwner` the app catches by type), and it adds **no** structural pressure: because `implements` is a Rust-like trait relation admitting external impls, keeping an inner-channel error (`CallError`) typed across a capability boundary is a *coverage convention* — the channel author writes one `implements baml.errors.MeteringError for <upstream error>` (or `BatchError for …`) row, or has transport errors implement the four common interfaces, and the crossing stays typed with no box. The only residuals are the unenforced part of that convention (a crossing the author forgot to cover still boxes — but the data and type survive in `.data`, recoverable via an explicit `from<CallError>` probe, which is always explicit since a plain `catch` does *not* auto-unwrap the box and only ever sees the outer interface or `UnknownError`) and the genuinely-foreign value (a host panic, unmapped batch JSON) for which the `UnknownError` escape hatch is correct. So the static signal is preserved wherever the coverage row exists; where it is missing, precision degrades to a recoverable runtime promise (the P2-analog), not an irreversible erasure.
