# Evaluation — Reasoning models (effort, verbosity, thinking, continuity)

Adversarial read of whether the proposed Provider/capability model expresses reasoning cleanly. Stress, don't sell.

## (a) What the proposal reuses unchanged

- **Value+sidecar model carries the reasoning *text* (the P1 fix).** Reasoning text is a *product* sidecar — it accompanies the answer — so it rides the `HttpProvider.call_with` + a `ResponseMeta` projection (`ReasoningMeta.reasoning_blocks()`), exactly the mechanism `../value-sidecar-model.md` prescribes for usage/logprobs/citations. There is **no bespoke `Thinks.think` companion and no `WithReasoning<T>` carrier**: the parallel-companion-per-sidecar pattern this scenario originally invented is precisely what P1 retires. Because `call_with` is owned by `HttpProvider` and forwarded by combinators, the projection **survives Fallback/Retry** — the old `.think` companion silently dropped under inherited `.call`.
- **`ResponseMeta` as interface + external-impl dimensions.** `ReasoningMeta` / `ContinuationMeta` are external-impl extensions of `ResponseMeta` (the `Grounded` pattern in value-sidecar-model.md §7): concrete `OpenAIReasoningResponse` / `AnthropicReasoningResponse` implement them and normalize the wire response *lazily*; a projector reaches them by runtime `match` and falls back to `Unsupported` when absent. Same interface/concrete/external-impl/`Supported` shape as the error model.
- **`HttpProvider` + `parse<T>` as the seam.** Surfacing the *answer* needs no new response interface; `parse<T>` SAP-parses it (`call` discards reasoning for free). Both `parse<T>` and `meta_of` are `HttpProvider` methods (the `Provider` base is a bare marker now); `meta_of` is the sidecar seam from `_conventions.md`'s `HttpProvider`, supplied by each reasoning provider.
- **Options-dissolve-into-fields (§4).** `effort`, `verbosity`, `summary`, `thinking_budget`, `max_tokens` are all just provider class fields. No `provider_options` union, no `@providers:` map. The two incompatible control models are simply two different field sets on two different classes — the model does not force a fake unified knob.
- **Capability = interface that `requires Provider` + runtime `match` (§5).** `Continuity` remains an ordinary capability: `.resume` honestly errors on a non-`Continuity` provider (a stateful interaction shape — there is no honest way to fake reasoning continuity). The reasoning-*text* half no longer needs a capability at all — "can this provider think?" is answered by whether its response implements `ReasoningMeta`, discovered by the same `match` the projector does. The error model mirrors the split: `call_with` rides the **`baml.errors.CallError`** channel; because `resume` is a distinct stateful protocol, it gets its **own** channel (see (b.6)).
- **`client` is sugar (§3).** Every client here (`DeepThinker`, `BudgetThinker`, `ResilientThinker`) is a zero-arg function returning a Provider; the combinator chain `DeepThinker().fallback_to(BudgetThinker())` is a plain function call.
- **Shared read-interface pattern.** `ReasoningOptions` mirrors `ChatModelOptions` from §4 — tooling can ask "effort? budget? verbosity?" without knowing the concrete class, with `null` for knobs a provider lacks.

## (b) Net-new surface it must add (tied to a primitive)

1. **Tuples `(T, U)` + destructuring — REQUIRED.** *Primitive: first-class tuple types + `let (v, u) = …` (does NOT exist yet).* The whole value+sidecar path returns a tuple: `call_with<Diagnosis, Supported<ReasoningBlock[]>>(…) -> (Diagnosis, Supported<ReasoningBlock[]>)`, and `resume_with` returns `(T, U)`. Every reasoning call site here destructures one. This is a shared dependency (the streaming folds in scenario 04 also need it), not bespoke to reasoning — but it is hard net-new surface the proposal must add. (The fallback is a named `Output<T, U> { value, extra }` struct at an ergonomic cost.)
2. **`ReasoningBlock` / `ReasoningRaw` — a distinct content kind.** *Primitive: none exists.* The proposal has no notion of "content that is not the answer." Reasoning must be modeled as a value separate from `T` so it can be displayed, billed, and stripped. `ReasoningRaw` is a union of the three real wire shapes (Anthropic signed thinking, OpenAI encrypted item, Gemini thought). This is genuinely new and is the heart of the scenario.
3. **`ReasoningMeta` / `ContinuationMeta` — external-impl `ResponseMeta` dimensions.** *Primitive: external-impl interface reached by `match` (exists; the `Grounded` pattern).* New named dimensions carrying the reasoning *text* (`reasoning_blocks() -> Supported<ReasoningBlock[]>`) and the continuation *handle* (`continuation() -> Supported<ContinuationState>`) off the normalized response. These REPLACE the old `WithReasoning<T>` carrier and `Thinks` companion: there is no parallel companion method and no wrapper return type — the sidecars ride `HttpProvider.call_with`.
4. **`Continuity` capability + `ContinuationState`.** *Primitive: opaque associated/owned type, like `Tools.Transcript` (exists).* New. `resume<T> -> T` (plus the `resume_with` value+sidecar form) and an opaque, provider-owned state union. This is the reasoning analog of the `Tools.Transcript` seam: the app threads it back, never inspects it. Note the partition — the capability is now ONLY the stateful round-trip; the displayable reasoning that used to share `WithReasoning<T>` with it has moved to the sidecar path.
5. **`Effort` / `Verbosity` enums + `ReasoningOptions` read-interface.** *Primitive: enum + read-interface (exist).* New named values; cheap.
6. **`baml.errors.ContinuityError` — a NET-NEW capability-error interface.** *Primitive: the per-capability error interface (`CallError`/`StreamError`/… exist).* The four core channels (`CallError`, `StreamError`, `ToolError`, `RealtimeError`) don't fit `resume`: continuity is a cross-turn, server/client-state-bearing protocol, and its signature failure (resuming Anthropic state on an OpenAI provider) has *no analog* on the call path. So `Continuity.resume` declares `baml.ExtendUnknownError<baml.errors.ContinuityError>`, and `ContinuityError` adds a classifier the others lack — `is_cross_provider()`. The concrete `CrossProviderContinuity` (carrying `expected_provider`/`state_provider`) implements it. This is the error-model analog of the capability split itself: a genuinely new interaction shape earns a genuinely new error channel. The old single `type Error = baml.errors.LlmClient` could not have expressed this distinction at all.

## (c) Where it is awkward, leaky, or unresolved

- **Server-authoritative state is the real fault line (OQ #1 now resolved; engages OQ #3).** OpenAI's `previous_response_id` continuity is *server-held* reasoning. The `HttpProvider` call path is near-stateless — `call<T>(prompt)` builds, sends, parses one request. Server-side state means the *previous* `OpenAIReasoning.call` mutated state on the server that the *next* call depends on by id. We smuggle this into `ContinuationState.openai_previous_response_id`, but that is a confession, not a solution: the model has no first-class notion of a session/connection that outlives a single `call`. Under the marker revision OQ #1 ("does every capability refine `call`, or should some stand alone?") is **closed as no** — `Provider` is a bare marker and `call`/`call_with` are themselves just the `HttpProvider` capability, so `Continuity` does not have to be a refinement of `call`; it stands alone as its own stateful capability with its own interaction method (`resume`/`resume_with`) and its own error channel. That makes the *modeling* of `Continuity` natural rather than forced. The remaining bend is real but separate: `ContinuationState` is the same opaque escape valve `Tools.Transcript` is, and it leaks the server/client distinction up to where the app must hold a handle.

- **Two continuity models inside one capability is a bulge, not a clean abstraction.** `ContinuationState` carries *both* `openai_previous_response_id` (server) *and* `resend_blocks` (client), and `resume` branches on which arm is populated. That is honest but ugly: one capability papering over two mechanisms, with an `origin_provider` string guard doing runtime work the type system can't. There is no compile-time guarantee you won't try to resume Anthropic state on OpenAI — it throws at runtime (engages OQ #5: membership/identity checks are all runtime because `client` returns the existential). The new error model *upgrades* this guard from a stringly-typed `LlmClient { message: "cannot resume …" }` to a concrete, catchable `CrossProviderContinuity { expected_provider, state_provider }` carrying `is_cross_provider() -> true`. The app can now branch on the failure structurally instead of pattern-matching a message — a real improvement. But it remains a *runtime* check: the error type is recovered at the `catch`, not prevented at the signature.

- **Fallback + continuity is genuinely broken, and the model can't catch it.** `ResilientThinker = DeepThinker().fallback_to(BudgetThinker())` forwards `call_with` (so the reasoning-text sidecar survives failover — a clean win) and statically *claims* `Continuity` because the proposal says a combinator claims every capability any member forwards (§6). But a `ContinuationState` *projected* from the OpenAI member cannot be resumed by the Anthropic member — `origin_provider` mismatch throws. Worse: a turn-1 `call_with` that failed over to Anthropic yields Anthropic state, and a turn-2 `resume` that succeeds on OpenAI will reject it. Cross-turn reasoning continuity is fundamentally incompatible with per-turn fallback, and the combinator layer has no way to express "this capability does not survive delegation." The value+sidecar split sharpens the diagnosis — the *handle* now rides the same forwarded projection as usage, so Fallback hands you a winner's-view handle with no hint it came from a different member — but does not fix it. This is a real, unresolved leak — not a wart.

- **The "one knob" dream is explicitly abandoned (and that's correct).** The background asks whether any abstraction can reconcile effort-category vs token-budget into one control. The proposal's answer is "don't" — they stay two fields on two classes. Good for honesty, but it means a portable app function (`function Diagnose`) is *not* actually portable across `DeepThinker` and `BudgetThinker` without the author knowing which knob each honors. The `ReasoningOptions` read-interface lets tooling *observe* the divergence but does nothing to *erase* it. `verbosity` exists on OpenAI and is `null` on Anthropic; an app that sets verbosity silently no-ops on the budget provider.

- **Truncation-as-correctness-bug is invisible here (engages OQ #4).** The background warns that for reasoning models the output cap must also cover hidden reasoning tokens — a budget that worked non-reasoning truncates the answer to nothing. `parse<T>` receives the full `Body` (and `meta_of` exposes `finish_reason()`), so a provider *could* inspect the finish/stop reason and throw — but nothing in the `HttpProvider` contract *requires* it, and the differently-named finish reasons (`length`/`max_tokens`/`MAX_TOKENS`) are per-provider. The model permits a correct implementation; it does not enforce one. This is a contract gap, not a model gap.

- **Reasoning absence is a runtime promise, not a static type (P2, localized to metadata).** On `PlainChat`, the SAME `call_with` projection runs, but the response carries no `ReasoningMeta`, so the projector's `_` arm yields `Unsupported { reason: "non-reasoning model" }` — typed and self-explaining (better than the old `.think` returning a silent empty `WithReasoning`). But *which* dimensions a given client supports is still answered at runtime (a `match` miss → `Unsupported`), never by the static type of the client. "Did I actually get a thinking model?" is answerable only by inspecting the projected `Supported<…>`, not the signature. This is exactly the **per-field-absence residual** value-sidecar-model.md §8.3 names — P2 reappearing on the metadata path. The escape hatch (§7, `-> OpenAIReasoning`) restores compile-time certainty that the response *will* implement `ReasoningMeta`, but costs the `client` sugar.

- **The reasoning projection rides OQ5 wrapper-transparency.** `m => match (m) { let rm: ReasoningMeta => … }` must see through the `FrameworkMeta` (and any `CacheMeta`) the framework wraps the provider's response in — the same occlusion value-sidecar-model.md §8.1 names for the `OpenAIResponse` escape hatch and the error model names for `UnknownError` boxing. The delegation wrappers forward `ReasoningMeta` themselves, or the layers must expose `inner` to probe through. Metadata does not escape OQ5; it leans on the same wrapper-transparent `match` everything else does.

- **NEW (error model): a multi-turn function spans two capability channels, and that union is load-bearing, not incidental.** `MultiTurnDiagnose` calls `call_with` (turn 1, `CallError`) *and* `resume` (turn 2, `ContinuityError`), so its honest channel is `baml.ExtendUnknownError<baml.errors.CallError | baml.errors.ContinuityError>` — a *union of two capability errors* plus the wrapper. The model permits this (non-generic `UnknownError` keeps the union flat), but it exposes a wrinkle the single-`Error` world hid: the moment a control-flow path touches two capabilities, the caller's `catch` must triage across two interface hierarchies. Whether a `CallError` raised by the turn-2 `resume`'s *internal* `self.send` stays typed on the way out is a **coverage convention**, not a wall. By default it is **not** a `ContinuityError`, so `resume`'s trailing `with_message<ContinuityError>` boxes it into `baml.UnknownError` — annotating the box *in place* and leaving the original error in `.data` untouched. But the box is avoidable: because `implements` is a Rust-like trait relation that admits *external* impls, the `Continuity` package (which owns `ContinuityError`) can declare `implements baml.errors.ContinuityError for baml.errors.CallError` (local trait, foreign type) — or, more narrowly, for the concrete down-stack errors it wants to forward — and then a `CallError` raised inside `resume` rides the `ContinuityError` channel *as its typed self*, caught concretely with no box. The author just has to write the row. Whichever way it goes, the classification is never destroyed: a rate-limit hit *during a resume* still carries its concrete `OpenAiRateLimitError` (with the row, directly as a typed `ContinuityError`; without it, inside `.data`, recoverable via `from<baml.errors.CallError>(e)`), `is_rate_limit()` intact. What the *missing-row* case costs is purely *static*: the channel the app holds is `ContinuityError | baml.UnknownError`, which does **not** advertise that a `CallError` is recoverable inside the box — so absent the `implements` row, recovery is by `from<CallError>` probing rather than type-directed, and the compiler can't tell the author "a rate-limit can reach you here." That is the (avoidable) cost of giving continuity its own channel *without* admitting the inner channel onto it: an un-covered cross-channel call demotes the inner channel's typed errors from a *statically promised* arm to a *runtime-recoverable* one — exactly P2 (capability = runtime promise) applied to the error channel, and closed by one external `implements`. And where a crossing *does* box, the recovery is firm, not conditional: `catch` does **not** auto-unwrap (settled by `error-model.md`). A `catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it. A plain `catch` across an un-covered boundary therefore only ever sees `ContinuityError` or `baml.UnknownError`; pulling the down-stack `CallError` back out is **always explicit** — `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm — never transparent, and only code that already knows to probe will find it. The single-channel `LlmClient` model would have preserved the message but never had the classification to recover; this model keeps the classification and (with the `implements` row) the *static* arm too, dropping the static guarantee only at a seam the channel author has not yet covered.

- **NEW (error model): the `Fallback` combinator must now forward the `ContinuityError` channel too — and that makes the (d) leak worse, not better.** §6/`_conventions.md` says a combinator declares the *same* channel as the capability it forwards; so `Fallback.resume` declares `baml.ExtendUnknownError<baml.errors.ContinuityError>`. Fine in isolation. But the cross-provider failure this scenario's `Fallback` *guarantees* (OpenAI turn-1 state, Anthropic turn-2 member) now surfaces as a perfectly well-typed `CrossProviderContinuity` — the type system will happily let you build `ResilientThinker`, call `.resume` through it, and hand you a clean typed error every time continuity crosses the failover boundary. The error model makes the broken path *type-check and classify cleanly*, which is arguably worse than a loud crash: it normalizes a combination that is semantically never correct. `is_cross_provider()` lets a diligent app detect it, but nothing in the channel discourages building the doomed combinator in the first place. A typed error channel cannot encode "this capability does not survive delegation."

## (d) Verdict

**Workable-with-additions — and P1 is resolved-with-mechanism for the reasoning-text sidecar.**

The displayable/billable half of reasoning is now clean *and on the canonical mechanism*: a distinct content kind (`ReasoningBlock`) projected through the **`HttpProvider.call_with` + a `ResponseMeta` dimension** (`ReasoningMeta.reasoning_blocks()`), with effort/verbosity/budget as plain fields. This is the P1 resolution applied: the bespoke `Thinks.think -> WithReasoning<T>` companion and the `WithReasoning<T>` carrier — the exact parallel-companion-per-sidecar pattern P1 indicts — are **deleted**, and the reasoning text rides the same `call_with` everything else does. The concrete win over the old design is real: because `call_with` is owned by `HttpProvider` and forwarded by combinators, the reasoning projection **survives Fallback/Retry** (the companion silently dropped under inherited `.call`), and degradation on a non-reasoning model is a *typed* `Unsupported` from a uniform projection rather than a silent empty wrapper. The cost is honest net-new surface — chiefly **tuples `(T, U)` + destructuring**, REQUIRED and shared with the streaming folds (b.1).

The residuals are the model's *existing* tensions reappearing on this path, not new ones: (i) the **Fallback aggregate carries only the winner's view** — the projected continuation handle and reasoning come from whichever member answered, with no slot for the chain; (ii) **per-field absence is a runtime promise** — whether a client's response implements `ReasoningMeta` is a `match` miss → `Unsupported`, never the static type of the client (P2); (iii) the escape hatch and the `ReasoningMeta` projection both ride **OQ5 wrapper-transparency** (seeing through `FrameworkMeta`); (iv) the **stateful** cases stay deliberately off `call_with` — refusal on `throws`, and the continuity *round-trip* on the `Continuity` capability, because `(T, U)` cannot carry state across turns (P4).

The continuity half is where it still bends — and the partition makes the bend *cleaner to see*, not gone: `ContinuationState` works as an opaque round-trip handle (the `Tools.Transcript` pattern), but it encodes *two* mechanisms (server-id vs client-resend), guards cross-provider misuse only at runtime (the concrete, classifiable `CrossProviderContinuity` on the net-new `baml.errors.ContinuityError` channel — a strict improvement over the old `LlmClient` message string, but still a runtime check), and remains **incompatible with the Fallback combinator**, which the model lets you build but cannot make correct. Extracting the handle is a sidecar (`ContinuationMeta`); *threading it back* is the capability — that split is exactly the value+sidecar partition, and it correctly keeps the hard part (state, P4) off the carrier shape. The per-capability error model sharpens rather than resolves the Fallback leak: `resume` earns its own typed channel, multi-turn functions carry a two-capability error *union*, and `Fallback.resume` forwards `ContinuityError` so cleanly that the doomed cross-provider path now type-checks and classifies without complaint. Server-authoritative reasoning state sits awkwardly against an `HttpProvider` call path whose mental model is a near-stateless `call<T>` (the `Provider` base is now a bare marker, so `Continuity` standing alone is no longer an OQ #1 tension — that question is closed by the marker revision); Open Questions #3 and #5 still land directly on this scenario. Net: the *product* half of reasoning is settled by `call_with`; the *stateful* half is expressible the way `Tools` is — an opaque provider-owned handle the app threads back — which earns "workable-with-additions," not "clean."
