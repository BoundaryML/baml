# Evaluation — Reasoning models (effort, verbosity, thinking, continuity)

Adversarial read of whether the proposed Provider/capability model expresses reasoning cleanly. Stress, don't sell.

## (a) What the proposal reuses unchanged

- **Provider base + `parse<T>` as the seam.** Surfacing reasoning needs *no new response interface*. `parse<WithReasoning<T>>` is the same output-specialized parse the proposal already shows for `GptImage` (`parse` decodes bytes; here it peels reasoning blocks then SAP-parses the answer). `T` flows into `build_request` *and* `parse` exactly as §2 describes.
- **Options-dissolve-into-fields (§4).** `effort`, `verbosity`, `summary`, `thinking_budget`, `max_tokens` are all just provider class fields. No `provider_options` union, no `@providers:` map. The two incompatible control models are simply two different field sets on two different classes — the model does not force a fake unified knob.
- **Capability = interface that `requires Provider` + runtime `match` (§5).** `Thinks` and `Continuity` are ordinary capabilities. `.think` degrades to `.call` (delivery refinement: reasoning is "same call, richer surfacing"), while `.resume` honestly errors on a non-`Continuity` provider (different interaction shape — there is no honest way to fake reasoning continuity). This is precisely the split the proposal draws between `Streaming` and `Realtime`.
- **`client` is sugar (§3).** Every client here (`DeepThinker`, `BudgetThinker`, `ResilientThinker`) is a zero-arg function returning a Provider; the combinator chain `DeepThinker().fallback_to(BudgetThinker())` is a plain function call.
- **Shared read-interface pattern.** `ReasoningOptions` mirrors `ChatModelOptions` from §4 — tooling can ask "effort? budget? verbosity?" without knowing the concrete class, with `null` for knobs a provider lacks.

## (b) Net-new surface it must add (tied to a primitive)

1. **`ReasoningBlock` / `ReasoningRaw` — a distinct content kind.** *Primitive: none exists.* The proposal has no notion of "content that is not the answer." Reasoning must be modeled as a value separate from `T` so it can be displayed, billed, and stripped. `ReasoningRaw` is a union of the three real wire shapes (Anthropic signed thinking, OpenAI encrypted item, Gemini thought). This is genuinely new and is the heart of the scenario.
2. **`WithReasoning<T>` carrier.** *Primitive: generic class (exists).* Built from existing generics, but it is new std-lib surface: the agreed way a plain `-> T` function opts into reasoning + a continuation handle without polluting `T`. Without it, every answer type would need reasoning fields bolted on.
3. **`Thinks` capability.** *Primitive: `interface … requires Provider` (exists).* New interface. Needed because `call<T> -> T` structurally cannot return reasoning out-of-band; `think<T> -> WithReasoning<T>` is the companion.
4. **`Continuity` capability + `ContinuationState`.** *Primitive: opaque associated/owned type, like `Tools.Transcript` (exists).* New. `resume<T>` and an opaque, provider-owned state union. This is the reasoning analog of the `Tools.Transcript` seam: the app threads it back, never inspects it.
5. **`Effort` / `Verbosity` enums + `ReasoningOptions` read-interface.** *Primitive: enum + read-interface (exist).* New named values; cheap.

## (c) Where it is awkward, leaky, or unresolved

- **Server-authoritative state is the real fault line (engages OQ #1 and OQ #3).** OpenAI's `previous_response_id` continuity is *server-held* reasoning. The proposal's whole world is "a Provider is a pure-ish function `call<T>(prompt)`." Server-side state means the *previous* `OpenAIReasoning.call` mutated state on the server that the *next* call depends on by id. We smuggle this into `ContinuationState.openai_previous_response_id`, but that is a confession, not a solution: the model has no first-class notion of a session/connection that outlives a single `call`. OQ #1 ("does every capability refine `call`, or should some stand alone?") bites here — `Continuity` is arguably *not* a refinement of a stateless `call` at all; it is a stateful protocol. The `ContinuationState` type works, but it is the same escape valve `Tools.Transcript` is, and it leaks the server/client distinction up to where the app must hold a handle.

- **Two continuity models inside one capability is a bulge, not a clean abstraction.** `ContinuationState` carries *both* `openai_previous_response_id` (server) *and* `resend_blocks` (client), and `resume` branches on which arm is populated. That is honest but ugly: one capability papering over two mechanisms, with an `origin_provider` string guard doing runtime work the type system can't. There is no compile-time guarantee you won't try to resume Anthropic state on OpenAI — it throws at runtime (engages OQ #5: membership/identity checks are all runtime because `client` returns the existential).

- **Fallback + continuity is genuinely broken, and the model can't catch it.** `ResilientThinker = DeepThinker().fallback_to(BudgetThinker())` statically *claims* `Thinks` because the proposal says a combinator claims every capability any member forwards (§6). But a `ContinuationState` produced by the OpenAI member cannot be resumed by the Anthropic member — `origin_provider` mismatch throws. Worse: a turn-1 call that failed over to Anthropic yields Anthropic state, and a turn-2 call that succeeds on OpenAI will reject it. Cross-turn reasoning continuity is fundamentally incompatible with per-turn fallback, and the combinator layer has no way to express "this capability does not survive delegation." This is a real, unresolved leak — not a wart.

- **The "one knob" dream is explicitly abandoned (and that's correct).** The background asks whether any abstraction can reconcile effort-category vs token-budget into one control. The proposal's answer is "don't" — they stay two fields on two classes. Good for honesty, but it means a portable app function (`function Diagnose`) is *not* actually portable across `DeepThinker` and `BudgetThinker` without the author knowing which knob each honors. The `ReasoningOptions` read-interface lets tooling *observe* the divergence but does nothing to *erase* it. `verbosity` exists on OpenAI and is `null` on Anthropic; an app that sets verbosity silently no-ops on the budget provider.

- **Truncation-as-correctness-bug is invisible here (engages OQ #4).** The background warns that for reasoning models the output cap must also cover hidden reasoning tokens — a budget that worked non-reasoning truncates the answer to nothing. `parse<T>` receives the full `Body`, so a provider *could* inspect the finish/stop reason and throw — but nothing in the `Thinks`/`HttpProvider` contract *requires* it, and the differently-named finish reasons (`length`/`max_tokens`/`MAX_TOKENS`) are per-provider. The model permits a correct implementation; it does not enforce one. This is a contract gap, not a model gap.

- **`.think` degradation is lossy but silent.** On `PlainChat`, `.think` returns `WithReasoning` with `reasoning: []` and `continue_from: null`. That's the honest fallback, but a caller who *expected* reasoning gets an empty list with no error — the runtime-promise nature of capabilities (OQ #5) means "did I actually get a thinking model?" is only answerable by inspecting the result, not the type. The escape hatch (§7, `-> OpenAIReasoning`) restores compile-time certainty but costs the `client` sugar.

## (d) Verdict

**Workable-with-additions.**

The displayable/billable half of reasoning is clean: a distinct content kind (`ReasoningBlock`), an out-of-band companion (`Thinks.think`), and effort/ verbosity/budget as plain fields all fall straight out of the existing parse-seam + capability + options-as-fields machinery, with no strain. The proposal absorbs "reasoning is not text" and "two control models" without inventing a fake unified knob — that is a real win. The continuity half is where it bends: `ContinuationState` works as an opaque round-trip handle (the `Tools.Transcript` pattern reused), but it is forced to encode *two* mechanisms (server-id vs client-resend), it guards cross-provider misuse only at runtime, and — critically — it is **incompatible with the Fallback combinator**, which the model lets you build but cannot make correct. Server-authoritative reasoning state sits awkwardly against a base whose mental model is a near-stateless `call<T>`, and Open Questions #1, #3, and #5 all land directly on this scenario. None of this is unsupported — every case is expressible — but it is expressible the way `Tools` is: by handing the app an opaque provider-owned handle and trusting it to thread it back, with the hard provider-divergence buried inside the bodies. That earns "workable-with-additions," not "clean."
