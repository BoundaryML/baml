# Evaluation — Transport taxonomy: why request/response cannot model realtime

Adversarial read. The background's claim is structural: a `(request) -> response` (or even `(request) -> Stream<chunk>`) signature is *wrong-shaped* for a live session — five distinct reasons. Does the proposed model express the full transport taxonomy (HTTP / SSE / chunked-JSON / WS / WebRTC) *and* honor the cliff, with Realtime as its own capability rather than a refinement of `call`? Where does it leak?

## (a) What the proposal reuses unchanged

- **`Realtime requires Provider` with `run(prompt, io: Channel) -> Transcript`** — used verbatim from `_conventions.md`. This is the entire load-bearing claim of the scenario: realtime is a *separate interface*, not a richer `call`. Under the provider-as-marker spine `Provider` is a bare marker (no interaction method), so `Realtime requires Provider` gives `RealtimeWS`/`RealtimeWebRTC` composability WITHOUT forcing a `call` onto them at all — they implement ONLY `run`. All five structural reasons land on `run`'s duplex body (`implement.baml` §5), and **none** of them is reachable from `HttpProvider.call`'s `(prompt) -> T` signature (which the realtime providers do not even carry). The proposal's decision to make Realtime its own capability is *exactly* the background's conclusion ("an event-stream shape can express single-shot as a degenerate case; the inverse cannot"), and it holds up.
- **`Channel` with `on(handler)` / `send(data)` / `close()`** (proposal §3, conventions). The duplex endpoint is a pass-in parameter of the capability method, handed in at `.live` — never a client field. `run_barista_session` (usage §3) is the canonical shape: `io.on(out => …)` for server→caller, `io.send(InEvent)` for caller→server, concurrently.
- **The companion `match` + the `Realtime` no-fallback arm** (proposal §5). `.live` matches for `Realtime`; on a non-realtime provider the `_` arm throws `Unsupported`. `invalid_live` (usage §4) exercises exactly that: `Extract.live` over `ChatHTTP` throws, because a request/response transport cannot fake a duplex session. This is the proposal's "different interaction shapes → no honest fallback" split, and it is precisely the cliff.
- **`Streaming` degrades to `.call`** for the *delivery refinement* providers (`ChatSSE`, `ResponsesWS`). `ExtractLive.stream` over `Batch()` buffers; over `Reading()` runs incrementally — same body, swapped wire (usage §2).
- **The combinator/wrapper pattern** (proposal §6) for `WarmThenCold`: a plain class wrapping two providers, forwarding `HttpProvider` (call + call_with) and `Streaming` by delegation. Under provider-as-marker its request/response forwarding moved off `implements Provider` onto `implements HttpProvider`, and its `call_with` **forwards the projection to whichever member serves the turn** (warm preferred, cold on fallback) so usage/finish-reason/cost is not dropped — the P1 fix. The combinator factories (`with_retry`/`fallback_to`/`cached`) still ride the `Provider` marker via `requires`, inherited, never redefined.
- **Provider-fields, no options blob** (proposal §4): `RealtimeWS.voice`, `ResponsesWS.model` are bespoke fields; the warm `_socket` is a connection-local field, not a client parameter.
- **`Transcript` as a provider-owned opaque type** (proposal §7) — the realtime record is `$rust_type`, exactly like the `Tools` transcript.
- **The per-capability error channel** (`error-model.md`). There is no `type Error = baml.errors.LlmClient` anymore: every fallible method declares `baml.ExtendUnknownError<CapErr>` = `CapErr | baml.UnknownError`, and the capability *picks the channel*. The call-path methods (`build_request`/`send`/`parse`/`call`/`call_with`, plus `ResponsesWS`'s pool accessors) use `baml.errors.CallError`; `stream` uses `baml.errors.StreamError`; `RealtimeWS.run` / `RealtimeWebRTC.run` / the shared `drive_realtime_events` loop use `baml.errors.RealtimeError`. Under the provider-as-marker spine the channel *aligns with the owning capability*: `call`/`call_with` live on `HttpProvider` (so `ResponsesWS`, a genuine warm-socket request/response provider, carries `CallError`), and `run` lives on `Realtime` (so `RealtimeWS` carries only `RealtimeError` — it has no `call` to give a `CallError`). Deliberate domain failures become concrete classes — `TransportHttpError { status }` (a non-2xx, `is_rate_limit()` true on 429) and `SocketClosed { detail }` (connection-loss = state-loss, Reason #5, made into a *typed* error). Foreign `baml.errors.Io` from `baml.ws`/`baml.webrtc`/`baml.http` normalizes through one trailing `catch (e) { _ => throw baml.UnknownError.with_message<CapErr>(e, "…") }` per method — `with_message` returns a known `CapErr` unchanged, so the trailing catch never swallows a deliberately-thrown `SocketClosed`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.ws.connect(req) -> WsSocket`** plus the `WsSocket` type with `.send(frame)` / `.recv()` / `.close()` (`implement.baml` §0). This is *the* addition. The conventions ship `fetch_sse → SseStream`, which has `.next()` and `.close()` but **no `.send()`** — that absence is the cliff made literal. A duplex socket where `.send` is callable *while* `.recv` is pending is the host primitive every realtime feature rides on. Tied to: `Realtime`. Without it, `Realtime.run` has no transport to drive.
2. **`baml.webrtc.connect(offer_req, ek) -> RtcSession`** plus `RtcSession` (`data: WsSocket` + `media: MediaTrack`) and `MediaTrack` (`implement.baml` §0, §6). The media-vs-data split is structural: the audio bytes never become BAML values, and the host owns echo-cancel/jitter/PLC on the RTP track. Tied to: `Realtime` (same capability, second transport).
3. **The duplex event grammar — `InEvent` / `OutEvent` unions** (`implement.baml` §8). The conventions' `Channel` references `InEvent`/`OutEvent` abstractly; this scenario pins them, because the **four cliff use cases ARE four `InEvent` variants** (`BargeInEvent`, `ToolResultInEvent`, `ControlEvent`, plus `AudioInEvent`) and the **server-initiated events are `OutEvent` variants** (`SpeechStartedOut`, `RateLimitOut`, `ServerErrorOut`). These have no analogue on a `Stream`. Tied to: `Channel`.
4. **`TransportInfo` read-interface** (`Wire` + `StateLocation` enums, `implement.baml` §1). Net-new, but optional — the *orthogonal-axis* point needs a way to expose "wire" and "state location" independently so tooling can show `websocket / server-session` vs `websocket / server-stored-by-id`. Tied to: the `ChatModelOptions`-style optional read-interface pattern (proposal §4).
5. **A host-handle warm-socket pool** (`ResponsesWS._pool: $rust_type` + `warm_socket` / `last_id` / `remember_id`, `implement.baml` §4). The warm socket is mutable, connection-local state reused across `call`s. We follow the std-lib idiom (scenario 17's `MemoryStore._cells`) and hide it behind a host handle rather than mutating a BAML field — keeping the provider value pure config. But the *lifecycle* of that handle is net-new surface the host must own — see (c). Tied to: the `$rust_type` host-boundary pattern (proposal §7 / OQ7).
6. *(Not net-new — uses the real stdlib.)* The per-frame reads inside the event loops are **not** a missing primitive: each raw frame is decoded with the real `baml.json.from_string<T>` into a small partial typed class (`ResponsesWsFrame` / `RealtimeFrame`, fields the loop reads, rest ignored by SAP's structural decode), and fields are read off that class. No `json.get_str`/`get_int` path-accessor is needed.
7. **Concrete transport-error classes — `TransportHttpError { status }` and `SocketClosed { detail }`** (`implement.baml` §1b). Net-new *to this scenario* but built entirely on the canonical error-model machinery (no new interface): `TransportHttpError` implements `CallError` + `StreamError`; `SocketClosed` implements `CallError` + `StreamError` + `RealtimeError` because the same closed socket is a failure on all three companions. The scenario needs **no** new `baml.errors.<Cap>Error` interface — `RealtimeError` already existed in the spine — so the error side of "transport is a provider property" reuses the per-capability channels unchanged. The only net-new *interface* surface is that `RealtimeError` here is exercised with a real classifier (`is_network_error()`); the conventions left its method set as "classifiers as needed," and this scenario pins at least that one. Whether `is_network_error()` is the *right* classifier for realtime is itself a tension — see (c).

## (c) Where it is awkward, leaky, or unresolved

**Open Question 1 — RESOLVED by provider-as-marker.** OQ1 asked whether every capability should `requires` a `call`, i.e. whether a realtime model is forced to implement a degenerate single turn. The earlier draft of this scenario implemented exactly that (`RealtimeWS.call`, `RealtimeWebRTC.call`) and it was the worst code in the file: to satisfy `call`, the realtime provider dialed a fresh socket, sent one prompt, drained to the first `response.done`, and closed — throwing away **everything that makes it realtime** (no `io`, no barge-in, no duplex, no server-authoritative session), and for WebRTC was actively absurd (spin up an SDP/ICE negotiation to read one text answer). The provider-as-marker spine (`../provider-as-marker.md`) **removes the forcing function entirely**: `Provider` is a bare marker with NO interaction method, `call`/`call_with` belong to `HttpProvider`, and `Realtime requires Provider` (the marker). So `RealtimeWS` and `RealtimeWebRTC` are Providers — composable, host to `with_retry`/`fallback_to` — while implementing ONLY `run`. Both degenerate `call`s are **deleted**; a function over a realtime client simply has no `.call` companion (`Foo.live(args, io)` matches `Realtime` with no degrade). The "best-effort single turn" footgun the background warned about is gone, not papered over. The one provider here that *does* keep `call` is `ResponsesWS` — and that is honest, because a warm-socket Responses turn genuinely **is** request/response (one response.create → one response.completed), so it is a real `HttpProvider`, not a faked one. The distinction provider-as-marker draws (warm socket = HttpProvider, duplex socket = Realtime) is exactly the "two `wss://` providers, opposite capabilities" teaching point of this scenario, now reflected in *which interaction methods each class even has*.

**Open Question 3 — the request side is HTTP-shaped, and realtime has no request.** OQ3 admits `build_request` returns `baml.http.Request` and asks whether non-HTTP transports want their own associated type. This scenario makes the gap concrete in a new way: `RealtimeWS` and `ResponsesWS` both reach for `baml.http.Request` *only* as a bag to carry the upgrade URL + auth headers into `baml.ws.connect` — the body is `""`. The real "request" for a realtime session is the *stream of frames* sent over the socket's lifetime, which has no single-request representation at all. So we are abusing `baml.http.Request` as a connect-params struct. A `baml.ws.ConnectParams` (url + headers, no body/method) would be honest; the proposal has no such type, so the wire-divergence the proposal wanted in `build_request` ends up smeared across ad-hoc frame-builder helpers (`session_update_frame`, `initial_prompt_frame`, …) instead. This is the realtime face of OQ3, and it is **unresolved**: HTTP-is-a- capability covers `call`, but it does not give the request side a transport-neutral home.

**The warm socket is a resource with a lifecycle the model cannot manage (OQ7).** `ResponsesWS` keeps the warm socket + last-id behind a `_pool: $rust_type` host handle (§4) rather than a mutable field — the *right* call, since the proposal's frame is "a client is a pure function returning a Provider; options dissolve into immutable fields," and a warm, ~60-minute, one-in-flight socket is none of those. But pushing it host-side only relocates the problem: nothing in the model says where that socket gets closed, what happens on a second concurrent `call` (the protocol forbids two in-flight responses per connection), or how the pool interacts with `Fallback` copying the provider value (two BAML copies, one socket? two sockets?). The proposal can *hold* the resource (a `$rust_type` field is OQ7's blessed bridge) but offers **no structural help** for its lifecycle — no `Drop`, no scoped ownership, no concurrency guard, no statement of identity semantics when a provider value is copied. Background flags exactly this ("one in-flight response per connection; parallel work needs multiple sockets"); the proposal is silent, and OQ7 ("is an `implements` block with native bodies the supported bridge boundary?") does not reach the harder question of *resource lifecycle* behind that boundary.

**The error channel splits where the capability does — and `SocketClosed` is the seam where that split lands.** The model forces a choice the old single `LlmClient` channel hid: when a socket closes, *which* capability error is it? Under provider-as-marker the answer is clean: `SocketClosed` implements `CallError` **for the warm-socket request/response provider** (`ResponsesWS.call_with`), `StreamError` (since `ResponsesWS.stream` rides the same socket), and `RealtimeError` (inside `run`). The *same physical event* — `baml.ws` `.recv()` returning `null` or `.send()` throwing `Io` — therefore implements all three, but now **honestly**: each channel corresponds to a capability some provider in this file genuinely has. The earlier draft's complaint ("`SocketClosed`'s `CallError` is dead weight, forced only by a dishonest realtime `call`") is **gone** — provider-as-marker deleted that `call`, and `SocketClosed`'s `CallError` impl is now load-bearing solely because of the *real* request/response warm socket. So the error model no longer *inherits* OQ1. What survives is a narrower, genuine tension: the `is_network_error()` classifier is a lie-by-rounding on the realtime channel — a server-authoritative session closing is *state loss*, not a network blip, yet the only triage vocabulary the `RealtimeError` interface gives the app is `is_network_error()`, so a barge-in session the server tore down for a content violation and a Wi-Fi drop are indistinguishable at the `catch`. The classifiers were designed for request/response transports; realtime's failure taxonomy (state-loss vs. transport-drop vs. server-initiated `error` frame) does not fit the three-bool shape, and nothing in the model flags that mismatch. That is a `RealtimeError`-interface design gap, not an artifact of a forced `call`.

**Server-initiated `error` frames are NOT on the error channel at all — and that is either a feature or a hole.** The single most realtime-specific failure mode (Reason #2: an unsolicited mid-session `error` frame from the server) does *not* travel the `throws baml.ExtendUnknownError<RealtimeError>` channel. It arrives as data — `io.send(ServerErrorOut { message })` — and the app handles it in its `io.on(out => …)` match, not in a `catch`. This is arguably *correct* (the session is still alive; an error frame is an event, not a thrown failure), and it is a genuine expressiveness win that the duplex `Channel` can carry it. But it means a realtime provider has **two** error surfaces — thrown `RealtimeError` (the session died) and `ServerErrorOut` (the session reported a problem and continued) — and the new error model only governs one of them. An app author who writes a textbook `catch (e) { let r: baml.errors.RealtimeError => … }` and forgets the `ServerErrorOut` arm in `io.on` will silently drop every server-reported error while believing they handled "the errors." The typed-channel model makes thrown failures rigorous and says nothing about the in-band-error half of the duplex grammar, which for realtime is where most operational errors actually live.

**Two `wss://` providers, opposite capabilities — only convention keeps them apart.** `ResponsesWS` and `RealtimeWS` share a transport (`wire() == WebSocket`) and a wire technology, yet one is `Provider + Streaming` and the other is `Realtime`. The model expresses this *correctly* — they implement different interfaces — and `describe_transport` (usage §5) reads wire and state as independent coordinates, which is the orthogonal- axis win. But there is **nothing stopping** a careless author from writing a single `OpenAIWS` class that `implements` both `Streaming` and `Realtime` over one socket and conflating the two grammars (the background's explicit "don't conflate the two WebSockets" warning). The capability interfaces make the *right* design natural but do not make the *wrong* design impossible.

**Open Question 2 — `io` propagation onto `.live` is fine; the In/Out unions are the real cost.** OQ2 (how the live `io` surfaces) is comfortable here: `io` rides on `.live`, never on the plain call. But the cliff's expressiveness depends entirely on the `InEvent`/`OutEvent` unions being *rich and exhaustive*. The background's "What's hard / Exhaustiveness" warning (20+ event types, stringly-typed dispatch silently drops the ones you forgot) applies to our `match (out) { … }` in `run_barista_session`: BAML's union `match` is exhaustive, which is a genuine win over the SDKs — **but** the event loop inside `run` (§5) dispatches raw frames with a chain of `if (etype == "…")`, which is *not* exhaustive and silently ignores unknown frame types. So the model gives exhaustiveness on the BAML-typed `Channel` boundary but loses it at the host-frame boundary inside the provider. The honest seam (typed `OutEvent`) exists; the un-honest seam (stringly `etype`) is where the real wire is handled, and the proposal does nothing to make that typed.

**No compile-time "this is realtime" guarantee.** Because `client Voice()` returns the existential `Provider`, `VoiceChat.live` is a runtime promise — `invalid_live` *compiles*. The proposal's escape hatch (drop the sugar, write `function … -> RealtimeWS`) works, but then you lose combinators (a `Fallback` is `Realtime` only by runtime claim, §6). For the cliff this is more defensible than for streaming: you genuinely *want* `.live` to be reachable on any client so the `_` arm can give a clear `Unsupported` error rather than a type error the app author can't act on at a tenant boundary. Still, "is this client realtime?" is not a type-checker question here, and that is worth stating plainly.

## (d) Verdict: **Workable-with-additions**

The central claim survives the stress test: making `Realtime` its own capability (not a refinement of `call`) is *correct*, and the model expresses the full taxonomy cleanly along the right axes — transport is which host primitive the provider reaches for (`send` / `fetch_sse` / `ws.connect` / `webrtc.connect`), capability is which interface it implements, and the two are genuinely orthogonal (the two `wss://` providers prove it, `describe_transport` reads both coordinates). The five structural reasons each land on a concrete part of `Realtime.run` that `call` structurally cannot reach, and the four cliff use cases become four `InEvent` variants with no `Stream` analogue — that is the strongest possible evidence that "capabilities are interfaces" is the right spine for transports. The provider-as-marker spine sharpens this further: `Provider` is a bare marker, `call`/`call_with` belong to `HttpProvider`, and `Realtime requires Provider` — so the realtime providers carry **no `call` at all**, which **resolves OQ1**: there is no dishonest "best-effort single turn" to write, both fake `call`s are deleted, and the warm-socket `ResponsesWS` keeps `call`/`call_with` only because it is a genuine request/response `HttpProvider`. But it is *not* clean out of the box: it needs a real duplex socket primitive (`baml.ws`, the thing `SseStream` deliberately lacks), a WebRTC two-plane primitive, and the pinned In/Out event grammar. The one structural gap that remains genuinely unresolved is OQ3: the HTTP-shaped request side has no transport-neutral home, so realtime ends up abusing `baml.http.Request` as connect-params and smearing the real "request" across frame-builder helpers. Add to that the warm-socket lifecycle the model can hold but cannot manage. So: workable, with `baml.ws`/`baml.webrtc`/the event unions as additions, OQ1 now answered (marker `Provider`), and OQ3 still demanding an answer before realtime is first-class. The per-capability error model rides along well — `ResponsesWS` carries `CallError` on `.call_with` and `RealtimeWS` carries `RealtimeError` on `.run`, with no per-provider error type, deliberate failures become concrete (`SocketClosed`, `TransportHttpError`), and foreign `Io` normalizes through one trailing `with_message` per method. With OQ1 resolved, `SocketClosed`'s `CallError` impl is no longer dead weight (it is load-bearing for the *real* warm-socket request/response provider); the surviving error-side quirk is narrower — the realtime failure taxonomy (state-loss vs. transport-drop vs. server-initiated `error` frame) does not fit the three-bool classifier shape, and most realtime errors arrive in-band as `ServerErrorOut` on the `Channel`, which the typed `throws` channel does not govern at all.
