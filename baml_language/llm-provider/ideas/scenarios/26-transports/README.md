# Scenario 26 — Transport taxonomy: why request/response cannot model realtime

This scenario stress-tests the proposal's sharpest structural claim: that **transport** (HTTP / SSE / chunked-JSON / WebSocket / WebRTC) is a property of the *provider*, not of the call, and that **Realtime must be its own capability** rather than a refinement of `HttpProvider.call` (under the provider-as-marker spine `Provider` is a bare marker; `call`/`call_with` belong to `HttpProvider`). It walks the five rows of the transport taxonomy as five providers — `ChatHTTP` (the floor), `ChatSSE` (token streaming), `ResponsesWS` (a *warm socket carrying ordinary request/response*), `RealtimeWS` (full-duplex audio), and `RealtimeWebRTC` (same event grammar, media plane split off) — and shows that the two `wss://` providers share a wire but implement opposite capabilities, proving transport and capability are orthogonal axes. The duplex side is where the proposal earns its keep: the background's five reasons request/response is wrong-shaped (concurrent duplex, server-initiated events, 1:N responses, server-authoritative state, connection-loss=state-loss) and the four use cases that force the bidirectionality cliff (barge-in, mid-stream tool injection, side-channel commands, unsolicited server events) all land on `Realtime.run`'s pass-in `Channel` and have no analogue on a `Stream`. The net-new cost is a real duplex socket primitive (`baml.ws` — the `.send` that `SseStream` deliberately lacks), a WebRTC two-plane primitive, and the In/Out event grammar. Under the provider-as-marker spine (`../provider-as-marker.md`), `Provider` is a bare marker and `call`/`call_with` belong to `HttpProvider` — so the realtime providers (`RealtimeWS`, `RealtimeWebRTC`) carry NO `call` at all and expose only `Realtime.run`, which RESOLVES Open Question 1 (no dishonest single-turn `call` is forced onto a realtime provider; the warm-socket `ResponsesWS`, being genuine request/response, simply IS an `HttpProvider`). The one unresolved tension is Open Question 3 (a realtime session has no single HTTP-shaped request, so the connect-params are smeared across `baml.http.Request` + frame builders).
