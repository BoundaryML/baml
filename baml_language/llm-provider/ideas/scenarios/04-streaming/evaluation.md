# Evaluation — Streaming tokens + streaming partial structured output

Adversarial read. Does the proposed model express *both* token streaming and streaming partial structured output across SSE and Gemini chunked-JSON, with an honest fallback for non-streaming providers? Where does it leak?

## (a) What the proposal reuses unchanged

- **`Streaming requires Provider`** — used verbatim from `_conventions.md`. One method, `stream<TStream, TFinal>(prompt) -> baml.llm.Stream<TStream, TFinal>`. Three providers (`OpenAI`, `Anthropic`, `Gemini`) implement it; the app author sees one interface.
- **The companion `match` + fall-back-to-`.call`** (proposal §5). Streaming is a *delivery refinement*, so the `_` arm does something useful (`buffer_as_stream`) rather than erroring. `EchoModel` (no `Streaming`) exercises exactly that arm; the consumer in `usage.baml` (D) is byte-identical to the streaming consumers.
- **`baml.llm.Stream<TStream, TFinal>`** is listed as reused machinery. We treat it as a pull-based iterator (`next -> TStream | StreamDone`, `final -> TFinal`, `close`) — the `Iterator.next -> Item | Done` shape the proposal leans on throughout. Consumers loop with the same `match` they'd use on any iterator.
- **`Fallback` forwarding `Streaming` by runtime delegation** (proposal §6). The `ResilientStream` client is `GPT4o().with_retry(2).fallback_to(GeminiFlash())` and its `.stream` routes to the first `Streaming` member — OpenAI's SSE reader and Gemini's chunked-JSON reader sit behind the one forwarded capability with no app-visible difference. `with_retry`/`fallback_to` are the inherited default combinators, unchanged.
- **SAP as one `parse` branch** for the *final* validated object (`finalize` calls `baml.sap.parse<TFinal>`), exactly as §2 frames it.
- **Provider-field model** — `Anthropic.max_tokens` is a bespoke field, no options blob (proposal §4).

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.llm.stream_unfold<S, TStream, TFinal>(seed, step, done)`** and its result helper **`StreamStep<S, TStream>`** (`implement.baml` §0). This is the load-bearing addition. The proposal hand-waves stream construction (the `OpenAIStream.parse` body in proposal §2 is literally `// drain from, SAP-parse the final value` — it never says *how* a `Stream` value with incremental `next()` gets built). `stream_unfold` turns a stateful reassembly closure into a `baml.llm.Stream` without each provider author writing a bespoke iterator class. Tied to: `baml.llm.Stream`.
2. **`baml.http.fetch_json_seq(request) -> JsonSeq`** plus the `JsonSeq` body type (`implement.baml` §5). The conventions ship only `fetch_sse`/`SseStream`. Gemini's chunked-JSON transport is unreadable by an SSE parser — "open an SSE stream" is not universal (background, *What's hard*). This is a *second* host stream reader. The `Streaming` interface is untouched; only the body behind it differs — which is precisely the proposal's `type Body` thesis applied to streaming, except the `Body` here is hidden inside `stream` rather than being an associated `type` (see Open Question 4 below).
3. **`baml.sap.parse_partial<TStream>(buffer) -> TStream`** (`implement.baml` §2). The tolerant/best-effort partial parser. SAP today only has the strict final parse. This is the streaming twin and is what makes partial structured output a client-side read of the same buffer. Tied to: SAP / proposal Open Question 6 (expose SAP publicly).
4. **`baml.sap.partial_of<TStream, TFinal>(final) -> TStream`** (`implement.baml` §7). Needed *only* by the fallback path to manufacture a single `TStream` from a `.call` result. Tied to: the companion fallback arm.
5. **`baml.llm.stream_once<TStream, TFinal>(partial, final)`** — degenerate one-element stream for the fallback. Tied to: `baml.llm.Stream`.
6. **Per-provider "mark as stream" request transforms** — `baml.llm.openai_mark_stream` / `anthropic_mark_stream` / `gemini_mark_stream`. These encode that turning a request into its streaming form *diverges*: OpenAI flips `stream:true` + `stream_options.include_usage`; Anthropic flips `stream:true`; Gemini changes the URL (`:streamGenerateContent`). A body flag for two providers, a route change for the third. Tied to: `baml.http.Request`.
7. **`baml.json.get_str/get_int(raw, path)`** — typed JSON-path readers used inside the folds. The conventions give `Response.json_path` for whole responses; the folds need it on individual frames. Minor, but net-new at this granularity.

## (c) Where it is awkward, leaky, or unresolved

**The two stream readers leak into `stream`, not into `Body` (Open Question 4).** OQ4 says the seam is the associated `type Body`, and §2 even shows `OpenAIStream` with `type Body = baml.http.SseStream`. But that pattern only works for the *non-stream* `.call` codec. For `Streaming.stream`, `Body` is not in the signature at all — `stream` returns `baml.llm.Stream`, and the choice of `SseStream` vs `JsonSeq` is made *inside the method body* (`fetch_sse` vs `fetch_json_seq`). So the transport divergence the proposal wanted to hoist into an associated type ends up as an ad-hoc local choice. The interface is genuinely uniform, but the `Body` mechanism does **not** carry streaming — that is a real gap between what OQ4 claims and what streaming needs. A streaming-specific associated `type StreamBody` would restore symmetry, but the proposal doesn't have it.

**`TStream` and `TFinal` are independent, and the fallback can't honor that (Open Question 4 again, plus §5).** `Streaming.stream<TStream, TFinal>` takes two *unrelated* generics. The real streaming path is fine: `fold` parses the buffer into `TStream`, `finalize` parses into `TFinal`. But the `_` fallback arm only has `.call -> TFinal`, and must conjure a `TStream` to satisfy the return type — hence `partial_of<TStream, TFinal>`. That coercion is only meaningful when `TStream` is reachable from `TFinal` (it's `string`, or a deep-partial of `TFinal`). If an app picks an unrelated `TStream`, the *streaming* providers happily produce it (they parse the wire), but the *fallback* throws at runtime. So the same companion has two providers that disagree about which `TStream`s are valid — a leak the type system can't catch because `client` returns the existential `Provider` (§3). This is the streaming face of the proposal's "capability is a runtime promise."

**No compile-time guarantee that a stream is incremental.** `RenderMeetingLive` *looks* like it streams, but against `Canned()` it yields exactly one partial. The proposal is explicit that you'd drop the `client` sugar and write `function … -> ConcreteStreamingProvider` for a static guarantee (§5) — but then you lose `Fallback` (which is `Streaming` only by runtime claim, §6). So you **cannot** have both "guaranteed incremental" and "fallback across providers" at compile time. For streaming UIs that is an honest, unavoidable limitation, and worth stating plainly: the model gives you portability *or* a static streaming guarantee, never both.

**Stateful reassembly is expressible but verbose.** "Reassembly is stateful" (background) maps cleanly onto an `unfold` seed (`StreamAcc`), and the proposal's functional, no-mutation idiom (rebuild the accumulator each fold) handles it. But the cost is real: every fold rebuilds the whole `StreamAcc` record by hand (seven fields, three providers). The Anthropic event grammar — block indices, `thinking_delta` kept out of `buffer`, usage split start/end — is ~50 lines of `if (etype == ...)`. The model *absorbs* it (nothing here is inexpressible), but it does not make it *short*. A real implementation would want a mutable accumulator; BAML's `mut` exists (used in `usage.baml` E) but threading it through `stream_unfold`'s closures is clunkier than the rebuild shown.

**Cancellation is by convention, not enforced.** `s.close()` (usage E) must abort the HTTP request and stop the fold. Nothing in the type system ties `Stream.close` to `SseStream.close`/`JsonSeq.close`; it's a contract `finalize`/`close` must honor. The proposal's `Stream` is assumed, so this is under-specified rather than wrong — but background flags cancellation as hard, and the model offers no structural help (no `Drop`, no scoped lifetime).

**`final()` after a partial loop double-reads conceptually.** The consumer drains `next()` then calls `final()`. `final()` re-runs strict SAP over the *same* buffer the folds already grew. That's correct (validation timing must be at the end, per background) but means the buffer must survive past `StreamDone` — i.e. `stream_unfold`'s `done(state)` keeps the accumulator. Fine, but it makes the `Stream` stateful past its last `next()`, which the bare `Iterator` analogy (`next -> Item | Done`) doesn't cover. `Stream` needs the extra `final` method the plain iterator doesn't have — a small but real extension of the template the proposal claims to reuse "top to bottom."

## (d) Verdict: **Workable-with-additions**

The capability shape is right: one `Streaming` interface genuinely spans flat SSE deltas, Anthropic's event grammar, and Gemini's chunked JSON, and partial structured output really does fall out as a client-side `parse_partial` over the same buffer with a different `TStream` — that is the strongest evidence in this folder that "capabilities are interfaces" pays off, because the app code in `usage.baml` is identical across three divergent transports and a non-streaming fallback. But it is *not* clean out of the box: it needs a real stream-construction primitive (`stream_unfold`), a second host reader for non-SSE transports (`fetch_json_seq` — directly contradicting the implication that `fetch_sse` is the streaming primitive), a public tolerant parser (`parse_partial`), and a fallback coercion (`partial_of`) whose validity the type system can't check. Two structural gaps remain genuinely unresolved: the `Body` seam of OQ4 does **not** carry streaming transport divergence (it's chosen inside the method instead), and you cannot get both cross-provider fallback **and** a compile-time "this is incremental" guarantee — the existential `Provider` makes streaming a runtime promise, exactly like every other capability here. Those are admissions, not blockers, so: workable, with the four named additions.
