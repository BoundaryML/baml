# Evaluation — 24 · Tools in a realtime session

Adversarial read of whether the proposed Provider/capability model expresses event-driven realtime tool-calling. The scenario's whole difficulty is that the synchronous `Tools` seam (`begin`/`step`/`submit`) is the *wrong shape*: the tool call is an **event**, the response is **not paused**, there is **no return slot**, and the result is an **outbound event with a correlation id** plus a *separate* continuation request. (Background: `04-realtime-and-transports.md` → `## ◆ Tools in a realtime session`.)

## (a) What the proposal reuses unchanged

- **`Realtime` verbatim.** `run(self, prompt, io: Channel) -> Transcript` is the spine. Realtime tools are just *more events on the same channel* — the duplex driver does not change. We add a capability on top, not a new transport.
- **The pass-in `Channel`.** `on`/`send`/`close` are exactly the primitive in `_conventions.md`. Tool events arrive via the same `io.on` the audio uses; the `function_call_output` splice goes out via the same `io.send`. No new channel.
- **`Tool { name, description, parameters: type }`** and `reflect.type_of<T>()`. The app declares tools identically to the synchronous loop (scenario 09). The per-provider schema encoders (`type_to_json_schema`, `type_to_gemini_openapi`) are reused, just delivered in a `session.update` / `setup` event instead of an HTTP body.
- **Capability negotiation = `match`, now including the basic call.** `.run_tools_live` is the same companion pattern as `.live`/`.run_tools`: `match (p) { let rt: RealtimeTools => … , _ => throw Unsupported }`. No honest fallback to `.call` — correct, same as `.live`. And under the marker revision the *plain* `Concierge(persona)` value form is itself just a `match` for `HttpProvider.call`, which a realtime-only provider does not implement — so it throws `Unsupported` rather than silently degrading. `call` is no longer a privileged base method sitting under the negotiation; it is one more capability matched for.
- **Combinator-by-delegation.** `RealtimeFallback` is a plain non-generic class that `match`es its members and routes — the §6 pattern.
- **The `id` correlation discipline** from scenario 09 (echo the wire id; or synthesize when the wire has none) ports directly to `call_id`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface RealtimeTools requires Realtime`** — the event-driven loop. This is the load-bearing addition. It deliberately does **not** reuse `Tools`, because `Tools` is request/response and realtime is push/event. Tied to: the capabilities-as-interfaces primitive — this is "another capability that `requires` a richer base (`Realtime`, not just `Provider`)", the first capability in the set whose base is *itself* a capability. The proposal allows it (`A requires B`, `B requires Provider`) but no prior scenario exercised a two-level `requires` chain on a capability.

2. **`ToolEvent { call_id, name, args_json }` and `ToolOutputEvent { call_id, output_json }`** — the realtime analogue of `ToolCall`/`ToolResult`, but they travel as events, not as a return value + request-body slot. Tied to: the `ToolCall`/`ToolResult` seam types. Net-new because the existing pair assumes a synchronous return; these carry only a correlation id and JSON, because there *is* no slot.

3. **`ExecutionContext.dispatch_async(ev) -> ToolOutputEvent`** plus an event-`emit` surface. Tied to: the proposal's own §7 net-new flag — "`ExecutionContext` … for realtime/harnesses, an event-`emit` surface." This scenario is the concrete cash-out of that flag. The synchronous `dispatch -> ToolResult[]` cannot be reused: it returns a value to thread into `submit`, and realtime has nowhere to thread it.

4. **`RealtimeTools.configure_tools` as a distinct step.** Realtime declares tools *once at session open* (`session.update` / `setup`), not per call. There is no `tools` parameter on a per-turn method to hang them on, so configuration is its own seam method. Tied to: the `Tools.begin` "declare tools" role, split out because the loop is push, not pull.

5. **`interface baml.errors.RealtimeToolError`** — a NET-NEW capability-error channel. The error model ships four interfaces (`CallError`/`StreamError`/`ToolError`/`RealtimeError`); `RealtimeTools` is a fifth capability, so it earns a fifth error interface. It is deliberately **neither** `ToolError` (that is the *synchronous* begin/step/submit loop — a different shape) **nor** `RealtimeError` (an audio-transport failure is a different concern than a tool blowing up off the audio path or a `function_call_output` failing to splice). Its classifiers are `is_network_error` / `is_rate_limit` / `is_dispatch_error` — the third replaces `is_parse_error` because the characteristic realtime-tool failure is *the handler died*, not *the bytes didn't parse*. Tied to: the error model's "any NEW capability → a NEW `baml.errors.<Cap>Error` interface, same shape" rule. This scenario is the concrete cash-out of that escape valve, and it shows the classifier *set* is not actually uniform across capabilities — a new capability brings a new failure vocabulary, not just a new name.

## (c) Where it is awkward, leaky, or unresolved

- **OQ#2 (how the live `io` surfaces) is stretched, not broken.** The proposal says `io` rides on the capability companion and "propagates from `Realtime.run`'s signature onto the companion." Here the companion needs `io` **and** `ctx` (deps
  + handlers) **and** `tools` — three pass-in params on `.run_tools_live`. That is a lot of plumbing on a companion the proposal pitched as nearly invisible. It is expressible, but the "app writes almost nothing" ergonomic is weaker than for `.call`: `AnswerCall` has to build the Channel and the ExecutionContext by hand. The proposal's own OQ#2 ("should a realtime function name the channel in its own signature?") is the right question, and this scenario argues *yes* — a realtime function is honestly different-shaped and pretending the companion is free hides real ceremony.

- **OQ#1 is now RESOLVED — `Provider` is a marker, so the degenerate `.call` is gone.** Under the old spine `RealtimeTools requires Realtime requires Provider` forced a realtime-tools provider to owe a best-effort `.call` — for `OpenAIRealtime` a degraded, audio-less, open-a-throwaway-socket single turn that existed only to satisfy the chain. With the [marker revision](../../provider-as-marker.md) `call`/`call_with` belong to `HttpProvider`, not the base; `Provider` carries only the combinator factories. So a realtime provider `requires Provider` (the marker) transitively via `Realtime`/`RealtimeTools` and exposes *only its real interaction* (`run`, `run_tools_live`) — no fake `call`. `OpenAIRealtime` and `GeminiLive` drop their `implements Provider { call }` blocks entirely. What remains is two genuine entry points (`run`, `run_tools_live`) for one socket — and `plain run` (audio, no tools) is a real, wanted shape (a tool-less voice agent), not surface bloat minted to satisfy a base contract. The old "degenerate / dishonest `call`" complaint disappears: there is no `call` here to be dishonest.

- **Server-authoritative state is inexpressible as a client value — and we leaned into that.** The synchronous `Tools.Transcript` is a *client-held* opaque value threaded through `step`/`submit`. In realtime the conversation lives on the *server*; the client holds no transcript between events. So `emit_tool_output` takes **no transcript** — it just emits onto the socket. The `Transcript` we finally return from `run` is whatever the server reports at close. The proposal has no vocabulary for "state the client cannot hold"; we modeled it by *omission* (a method with no transcript param), which works but is a silent convention, not something the type system enforces. A provider author could wrongly try to keep client-side history and the interface wouldn't stop them.

- **The combinator degrades hard, and the interface can't say so.** `Fallback` in §6 retries per request. `RealtimeFallback` can only choose at session *open* — a live socket can't fail over mid-call without dead air and lost server history. We encoded this by making `configure_tools`/`decode_tool_event`/`emit_tool_output` on the combinator **throw** ("call `run_tools_live`"), overriding only the whole-loop default. That is a leak: the combinator statically *claims* `RealtimeTools` (all three seam methods) but only one of its four methods is real. The proposal's "a combinator claims every capability it forwards, degrading at call time" tradeoff (§6) here degrades to "three of these methods are traps." Capability-as-runtime-promise can't express "this method is forwardable but those three aren't."

- **Ordering-with-audio and latency are policy the seam can't surface.** Whether to `await_response_done` before `response.create` (OpenAI) — versus Gemini's single implicit `toolResponse` with no continuation event at all — is a genuine shape difference fully hidden inside `emit_tool_output`. Good for portability, but the app *cannot* influence it without dropping to the manual loop (`BudgetedConcierge`), which then has to know provider-specific timing to do anything smarter than a blanket deadline. The "dead air" problem is real and the seam offers the app no portable hook for it (no "on_tool_pending" to fill silence).

- **No compile-time capability guarantee (status-quo limitation, restated).** Because `client` returns the existential `Provider`, "is this client realtime-tools-capable?" is the runtime `match` in `.run_tools_live`. A phone system would much rather fail at deploy than when the call connects. The escape hatch (`function … -> OpenAIRealtime`) gives compile-time precision but forfeits client-level swappability — the exact thing this scenario wants.

- **Cross-capability channel forwarding *can* box a typed error into `UnknownError` — but boxing here is a coverage convention, not a wall (NEW — the error model surfaces this).** `RealtimeTools.run_tools_live` *ends* by calling `self.run(prompt, io)` — and `run` declares the **`RealtimeError`** channel, while `run_tools_live` declares **`RealtimeToolError`**. These are independent interfaces (the error model is explicit that capability error interfaces are NOT a hierarchy), so a `RealtimeError` is foreign on the `RealtimeToolError` channel *only if it does not implement `RealtimeToolError`*. The clean fix is one external `implements` row: because BAML's `implements` is a Rust-like trait relation that admits external impls in both directions, the **`RealtimeTools` package — which owns `RealtimeToolError`** — declares `implements baml.errors.RealtimeToolError for <the RealtimeError types it forwards>` (local trait, foreign type, allowed). With those rows in place a mid-session socket drop rides the `RealtimeToolError` channel as its *typed self* — caught concretely, `is_network_error()` intact, **no box**. (For the common path this is already paid for: the stdlib `baml.errors.Io`/`Timeout` and the bespoke `Refused`/rate-limit errors implement all four common interfaces, so most realtime drops stay typed without any extra row.) Where a row *is* missing, the crossing falls back to `baml.UnknownError.with_message<RealtimeToolError>(e, …)`, and even then the error is **not destroyed**: `with_message` annotates the box in place and `UnknownError.data: unknown` keeps the original `RealtimeError` untouched, so `baml.UnknownError.from<RealtimeError>(e)` pulls the same concrete error back out with `is_network_error()` intact. What the missing-row case loses is only the **static** signal: the app's channel is `RealtimeToolError | baml.UnknownError`, which does not advertise that a network drop can reach it boxed; an app catching `baml.errors.RealtimeToolError` won't triage the drop unless it speculatively probes `from<RealtimeError>(e)`. And when it *does* box, the probe is **mandatory, never transparent** (settled in `error-model.md`): a plain `catch (e) { let r: baml.errors.RealtimeError => … }` arm is a runtime is-a test on `e` *itself*, and the boxed drop *is* a `baml.UnknownError` (which does not implement `RealtimeError`), so that arm never fires on it — the author must explicitly `baml.UnknownError.from<RealtimeError>(e)` inside the `UnknownError` arm. `BudgetedConcierge` (usage.baml) sits in the same spot — its trailing catch wraps `rt.run`'s `RealtimeError`, and the same row (or probe) applies. So a capability that *delegates into its base capability's failure path* has a clean answer — the channel author writes `implements <ThisChannel>Error for <upstream error>` so the forwarded errors flow through typed — and the only residuals are (a) nothing *forces* the row, so a forgotten one re-introduces a box (recoverable via `from<…>`, data intact), and (b) a genuinely foreign value (host panic, unmapped JSON) has no inner typed error, so the `UnknownError` escape hatch is doing exactly its job. The synchronous `Tools.run_tools` never raised the question because it only ever called *other `ToolError` methods*; the realtime loop is just the first capability whose default body crosses a channel boundary into its base, which surfaces the coverage convention — not a new structural pressure.

- **The combinator advertises `RealtimeTools` but three of its four seam methods now throw `RealtimeFallbackMisuse` (typed, but still traps).** Under the old single-channel model the traps threw a generic `LlmClient`; now they throw a concrete `RealtimeFallbackMisuse` implementing `RealtimeToolError`. That is strictly better — an app *can* catch the misuse concretely — but it does not fix the underlying leak from section (c) above: the type system still says `RealtimeFallback` is a full `RealtimeTools`, and only `run_tools_live` is real. Typing the trap did not make it less of a trap; it just made the trap legible at the catch.

## (d) Verdict: **Workable-with-additions**

The model bends to fit: capabilities-as-interfaces cleanly admits a *new* capability (`RealtimeTools`) that `requires` another capability (`Realtime`) rather than forcing the event-driven loop into the synchronous `Tools` seam — and that refusal-to-reuse is the right call, not a workaround. The Channel, `Tool`, schema encoders, id-correlation, and `match`-based negotiation all port unchanged. The error model follows the same pattern: a fifth capability earns a fifth error interface (`baml.errors.RealtimeToolError`, with `is_dispatch_error` replacing `is_parse_error`), and the trap methods on the combinator at least gain a concrete, catchable type (`RealtimeFallbackMisuse`). But it is not *Clean*: it needs three genuine additions (`RealtimeTools`, `ToolEvent`/`ToolOutputEvent`, `dispatch_async`/event-emit) plus a net-new error channel, its combinator can forward only the whole loop (three seam methods become *typed* traps the type system still advertises), and it can only *gesture* at server-authoritative state by omitting a parameter. The marker revision *removes* one prior cost: there is no longer a degenerate `.call` minted per provider to satisfy a base contract — `call`/`call_with` live on `HttpProvider`, which a realtime provider simply does not implement, so `OpenAIRealtime`/`GeminiLive` expose only their real `run`/`run_tools_live` (OQ1 resolved). The error-model finding is real but smaller than it first looks: because `run_tools_live` delegates into its base capability's `run`, and `RealtimeError` and `RealtimeToolError` are independent (not hierarchical) channels, a mid-session network drop *would* box into `UnknownError` on the `RealtimeToolError` channel — except that boxing here is a coverage convention, not a wall. Because `implements` is a Rust-like trait relation with external impls, the `RealtimeTools` package keeps the crossing typed by declaring `implements baml.errors.RealtimeToolError for <the forwarded RealtimeError types>` alongside its channel (and the common stdlib/`Refused`/rate-limit errors already implement all four core interfaces, so the typical drop stays typed for free). The residual is only that nothing *forces* the row: a forgotten one re-boxes, where the data and `is_network_error()` classifier still survive in `.data` and are recoverable via an explicit `from<RealtimeError>(e)` probe (mandatory, never transparent — a plain `catch` arm tests `e` itself, which is the `UnknownError` box, so it never matches `RealtimeError`); and a genuinely foreign value (host panic) has no inner typed error, where the `UnknownError` escape hatch is correct. The first capability whose default body crosses a channel boundary surfaces this convention rather than a new structural pressure. The two hardest realities of the background — "no synchronous return slot" and "latency is dead air" — are expressible but the first is an unenforced convention and the second has no portable app-facing hook.
