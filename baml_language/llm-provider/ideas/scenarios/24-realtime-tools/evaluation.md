# Evaluation — 24 · Tools in a realtime session

Adversarial read of whether the proposed Provider/capability model expresses event-driven realtime tool-calling. The scenario's whole difficulty is that the synchronous `Tools` seam (`begin`/`step`/`submit`) is the *wrong shape*: the tool call is an **event**, the response is **not paused**, there is **no return slot**, and the result is an **outbound event with a correlation id** plus a *separate* continuation request. (Background: `04-realtime-and-transports.md` → `## ◆ Tools in a realtime session`.)

## (a) What the proposal reuses unchanged

- **`Realtime` verbatim.** `run(self, prompt, io: Channel) -> Transcript` is the spine. Realtime tools are just *more events on the same channel* — the duplex driver does not change. We add a capability on top, not a new transport.
- **The pass-in `Channel`.** `on`/`send`/`close` are exactly the primitive in `_conventions.md`. Tool events arrive via the same `io.on` the audio uses; the `function_call_output` splice goes out via the same `io.send`. No new channel.
- **`Tool { name, description, parameters: type }`** and `reflect.type_of<T>()`. The app declares tools identically to the synchronous loop (scenario 09). The per-provider schema encoders (`type_to_json_schema`, `type_to_gemini_openapi`) are reused, just delivered in a `session.update` / `setup` event instead of an HTTP body.
- **Capability negotiation = `match`.** `.run_tools_live` is the same companion pattern as `.live`/`.run_tools`: `match (p) { let rt: RealtimeTools => … , _ => throw Unsupported }`. No honest fallback to `.call` — correct, same as `.live`.
- **Combinator-by-delegation.** `RealtimeFallback` is a plain non-generic class that `match`es its members and routes — the §6 pattern.
- **The `id` correlation discipline** from scenario 09 (echo the wire id; or synthesize when the wire has none) ports directly to `call_id`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface RealtimeTools requires Realtime`** — the event-driven loop. This is the load-bearing addition. It deliberately does **not** reuse `Tools`, because `Tools` is request/response and realtime is push/event. Tied to: the capabilities-as-interfaces primitive — this is "another capability that `requires` a richer base (`Realtime`, not just `Provider`)", the first capability in the set whose base is *itself* a capability. The proposal allows it (`A requires B`, `B requires Provider`) but no prior scenario exercised a two-level `requires` chain on a capability.

2. **`ToolEvent { call_id, name, args_json }` and `ToolOutputEvent { call_id, output_json }`** — the realtime analogue of `ToolCall`/`ToolResult`, but they travel as events, not as a return value + request-body slot. Tied to: the `ToolCall`/`ToolResult` seam types. Net-new because the existing pair assumes a synchronous return; these carry only a correlation id and JSON, because there *is* no slot.

3. **`ExecutionContext.dispatch_async(ev) -> ToolOutputEvent`** plus an event-`emit` surface. Tied to: the proposal's own §7 net-new flag — "`ExecutionContext` … for realtime/harnesses, an event-`emit` surface." This scenario is the concrete cash-out of that flag. The synchronous `dispatch -> ToolResult[]` cannot be reused: it returns a value to thread into `submit`, and realtime has nowhere to thread it.

4. **`RealtimeTools.configure_tools` as a distinct step.** Realtime declares tools *once at session open* (`session.update` / `setup`), not per call. There is no `tools` parameter on a per-turn method to hang them on, so configuration is its own seam method. Tied to: the `Tools.begin` "declare tools" role, split out because the loop is push, not pull.

## (c) Where it is awkward, leaky, or unresolved

- **OQ#2 (how the live `io` surfaces) is stretched, not broken.** The proposal says `io` rides on the capability companion and "propagates from `Realtime.run`'s signature onto the companion." Here the companion needs `io` **and** `ctx` (deps
  + handlers) **and** `tools` — three pass-in params on `.run_tools_live`. That is a lot of plumbing on a companion the proposal pitched as nearly invisible. It is expressible, but the "app writes almost nothing" ergonomic is weaker than for `.call`: `AnswerCall` has to build the Channel and the ExecutionContext by hand. The proposal's own OQ#2 ("should a realtime function name the channel in its own signature?") is the right question, and this scenario argues *yes* — a realtime function is honestly different-shaped and pretending the companion is free hides real ceremony.

- **OQ#1 (does every capability `requires Provider`) bites twice.** `RealtimeTools requires Realtime requires Provider`, so a realtime-tools provider owes a best-effort `.call`. For `OpenAIRealtime` that `.call` is a degraded, audio-less, open-a-throwaway-socket single turn — honest but nearly useless, and it exists only to satisfy the chain. Worse, it owes a *plain* `Realtime.run` too (audio with no tools). Three near-identical entry points (`call`, `run`, `run_tools_live`) for one socket is real surface bloat that the "every capability refines `call`" rule forces.

- **Server-authoritative state is inexpressible as a client value — and we leaned into that.** The synchronous `Tools.Transcript` is a *client-held* opaque value threaded through `step`/`submit`. In realtime the conversation lives on the *server*; the client holds no transcript between events. So `emit_tool_output` takes **no transcript** — it just emits onto the socket. The `Transcript` we finally return from `run` is whatever the server reports at close. The proposal has no vocabulary for "state the client cannot hold"; we modeled it by *omission* (a method with no transcript param), which works but is a silent convention, not something the type system enforces. A provider author could wrongly try to keep client-side history and the interface wouldn't stop them.

- **The combinator degrades hard, and the interface can't say so.** `Fallback` in §6 retries per request. `RealtimeFallback` can only choose at session *open* — a live socket can't fail over mid-call without dead air and lost server history. We encoded this by making `configure_tools`/`decode_tool_event`/`emit_tool_output` on the combinator **throw** ("call `run_tools_live`"), overriding only the whole-loop default. That is a leak: the combinator statically *claims* `RealtimeTools` (all three seam methods) but only one of its four methods is real. The proposal's "a combinator claims every capability it forwards, degrading at call time" tradeoff (§6) here degrades to "three of these methods are traps." Capability-as-runtime-promise can't express "this method is forwardable but those three aren't."

- **Ordering-with-audio and latency are policy the seam can't surface.** Whether to `await_response_done` before `response.create` (OpenAI) — versus Gemini's single implicit `toolResponse` with no continuation event at all — is a genuine shape difference fully hidden inside `emit_tool_output`. Good for portability, but the app *cannot* influence it without dropping to the manual loop (`BudgetedConcierge`), which then has to know provider-specific timing to do anything smarter than a blanket deadline. The "dead air" problem is real and the seam offers the app no portable hook for it (no "on_tool_pending" to fill silence).

- **No compile-time capability guarantee (status-quo limitation, restated).** Because `client` returns the existential `Provider`, "is this client realtime-tools-capable?" is the runtime `match` in `.run_tools_live`. A phone system would much rather fail at deploy than when the call connects. The escape hatch (`function … -> OpenAIRealtime`) gives compile-time precision but forfeits client-level swappability — the exact thing this scenario wants.

## (d) Verdict: **Workable-with-additions**

The model bends to fit: capabilities-as-interfaces cleanly admits a *new* capability (`RealtimeTools`) that `requires` another capability (`Realtime`) rather than forcing the event-driven loop into the synchronous `Tools` seam — and that refusal-to-reuse is the right call, not a workaround. The Channel, `Tool`, schema encoders, id-correlation, and `match`-based negotiation all port unchanged. But it is not *Clean*: it needs three genuine additions (`RealtimeTools`, `ToolEvent`/`ToolOutputEvent`, `dispatch_async`/event-emit), it forces a `requires` chain that mints two near-useless entry points (`call`, plain `run`) per provider, its combinator can forward only the whole loop (three seam methods become traps the type system still advertises), and it can only *gesture* at server-authoritative state by omitting a parameter. The two hardest realities of the background — "no synchronous return slot" and "latency is dead air" — are expressible but the first is an unenforced convention and the second has no portable app-facing hook.
