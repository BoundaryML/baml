# Evaluation — Reliability (retry / fallback / load-balance / error taxonomy)

Adversarial read of whether the proposed model expresses reliability cleanly.

## (a) What the proposal reuses unchanged

- **Combinators-wrap-a-Provider is the whole design.** The proposal already ships `with_retry`/`fallback_to`/`cached` as default methods on the `Provider` *marker* (the combinator factories; see [`../../provider-as-marker.md`](../../provider-as-marker.md)) and the `Fallback` class verbatim. `Retry`, `Fallback`, and `RoundRobin` here are exactly that pattern: plain, non-generic classes that forward by runtime delegation. Because they forward request/response, they `implements HttpProvider` — the capability that *owns* `call`/`call_with` now that `Provider` is a bare marker — and remain providers via `HttpProvider requires Provider`. Each also forwards the projection: a combinator's `call_with` routes `project` to the member's `call_with`, so usage/sidecar survives the wrapper (the P1 fix) rather than being dropped. The ClientType enum loop (`ns_llm/llm_types.baml:6,273`) dissolves into ordinary classes with no new language feature.
- **`client` = `function -> Provider` sugar.** `Reliable()`, `Resilient()`, `Balanced()` are just combinator chains on provider values — composition is a function call. The app author writes one line; no `retry_policy:` stanza, no options blob. This is the cleanest part of the scenario.
- **`service_tier` dissolves into provider fields (§4).** OpenAI's `flex`/`priority` and Anthropic's `auto`/`standard_only` are bespoke fields on the two classes — different value sets, no shared blob, no `@providers:` map. The proposal's "options are fields" rule lands this with zero friction.
- **`throws`/`catch` + interface-membership `match`** carry the entire retry decision and capability forwarding. The `match (e.kind)` table and the `match (p) { let s: Streaming => ... }` routing are stock machinery.
- **The per-capability error channel is exactly what retry needs.** Every fallible method now declares `baml.ExtendUnknownError<baml.errors.CallError>` (and `StreamError`/`ToolError` on the other channels). A combinator catches a concrete `LlmError` thrown by a member and reads its `kind` to decide retry — concreteness is recovered at the `catch`, precisely as the error model promises. The old "`type Error` so combinators can reason about failures" intent survives, now expressed as a concrete `CallError` rather than a per-provider associated type.

## (b) Net-new surface it must add (each tied to a primitive)

1. **A richer classifier than `baml.errors.CallError` exposes** — `enum FailureKind` + `class LlmError { kind, status_code, retry_after_secs, provider_name }` that `implements baml.errors.CallError` (and `StreamError`/`ToolError`). The canonical interface offers only three coarse classifiers (`is_network_error` / `is_rate_limit` / `is_parse_error`); those answer "transport noise?" but not "context-length vs content-filter vs plain-permanent," which the background's 4-row retry table requires. So this scenario adds a concrete `CallError` with a `FailureKind` discriminator and *derives* the three canonical classifiers from `kind`, so a combinator reads the rich `kind` while interface-only app code still triages. A retry loop that could only read the three booleans degrades to string-sniffing `e.message` (what the TS background does) for the two distinctions it most needs. The error model gives the channel and the escape hatch; it does **not** give this taxonomy — the scenario supplies the minimum one.
2. **A `Classifier` interface** (`classify(resp) -> LlmError`). Tied to `HttpProvider`. Each provider owns wire-dialect→taxonomy mapping because "same condition, four shapes" (background) can't be written once for all providers — it lives inside the provider, like the four structured-output encodings.
3. **`Retry-After` parsing at the host boundary** — `parse_retry_after`, `jittered_backoff`, `backoff_sleep`. Tied to `baml.http`. Honoring the header is non-negotiable per the background; `baml.http.Response` exposes `.headers`, so this is a thin host function, not a language change.
4. **`Retry.idempotent: bool`** — a provider/combinator field with no analog in the proposal. Tied to nothing existing. The proposal never models side-effect safety; without this flag, `with_retry` on a tool-executing step silently risks double execution.
5. **`OpaqueTranscript { provider, inner_handle: unknown }`** — a box so `Fallback` can forward `Tools` while remembering which member owns the opaque, per-provider `type Transcript`. Tied to the `Tools` capability. The associated `type` is per-provider; a combinator that forwards it must erase + re-tag.
6. **Mutable host state for `RoundRobin`** — `state: $rust_type` + `rr_*` functions (cursor, per-member health, cooldown clock). Tied to nothing in the proposal. This is the real gap (see (c)).

## (c) Where it is awkward, leaky, or unresolved

- **RoundRobin needs mutable state, and `client → -> Provider` forbids it.** The sugar (proposal §3) rewrites `client RoundRobin()` to a function that produces a *fresh value per call*. A round-robin cursor, a least-busy counter, and a circuit-breaker cooldown are all *cross-call mutable state*. A pure function returning a provider cannot hold them — so `state: $rust_type` is smuggled in as a host handle constructed once by `RoundRobin.over(...)` and threaded through `$rust_io_function`s. That works, but it quietly violates the "providers are values, clients are pure config functions" story: the value now hides a pointer to mutable host state, and two `RoundRobin.over(...)` calls with the same members are *not* interchangeable. The proposal has no notion of a stateful combinator; LiteLLM's Router (the background's canonical example) is fundamentally stateful, so this is a genuine miss, not a detail.

- **Open Question 5 (capability `match` over an existential) is load-bearing and assumed.** Every combinator's `implements` block does `match (p) { let s: Streaming => ... }` at runtime. Reliability *multiplies* the dependence: `Fallback` must runtime-test `Streaming`, `Tools`, and `Realtime` membership on each member to route correctly. If value-level reflection can't test interface membership on an existential `Provider`, the entire combinator layer collapses. OQ5 asks us to "confirm" this works — the whole scenario is staked on a yes.

- **Stateful chains break under fallback, and the model gives ZERO compile-time protection (the server-statefulness hazard, §5).** (This is distinct from the proposal's original OQ1 — the "degenerate `call` forced onto realtime/harness" question — which the marker revision in [`../../provider-as-marker.md`](../../provider-as-marker.md) now resolves as "no": `call` is an `HttpProvider` capability, not a base method, so nothing fakes it. This scenario never had a degenerate `call`; the hazard below is about server-authoritative *state*, which is not a capability interface at all.) `StatefulTurn(prev).fallback_to(Claude)` type-checks and runs; the fallback turn silently can't see `previous_response_id`. Because `client` returns the existential `Provider`, "is this provider server-stateful?" is unanswerable by the type checker — it's not even a runtime `match` we can write, since "statefulness" isn't a capability interface. This is precisely the "fallback that changes behavior silently is worse than a clean failure" hazard, and the proposal's runtime-promise stance (§5) cannot catch it. The escape hatch (drop the sugar, return a concrete type) doesn't help: the problem is *combining* a stateful provider with a stateless one, not naming a capability. **Plainly: server-authoritative conversational state cannot be made safe under fallback in this model.**

- **Tools-under-fallback can't fail over mid-loop (OQ via §7's opaque Transcript).** A `Transcript` is provider-owned and opaque, so once `Fallback` picks a `Tools` member in `begin`, it must ride that member for the entire loop — a 503 on turn 3 cannot transparently re-home the half-built transcript to another provider (call ids, positional `tool_result` ordering, and assistant-turn phase are all member-specific). The model is *honest* about this (it forces the limitation into the open via `OpaqueTranscript`), but the result is that "reliable tool loops" degrade to "reliable choice of one tool provider," which is weaker than what a naive reader expects from `.fallback_to`.

- **Streaming retry is a half-truth.** `Retry` forwards `Streaming` to inner, but a stream that dies after emitting 200 tokens cannot be "retried" without re-emitting tokens the client already saw (the background's exact warning). Our `Retry.stream` just delegates — it does **not** retry a broken stream, because doing so correctly needs resumption/token-offset state the `baml.llm.Stream` interface doesn't expose. So `Reliable().stream(...)` retries the *initial connect* failure but silently gives up on mid-stream death. Defensible, but the combinator's name over-promises.

- **`idempotent` is a blunt instrument.** A single bool can't distinguish "the request never left the client" (safe to retry) from "we got a 500 after the tool ran" (unsafe). We approximate with `err.status_code == null` ⇒ no response ⇒ unsafe, but a 500 *after* a side effect has `status_code == 500` and we'd retry it. True idempotency needs request-level idempotency keys, which neither the proposal nor `baml.http.Request` models.

- **NEW (error model): `baml.UnknownError` is a hole every combinator must defensively plug, and it silently *under-retries*.** Under the old single `type Error` channel, a member's failure was *always* an `LlmError` the combinator could classify off the static type. Under `baml.ExtendUnknownError<baml.errors.CallError>`, a member can now also throw `baml.UnknownError` — either a genuinely foreign value the trailing `with_message` catch couldn't classify (a host panic, a malformed SSE frame, a JSON failure the provider didn't map to a `kind`), *or* a typed error from a nested capability boxed as it crossed into this channel. `Retry`, `Fallback`, and `RoundRobin` each grew a `let u: baml.UnknownError => { throw u; }` arm and re-throw it un-retried, because the *static* type `UnknownError` advertises no `kind`/`status_code` to decide "transient?". That re-throw is *defensible but not forced*: `UnknownError.data: unknown` still holds the original value untouched, so a boxed `LlmError` survives — speculatively probing `from<baml.errors.CallError>(u)` (or `from<LlmError>(u)`) recovers the *same* concrete error, classifiers intact, and could be retried. What `UnknownError` actually loses is the **static signal**, not the data: the `CallError | UnknownError` channel never advertises which classified errors are recoverable inside the box, so recovery is by speculative re-assertion rather than type-directed — the P2 "capability = runtime promise" stance applied to the error channel. Two caveats keep this honest. First, a *genuinely* foreign error (the host panic / unmapped JSON above) carries no recoverable inner `LlmError` at all — for those the un-retried re-throw is simply correct, and `.with_retry`'s reliability really is hostage to the provider's discipline in mapping foreign transport errors to a `Transient` `LlmError`. Second, recovery is **explicit, never transparent** (settled in `error-model.md`, not an open question): the plainer `let c: baml.errors.CallError => …` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on the box — it only ever catches an inner-typed `CallError` thrown directly on this channel. To recover a boxed transient the combinator must `from<baml.errors.CallError>(u)` *explicitly* inside the `UnknownError` arm; a plain catch across the boundary only ever sees `CallError` or `UnknownError`. The escape hatch that makes the model total (nothing is unrepresentable) is thus not a *data*-loss: it trades a static "this is retryable" signal for an explicit runtime probe, and the absence of that signal — not the data — is what is invisible at the call site.

- **NEW (error model): the three canonical classifiers and `FailureKind` can drift out of sync.** `LlmError.is_rate_limit()` is *derived* from `kind == Transient && status ∈ {429,503,529}`, but `kind` is set independently by each provider's `classify`. Nothing forces the derivation and the assignment to agree: a provider could mint a `Transient` `LlmError` with `status_code: null` (conn reset) for which `is_rate_limit()` correctly returns false, but it could equally mislabel a 429 as `Permanent` and then `is_rate_limit()` lies to every interface-only consumer. The error model's promise — "interface-only callers triage correctly via classifiers" — holds only if every provider's `classify` and every classifier method stay mutually consistent, and the type system checks neither. Collapsing two notions of "what kind of failure is this" (the rich `kind`, the three booleans) into one class is convenient but creates a consistency obligation the old opaque error never had.

- **NEW (error model): `Unsupported` on the capability channels is correct but coarsens the failover story.** The combinators' capability-negotiation `_` arms now throw the canonical `baml.errors.Unsupported` (legal on `CallError`/`StreamError`/`ToolError` alike) instead of a hand-rolled "permanent" `LlmError`. That is cleaner — but it means a `Fallback` whose members are *none* streaming now raises `Unsupported`, which an app catching `baml.errors.StreamError` will classify as `is_network_error() == false` and treat as a flat failure, indistinguishable at the interface level from a real refusal. The concrete `Unsupported` type is catchable, but the moment an app degrades to the interface, "I asked for a capability nobody has" and "the model declined" look the same through the three classifiers.

## (d) Verdict

**Workable-with-additions.**

Retry, fallback, the concrete-`CallError` taxonomy, `Retry-After` honoring, and `service_tier`-as-a-field are expressed cleanly and idiomatically — they are the combinator pattern the proposal already endorses, and the app-author ergonomics (`.with_retry(4)`, `.fallback_to(...)`) are excellent. The per-capability `baml.ExtendUnknownError<CapErr>` channels fit this scenario well: a combinator catches a member's concrete `LlmError`, reads its rich `kind`, and re-throws on the *same* channel with no variance gymnastics — concreteness recovered at the `catch` is exactly what retry needs. The `FailureKind` refinement is the one unavoidable net-new addition, and it's a small, well-motivated extension of the three canonical classifiers. The model genuinely *absorbs* most of this scenario. But it resists in three places: **RoundRobin's load-balancing/circuit-breaker state has nowhere to live** in a pure-function-returns-a-value model and is only rescued by an off-model host handle; **server-authoritative state (`previous_response_id`) under fallback cannot be made safe or even flagged** — the runtime-promise stance has no answer here, and the compile-time escape hatch doesn't apply to a *composition* hazard; and the error model's own escape hatch, **`baml.UnknownError`, is a hole the retry loop acts on only by speculation** — the `CallError | UnknownError` channel advertises no static signal that a boxed transient is recoverable inside, so `.with_retry` re-throws it un-retried by default even though an explicit `from<CallError>(u)` probe could pull a still-classified error back out of `.data`; for a *genuinely* foreign error (no recoverable inner type) the un-retried re-throw is simply correct, leaving reliability hostage to each provider's discipline in mapping foreign errors to a `Transient` `LlmError`. Recovery here is explicit, never transparent — a plain `catch` arm does *not* auto-unwrap the box (it tests `u` itself, and the box is a `baml.UnknownError`, not a `CallError`), so a boxed transient is reachable only by a combinator that already knows to `from<CallError>(u)` for it. Those aren't fatal — the additions are mechanical and the unsafe combinations are documentable — but they are real holes the proposal must own rather than wave at.
