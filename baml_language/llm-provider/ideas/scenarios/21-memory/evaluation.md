# Evaluation — Memory (cross-conversation, long-term)

Adversarial read of how the Providers/Clients/Capabilities proposal holds up when asked to express cross-conversation memory: mem0's implicit curation, Letta's self-editing core blocks, the Anthropic memory-tool the model drives, and the three-independent-things (Session / Memory / Working-core) distinction.

The single most important finding up front: **Memory is not a Provider.** A `Provider` produces a typed answer from a prompt; a memory layer stores and recalls facts. The proposal's spine does not give us memory — we had to introduce a brand-new `MemoryStore` interface. What the proposal *does* give us is the machinery to wire memory into a call cleanly, and a clean home for the LLMs a memory layer consumes (the extractor/decider are just `Provider`s). So the proposal is reused as *substrate*, not as the memory model itself.

## (a) What the proposal reuses unchanged

- **`Provider` as a consumed dependency.** `Mem0` holds `extractor: Provider` and `decider: Provider` and runs the extract→decide pipeline as two ordinary `.call<T>` invocations (`call<string[]>`, `call<MemoryDecision>`). This is the cleanest win: the four-stage pipeline is just typed provider calls, and you can point extraction at a cheap model and decision at a careful one without any new concept. Open Question 1 ("does every capability require Provider?") is irrelevant here — we only need the base.
- **The combinator pattern for the middleware posture.** `WithMemory` is a plain non-generic class that `implements Provider` and delegates to `inner`, exactly like the spine's `Cache`/`Retry`. retrieve-before/store-after fits the `.call` override with zero new capability interface. It drops into the `client:` slot and chains with `.with_retry().fallback_to(...)` for free (§6).
- **The `Tools` capability, completely unchanged, for both tool postures.** The mem0 `search_memory` tool, the Anthropic memory-tool filesystem, and Letta's self-editing `core_memory_*` tools are all just entries in the `tools` array with a dispatch handler. `begin/step/submit`/`run_tools` and the `ToolCall`/`ToolResult` seam (id-opaque) are reused verbatim — the only new code is the handler bodies. Letta's celebrated "self-editing loop" turns out to be the canonical Tools loop whose handlers mutate a `CoreMemory`.
- **`client` = function sugar.** `CuratedMemory()`/`RawMemory()`/`Disk()` are ordinary functions returning interfaces; swapping mem0 for the raw store is a one-line factory change because both `implements MemoryStore`. Dynamic per-tenant scope is just a function argument.
- **`throws`/`catch`** for best-effort writes (store-after must not fail the turn) and `match` over an enum (`MemoryOp`) for the persist step.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface MemoryStore` (+ `Scope`, `Memory`, `MemoryOp`, `MemoryDecision`, `Turn`).** This is the core net-new abstraction and it does **not** reduce to `Provider`. It is its own interface with `search`/`add`/`put`/`get_all`. Tied to: nothing in the spine — the spine has no notion of a fact store. This is the honest cost: the proposal's "everything is a Provider" does not extend to memory; memory is a *sibling* abstraction that consumes providers.
2. **`interface VectorStore` + a host bridge (`Qdrant`).** The disk. Pure `$rust_io_function` bodies, the `PrimitiveClient` pattern — directly validating **Open Question 7** ("is an `implements` block with native bodies the supported bridge boundary?"). Here it is load-bearing twice over (vector ops *and* embedding).
3. **Host primitives to manipulate the opaque `PromptAst` from the middleware.** The middleware posture needs to (a) read the user's last message to use as a search query and (b) splice retrieved facts into the system position:
   - `baml.llm.last_user_text(prompt) -> string`
   - `baml.llm.with_system_suffix(prompt, text) -> PromptAst`
   - `baml.llm.text_of<T>(value) -> string` (turn the answer into a `Turn` for store-after). Tied to: the `call<T>(prompt: PromptAst)` signature. Because the base method only sees an *opaque* `PromptAst`, any middleware that wants to read or rewrite the messages must go through new host accessors. This is the proposal's seam showing a real cost (see (c)).
4. **`ExecutionContext.with_handlers([...])`** to bind a `Tool` descriptor to a handler closure for dispatch. The proposal's §7 net-new note already says `ExecutionContext` needs `dispatch`; the memory tools need the *registration* side of that, which isn't spelled out.
5. **`LettaProxy`** — a `Provider` that proxies a server-authoritative agent. Net-new only as a class; it reuses the base. But it exposes a gap (see (c)).

## (c) Where it is awkward, leaky, or unresolved

- **The middleware posture leaks through the opaque `PromptAst`.** `Provider.call` takes `prompt: baml.llm.PromptAst` and nothing else. A memory middleware fundamentally needs *structured* access to the conversation: which turn is the user's latest (the search query), and where the system prompt is (the injection point). The proposal models the prompt as an opaque blob (`class PromptAst { _data }`), so we are forced to invent `last_user_text` and `with_system_suffix` host primitives. These are real, and they are exactly the kind of "request side" questions **Open Question 3** raises ("the request side is HTTP-specific... does the request side also want an associated type?") — except here the problem is one level up: it's not transport, it's *semantic structure of the prompt*. The proposal has no typed view of messages, so prompt-rewriting middleware (memory, but also compaction and few-shot injection) all bottom out in host functions. That is workable but it means a whole class of middleware is un-typed BAML over an opaque AST.
- **Cache interaction is unaddressed and the proposal makes it worse.** The background flags that injecting memories into the system prompt breaks prefix caches. In this model, `WithMemory` sits *outside* `Cache` (or inside — unspecified), and because `with_system_suffix` changes the prefix every turn, the spine's `cached(store)` combinator would key on a constantly-changing prompt. Nothing in the proposal lets a combinator say "cache on everything except the injected memory block." Ordering of `with_memory().cached()` vs `cached().with_memory()` matters and is silent.
- **`store-after` has no honest place to run in the streaming/tools paths.** The `WithMemory.call` override does retrieve-before and store-after around one `.call`. But if the app uses `.stream` or `.run_tools`, those companions `match` on `Streaming`/`Tools` of the *inner* provider — they bypass `WithMemory.call` entirely unless `WithMemory` also `implements Streaming`/`Tools` and re-wraps each. The combinator-forwarding rule (§6) says a combinator *claims* every capability it forwards, but a memory middleware that forwards `.stream` would have to re-implement retrieve/store around the stream — and store-after on a stream means draining it first. This is genuinely awkward and the proposal's "degrade to .call" fallback doesn't help, because memory must run on *every* path, not just `.call`.
- **Server-authoritative state (Letta) cannot be modeled, only proxied.** Letta's agent is a stateful object on a server with three memory tiers the *server* owns. The proposal can host it only as `LettaProxy implements Provider` whose `.call` is a `$rust_io_function` POST. The memory is then invisible to BAML — there is no BAML `MemoryStore` for it, no typed `search`, no `Scope`. The proposal is honest about this kind of thing (a harness is "a Provider with no HTTP", §8) and Letta is the same: a Provider with no inspectable memory. But it means "memory" as a first-class BAML concept and "Letta" are mutually exclusive — you get one or the other, never Letta's tiers expressed in BAML. **This is a plain limitation, not a workaround.**
- **No compile-time guarantee that a client even has memory.** Per §5, `client` returns the existential `Provider`, so "is memory wired in?" is invisible to the type checker. `with_memory(Assistant(), ...)` returns `WithMemory`, but the moment it enters a `client:` slot it widens to `Provider`. There is no type that says "this function recalls user facts." For a safety-relevant property (did we actually scope to the right user before answering?) that is uncomfortable; the only recourse is the escape-hatch longhand `function ... -> WithMemory`.
- **Three-independent-things is expressible but not enforced.** Session / Memory / Working-core come out as three different code shapes (a `MemoryStore`, a prompt-injected `CoreMemory`, and — out of scope here — a session log). The model does not *unify* them, which is arguably correct (the background says they *should* be independent). But nothing stops an app from conflating them, and ADK's prefix-scope blur (`user:`/`temp:`) has no natural home: it would be a `Scope`-like discriminator inside a single store, which we didn't model.

## (d) Verdict: **Workable-with-additions**

The proposal is not the memory model — `MemoryStore`/`VectorStore` are net-new abstractions it cannot derive from `Provider`, and that is the correct shape (memory genuinely is a different thing). Where the proposal shines is as *substrate*: the curation LLMs are plain `Provider`s, the tool postures (mem0 recall tool, Anthropic memory-tool filesystem, Letta self-editing) are the canonical `Tools` loop with new handlers and nothing else, and the middleware posture is a textbook combinator. The two real costs are (1) the opaque `PromptAst` forces every prompt-rewriting middleware — memory included — into host primitives, with an unaddressed cache-prefix interaction, and (2) server-authoritative memory (Letta) can only be proxied as an opaque `Provider`, so its tiered memory model is inexpressible in BAML. Neither is fatal; both are honest limitations. Add the `PromptAst` accessors and `MemoryStore` interface and the everyday mem0/raw/Anthropic-tool cases are clean; the Letta tier model and the streaming/tools store-after paths remain awkward.
