# Evaluation — 05 · Multimodal input

Adversarial read: does the proposed `Provider` / `HttpProvider` model actually absorb the three media encodings, the supportedUrls-style pre-fetch/pre-upload negotiation, and the per-media capability gaps (audio ≠ Anthropic, video = Gemini-only)? Mostly yes — but the negotiation logic forced a *new capability interface*, and the gaps land as **runtime throws, never compile-time guarantees**.

## (a) What the proposal reuses unchanged

- **The base seam is exactly right.** Multimodality is *not* a new interaction shape — it is the per-provider serialization of media that already rides inside `baml.llm.PromptAst`. So nothing about `HttpProvider.call<T>` or the `.stream`/`.live` companions changes. (Under the marker revision — `provider-as-marker.md` — `call`/`call_with` live on `HttpProvider`, not on the bare `Provider` marker; multimodal serialization never touches that move because it lives one level down, in `build_request`.) The whole scenario lives inside one method, `HttpProvider.build_request` (proposal §2), which is precisely the seam the proposal says "captures the wire divergences." Image-as-`image_url` vs image-as-`source.base64` vs `inline_data` is the same kind of divergence as the four structured-output encodings — and it lands in the same place.
- **Per-provider fields, no options blob (§4).** `Anthropic.max_tokens` is a bare field; there is no `provider_options` union and no `@providers:` map carrying "does this model do video." The capability lives in code (`accepts`), not in an annotation map.
- **Combinators wrap, unchanged (§6).** `ImageReader = GPT4().fallback_to(Flash())` and `Flash().with_retry(2).cached(store)` compose with zero media-awareness. `TranscribeFirst` is "just another `Provider`-wrapping combinator," validating that the degrade path is expressible at the combinator layer rather than inside a model. Under the marker revision it `requires Provider` (for the inherited factories) and `implements HttpProvider` (the request/response shape it forwards): it rewrites the prompt then routes `call_with` to `inner`'s `call_with`, so the inner chat completion's `ResponseMeta` (usage/cost) reaches the projection instead of being dropped — the P1 fix applied to the combinator.
- **`throws`/`catch` is the gap channel.** `resolve` throwing `baml.errors.Unsupported` and the app `catch`ing it (usage §3/§4) is the same machinery everything else uses. Under the new error model every fallible method here declares one channel — `baml.ExtendUnknownError<baml.errors.CallError>` — because media resolution runs *entirely on the call path* (`build_request` → `resolve` → `upload`). There is no per-provider `type Error`; the old `baml.errors.LlmClient` is gone. `baml.errors.Unsupported` (the hard-gap throw) now `implements` all four capability-error interfaces, so it is legal on the `CallError` channel and is still caught by its concrete type. Deliberate transport-negotiation failures became a concrete `MediaTransportError implements baml.errors.CallError` (all three classifiers false — it is neither network, rate-limit, nor parse); foreign `Io`/host-upload failures are normalized by a trailing `} catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CallError>(e, "…") }` instead of being flattened into a generic `LlmClient { message: "http failed" }`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.media.*` host functions** — `view(prompt) -> PromptView`, `download` (Url→Bytes pre-fetch), `to_data_url` / `to_base64` / `to_base64_bytes` (re-framing between the three inline encodings), `guess_mime`, `audio_format`. *Tied to:* `baml.llm.PromptAst` gaining a readable media view, and a small `baml.media` namespace beside `baml.http`. The proposal already names `baml.media.image_from_base64` in §2, so the namespace is half-assumed — but the *reader* (`view`) and the *converters* are genuinely new host primitives.
2. **`MediaRef` / `MediaTransport` / `MediaKind` / `PromptView` view types.** *Tied to:* the opaque `PromptAst`. These are the value-level shape `build_request` walks; without them every provider re-reaches into `_data: $rust_type` by hand.
3. **The `MediaIngest` capability interface** — `accepts(kind, transport) -> bool`, `upload`, and the default `resolve` engine. *Tied to:* the "capability is an interface that `requires Provider`" rule. This is the supportedUrls map made into a method, plus the forward/pre-fetch/pre-upload state machine the Vercel SDK hand-rolls per call. It is the single biggest add, and it is genuinely net-new: nothing in the spine knows about media. **Notably it did NOT need a new `baml.errors.<Cap>Error` interface:** even though `MediaIngest` is a capability interface, its failures all surface *on the call path* (inside `build_request`), so `resolve`/`upload` declare the existing `baml.ExtendUnknownError<baml.errors.CallError>` channel. Media ingestion is a new *capability* but not a new *failure mode* — the right call here, but see §c for the tension this papers over.
4. **`MediaTransportError` concrete error (NET-NEW).** A class `implements baml.errors.CallError` (all three classifiers false) for the deliberate transport-negotiation throws ("no acceptable transport for inline bytes", "handle not portable"). *Tied to:* rule 2 — a deliberate domain throw must `implement` the capability interface. It is the typed replacement for the old `throw baml.errors.LlmClient { message: ... }` and is what lets the app branch on "couldn't encode this media" vs. a model refusal vs. a network blip.

## (c) Where it is awkward, leaky, or unresolved

- **The capability gaps are runtime-only — engages Open Question #5 directly.** There is no way to make "this client accepts audio" part of the type. `TranscribeNotesClaude(clip)` *compiles* and throws at `build_request` time. The proposal embraces this (capability is a runtime promise because `client` returns the existential `Provider`), and the escape hatch — "drop the sugar, return a concrete type" — does **not help here**, because the gap is not at the capability-interface granularity. Both Anthropic and Gemini *are* `MediaIngest`; the difference is `accepts(audio, _)`, a value, not a type. So even the longhand `function … -> Gemini` escape hatch can't encode "audio-capable" as a property the checker enforces across providers. **Plainly: a compile-time "this client can take audio" guarantee is not expressible in this model.** That is the honest cost.
- **`resolve` is a default method that recurses and re-`match`es `self` — engages #5 again.** The `handle` arm does `match (self) { let mi: MediaIngest => … }` *inside* a `MediaIngest` default method, purely to read `self.provider_id()`/`self.accepts(...)`. That is circular and only works if value-level reflection lets an interface default method match `self` against its own interface (or, better, call sibling methods directly — `self.accepts(...)` already assumes this). It leans hard on #5's "confirm `match (provider) { let s: Streaming => … }` works at runtime," and additionally on *default methods being able to call peer methods on `self`*, which the `Iterator` precedent supports but is worth confirming for this recursive shape.
- **Handles aren't portable, and the type system can't see that.** A `MediaRef.handle` minted by Gemini is meaningless to OpenAI. We guard it with a `handle_provider` string compared to `provider_id()` — a stringly-typed runtime check. A `Fallback` over `[GPT4(), Flash()]` that receives a pre-uploaded Gemini handle will (correctly) fail OpenAI and fall through to Gemini, but only by *re-uploading* logic we did not write here; cross-provider handle reuse is a sharp edge the model surfaces but does not solve.
- **Pre-fetch/pre-upload is invisible cost.** `resolve` may silently `download` a 200MB video or `upload` to a Files API — real I/O and latency hidden behind a field-read-looking `build_request`. The proposal's "transport envelope lives at the combinator layer" (§4) means there is no natural place to put an upload *budget* or *cache*; you'd need yet another combinator (or to thread `ExecutionContext`, cf. Open Question on §7's `ExecutionContext`).
- **The error model flattens two unlike failures onto one channel — engages rule 1 honestly.** `MediaTransportError` ("I can't *encode* this media for this wire") and a model `Refused` / an HTTP 429 / a torn socket all ride the *same* `baml.errors.CallError` channel, and the three classifiers (`is_network_error` / `is_rate_limit` / `is_parse_error`) say *false* for all of `MediaTransportError`, `baml.errors.Unsupported`, and a refusal alike. So a caller holding only the interface (the common case — `client` returns the existential `Provider`) genuinely cannot tell "you handed me audio Anthropic can't take" apart from "the model declined" apart from "this PDF's bytes had no acceptable transport" without down-matching to each concrete class. The classifier vocabulary is transport-shaped (network/rate-limit/parse); a *media-encoding* failure has no classifier of its own, so it is only distinguishable by concrete type. That is arguably correct — these really are app-branch-by-concrete-type cases — but it means the "triage without knowing the concrete class" promise of the capability interface buys *nothing* for the failures this scenario actually introduces. A `is_unsupported()` / `is_media_error()` classifier would have helped; adding one to `baml.errors.CallError` to serve one capability would bloat the universal interface. The honest read: this scenario's distinctive errors are caught by concrete match or not usefully at all.
- **Combinators silently re-widen the channel they forward.** `TranscribeFirst.call` and the spine's `Fallback`/`Retry`/`Cache` all declare `baml.ExtendUnknownError<baml.errors.CallError>`. When `Fallback` over `[GPT4(), Flash()]` receives a Gemini-minted handle, OpenAI's `resolve` throws `MediaTransportError`; because that is a known `CallError`, the trailing `with_message` catch passes it through *unannotated*, and `Fallback` then tries the next member — exactly right. But `TranscribeFirst` calls `self.stt.call<string>(...)` to transcribe, and *that* call's errors (a network blip in the STT provider) surface on the *same* `CallError` channel as the outer model's errors with no breadcrumb distinguishing "STT failed" from "the chat model failed" unless the STT path is wrapped in its own annotating catch — which the current body does not do. The new model makes this composable (one flat channel) but also makes it easy to lose *which* sub-call failed.

- **Brushes Open Question #4.** `parse`'s `Body` widening is reused as-is for *input* media, but #4 is about the response `Body`; the *request* side has no associated type, and media resolution is bolted onto `build_request`'s body string. #3 ("the request side is HTTP-specific") bites mildly: a non-HTTP multimodal provider (a harness that takes images) would have to re-implement `resolve` against its own transport, since `MediaIngest`'s default only assumes `accepts`/`upload`, not HTTP — which is actually fine, but means `MediaIngest` must stay HTTP-agnostic (it does).

## (d) Verdict

**Workable-with-additions.** The proposal's core claim holds: multimodal input is just per-provider encoding inside `build_request`, the base `Provider` and the combinators need zero changes, and the audio/video gaps fall out as honest runtime throws on a capability the provider declares in data (`accepts`). The cost is one real new capability interface (`MediaIngest` with the `resolve` negotiation engine) plus a `baml.media` host surface — both defensible and both built *on* the spine rather than against it. The unavoidable blemish is the one the proposal already owns: capability is a runtime promise, and here it is *sub*-interface (per media kind), so not even the concrete-return escape hatch buys a compile-time "audio-capable" guarantee. For a feature whose whole difficulty is "which provider accepts what, in which encoding," pushing that into a `match`/`accepts` runtime check is the right altitude — but call it what it is: detected, not typed.
