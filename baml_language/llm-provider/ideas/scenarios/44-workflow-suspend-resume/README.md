# Suspend / resume & human-in-the-loop

A workflow is a function that can pause, persist itself, and resume later — possibly in a different process, after a redeploy, days later. This scenario models that on the Provider/capability spine: suspension is a new capability `Suspendable requires Provider` whose `start<T> -> T | Suspend` / `reenter<T> -> T | Suspend` mirror `Iterator.next`; the live run state crosses the wait as an opaque, serializable `Snapshot` (the `$rust_type` twin of `Transcript`/`PromptAst`); human-in-the-loop approval is an `ApprovalGate` combinator that rewrites a gated `ToolCall` into a `Suspend`; and a `Durable` combinator persists snapshots through a `RunStore`, detecting schema drift on resume and enforcing exactly-once via an atomic `claim`. Read `implement.baml` for the library/host code, `usage.baml` for the app author's two-line clients and start/resume handlers, and `evaluation.md` for where it leaks (suspend is not a refinement of `call`; you must drop the `client` sugar to reach resume; drift is detected, not migrated; exactly-once lives in the host).
