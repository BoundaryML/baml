# Evaluation — Suspend / resume & human-in-the-loop

Adversarial read of whether the Provider/capability model expresses a *suspendable workflow* (pause → persist → resume, possibly across a process restart and a redeploy) without inventing a parallel runtime.

## (a) What the proposal reuses unchanged

- **The capability pattern itself.** `Suspendable requires Provider` is just another capability interface in the §1 sense — it layers on `HttpProvider`/`Tools` exactly as `Streaming` does. No new mechanism: a provider gets it by adding an `implements` block. `Anthropic`, `ClaudeCode`, and the combinators all wear it the same way.
- **The `T | Sentinel` union shape.** `start<T> -> T | Suspend` and `reenter<T> -> T | Suspend` are the literal `Iterator.next -> Item | Done` shape the spine already leans on for `Tools.step<T> -> T | ToolCalls`. The driving loop in `ApprovalGate.drive` is the `run_tools` loop with one extra `match` arm.
- **Opaque host-owned state.** `Snapshot { _state: $rust_type }` reuses the `PromptAst { _data: $rust_type }` / `Transcript` discipline verbatim. The "no closures/sockets/streams" rule from the background is enforced where it has to be — inside `freeze`, a host body — not in the type system.
- **Combinators wrap a Provider.** `Durable` and `ApprovalGate` are plain non-generic classes wrapping an `inner`, returning a `Provider`, composing by delegation — the §6 combinator template. `RefundDesk()` is `Durable { inner: ApprovalGate { inner: Anthropic{...} } }`, a three-layer chain that reads like `GPT4().with_retry(2)`.
- **`throws`/`catch` and the first-class `type`.** Resume validation rides `Suspend.resume_schema: type` (same as `Tool.parameters: type`); persistence errors ride the per-capability `baml.ExtendUnknownError<…>` channel — the store's foreign `baml.errors.Io` is normalized into a `SuspendError` by a trailing `catch (e) { _ => throw baml.UnknownError.with_message<…>(e, …) }`, exactly the spine's normalization pattern.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Suspendable` capability** (interface `requires Provider`). New, but *in-pattern* — this is the §1 extension point doing its job. Cost: it is a fourth interaction shape alongside `call`/`stream`/`run`, so every combinator that wants to be transparent to suspension must add an `implements Suspendable` block (Durable, ApprovalGate do; a bare `Fallback` does not, and would swallow suspendability silently — see (c)).
- **`Suspend` as a value on the result union, not the error channel.** The background's "suspend()" is control flow, not failure. We model it as the right side of `T | Suspend` rather than `throw`, because catching control flow on the `throws` channel would collide with genuine `SuspendError`s (store failures, drift, an unfreezable continuation). This is a genuine design commitment the proposal does not currently make (it has no notion of a non-error early return). **Net-new.**

- **A new capability error interface: `baml.errors.SuspendError`.** Suspend/resume is a capability beyond `call`/`stream`/`realtime`/`tools`, so per the error model's "any NEW capability" row it gets its own interface (`is_network_error` / `is_drift` / `is_unfreezable`), and `start`/`reenter`/`freeze` plus `Durable.start_run`/`resume_run` all declare `baml.ExtendUnknownError<baml.errors.SuspendError>`. The concrete domain failures become typed classes: `SchemaDrift` (drift gate) and `Unfreezable` (non-serializable continuation). Both ride the `SuspendError` channel that the suspend surface declares — there is no longer a `SuspendedOnPlainCall` straddling the `CallError` channel, because under the marker revision `Durable` exposes no degenerate `call` to park (its real surface is `start_run`/`resume_run`). **Net-new error interface the proposal must add.**
- **`Snapshot` + `RunStore` + `RunHandle` host primitives.** `_state: $rust_type` is in-pattern, but the *contract* — "serializable, version-stamped, plain-data-only" — is a new host guarantee. `RunStore.claim` (compare-and-set) is a **new host primitive**: nothing in the spine does atomic exactly-once. This is the real weight of the scenario and it lives entirely below BAML.
- **`Durable.start_run` / `resume_run` statics.** The plain `client → -> Provider` sugar only yields `.call`/`.stream`/`.live` companions. Suspend/resume need a *run id* threaded across two process invocations, which no companion carries. So the app drops the sugar and calls concrete statics on the `Durable` provider (`let d: Durable = RefundDesk(); d.resume_run<T>(...)`). **Net-new ergonomic seam.**
- **`ApprovalGate` (Pydantic AI's `requires_approval`).** A Tools-layer combinator that rewrites a gated `ToolCall` into a `Suspend`. New, but composed entirely from the existing `Tools` seam (`begin`/`step`/`submit`) — no new provider hook.

## (c) Where it is awkward, leaky, or unresolved

- **Suspend rides a result union — and under the marker revision it no longer has to fake a `call` (OQ #1 resolved).** `Suspendable` owns its own `start<T> -> T | Suspend` / `reenter<T> -> T | Suspend`, and because `Provider` is now a bare *marker* with no base `call`, suspension is *not* obligated to be a refinement of `call` — it is simply a different interaction shape, exactly as the per-capability marker model intends. The old worry was that `Durable` had to carry a degenerate `Provider.call` that ran to completion and threw `SuspendedOnPlainCall` when the run parked, so a `Fallback` forwarding `.call` could turn a legitimate suspend into a thrown `CallError` and silently lose the run. That degenerate path is **gone**: `Durable`/`ApprovalGate`/`ClaudeCode` expose no `call` at all (they `implements Suspendable` and are Providers only via the marker). There is no `CallError`-shaped hole for a suspend to fall into, and nothing for a `Fallback`'s `.call` route to mis-degrade. The residual is milder and honest: a combinator that wants to be *transparent to suspension* must `implements Suspendable` and forward `start`/`reenter`/`freeze` (Durable, ApprovalGate do); a bare `Fallback` that only forwards `HttpProvider`/`Streaming` simply is **not** Suspendable, and a companion that needs suspension `match`es for `Suspendable` and errors with `Unsupported` if absent — the ordinary capability-negotiation story, not a silent type-checked loss.

- **No compile-time guarantee that a client is resumable (OQ #5).** `RefundDesk()` is written longhand (`-> Durable`) precisely because the `client` existential `Provider` would erase `Suspendable`, and the app must reach `start_run`/`resume_run`. So the proposal's own escape hatch ("drop the sugar for compile-time precision") is *forced*, not optional, the moment you want suspend/resume. The clean `client` ergonomic does not reach this scenario. OQ #5 (runtime membership `match`) doesn't even help: a UI that gets back an existential `Provider` cannot statically know `resume_run` exists.

- **Schema drift is detected, not solved (background "what's hard").** `Durable.resume_run` compares `snap.version != self.build_version` and *refuses* a mismatched resume. That is honest but blunt: a Monday run simply fails to resume on a Friday deploy. The proposal offers no migration hook — there is no `migrate(old_snap) -> new_snap` seam, because `Snapshot._state` is opaque and only the host can read it. Versioned workflow definitions (the background's "genuine migration problem") are entirely out of model; we can only fail loudly.

- **Exactly-once lives below the abstraction, not in it.** `RunStore.claim` is where double-click / two-replica safety actually happens, and it is a `$rust_io_function` host primitive doing a compare-and-set. The BAML layer can *call* it but cannot *guarantee* it; the proposal contributes the orchestration shape (claim → reenter → release) but none of the durability. This is correct division of labor, but it means "exactly-once resume" is a claim about the host, not about the model.

- **`freeze` can refuse, and the type system can't see it (OQ #7).** The background's hardest constraint — no live sockets/streams in the snapshot — is enforced by `freeze` *throwing* at runtime when `ClaudeCode`'s subprocess is unrecoverable. OQ #7 asks whether an `implements` block with native bodies is the supported bridge; this scenario leans on it hard (every `Suspendable` body except the combinator glue is `$rust_io_function`) and additionally needs those native bodies to *reject* certain states. Nothing in the interface signals "this provider may be unfreezable."

- **The harness leaks the most.** `Anthropic`'s suspend is clean (re-hydrate a frozen transcript). `ClaudeCode`'s suspend is a lie we paper over: a subprocess + socket cannot be snapshotted, so `freeze` persists only a session id + replayable cwd and `reenter` *re-spawns*. The capability ports syntactically (both `implements Suspendable`), but the semantics diverge sharply — and the model gives the app author no signal that one is durable-across-restart and the other is best-effort-reattach.

- **The new error model surfaces a channel-crossing question — answered by a coverage convention, not a wall (NEW).** Inside `Suspendable`/`Durable`, BAML code calls *down* into three different capability channels: `inner.begin`/`step`/`submit` throw `ToolError`, the store throws foreign `baml.errors.Io`, and `inner.start`/`reenter`/`freeze` throw `SuspendError`. The method's own declared channel is `SuspendError`, so the question is whether a `ToolError` raised mid-loop boxes into `baml.UnknownError`. It boxes **only if it does not implement `SuspendError`** — and that is the `SuspendError` author's call, not a structural fact. Because BAML `implements` is a Rust-like trait relation that admits **external impls in both directions**, the *workflow package* (which owns `SuspendError`) declares, alongside the channel, `implements baml.errors.SuspendError for baml.errors.ToolError` (and `…for baml.errors.CallError`) — local trait, foreign type, allowed under coherence. Now a down-stack `ToolError`/`CallError` rides the `SuspendError` channel as its **typed self**, caught concretely by `let t: baml.errors.ToolError =>`, **no box**, classifiers intact. There is no "forward-reference wall": `SuspendError` retro-admits the upstream error types it wants to flow through, even though those types predate it. So keeping the crossing typed is a **coverage convention** the channel author follows when defining the channel — not an irreducible cost. Where the author *omits* the row, the crossing boxes into `baml.UnknownError`, but the data is not destroyed: `UnknownError.data` holds the original untouched, and re-asserting `from<ToolError>(e)` pulls the *same* concrete error back out (and because `with_message` annotates the existing `UnknownError` in place rather than re-wrapping, a single re-assertion recovers it however many channels it crossed). The residual is narrow and twofold: (i) nothing *forces* the `implements` row — a forgotten one is an unenforced-convention gap (the crossing boxes, recoverable via an explicit `from<…>` probe), and (ii) a *genuinely foreign* value (a host panic in the store, unmapped JSON) has no inner typed error, so the `baml.UnknownError` escape hatch is doing exactly its job there. The recovery, *when* a crossing does box, is **explicit, never transparent** (settled, not an open question): a plain `catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a box *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it — to reach the inner error the author must explicitly `baml.UnknownError.from<…>(e)` inside the `UnknownError` arm. So the honest cost is not "the provenance survives but the static story is lost" — with the `implements` rows in place the static channel *does* carry the inner errors typed; the only standing weakness is that the rows are by convention rather than forced, plus the genuinely-foreign value for which boxing is correct.

- **`Unsupported` on the `SuspendError` channel is one external `implements` row — cheap, but unenforced.** The canonical `baml.errors.Unsupported` implements the four *core* interfaces but not the net-new `SuspendError`, so out of the box a combinator that wants to negotiate "this provider isn't Suspendable" cannot throw `Unsupported` on the `SuspendError` channel. But this is **not** a structural gap and does **not** force `Unsupported` to "know about every capability ever added": because BAML `implements` is a Rust-like trait relation admitting *external* impls (implement *your* interface for a parent-package type), the **`SuspendError` author** writes one row alongside the channel — `implements baml.errors.SuspendError for baml.errors.Unsupported` — and now `Unsupported` is legal on the `SuspendError` channel, caught concretely. No reaching back to widen the universal error, no per-capability sentinel. The only residual is that nothing *forces* the row: a net-new channel that forgets it gets a type error at the first `_` arm that throws `Unsupported`, not a silent gap — and a blanket `implements <Cap>Error for baml.errors.Unsupported` shipped with every capability template closes it by construction.

## (d) Verdict: **Workable-with-additions**

The capability pattern absorbs the *structure* of suspend/resume gracefully: `Suspendable requires Provider`, the `T | Suspend` union mirrors `Iterator.next`, `Snapshot` reuses the opaque-`$rust_type` discipline, and `Durable`/`ApprovalGate` are ordinary combinators. Human-in-the-loop approval falls out as a Tools-layer rewrite of a `ToolCall` into a `Suspend`, which is genuinely elegant. Under the marker revision suspension fits the spine cleanly *as its own interaction shape*: `Provider` is a marker, `Suspendable` owns `start`/`reenter`/`freeze`, and none of `Durable`/`ApprovalGate`/`ClaudeCode` is forced to fake a degenerate `call` (OQ #1 resolved — there is no base `call` to refine or dishonor). But it is *not* fully clean: two real additions are still forced — a non-error early-return on the result union (`T | Suspend`, which the spine had no notion of), a `RunStore.claim` host primitive for exactly-once — plus an abandonment of the `client` sugar (you must drop to a concrete `-> Durable` to reach `start_run`/`resume_run`, OQ #5). The genuinely hard problems the background names — schema drift across a redeploy and server-authoritative exactly-once state — are pushed below the BAML boundary into the host: the model can *detect and refuse* drift but cannot *migrate*, and it can *orchestrate* exactly-once but cannot *guarantee* it. That is the correct boundary, but it means the proposal expresses the control flow of a suspendable workflow, not its durability.
