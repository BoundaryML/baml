# Evaluation — Constrained decoding beyond JSON Schema

Adversarial read of whether the proposed model (`Provider` *marker* + `requires Provider` capabilities + `client`-as-function sugar) actually expresses token-level constrained decoding, and where it leaks. Under the marker revision ([`../../provider-as-marker.md`](../../provider-as-marker.md)) `Provider` carries no interaction method: request/response `call`/`call_with` live on `HttpProvider`, and `Constrained.decode` is just another capability you `match` for — exactly the framing this scenario already used.

## (a) What the proposal reuses unchanged

- **The capability-as-interface pattern.** `Constrained requires Provider` is a verbatim copy of how `Streaming` / `Realtime` / `Tools` are added. No new mechanism; a new capability is just a new interface. This is the single biggest win — the two-tier split (hosted vs self-hosted) is expressed *purely* as "some classes implement `Constrained`, some don't", with zero new language surface.
- **Capability negotiation = runtime `match`** (§5). `Classify$decode` matches the client's provider against `Constrained` and errors on the `_` arm. Identical to the `.live` companion shape. "Where it runs is a property of the provider class" falls out of this for free: a hosted client simply misses the `match`.
- **`client` as config-only sugar** (§3). `client LocalLlama() { VLLM { base_url: ... } }` is one line; `base_url` / `device` / `model_id` are ordinary provider fields — exactly the "options dissolve into provider fields" rule (§4). `where it runs` (localhost:8000, in-process cuda) is a field, not a special construct.
- **Combinators wrap a Provider** (§6). `ConstrainedFallback` is a plain non-generic class that forwards by runtime delegation and statically claims `Constrained`, degrading at call time — the same tradeoff the proposal already accepts for `Fallback`. Its unconstrained-degrade path is `HttpProvider` (not the old base `call`): `call_with` `match`es members for the first `HttpProvider` and forwards the `project` closure, so usage/cost survives the degrade (the P1 fix) instead of being dropped; `call` derives from it.
- **The HTTP codec + SAP** (§2). vLLM and llama.cpp reuse `HttpProvider` for the *unconstrained* path and `baml.sap.parse` for the `JsonShape` tier. `Outlines` shows the other face of `HttpProvider`: "request/response" is the capability, not "speaks HTTP". It implements `HttpProvider` by supplying `call`/`call_with` *directly* (overriding the `build_request/send/parse` defaults) over an in-process `$rust_io_function` — no HTTP underneath at all. So even an in-process value-returning provider owns the request/response capability rather than faking a base `call`.
- **The first-class `type` primitive.** `JsonShape { schema_of: type }` reuses `type` + `reflect`, exactly as `Tool { parameters: type }` does in §7.

## (b) Net-new surface it must add (each tied to a primitive)

- **`interface Constrained requires Provider`** with `decode<T>(prompt, constraint)`. New capability interface. Tied to the §1 capability mechanism. Crucially it has **no default method** — unlike `Streaming` (degrades to buffered `.call`) and `Inspectable`, a constraint guarantee cannot be synthesized on top of an unconstrained `.call`, so the base cannot supply one. This asymmetry is new relative to every capability in the proposal so far, all of which either degrade or are pure additions.
- **The `Constraint` union** (`Choice | Regex | Grammar | JsonShape`) + `Unsatisfiable`. New data types. `Constraint` is a *parameter of the capability method*, like `io: Channel` on `Realtime.run` (§3) — it is not a provider field and not a client param. This is the right home and reuses the precedent, but it is genuinely new vocabulary.
- **`interface baml.errors.ConstraintError` — a NET-NEW capability-error interface.** Constrained decoding is the first capability in this folder that is *not* one of call/stream/realtime/tools, so under the per-capability error model it must carry its own error channel: `decode` declares `throws baml.ExtendUnknownError<baml.errors.ConstraintError>`. Its classifiers diverge from `CallError`: alongside `is_network_error`, the load-bearing one is `is_unsatisfiable` (was this constraint *impossible to honor on this backend* — dialect miss, regex-on-llama.cpp, hosted-can't-do-Choice — as distinct from a transport failure). `Unsatisfiable` is now a concrete error `implements baml.errors.ConstraintError` (not a bare struct), so the negotiation `match`-miss and the per-constraint refusal both land as typed values on the same channel the app already triages. The per-provider deliberate throws (`vLLM guided_grammar dialect`, `llama.cpp regex`, `Outlines CFG dialect`) all collapse onto this one `Unsatisfiable` type; foreign transport/host failures route through `baml.UnknownError.with_message<baml.errors.ConstraintError>` in each `decode`'s trailing catch. `cast_exact` — the non-SAP strict decode — also rides the `ConstraintError` channel (a cast failure on an already-guaranteed string is a constraint-engine inconsistency, normalized to `UnknownError`, not a `CallError`).
- **`json_schema_of(type) -> string`** and **`cast_exact<T>(string) -> T`** host primitives. `json_schema_of` likely already exists internally (it powers `response_format`); the proposal's Open Question 6 (expose SAP publicly) extends naturally to "expose the schema-lowering too." `cast_exact` is genuinely new: it is the *non*-SAP decode — the string is already exact, so we want a strict cast, not schema-aligned repair. The proposal only ever names one parse mechanism (SAP); constrained decoding needs a second.
- **`gbnf_from_choice` / `gbnf_from_json_schema` host helpers.** The llama.cpp lowering. These are provider-internal divergence-absorbers, the constrained analog of the "four wire encodings of one schema" in §2.
- **`ConstrainedFallback` combinator + `or_else_hosted` default method.** New combinator class and a new `Provider` default method, following the §6 `with_retry`/`fallback_to` template.

## (c) Where it is awkward, leaky, or unresolved

**The runtime-promise hole is sharper here than anywhere else in the proposal (the "capability is a runtime promise" admission).** The marker revision makes *every* interaction a runtime `match` (even the basic `call`), so `Constrained` is no longer special in *kind* — it's the same negotiation as `HttpProvider.call`. But it is special in *stakes*: for `Streaming` the degradation is benign — a non-streaming provider still returns the right answer, just buffered. For `Constrained` the whole *value proposition* is a compile-time-ish guarantee, and the model can only offer a runtime `match`. An app that writes `Classify.decode(...)` against `client Hosted()` compiles fine and throws at runtime. The proposal's own escape hatch ("drop the `client` sugar, write `function ... -> ConcreteProvider`") does let you demand a `Constrained` return type — but you lose dynamic selection, and you cannot express "*some* `Constrained` provider, any of vLLM/llama.cpp/Outlines" without writing the union longhand. There is no way to say at the type level "this function is guaranteed-shaped." For a *guarantee* feature, "the type checker can't see the guarantee" is the worst possible place for the runtime-promise tradeoff to land.

**The marker revision *sharpens* the capability partition (old OQ1 resolved).** Under the marker model, `Constrained requires Provider` requires only the bare marker — it does NOT force a constrained backend to also carry an unconstrained `.call`. A backend could, in principle, implement `Constrained` and *not* `HttpProvider` and still be a `Provider`. In practice vLLM/llama.cpp/Outlines implement both (their unconstrained chat is genuinely useful), and that is now an *honest, separate choice* per provider rather than an obligation inherited from the base. This cleans up the old "muddied two-tier story": "`Constrained`-capable" and "request/response-capable" are two independent capability rows, so the type encodes exactly which a provider has. What it still cannot encode is *which* call is constrained: `VLLM` having both `HttpProvider.call` (unconstrained) and `Constrained.decode` (constrained) is indistinguishable from a hypothetical provider whose `.call` is itself always-constrained — both expose the same two capability rows from outside.

**The `Constraint` union is closed, but backends disagree on what's expressible.** vLLM has four native knobs; llama.cpp has *one* (GBNF) and must lower choice/json into it and *refuse* regex; Outlines has choice/regex/cfg but folds json into regex. The model handles this with per-provider `match` + `throw`, which is honest — but it means a `Constraint` is not actually portable across the self-hosted tier. `Grammar { dialect: "gbnf" }` runs on llama.cpp and fails on Outlines (`lark`/`ebnf`); `Grammar { dialect: "lark" }` is the reverse. So portability is *real for Choice/Regex* and *leaky for Grammar*, and the leak is invisible until runtime. The model surfaces it (typed `throw`) but cannot prevent it — there is no "does provider P accept dialect D?" at compile time.

**`ConstrainedFallback`'s degrade is dishonest for non-JSON shapes.** `Fallback` can always degrade `.stream` to `.call`. `ConstrainedFallback` *cannot* honestly degrade a `Choice` guarantee onto a hosted provider — a bare enum token is not JSON. The combinator does the only correct thing (throws `Unsatisfiable` for `Choice`/`Regex`/`Grammar`, degrades only `JsonShape`), but this means the combinator's *claimed* `Constrained` capability is a lie for most inputs when the only live member is hosted. The §6 admission "a combinator statically claims every capability it forwards" is technically satisfied, but here the claim is empty for 3 of 4 constraint kinds. The app must hand-write the recovery (`PortableLabel`'s `catch`), which is more code than the "portable" framing promises.

**The new error model makes the cross-capability degrade widen the channel — and the classifiers don't line up.** `PortableLabel` decodes on the `ConstraintError` channel, then its recovery falls back to an unconstrained `HttpProvider.call`, which is on the `CallError` channel. So the *app function* ends up declaring `throws baml.ExtendUnknownError<baml.errors.ConstraintError | baml.errors.CallError>` — two capability-error interfaces in one channel. That is legal (the union just flattens, and `UnknownError` collapses once), but it exposes a real seam the single-`LlmClient`-channel model hid: a caller of `PortableLabel` now has to triage across *two* interface vocabularies whose classifier methods only partially overlap. `ConstraintError` has `is_unsatisfiable` + `is_network_error`; `CallError` has `is_rate_limit` + `is_parse_error` + `is_network_error`. Only `is_network_error` is common. There is no `is_network_error`-style universal base across capability interfaces (the model is deliberately a flat set, not a hierarchy), so an app that wants "did the network die, on either path?" can ask that — but "was this unsatisfiable OR rate-limited?" requires two separate concrete/interface arms. The degrade that the *capability* model makes ergonomic (just call `.call`), the *error* model makes slightly more verbose at the catch. Whether `ConstraintError` should have reused `CallError` instead of being its own interface is a genuine open question: `decode` really is a different failure mode (`is_unsatisfiable` has no `CallError` analog), so a fresh interface is defensible — but every such fresh capability interface multiplies the classifier-vocabulary the consumer must learn, and the flat-not-hierarchy choice means they never unify.

**`ConstrainedFallback` forwards the `ConstraintError` channel too — and its degrade is where the channel choice bites.** Rule 4 says combinators declare the SAME channel as what they forward, no variance gymnastics — and indeed `ConstrainedFallback.decode` declares exactly `baml.ExtendUnknownError<baml.errors.ConstraintError>`, identical to a single member. But the honest content is asymmetric: when the combinator's only live member is hosted, the `_` arm throws `Unsatisfiable` for `Choice`/`Regex`/`Grammar`. So the combinator's `ConstraintError` channel is *dominated by `Unsatisfiable`* for 3 of 4 constraint kinds — the typed error faithfully reports "I claimed this capability but cannot honor it here," which is the combinator's empty-claim problem (above) now surfaced as a *typed value* rather than hidden. That is strictly better than the old model (where it was an opaque `LlmClient { message }`), but it also means `is_unsatisfiable()` returning `true` is the *expected* outcome of the portable path, not an exceptional one — the classifier that exists to flag the rare case is, for this combinator, the common case.

**No server-authoritative grammar compilation state.** The background notes grammars have setup/compile cost, amortized when reused. The model has no place to express "this provider holds a compiled-grammar cache keyed by grammar source." It would have to be a hidden field on the provider class mutated by `decode` — but providers are values constructed fresh by the `client` function on every call, so there is no stable identity to hang a cache on. This is the same statelessness limitation the proposal has elsewhere; for constrained decoding it means the amortization story isn't expressible in-language (it'd live in the `$rust` backend, opaque to BAML).

## (d) Verdict: **Workable-with-additions**

The capability-interface mechanism absorbs the two-tier split cleanly and idiomatically: hosted-vs-self-hosted becomes "implements `Constrained` or doesn't," `where it runs` is a provider field, and per-backend divergence (guided_* keys, GBNF lowering, in-process Outlines) is isolated exactly where the proposal puts divergence — inside the provider body. The net-new surface (`Constrained`, the `Constraint` union, `cast_exact`, the GBNF helpers, and — under the new error model — a `baml.errors.ConstraintError` interface with an `is_unsatisfiable` classifier) is small and each piece lands on an existing primitive. But two things keep it from Clean. First, `Constrained` is the capability where the proposal's "capability is a runtime promise" stance hurts most: the feature's entire selling point is a guarantee, and the model cannot lift that guarantee into the type system without abandoning the `client` sugar and even then cannot express "any constrained provider." Second, true portability holds only for `Choice`/`Regex`; `Grammar` dialects and the hosted-degrade case leak at runtime in ways the type checker cannot catch. The model *expresses* all of this correctly and honestly — it never silently does the wrong thing — but it cannot *prevent* the foot-guns, which for a constraint-guarantee feature is exactly the property a user most wants from the type system.
