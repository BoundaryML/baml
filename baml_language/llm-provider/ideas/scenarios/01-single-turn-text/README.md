# Scenario 01 — Plain text in / text out

The irreducible case: send some text, get text back. This scenario stress-tests the proposal's base method `Provider.call<T>(prompt) -> T` against three real providers (Anthropic, OpenAI Chat, Gemini) and the divergences the background documents — the system prompt living in three different places (in-array message, top-level `system` string, top-level `system_instruction` object), the assistant-vs-`model` role split, sampling params / `max_tokens` modeled as plain provider fields (usage is a *sidecar*, not a field — see below), and the fact that a refusal is not the answer but arrives in a separate channel. `implement.baml` is the std-lib provider/codec code; `usage.baml` is the one-line-per-provider app surface; `evaluation.md` argues that the happy path is clean but that **usage** and **refusal** don't fit `call<T> -> T` and force net-new surface. Usage is a *product* sidecar (answer AND metadata), so it rides the base `call_with<T,U>(prompt, project: (ResponseMeta) -> U) -> (T, U)` method and a `ResponseMeta` projection (`m => m.usage()`) — replacing the earlier bespoke `Metered`/`call_metered`/`Metered_Result<T>` companion, and requiring first-class **tuples** as net-new surface (see [`../../value-sidecar-model.md`](../../value-sidecar-model.md)). Refusal is a *sum* (no `T`), so it stays a `Refused` concrete error on the `baml.errors.CallError` channel. A readable view over the opaque `PromptAst` is the third addition.
