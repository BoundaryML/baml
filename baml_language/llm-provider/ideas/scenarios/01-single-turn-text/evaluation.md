# Evaluation — Plain text in / text out

Adversarial read of whether the proposed model (`Provider.call` base + capabilities-as-interfaces + `client`-as-sugar) actually expresses the most basic LLM scenario cleanly. The honest answer: the *happy path* is clean, but this scenario is where two real surfaces — **usage** and **refusal** — turn out not to fit `call<T>(prompt) -> T` at all, and the proposal has to grow.

## (a) What the proposal reuses unchanged

- **`Provider` / `HttpProvider` verbatim.** `Anthropic`, `OpenAI`, and `Gemini` are plain classes with one `implements HttpProvider` block each and inherit `call` for free from the codec default (`call = parse ∘ send ∘ build_request`). Nothing about the base needed touching to get text-in/text-out.
- **`build_request<T>` as the re-shaping seam.** The proposal's claim that "`build_request` decides where the schema goes" generalizes exactly to "where the *system prompt* goes." Each provider re-shapes the same `PromptAst` into its own envelope: OpenAI keeps `system` as an in-array message, Anthropic hoists it to a top-level string, Gemini hoists it to a `system_instruction` object. Three placements, one interface, no shared message type leaking out.
- **Options-as-fields.** `max_tokens` (required on `Anthropic`, optional on `OpenAI`), `top_k` (present on Anthropic/Gemini, absent on OpenAI Chat), `frequency_penalty`/`presence_penalty` (OpenAI-only), `stop` vs `stop_sequences` — all land as plain provider fields with no `options:` blob and no `@providers:` map. This is the cleanest part of the scenario; the per-provider sampling divergence the background calls out is exactly what per-class fields are for. `ChatModelOptions` reads `model`/`api_key` uniformly.
- **`ChatModelOptions`, `catch`, `match`, `for-in`, static-free class functions, `baml.sap.parse`, `baml.http.send`** — all used as given.
- **Combinators inherited from `Provider`.** `Claude().with_retry(2).fallback_to(GPT())` reads as a chain with zero new machinery; orchestration stays off the provider.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.llm.turns` / `system_text` / `non_system_turns` read-interface over `PromptAst`** (host primitive). The proposal makes `PromptAst` opaque (`_data: $rust_type`) and only ever *passes it through* to `build_request`. But the three system-prompt placements require **reading** the AST's normalized turns to decide where each turn goes. Today nothing exposes that. This is the single biggest addition: the opaque-prompt assumption breaks the moment a pure-BAML provider has to re-home the system turn. (Open Question 3 touches the request side but frames it as transport-shape, not AST-read; this is a *different* gap — the read side of the prompt, not the write side of the transport.)
2. **`baml.json.{obj,arr,raw}`** (host primitive). The proposal shows `build_request` bodies as `$rust_io_function` and never writes a body in BAML. To make the placement divergence the *teaching point* rather than a black box, a pure-BAML provider needs structured JSON assembly. Minor, but genuinely absent from the conventions.
3. **`interface Metered` + `Usage` + `Metered_Result<T>`** (capability + types). This is the load-bearing finding: **token usage does not fit `call<T> -> T`.** `call` returns the answer; usage is a side-band fact about the same call. There is nowhere in the base signature to put it. So usage becomes a *new capability interface* (`requires Provider`, companion `.metered`), structurally identical to `Streaming`/`Inspectable` — a refinement that returns *more* than `call`. The proposal never lists usage, yet it's present on literally every chat response. It slots into the model, but it is net-new and the proposal should name it.
4. **`class Refused` on the typed `throws` channel** (type, reusing `Error`). A refusal is HTTP 200 with no usable `T` and a reason in a separate field (`stop_reason: "refusal"`, `choices[0].message.refusal`, Gemini `finishReason`). It is neither the answer nor a transport failure. We model it as a distinct error class on the existing `type Error` channel so `parse` can `throw Refused` and the app can `catch (e) { let r: Refused => ... }`. This reuses the `throws`/`catch` primitive but adds a semantic the proposal never mentions: `parse<T>` must inspect the *refusal channel before* it ever calls `sap.parse`, or it surfaces an empty string and misclassifies a decline as a malformed answer.

## (c) Where it is awkward, leaky, or unresolved

- **Usage forces a parallel method, not a parameter.** Because `call<T> -> T` is fixed, `Metered` has to expose a *separate* `call_metered<T> -> Metered_Result<T>`, and the providers duplicate the `send`/`parse` plumbing inside it. There's no way to say "call, and also give me usage" without a second entry point. A caller who wants usage from a `Fallback` gets it only if the combinator also forwards `Metered` (runtime delegation) — and the proposal's own tradeoff bites: a `Fallback` statically *claims* `Metered` and degrades at call time if the chosen member can't report it. For usage that degradation is silent zeros, which is exactly the kind of "looks fine, is wrong" the background warns about.
- **Refusal vs. the existential return (Open Question 1).** OQ1 asks whether every capability should refine `call` best-effort. Refusal exposes the dual problem on the base method itself: `call<T> -> T` has no room for "succeeded at the HTTP level, declined at the policy level." We smuggle it onto the `throws` channel, which works, but it means *refusal is invisible in the type* — a `Summarize(work) -> string` gives no compile-time hint that a `Refused` can come back, exactly the runtime-promise property OQ5 accepts for capabilities. Fine, but worth stating plainly: **the model cannot make "this call may be refused" part of the answer type.**
- **Capability `match` over the existential (Open Question 5).** `.metered` depends on `match (p) { let m: Metered => ... }` working at runtime against the existential `Provider` the client returns. The whole usage path is hostage to OQ5 being answered yes (value-level interface-membership reflection). If it isn't, usage has no clean home at all and you're back to dropping the `client` sugar and writing `function Summarize -> Anthropic` longhand — which leaks the concrete provider into every signature that wants tokens.
- **SAP as a public primitive (Open Question 6).** Every `parse` here calls `baml.sap.parse<T>(...)` on extracted text, and `call_metered` calls it on scalar token counts too. The scenario is unbuildable in pure BAML until OQ6 exposes `baml.sap.parse` publicly. Confirmed dependency, not optional.
- **The `PromptAst` read-interface is a real hole (Open Question 3, adjacent).** OQ3 worries the *request* side is HTTP-specific; the sharper issue this scenario surfaces is that the *prompt* side is opaque. "There is no shared message type" is true on the wire — but to re-shape into three envelopes the provider needs *some* shared, readable in-memory shape, and `PromptTurn[]` is it. The proposal's opaque `PromptAst` quietly assumes providers never need to introspect turns; system-prompt placement disproves that on the very first scenario.
- **Role normalization is assumed, not specified.** We map normalized `assistant -> "model"` (Gemini) and `assistant -> "assistant"` (OpenAI/Anthropic) inside `build_request`. That assumes the renderer already normalized roles to `system|user|assistant`. The proposal never says what role vocabulary `PromptAst` carries, so the tool/`function`-role divergence (OpenAI `tool` vs Gemini `function`) is out of scope here but will reappear in the tools scenario with no defined normalization contract.

## (d) Verdict: **Workable-with-additions**

The portability claim genuinely holds for the part everyone thinks of as "the basic case": one function body, three providers, three system-prompt placements and divergent sampling knobs all absorbed inside `build_request` and provider fields, with no options blob and no shared message type leaking to the caller. That is a real win and it falls out of the existing primitives. But the scenario also exposes that the proposal's headline signature, `call<T>(prompt) -> T`, is *too narrow for what a single chat response actually carries*: usage and refusal are both first-class facts of every response, and neither fits the return type — usage needs a whole new `Metered` capability, refusal needs a typed error channel and a "check refusal before parsing" rule, and both rely on OQ5's runtime membership match and OQ6's public SAP to even compile. None of that is fatal, and each addition sits naturally on the model's own grain (capabilities + throws), which is why this is "workable" rather than "awkward" — but the proposal as written undersells the base method by omitting the two things that make even "text in / text out" more than `T`.
