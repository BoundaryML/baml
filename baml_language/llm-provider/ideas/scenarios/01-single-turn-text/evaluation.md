# Evaluation — Plain text in / text out

Adversarial read of whether the proposed model (`Provider.call` base + capabilities-as-interfaces + `client`-as-sugar) actually expresses the most basic LLM scenario cleanly. The honest answer: the *happy path* is clean, but this scenario is where two real surfaces — **usage** and **refusal** — turn out not to fit `call<T>(prompt) -> T` at all, and the proposal has to grow. The two grow in *different directions*, and that split is the load-bearing finding. Usage is a **product** sidecar (answer AND metadata), now resolved by the value+sidecar mechanism — the base `call_with<T,U>` method plus a `ResponseMeta` projection (see [`../../value-sidecar-model.md`](../../value-sidecar-model.md)) — which supersedes the bespoke `Metered`/`call_metered`/`Metered_Result<T>` companion this scenario originally invented. Refusal is a **sum** (no `T`), which correctly stays on the `throws` channel. P1 ("`call<T> -> T` is too narrow") is therefore **resolved-with-a-named-mechanism** for the product half here; the residual tensions below are the mechanism's *existing* ones (OQ5, aggregate provenance, P2), not new pressures.

## (a) What the proposal reuses unchanged

- **`Provider` / `HttpProvider` verbatim.** `Anthropic`, `OpenAI`, and `Gemini` are plain classes with one `implements HttpProvider` block each and inherit `call` for free from the codec default (`call = parse ∘ send ∘ build_request`). Nothing about the base needed touching to get text-in/text-out.
- **`build_request<T>` as the re-shaping seam.** The proposal's claim that "`build_request` decides where the schema goes" generalizes exactly to "where the *system prompt* goes." Each provider re-shapes the same `PromptAst` into its own envelope: OpenAI keeps `system` as an in-array message, Anthropic hoists it to a top-level string, Gemini hoists it to a `system_instruction` object. Three placements, one interface, no shared message type leaking out.
- **Options-as-fields.** `max_tokens` (required on `Anthropic`, optional on `OpenAI`), `top_k` (present on Anthropic/Gemini, absent on OpenAI Chat), `frequency_penalty`/`presence_penalty` (OpenAI-only), `stop` vs `stop_sequences` — all land as plain provider fields with no `options:` blob and no `@providers:` map. This is the cleanest part of the scenario; the per-provider sampling divergence the background calls out is exactly what per-class fields are for. `ChatModelOptions` reads `model`/`api_key` uniformly.
- **`ChatModelOptions`, `catch`, `match`, `for-in`, static-free class functions, `baml.sap.parse`, `baml.http.send`** — all used as given.
- **Combinators inherited from `Provider`.** `Claude().with_retry(2).fallback_to(GPT())` reads as a chain with zero new machinery; orchestration stays off the provider.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.llm.turns` / `system_text` / `non_system_turns` read-interface over `PromptAst`** (host primitive). The proposal makes `PromptAst` opaque (`_data: $rust_type`) and only ever *passes it through* to `build_request`. But the three system-prompt placements require **reading** the AST's normalized turns to decide where each turn goes. Today nothing exposes that. This is the single biggest addition: the opaque-prompt assumption breaks the moment a pure-BAML provider has to re-home the system turn. (Open Question 3 touches the request side but frames it as transport-shape, not AST-read; this is a *different* gap — the read side of the prompt, not the write side of the transport.)
2. **JSON assembly + decode — already in the stdlib, NOT net-new.** The proposal shows `build_request` bodies as `$rust_io_function` and never writes a body in BAML, but a pure-BAML provider needs structured JSON both ways — and the real `baml.json` surface covers it. *Build:* construct a native `map<string, json>` body literal (nested arrays are `json[]`, nested objects are `map<string, json>`) and serialize once with `baml.json.stringify`. *Read:* decode the response text into a typed wire class with `baml.json.from_json<T>(baml.json.parse(resp.text()))` and read named fields — no `Response.json_path` (which the `Response` class does not have). So the JSON half of this scenario costs **zero** net-new surface; the earlier draft's `baml.json.{obj,arr,raw}` and `Response.json_path` were mis-spellings of primitives that already exist.
3. **`call_with<T,U>` + `interface ResponseMeta` + `Supported<T>` + tuples `(T, U)`** (base method + interface + std type + **language surface**). This is the load-bearing finding: **token usage does not fit `call<T> -> T`** — `call` returns the answer; usage is a side-band fact about the same call, with nowhere in the base signature to put it. The earlier draft modeled usage as a *new capability interface* `Metered` (companion `.metered`, returning a bespoke `Metered_Result<T>` wrapper), structurally like `Streaming`/`Inspectable`. The value+sidecar model retires that: usage is a **product** sidecar (answer AND metadata), so it rides the BASE method `call_with<T,U>(prompt, project: (ResponseMeta) -> U) -> (T, U)` and a `ResponseMeta` projection (`m => m.usage()`), with each provider's `meta_of` wrapping the wire Body into a concrete `AnthropicResponse`/`OpenAIResponse`/`GeminiResponse` that normalizes LAZILY. Three things this buys over the bespoke companion: (i) it lives on the base so **every combinator forwards it** — the silent zero-usage degrade under `Fallback` is gone; (ii) one normalized shape instead of N wrappers; (iii) `Supported<T> = T | Unsupported` types per-field "can't" (the three chat providers return `Unsupported` for `logprobs`) instead of a zeroed struct. **The required net-new LANGUAGE surface is tuples `(T, U)` and tuple destructuring** (`let (answer, usage): (string, Usage) = …`) — not a library type but a primitive the grammar must add; it is a *shared* dependency (the streaming folds in scenario 04 need it too), plus closures-as-method-params (`project`) and the one-line `Supported<T>` std type. The proposal never lists usage, yet it's present on literally every chat response; the model now names it and resolves it on its own grain.
4. **`class Refused` as a concrete `baml.errors.CallError`** (type, reusing the call channel). A refusal is HTTP 200 with no usable `T` and a reason in a separate field (`stop_reason: "refusal"`, `choices[0].message.refusal`, Gemini `finishReason`). It is neither the answer nor a transport failure. We model it as a concrete error class that `implements baml.errors.CallError` (all three classifiers — `is_network_error`/`is_rate_limit`/`is_parse_error` — return `false`, because it is none of those), so it rides the method's existing `baml.ExtendUnknownError<baml.errors.CallError>` channel and the app can `catch (e) { let r: Refused => ... }`. This reuses the `throws`/`catch` primitive but adds a semantic the proposal never mentions: `parse<T>` must inspect the *refusal channel before* it ever calls `sap.parse`, or it surfaces an empty string and misclassifies a decline as a malformed answer. Note the error model does NOT special-case refusal — it is just one more concrete `CallError`, indistinguishable at the channel level from `AnthropicHttpError`; the app recovers its meaning by matching the concrete `Refused` type *before* the `baml.errors.CallError` interface arm.

## (c) Where it is awkward, leaky, or unresolved

- **Usage no longer forces a parallel method (resolved by `call_with`).** The earlier draft had `Metered` expose a *separate* `call_metered<T> -> Metered_Result<T>` that duplicated `send`/`parse`, and a caller who wanted usage from a `Fallback` got it only if the combinator forwarded `Metered` — degrading to *silent zeros* if the chosen member couldn't, exactly the "looks fine, is wrong" the background warns about. The value+sidecar model fixes this at the source: `call_with` is on the BASE, so "call, and also give me usage" is `Summarize.call_with(work, m => m.usage())` with no second entry point and no duplicated plumbing (the codec runs `parse<T>` and `project(meta_of(body))` in one pass), and because every combinator forwards `call_with` structurally, `Fallback`/`Retry`/`Cache` cannot silently drop the sidecar. The honest residual is narrower and inherited, not introduced (see the Fallback-aggregate bullet below): `project` runs over the *winner's* `ResponseMeta` only, so the tokens burned on members that failed first have nowhere to go — the same aggregate-provenance gap the error side has. And *which* dimensions a client supports is still a runtime promise (`Supported`/`Unsupported` answered at call time, never in the client's static type) — P2 localized to metadata, not a new pressure.
- **Refusal vs. the existential return (Open Question 1).** OQ1 asks whether every capability should refine `call` best-effort. Refusal exposes the dual problem on the base method itself: `call<T> -> T` has no room for "succeeded at the HTTP level, declined at the policy level." We smuggle it onto the `baml.ExtendUnknownError<baml.errors.CallError>` channel, which works, but it means *refusal is invisible in the answer type* — a `Summarize(work) -> string` gives no compile-time hint that a `Refused` can come back, exactly the runtime-promise property OQ5 accepts for capabilities. And the new error model makes the channel *uniform per capability*, not per provider: the static type of `Summarize`'s error is the same `baml.errors.CallError | baml.UnknownError` whether the wired client is Anthropic, OpenAI, or Gemini — `Refused`, `AnthropicHttpError`, and `GeminiHttpError` are all only recoverable by *runtime* match, never surfaced in the signature. Worth stating plainly: **the model cannot make "this call may be refused" — or even "which provider's errors can come back" — part of any type the caller reads.**
- **Wrapper-transparent `match` is still the keystone (Open Question 5), just relocated.** Moving usage onto `call_with` removes the `match (p) { let m: Metered => ... }` capability dispatch — `call_with` is on the base, so there is no negotiation and no degrade arm for the common projection. But OQ5 does not go away; it moves to the *escape hatch*. The moment an app wants a provider-only raw field — `m => match (m) { let o: OpenAIResponse => baml.json.from_json<OpenAiBodyWire>(baml.json.parse(o.raw.text())), _ => default }` — it must test a concrete type *through* the framework's `FrameworkMeta`/`CacheMeta` wrapper layers, the same occlusion as `UnknownError` boxing a concrete error and `Fallback` hiding its member. So usage's *common* path is now free of OQ5, but the per-provider escape hatch rides it exactly as before (this is residual §1 of the value+sidecar model). If OQ5 is answered no, the escape hatch silently misses; the common `m => m.usage()` projection is unaffected.
- **SAP as a public primitive (Open Question 6).** Every `parse` here calls `baml.sap.parse<T>(...)` on extracted text, and each `ResponseMeta.usage()` calls it on scalar token counts too. The scenario is unbuildable in pure BAML until OQ6 exposes `baml.sap.parse` publicly. Confirmed dependency, not optional.
- **The `PromptAst` read-interface is a real hole (Open Question 3, adjacent).** OQ3 worries the *request* side is HTTP-specific; the sharper issue this scenario surfaces is that the *prompt* side is opaque. "There is no shared message type" is true on the wire — but to re-shape into three envelopes the provider needs *some* shared, readable in-memory shape, and `PromptTurn[]` is it. The proposal's opaque `PromptAst` quietly assumes providers never need to introspect turns; system-prompt placement disproves that on the very first scenario.
- **`call_with` dissolves the rule-4 soft edge the bespoke `Metered` exposed.** The earlier draft made usage a *new capability* (`Metered`) whose method nevertheless reused the `CallError` channel — a counterexample to rule 4 (new capability ⟿ new error interface) with no syntactic guardrail against a careless author minting a redundant `MeteredError`. Folding usage onto `call_with` removes the dilemma entirely: `call_with` is not a new capability, it is a second base method that **declares `baml.ExtendUnknownError<baml.errors.CallError>` by construction** (it shares the call path's `send`/`parse`/`meta_of`). There is no new channel to mint and no judgment call to get wrong — `call` and `call_with` fail in exactly the same ways *because they are the same codec pass*, and that identity is now structural rather than a thing the author must notice. The error model's rule 4 is untouched; this scenario simply no longer tests it.
- **The combinator forwards a capability's error channel, and the *set* of what each member threw has no typed home.** `Claude().with_retry(2).fallback_to(GPT())` produces a `Fallback`/`Retry` whose `call` declares the *same* `baml.ExtendUnknownError<baml.errors.CallError>` — no widening, which is the model's stated win. But consider the failure: `Retry` exhausts on an `AnthropicHttpError`, then `Fallback` moves to GPT, which throws an `OpenAiHttpError`. Whatever the combinator finally surfaces, the app's `catch` sees a *single* `CallError` with no record that a different provider failed first. To be precise about what survives: if either leg threw something foreign and got normalized via `with_message<CallError>`, that error is *boxed* into `baml.UnknownError`, not destroyed — `UnknownError.data` holds the original value untouched, so re-asserting `from<TheConcreteError>(e)` where that type is in scope pulls the same classified error back out, breadcrumb in `message: string[]` alongside. What the flatness actually costs is two distinct things. First, *statically*: the surfaced `CallError | UnknownError` channel does not advertise which inner errors are recoverable inside the box, so recovery is by speculative `from<T>` probing rather than type-directed — the compiler can't tell the author "an `OpenAiHttpError` can reach you here." That is exactly the runtime-promise property OQ5 accepts for capabilities, applied to the error channel. And recovery is *explicit, never transparent* (settled, not an open question): a `catch (e) { let h: OpenAiHttpError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `OpenAiHttpError`), so that arm never fires on the box — the author must explicitly `baml.UnknownError.from<OpenAiHttpError>(e)` inside the `UnknownError` arm to pull it back. So the cost is firm: a plain `catch` across the boundary only ever sees `CallError` or `UnknownError`, and the down-stack classifier is reachable only by code that already knows to probe for it — which makes the discoverability gap load-bearing, since nothing in the channel type tells the author which `from<…>` probes are worth writing. Second, and genuinely lost rather than merely de-typed: the *aggregate* history. A `Fallback` surfaces one error; the box recovers that one, but there is no typed (or even untyped) way to ask "what did the *other* members throw?" — the model keeps the last/chosen error's identity recoverable, not the set.
- **Role normalization is assumed, not specified.** We map normalized `assistant -> "model"` (Gemini) and `assistant -> "assistant"` (OpenAI/Anthropic) inside `build_request`. That assumes the renderer already normalized roles to `system|user|assistant`. The proposal never says what role vocabulary `PromptAst` carries, so the tool/`function`-role divergence (OpenAI `tool` vs Gemini `function`) is out of scope here but will reappear in the tools scenario with no defined normalization contract.

## (d) Verdict: **Workable-with-additions**

The portability claim genuinely holds for the part everyone thinks of as "the basic case": one function body, three providers, three system-prompt placements and divergent sampling knobs all absorbed inside `build_request` and provider fields, with no options blob and no shared message type leaking to the caller. That is a real win and it falls out of the existing primitives. The scenario also exposes that the proposal's headline signature, `call<T>(prompt) -> T`, is *too narrow for what a single chat response actually carries* — but P1 now has a **named mechanism** for the half this scenario stresses. Usage is a *product* sidecar, and the value+sidecar model (`call_with<T,U>` + `ResponseMeta` projection, returning a **tuple `(T, U)`**) resolves it cleanly: on the base so combinators forward it, one normalized shape instead of N wrappers, `Supported<T>` typing per-field "can't". The cost is real but bounded and *language-level*: first-class **tuples** are required net-new surface (shared with the streaming folds, not bespoke here). Refusal is a *sum* (no `T`) and correctly stays a concrete `CallError` with a "check refusal before parsing" rule — `call_with` deliberately does **not** absorb it, which is the partition working as designed. The honest residuals are the mechanism's own, not new: the Fallback aggregate carries only the winner's `ResponseMeta` view; per-field absence is a runtime promise (P2); the per-provider escape hatch rides OQ5 wrapper-transparency; and sums/stateful round-trips stay on their separate mechanisms. Both halves still rely on OQ6's public SAP to compile. None of that is fatal, and each piece sits on the model's own grain — which is why this is "workable-with-additions" and, for the product-sidecar pile specifically, **resolved**.
