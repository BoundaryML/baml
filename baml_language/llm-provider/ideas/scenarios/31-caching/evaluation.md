# Evaluation — Caching

Caching is not one feature; it is four mechanisms that share a name. The proposal handles three of them cleanly and one of them (Gemini's explicit resource) only with net-new surface and a visible ergonomic leak.

## (a) What the proposal reuses unchanged

- **The `Cache` combinator (client-side response cache).** Lifted verbatim from the spine: a plain non-generic class wrapping a `Provider`, reached via the `Provider.cached(store)` default method (an inherited combinator factory on the bare marker). It is the *only* vendor-neutral cache because it keys on the rendered prompt and never touches the wire. It reuses the exact `Fallback`/`Retry` pattern — no new idea. Under the marker model, request/response is an `HttpProvider` capability, so `Cache implements HttpProvider` (not the bare marker), owning `call`/`call_with` and routing both to its wrapped member by `match`ing it for `HttpProvider`. Those methods declare the same `baml.ExtendUnknownError<baml.errors.CallError>` channel as every other request/response provider (rule 4: combinators never narrow/widen/forward error types), so a `Refused` or a rate-limit from the wrapped `inner` passes through the combinator untouched and is recovered at the consumer's `catch`. Crucially `call_with` FORWARDS the projection to the inner member (the P1 fix), so the usage/cost sidecar — `cache_read_input_tokens`, `cached_tokens` — is not dropped on a cache miss; on a HIT, where the model was skipped entirely, the projection sees a synthetic `CacheHitMeta` (zero usage, `finish_reason: "cached"`) so the sidecar stays honest. Its choice to implement *only* `HttpProvider` (not `Streaming`/`Tools`) is the same "a combinator forwards only what it can honestly forward" rule, and the `.stream` degradation to `buffer-from-call` is correct for a cached single value.
- **`build_request` as the seam for inline / automatic caching.** Anthropic `cache_control` and OpenAI `prompt_cache_key` are *body* concerns, exactly the kind of provider-divergence the proposal already parks inside `build_request`. No new interface, no combinator — `cache_control` placement is a `for`-loop over tagged segments; `prompt_cache_key` is one optional field spliced into the body. This is the proposal working as advertised: "options dissolve into provider fields" (§4) absorbs both with zero ceremony.
- **The escape hatch (§3/§5).** The Gemini path *needs* a statically-known `ManagedCache`, so it drops the `client` sugar and uses `function ContractAnalyst() -> Gemini`. The proposal explicitly blesses this, and we use it as designed.

## (b) Net-new surface it must add

- **`interface ManagedCache requires Provider`** with an associated `type Handle` and four methods (`create_cache` / `refresh_cache` / `delete_cache` / `call_with_cache`). Tied to primitive: *capabilities are interfaces that `requires Provider`*. This is a legitimate new capability — a provider that holds a long-lived, server-authoritative cache resource — and it composes exactly like `Tools`: an opaque provider-owned `Handle` (mirrors `Tools.Transcript`) that callers never interpret.
- **`interface baml.errors.CacheError` — a NET-NEW capability-error channel.** The four core channels (`CallError`/`StreamError`/`ToolError`/`RealtimeError`) describe per-call failures; managing a server-authoritative cache resource is none of those, so `ManagedCache`'s methods declare `baml.ExtendUnknownError<baml.errors.CacheError>`. It keeps the shared `is_network_error` / `is_rate_limit` classifiers but adds a cache-specific one, `is_expired_handle()`, because a dangling `cachedContents/abc123` is the failure the caller actually branches on (recreate vs. retry). The concrete `GeminiExpiredCacheError { handle_name }` implements it; everything foreign on these methods normalizes through `baml.UnknownError.with_message<baml.errors.CacheError>(...)`. This is the error model's rule-4 extension point exercised for real — a novel capability forces a novel error interface, not a reuse of `CallError`.
- **`class CacheHandle { name, _data: $rust_type }`** — net-new opaque type, the addressable `cachedContents/abc123` handle. Tied to primitive: the `$rust_type` opaque-state pattern (`PromptAst._data`, `Transcript`).
- **`class CacheScope` with `with_cache<T,R>(provider, prefix, ttl, body)`** — net-new lifecycle helper. Tied to primitive: static no-`self` class function + `catch` for cleanup. This exists *only* because the model has no `defer`/RAII; it is hand-rolled garbage collection in BAML.
- **Host seams:** `baml.llm.prompt_fingerprint` and the `baml.llm.{anthropic,openai,gemini}` codec helpers. The codec helpers are ordinary `build_request` host calls (no new primitive). The response cache's read/write round-trip uses *existing* stdlib — `baml.json.to_string<T>(value)` to serialize the typed result for storage and `baml.sap.parse<T>` to revive it — so nothing new is needed there. The typed wire reads use `baml.json.from_json<RespClass>(baml.json.parse(resp.text()))` (also existing stdlib; `baml.http.Response` carries no `.json_path`). Only `prompt_fingerprint` (a stable hash of the opaque `PromptAst`) is genuinely new public surface the response cache needs.

## (c) Where it is awkward, leaky, or unresolved

- **Server-authoritative state has no home in the model (the core leak).** Every capability in the proposal is *per-call*: `call`, `stream`, `run`, the tool loop all begin and end within one logical interaction. Gemini's `cachedContents` is a resource that *outlives* any call and *costs money while idle*. `ManagedCache` can describe the operations, but the proposal has no notion of a resource owner, a destructor, or a finalizer — so the storage bill is the application's manual problem. `CacheScope` is a band-aid: it works for a bounded session but cannot express a handle that should survive across requests in a long-lived server (the realistic Gemini use case), because there is nothing to attach the handle's lifetime to. **This is genuinely unsupported: the proposal cannot model server-authoritative, billed, cross-call state.**
- **`client` sugar cannot carry `ManagedCache`.** Because `client` rewrites to `-> Provider` (the existential), the capability is erased and `create_cache` is unreachable through a client. The Gemini path is forced out of the ergonomic surface every other shape enjoys, into a longhand function returning the concrete `Gemini`. This is the documented escape hatch, but here it is not an edge case — it is the *only* way to use the second-most-common caching vendor. **OQ1 is resolved by the marker model** ("no — a capability `requires Provider`, the bare marker, and adds its own interaction; nothing fake is forced on it"): `ManagedCache requires Provider` carries *only* its real `create_cache`/`call_with_cache` surface, with no degenerate `call` to fake. The residual tension here is unrelated to OQ1 — it is that `client` erases to the existential `Provider`, so the static `ManagedCache` capability is unreachable through the sugar; that is a property of `client`-as-`-> Provider`, not of the marker.
- **No compile-time guarantee that a chosen breakpoint is byte-stable.** The whole value of (B)/(C) depends on a byte-stable front prefix. The model expresses *which* segments to cache (`cache_breakpoints`) but cannot prove the renderer emits them stably — a timestamp injected into the system block silently busts the cache with no type error. The proposal offers no primitive for "this prefix is stable," and arguably shouldn't, but it means caching correctness is entirely a runtime/observability concern.
- **Capability negotiation is runtime-only here too.** Engages **Open Question 5**: `CacheScope.with_cache` takes `provider: ManagedCache`, so the caller must already hold the concrete capability. If an app *did* want to ask "does my fallback chain support managed caching?", it would `match` on `ManagedCache` at runtime — and a `Fallback` claiming `ManagedCache` would have to pick *one* member's handle, which is incoherent (handles aren't portable). We deliberately did **not** make `Fallback` forward `ManagedCache`, which means the fluent surface silently lacks it.
- **The new `CacheError` channel does NOT compose with the lifecycle helper's swallow-and-rethrow — and that is a real tension.** `CacheScope.with_cache` exists precisely to guarantee `delete_cache` runs even when `body` throws. But to honor "stop the storage bill no matter what," its failure path catches *everything*, deletes the handle, and then re-raises through `baml.UnknownError.with_message<baml.errors.CacheError>(e, ...)`. Because `with_message` returns a *known* `CacheError` unchanged, a deliberately-thrown `GeminiExpiredCacheError` does survive with its identity — good. But the *cleanup* `delete_cache` is itself fallible on the same channel, and we deliberately discard its error (`catch (e2) { _ => null }`): if deletion fails, the storage bill silently continues and the caller is told only about the original `body` failure. The error model gives us no way to surface *two* concurrent failures (the body error AND a failed cleanup) on one channel — `UnknownError.message` is a breadcrumb list, not a tree — so the helper has to drop one. This is the classic try/finally double-fault, and the flat `CapErr | UnknownError` channel cannot represent it. A second tension: `CacheError` reuses `is_network_error`/`is_rate_limit` from the core interfaces but those classifiers are *advisory* — nothing forces `GeminiExpiredCacheError` to answer them consistently with how a `CallError`-typed transport blip would, so an app that triages a fallback chain mixing call-path and cache-path errors under one `is_rate_limit()` test is trusting per-provider honesty, not the type system.
- **Caching x fallback is provider-local and the model makes that explicit — good, but ugly.** Native caching must live *inside* each fallback member, never wrapping `Fallback`, because a prefix/handle is provider-local. The author has to know this and structure the chain accordingly (`.cached(...)` outermost for the vendor-neutral cache, native fields innermost). The model does not stop you from wrapping a `Fallback` in a way that claims a shared prefix cache it cannot deliver; it just won't hit. Engages **Open Question 7** only loosely (host bodies in `implements` are fine here).

## (d) Verdict

**Workable-with-additions.** Three of the four caching shapes fall out for free: the response cache *is* the spine's combinator (carrying the unchanged `baml.ExtendUnknownError<baml.errors.CallError>` channel), and inline/automatic caching are pure `build_request`/provider-field concerns that the "options dissolve into fields" model absorbs with no new machinery. The proposal earns real credit here. The error model also extends cleanly: the genuinely-new `ManagedCache` capability forces a genuinely-new `baml.errors.CacheError` interface (with a cache-specific `is_expired_handle()` classifier and a concrete `GeminiExpiredCacheError`), and that is rule 4 working as intended rather than a wart. But Gemini's explicit `cachedContents` exposes the model's one structural gap: it has no concept of a long-lived, server-authoritative, *billed* resource, and no destructor/RAII to manage one. We can bolt on a `ManagedCache` capability and a manual `CacheScope`, and that is enough for bounded sessions — but it cannot express a handle that lives across requests in a server, it is locked out of the `client` sugar, and it cannot participate in `fallback`. The additions are clean and idiomatic (capability + opaque associated type, mirroring `Tools`), so this is not *Awkward* — but the cross-call resource lifecycle is the honest "the proposal cannot express this" line, and a real framework would still have to choose between hiding handles (and GC'ing them out-of-band, outside this model) or leaking Gemini's lifecycle to every app.
