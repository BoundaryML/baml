# Caching — three shapes behind one idea

"Caching" in LLM land is four different mechanisms wearing one word. This scenario shows the proposed provider/capability model absorbing each: (A) a vendor-neutral **client-side response cache** — the spine's `Cache` combinator, an `HttpProvider` that forwards `call`/`call_with` (and so the usage sidecar) to its wrapped member; (B) Anthropic's **inline `cache_control`** annotation, which is just a content-block detail inside `build_request`; (C) OpenAI's **automatic prefix cache + `prompt_cache_key` routing hint**, which is one optional provider field; and (D) Gemini's **explicit `cachedContents` resource** — a server-authoritative, billed-while-idle handle with a create/refresh/delete lifecycle. (A)/(B)/(C) need nothing new. (D) forces a net-new `ManagedCache` capability, an opaque `CacheHandle`, and a manual `CacheScope`, and still leaves the cross-call resource lifecycle outside the model — see `evaluation.md`. The files also show why native caching must sit *inside* each fallback member (provider-local prefix) while the response cache can wrap the whole chain.
