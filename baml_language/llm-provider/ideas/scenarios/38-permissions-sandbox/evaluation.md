# Evaluation — Permissions & sandboxing

Adversarial read: does the base-`Provider` + capabilities model express the two fences (which tools, where they run) cleanly, or does it leak? The honest answer: the *config* fences land beautifully as bound fields, the *per-call* gate lands on the right chokepoint, but the model gives no static guarantee that a disallowed tool can't run, and the three homes for the approval decision (field / hook / channel event) are all needed at once — which is itself a finding.

## (a) What the proposal reuses unchanged

- **Provider fields for `allowed_tools` / `disallowed_tools` / `permission_mode` / `sandbox`.** This is §4 ("options dissolve into provider fields") working exactly as advertised, and it is the cleanest part of the scenario. The background's whole "Options on the harness" surface maps 1:1 to bound fields on `ClaudeCode`; no `options:` blob, no `provider_options` union. The proposal's §8 already wrote `sandbox`/`permission_mode`/`allowed_tools` as `ClaudeCode` fields — we just filled in the bodies.
- **`Tools` + the `ToolCall`/`ToolResult` seam, verbatim.** Every permission check rides *below* the loop, inside `ExecutionContext.dispatch`. `run_tools` is inherited unchanged; the app swaps only the `ctx`. Because the gate sits above the seam, the identical `PermissionedContext` works for ClaudeCode and FlueHarness despite their divergent internals.
- **`Realtime` + `Channel` (pass-in) for the steerable session.** The control channel is a parameter of the capability method, not a client field (§3) — which is exactly what lets the *same* channel carry the "ask" approval event back to the operator. The proposal's "the live channel is handed in at the call" claim is load-bearing here in a way §8 only gestured at.
- **Capability `match` as negotiation (§5).** `.run_tools` matches the client against `Tools`; a non-Tools provider hits the `_` arm and errors. No new enforcement mechanism invented.
- **`client` = function returning a `Provider` (§3).** `CiFixer()`, `PreviewPlanner()`, `FluePreview()` are ordinary functions; swapping a container sandbox for a virtual one is a field change in the function body.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`Sandbox` interface + `VirtualSandbox` / `LocalSandbox` / `ContainerSandbox`.** Tied to: **a bound provider field whose value is itself a capability object**. The proposal's §8 typed `sandbox` as an opaque `Sandbox` (local|container| virtual) but never said what `Sandbox` *is*. It has to be an interface with an `exec` method, because the tool loop's `Bash` must route through it — the sandbox is the actual fence. This is genuinely new: a field that is not config data but a behavior-bearing object the provider calls into.
2. **`ApprovalRule` / `ToolPolicy` (declarative `require_approval`).** Tied to: **ordinary data the provider reads**. The canonical `Tool` is fixed at `{name, description, parameters}`, so we *cannot* add `require_approval` as a field on `Tool` (background shows the Responses-API path putting it on the tool spec). We model it as a side table. This is a real concession — see (c).
3. **`PermissionedContext implements ExecutionContext` with a `can_use_tool` hook + an `escalate`-to-Channel path.** Tied to: §7's explicit note that **`ExecutionContext` needs a `dispatch` surface (and an event-`emit` surface for realtime/harnesses)**. The approval callback is the per-call half of dispatch; the Channel-event escalation is the emit half. Both were flagged as net-new in the proposal; this scenario instantiates them.
4. **`ApprovalDecision { behavior, updated_input, message }`.** Tied to: the callback's return shape (allow/deny/ask + arg-rewrite). New plain class; the `updated_input` field is what lets the Edit case rewrite args, which a pure allow/deny boolean couldn't express.
5. **`mode_to_rules` on `ClaudeCode`.** Tied to: **a static provider method that interprets provider-specific vocabulary**. The mode words are Claude-specific; translating them to provider-agnostic `ApprovalRule`s is the seam that keeps the divergence inside the provider. FlueHarness simply has no such method.
6. **A net-new `baml.errors.SandboxError` capability-error interface.** Tied to: **the error model's rule that every fallible capability declares `baml.ExtendUnknownError<CapErr>`**. `Sandbox.exec` is a capability beyond `call`/`stream`/`realtime`/`tools` — running a shell command in a fence — so it gets its own channel rather than overloading `CallError`. Its classifiers (`is_network_error`, `is_exec_failure`) are the honest subset a sandbox can answer; `is_rate_limit`/`is_parse_error` would be noise, so the interface is deliberately smaller than `CallError`. The deliberate-failure side also adds **`BadApprovalBehavior implements baml.errors.ToolError`**: the dispatcher's "bad behavior string" throw is now a typed tool-loop error, not an untyped `LlmClient` blob.

## (c) Where it is awkward, leaky, or unresolved

- **`require_approval` can't live on `Tool`, so it splits from the tool it guards.** The background's hosted-MCP path puts approval *on the tool spec*; a declarative posture travels with the tool. Our `Tool` is frozen, so we put it in a parallel `ApprovalRule[]` keyed by tool *name*. That re-introduces the exact id/name correlation problem the `Tools` seam works so hard to hide — a rule references a tool by string, and nothing checks the names line up. A better model would extend `Tool` with optional metadata, but that is a change to a canonical primitive, not something the capabilities model grants for free.

- **No compile-time guarantee a disallowed tool can't run.** `allowed_tools` / `disallowed_tools` are runtime fields read inside `begin` (`filter_tools`) and the deny pattern is a runtime `if` in `dispatch`. The type system cannot say "this client may not run `Bash`." A harness that ignores its own `allowed_tools` (or a buggy `filter_tools`) is not a type error. The proposal is honest that capability is a runtime promise (§5); permission is *finer* than capability and is even more runtime — there is no `Provider`-minus-`Bash` type the way scenario 16 could express `Provider`-minus-`Tools`. Tool-granularity permission is below the resolution of the capability type system.

- **Open Question 1 (must every capability fake a `call`?) — RESOLVED by the marker, and it removes a permission hazard.** Under the old base-`Provider`-with-`call` thesis, `ClaudeCode` had to carry a degenerate one-shot `call`: a spawn with no human in the loop, where every "ask" posture had nowhere to go and collapsed to deny (or `bypassPermissions`). That fake `call` *could not honor an interactive permission mode* — the mode only means something in `Tools` / `Realtime` — so the same provider's `call` and `run_tools` enforced permissions differently, with nothing in the type to signal it, and a `plan`-mode client used via plain `Foo(args)` silently did nothing useful. Under ../provider-as-marker.md that hazard is gone: `Provider` is a bare marker, `call`/`call_with` belong to `HttpProvider`, and a harness that is not an `HttpProvider` simply does not have `call`. `ClaudeCode`/`FlueHarness` expose only `Tools` and `Realtime` — exactly the surfaces where permission modes are meaningful. A bare `Foo(args)` against such a client now `match`es for `HttpProvider`, misses, and throws `Unsupported` (an honest "this client cannot produce a single value") instead of running a permission-blind one-shot. The mismatch the old model couldn't signal is now a typed-capability fact: the permission-enforcing surfaces are the *only* surfaces the harness offers.

- **Open Question 2 (how the live `io` channel surfaces) is where the three homes collide.** The approval decision wants to be: a **field** (declarative require_approval), a **hook** (can_use_tool callback), AND a **Channel event** ("ask" in a live session). We made `PermissionedContext` hold all three (`policy`, `can_use_tool`, `control`) and resolve precedence in `decide`/ `escalate`. That works but is a lot of policy crammed into one dispatcher, and the precedence (callback beats declarative; "ask" needs a channel or default-denies) is a convention this scenario invents, not something the model prescribes. Q2 asks whether the channel should appear in the function signature; here it must appear in *two* places at once (the `.live` call AND the ctx), which the proposal never contemplated.

- **Pattern matching is a sieve and the model can't make it anything else.** The background is blunt: denying `Bash(rm*)` doesn't stop `find . -delete`. Our `is_denied`/`command_matches` faithfully reproduce the sieve, and the *fence* is `Sandbox.exec`. The capability model correctly locates the fence (the sandbox is a bound object the loop routes Bash through), but it offers no help proving that *all* shell egress actually goes through `self.sandbox` — a provider could call `local_shell_exec` directly and bypass its own sandbox field. The model gives you a place to put the fence; it does not verify the fence is wired in.

- **The per-capability error channel forces a decision the security model can't make cleanly: which channel does a *denied tool* land on?** The dispatcher runs on the `ToolError` channel, and a `BadApprovalBehavior` is a clean `ToolError`. But the security-interesting events — "policy denied this call", "operator denied via the channel" — are NOT thrown at all; they are written into a `ToolResult` payload (`deny_payload`) and handed back to the model, by design (the model must see the denial to react). So the error model and the permission model disagree about what a "denial" is: the error model would type it as a `ToolError` the app catches; the permission model deliberately keeps it *in band* as a tool result the model reads. A refusal-as-typed-channel story (scenario 02's `Refused implements CallError`) does NOT transfer here — a permission denial is not a `Refused`, because the loop must continue, not abort. That mismatch is real and the model gives no guidance on it.

- **`Sandbox.exec`'s foreign `baml.errors.Io` is boxed into `baml.UnknownError`, and `SandboxError`'s channel never *advertises* the one classification that mattered.** A container connector dropping mid-`exec` is genuinely an `is_network_error`, but `container_exec` is a `$rust_io_function` whose failure is opaque at the BAML level, so the trailing `with_message<baml.errors.SandboxError>` routes it onto the `UnknownError` arm rather than a classified `is_network_error -> true`. Two distinct things bite here, and only one is a real loss. First, *if* the host does hand back a typed `baml.errors.Io`, boxing does **not** destroy it: `UnknownError.data` holds the original untouched and `from<baml.errors.Io>(e)` at any layer where `Io` is in scope pulls the same concrete error back out, classifiers intact — so its data and identity *survive and are recoverable*. What is actually lost is the **static** story: the consumer's channel is `SandboxError | baml.UnknownError`, which does not enumerate that an inner network-class `Io` can reach the box, so recovery is by *speculative* `from<Io>` probing rather than type-directed — the P2-analog (precision recoverable at runtime, not statically guaranteed). And recovery is *always explicit, never transparent* (settled): a `catch (e) { let io: baml.errors.Io => … }` arm is a runtime is-a test on `e` itself, and a boxed error *is* a `baml.UnknownError` (which does not implement `Io`), so that arm never fires on the box — the author must reach in with `baml.UnknownError.from<baml.errors.Io>(e)` inside the `UnknownError` arm. The cost is therefore firm, not conditional: a plain `catch` across this boundary only ever sees `SandboxError` or `UnknownError`, and the down-stack `is_network_error` is reachable but only by code that already knows to probe for it. Second, and independently, we introduced `SandboxError` with the right classifier but can't populate *it* without a host-side predicate to distinguish a dropped container from a non-zero exit — and where the host hands back a genuinely opaque value (no typed `Io` at all), there is nothing inside the box to re-assert. The new error model makes the *interface* expressible; it cannot make the host hand us a classifiable error. So the most operationally-useful sandbox failure (the fence went away vs. the command failed) is the one whose classification is either un-advertised on the channel (recoverable, but only by probing) or, when the host stays opaque, never produced at all.

- **Open Question 7 (host-backed `implements` bodies) carries the whole fence.** `just_bash_exec`, `container_exec`, `local_shell_exec`, `await_approval`, `filter_tools` are all `$rust_io_function`. The actual isolation, the actual command execution, and the blocking-on-operator-reply all live on the far side of the bridge. The BAML reader sees the *policy* (which call needs approval) but not the *mechanism* (what "container isolation" actually enforces). That is unavoidable — it is a host concern — but it means the security-critical part is exactly the part BAML can't show or test.

## (d) Verdict: **Workable-with-additions**

The configuration fences are a genuine win: `allowed_tools`, `disallowed_tools`, `permission_mode`, and `sandbox` are bound provider fields with no ceremony, mode vocabulary stays sealed inside the provider (`mode_to_rules`), and the same `PermissionedContext` is portable across a mode-rich provider (ClaudeCode) and a mode-less one (Flue) because it rides above the `ToolCall` seam — that portability across a real divergence is the strongest evidence the model is doing useful work. The approval *decision* also finds the one correct chokepoint, `dispatch`, and the pass-in `Channel` cleanly doubles as the approval-event transport for live sessions. But three additions are unavoidable — a behavior-bearing `Sandbox` interface (which drags in a net-new `baml.errors.SandboxError` channel of its own, since `exec` is a capability outside `call`/`stream`/`realtime`/`tools`), a declarative `ApprovalRule`/`ToolPolicy` side table (because `Tool` is frozen and can't carry `require_approval`), and an `ExecutionContext` extended with a callback hook plus channel escalation — and two things the model simply cannot do: give a compile-time guarantee that a disallowed tool won't run (permission is finer-grained than the capability type system), and prove the sandbox fence is actually in the command path (that is host-side, behind Q7's bridge). The model is an excellent *organizer and locator* of these fences and a poor *prover* of them — which, for a security feature, is the limitation worth stating plainly.
