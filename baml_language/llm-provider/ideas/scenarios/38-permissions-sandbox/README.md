# 38 — Permissions & sandboxing

This scenario bounds what a code-running harness may do across two fences: *which* tools it may use (permissions) and *where* its shell commands actually run (sandbox). It shows the easy half landing cleanly — `allowed_tools`, `disallowed_tools`, `permission_mode`, and `sandbox` are bound provider fields, exactly like `model`, and the Claude-specific mode vocabulary (`plan` / `acceptEdits` / `bypassPermissions`) stays sealed inside the provider via `mode_to_rules` — and the hard half needing additions: a behavior-bearing `Sandbox` interface (virtual / local / container) that is the real fence — and, because `exec` is a capability of its own, a net-new `baml.errors.SandboxError` channel beside the `ToolError`/`RealtimeError` the providers already use (they are subprocess harnesses, not `HttpProvider`s, so they carry no `call`/`CallError` at all — `Provider` is a bare marker per ../provider-as-marker.md) — a declarative `require_approval` modeled as an `ApprovalRule` side table because the canonical `Tool` is frozen, and an `ExecutionContext` (`PermissionedContext`) extended with a per-call `can_use_tool` hook whose "ask" decision escalates as a `Channel` event in a live session. `implement.baml` is the library code; `usage.baml` wires it for ClaudeCode (mode-rich) and FlueHarness (mode-less, virtual sandbox by default) to prove the dispatcher is portable; `evaluation.md` stresses where the model cannot guarantee a disallowed tool won't run, or prove the sandbox is actually in the command path.
