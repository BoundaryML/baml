# 18 — Compaction: shrinking the live context

A long-running run accumulates old turns, tool logs, and stale detail that crowd out the state the model needs. Compaction shrinks the live window while preserving forward-looking state — but the mechanism diverges hard by provider: OpenAI Responses returns provider-produced **replacement** machine state from a dedicated `compact()` endpoint; Anthropic does **server-side context editing** (prune stale tool/thinking blocks in place, report `applied_edits`) plus a separate summarize primitive; Gemini has **no endpoint** and you roll your own LLM summary. This scenario models compaction as a `Compaction` capability whose `Window`/`Compacted` state is provider-owned and opaque (pass it forward verbatim — it is lossy machine state, not prose), a sibling `ContextEditing` capability for the prune-in-place shape, and an `AutoCompact` combinator that carries the window between turns and compacts at a milestone. `implement.baml` is library code (the three providers + combinator); `usage.baml` is the application author's clients and milestone driver; `evaluation.md` stresses where the model leaks (stateful combinators, two capabilities for one goal, opaque output that lies about Gemini, cache-prefix busts that can't be enforced, and a net-new `baml.errors.CompactionError` channel whose transport-shaped classifiers are unreachable for the one provider whose compaction is really an `HttpProvider.call`). Errors follow the per-capability model: each method declares `baml.ExtendUnknownError<CapErr>` (compaction methods use the net-new `baml.errors.CompactionError`; the HTTP call path uses `baml.errors.CallError`), with foreign host failures normalized through `baml.UnknownError` — there is no single per-provider error type.
