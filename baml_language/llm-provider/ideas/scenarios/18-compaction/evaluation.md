# Evaluation — Compaction: shrinking the live context

Adversarial read of whether the proposed `Provider` / capability model expresses context compaction. Background: `background/03-state-sessions-memory.md` → `## ◆ Compaction: shrinking the live context`.

## (a) What the proposal reuses unchanged

- **Capability-as-interface (`requires Provider`).** `Compaction` is a textbook capability: a few providers can shrink a window, most can't, and the set of who can *is* the type. No new mechanism — it slots in beside `Streaming`, `Tools`, `Realtime` with the exact `requires Provider` shape.
- **Associated `type` for opaque provider state.** `Compaction.Window` is bound per provider (`OpenAIWindow`, `AnthropicWindow`, `GeminiWindow`) exactly like `Tools.Transcript`. The "machine state is opaque, pass it forward verbatim" contract from the background is the *same* discipline already paid for in §7's transcript: the loop/app never decodes; the provider owns the wire grammar.
- **Capability negotiation by runtime `match`.** `CompactNow` and `EditDownTo` `match` the existential `Provider` against `Compaction` / `ContextEditing` and error in the `_` arm. This is verbatim §5 — no fallback for replacement state, because (correctly) you cannot fake machine state from a single `.call`.
- **Combinator wrapping a provider.** `AutoCompact` is the §6 pattern: a plain class holding `inner: Compaction`, forwarding the `HttpProvider` capability (`call`/`call_with`) by `match`ing the inner provider for it, adding a policy method (`checkpoint`). The "compact at a milestone" orchestration lives in the wrapper, not in any provider — same separation as `Retry`/`Cache`.
- **Pure-BAML provider implementing a capability from `call`.** `GeminiSummary` implements `Compaction.compact` by calling `self.call<string>(summary_prompt)` — and it can, because `GeminiSummary` itself `implements HttpProvider`, the capability that owns `call`. This is the payoff the proposal advertises (§8's harness move): a capability built *out of* the provider's own `HttpProvider.call`, no compaction endpoint required. (Per ../provider-as-marker.md, `call` is no longer a privileged base method but an `HttpProvider` capability — Gemini has it because it implements that capability, not because every provider does.)

## (b) Net-new surface it must add (each tied to a primitive)

- **`Compaction` interface** (capability primitive). New capability with `type Window`, `window_of`, `compact`. Justified: there is no existing interface whose method shape is "shrink an opaque window into smaller opaque state."
- **`ContextEditing` interface** (capability primitive). A *second* capability for Anthropic's prune-in-place mode, because its result is a side effect of a normal turn and it *can* report `removed` precisely — a different signature than `compact`. See (c): this split is a smell, but it is honest.
- **`Compacted` result type** (plain class). Opaque `output: WindowItems` plus *non-authoritative* metadata (`busts_cache_prefix`, token deltas, `removed`). The metadata is the only inspectable seam; the state itself is not. New type — no existing result carries "opaque body + cache-prefix bookkeeping."
- **`WindowItems` opaque body** (`{ _data: $rust_type }`, the `PromptAst`/`History` pattern). The live item list in a provider's round-trip grammar. New value-type, sibling to `Tools`'s `History`.
- **`AppliedEdit` / `ContextEdit`** (plain classes) — the Anthropic edit knobs and per-turn deletion report. Bespoke provider fields, exactly the §4 "options dissolve into provider fields" rule (`edits: ContextEdit[]` is Anthropic's field, `compact_threshold: int?` is OpenAI's). No `provider_options` union needed.
- **`auto_compact` free function** instead of a `Provider` default method. Net-new *shape*: a combinator constructor gated on a capability the base lacks. See (c).
- **`baml.errors.CompactionError` interface** (capability-error primitive). Compaction is a capability *beyond* call/stream/realtime/tools, so under the canonical error model it needs its own capability-error interface, declared as `baml.ExtendUnknownError<baml.errors.CompactionError>` on `Compaction.{window_of,compact}` and `ContextEditing.edit`. It carries the same three classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) — which fit, but only just (see (c)). Both providers' `compact`/`edit` bodies normalize foreign host failures with a trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.CompactionError>(e, "…") }`, and `baml.errors.Unsupported` (legal on every channel) remains the `_`-arm throw. Net-new error channel — flagged here because the proposal's canon only ships CallError/StreamError/ToolError/RealtimeError.

## (c) Where it is awkward, leaky, or unresolved

- **The combinator carries mutable conversational state, not just config.** `AutoCompact.window` is the live context threaded between turns and *mutated* by `checkpoint`/`append_turn`. Every other combinator in the proposal (`Retry`, `Cache`, `Fallback`) is stateless config that wraps a `Provider`. A compaction combinator is fundamentally a *stateful session object*. The proposal never says a combinator may hold turn-state, and nothing in the model forbids it — but it stretches "combinators are plain classes that forward capabilities" into "...and also own the conversation." The real seam here: the window is logically an argument to every `call`, yet `HttpProvider.call<T>(prompt) -> T` has no window parameter. We smuggle the window in as combinator state precisely because the `call` signature can't carry it. A cleaner model might thread the window through a dedicated *session* capability (its own interface, `requires Provider`); the marker model makes adding such a capability cheap, but this scenario uses none — so the window lives as combinator state. (Note this is no longer "does every capability refine a base `call`?" — under ../provider-as-marker.md `call` is just one capability among many and nothing refines it; the open question is the orthogonal one of where stateful session state lives.)

- **`compact` can't be a `Provider` default method.** `with_retry`/`cached` are default methods on `Provider` because every provider has them. Compaction does not — so `auto_compact` is a free function gated on `p: Compaction`. That is fine, but it means the fluent `.compact()`/`.auto_compact()` chaining the proposal sells for orchestration *does not extend* to capability-specific combinators. You get `auto_compact(p, init)`, not `p.auto_compact(init)`. Minor, but it shows the "combinators are inherited methods" story only holds for capabilities in the base.

- **Two capabilities for one user goal.** `Compaction` vs `ContextEditing` is a real leak. The background frames OpenAI-compact, Anthropic-clear/compact, and Gemini-summary as one *goal* ("shrink the window"), but the mechanisms don't share a signature: replacement returns new state from a dedicated call; editing reports deletions as a side effect of a normal turn. Forcing them into one interface would mean a `compact` whose semantics ("did this run a turn?") vary by provider — worse than two honest interfaces. The cost: the app must know which capability its provider has, so the portable `AutoCompact` driver silently only covers the `Compaction` providers; Anthropic's *editing* path needs `EditDownTo`, a separate companion. Portability leaks exactly where the background says the mechanisms diverge. This is the model behaving correctly, but it is not "write once, run on any provider."

- **Opaque output has no inspection seam — by design, and the type can't help.** The background's "trusting opaque machine state" hazard is unmitigated and *unmitigatable* here: `Compacted.output` is `WindowItems { _data }`, and we deliberately expose no reader. That is faithful for OpenAI/Anthropic, but **dishonest for Gemini**, whose output is LLM prose the app *could and arguably should* inspect. We hide an inspectable summary behind the same opaque wrapper to keep one portable surface. The model has no way to say "opaque for these providers, readable for that one" without splitting the return type — which would re-leak portability. So we pick portability over honesty, and the type lies about Gemini.

- **`busts_cache_prefix` is advisory, not enforced.** The model surfaces the cache-miss fact as metadata, but nothing in the type system ties "you adopted a compacted window" to "your next `call` pays a miss." The app can ignore the flag. There is no compile-time way to express "this provider state invalidates the prompt-cache key" — it is just a `bool` the provider sets and the app may log. This is the recurring limit of the proposal: capability is a **runtime promise** (§5), and so is every cross-turn invariant. **Open Question #5** (runtime membership over the existential) is fine here — `match (p) { let c: Compaction => ... }` is exactly the supported move — but it confirms there is no compile-time guarantee that a given client supports compaction at all.

- **The new capability-error interface fits the classifiers only superficially — and Gemini exposes the seam.** The canonical error model says a capability beyond the core four gets its own `baml.errors.<Cap>Error` interface "with sensible classifier methods." `CompactionError` dutifully copies `is_network_error`/`is_rate_limit`/`is_parse_error` from `CallError` — but those three were chosen for the *transport* shape of an HTTP chat call, and only one of the three compaction providers is actually a transport call. OpenAI/Anthropic compaction are HTTP, so the classifiers are honest there. **Gemini's `compact` is not a transport call at all** — it is `self.call<string>(summary_prompt)`, whose failures arrive on the *`CallError`* channel. The body re-homes them onto the `CompactionError` channel via the trailing `with_message<baml.errors.CompactionError>` catch, which is type-correct, but it means a Gemini compaction failure surfaces *statically* as `baml.UnknownError` rather than as a classified `CompactionError`. The underlying `CallError` is **not destroyed**: `with_message` boxes it into `UnknownError` *in place*, so it survives untouched in `.data`, and an app that re-asserts `from<baml.errors.CallError>(e)` pulls the *same* concrete rate-limit/network error back out, classifiers intact. What the channel loses is the *static* signal: the consumer's type is `CompactionError | baml.UnknownError`, which does not advertise that a `CallError` is recoverable inside the box, so the app's `if (c.is_network_error())` branch in `after_milestone` — written against `CompactionError` — does not fire for Gemini *unless the author speculatively probes `from<CallError>`*. And the probe is *always* explicit: a plain `catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` itself, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it — recovering the inner `CallError` requires `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm, never a transparent reach-through. So the opaque-portability *lie* from the output type (we hide Gemini's prose) has a milder analog in the error channel: the data is preserved and recoverable, but for one of three providers the classifiers are not reachable *by type* — only by an explicit re-assertion that the author has to know to write. The cost is no static discoverability, not lost provenance — the same P2 runtime-promise pattern (Open Question #5) applied to the error channel.

- **`AutoCompact` forwards *two* error channels, and the proposal's "combinators declare the same channel" rule was written for one.** Rule 4 of the error model — combinators declare the SAME channel as what they wrap, no widen/forward — is clean when a combinator forwards a single capability. `AutoCompact` forwards two: `call`/`call_with` on `baml.ExtendUnknownError<baml.errors.CallError>` (its `HttpProvider` capability, `match`ing the inner provider for `HttpProvider` and delegating to it) and `checkpoint`/`append_turn` on `baml.ExtendUnknownError<baml.errors.CompactionError>` (driving compaction). That is correct — each method declares the channel of the capability it forwards — but it quietly shows that a stateful session-combinator is a *multi-capability* object whose error surface is the union of its members' channels, and the consumer must catch on the right one per call site. `session.checkpoint()` and `session.call()` look like methods on one object but throw disjoint error families; nothing in the type names that the failure modes differ. The "one channel per combinator" mental model the canon implies does not survive a combinator that wraps more than one capability.

- **The `Compaction`/`ContextEditing` split now also splits the error channel — but both landed on the SAME interface, which under-specifies.** (b) flagged that two mechanisms force two capabilities; under the error model both `compact` and `edit` declare `baml.errors.CompactionError`. Reusing one error interface across two capabilities is defensible (they are the same "shrink the window" goal), but it means a caller catching `baml.errors.CompactionError` cannot tell *which* mechanism failed — a failed prune and a failed summarize are indistinguishable at the classifier level, even though their recovery differs (a failed `edit` can be retried as a normal turn; a failed `compact` cannot). The model gives us either one shared interface (loses which-mechanism) or two near-identical interfaces (duplicates the classifiers for no classifier difference). We chose the former; the honesty cost is that `CompactionError` is now overloaded across two capabilities that the rest of the scenario went out of its way to keep distinct.

- **Server-authoritative state is half-expressible.** Server-managed compaction (`compact_threshold`) is genuinely just a field on the request (§4 dissolves it cleanly) — good. But the *authoritative* window then lives on the server (`previous_response_id` chain), and the proposal has no model for "the provider, not the client, owns the state." We represent it as "a field that changes what `build_request` attaches," which works only because the client holds *nothing*. The moment an app wants to mix server-managed and client-held state (compact server-side but also read token counts locally), the model has no seam for the server-owned half. The proposal can express *client-held* compaction richly and *server-managed* compaction only as an opaque config toggle.

## (d) Verdict: **Workable-with-additions**

Compaction lands cleanly *as a capability*: `requires Provider`, an associated opaque `Window`/`Compacted` type, runtime `match` negotiation, and a pure-BAML provider (Gemini) implementing the capability out of its own `HttpProvider.call` are all exactly the moves the proposal already pays for, and they fit the background's "opaque machine state, pass forward verbatim" contract without strain. The additions are modest and well-typed (`Compaction`, `Compacted`, `WindowItems`, provider fields, plus a net-new `baml.errors.CompactionError` capability-error channel that the per-capability error model requires). What keeps it from Clean is structural, not cosmetic: a compaction combinator must hold *mutable conversational state*, which is outside the proposal's stateless- combinator story and exposes that `HttpProvider.call(prompt)` has no place to thread a window (so session state lives on the combinator, not in any provider method); the two genuinely different mechanisms force two capabilities (`Compaction` / `ContextEditing`), so portability leaks precisely where the providers diverge; the opaque-output type is forced to lie about Gemini's inspectable prose to stay portable; server-authoritative state is only expressible as an opaque config toggle; and the net-new `CompactionError` channel inherits transport-shaped classifiers that are not statically reachable for the one provider (Gemini) whose compaction is really a `call`, so its failures surface as `baml.UnknownError` — the underlying `CallError` survives in `.data` and is recoverable via an explicit `from<CallError>` probe (a plain `catch` never reaches through the box), but the channel does not advertise it (a P2-style runtime promise: recovery is explicit-and-by-convention, with no static discoverability). None of these block the scenario, but each is a real seam the proposal must add or concede. Workable, with additions — not Clean.
