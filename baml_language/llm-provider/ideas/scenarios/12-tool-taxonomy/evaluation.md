# Evaluation — Tool taxonomy (hosted / computer-use / MCP)

Adversarial read of how the proposal in `../01-providers-clients-capabilities.md` holds up against five tool kinds that differ by **who executes and where**.

## (a) What the proposal reuses unchanged

- **The `Tools` capability and its `ToolCall`/`ToolResult` seam** carry the *client-executed function tool* case (background's only "you write the body" kind) with zero change. `begin`/`step`/`submit`/`run_tools` are reused verbatim; `Anthropic.Tools` and `OpenAIResponses.Tools` implement them as the proposal's §7 describes, and `step -> T | ToolCalls` is the exact `Iterator.next -> Item | Done` shape the proposal leans on.
- **`Transcript` as a provider-owned associated `type`.** The id-vs-positional correlation divergence the proposal §7 calls out lives entirely inside the provider: Claude correlates `ToolResult.id` to a prior `tool_use_id`; Responses threads `previous_response_id` + `call_id`. The loop never sees it.
- **`client` = function sugar.** `Claude()` / `GPT()` are config-only zero-arg clients, rewritten to `function -> Provider`. Nothing about tools touches the client surface — the tool set is a parameter of the capability companion, not a client field, exactly as the live-`io` channel is in §3/§5.
- **Capability negotiation via `match`.** Every `Run*` function does `match (p) { let m: MixedTools => …, _ => throw baml.errors.Unsupported }` — the §5 runtime gate, with the "no honest fallback" arm (a `.call` can't fake a hosted-search loop, just as it can't fake `Realtime`). Under the new error model `baml.errors.Unsupported` `implements` all four capability-error interfaces, so it is legal on the `ToolError` channel these `Run*` functions declare without any wrapping.
- **The per-capability error channel.** The old single `type Error = baml.errors.LlmClient` is gone: every tool-loop method (`begin_mixed`/`step_mixed`/`submit_screenshots`/`run_mixed`, plus `build_tools`/`resolve_mcp_token`) now declares `throws baml.ExtendUnknownError<baml.errors.ToolError>`, while the `HttpProvider` base (`build_request`/`send`/`parse`) stays on `baml.errors.CallError`. The split falls out naturally: one provider class has methods on *two* channels, picked by which capability the method belongs to.
- **Combinator-over-context for HITL.** `ApprovalGate` is a wrapper that `implements ExecutionContext` and delegates — the same forward-by-delegation pattern §6 uses for `Fallback`/`Retry`, applied one layer down (wrapping the dispatch context instead of the provider). It forwards the *error channel* too: because `ExecutionContext.dispatch`/`perform` now declare `ToolError`, the gate re-raising a concrete `ApprovalDenied` (a `baml.errors.ToolError`) needs no widening — the wrapper and the wrapped share one channel.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`ToolKind` union (execution location as a variant).** Tied to the `Tool` type primitive (§7 net-new). The proposal's `Tool { name, description, parameters: type }` models *only* the function case. The background's hard-requirement — "distinguish *execution location*, not just *name + schema*" — forces lifting `Tool` into `FunctionTool | HostedTool | ComputerUseTool | McpServerTool`. `HostedTool`/`McpServerTool` have **no** `parameters: type` because the schema lives provider- or server-side; that alone breaks the canonical `Tool` shape.
2. **`MixedTools requires Tools` + widened `step`.** Tied to the capability- interface mechanism. The canonical `step -> T | ToolCalls` cannot express "the provider is running a tool you only observe." We add a third and fourth arm: `step_mixed -> T | ToolCalls | ComputerCalls | ToolActivity`. This is additive (`requires Tools`), so function-only providers are untouched — but it *is* a new capability the proposal doesn't enumerate.
3. **`ToolActivity` — the observe-but-can't-drive channel.** Tied to the `ToolCall`/`ToolResult` seam. The background: "You observe but don't drive hosted tools." There is no `submit` for a hosted call, so a status that is *emitted, never answered* has no home in the canonical seam. `ToolActivity` carries a **provider-minted** id the loop never sends anything back keyed to — the structural inverse of `ToolCall.id`.
4. **`ComputerCall`/`Screenshot` + `submit_screenshots`.** Tied to the seam again. The hybrid leg drives your code (like `ToolCalls`) but its result is image bytes correlated by `call_id`, not arbitrary `ToolResult.output: unknown`. Overloading `ToolResult` would have lost the wire shape (`computer_call_output` / `input_image`), so it gets its own arm + submit.
5. **`ExecutionContext.perform` + `.observe`.** Tied directly to §7's flagged "`ExecutionContext` needs … an event-`emit` surface." `observe` *is* that emit surface (hosted/MCP status sink); `perform` is the new computer-use callback.
6. **`McpAuth` / `OAuth21` with an RFC-8707 `resource` field.** Net-new types for remote-MCP transport+auth. `resolve_mcp_token` runs the discovery + audience-bound token grant inside the provider; the `resource` URI is what the background calls the thing that makes the model "secure to federate."
7. **`ApprovalDenied implements baml.errors.ToolError` (net-new concrete error).** HITL denial was an ad-hoc `throw baml.errors.LlmClient { message: "denied by operator" }` under the old single channel; it is now a concrete class on the `ToolError` channel that the app catches *by type* (`RunBooking`'s `catch` turns it into an unconfirmed `Booking`). The `Approver.review` and `ExecutionContext.dispatch`/`perform` signatures had to *gain* an explicit `throws baml.ExtendUnknownError<baml.errors.ToolError>` — the old `ExecutionContext` had infallible-looking method signatures even though their bodies threw, which the per-capability channel now forces them to declare. No NEW capability-error *interface* was needed: the whole tool taxonomy — function, hosted, computer-use, MCP, HITL — rides the existing `baml.errors.ToolError`, because every one of them is a leg of the *same* tool loop.

## (c) Where it is awkward, leaky, or unresolved

- **The taxonomy unifies the *type*, not the *catalog* (a real leak).** `HostedTool.kind = "web_search"` lowers to `web_search_20260209` on Anthropic and `{"type":"web_search"}` on Responses; `"code_execution"` lowers to `code_execution_20260120` vs `code_interpreter`. `build_tools` absorbs the rename, but a `kind` a provider *doesn't host* has no compile-time signal — it silently no-ops on the wire or the provider must throw at runtime. The background's "the names and capabilities don't line up … endpoint-gated" problem is **not** solved by the type system here; it's pushed into each provider's `build_tools` match arm. This directly stresses **Open Question 5** (capability `match` over an existential): membership testing tells you the provider implements `MixedTools`, but **not** *which hosted kinds it actually supports*. There is no `provider supports web_search?` predicate short of trying it. A compile-time guarantee that "this client can run code_interpreter" is **unexpressable** without dropping the `client` sugar and inventing a per-kind marker interface — which would explode into one interface per hosted tool per provider.

- **`step_mixed`'s sum type is provider-classification, not model truth.** One Claude/Responses response can interleave a function `tool_use`, a `computer_use`/`computer_call`, and N hosted-tool blocks. We must pick **one** arm per `step`. The native body batches function calls into `ToolCalls` and computer calls into `ComputerCalls`, but a single response carrying *both* a function call you must answer *and* a hosted activity you must observe forces an ordering decision the type doesn't express (we observe, then re-step to surface the function calls). This is the cost of modeling a genuinely concurrent protocol with a sequential `next()`-shaped seam — the `Iterator` analogy strains here in a way it does not for plain function tools.

- **Server-authoritative state is only half-expressible.** For hosted tools and server-side MCP, the *provider* owns the loop: `pause_turn` (Claude) / server-side sampling means the model advances the hosted call without the client. Our loop models this honestly (the `ToolActivity` arm re-steps without submitting), but it means `run_mixed` can spin returning only `ToolActivity` until the provider decides to stop — the client cannot *drive* progress, only poll. There is no way in the proposal to say "this capability is server-driven; my loop is a spectator." We approximate it; we cannot type it. This is the tool-taxonomy face of **Open Question 1** — does every capability really refine `call`? A hosted-tool run is arguably *not* a best-effort single `call`; it's a server-run session the client observes, closer to `Realtime` than to `HttpProvider`.

- **MCP discovery is invisible to types.** "The available capabilities aren't known until connect time." `McpServerTool` is declared statically, but the tools it exposes materialize only after the provider connects. Nothing in the `ToolKind` set reflects discovered tools — they surface only as `ToolActivity` with `source = "mcp:github"`. A caller cannot reference an MCP tool by name at authoring time; it is purely runtime. The type system has nothing to say about a remote catalog, which is correct (it can't) but worth stating plainly.

- **OAuth-flow-inside-`build_tools` is a side-effect smell.** `resolve_mcp_token` runs a multi-step network handshake (401 → `.well-known` → DCR → token) from inside what reads like request serialization. It's behind a `$rust_io_function` and `throws baml.ExtendUnknownError<baml.errors.ToolError>`, so it's honest, but the "transport envelope is not a provider field" rule (§4) sits uneasily with auth that is this stateful living on the provider class. It arguably wants its own combinator layer, like retry — unresolved. There is a second smell now that errors are typed: an OAuth audience-binding failure, an MCP discovery 401, and a token-refresh timeout all flatten into `baml.errors.ToolError` (or, when foreign, `baml.UnknownError` annotated `"… mcp oauth flow failed"`). The classifiers `is_network_error`/`is_rate_limit`/`is_parse_error` say *nothing* about "auth/audience-binding rejected" — the one failure mode the background calls security-critical. The error model gives MCP auth a channel but no vocabulary; expressing it would mean either a concrete `McpAuthError implements baml.errors.ToolError` (which the app can only catch if it knows the provider's class) or a net-new `is_auth_error()` classifier on `ToolError` that every provider must now answer.

- **NEW TENSION — the observe-only channel routes failure as *data*, not as a thrown error.** This is the sharpest place the new model strains for this scenario. A hosted tool that *fails* (`web_search` quota exhausted, `code_execution` sandbox crash, an `mcp_call` the remote server 500s) surfaces through `step_mixed`'s **`ToolActivity` arm** with `phase: "failed"` — it is a returned value, **not** a `throw` on the `baml.errors.ToolError` channel. So the same provider has *two* disjoint failure surfaces for the same loop: typed thrown `ToolError` (transport/parse/refusal on the call leg) and untyped `ToolActivity.phase == "failed"` data (anything the *provider* ran and couldn't). `is_network_error()` will never fire for a hosted-tool network failure, because that failure never becomes a `CallError`/`ToolError` at all — it's an observation. The split is *inherent* (you can't drive or retry a server-run tool, so you can't throw on its behalf), but it means an app's `catch (e) { … baml.errors.ToolError … }` is **structurally blind** to hosted-tool failures; those must be inspected inside `observe`, by hand, with stringly-typed `phase`. The error model's promise — "triage without knowing the concrete class" — holds only for the half of the taxonomy your code drives.

- **Concrete errors are de-typed (not lost) through the existential.** `Run*` functions hold `p = Claude()` as the existential `Provider` and dispatch through `m: MixedTools`. A provider-specific mid-loop error (say an `AnthropicOverloadedError implements baml.errors.ToolError`) is thrown across that existential boundary and reaches the app intact *as* `baml.errors.ToolError` — same value, classifiers live; only its *static* concrete type is hidden behind the existential. Rule 5 says the app can still `catch` it by concrete type via runtime refinement — but only if the app statically *names* `anthropic.AnthropicOverloadedError`, which couples app code back to a provider it deliberately abstracted behind `client Claude()`. In practice these `Run*` functions catch at the interface (`baml.errors.ToolError`) or not at all; the concrete-recovery escape hatch exists but is unused here precisely because the `client` sugar hid the provider. The precision the model offers is real but unreachable without breaking the abstraction the scenario is built on.

## (d) Verdict

**Workable-with-additions.**

The base-`Provider` + capability-interface spine genuinely absorbs the *function tool* case for free and degrades gracefully via `match`. But four of the five tool kinds require real net-new surface — a `ToolKind` union (because the canonical `Tool` can't model schema-less hosted tools), a widened `step` with an observe-only `ToolActivity` arm (because the `ToolCall`/`ToolResult` seam has no slot for a status you can't answer), a computer-use leg, and OAuth-2.1 auth types. None of these *fight* the proposal — they all land as `requires`-style extensions and context callbacks the proposal explicitly anticipated in §7 — but they are substantial, and they expose two things the model genuinely **cannot** express: a compile-time guarantee that a given provider hosts a given tool kind (the catalog/endpoint-gating problem, OQ5), and a typed notion of server-authoritative, client-as-spectator execution (OQ1). The taxonomy unifies at the type level and leaks at the catalog level; that leak is inherent to the domain, but the proposal offers no machinery to even name it.

The **error model** mostly fits: the entire taxonomy collapses onto one `baml.errors.ToolError` channel (no new capability-error interface needed), the per-capability split cleanly puts the `HttpProvider` legs on `CallError` and every tool-loop leg on `ToolError` within the same provider class, `baml.errors.Unsupported`'s membership in all four interfaces makes the negotiation `_` arms legal for free, and the `ApprovalGate` combinator forwards the channel without variance gymnastics. But the model's central promise — *triage by classifier without knowing the concrete class* — covers only the half of the taxonomy your code drives. Hosted/MCP failures arrive as `ToolActivity.phase == "failed"` **data**, never as a thrown `ToolError`, so `is_network_error()`/`is_rate_limit()` are structurally blind to them; and MCP-auth failures — the security-critical mode — have a channel but no classifier vocabulary. The taxonomy that splits by *who executes* re-splits, in the error model, into *who can throw*: only the legs you drive.
