# Evaluation — The agent security threat model (lethal trifecta)

Adversarial read: does the base-`Provider` + capabilities model express the defenses against indirect prompt injection / MCP tool poisoning, or does it leak?

## (a) What the proposal reuses unchanged

- **`Tools` + the `ToolCall`/`ToolResult` seam, verbatim.** The whole taint story rides *below* the loop. `run_tools` is inherited unchanged; the only thing the app swaps is the `ExecutionContext` passed in (`GatedContext`). The proposal's claim that "overriding the loop changes *dispatch policy* and never touches threading" (§7) is exactly what made the gate cheap to write — the allowlist/taint/approval code never had to know about id-vs-name correlation.
- **Capability `match` as the negotiation primitive (§5).** Quarantine is enforced by the *absence* of a `Tools` impl: `SummarizeUntrusted.run_tools` hits the `_` arm and throws. We did not invent an enforcement mechanism; we reused "a companion works iff the provider implements the capability."
- **Combinators wrap a `Provider` (§6).** `Quarantined` is an ordinary combinator with one `implements HttpProvider` block — same shape as `Fallback`, but it forwards *only* the request/response capability (`call`/`call_with`) and nothing else. `quarantined()` is a default method on the `Provider` marker, the `Iterator.map` pattern again.
- **`client` = function returning a `Provider` (§3).** `Reader()`, `Privileged()`, `PrivilegedGemini()` are just functions; the dual-LLM split is "two clients," no new construct.
- **`Tool { parameters: type }` + `reflect.type_of`** for tool schemas, as in §7.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`Tainted<T>` + `TaintSet` (host-owned set).** Tied to: the **content trust boundary the proposal has no primitive for**. The background is explicit — no provider marks content `trusted:false`, so taint is the caller's to build. This is genuinely new state with no home in `Provider`/`Tools`. `TaintSet` is `$rust_type` because it must survive being passed through `ToolResult.output: unknown` and through `Quarantined.call`'s opaque `T`.
2. **`Provenance requires Tools` capability (`label_for`).** Tied to: the **capability-interface mechanism**. It is a *new capability* a Tools provider may implement, defaulting to "labels nothing" — which honestly mirrors the API reality that most providers can't distinguish provenance. Lives below the ToolCall seam so it composes with both id- and name-based providers.
3. **`GatedContext implements ExecutionContext` (allowlist + taint + gate).** Tied to: §7's note that **`ExecutionContext` needs a `dispatch` surface**. We lean on exactly that: `dispatch` is the one chokepoint where every tool call passes, so it is the only correct place for the allowlist and provenance gate.
4. **`Quarantined` combinator (capability subtraction).** Tied to: **combinators wrap a Provider**. New in *intent*: existing combinators *forward* every capability; this one deliberately forwards only the request/response capability (`implements HttpProvider`, routing `call`/`call_with` to the inner http member). The model supports it for free (you simply don't write the other `implements` blocks), which is the nicest result in this scenario — "breaking the trifecta costs capability" is literally encoded as "the combinator's type is missing capabilities." Under the marker model this reads even more cleanly: the quarantined provider *is* a `Provider` (the marker) that implements exactly one capability — request/response — and no live/streaming/tool surface, so the subtraction is the absence of those capability impls, not a degraded version of them.
5. **`scrub_output` + `Approver`/`ApprovalDecision`.** Tied to: ordinary functions/interfaces. The markdown-image channel lives in the *renderer*, which the model API never sees, so it can only be a post-pass — correctly outside the provider.
6. **`BlockedOutboundUrl` / `HumanDeniedCall` as concrete `baml.errors.ToolError`s.** Tied to: the **per-capability error channel**. The gate's two deliberate refusals are *security decisions*, not transport failures — so under the new error model they are concrete classes implementing `baml.errors.ToolError` (all classifiers `false`: a blocked exfil is neither a network error, a rate limit, nor a parse error), thrown on the `GatedContext.dispatch` channel, and caught by type at the call site. This is the security analogue of the canonical `Refused`: the *refusal-as-typed-channel* idea, applied to a policy gate rather than a model decline. No net-new capability-error *interface* was needed — the gate runs *inside* the tool loop, so `ToolError` is the right channel; `dispatch`, `Approver.review`, and `as_provenance` (whose `_` arm throws `baml.errors.Unsupported`, legal on any channel) all declare `baml.ExtendUnknownError<baml.errors.ToolError>`.

## (c) Where it is awkward, leaky, or unresolved

- **No compile-time guarantee that untrusted bytes never reach an exfil tool.** This is the central honesty problem. `Quarantined` makes "no tools" a type fact, but the *taint* itself is runtime data threaded through `unknown` (`ToolResult.output`) and an opaque ledger. BAML's type system cannot say "a `Tainted<T>` value may not flow into `http_post`'s args" — that is a data-flow property (CaMeL-style), and the proposed model has no information-flow types. The gate is a runtime `match`/`if`, defeatable by any provider whose `label_for` under-reports (the default impl labels *nothing*, so a poisoned MCP server the provider doesn't recognize as MCP produces clean-looking results). The proposal is structurally a **runtime** discipline; it cannot promise the static one.

- **Open Question 5 (capability `match` over an existential) is load-bearing twice.** Both quarantine enforcement (`_` arm on `Tools`) and `as_provenance` depend on runtime interface-membership testing against the *concrete* provider behind `client`. If value-level reflection can't reliably answer `match (provider) { let x: Provenance => … }` for a provider produced through a combinator, the whole gate silently degrades to the `_` arm. The proposal flags Q5 as "confirm"; this scenario *requires* it, and requires it to see through a combinator wrapper (does `Quarantined` correctly *not* match `Tools`? does a hypothetical `Fallback` of two Tools providers match `Provenance` only if both do?). That's unresolved.

- **The quarantined model cannot re-type its own output as `Tainted<T>`.** `Quarantined` exposes request/response (`implements HttpProvider`) — good — but a quarantined model's `call` result is untrusted, and the type is still bare `T`, not `Tainted<T>`. The combinator cannot re-type its own output, so the taint wrap is pushed onto the *caller* (`Tainted<PageFacts>.from(SummarizeUntrusted(...), ...)`). A caller who forgets to wrap silently launders the page. The model offers no way to make `Quarantined.call` return `Tainted<T>` without changing `HttpProvider`'s `call`/`call_with` signature for everyone. (Note: OQ1 — "is every provider forced to carry a best-effort `call`?" — is **resolved** by the marker model: `call`/`call_with` live on `HttpProvider`, not on the `Provider` marker, so realtime/harness/pure-capability providers no longer fake a `call`. `Quarantined` opts *into* request/response on purpose. What remains is the narrower, unrelated limitation that `HttpProvider.call`'s fixed `-> T` cannot be specialized to `-> Tainted<T>` per-combinator.) This is the leakiest seam in the scenario.

- **Open Question 7 (host-backed `implements` bodies) is assumed throughout.** `TaintSet`, the ledger, `outbound_urls`, `run_tool` are all `$rust_io_function`. Taint as a host-owned `$rust_type` set means the *propagation* logic (`taint_of_args`, `union`) lives in Rust, not BAML — so the security-critical data-flow is opaque to the BAML reader and untestable in pure BAML. If Q7's "implements block with native bodies is the bridge" is the answer, the trust boundary's actual mechanism sits entirely on the far side of that bridge.

- **Taint laundering across the quarantine handoff.** `Tainted<T>.map` carries the set across a transform, but the moment a value crosses `Quarantined.call` (typed `T`, not `Tainted<T>`, on the `HttpProvider` capability) the taint is dropped by the type and must be manually reattached. The background calls this out as "the hard part," and the model does not solve it — it relocates the obligation to the call site.

- **The error model cannot mark a `ToolError` as security-load-bearing — a failed gate is indistinguishable from a flaky tool until you match its concrete type.** `BlockedOutboundUrl` and `HumanDeniedCall` ride the *same* `baml.errors.ToolError` channel as an ordinary mid-loop transport failure, and the interface's classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) have no "is_security_refusal" axis — all three are `false` for both a blocked exfil and a benign 200-with-no-tools. So a consumer that catches only the *interface* (`let te: baml.errors.ToolError => retry()`) will happily **retry a denied exfil attempt**, re-driving the loop against the same poisoned context. Safety here depends on catching the *concrete* class first; the classifier triage the model offers for ergonomics is actively wrong for this scenario. The new model gives us a typed refusal channel (good) but no way to say "this error must not be swallowed or retried" (the thing a security gate most needs). Adding an `is_policy_refusal()` classifier to `ToolError` would help but is net-new surface, and it would still be advisory — nothing forces the consumer to honor it.

- **A net-new capability (`Provenance`) with no error interface of its own borrows `ToolError`, which is a category slip.** `Provenance.label_for` is pure and total (defaults to "no labels"), so it needs no channel — fine. But `as_provenance`'s capability-negotiation miss throws `baml.errors.Unsupported` on a `ToolError` channel, asserting that "this provider has no provenance" is a *tool* error. It isn't really: provenance is orthogonal to the tool loop (it sits *below* the `ToolCall` seam, per (b)). The model's rule "reuse `CallError`/`StreamError`/`ToolError`/`RealtimeError` when the capability really is one of those" forces a choice, and none of the four fit a *provenance-negotiation* failure cleanly. We picked `ToolError` because the gate consumes provenance, but that conflates "I couldn't get provenance" with "the tool loop failed." A faithful model would mint a `baml.errors.ProvenanceError` interface — but that's net-new, and for a failure that, in practice, only ever surfaces as `Unsupported` (which already implements all four interfaces), so minting it buys almost nothing. This is the new error model's version of the same tension the rest of the scenario has: provenance is real surface the proposal has no first-class home for.

- **MCP tool *poisoning* (description-time attack) is only partially addressed.** Provenance labels tool *results*; it does nothing about a malicious tool *description* or a rug-pull rewrite between connect and call. Nothing in `Tool { name, description, parameters }` is hashed or pinned. The model would need a connect-time `Tool` integrity check that is out of scope for the provider/capability layer entirely.

## (d) Verdict: **Workable-with-additions**

The proposal hosts the *structural* defenses cleanly: dual-LLM/quarantine falls out of capability subtraction (a combinator that implements only `HttpProvider`, forwarding `call`/`call_with` and nothing else), the provenance-aware gate slots into the one `ExecutionContext.dispatch` chokepoint the model already exposes, and the same gate is portable across id-based and name-based providers because everything sits below the `ToolCall` seam. That is a real, non-trivial win — "breaking the trifecta costs capability" becomes a type-level statement. But the *core* of the threat model — keeping untrusted data from reaching a privileged action — is an information-flow property, and the proposed model has no information-flow types: taint is runtime state carried through `unknown` and host `$rust_type`, the gate is a defeatable runtime `if` whose refusal — though now a *typed* `baml.errors.ToolError` (`BlockedOutboundUrl`/`HumanDeniedCall`) rather than an opaque message — is still triageable as "retryable" by a consumer matching only the interface, and the one place the model could have helped (re-typing a quarantined model's output as `Tainted<T>`) is blocked by `HttpProvider.call`'s fixed `-> T` signature (a per-combinator return-type specialization the model can't express — note OQ1's degenerate-`call` worry is itself *resolved* by the marker model, since `call` now lives on `HttpProvider`, not the bare `Provider`). So the model *organizes* the defenses well and *enforces* the coarse one (no-tools) at the type level, but it cannot *guarantee* the fine one. Honest verdict: a good substrate for these patterns, not a proof of their soundness.
