# Server-stored chains + the three ownership models

This scenario asks whether the `Provider`/capability model can express conversations the *provider* holds — OpenAI Responses' `previous_response_id` and `conversations` resource — where the app sends only the new turn and a **handle** to everything before it, never the bytes. The key insight it exercises is that "who owns the conversation" (client-held, server-session, server-stored-by-id) is a property of the *provider and transcript*, not of the prompt: it changes how you formulate every request. `implement.baml` adds a net-new `Chain` capability (with an opaque, owner-tagged `ChainHandle`, modeled on `Tools.Transcript`), keeps Anthropic deliberately client-held to expose the divergence, and guards the "layer a client session over a server chain double-counts" trap. `usage.baml` writes the same geography chat three ways — one per ownership model — and shows the durability win (persist an id, not a transcript) plus the non-portability cost (you cannot migrate the chain). `evaluation.md` stresses where reasoning-continuity and non-migratability stay runtime promises rather than type guarantees.
