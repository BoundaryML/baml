# Evaluation — Server-stored chains + the three ownership models

Adversarial read of whether the `Provider` / capability / `client`-sugar model expresses server-stored conversations (OpenAI Responses' `previous_response_id` and `conversations` resource) and the three ownership models from background §5.

## (a) What the proposal reuses unchanged

- **Capability-as-interface.** `Chain` is just another `interface … requires Provider`, alongside `Streaming`/`Realtime`/`Tools`. No new mechanism: a provider that can hold history server-side `implements Chain`; one that can't (Anthropic) simply omits it. The "capability set *is* the type" rule (proposal §1) carries the whole ownership distinction for free.
- **Opaque associated/threaded handle, exactly like `Tools.Transcript`.** The `ChainHandle` the app threads turn-to-turn is the same design as the Tools loop's provider-owned, app-uninterpreted transcript (proposal §7). We reused that shape verbatim — the app never reads the id, it only forwards it.
- **Runtime capability negotiation by `match`.** `.open`/`.continue` are companions that `match (p) { let c: Chain => …, _ => throw … }`. This is the proposal §5 split applied cleanly: a server-stored chain is a *different interaction shape* (like `Realtime`), so the `_` arm **errors** rather than degrading — a stateless `.call` cannot fake resumption of a server-held chain.
- **`client` sugar absorbs ownership as a field.** `GptChained()` vs `GptStateless()` differ only by `store: true|false` on the same `OpenAIResponses` class. Ownership dissolved into a provider field, exactly as options do in proposal §4. No `client` syntax was touched.
- **One `build_request`, multiple wire encodings.** `build_with_chain` is a single method that emits three different bodies (no prior / `previous_response_id` / `conversation`) — the same "build_request decides where the schema goes" pattern the proposal uses for the four structured-output encodings (§2).

## (b) Net-new surface it must add

- **The `Chain` capability interface** (ties to: capabilities-as-interfaces, proposal §1). The base `Provider.call<T>(prompt) -> T` is *stateless and single-shot by construction*; "continue from where we left off" has no verb there. `Chain.open`/`continue`/`forget`/`preserves_reasoning` is irreducibly new. This is the central addition and it is genuinely net-new — nothing in the conventions cheat-sheet covers server-owned, handle-addressed state.
- **`ChainHandle` + `ChainKind`** (ties to: the `Tools.Transcript` opaque-handle primitive, generalized). Net-new *types*, but they reuse the existing threading pattern. `ChainKind` exists because Responses has **two** handle shapes (`previous_response_id` vs `conversations`); a single opaque id would collapse a real provider divergence.
- **`ChainTurn<T>` (value + next-handle).** Net-new return type. The base `call` returns bare `T`; a chained turn must return the answer *and* the new handle, so the app can thread it. Unavoidable given that `call`'s signature can't grow an out-param.
- **`preserves_reasoning(self) -> bool` as a capability method** (ties to: Open Question 1). Reasoning-continuity is the *reason this layer exists*, yet it is a **runtime** boolean, not a type. The model has no way to make "preserves reasoning" a compile-time guarantee (see (c)).
- **`ClientHeldSession` + a double-counting guard** (ties to: combinator/value layering). The client-held ownership model is a plain threaded value, not a provider — net-new, but small. The guard that refuses to wrap a `Chain` provider is the only place the proposal's "independent layers" reality (background §5) is enforced, and it can only be enforced *dynamically*.
- **`ChainRetry`** (ties to: combinators, proposal §6). The generic `Retry`/ `Fallback` combinators forward `.call` and capability companions, but they **cannot** thread a `ChainHandle` (it is owner-bound; you can't fail over a half-built chain to a different provider). So chain-aware orchestration needs a bespoke combinator. This is a real limit of the "combinators wrap a Provider" story for stateful capabilities.

- **A net-new `baml.errors.ChainError` capability-error interface** (ties to: the per-capability error model). `Chain` is a capability beyond call/stream/realtime/tools, so under the new error model it gets its own channel — every chain method declares `throws baml.ExtendUnknownError<baml.errors.ChainError>` rather than borrowing `CallError`. `ChainError` adds a chain-specific classifier, `is_handle_error()`, alongside the usual `is_network_error()`/`is_rate_limit()`, because the one failure mode this capability invents — *state you cannot migrate* (a foreign-owner or evicted handle) — has no analogue on the call path and an app genuinely wants to triage it separately. The concrete domain errors this scenario raises are now typed classes that `implement` the right interface(s): `ForeignChainHandle` / `ChainNotStored` (`ChainError`, `is_handle_error -> true`), `ChainExhausted` (`ChainError`, retry budget gone), and `DoubleCountedChain`, which `implements` **both** `CallError` and `ChainError` so it is legal whether it surfaces from `ClientHeldSession.ask`'s plain-`.call` channel or from chain-aware code. Foreign transport failures (`baml.http.send`'s `Io`/`Timeout`) are normalized through a trailing `catch (e) { _ => throw baml.UnknownError.with_message<…>(e, "…") }` on every fallible method — the old single `baml.errors.LlmClient` channel is gone.
  - **A consequence the net-new channel forces back onto a spec type:** because `Chain` invents a fresh capability-error interface, `baml.errors.Unsupported` — the capability-negotiation error a companion's `_` arm throws — must be *extended* to `implements baml.errors.ChainError`, since its canonical definition in `_conventions.md` only covers `Call`/`Stream`/`Tool`/`Realtime`. `usage.baml` throws `baml.errors.Unsupported` on the `ChainError` channel (the `_` arms of every `match (p) { let c: Chain => … }`), and under rule 2 that throw is only legal if `Unsupported` implements the channel interface. So *every* net-new capability channel silently obligates a downstream `extend` of `baml.errors.Unsupported`: the "Unsupported is legal on ANY capability channel" promise is not free for capabilities the proposal didn't enumerate — it must be re-established per net-new interface.

## (c) Where it is awkward, leaky, or unresolved

- **No compile-time guarantee of reasoning-continuity (Open Question 5, and the proposal's own §5 admission).** Because `client` returns the existential `Provider`, "this client preserves reasoning across turns" is answered by a runtime `match` plus a runtime `preserves_reasoning()` boolean — never by the type checker. For the *single biggest reason Responses exists*, that is a weak guarantee. The escape hatch (drop the sugar, `function … -> OpenAIResponses`) recovers `Chain`-membership at compile time but **still** can't prove `store == true` or `reasoning_model == true` — those are field values, not types. So even the longhand can't make "reasoning is preserved" a static fact. The proposal has no answer here; this is a genuine expressiveness gap.

- **Open Question 1 bites directly.** "Does every capability `requires Provider`?" `Chain requires Provider`, so a `Chain` provider also has a best-effort stateless `.call`. But for `OpenAIResponses` with `store:false`, `.call` works while `.open` *throws*. The capability is present in the type but conditionally dead at runtime, depending on a field. The model cannot express "this is a Chain only when `store`" — `implements Chain` is unconditional. This is the OQ1 tension ("best-effort single turn, or should some capabilities stand alone") showing up as: a capability whose validity depends on a sibling field.

- **The double-counting hazard can only be caught dynamically.** Background §4's central warning — client-held `Session` + server-held chain = context counted twice — is enforced in `ClientHeldSession.ask` by `match (p) { let c: Chain => throw … }`. That works, but it is a runtime trip-wire, and it is *coarse*: it refuses ALL `Chain` providers even one with `store:false` (which would be safe to wrap). We can't read `store` off the existential to refine the check. The proposal gives no way to say "these two layers are mutually exclusive" at the type level; the best we get is a defensive throw.

- **State you cannot migrate is modeled by a string tag, not the type system.** `ChainHandle.owner: "OpenAIResponses"` and the string compare in `build_with_chain`/`forget`/`continue` is how we refuse cross-provider resumption. It works and it reads honestly, but it is stringly-typed: nothing *prevents* an app from constructing a `ChainHandle { owner: "OpenAIResponses" }` by hand (as `ResumeLater` in fact does to rehydrate from a persisted id). The non-portability of Responses state is real and the model can only *advertise* it, not *enforce* it. A typed, provider-parameterized handle (`ChainHandle<OpenAIResponses>`) would be stronger but the conventions give handles as opaque associated/threaded values, not generics over the provider.

- **`ChainTurn<T>` vs the `call<T> -> T` contract is a slight schism.** The whole proposal leans on "every provider does `call<T>(prompt) -> T`." Chaining can't fit that mold (it must return a handle too), so `Chain` introduces a *parallel* return convention. It's not wrong, but it means a `Chain` provider has two different answer-shapes (`T` from `.call`, `ChainTurn<T>` from `.continue`) and the app must know which world it's in. Open Question 3 ("the request side is HTTP-specific") has a sibling here: the *response* side isn't uniform once state enters.

- **The error model re-opens the very non-migratability hole it seems to close, AND the dual-channel `DoubleCountedChain` is a smell.** Making `ForeignChainHandle` a typed `ChainError` with `is_handle_error() -> true` reads better than a stringly-typed message — but it changes nothing about *enforcement*. The check is still `h.owner != "OpenAIResponses"` against a hand-constructable field (`ResumeLater` builds `ChainHandle { owner: "OpenAIResponses" }` from a bare persisted string), so the typed error only *reports* non-migratability at runtime; it cannot *prevent* a smuggled handle, exactly as the old throw couldn't. Worse, the new model surfaces a fresh tension the single-channel model hid: `DoubleCountedChain` has to `implement` **both** `CallError` and `ChainError` because the double-counting guard lives in `ClientHeldSession.ask`, whose channel is `CallError` (its real work is `p.call`), even though the failure is conceptually a *chain* problem. A single error implementing two unrelated capability interfaces — with two copies of `is_network_error`/`is_rate_limit` that must agree — is the seam where "one independent interface per capability" frays: cross-capability domain errors don't belong to exactly one channel, and the model makes you pick a home (or implement both) rather than express "this is a chain-layering error regardless of how you got here." A related leak: `build_with_chain` is declared on the `ChainError` channel because its one deliberate throw is `ForeignChainHandle`, yet it is also called from `build_request` on the `CallError` channel — only the trailing `with_message<CallError>` normalization makes that legal, which means a `ForeignChainHandle` reaching the plain `.call` path is silently demoted to an `UnknownError` instead of staying a typed handle error. On `.call` there is no prior handle so it can't actually fire, but the typing only *happens* to be sound for a reason the signature doesn't state.

- **Branching is expressible but unguarded.** Re-`continue`ing from the same prior handle branches server-side — we use this in `GeographyChat_ServerStored` (t2 and t2b share turn 1). The model expresses it naturally (a handle is a value; reuse it). But there is no way to express "this handle was already consumed" if a provider DIDN'T support branching — the opaque-handle design assumes every continuation is forkable, which is true for Responses but is a Responses-specific assumption baked into the shared `Chain` interface.

## (d) Verdict: **Workable-with-additions**

The capability-interface spine absorbs server-stored chains cleanly at the *structural* level: `Chain` slots in beside `Streaming`/`Realtime`, the opaque handle reuses the `Tools.Transcript` pattern, ownership dissolves into a `store` field, and the three ownership models become three legible code shapes (handle-threaded, session-threaded, and a guarded double-count failure). What it adds is real but proportionate — one capability interface, a handle type with a two-shape discriminator, a value-typed client-held session, and a chain-specific retry combinator. The model does **not** collapse here. But it cannot express the two things that matter most about this layer as *guarantees*: reasoning-continuity is a runtime boolean, not a type (Open Questions 1 and 5), and non-migratability is a stringly-typed `owner` tag rather than an enforced constraint. Those are exactly the high-stakes properties an engineer would want the compiler to hold, and the existential-`Provider` design pushes them to runtime — consistent with the proposal's own stated tradeoff, but a sharper cost here than for streaming, because getting ownership wrong silently double-bills or silently drops reasoning state. Workable, with the additions above, and with eyes open about what stays dynamic.
