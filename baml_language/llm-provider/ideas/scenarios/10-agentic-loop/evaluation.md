# Evaluation — the agentic loop + stop conditions

Adversarial read of whether the proposed model expresses the agent loop (default loop, stop policy, partial-at-budget, `phase` preservation, per-turn tool filtering) cleanly. Background: `background/02-tools-and-agents.md → ## 2. ★ The tool loop / agentic loop`.

## (a) What the proposal reuses unchanged

- **`Tools` capability, verbatim.** `type Transcript`, `begin/step/submit`, and the default `run_tools` come straight from proposal §7 / `_conventions.md`. The loop being a *default method* is the entire trivial case (`usage.baml` (1)): the app writes a `client` and calls `.run_tools` — zero loop code.
- **`step -> T | ToolCalls` as `Iterator.next -> Item | Done`.** Both providers' `step` return the typed value (Item) or the `ToolCalls` sentinel (Done). The override loops in `Bounded.run_tools` are the same `match`/`while` skeleton as the default — only the policy between turns differs. This is the proposal's central claim and it holds.
- **The `ToolCall`/`ToolResult` id seam keeps threading inside the provider.** OpenAI correlates by `tool_call_id`; Gemini has no ids and correlates by `name + position`. Both satisfy the *same* seam because `GeminiTools` mints synthetic ids in `step` and resolves them back in `submit`. The loop above the seam never learns the difference — so the stop-policy combinator `Bounded` forwards to OpenAI and Gemini with one body.
- **Combinators as `Provider`-returning classes — and they forward the error channel for free.** `Bounded` is a plain class that `implements Tools` (its real interaction), delegating `begin/step/submit` to `inner` and overriding only `run_tools`. Under the marker model it carries NO `implements Provider { call }`: `Provider` is a bare marker, `call` is an `HttpProvider` capability, and `Bounded`'s `inner` is a `Tools` provider with no honest single-turn `call` to forward — so the old degenerate `Bounded.call` is dropped, not faked. Because `Tools requires Provider`, `Bounded` still IS a `Provider` (the marker), so `.with_retry(2)` still chains off it via the inherited combinator factory. Per error-model rule 4, the combinator declares the **same** channel as the capability it forwards: `Bounded`'s `Tools` methods all declare `throws baml.ExtendUnknownError<baml.errors.ToolError>` — no narrow / widen / forward gymnastics, the inner provider's concrete errors pass straight through and are recovered at the app `catch`. This is the combinator pattern unchanged.
- **`client` sugar.** Every variant (`CappedResearcher`, `SmartResearcher`, `FocusedResearcher`) is a zero-arg `client` whose body constructs a `Bounded`. No new syntax: a combinator instance is just an expression of provider type.

## (b) Net-new surface it must add (each tied to a primitive)

- **`History` (opaque read view) + `Tools.history(t)`.** Stop predicates and tool filters must *observe* progress without reading the wire format. The proposal gives `Transcript` (opaque, write-through via submit) but no read projection. `History` is a second opaque type companion to `Transcript`, plus a `history` method on the `Tools` interface. Tied to: the `Transcript` associated type.
- **Stop-predicate type `(StepInfo) -> bool` + `StepInfo`.** The `stopWhen` knob has no analogue in §7's `run_tools` (which loops forever). `StepInfo { step, history }` and the constructors `step_count_is` / `has_tool_call` / `any_of` are net-new — but they are *ordinary BAML closures and free functions*, not new language surface. Tied to: closures + `History`.
- **`Budget<T>` + the `T | Budget<T>` return of `run_to_budget`.** "Partial result at the cap" (background §2) has no home in `run_tools -> T`: the default loop can only return `T` or diverge. We add an outer sum `T | Budget<T>`, mirroring `step`'s inner `T | ToolCalls` one level up. Tied to: the same union-return shape the proposal already uses for `step`.
- **A per-turn tool filter `(int, History) -> Tool[]` + `inner_set_tools`.** The `Tools` interface fixes the tool list at `begin`. To change it per turn we poke `t.tools` between rounds via a host helper. Tied to: `Tool` type + `Transcript`. This is the leakiest addition — see (c).
- **Helpers over `History`** (`history_contains_tool_call`, `history_last_assistant_text`). Host-backed narrow queries so policy code never parses the wire format. Tied to: `$rust_io_function` boundary.

## (c) Where it is awkward, leaky, or unresolved

- **Per-turn tool filtering breaks the `Transcript` abstraction (OQ not covered by any of the 7).** `inner_set_tools(t.inner, ...)` mutates the *inner* provider's opaque transcript from *outside* the provider. The whole point of `Transcript` being an associated opaque type is that only the provider touches it. To filter tools per turn, `Bounded` must reach in. Two honest fixes, both net-new: (i) add `set_tools(self, t, tools)` to the `Tools` interface so the provider re-renders its own wire envelope; or (ii) make `begin`/`submit` take the tool list each round. As written this is a host shim that quietly assumes every provider stores tools in a pokeable field — false for a provider that inlines tool schemas into a cached prompt prefix. **This is genuinely awkward.**

- **`phase` preservation is invisible at the model layer — by design, but it is a trust-me.** OpenAI's `phase` (`commentary` vs `final_answer`) must be kept on the assistant turn and re-sent (background §2). In our model that lives entirely inside `OpenAITools.step` (`openai_assistant_message(turn)` carries `phase`). Good: the seam above never sees it. Bad: there is **no compile-time guarantee** a provider preserves `phase` — `GeminiTools` has no `phase` and that is correct, but a buggy `OpenAITools` that drops it type-checks fine. The model has no way to express "this capability must round-trip assistant metadata." Engages **OQ #4** (the `Body`/parse seam): the request-side analogue — *what an assistant turn must carry back into the next request* — has no associated type at all, so per-provider history fidelity is unchecked.

- **`Budget` via a thrown `BudgetHit` is a smell — now doubly so under the per-capability error model.** `run_tools` is fixed at `-> T` by the interface, so the only way to surface a partial from an *override* of it is to throw and re-catch in `run_to_budget`. That works (`throws` is the typed channel) but means the budget path is an exception, not a value, until the wrapper normalizes it. Under the new model the cost is concrete: `run_tools` declares `throws baml.ExtendUnknownError<baml.errors.ToolError>`, and rule 2 says *a throw is legal iff it implements the capability interface or routes through `UnknownError`*. So `BudgetHit` — a pure control signal, not a failure — is forced to `implements baml.errors.ToolError` with three classifiers that are vacuously `false`, just to be throwable on the channel. The error model has no notion of a "non-error control throw"; a budget cap masquerades as a `ToolError`, and any consumer catching `baml.errors.ToolError` broadly (not the concrete `BudgetHit`) would silently swallow the budget signal as if it were a transport failure. A cleaner model would let a capability *widen its own default method's return type* — which the interface does not allow. (Under the marker model nothing is "the irreducible base method" anyway — `run_tools` is just the `Tools` capability's default loop — so the open question is purely local: should `Tools` expose a `run_tools<T> -> T | Budget<T>` variant rather than forcing the partial through `throws`?)

- **Retry around a `Tools` loop is statically claimed, semantically dubious.** `usage.baml` (6) writes `Bounded{...}.with_retry(2)`. `with_retry` is a `Provider`-marker factory that produces a `Retry`; `Retry` forwards `HttpProvider.call`, not `run_tools`. Under the marker model `Bounded` no longer even *has* a `call` (it dropped the degenerate `implements Provider { call }`), so `.with_retry(2)` over a Tools-only combinator can retry nothing on the call path — and if `Retry` blindly forwards `Tools`, it retries the *entire* multi-turn loop from scratch, re-dispatching every tool (re-charging side effects). The proposal's "a combinator statically claims every capability it forwards" bites here: `Retry` cannot retry a loop sanely. The model lets you write it; it does the wrong thing at runtime. The real gap is that combinator forwarding is unaware of the loop's statefulness — orthogonal to the marker revision, which only makes the absence of a single-turn `call` on `Bounded` honest rather than faked.

- **`stopWhen` only sees the past — faithfully, and that is a limitation we inherit, not introduce.** `StepInfo.history` is a post-step snapshot; a predicate cannot make the model "try once more" (background §2). Our model reproduces exactly this asymmetry. Not a flaw of the proposal, but worth noting the proposal gives no extra leverage here either.

- **The error model forces the loop's domain failures onto `ToolError`, flattening a call-path/loop distinction. (NEW under the per-capability model.)** Every `Tools` method now declares `throws baml.ExtendUnknownError<baml.errors.ToolError>`, replacing the old single `type Error = baml.errors.LlmClient` channel. A refusal is the sharp case: `OpenAITools.step` parses the *final* assistant content and a decline (`message.refusal` / Gemini `finishReason: "SAFETY"`) is a typed `Refused`. But `Refused` is identically a single-turn `HttpProvider.call`-path failure (it `implements` *both* `baml.errors.CallError` and `baml.errors.ToolError`), so the same concrete error rides two different capability channels depending on whether it surfaced inside a `Tools.step` or inside an `HttpProvider.call` on some other provider. The app's `catch` recovers concreteness at runtime (`let r: Refused =>`), which is exactly the model's promise — but the static channel type (`ToolError` vs `CallError`) no longer tells you *where* the refusal came from. The per-capability split buys triage-by-classifier and loses the call-vs-loop provenance the old monolithic channel never had to choose between. **Honest tension: the same domain error implementing N capability interfaces means the channel type is not a reliable witness of the failure's origin.**

- **Normalizing foreign host failures inside the loop is per-method boilerplate, and the breadcrumb is the only provenance left.** Each of `begin/step/submit/history` on both providers ends in `} catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.ToolError>(e, "<provider> <op> failed"); }`. This is correct (foreign host-boundary failures from `openai_chat_once` / `gemini_generate_once` are not classified `ToolError`s, so they route to `UnknownError`) and rule 3 guarantees the trailing catch never swallows a deliberately-thrown `Refused`/`BudgetHit` because `with_message<ToolError>` returns a known `ToolError` unchanged. But it means a transport failure mid-loop reaches the app only as `baml.UnknownError` with a `message: ["gemini step failed"]` breadcrumb — there is no `is_network_error()` to branch on, because we declined to mint a concrete classified `NetworkError` for a boundary that was never classified before. The loop's many host boundaries multiply this: the partial-progress an agent had accumulated is *gone* the moment any one of N per-turn host calls throws something exotic, and the app cannot tell a timeout from a JSON-decode failure without reading prose.

- **"What counts as a step" is provider-defined and unchecked.** `step_no` increments per `ToolCalls`-bearing round-trip in `Bounded`. A provider that batches parallel calls into one `step` vs one that splits them would make `step_count_is(8)` mean different things — exactly the background's "8 is not always the same thing." The model has no place to *declare* a step's unit, so portability of a numeric cap is nominal, not semantic.

## (d) Verdict: **Workable-with-additions**

The spine fits unusually well: `run_tools` as a default method makes the trivial case free, the `T | ToolCalls` seam keeps OpenAI's id-correlation and Gemini's name+position correlation behind one interface, and stop policy lives in a `Bounded` `run_tools` override that never touches the wire — proving the proposal's headline claim that dispatch policy and threading are separable. But three additions are mandatory (a read-only `History` projection, a `Budget<T>` partial-return, and a `set_tools` hook on `Tools`), and two are awkward: per-turn tool filtering forces a write into the inner provider's opaque transcript, and the budget partial has to travel through `throws` because a default method's return type is frozen by its interface. None of these are fatal, and all are local to the `Tools` capability rather than the base model — hence *Workable-with-additions* rather than *Clean*. The one thing the model genuinely **cannot express** is a compile-time guarantee that a provider preserves assistant-turn metadata (`phase`); that fidelity is a runtime trust boundary, the same class of gap as capability negotiation being a runtime promise.
