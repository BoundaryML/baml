# Evaluation — Async jobs: background + poll

Adversarial. The question is not "can we hack this in" but "does the proposal's model — base `Provider`, capabilities that `requires Provider`, `client` as sugar, combinators that wrap — actually *fit* a fourth request lifecycle whose defining property is that **the server owns durable state and the client comes back by id**."

## (a) What the proposal reuses unchanged

- **`requires Provider` capability shape.** `Background requires Provider` is the exact same move as `Streaming` / `Realtime` / `Tools`: a concrete provider implements the base plus this. `OpenAIResponses` and `AnthropicBatch` each carry `implements HttpProvider` (the foreground face) *and* `implements Background` in separate blocks — the `ArrayIterator implements Iterable + Iterator` pattern, reused verbatim.
- **Default method over irreducible verbs.** `Background.await` is a default method built on `submit`/`poll` — structurally identical to `Tools.run_tools` over `begin`/`step`/`submit`, and to `HttpProvider.call` over `build_request`/`send`/ `parse`. No new language feature.
- **Capability negotiation = a `match`.** The `.background` companion `match`es the client's provider against `Background` and **errors** on the `_` arm (case G). It reuses the proposal's own taxonomy: this is a *different interaction shape*, not a *delivery refinement*, so — like `Realtime.live` — there is no honest fallback to `.call`.
- **`client` as config-only sugar.** `BigAnalysis()` is `function … -> Provider`; the durable handle, the idempotency key, and the cadence are all supplied *at the call*, never in the client. This is the §3 rule ("live, execution-time handles are parameters of the capability method, not the client") applied cleanly to a job id.
- **Combinator-vs-field split.** Cadence/backoff and deadline are *not* provider fields; they live in `Cadence` / `Poller`, wrapping the provider — the §4 / §6 "transport envelope and orchestration wrap, they don't embed" rule, reused.
- **`reflect.type_of<T>()` + SAP** for the structured result, `baml.http` for the GET-by-id and the second batch fetch — all unchanged.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Background` capability interface** — *tied to: "capabilities are interfaces that `requires Provider`."* It is new the same way `Tools` is new; it slots in without amending the base. ✅ in-model.
- **`Job<T>` handle type** — *tied to: associated/opaque provider-owned state, like `Tools.Transcript`.* The base `Provider.call<T>` is single-shot and has nowhere to put "here is an id, come back later," so the handle is irreducible. Note it is a **generic class the app holds**, not an associated `type` on the interface (unlike `Tools.Transcript`) — because the app must *persist and re-hydrate* it across processes, so its shape must be nominal and serializable, not opaque-to-the-app. That is a real deviation from the `Transcript` precedent (see (c)).
- **`JobStatus` enum + `JobState<T>`** — *tied to: nothing in the proposal.* The proposal has no vocabulary for **server-authoritative lifecycle state**. `call` is binary (returns `T` or `throws`); `Streaming` is delta-or-done; `Tools.step` is `T | ToolCalls`. A five-state queued/running/done/failed/cancelled machine that the *server* owns is genuinely outside the current surface. This is the largest net-new piece.
- **`Cadence` interface (+ `Fixed`/`Backoff`)** — *tied to: combinator/host-policy layer.* New, but trivially in-model: a swappable strategy object passed to a method.
- **`Poller` combinator** — *tied to: §6 combinators.* But see (c): it is **not** a `Provider` combinator and cannot be one.
- **Host seams:** `baml.sys.sleep_ms` (the only blocking wait the runtime must expose for a poll loop), `baml.rand.idempotency_key`, `baml.http.with_header`, `baml.http.jsonl_find` (Anthropic's batch results are JSONL). `sleep_ms` is the notable one — *the proposal's runtime has never needed a first-class sleep before*; every other lifecycle is event- or response-driven.

## (c) Where it is awkward, leaky, or unresolved

1. **Server-authoritative state has no home in the model — and the proposal admits it can't express it.** Open Question 1 asks whether every capability should `requires Provider` (best-effort single turn). Here `Background.call` = `await`, which is *fine* — but the deeper issue is that `JobStatus` is **the server's truth, not ours**, and the type system cannot encode "this value is only valid until the next poll." Two `poll`s seconds apart legitimately disagree. The proposal's whole stance is value-level (`call` returns a *value*); a job is a *reference to mutable remote state*. We model it as "re-read every time," which is correct but means `Job<T>` is a pointer wearing a value's clothes. **The background doc's own conclusion — "the primitive has to be event-shaped, with single-shot as the degenerate" — applies here too: background+poll is request/response only at the wire, but its *semantics* are a tiny state machine the proposal has no primitive for.** We had to invent `JobState`.

2. **`Poller` cannot be a `Provider` combinator — the §6 "forward every capability" story breaks.** A `Fallback` forwards `.call`/`.stream`/`.live` by `match`ing its members. It **cannot** forward `submit`/`poll`: a `Job<T>` id is *owner-bound* (`job.owner` check), so a Fallback that submitted via member A cannot poll via member B, and a member that fails *after* submit has already consumed a durable, possibly-billable server job. So `Poller` wraps a single `Background` and the fluent `with_retry`/`fallback_to`/`cached` defaults inherited from `Provider` are **actively wrong** for the job lifecycle (they'd retry the blocking `await`, double- submitting). The proposal's "a combinator statically claims every capability it forwards, degrading at call time" tradeoff (§6) is *more* dangerous here than for streaming: a degraded `.stream` wastes tokens; a wrongly-retried `submit` spawns a second multi-minute, billed job. **The model does not stop you from writing `BigAnalysis().with_retry(3)` and getting silent double-submits.**

3. **The store/ZDR tension is expressible but only as a runtime throw, not a type.** `background:true` requires `store:true`; ZDR forbids storage. We catch it at `background()` construction and again in `build_responses`. But the proposal has *no way to say "this provider is Background **iff** store is true" at the type level* — `store` is a runtime field, so `implements Background` is unconditional and a `store:false` instance is a `Background` that throws on first `submit`. This is the same runtime-promise weakness as capability negotiation generally (§5 "drop the sugar for compile-time precision"), but here it bites harder because the precondition is a *field value*, not a *capability*, and the escape hatch (concrete return type) cannot encode a field-value constraint either.

4. **`Job<T>` deviates from the `Transcript` precedent and exposes a typing gap.** `Tools.Transcript` is an *opaque associated type* the app threads but never inspects or persists. `Job<T>` must be **persisted across processes** (case C), so it is a concrete, serializable class with a hand-readable `id`/`owner`. When the app re-hydrates it in `CheckReview`, *nothing checks that `row.owner` actually matches the client `BigAnalysis()`* — the app could load an `AnthropicBatch` id and poll it with `OpenAIResponses`; only the runtime `owner` string guard inside `poll` catches it, as a throw. The proposal gives us no static correlation between a `Job<T>` and the provider that can poll it.

5. **Webhook delivery is unmodeled.** Background §"what varies" lists three ways to learn a job finished: poll, stream-progress, webhook. We modeled **poll** cleanly and could fold **stream-progress** into the existing `Streaming` capability (a `background:true, stream:true` reconnect). But a **webhook** inverts control — the *provider* calls *us* — and there is no primitive in the proposal for an inbound HTTP handler. That is a server/runtime concern the `client`/`Provider` model genuinely does not reach; it belongs to deployment shape, and we left it out honestly rather than fake it.

6. **`await` blocks a runtime that may not want to block.** `baml.sys.sleep_ms` in a loop is fine in a worker but wrong in a serverless function billed by wall-clock or in a UI thread. The proposal has no notion of "suspend and resume" — so `await` is only safe in some deployments, and the *correct* usage (case C, poll-once-and- return) is the one that doesn't use the model's marquee `await` default at all.

## (d) Verdict: **Workable-with-additions**

The capability mechanism carries background+poll surprisingly far: `Background requires Provider`, `submit`/`poll`/`cancel` as irreducible verbs with `await` as a default, the `.background` companion that errors-not-degrades, and config-only clients all fall straight out of the existing model, and the two wildly divergent wire shapes (OpenAI inline-result vs Anthropic batch-of-one-with-a-second-JSONL-fetch) hide behind one `Job<T>` so application code is byte-identical. That is a genuine win. But three additions are unavoidable and one is a real limit. The additions: a server-state vocabulary (`JobStatus`/`JobState`) the proposal simply lacks; a first-class blocking `sleep`; and a job-shaped combinator (`Poller`) that is pointedly **not** a `Provider` combinator. The limit: the model cannot express, at the type level, the two constraints that matter most here — "Background-only-if-stored" (store/ZDR) and "this combinator must not retry a submit" — so both are runtime throws, and the §6 inherited `with_retry`/`fallback_to` defaults are *silently unsafe* on a Background provider (double-submit). And webhooks fall outside the model entirely. It is not Clean (too much net-new and one foot-gun the model invites), but it is well short of Unsupported: every divergence the background doc names is absorbed, with the honest caveat that server-authoritative durable state is modeled by convention (re-read every poll, owner-bound handle) rather than guaranteed by the type system.
