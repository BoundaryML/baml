# Evaluation — Async jobs: background + poll

Adversarial. The question is not "can we hack this in" but "does the proposal's model — base `Provider`, capabilities that `requires Provider`, `client` as sugar, combinators that wrap — actually *fit* a fourth request lifecycle whose defining property is that **the server owns durable state and the client comes back by id**."

## (a) What the proposal reuses unchanged

- **`requires Provider` capability shape.** `Background requires Provider` is the exact same move as `Streaming` / `Realtime` / `Tools`: a concrete provider implements the base plus this. `OpenAIResponses` and `AnthropicBatch` each carry `implements HttpProvider` (the foreground face) *and* `implements Background` in separate blocks — the `ArrayIterator implements Iterable + Iterator` pattern, reused verbatim.
- **Default method over irreducible verbs.** `Background.wait_for` is a default method built on `submit`/`poll` — structurally identical to `Tools.run_tools` over `begin`/`step`/`submit`, and to `HttpProvider.call` over `build_request`/`send`/ `parse`. No new language feature. (It is named `wait_for`, not `await`: `await` is now the BEP-034 reserved keyword for awaiting an in-process `baml.future.Future`, and this server-side poll loop is a different mechanism — see (c.6).)
- **Capability negotiation = a `match`.** The `.background` companion `match`es the client's provider against `Background` and **errors** on the `_` arm (case G). It reuses the proposal's own taxonomy: this is a *different interaction shape*, not a *delivery refinement*, so — like `Realtime.live` — there is no honest fallback to `.call`.
- **`client` as config-only sugar.** `BigAnalysis()` is `function … -> Provider`; the durable handle, the idempotency key, and the cadence are all supplied *at the call*, never in the client. This is the §3 rule ("live, execution-time handles are parameters of the capability method, not the client") applied cleanly to a job id.
- **Combinator-vs-field split.** Cadence/backoff and deadline are *not* provider fields; they live in `Cadence` / `Poller`, wrapping the provider — the §4 / §6 "transport envelope and orchestration wrap, they don't embed" rule, reused.
- **`reflect.type_of<T>()` + SAP** for the structured result, `baml.http` for the GET-by-id and the second batch fetch — all unchanged.
- **The per-capability error model.** Foreign transport failures (`baml.http.send`, SAP parse, JSONL fetch) are normalized through one trailing `catch (e) { _ => throw baml.UnknownError.with_message<…>(e, "…") }` per method instead of the old hand-rolled `throw baml.errors.LlmClient { message }`. Deliberate domain failures become concrete typed errors (`JobFailed`/`JobCancelled`/`PollDeadlineExceeded`/`WrongOwnerJob`) that the consumer catches most-specific-first (`ReviewRepoOrPlaceholder`), then the `baml.errors.BackgroundError` interface via `is_rate_limit()`, then `baml.UnknownError`. The old single `type Error = baml.errors.LlmClient` channel — which collapsed "server failed the job", "we gave up polling", and "the socket died" into one opaque string — is gone; those are now distinguishable by type and by `is_terminal_job_failure()`.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Background` capability interface** — *tied to: "capabilities are interfaces that `requires Provider`."* It is new the same way `Tools` is new; it slots in without amending the base. ✅ in-model.
- **`Job<T>` handle type** — *tied to: associated/opaque provider-owned state, like `Tools.Transcript`.* The base `Provider.call<T>` is single-shot and has nowhere to put "here is an id, come back later," so the handle is irreducible. Note it is a **generic class the app holds**, not an associated `type` on the interface (unlike `Tools.Transcript`) — because the app must *persist and re-hydrate* it across processes, so its shape must be nominal and serializable, not opaque-to-the-app. That is a real deviation from the `Transcript` precedent (see (c)).
- **`JobStatus` enum + `JobState<T>`** — *tied to: nothing in the proposal.* The proposal has no vocabulary for **server-authoritative lifecycle state**. `call` is binary (returns `T` or `throws`); `Streaming` is delta-or-done; `Tools.step` is `T | ToolCalls`. A five-state queued/running/done/failed/cancelled machine that the *server* owns is genuinely outside the current surface. This is the largest net-new piece.
- **`Cadence` interface (+ `Fixed`/`Backoff`)** — *tied to: combinator/host-policy layer.* New, but trivially in-model: a swappable strategy object passed to a method.
- **`Poller` combinator** — *tied to: §6 combinators.* But see (c): it is **not** a `Provider` combinator and cannot be one.
- **Host seams:** essentially none are net-new. The poll loop's cooperative wait is `baml.sys.sleep` (BEP-034 already ships it — it yields, it does not peg a thread). The dedupe key is `baml.id.new()` (the real runtime id; a general UUID would be a separate gap, but `baml.id.new()` suffices for idempotency). The Idempotency-Key and Anthropic header trio are plain `map<string, string>` literals, not sugar functions. Anthropic's JSONL results file is scanned with **real** stdlib — `resp.text().lines().filter(..).map(..).find(..)` over typed wire classes decoded with `baml.json.from_json<…>` — so there is no `jsonl_find` host primitive to add. Request bodies are native `map<string, json>` literals serialized with `baml.json.stringify`; responses are read with `baml.json.from_json<T>` into typed wire classes (Response has no `.json_path`). All of that is existing surface.
- **`baml.errors.BackgroundError` capability-error channel** — *tied to: the error model's "any NEW capability → a NEW `baml.errors.<Cap>Error` interface, same shape."* `submit`/`poll`/`cancel`/`wait_for` are none of call/stream/realtime/tools, so they declare `throws baml.ExtendUnknownError<baml.errors.BackgroundError>`. The interface carries the usual `is_network_error` / `is_rate_limit` **plus a background-specific classifier `is_terminal_job_failure`** — the axis no existing channel has: did the SERVER kill the job (re-submit) or did we merely time out polling (re-drive)? Concrete members: `JobFailed { reason }`, `JobCancelled`, `PollDeadlineExceeded { job_id }`, `WrongOwnerJob { expected, actual }`, and `ZdrIncompatible` (which implements **both** `CallError` and `BackgroundError`, since the store/ZDR guard fires on the call path *and* the submit path). This slots in exactly like `CallError` — but it is the first scenario to need a fifth core channel, and it exposes the tension in (e).

## (c) Where it is awkward, leaky, or unresolved

1. **Server-authoritative state has no home in the model — and the proposal admits it can't express it.** Open Question 1 asks whether every capability should `requires Provider` (best-effort single turn). Here `Background.call` = `wait_for`, which is *fine* — but the deeper issue is that `JobStatus` is **the server's truth, not ours**, and the type system cannot encode "this value is only valid until the next poll." Two `poll`s seconds apart legitimately disagree. The proposal's whole stance is value-level (`call` returns a *value*); a job is a *reference to mutable remote state*. We model it as "re-read every time," which is correct but means `Job<T>` is a pointer wearing a value's clothes. **The background doc's own conclusion — "the primitive has to be event-shaped, with single-shot as the degenerate" — applies here too: background+poll is request/response only at the wire, but its *semantics* are a tiny state machine the proposal has no primitive for.** We had to invent `JobState`.

2. **`Poller` cannot be a `Provider` combinator — the §6 "forward every capability" story breaks.** A `Fallback` forwards `.call`/`.stream`/`.live` by `match`ing its members. It **cannot** forward `submit`/`poll`: a `Job<T>` id is *owner-bound* (`job.owner` check), so a Fallback that submitted via member A cannot poll via member B, and a member that fails *after* submit has already consumed a durable, possibly-billable server job. So `Poller` wraps a single `Background` and the fluent `with_retry`/`fallback_to`/`cached` defaults inherited from `Provider` are **actively wrong** for the job lifecycle (they'd retry the blocking `wait_for`, double- submitting). The proposal's "a combinator statically claims every capability it forwards, degrading at call time" tradeoff (§6) is *more* dangerous here than for streaming: a degraded `.stream` wastes tokens; a wrongly-retried `submit` spawns a second multi-minute, billed job. **The model does not stop you from writing `BigAnalysis().with_retry(3)` and getting silent double-submits.**

3. **The store/ZDR tension is expressible but only as a runtime throw, not a type.** `background:true` requires `store:true`; ZDR forbids storage. We catch it at `background()` construction and again in `build_responses`. But the proposal has *no way to say "this provider is Background **iff** store is true" at the type level* — `store` is a runtime field, so `implements Background` is unconditional and a `store:false` instance is a `Background` that throws on first `submit`. This is the same runtime-promise weakness as capability negotiation generally (§5 "drop the sugar for compile-time precision"), but here it bites harder because the precondition is a *field value*, not a *capability*, and the escape hatch (concrete return type) cannot encode a field-value constraint either.

4. **`Job<T>` deviates from the `Transcript` precedent and exposes a typing gap.** `Tools.Transcript` is an *opaque associated type* the app threads but never inspects or persists. `Job<T>` must be **persisted across processes** (case C), so it is a concrete, serializable class with a hand-readable `id`/`owner`. When the app re-hydrates it in `CheckReview`, *nothing checks that `row.owner` actually matches the client `BigAnalysis()`* — the app could load an `AnthropicBatch` id and poll it with `OpenAIResponses`; only the runtime `owner` string guard inside `poll` catches it, as a throw. The proposal gives us no static correlation between a `Job<T>` and the provider that can poll it.

5. **Webhook delivery is unmodeled.** Background §"what varies" lists three ways to learn a job finished: poll, stream-progress, webhook. We modeled **poll** cleanly and could fold **stream-progress** into the existing `Streaming` capability (a `background:true, stream:true` reconnect). But a **webhook** inverts control — the *provider* calls *us* — and there is no primitive in the proposal for an inbound HTTP handler. That is a server/runtime concern the `client`/`Provider` model genuinely does not reach; it belongs to deployment shape, and we left it out honestly rather than fake it.

6. **`wait_for` holds *this process* open for a wall-clock-long server job.** `baml.sys.sleep` in a poll loop yields cooperatively (it does *not* peg a thread), so this is not a "the runtime can't suspend" gap — BEP-034 structured concurrency gives the runtime exactly a cooperative suspend/resume scheduler, and you can even `spawn { client.wait_for(...) }` to drive several jobs concurrently and `await` the resulting `baml.future.Future`s. The real limit is *process lifetime*, not scheduling: `wait_for` keeps THIS process alive for the (possibly multi-minute) duration, which is wrong in a serverless function billed by wall-clock or behind a short request timeout. The whole point of a *background* job is that its durability is **server-side** — the job survives this process dying — so the deployment-correct usage (case C, submit + persist the handle + poll-once-and-return from a later request, or a `spawn`ed `wait_for` whose `Future` you do not block on in the request path) is the one that does NOT sit in `wait_for`. So `wait_for` is the right convenience for a CLI/worker that genuinely wants to wait, and the wrong one for a request handler — a deployment-shape choice, not a missing-primitive one. (Note the symmetry: in-process `spawn`/`await`/`Future` is for concurrency *within* this runtime; background `submit`/`poll` is for durability *outside* it. They compose but are orthogonal.)

## (e) Where the NEW error model bites — honest tensions

1. **A new capability needs one external `implements` row to admit `Unsupported` — cheap, but unenforced.** The error model's canonical `baml.errors.Unsupported` implements exactly the **four** core capability-error interfaces (Call/Stream/Realtime/Tool). The moment this scenario introduces `baml.errors.BackgroundError` (rule 4), the `.background` companion's `_` arm wants to `throw baml.errors.Unsupported`, which is legal on the new channel only once `Unsupported` is admitted to it. But this is **not** a retroactive widening of a "closed" core type, and not a forward-reference wall: because BAML `implements` is a Rust-like trait relation that admits *external* impls (implement your interface for a parent-package type), the `BackgroundError` author writes one row **alongside the new channel, in its own package** — `implements baml.errors.BackgroundError for baml.errors.Unsupported` — and `Unsupported` now rides the `BackgroundError` channel as its typed self. The conventions file's `Unsupported` declaration does **not** grow a fifth block; the new capability supplies the coverage from its own side. So this is a *coverage convention*, not the open-vs-closed tension it first appeared to be — the only residual is that nothing *forces* the row: a capability that forgets it gets a type error at the first `_` arm rather than a silent gap (a blanket `implements <Cap>Error for baml.errors.Unsupported` shipped with each capability template closes it by construction). `TryBackgroundOnPlain` typechecks once that one row is present.

2. **`is_terminal_job_failure` is a classifier the interface contract can't make every member answer correctly.** The model's value proposition is "triage without knowing the concrete class" via shared classifiers. But the background-specific axis (terminal server failure vs poll-timeout) is meaningless for a *foreign* error routed through `baml.UnknownError` — and `UnknownError` doesn't implement `BackgroundError` at all, so a consumer holding `baml.errors.BackgroundError | baml.UnknownError` **cannot** call `is_terminal_job_failure()` until it has narrowed away the `UnknownError` arm. The classifier is only present on the *typed* half of the channel, so the very triage the interface promises (decide re-submit vs re-drive) is unavailable for precisely the transport failures most likely to interrupt a multi-minute poll loop. The app must fall through to the `UnknownError` arm and then *cannot tell* whether re-submitting is safe — the double-submit foot-gun (c.2) re-appears, now in the error-handling path.

3. **`ZdrIncompatible` implementing two channels is correct but proves the channel taxonomy is leaky.** `build_responses` is shared by `build_request` (CallError) and `submit` (BackgroundError), so its one guard error has to implement both interfaces. That works — but it means a single deliberate domain error is **simultaneously a `CallError` and a `BackgroundError`**, and a consumer catching `baml.errors.CallError` on a plain `.call` will catch a ZDR violation it could only have triggered via background. The "one capability, one channel" story is already an approximation the first time a helper straddles two capabilities; the more capabilities a provider fuses through shared builders, the more concrete errors will wear multiple channel hats, and the consumer's most-specific-first `catch` cannot rely on "this came from the call path."

## (d) Verdict: **Workable-with-additions**

The capability mechanism carries background+poll surprisingly far: `Background requires Provider`, `submit`/`poll`/`cancel` as irreducible verbs with `wait_for` as a default (named to avoid colliding with the BEP-034 `await` keyword for in-process `Future`s — server-side durability and in-process concurrency are orthogonal mechanisms), the `.background` companion that errors-not-degrades, and config-only clients all fall straight out of the existing model, and the two wildly divergent wire shapes (OpenAI inline-result vs Anthropic batch-of-one-with-a-second-JSONL-fetch) hide behind one `Job<T>` so application code is byte-identical. That is a genuine win. But two additions are unavoidable and one is a real limit. The additions: a server-state vocabulary (`JobStatus`/`JobState`) the proposal simply lacks; and a job-shaped combinator (`Poller`) that is pointedly **not** a `Provider` combinator. (The poll loop's cooperative sleep is *not* an addition — BEP-034's `baml.sys.sleep` already provides it.) The limit: the model cannot express, at the type level, the two constraints that matter most here — "Background-only-if-stored" (store/ZDR) and "this combinator must not retry a submit" — so both are runtime throws, and the §6 inherited `with_retry`/`fallback_to` defaults are *silently unsafe* on a Background provider (double-submit). And webhooks fall outside the model entirely. The new per-capability error model is a clear improvement here — `JobFailed` / `PollDeadlineExceeded` / `WrongOwnerJob` are now distinct types instead of one opaque `LlmClient` string, and `is_terminal_job_failure()` encodes the re-submit-vs-re-drive decision — but it surfaces its own tensions (e): a fifth channel that needs one external `implements` row to admit `Unsupported` (a coverage convention the `BackgroundError` author supplies from its own package, not a retroactive widening of a "closed" core type), a classifier that's absent on the `UnknownError` half of the channel exactly when poll loops fail, and a shared-builder error (`ZdrIncompatible`) that wears two channel hats at once. It is not Clean (too much net-new and one foot-gun the model invites), but it is well short of Unsupported: every divergence the background doc names is absorbed, with the honest caveat that server-authoritative durable state is modeled by convention (re-read every poll, owner-bound handle) rather than guaranteed by the type system.
