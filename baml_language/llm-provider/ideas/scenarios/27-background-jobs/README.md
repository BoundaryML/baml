# Scenario 27 — Async jobs: background + poll

The fourth request lifecycle. Sync is one blocking response; Streaming is one held connection; Realtime is a live duplex session. **Background+poll is none of these:** `submit` returns an opaque job id *immediately* holding no connection, the work runs server-side while the client process may die, and you come back *by id* and `poll` until the job lands. This scenario models that as a new `Background` capability (`requires Provider`) whose `submit`/`poll`/`cancel` verbs return a durable, persistable `Job<T>` handle, with `wait_for` as a default tying them together over a swappable backoff `Cadence` (named `wait_for`, not `await` — `await` is the BEP-034 keyword for in-process `Future`s; this server-side submit/poll durability is a distinct mechanism). It exercises the store=True↔ZDR tension (a hard construction guard), poll cadence/backoff, the inline-result vs batch-second-fetch provider divergence (OpenAI Responses vs Anthropic Batch, used through byte-identical app code), and reconciliation with the caller's own retry/idempotency key — and flags where server-authoritative state, type-level store/ZDR guarantees, unsafe inherited combinators, and webhook callbacks fall outside the proposal's model. Because `submit`/`poll`/`cancel` are none of call/stream/realtime/tools, the scenario also introduces a **net-new `baml.errors.BackgroundError`** capability-error channel (`throws baml.ExtendUnknownError<baml.errors.BackgroundError>`) with concrete typed job outcomes (`JobFailed`, `JobCancelled`, `PollDeadlineExceeded`).
