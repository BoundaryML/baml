# Evaluation — Structured / typed output: one type, four wire encodings

Adversarial read of whether the proposed model expresses "one return type, four provider encodings" cleanly. The scenario stresses the `T` generic threading, strict-vs-nonstrict negotiation, refusal-before-parse, and repair-as-parse-layer.

## (a) What the proposal reuses unchanged

- **The `HttpProvider` seam, verbatim.** `build_request<T>` / `send` / `parse<T>` with the default `call<T> = call_with<T,null>(…)` (itself `parse(send(build_request))`) is exactly the canonical interface. `call`/`call_with` live on `HttpProvider`, not on the bare `Provider` marker (see ../provider-as-marker.md). All four encodings fit inside `build_request<T>` and `parse<T>`; the `HttpProvider.call<T>` seam never changes. This is the proposal's §2 claim doing real work — *"`build_request` decides where the schema goes; the function still writes `-> Event`."*
- **The `T` generic threaded twice.** `reflect.type_of<T>()` in `build_request` lowers the schema; `parse<T>` decodes it. No new generic machinery — this is the same `parse<T>` that §2/OQ-4 already calls generic.
- **SAP as one parse branch.** `baml.sap.repair_parse<T>` is layered under each provider's `parse`, exactly the "SAP is ONE parse mechanism" framing. The four providers differ only in *where* they read the answer/refusal out of the parsed `json` body (the `JsonNav` path, over real `baml.json.parse`/`field`), then converge on one decode helper.
- **Combinators wrap a `Provider`.** `StrictFallback`, `.with_retry`, `.fallback_to` are the inherited default-method pattern; `-> Event` threads through each layer's `call<Event>` untouched. `StrictFallback` forwards request/response, so it `implements HttpProvider` (not the bare marker) and routes both `call` and `call_with` to a member that is itself an `HttpProvider` — the projection rides along so usage/sidecar is not dropped (the P1 fix), and a non-http member fails honestly with `Unsupported`. The combinator factories (`with_retry`/`fallback_to`/`cached`) are inherited via `requires Provider`, never redefined. Orchestration stays out of the provider, per §4/§6.
- **Clients as sugar.** Four `client` blocks differ by one line; the same function body works across all four. Portability is the headline and it lands.
- **Per-capability `throws baml.ExtendUnknownError<baml.errors.CallError>` channel** carries the refusal as a first-class error, caught specifically at the call site — reusing `throws`/`catch` with interface-membership matching, no new control flow. The old single `type Error = baml.errors.LlmClient` channel is gone; every call-path method (`build_request<T>`, `send`, `parse<T>`, `StructuredDecode.decode<T>`, `StrictFallback.call<T>`/`call_with<T,U>`) now declares the `CallError` channel uniformly, and the combinator declares the *same* channel as its members — no widen/forward.

## (b) Net-new surface it must add (each tied to a primitive)

- **`baml.schema.json_schema(type, strict) -> string`** and **`baml.schema.gemini_schema(type) -> string`** — host functions that lower a first-class `type` into provider-specific schema *text*. Tied to the `type` primitive + `reflect.type_of<T>()`. The proposal assumes SAP can parse any `T`, but says nothing about *emitting* a schema for `T` on the request side. Two distinct lowerings are unavoidable: JSON Schema vs Gemini's UPPERCASE OpenAPI subset are genuinely different dialects, not a formatting flag.
- **`baml.schema.strict_supports(type) -> bool`** — feature-detection over a `type` ($ref cycles, unions, patternProperties, if/then/else). Tied to the `type` primitive. This is the "schema-feature negotiation before the call" the background calls hard; it has to be a host predicate because it inspects the reflected type graph.
- **`baml.sap.repair_parse<T>(string) -> T`** — coercion/repair distinct from plain SAP. Tied to the `parse<T>` seam (OQ-6, "expose SAP as a public primitive"). The proposal exposes `baml.sap.parse`; this scenario shows repair is a *separate* mandatory pass ("coercion is mandatory even under guaranteed modes"), so the SAP surface needs at least two entry points.
- **`Refused`** (the canonical refusal class, a concrete `implements baml.errors.CallError`/`StreamError`) — a distinct typed error so the parse layer and the app can branch on decline vs malformed-output. Tied to the `CallError` capability channel. Without it, a refusal collapses into an `UnknownError` and the "never repair a refusal" rule cannot be enforced or caught by type. Note the refusal classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error` all `false`) say what a refusal is *not* — it is its own concrete arm, recovered at the consumer `catch` *above* the `CallError` interface arm. The sibling concretes this scenario adds — `EmptyStructuredError` (`is_parse_error -> true`) and `StructuredHttpError { status }` (`is_rate_limit -> status == 429`) — replace the old undifferentiated `LlmClient { message }` throws with classified `CallError`s.
- **Response-body navigation rides the *real* `baml.json` surface — nothing net-new.** Each provider reads a handful of fields out of its response at four diverging paths (`choices.0.message.refusal` vs `.content`, `stop_reason`, `candidates.0.finishReason`). There is no `Response.json_path` (that was invented); instead `parse<T>` reads `from.text()`, parses it once with `baml.json.parse`, and walks the `json` union with `baml.json.field` (map arms) + the Array `.at` method (array arms), wrapped in a small library-local `JsonNav` helper. The four refusal slots are still pure path *data* (`["choices","0","message","refusal"]`, …) — the good outcome — and it falls out of the existing stdlib rather than a new host primitive. Anthropic's answer is a nested JSON object (`content.0.input`), so `JsonNav.obj_text` re-serializes it with `baml.json.stringify` before handing it to repair/SAP.
- **Body-builder host helpers** (`baml.llm.openai_chat_body`, `..._responses_body`, `anthropic_body`, `gemini_body`). Arguably these could be pure-BAML string assembly, but realistically message-role encoding is a host concern; flagged as net-new convenience, not strictly required by the model.

## (c) Where it is awkward, leaky, or unresolved

- **Strict-vs-nonstrict negotiation is trapped inside `build_request`, so the combinator can only retry the whole call.** The standard chain is "try strict → if the *schema* is rejected, retry the *same provider* with `strict:false`." But `build_request<T>` picks strict internally from `strict_supports(T)`; there is no parameter on `call`/`build_request` to say "this attempt, go loose." So `StrictFallback` cannot re-run the *same* OpenAI provider in a looser mode — it has to hold two pre-configured providers and swap. To make same-provider strict retry expressible you would need either (i) a second provider field flipped to non-strict, or (ii) a strictness field on the provider class and two client instances. Both leak the toggle up into config. **This is the sharpest awkwardness and it stems directly from "options dissolve into provider fields" (§4): a per-attempt knob has nowhere to live.** A `call` with an attempt-scoped options bag is exactly what the proposal deleted.

- **Anthropic's tool-injection side effect is invisible at this layer (OQ-7-adjacent / §7 tension).** Forcing `record_output` works for structured-output-only, as written. But the background notes that when you want *both* structured output AND real tools you must NOT force the return tool — you let the model choose and terminate when it picks the return tool. That couples this `HttpProvider.parse` path to the `Tools` capability's loop. In this model they are separate interfaces on the same class with no shared state, so "structured output that coexists with a tool loop" would require the `Tools.step` implementation to know about the synthetic return tool. The proposal has no seam where `parse<T>`'s schema-as-tool and `Tools.begin`'s real tools meet. Unresolved here; a real Anthropic provider would need the return-schema to be threaded into `begin<T>`, not `build_request<T>`.

- **Compile-time guarantee of "this client produces strict, validated output" is unavailable.** Per §5 and OQ-1, `client` returns the existential `Provider`, so "is this provider constrained-decoding or just prompt-and-pray?" is a runtime property — there is no type distinguishing `OpenAIChat`-strict from a no-schema "just ask" provider. The app author cannot get a compile error for pointing a schema-critical function at a provider that only does `json_object` mode. The escape hatch (`function … -> OpenAIChat`) recovers the concrete type but loses portability — the very thing this scenario sells. So you choose: portable OR statically-guaranteed-strict, not both. Plainly: **the model cannot express a compile-time "this output is schema-constrained" capability.**

- **`reflect.type_of<T>()` inside `build_request` assumes the generic `T` is reified at runtime (OQ-5-adjacent).** The four encodings all depend on reflecting `T` to JSON at request-build time. The proposal confirms value-level reflection for capability `match`, but schema emission needs the *full structural type* of an arbitrary generic, monomorphized or reflected. If `T` is erased, none of this compiles. Conventions list `reflect.type_of<T>()` as reused, so we lean on it — but it is doing more here (structural emission) than membership testing, and that load is worth confirming.

- **Refusal-vs-empty is a per-provider convention, decentralized.** Each `parse` hand-pulls a different path and decides what "refused" means (OpenAI `refusal` field, Anthropic `stop_reason`, Gemini `finishReason SAFETY`). The shared `StructuredDecode.decode` enforces *order* (refusal → empty → repair) but cannot enforce that every provider correctly *finds* its refusal slot. A provider author who forgets to read the refusal path will silently run repair on an empty body and throw a generic `EmptyStructuredError` — the right failure shape (`is_parse_error -> true`), but for the wrong reason, and the "never fabricate" guarantee is only as good as each provider's diligence. There is no interface forcing a refusal check.

- **The error model surfaces a new tension: the refusal-vs-parse-failure distinction is invisible through the `CallError` interface, only through the concrete `Refused` arm.** The new model gives the app two ways to catch: the concrete `Refused` class, or the `baml.errors.CallError` interface with classifiers. But a refusal is deliberately *not* a network error, *not* a rate limit, and *not* a parse error — all three classifiers return `false`. So an app that triages only by `is_network_error()/is_rate_limit()/is_parse_error()` (the portable, provider-agnostic path the model advertises) cannot tell a `Refused` apart from any *other* unclassified `CallError`: both fall through every `is_*` predicate to the same default branch. To distinguish "the model declined" from "something else went wrong but isn't network/rate/parse" the app is *forced* back to the concrete `Refused` type — which means it must depend on the std-lib class, not just the `baml.errors` interface. Refusal is a first-class *outcome* but the classifier vocabulary has no `is_refusal()`, so the interface under-describes it. The honest fix is either an `is_refusal()` classifier on `CallError` (privileging refusal among all domain errors) or accepting that refusal handling is inherently concrete-typed and non-portable across the interface — exactly the precision-vs-portability tradeoff this scenario already pays for "is-constrained". The `StrictFallback` combinator dodges it correctly (it matches the concrete `Refused` to avoid retrying a decline), but only because it, too, reaches for the concrete class rather than the interface.

- **`StrictFallback` now forwards the `CallError` channel, which makes the `loose` retry's *foreign* failures observable as the primary's.** Both members declare `baml.ExtendUnknownError<baml.errors.CallError>`, and the combinator declares the same — clean per rule 4. But if the `loose` provider raises an `UnknownError` (some exotic transport panic normalized via `with_message`), the app catching `ExtractOrg(...)` sees a `baml.UnknownError` whose `message` breadcrumb names the *loose* provider, with no structural hint that a strict-attempt happened first and was discarded. The flattened non-generic `UnknownError` is what keeps the union from exploding, but it also erases which arm of the fallback actually failed — a debuggability cost the combinator cannot annotate without re-wrapping (and re-wrapping a *known* `CallError` is forbidden, so it cannot uniformly add "via StrictFallback" context to typed and untyped failures alike).

## (d) Verdict: **Workable-with-additions**

The core claim — one `-> Event` return type, four wire encodings absorbed inside `build_request<T>`/`parse<T>`, with portability across providers that the background shows diverging sharply — holds cleanly and is the model's best showing. The `T`-threaded-twice story, SAP-as-one-branch, repair-as-parse-layer, and refusal-as-typed-error all land with only host-boundary additions (`baml.schema.*`, `repair_parse`, the concrete `Refused`/`EmptyStructuredError`/`StructuredHttpError` `CallError`s) that are honest host concerns, not model patches. It is *not* Clean because two real divergences resist the model: (1) per-attempt strict→non-strict retry has nowhere to live now that options are provider fields, forcing an awkward two-provider `StrictFallback`; and (2) structured-output-via-forced-tool cannot coexist with a real tool loop without a seam between `HttpProvider.parse` and `Tools.begin` that the proposal does not provide. Both are expressible with additions rather than redesign, and neither breaks the spine — hence Workable-with-additions, not Awkward. The one thing the model genuinely *cannot* do is give a compile-time guarantee that a portable client is schema-constrained; that is the documented cost of `client`-as-sugar returning the existential `Provider`.
