# 46 — Streaming & observability of a workflow

A workflow is an orchestrator that calls models — the layer *above* a single call. This scenario models a workflow as an ordinary `Provider` (a marker — ../provider-as-marker.md) that `implements HttpProvider` so its `.call` runs the graph to its result, and adds a net-new `Steppable` capability whose companion, `.steps`, yields a `baml.llm.Stream<StepEvent, T>`: a per-step event hierarchy (step-start / step-token / step-result / step-suspended / workflow-finish) keyed by step id, reusing the *same* Stream type streaming uses. Inside a step that calls a streaming model, the inner token stream is multiplexed up as `step-token` frames, and each step opens an obs span under which the §32 `Traced` combinator nests every model span — so the graph renders as a span tree. The durable step log (`baml.flow`) gives per-step replay / time-travel. Errors ride a net-new `baml.errors.StepError` capability channel (with `is_replay_error()` / `is_missing_checkpoint()` classifiers the four core capability errors lack), declared as `baml.ExtendUnknownError<baml.errors.StepError>` on `Steppable.stream_steps` / `replay_step`; concrete engine errors are `StepFailed` / `MissingCheckpoint` / `UnknownStep` / `ReplayFailed`. Read `evaluation.md` for where this leaks: the inter-step carry is `unknown` (the graph is untyped), the token multiplex is buffered rather than truly interleaved, replay fidelity is unenforced, durable suspend/resume is approximated through out-of-band host state rather than a language primitive, and the `StepError` channel collapses into `baml.UnknownError` the moment the workflow is run via the `HttpProvider.call` seam (whose channel is only `CallError`) unless the package writes the external `implements baml.errors.CallError for baml.errors.StepError` row, while a model's `CallError` raised inside a step is buried under `StepError` with its classifiers unreachable absent the symmetric forwarding row.
