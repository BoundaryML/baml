# Evaluation — Streaming & observability of a workflow

Adversarial read: can the Provider / capability / `client`-sugar model express a *workflow* that (a) is itself a provider, (b) emits a per-step event hierarchy, (c) multiplexes an inner model token stream up through that hierarchy, (d) correlates each step with its model spans, and (e) supports per-step replay / time-travel? This is the layer *above* a single model call — a workflow is an orchestrator that happens to call models.

## (a) What the proposal reuses unchanged

- **A workflow IS a `Provider` (the marker) and `implements HttpProvider`.** Under the marker-`Provider` revision (../provider-as-marker.md) `Provider` carries no interaction method; `call`/`call_with` are an `HttpProvider` capability. A workflow is request/response — it produces one typed value — so it `implements HttpProvider`, and `Workflow.call<T>` runs the graph to that result (the graph body is the call body; §1's "everything is a provider," including harnesses §8). So `Workflow` drops into `with_retry` / `fallback_to` / `with_traced` with zero new machinery — the `ResilientResearch` client wraps a workflow in combinators exactly as scenario 32 wraps a model. This is the cleanest part: orchestration-over-orchestration is just provider composition. (`Workflow.call_with` declines — a graph has no *single* normalized `ResponseMeta`; per-step usage rides the Steppable observability path, not a `(T, U)` tuple. The decline is honest, the same shape `Durable.call_with` takes when its inner has no sidecar; it is not a fabricated graph-level meta.)

- **A `client` is a workflow.** Because `client Name() { … }` is sugar for `function Name() -> Provider { … }` (§3) and a `Workflow` is a `Provider`, `ResearchFlow()` is an ordinary client. No "workflow client" concept is needed.

- **`baml.llm.Stream<TStream, TFinal>` carries step events unchanged.** The whole Steppable capability returns `Stream<StepEvent, T>` — the *same* Stream type streaming uses, with TStream instantiated to our event type instead of a token partial (scenario 04). `stream_unfold` (scenario 04's net-new constructor) drives the graph the same way it drives an SSE reader. The progress stream of a workflow is a `baml.llm.Stream` like any other.

- **The §32 `Traced` combinator does the model-span correlation.** A step opens a step span and wraps any model provider it calls in `Traced { parent: step_span }`. Because `Traced.stream` / `Traced.call` open a model span *under* the supplied parent, model spans nest under the step span for free. We reuse `obs_start` / `obs_finish` / `obs_event` verbatim.

- **Capability negotiation via `match` on the existential** (§5). `StepStreaming.pipe` `match`es the injected model for `Streaming` and degrades to `.call` when it isn't — the exact delivery-refinement fallback the proposal prescribes. The `.steps` and `.replay_step` companions `match` the client for `Steppable` and error when absent (a different-interaction-shape capability, no honest fallback — §5's second bucket).

## (b) Net-new surface it must add (tied to a primitive)

- **`Steppable requires Provider`** → a new capability interface, the workflow twin of `Streaming`. `Streaming.stream` is "same call, delivered as tokens"; `Steppable.stream_steps` is "same call, delivered as step events." Justified and structurally identical to an existing primitive — but it *is* net-new: the proposal lists `Streaming`/`Realtime`/`Tools`/`HttpProvider` and not this.

- **The `StepEvent` vocabulary + `Step` / `StepContext` / `StepOutcome`** → new types. The proposal has no graph/step model at all; `call<T>` is a single opaque activity. Everything about "a run made of named, checkpointed steps" lives here. `StepOutcome { value? | suspend? }` is the workflow analogue of `Tools`' `T | ToolCalls` sentinel (§7) — we copied that shape deliberately, but it is still net surface.

- **`baml.errors.StepError` — a NET-NEW capability-error interface.** A workflow engine is a capability *beyond* call / stream / realtime / tools (it runs a durable step graph, suspends, replays), so under the error model (rule 4) it earns its own capability-error channel. `Steppable.stream_steps` / `replay_step` and the internal graph helpers (`advance`, `finish`, `find_step`) declare `baml.ExtendUnknownError<baml.errors.StepError>`. The interface adds two classifiers the core ones lack — `is_replay_error()` and `is_missing_checkpoint()` — because time-travel/durability failures are the genuinely new failure mode here. Concrete `StepError`s the engine raises on purpose: `StepFailed`, `MissingCheckpoint`, `UnknownStep`, `ReplayFailed`. This is net-new surface the proposal must add; it is *not* one of the four core capability errors. Defining a net-new channel does **not** re-open any gap: because `implements` is a Rust-like trait relation admitting external impls, the workflow package declares, alongside `StepError`, one-line rows like `implements baml.errors.StepError for baml.errors.Unsupported` (and for any upstream error it wants to ride the channel typed) — local trait, foreign type, allowed by coherence. So `Unsupported` is legal on `StepError` immediately, by the row the channel author writes, not "eventually" by reaching back to widen anything.

- **`baml.flow` durable log** (`flow_open_log` / `flow_put` / `flow_get` / `flow_new_run_id`) → host primitives. Durable, server-authoritative checkpointing is not pure BAML, and the proposal's model has *no* persistence concept. Ties to Open Question #7 (host-backed bodies as the bridge boundary): the step log is exactly such a boundary.

- **`TokenCollector` + `baml.flow.collect/drain`** → a mutable host buffer. This is the multiplexing plumbing: a step's `ctx.emit` closure must accumulate inner model tokens so `advance` can splice them into the outer stream's `pending` queue. We need it **because BAML closures capture by value** — a step body cannot append to a local array from inside `emit`. That is a real language limitation surfacing as net host surface (see (c)).

- **`StepContext.emit: (StepEvent) -> null`** → the workflow's event surface. This is the *same flag* the proposal raises in §7 ("`ExecutionContext` … needs … an event-`emit` surface") and scenario 32 made concrete for tool dispatch. Here it carries step-token frames up through the multiplex. Same primitive, second customer.

- **`baml.flow.coerce<T>` / `as_*` casts over `unknown`** → host coercions. The carry value flowing step→step is `unknown` (a step's output type is not known to the next step at the graph level). Every step boundary pays an `unknown`→typed cast. The proposal threads `T` end-to-end through a single `call`; a multi-step graph has no single `T`, so the inter-step seam is untyped. This is the biggest *type-system* gap (see (c)).

## (c) Where it is awkward, leaky, or unresolved

- **The inter-step carry is `unknown` — the graph is untyped.** The proposal's strength is that `call<T>` threads one output type the compiler checks. A workflow has N steps with N different I/O types and no single `T`; we model the carry as `unknown` and cast at each boundary (`baml.flow.as_doc`, `as_findings`, …). So **the step graph has no compile-time type safety** — a step that expects a `Doc` but is wired after a step producing `Findings` fails at runtime, not at compile time. Frameworks like pydantic-graph get this from typed nodes; the Provider model, being single-`T`, cannot express a typed *pipeline* without a genuinely new generic-graph construct. This is the scenario's sharpest limitation and it is structural, not cosmetic.

- **Multiplexing fights value-capture closures.** Splicing inner model tokens into the outer step stream *should* be a simple "yield from the inner stream inside the outer unfold." But the outer stream is pull-based (`stream_unfold` advances one step per `next`), and a step runs to completion *within one advance* — so its inner tokens have already all been produced by the time `advance` returns. We buffer them in a host `TokenCollector` and replay them as `pending` frames *after* the fact. The ordering is correct (start, tokens, result) but the tokens are **not actually live** — they were generated during the step body and flushed afterward. True interleaving (UI sees token 3 of step 2 *before* step 2 finishes) requires a *coroutine/yield* boundary the unfold seam does not have. The proposal's `Stream` is pull-of-whole-steps; a workflow wants pull-that-can-suspend-mid-step. **Genuinely awkward, and arguably the multiplex is faked.**

- **Open Question #5 (capability `match` over an interface-existential).** The `.steps` companion and `StepStreaming.pipe` both `match (model) { let s: Streaming => … }` — runtime membership testing on the existential `Provider`. This scenario leans on QO#5 twice (Steppable on the client, Streaming on the injected step model). If value-level reflection cannot test `let s: Streaming` at runtime, the multiplex degrade and the `.steps` gate both collapse. We assume QO#5 resolves yes; it is load-bearing here.

- **OQ1 (degenerate `call` on non-HTTP capabilities) — resolved by the marker.** Under ../provider-as-marker.md `Provider` is a bare marker with no interaction method, so `Steppable requires Provider` does **not** force a `Workflow` to grow a `call`. The workflow has `call` only because it *chose* to `implements HttpProvider` — and that choice is honest: a workflow run genuinely produces one typed value, so request/response is a real capability it has, not a fake best-effort one. (Contrast realtime/harness scenarios, which under the revision simply drop their degenerate `call` and expose only their real interaction; OQ1's "best-effort single turn or stand-alone capability?" is closed as "stand-alone — `call` is an `HttpProvider` capability, not a base method.") What remains is only an *ordering* observation, not a forced degeneracy: for a model, `call` is the codec primitive and `stream` refines it; for a workflow, `stream_steps` is the *richer* path and `call` is implemented *by draining it* (one execution path → no observed-vs-unobserved drift, the §5 background's central risk). That inverts the model case's "codec is primitive" intuition, but it is a free design choice the marker permits, not a contradiction the base forces.

- **Replay fidelity is unenforced (the §5 "what's hard" + §4 nondeterminism).** `replay_step` re-runs a step against its recorded input. For `FetchStep` that is safe only if `http_get_text` is cached; for `ExtractStep` it is *not* safe at all — re-running calls the model afresh and gets a different generation (`debug_extract` documents this). The proposal has **no purity marker** on `HttpProvider.call` (nor on `Step.run`), so nothing distinguishes a replayable step from a non-deterministic one. Time-travel "works" mechanically but the fidelity guarantee the background wants ("re-run is safe iff the step is pure") cannot be expressed in the type. Same family as scenario 32's "capability is a runtime promise."

- **Server-authoritative suspend/resume is smuggled through host state.** A real durable workflow's suspended state lives on a server (Temporal/Inngest/the §7 engines). Here suspend is a `StepOutcome.suspend` that ends the unfold, with the checkpoint in `baml.flow` host state, and resume is a *fresh* `replay_step` call keyed by `run_id`. The proposal's model is request/response — `call<T>` returns or throws — so a workflow that pauses for a human for three days has **no native representation**. We approximate it with an out-of-band `run_id` + host log. The BAML program cannot itself *be* the durable entity; it can only drive one. This is an honest "unsupported as a language primitive; expressible only as a host binding."

- **Two parents, one tree, agreed out-of-band.** Step spans nest under the workflow span (opened in `stream_steps`); model spans nest under step spans (opened in the step body via `Traced{parent}`). The correlation holds only because the step body is *handed* `ctx.step_span` and chooses to use it. Nothing enforces that a step's model call actually parents under `ctx.step_span` — a careless step author can open an orphan span. Same gap scenario 32 flagged: no *ambient* span context; correlation is by passed `SpanId`, by convention.

- **The error channel at the `.call` seam — a workflow's typed `StepError` boxes into `CallError`'s channel *only if* no `implements` row keeps it typed.** `Steppable.stream_steps` raises `baml.errors.StepError` (with `is_replay_error()` / `is_missing_checkpoint()`), and `Workflow.call` lives on `HttpProvider` (the marker revision: `call`/`call_with` are an `HttpProvider` capability), whose channel is `baml.errors.CallError`. By default `StepError` is foreign to `CallError`, so `call` would route every step failure through `baml.UnknownError.with_message<CallError>(...)`. But this boxing is a **coverage convention, not a wall**: because `implements` is a Rust-like trait relation admitting external impls, the workflow package can declare `implements baml.errors.CallError for baml.errors.StepError` (local type meets foreign trait — the workflow owns `StepError`, so coherence is satisfied), supplying `is_network_error()` / `is_rate_limit()` / `is_parse_error()` in terms of the step failure. With that one row, a `MissingCheckpoint` or `StepFailed` rides the `.call` seam as its **typed self** — caught concretely by `let s: baml.errors.StepError =>` on the `HttpProvider` (CallError) channel, *no box*. Where the workflow author omits the row, the crossing still boxes — but the concrete step error is **not** lost: it rides untouched on `.data`, and `from<baml.errors.StepError>(e)` pulls the *same* concrete error back out, classifiers intact. So the residual is exactly the two honest cases: (1) an *un-implemented* crossing (the convention wasn't followed) still boxes, and when it does, recovery is **explicit, never transparent** (error-model.md settles this) — a `catch (e) { let s: baml.errors.StepError => … }` arm on the CallError channel is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `StepError`), so that arm never fires; the author must `baml.UnknownError.from<baml.errors.StepError>(e)` inside the `UnknownError` arm; and (2) a genuinely-foreign value (host panic) has no inner `StepError`, so `baml.UnknownError` is correct there. The deeper static point survives — this is P2 (capability-as-runtime-promise) applied to the error channel: nothing *forces* the channel author to write the row, so a forgotten row is a missed crossing rather than a guaranteed one. The cleanest path stays to hold the `Steppable` companion and use `.steps`/`.replay_step`, but the `HttpProvider.call` seam can keep `StepError` typed by the one external `implements` row.

- **Inner model `CallError`/`StreamError` crossing into `StepError`'s channel — typed when an `implements` row exists, boxed otherwise (and, on one path, re-tagged away).** A model call *inside* a step (`StepStreaming.pipe`, `ReviewStep`'s `traced.call`) raises `baml.errors.CallError` / `StreamError` — by default foreign to the enclosing `StepError` channel, so `pipe` would normalize it into `baml.UnknownError.with_message<StepError>(...)`. But, as with the `.call` seam above, this crossing need not box: the workflow package (which owns `StepError`) can declare `implements baml.errors.StepError for baml.errors.CallError` (and `for baml.errors.StreamError`) — local trait, foreign type, allowed — so a transport failure raised three frames down rides the `StepError` channel as its **typed `CallError` self**, caught directly by `let c: baml.errors.CallError =>` on the `StepError` channel, *no box*, classifiers intact. Where that row is omitted the crossing still boxes, and the inner error is **not** gone: it sits untouched on `.data`, and `from<baml.errors.CallError>(e)` re-extracts the *same* `CallError`, `is_network_error()` answering truthfully on the unwrapped inner error. The residual is the two honest cases again: (1) an un-implemented crossing boxes, and recovery from the box is **explicit, never transparent** (error-model.md settles this) — a `let c: baml.errors.CallError =>` arm is a plain is-a test on `e`, the boxed value *is* a `baml.UnknownError` (foreign to `CallError`), so it never matches; the inner `CallError` is reachable only by an explicit `baml.UnknownError.from<baml.errors.CallError>(e)` inside the `UnknownError` arm; and (2) a genuinely-foreign value has no inner typed error and belongs in `baml.UnknownError`. The standing static point is just that nothing *forces* the channel author to write the forwarding row (P2-analog: a forgotten row is a missed crossing, caught at the first `_` arm, not a guaranteed one). (Separately, `advance`'s step catch re-tags a transport failure as `StepFailed` — that path genuinely *re-raises a new error* and so discards the original `CallError`; see the next bullet. That is a deliberate-funnel loss, not a boxing loss.) So one-interface-per-capability does **not** strand inner errors structurally: the channel author can forward upstream error types with external `implements` rows; the only residuals are the unwritten-row convention and the genuinely-foreign value. (Note also that the `StepError` classifiers still do not *auto*-delegate into a wrapped `CallError` — that is a separate ergonomics point about classifier vocabulary, not a boxing wall.)

- **`StepFailed` is a lossy funnel.** `advance` catches *anything* a step body raises and re-throws `StepFailed { step_id, detail }`. A deliberately-thrown typed `StepError` from the step (e.g. a `MissingCheckpoint` surfaced by a sub-workflow) is caught by the `let se: baml.errors.StepError =>` arm and *still* collapsed to `StepFailed` — losing the original classifier bits. We kept the funnel to preserve the original "step N failed" recording behavior, but it means the engine throws away structure it could have re-raised. A faithful design would re-raise `se` unchanged and only wrap genuinely-foreign `e`; the trade-off is that the step-span bookkeeping (`obs_finish(step_span, …, "step threw")`) wants to run on *every* failure, which pushes toward the lossy single funnel. Honest tension, not resolved here.

- **`workflow-finish` vs `final()` is redundant.** The stream ends and *also* carries a `workflow-finish` frame, and `final()` returns the typed result. Two channels for "the run is done" (an event and a terminal). We kept both to match the background's Mastra `workflow-finish` event, but it duplicates `Stream`'s own `StreamDone` + `final()` terminal. Minor, but it shows the event vocabulary and the Stream terminal don't quite align.

## (d) Verdict: **Workable-with-additions**

A workflow being a `Provider` (the marker) that `implements HttpProvider`, and therefore a `client`, and therefore composable with `Retry`/`Traced` — that part is genuinely clean and is the model paying off: orchestration-over-orchestration needs no new mechanism. (And the marker revision tidies one prior complaint: `requires Provider` no longer forces a degenerate `call` onto a workflow — OQ1 is resolved; the workflow has `call` only because request/response is a real capability it chose, `Workflow.call_with` honestly declining the single-`ResponseMeta` sidecar a graph cannot produce.) The step-event hierarchy rides on `baml.llm.Stream<StepEvent, T>` with `stream_unfold`, reusing the exact streaming primitive with a different item type, and per-step→model-span correlation falls out of the §32 `Traced{parent}` combinator. But three additions are mandatory and two are real warts. Mandatory: a `Steppable` capability, a net-new `baml.errors.StepError` capability-error interface (with `is_replay_error()` / `is_missing_checkpoint()` classifiers for the durability/time-travel failure modes the core four don't cover), the `Step`/`StepEvent`/`StepContext` vocabulary, and a `baml.flow` durable-log host seam (QO#7). The warts: (1) the inter-step carry is `unknown`, so the graph has **no compile-time type safety** — the single-`T` Provider model cannot type a multi-step pipeline without a genuinely new graph construct; and (2) the multiplex of inner model tokens is *faked* — a pull-based `stream_unfold` runs a step to completion per advance, so tokens are buffered and replayed rather than truly interleaved, because the seam has no mid-step yield. Add to that: replay fidelity is unenforced (no purity marker on a capability method — a separate gap from OQ1, which the marker revision resolves), and durable server-authoritative suspend/resume has no native representation — it is approximated via an out-of-band `run_id` and host state. On the error model specifically: a workflow gets a clean per-capability `StepError` channel, and crossings out of it stay typed by a **coverage convention**, not a wall — because `implements` is a Rust-like trait relation admitting external impls, the workflow package (which owns `StepError`) writes one-line rows like `implements baml.errors.CallError for baml.errors.StepError` (so step errors ride the `HttpProvider.call` seam typed) and `implements baml.errors.StepError for baml.errors.CallError` (so a model's `CallError` raised deep inside a step rides the `StepError` channel typed), as well as `implements baml.errors.StepError for baml.errors.Unsupported` to admit the negotiation error. With those rows the down-stack error is caught concretely with no box. Where a row is omitted the crossing boxes, but the data and type survive on `.data`, recoverable via an explicit `from<…>` probe — and a *genuinely foreign* value (host panic) correctly lands in `baml.UnknownError`. So the only standing residual is the P2-analog: nothing *forces* the channel author to write the forwarding row (a forgotten row is a missed crossing caught at the first `_` arm, recovery from a box being **explicit, never transparent** — a `catch` arm is a plain is-a test on `e`, so the author must `from<ArmType>(e)` by hand inside the `UnknownError` arm; error-model.md settles this), not a structural inability to keep the crossing typed. The model *absorbs the shape* of workflow observability and composes beautifully at the provider layer; it *cannot* give the typed-pipeline or true-streaming-interleave or durable-entity guarantees a dedicated graph framework does. Workable, with those additions and an honest "the graph itself is untyped and the multiplex is buffered."
