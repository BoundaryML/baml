# Evaluation — Composing a durable step graph

Adversarial read: does the proposed provider/client/capability model carry a durable step graph, and where does it leak?

The headline result is unusual for this set: **the proposal barely participates.** A step graph is code-defines-the-graph, and the proposal's whole bet is that clients are ordinary functions. So a step is a function, an edge is a `let`, a branch is a `match`, a loop is a `while`, and a model call in a step is `provider.call<T>(...)`. The provider model is untouched. The interesting question is therefore not "can the proposal express the graph" (the host language already does) but "does anything force the proposal to grow new surface" — and the answer is yes, in exactly two places, neither of which is a Provider capability.

## (a) What the proposal reuses unchanged

- **`Provider.call<T>` as the only model touch-point.** Every model step is one line: `p.call<Summary>(prompt)`. No step wrapper, no `Step` interface, no graph node type. The proposal's irreducible base is exactly the right granularity for "a node that asks a model one question."
- **`client` = function returning `Provider`.** `client Summarizer() { OpenAI… }` is config-only sugar; the step function calls it. Because clients are functions, a step picks its model the same way any function does — no special wiring.
- **The four structured-output encodings stay inside the provider.** `Summarize` uses an OpenAI provider (`response_format`); `Classify` uses an Anthropic provider (forced-tool `input_schema`). The two call-sites are identical (`p.call<T>(prompt)`); the divergence lives in `build_request`/`parse`. The graph is genuinely provider-portable — swapping a step's `client` is the only change, and it is a one-liner. (Reuses proposal §2.)
- **`Tools` capability for the model-decides node.** `LegalReview` is an agentic tool loop dropped in as one node of a code-defined graph, via the generated `.run_tools` companion. Code-defines and model-decides compose with zero glue — the background doc's two axes meet cleanly here. (Reuses proposal §7 verbatim; the only addition is a `ToolRegistryCtx` implementing the already-required `ExecutionContext.dispatch`.)
- **Host-backed `implements` blocks** for the checkpoint backends, exactly the `PrimitiveClient` bridge boundary (Open Question 7).

## (b) Net-new surface it must add (each tied to a primitive)

1. **`baml.async.join2 / join_all / map_concurrent` — a host structured-concurrency seam.** This is the real net-new primitive, and it is the load-bearing one. BAML expression evaluation is sequential: `let a = f(); let b = g();` runs f to completion first. A fan-out + sync-barrier join (Mastra `.parallel`/`.foreach`, pydantic-graph's parallel branches) cannot be expressed without a scheduler primitive that *starts* several thunks and joins them. Critically, **this is not a Provider capability** — it is orthogonal to `call`, lives outside the interface hierarchy, and operates on thunks. The proposal's model neither helps nor hinders here; it simply has nothing to say about concurrency, so the host must. This directly answers background §what's hard ("fan-in is where the complexity hides"): fan-out is a thunk list, the join is `join2`/`join_all`, and the fail-semantics question ("what does 'all' mean when one fails") is a choice between `join_all` (fail-fast) and `join_settled` (all-settled).

2. **`Checkpoint` + the `step(...)` memoizer — a durable-execution layer.** The "durable" half of the title needs each step's output content-addressed and stored so a re-run skips completed steps. This wraps step *execution*, not `provider.call`; it is the orchestration-layer analogue of how retry/fallback wrap a provider in the proposal. The point worth stating loudly: **the proposal does not need a "durable" capability.** Durability is a property of the step function (does it consult a checkpoint), not of the model call. A provider stays stateless and single-shot, which is exactly what we want — a checkpoint that cached a provider's connection would be wrong.

3. **`Result<T,E>` cell** for the all-settled join. Minor, but real: fail-fast joins re-throw, all-settled joins must return per-thunk outcomes, and there is no Result type in the canonical primitives.

## (c) Where it is awkward, leaky, or unresolved

- **No portable graph IR — by construction, and this is a genuine loss.** Background §what's hard's third point is "there is no portable IR for a step graph." The proposal *embraces* that: the graph is the function body, so there is no artifact to inspect, visualize, diff, or hand to a scheduler. You cannot, in this model, render the DocPipeline as a DAG, statically detect an unreachable branch, or have a runtime decide to run two nodes on different machines — because the topology is implicit in `let`/`match`/`while`. Mastra's `.commit()` and LangGraph's compiled `StateGraph` are reifiable; a BAML function body is not. For teams that want graph observability or distributed scheduling, this is a hard wall the proposal will not climb without a separate IR layer that has nothing to do with providers.

- **The join barrier is unchecked at the type level.** `Analyzed { summary: pair.0, label: pair.1 }` is a plain literal, which is ergonomic, but the proposal's capability-as-runtime-promise philosophy bleeds in: `join2`'s thunks each `throws Error`, and reconciling two different `type Error`s from two providers (OpenAI's vs Anthropic's, if they diverged) is unspecified. Today both are `baml.errors.LlmClient` so it is moot, but a graph that joins a harness step (subprocess error) with an HTTP step has two error channels and `join2`'s single `throws E` has to pick a unifying type. The proposal's `type Error` associated type does not compose across a concurrent join.

- **Open Question 5 (capability `match` over an existential) is dodged, not used.** This scenario almost never `match`es on capabilities — the graph calls `.call` and `.run_tools` directly. That is a feature (less runtime negotiation) but it also means the scenario provides no new evidence for OQ5; the one place it surfaces is inside the generated `.run_tools` companion, which `match`es for `Tools`. If `LegalAgent()` were swapped for a non-tool provider, the failure is a runtime throw, not a compile error — so a graph cannot *guarantee* at compile time that its agentic node is tool-capable. For a durable graph that may run for hours before reaching the legal node, discovering "not tool-capable" at node-execution time is genuinely bad. The escape hatch (drop `client` sugar, write `function … -> SomeToolsProvider`) exists but is not ergonomic for a graph node.

- **Open Question 1 (does every capability `requires Provider`) is irrelevant here, which is itself a finding.** Durability and concurrency are *not* capabilities in this model — they are orthogonal layers. So the proposal's capability machinery, which is the centerpiece for streaming/realtime/tools, contributes nothing to the step-graph story. The model is not wrong; it is simply silent, and the work falls to the host (`baml.async`) and the app (`Checkpoint`). An honest reading is that "step graph" is mostly *outside* the proposal's scope — the proposal governs what a node *does* when it talks to a model, not how nodes are sequenced, joined, or checkpointed.

- **Durability is shallow.** `step(...)` memoizes outputs, which resumes a crashed graph from the last completed step — but it does NOT snapshot in-flight execution. A step that crashes *mid-loop* (iteration 3 of refine) re-runs the whole step from iteration 1 on resume, because only the step's final output is checkpointed, not its internal loop counter. True suspend/resume (background §3, the `suspend()` inside a step) is a different and harder primitive this scenario does not provide, and the proposal has nothing to offer there either — it is, again, orthogonal.

## (d) Verdict

**Workable-with-additions.** The proposal carries the model-touching parts of a step graph cleanly and almost invisibly: a node is `provider.call`, providers stay portable across the divergent structured-output encodings, and a model-decides agent slots in as one node via the reused `Tools` capability — code-defines and model-decides compose with no friction. But the two things that make a step graph a *graph* and *durable* — concurrent fan-in/join and checkpointed resume — are net-new host/app layers (`baml.async`, `Checkpoint`) that sit entirely outside the provider/capability model. That is the correct architecture (concurrency and durability are not properties of a model call), but it means the proposal's central machinery is largely a spectator for this scenario. The genuine, unfixable-by-this- proposal losses are real and worth naming: no portable graph IR, no compile-time guarantee that an agentic node is tool-capable, and no true mid-step suspend/resume. None of these are provider concerns, so none are the proposal's fault — but a reader expecting "the new client model solves workflows" should leave understanding that it solves the *node*, and the host language solves the *graph*.
