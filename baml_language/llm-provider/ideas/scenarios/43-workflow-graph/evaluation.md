# Evaluation — Composing a durable step graph

Adversarial read: does the proposed provider/client/capability model carry a durable step graph, and where does it leak?

The headline result is unusual for this set: **the proposal barely participates.** A step graph is code-defines-the-graph, and the proposal's whole bet is that clients are ordinary functions. So a step is a function, an edge is a `let`, a branch is a `match`, a loop is a `while`, and a model call in a step is `provider.call<T>(...)`. The provider model is untouched. The interesting question is therefore not "can the proposal express the graph" (the host language already does) but "does anything force the proposal to grow new surface" — and the answer is yes, in exactly **one** place, and it is not a Provider capability: durable checkpoint/resume. The other thing a step graph needs — concurrent fan-in/join — is **not** net-new either: BAML ships first-class structured concurrency (BEP-034), so fan-out is a list of `spawn`s and the join is `baml.future.all`.

## (a) What the proposal reuses unchanged

- **`Provider.call<T>` as the only model touch-point.** Every model step is one line: `p.call<Summary>(prompt)`. No step wrapper, no `Step` interface, no graph node type. The proposal's irreducible base is exactly the right granularity for "a node that asks a model one question."
- **`client` = function returning `Provider`.** `client Summarizer() { OpenAI… }` is config-only sugar; the step function calls it. Because clients are functions, a step picks its model the same way any function does — no special wiring.
- **The four structured-output encodings stay inside the provider.** `Summarize` uses an OpenAI provider (`response_format`); `Classify` uses an Anthropic provider (forced-tool `input_schema`). The two call-sites are identical (`p.call<T>(prompt)`); the divergence lives in `build_request`/`parse`. The graph is genuinely provider-portable — swapping a step's `client` is the only change, and it is a one-liner. (Reuses proposal §2.)
- **The per-capability error channel is reused verbatim.** Every node body declares `throws baml.ExtendUnknownError<baml.errors.CallError>` (the default node channel — most nodes are `provider.call`), foreign host I/O (`http_get_text`, checkpoint reads) is normalized through `baml.UnknownError.with_message<…CallError>` in a trailing/inline `catch`, and the dountil cap failure is a concrete `RefineNotConverged implements baml.errors.CallError` the app can catch most-specific-first. There is no `type Error` associated type and no per-provider error type — the OpenAI and Anthropic steps already share the *same* `CallError` channel, which is why they were always join-compatible.
- **`Tools` capability for the model-decides node.** `LegalReview` is an agentic tool loop dropped in as one node of a code-defined graph, via the generated `.run_tools` companion. Code-defines and model-decides compose with zero glue — the background doc's two axes meet cleanly here. (Reuses proposal §7 verbatim; the only addition is a `ToolRegistryCtx` implementing the already-required `ExecutionContext.dispatch`.)
- **Host-backed `implements` blocks** for the checkpoint backends, exactly the `PrimitiveClient` bridge boundary (Open Question 7).

## (b) What is net-new — and what is NOT (concurrency is not)

1. **Concurrency is NOT net-new — it is a shipped language feature (BEP-034).** It is tempting to read fan-in/join as "the load-bearing net-new primitive," but that is wrong: BAML has first-class structured concurrency in the runtime today. A fan-out + sync-barrier join (Mastra `.parallel`/`.foreach`, pydantic-graph's parallel branches) is expressed directly — `spawn { body }` starts `body` concurrently and returns a `baml.future.Future` immediately; `await f` joins it. So the analyze step is two spawns awaited (`Analyzed { summary: await fSummary, label: await fLabel }`), a homogeneous list is `await baml.future.all(fs)`, and bounded fan-out is a `baml.spawn.TaskGroup` (the real rate limiter — spawns sharing a group are capped, excess queue FIFO). This is **not a Provider capability** — but it is also not a host scheduler seam the proposal must add: it is the *language's own* concurrency surface, already implemented. This answers background §what's hard ("fan-in is where the complexity hides") cleanly: fan-out is a list of spawns, the join is `baml.future.all`, and the fail-semantics question ("what does 'all' mean when one fails") is a choice between `baml.future.all` (fail-fast — cancels losers, re-throws) and `baml.future.all_complete` (losers finish, still throws the first error in input order). Cancellation and rate-limiting are first-class too (`Future.cancel()`, `baml.spawn.CancelToken`, `TaskGroup`). Nothing about concurrency forces the proposal to grow.

2. **`Checkpoint` + the `step(...)` memoizer — a durable-execution layer. THIS is the one genuinely net-new primitive.** The "durable" half of the title needs each step's output content-addressed and stored so a re-run skips completed steps. This wraps step *execution*, not `provider.call`; it is the orchestration-layer analogue of how retry/fallback wrap a provider in the proposal. The point worth stating loudly: **the proposal does not need a "durable" capability.** Durability is a property of the step function (does it consult a checkpoint), not of the model call, and not of concurrency. A provider stays stateless and single-shot, which is exactly what we want — a checkpoint that cached a provider's connection would be wrong.

## (c) Where it is awkward, leaky, or unresolved

- **No portable graph IR — by construction, and this is a genuine loss.** Background §what's hard's third point is "there is no portable IR for a step graph." The proposal *embraces* that: the graph is the function body, so there is no artifact to inspect, visualize, diff, or hand to a scheduler. You cannot, in this model, render the DocPipeline as a DAG, statically detect an unreachable branch, or have a runtime decide to run two nodes on different machines — because the topology is implicit in `let`/`match`/`while`. Mastra's `.commit()` and LangGraph's compiled `StateGraph` are reifiable; a BAML function body is not. For teams that want graph observability or distributed scheduling, this is a hard wall the proposal will not climb without a separate IR layer that has nothing to do with providers.

- **`baml.future.all` is homogeneous in `<T,E>`, so joining heterogeneous error channels still forces a box.** `Analyzed { summary: await fSummary, label: await fLabel }` is a plain literal over two awaited spawns, which is ergonomic — and because `await` re-throws each future's `E` independently, the two-future case never even has to unify a channel: each `await` fails on its own `baml.ExtendUnknownError<baml.errors.CallError>`. The friction appears only when you join a *homogeneous list* via `baml.future.all<T,E>(fs)`: it is generic over a single `T` and a single `E`, so every future in the array must share both. Here every analyze branch is a node body on `baml.ExtendUnknownError<baml.errors.CallError>`, so `E = baml.errors.CallError | baml.UnknownError` and it unifies for free — the new model makes the homogeneous case trivially clean (no per-provider `type Error` to reconcile, because there never was one). But put a `CallError` node and a `ToolError` node in the *same* `baml.future.all` array — exactly the legal-review branch, were it folded into the parallel list — and the two channels do **not** unify: `CallError` and `ToolError` are independent interfaces, not a hierarchy. The array's element type then has to widen to `baml.UnknownError` (the only common supertype), which is precisely what the `legal_review` step does today: it `catch`es `LegalReview`'s `ToolError` and boxes it through `baml.UnknownError.with_message<…CallError>` so it can ride the node's `CallError` channel. **That boxing is a real, named cost — but it is a loss of the *static* story, not of the error.** The `ToolError` is not destroyed: `with_message` annotates the `UnknownError` in place and `.data: unknown` holds the original value untouched, so re-asserting `from<ToolError>(e)` at any later layer where `ToolError` is back in scope pulls the *same* concrete error back out, `is_*` classifiers intact. What the heterogeneous join actually costs is *discoverability*: the channel is `CallError | baml.UnknownError`, which does not advertise that a tool failure can be recovered inside the box — so the app can only get its `is_*` classifiers back by *speculatively* probing `from<ToolError>(e)`, never by following the type. That is exactly the P2 pattern (capability-as-runtime-promise) applied to the error channel: precision is recoverable at runtime but not statically guaranteed. And the recovery is firm in cost, not conditional: a `catch (e) { let t: baml.errors.ToolError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `ToolError`), so that arm never fires on it — `catch` does **not** auto-unwrap. A plain catch across the join boundary therefore only ever sees `CallError` or `UnknownError`; to pull the tool failure back the author must *explicitly* `baml.UnknownError.from<baml.errors.ToolError>(e)` inside the `UnknownError` arm. The escape hatch (`baml.UnknownError` everywhere) keeps it typechecking and lossless; what the heterogeneous join costs is the *static* signal that a recoverable tool failure can reach you here — reachable, but only by code that already knows to probe for it. (Note this is a property of the homogeneous-list combinator, not of concurrency itself — two-future `spawn`/`await` fan-in side-steps it entirely.)

- **Open Question 5 (capability `match` over an existential) is dodged, not used.** This scenario almost never `match`es on capabilities — the graph calls `.call` and `.run_tools` directly. That is a feature (less runtime negotiation) but it also means the scenario provides no new evidence for OQ5; the one place it surfaces is inside the generated `.run_tools` companion, which `match`es for `Tools`. If `LegalAgent()` were swapped for a non-tool provider, the failure is a runtime throw, not a compile error — so a graph cannot *guarantee* at compile time that its agentic node is tool-capable. For a durable graph that may run for hours before reaching the legal node, discovering "not tool-capable" at node-execution time is genuinely bad. The escape hatch (drop `client` sugar, write `function … -> SomeToolsProvider`) exists but is not ergonomic for a graph node.

- **Open Question 1 (does every capability `requires Provider`) is irrelevant here, which is itself a finding.** Durability and concurrency are *not* capabilities in this model — they are orthogonal layers. So the proposal's capability machinery, which is the centerpiece for streaming/realtime/tools, contributes nothing to the step-graph story. The model is not wrong; it is simply silent. But the silence is asymmetric: concurrency is *already provided by the language* (`spawn`/`await`/`baml.future.all`/`baml.spawn.TaskGroup`, BEP-034), so only durability (`Checkpoint`) falls to the app. An honest reading is that "step graph" is mostly *outside* the proposal's scope — the proposal governs what a node *does* when it talks to a model, while sequencing/joining is plain BAML control flow plus shipped concurrency, and only checkpointing is a genuinely new app layer.

- **The durability layer is OFF the capability-error model, and that is a deliberate-but-awkward choice.** `Checkpoint.load/save` throw the raw host `baml.errors.Io`, NOT a `baml.ExtendUnknownError<…>` channel — because checkpointing is not a model capability, it has no `baml.errors.<Cap>Error` interface, and inventing a `CheckpointError` interface with `is_network_error()`/`is_rate_limit()` classifiers would be nonsense (a KV write failure is not a rate limit). So the orchestration layer keeps the pre-existing `baml.errors.Io` channel and the `step` memoizer simply swallows it (`catch (e) { _ => null }` forces recompute). This is the right call, but it means the scenario has TWO error vocabularies side by side — capability errors (`CallError`/`ToolError`) for the node bodies and bare `baml.errors.Io` for the durability store — and the new model only governs the first. A reader expecting "one error model for the whole graph" gets one model for *nodes* and a separate, older channel for *durability*. The new capability-error interfaces (§4) do not want a `CheckpointError` member, which is itself the finding: durability genuinely is not a capability.
- **Concrete typed errors do NOT survive a checkpoint round-trip.** `RefineNotConverged` is a concrete class the app catches most-specific-first — but the durable graph never gets to. `step(...)` only checkpoints *successful* outputs; a throw aborts the step and is never serialized. More subtly, even if we wanted to persist a failure, a `Refused` / `RefineNotConverged` value carrying behavior (its `implements baml.errors.CallError` classifier methods) cannot be round-tripped through a KV blob and rehydrated as the same concrete type with its `is_*` methods intact — serialization erases the `implements` witness. So on a *resumed* run a previously-failed step re-executes from scratch and may throw a *freshly-constructed* concrete error; the app's most-specific-first catch still works, but only because the error is recreated, not restored. The error model assumes errors are live in-process values, and durability assumes everything is a serializable blob; the two assumptions do not compose for typed errors.

- **Durability is shallow.** `step(...)` memoizes outputs, which resumes a crashed graph from the last completed step — but it does NOT snapshot in-flight execution. A step that crashes *mid-loop* (iteration 3 of refine) re-runs the whole step from iteration 1 on resume, because only the step's final output is checkpointed, not its internal loop counter. True suspend/resume (background §3, the `suspend()` inside a step) is a different and harder primitive this scenario does not provide, and the proposal has nothing to offer there either — it is, again, orthogonal.

## (d) Verdict

**Workable-with-additions.** The proposal carries the model-touching parts of a step graph cleanly and almost invisibly: a node is `provider.call`, providers stay portable across the divergent structured-output encodings, and a model-decides agent slots in as one node via the reused `Tools` capability — code-defines and model-decides compose with no friction. Of the two things that make a step graph a *graph* and *durable* — concurrent fan-in/join and checkpointed resume — only **one** is net-new: concurrent fan-in/join is a *shipped language feature* (BEP-034 — `spawn`/`await`, `baml.future.all`/`all_complete`, `baml.spawn.TaskGroup`, `CancelToken`), so fan-out is a list of spawns and the join is `baml.future.all`, with cancellation and rate-limiting first-class. Only durable checkpoint/resume (`Checkpoint`) is a genuinely net-new app layer, and it sits outside the provider/capability model. That is the correct architecture (durability is not a property of a model call, and concurrency is the language's job, not a Provider capability), but it means the proposal's central machinery is largely a spectator for this scenario. The genuine, unfixable-by-this-proposal losses are real and worth naming: no portable graph IR, no compile-time guarantee that an agentic node is tool-capable, no true mid-step suspend/resume, and — new under the per-capability error model — folding a tool node into a homogeneous `baml.future.all` list (or wrapping it in a `CallError`-typed step) boxes its typed `ToolError` into `baml.UnknownError`, where the error's data and identity survive (recoverable via an explicit `from<ToolError>` probe — `catch` does not auto-unwrap, so a plain `let t: ToolError =>` arm never matches the box) but the *static* signal that a tool failure is recoverable here does not — a runtime promise, the P2-analog. None of these are provider concerns, so none are the proposal's fault — but a reader expecting "the new client model solves workflows" should leave understanding that it solves the *node*, the language solves *concurrency*, and the app supplies only *durability*.
