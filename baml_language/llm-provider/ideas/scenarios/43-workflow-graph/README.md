# 43 — Composing a durable step graph

A step graph (Mastra's `.then/.parallel/.branch/.dountil` chain, pydantic-graph's node DAG, LangGraph's `StateGraph`) is, in the proposed model, just ordinary BAML: a step is a typed `function`, an edge is a `let`, a branch is a `match`, a loop is a `while`, and a model call inside a step is a plain `provider.call<T>(...)`. So the provider/client/capability model is almost a spectator here — it cleanly carries the *node* (including a model-decides agentic node, reused as the `Tools` capability) and keeps the two divergent providers (OpenAI `response_format` vs Anthropic forced-tool) portable behind identical call-sites. The concurrent fan-in/join sync barrier that makes a step graph a *graph* is **not** net-new: BAML has first-class structured concurrency (BEP-034) — fan-out is a list of `spawn`s and the join is `baml.future.all` (bounded fan-out is a `baml.spawn.TaskGroup`). The one genuinely net-new thing that makes a step graph *durable* is checkpointed resume (`Checkpoint` + a `step(...)` memoizer), which sits deliberately outside the Provider hierarchy. `implement.baml` is the library layer; `usage.baml` is the doc-pipeline graph an app author writes; `evaluation.md` stresses where this leaks — chiefly: no portable graph IR, no compile-time guarantee an agentic node is tool-capable, and only shallow (output-level, not mid-step) durability.
