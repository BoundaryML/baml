# Evaluation — Built-in tools + on-disk sessions

Adversarial read of whether the proposed `Provider`/capability model expresses a coding harness whose toolset is opinionated and whose transcript is a real on-disk store you can continue/resume/fork and query.

## (a) What the proposal reuses unchanged

- **`Provider` base + the `client → function … -> Provider` sugar.** `CodeAgent()` is config-only; `cwd` and `session_root` are ordinary fields (proposal §4, "options dissolve into provider fields"). The one-shot `Fix(...)` is just `.call`. No new surface for the basic shape.
- **The `SessionStore` 4-method protocol from scenario 17, verbatim.** The entire point — "a harness is a Provider whose transcript store is a real filesystem object" — is expressed by giving `JsonlSessionStore` the *same* `load/save/ append/clear` interface that scenario 17's in-process `MemoryStore` implements. The seam survived the substrate change with zero edits. The divergence (fsync-append vs hashmap insert; nested Anthropic `BetaMessage` flattening) is entirely inside the host bodies, which is exactly where the proposal says per-provider divergence belongs.
- **The `Realtime` + `ControlPlane` control plane from scenario 37, unchanged.** Steer/Interrupt/RewindFiles ride the handed-in `Channel`; this scenario adds storage without touching that. We elided it rather than re-teach it.
- **Capability negotiation as a runtime `match` (proposal §5).** "Can I query this client's sessions?" is `match (p) { let cat: SessionCatalog => …, _ => … }`, identical in shape to `.stream`/`.live`. The `_` arm errors honestly because a chat model genuinely has no store — there is no meaningful fallback, like `Realtime`.
- **The first-class `type` primitive + `reflect.type_of` for tool schemas.** The built-in toolset's `parameters` are real `type` values (`reflect.type_of<ReadArgs>()`), the same mechanism scenario 09/37 use for `Tool`.
- **`Tools` (begin/step/submit/run_tools)** for the host-dispatch path, unchanged from §7; we only wire `self.tools()` into `begin` so allow/deny is honored.

## (b) Net-new surface it must add (each tied to a primitive)

- **`SessionCatalog requires Provider`** — a new capability interface. Ties to proposal §1 (capabilities are `requires Provider` interfaces) and §5 (negotiated by `match`). It carries the queryable helpers (`list_sessions`, `session_messages`, `rename_session`, `tag_session`) and the pickup-and-run bridge (`call_in_session` default method + `resolve_pickup` + the provider-specific `call_with_session`). This is the harness analog of 17's `Conversational`: thread a persisted transcript through `Provider.call`, but addressable by id and on disk.
- **`type Store: SessionStore`** — an associated type with a bound on the capability. Ties to the associated-`type` machinery (`HttpProvider`'s `type Body`, `Tools`' `type Transcript`). Needed so a harness can bind its own store substrate (JSONL vs Pi tree) while the protocol stays storage-agnostic. **This is mild net-new: the proposal's associated types are unconstrained (`type Body`, `type Transcript`); a *bounded* associated type (`Store: SessionStore`) is a small extension the proposal never exercises.**
- **`Pickup` union (`Fresh | Continue | Resume | ResumeAt | Fork`)** — net-new data, the closed-union refinement of the Claude SDK's boolean bag (§5). Ties to the `type X = A | B` union primitive (same as scenario 37's `OutEvent`). Modeling it as a union *fixes* a real SDK footgun (you can't say `continue: true, resume: id` at once) — a place the proposal's data model is strictly better than the thing it models.
- **`BuiltinTools` catalog + allow/deny `resolve`** — net-new data + a pure function. Ties to the `Tool` type (§7) and the first-class `type`. The background's "you allow or deny, you don't define" is expressed by making the catalog a static and the only lever a `string[]` filter.
- **`SessionInfo`** — net-new metadata row (`tags`, `title`, `parent_id`, `branch_point`, `cwd`). Plain class; the return type of `list_sessions`. No new primitive, but it is surface the proposal's vocabulary didn't have.
- **Host boundary functions** (`encode_cwd`, `fork_copy_prefix`, `pi_tree_branch_at`, …) as `$rust_io_function`. Ties to Open Q7 (host-backed bodies inside `implements` blocks) — confirmed in scope by the proposal.

## (c) Where it is awkward, leaky, or unresolved

- **No compile-time guarantee that a client is queryable (Open Q5 + §5).** `CodeAgent()` returns the existential `Provider`. "Does this client persist sessions I can resume?" is answered only by a runtime `match`. For a harness this is worse than for streaming: an app that *needs* resume (a long-running incident agent) gets no type error if someone swaps in a chat client — it gets a runtime `Unsupported`. The proposal's escape hatch (drop the sugar, write `function … -> ClaudeCode`) works but then you lose Fallback/dynamic-selection, which is precisely what a resilient harness wants. **This is the proposal's acknowledged runtime-capability tradeoff, and harness-resume is one of the sharper places it bites.** Open Q5 is directly engaged: the whole scenario leans on `match (p) { let cat: SessionCatalog => … }` over an interface-existential.
- **`cwd`-keyed storage is a footgun the model surfaces but cannot prevent.** We made it *visible* (`store()` is literally `(session_root, cwd)`; `ContinueElsewhere` silently starts fresh). But the type system can't stop you: `Continue {}` against the wrong cwd is well-typed and returns a brand-new session with no error. The proposal gives us nowhere to encode "this Pickup only makes sense relative to the cwd that created the session." The honest mitigation is the day-one escape hatch (a non-cwd store), and we had to express it as a *whole different harness* (`PortableCoder`/`PiAgent`) because `ClaudeCode.store()` is hardwired. **You cannot "swap the store" as a field** — storage substrate is baked into the provider class, so the SqliteSessionStore we defined is unreachable from `ClaudeCode` without adding a `store: SessionStore` field, which the proposal's "fields are config" rule would happily allow but scenario 37 did not anticipate.
- **`tools()` lives on the concrete class, not the capability — so reading it from a client is ugly.** `ToolPalette()` wants the shipped toolset, but `tools()` is a `ClaudeCode` method, not a `SessionCatalog` method, and the client is the existential `Provider`. The `match` gets us `SessionCatalog` but not `tools()`; we fall back to recomputing `BuiltinTools.resolve(...)` with the literal allow/ deny list, which duplicates the client config. To do this cleanly we'd need *either* a `Toolset` capability (`function tools(self) -> Tool[]`) or to accept the compile-time escape hatch. This is a real ergonomic leak: a fully general "what can this agent do?" UI can't be written against the existential.
- **Server-authoritative / subprocess-authoritative state is unmodeled (Open Q3).** `call_with_session` must point `claude --resume <id>` at the *same* jsonl BAML's `JsonlSessionStore` reads. Nothing in the type system enforces that the subprocess and BAML agree on the file, or on the encoding of `<encoded-cwd>`. If the bundled `claude` binary changes its cwd-encoding, our `encode_cwd` silently diverges and resume breaks. The proposal's "HTTP is a capability, not the base" framing (Open Q3) has no story for "the transport *owns* the persistence and BAML is a second reader of it." We model the store as if BAML owns it; in reality the subprocess co-owns it. **This is genuinely unresolved — the proposal cannot express a store that is authoritative outside the BAML process.**
- **Fork-as-copy vs fork-as-pointer leaks into semantics, not just cost.** We hid it behind `resolve_pickup`, but the two are not actually equal: `ResumeAt` on Claude is in-place truncation (destructive to the existing id), while on Pi it *must* branch (a tree has no in-place truncation). So `ResumeAt` against the same `Pickup` value has different observable effects on the two harnesses — the portability is shallower than the shared interface suggests. The interface unifies the *call*, not the *consequence*.
- **`session_messages` returns flat `Turn[]`, but §5's "content blocks buried in nested types" means the flattening is lossy.** Our `Turn.blocks` is `map<string, unknown>[]` here (17 owns the real grammar); reaching into a Claude `SDKAssistantMessage.message: BetaMessage` to flatten thinking/tool_use blocks is a host-body concern we waved at. A consumer that wants the *raw* nested block (e.g. a thinking signature) can't get it through this interface.

## (d) Verdict: **Workable-with-additions**

The core claim holds and is even elegant: a harness is a `Provider`, its store is a real `SessionStore`, and the queryable/pickup surface is one negotiated capability (`SessionCatalog`) that two genuinely different substrates (cwd-keyed JSONL, pointer tree) both implement — the same way `HttpProvider` and a subprocess both implement `Provider`. The reuse of scenario 17's store protocol and scenario 37's control plane is real, not cosmetic. But it needs concrete additions the proposal doesn't ship — a `SessionCatalog` capability, a *bounded* associated type (`Store: SessionStore`, which the proposal never exercises), and a `Pickup` union — and it leaves three things unresolved that matter for harnesses specifically: no compile-time guarantee of resume-ability (Open Q5), a cwd footgun the type system can surface but not prevent, and — the real wall — no way to model a transcript store that is *authoritative outside the BAML process* (Open Q3), which is exactly what a subprocess-owned `~/.claude/projects/*.jsonl` is. The model treats BAML as the store's owner; in production it is a co-reader. That gap is honest and unfixed.
