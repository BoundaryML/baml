# Evaluation — Built-in tools + on-disk sessions

Adversarial read of whether the proposed `Provider`/capability model expresses a coding harness whose toolset is opinionated and whose transcript is a real on-disk store you can continue/resume/fork and query.

## (a) What the proposal reuses unchanged

- **`Provider` marker + the `client → function … -> Provider` sugar.** `CodeAgent()` is config-only; `cwd` and `session_root` are ordinary fields (proposal §4, "options dissolve into provider fields"). Under the marker model (`../provider-as-marker.md`) the harness is NOT an `HttpProvider` and carries no base `call`; the one-shot `Fix(...)` is the harness's REAL interaction — `SessionCatalog.call_in_session(..., Fresh {})` negotiated by a companion `match`. No degenerate `call` is faked, and the "basic shape" is simply the `Fresh {}` pickup.
- **The `SessionStore` 4-method protocol from scenario 17, verbatim.** The entire point — "a harness is a Provider whose transcript store is a real filesystem object" — is expressed by giving `JsonlSessionStore` the *same* `load/save/ append/clear` interface that scenario 17's in-process `MemoryStore` implements. The seam survived the substrate change with zero edits. The divergence (fsync-append vs hashmap insert; nested Anthropic `BetaMessage` flattening) is entirely inside the host bodies, which is exactly where the proposal says per-provider divergence belongs.
- **The `Realtime` + `ControlPlane` control plane from scenario 37, unchanged.** Steer/Interrupt/RewindFiles ride the handed-in `Channel`; this scenario adds storage without touching that. We elided it rather than re-teach it.
- **Capability negotiation as a runtime `match` (proposal §5).** "Can I query this client's sessions?" is `match (p) { let cat: SessionCatalog => …, _ => … }`, identical in shape to `.stream`/`.live`. The `_` arm errors honestly because a chat model genuinely has no store — there is no meaningful fallback, like `Realtime`.
- **The first-class `type` primitive + `reflect.type_of` for tool schemas.** The built-in toolset's `parameters` are real `type` values (`reflect.type_of<ReadArgs>()`), the same mechanism scenario 09/37 use for `Tool`.
- **`Tools` (begin/step/submit/run_tools)** for the host-dispatch path, unchanged from §7; we only wire `self.tools()` into `begin` so allow/deny is honored.

## (b) Net-new surface it must add (each tied to a primitive)

- **`SessionCatalog requires Provider`** — a new capability interface. Ties to proposal §1 (capabilities are `requires Provider` interfaces) and §5 (negotiated by `match`). It carries the queryable helpers (`list_sessions`, `session_messages`, `rename_session`, `tag_session`) and the pickup-and-run bridge (`call_in_session` default method + `resolve_pickup` + the provider-specific `call_with_session`). This is the harness analog of 17's `Conversational`: thread a persisted transcript through the harness's own subprocess run (`call_with_session`), addressable by id and on disk. Under the marker model there is no base `Provider.call` to bottom out on — the harness's real interaction IS this session run, which is why `call_in_session`/`call_with_session` (not a faked `call`) carry the one-shot.
- **`type Store: SessionStore`** — an associated type with a bound on the capability. Ties to the associated-`type` machinery (`HttpProvider`'s `type Body`, `Tools`' `type Transcript`). Needed so a harness can bind its own store substrate (JSONL vs Pi tree) while the protocol stays storage-agnostic. **This is mild net-new: the proposal's associated types are unconstrained (`type Body`, `type Transcript`); a *bounded* associated type (`Store: SessionStore`) is a small extension the proposal never exercises.**
- **`Pickup` union (`Fresh | Continue | Resume | ResumeAt | Fork`)** — net-new data, the closed-union refinement of the Claude SDK's boolean bag (§5). Ties to the `type X = A | B` union primitive (same as scenario 37's `OutEvent`). Modeling it as a union *fixes* a real SDK footgun (you can't say `continue: true, resume: id` at once) — a place the proposal's data model is strictly better than the thing it models.
- **`BuiltinTools` catalog + allow/deny `resolve`** — net-new data + a pure function. Ties to the `Tool` type (§7) and the first-class `type`. The background's "you allow or deny, you don't define" is expressed by making the catalog a static and the only lever a `string[]` filter.
- **`SessionInfo`** — net-new metadata row (`tags`, `title`, `parent_id`, `branch_point`, `cwd`). Plain class; the return type of `list_sessions`. No new primitive, but it is surface the proposal's vocabulary didn't have.
- **`baml.errors.SessionError` — a NET-NEW capability-error interface (error model rule 4).** Because `SessionCatalog` is a capability beyond call/stream/realtime/tools, the canonical error model forces a matching capability-error interface: every catalog method declares `baml.ExtendUnknownError<baml.errors.SessionError>`. Its classifiers are `is_network_error` (a transient store/DB blip) and a session-specific `is_not_found` — the latter is the honest admission that the core classifiers (`is_rate_limit`/`is_parse_error`) say nothing useful about a session control-plane failure. The concrete `SessionNotFound` implements it and is what a resume/continue/fork against a missing id or moved cwd raises — a *typed domain channel*, the direct analog of the old refusal-as-typed-channel idea (a declined resume is neither the answer nor a transport failure). Foreign `baml.errors.Io` from the on-disk store is normalized at the catalog boundary via the trailing `baml.UnknownError.with_message<baml.errors.SessionError>(e, …)`. This must be flagged net-new because the proposal ships only the four core capability-error interfaces.
- **Host boundary functions** (`encode_cwd`, `fork_copy_prefix`, `pi_tree_branch_at`, …) as `$rust_io_function`. Ties to Open Q7 (host-backed bodies inside `implements` blocks) — confirmed in scope by the proposal.

## (c) Where it is awkward, leaky, or unresolved

- **No compile-time guarantee that a client is queryable (Open Q5 + §5).** `CodeAgent()` returns the existential `Provider`. "Does this client persist sessions I can resume?" is answered only by a runtime `match`. For a harness this is worse than for streaming: an app that *needs* resume (a long-running incident agent) gets no type error if someone swaps in a chat client — it gets a runtime `Unsupported`. The proposal's escape hatch (drop the sugar, write `function … -> ClaudeCode`) works but then you lose Fallback/dynamic-selection, which is precisely what a resilient harness wants. **This is the proposal's acknowledged runtime-capability tradeoff, and harness-resume is one of the sharper places it bites.** Open Q5 is directly engaged: the whole scenario leans on `match (p) { let cat: SessionCatalog => … }` over an interface-existential.
- **`cwd`-keyed storage is a footgun the model surfaces but cannot prevent.** We made it *visible* (`store()` is literally `(session_root, cwd)`; `ContinueElsewhere` silently starts fresh). But the type system can't stop you: `Continue {}` against the wrong cwd is well-typed and returns a brand-new session with no error. The proposal gives us nowhere to encode "this Pickup only makes sense relative to the cwd that created the session." The honest mitigation is the day-one escape hatch (a non-cwd store), and we had to express it as a *whole different harness* (`PortableCoder`/`PiAgent`) because `ClaudeCode.store()` is hardwired. **You cannot "swap the store" as a field** — storage substrate is baked into the provider class, so the SqliteSessionStore we defined is unreachable from `ClaudeCode` without adding a `store: SessionStore` field, which the proposal's "fields are config" rule would happily allow but scenario 37 did not anticipate.
- **`tools()` lives on the concrete class, not the capability — so reading it from a client is ugly.** `ToolPalette()` wants the shipped toolset, but `tools()` is a `ClaudeCode` method, not a `SessionCatalog` method, and the client is the existential `Provider`. The `match` gets us `SessionCatalog` but not `tools()`; we fall back to recomputing `BuiltinTools.resolve(...)` with the literal allow/ deny list, which duplicates the client config. To do this cleanly we'd need *either* a `Toolset` capability (`function tools(self) -> Tool[]`) or to accept the compile-time escape hatch. This is a real ergonomic leak: a fully general "what can this agent do?" UI can't be written against the existential.
- **Server-authoritative / subprocess-authoritative state is unmodeled (Open Q3).** `call_with_session` must point `claude --resume <id>` at the *same* jsonl BAML's `JsonlSessionStore` reads. Nothing in the type system enforces that the subprocess and BAML agree on the file, or on the encoding of `<encoded-cwd>`. If the bundled `claude` binary changes its cwd-encoding, our `encode_cwd` silently diverges and resume breaks. The proposal's "HTTP is a capability, not the base" framing (Open Q3) has no story for "the transport *owns* the persistence and BAML is a second reader of it." We model the store as if BAML owns it; in reality the subprocess co-owns it. **This is genuinely unresolved — the proposal cannot express a store that is authoritative outside the BAML process.**
- **Fork-as-copy vs fork-as-pointer leaks into semantics, not just cost.** We hid it behind `resolve_pickup`, but the two are not actually equal: `ResumeAt` on Claude is in-place truncation (destructive to the existing id), while on Pi it *must* branch (a tree has no in-place truncation). So `ResumeAt` against the same `Pickup` value has different observable effects on the two harnesses — the portability is shallower than the shared interface suggests. The interface unifies the *call*, not the *consequence*.
- **`session_messages` returns flat `Turn[]`, but §5's "content blocks buried in nested types" means the flattening is lossy.** Our `Turn.blocks` is `map<string, unknown>[]` here (17 owns the real grammar); reaching into a Claude `SDKAssistantMessage.message: BetaMessage` to flatten thinking/tool_use blocks is a host-body concern we waved at. A consumer that wants the *raw* nested block (e.g. a thinking signature) can't get it through this interface.
- **The marker model *simplifies* the harness error surface: there is no base `call` channel to reconcile against.** Under `../provider-as-marker.md` the harness is not an `HttpProvider`, so it has NO `CallError` channel at all. The two error surfaces it actually exposes are the host-dispatch tool loop (`ToolError`) and the session run + catalog (`SessionError`) — both wired to the SAME subprocess and the SAME jsonl, but neither is a faked request/response `call`. When `call_with_session` spawns `claude --resume <id>` and the subprocess can't find the file, the run itself is *on the `SessionError` channel* (it is `call_in_session`/`call_with_session`, both declared `baml.ExtendUnknownError<baml.errors.SessionError>`), so a `SessionNotFound` rides it as its typed self with no boxing and no channel-crossing question — the cause (a missing session) and the channel (`SessionError`) now agree. The old worry — "the failure surfaces during a base `call` whose channel is `CallError`, so does the `SessionError` box?" — is **moot under the marker model**: there is no base `call` here. The only residual crossing is the genuinely cross-capability one (a `SessionError` from the run surfacing to a host-dispatch `ToolError` consumer, or vice versa), and that is the same coverage convention as everywhere else: declare `implements baml.errors.ToolError for baml.errors.SessionNotFound` if you want it typed across, else it boxes into `baml.UnknownError` (data preserved in `.data`, recover with `from<SessionError>`). `catch` remains no-auto-unwrap, so an unimplemented crossing never fires a plain `let s: SessionError =>` arm and must be probed explicitly. Nothing *forces* the `implements` row, so a forgotten one boxes silently — a convention to follow, not a wall the model erects.
- **`is_not_found` is a classifier the proposal's shape never anticipated, and it exposes the limit of "common classifiers."** The core interfaces standardized on `is_network_error`/`is_rate_limit`/`is_parse_error` precisely so a caller can triage *without* the concrete class. But the meaningful question for a session is "does it exist?", which none of those three answer — so we added `is_not_found` to `SessionError`. That is fine here, but it means the "triage without knowing the concrete class" promise is per-capability, not universal: a generic retry/fallback combinator that only knows `is_network_error` cannot distinguish a recoverable transport blip from a permanent missing-session error on the SessionError channel, and would either retry a hopeless resume or give up on a transient one. Each new capability that needs a new classifier silently widens what a generic consumer must know.
- **A combinator over a `SessionCatalog` forwards `SessionError`, a channel the canonical `Fallback`/`Retry` declare for HTTP providers don't carry — but adding it is mechanical, not variance gymnastics.** The canonical HTTP combinators declare `baml.ExtendUnknownError<CallError>` on their `call`/`call_with`. A `Fallback` between `ClaudeCode` and `PiAgent` (both `SessionCatalog`s, neither an `HttpProvider`) forwarding `call_in_session` declares `baml.ExtendUnknownError<SessionError>` on *that* method — still the SAME channel on both sides (each member's `call_in_session` already throws `SessionError`), so the "combinators declare the same channel, no variance" property holds method-by-method; a session-capable combinator simply carries the session channel on its session methods (and `ToolError` on any host-dispatch tool methods it also forwards). The `Unsupported` a member's `_` arm raises rides the `SessionError` channel typed via the channel author's external `implements baml.errors.SessionError for baml.errors.Unsupported` row (one impl declared alongside the channel), so negotiation failures don't box either. The genuinely structural residual is narrower and unrelated to boxing: a harness combinator that forwards *both* capabilities threads two distinct channels (`SessionError` on `call_in_session`, `ToolError` on the host-dispatch loop) — they don't merge into one — and a `Fallback` surfacing one member's `SessionError` still does not capture the *set* of what each member threw (the aggregate-provenance gap, independent of any channel choice).

## (d) Verdict: **Workable-with-additions**

The core claim holds and is even elegant: a harness is a `Provider` (the marker — `../provider-as-marker.md`), its store is a real `SessionStore`, and the queryable/pickup surface is one negotiated capability (`SessionCatalog`) that two genuinely different substrates (cwd-keyed JSONL, pointer tree) both implement — the same way an `HttpProvider` and a subprocess are both Providers without sharing a `call`. The marker model also *removes* the old "degenerate harness `call`" complaint (OQ1): `ClaudeCode`/`PiAgent` no longer fake an `implements Provider { call }`; their real one-shot is `SessionCatalog.call_in_session(..., Fresh {})`, a subprocess run on the `SessionError` channel — so the cause (a missing/failed session) and the channel finally agree. The reuse of scenario 17's store protocol and scenario 37's control plane is real, not cosmetic. But it needs concrete additions the proposal doesn't ship — a `SessionCatalog` capability, its matching net-new `baml.errors.SessionError` channel (with a `is_not_found` classifier the four core interfaces never anticipated), a *bounded* associated type (`Store: SessionStore`, which the proposal never exercises), and a `Pickup` union — and it leaves three things unresolved that matter for harnesses specifically: no compile-time guarantee of resume-ability (Open Q5), a cwd footgun the type system can surface but not prevent, and — the real wall — no way to model a transcript store that is *authoritative outside the BAML process* (Open Q3), which is exactly what a subprocess-owned `~/.claude/projects/*.jsonl` is. The per-capability error model adds NO fourth structural pressure here, and the marker model makes that *cleaner* than before: with no base `call`, there is no `CallError`-vs-`SessionError` reconciliation to make — the run lives on `SessionError` directly. The only residual error crossing is the genuinely cross-capability one (`SessionError` ↔ `ToolError`, both over the same subprocess), the same coverage convention as everywhere else: declare the `implements` row to keep it typed, else it boxes into `baml.UnknownError` (data and classifiers preserved, recover via `from<SessionError>`), and `catch` being no-auto-unwrap means recovery is an explicit `from<T>` probe, never a plain interface arm. A convention to follow, not a wall the model erects; the only true residual is that nothing *forces* the `implements` row, so a forgotten one boxes silently. The standing harness-specific gaps are the three above (Open Q5 resume-ability, the cwd footgun, Open Q3 external ownership), not the error channel. The model treats BAML as the store's owner; in production it is a co-reader. That gap is honest and unfixed.
