# Evaluation — Agents inside workflows, workflows inside agents

Adversarial read of whether the proposed Provider/capability/`client`-is-sugar model expresses two-directional nesting: an agent loop as a durable workflow step, and a whole durable workflow as a single agent tool.

## (a) What the proposal reuses unchanged

- **"A workflow IS a Provider" is the whole direction-B payoff, and it is free.** The proposal's load-bearing claim is `client = function -> Provider` and that a `Provider` is just `call<T>(prompt) -> T`. A workflow is also a function. So `WorkflowProvider.call` adapts one to the other with no new interface — the workflow then composes anywhere a provider does (member of a `Fallback`, wrapped in `Durable`). This is the cleanest part of the scenario.
- **`Tools` is reused verbatim for the inner agent.** The triage agent is just a `Tools` provider; `run_tools` (the default loop) drives it. The four structured-output encodings and the id-vs-name / positional `tool_result` correlation stay below the `ToolCall`/`ToolResult` seam inside `Anthropic`'s and `OpenAI`'s `Tools` impls. `usage.baml` never branches on which provider — portability holds because `Tool`/`ToolCall`/`ToolResult` are the neutral vocabulary the proposal already standardizes (proposal §7).
- **Combinator shape reused for `Durable`.** `Durable` is a plain non-generic class wrapping a `Provider` and forwarding `.call`, exactly like `Fallback`/ `Retry`/`Cache` (proposal §6). An entire agent loop becomes one `.call`, so one combinator fences the entire multi-turn nondeterminism.
- **Observability records reused.** `Usage`, `Cost`, `Price`, `obs_start/finish`, `UsageReporting` come straight from scenario 32; the rollup only sums and re-attaches them.
- **Capability negotiation = a runtime `match`** (proposal §5). Asserting "this client is actually a Tools agent" is `match (ClaudeAgent()) { let t: Tools => ... }`.

## (b) Net-new surface it must add (each tied to a primitive)

- **`DurableCtx` + `durable_activity` host seam** — tied to **Provider.call** and the **combinator layer**. The base `Provider` is single-shot and has *nowhere* to express record-and-replay; that is engine state (Temporal history, DBOS step log). New host primitive: an opaque journal with a memoized `activity(ctx, key, () -> string)`. This is the irreducible addition — the proposal models the LLM call but not the durable engine.
- **`Durable` / `DurableAgentStep` combinators** — tied to **Provider** as the thing wrapped. New, but shaped exactly like existing combinators.
- **`Workflow` interface (`run` + `as_tool`)** — tied to the **`type` primitive** (`as_tool` reflects `Input` to a `Tool.parameters`) and to **`Tool`**. Net-new because the proposal has no notion of a durable graph; it is additive, not a change to the spine.
- **`WorkflowProvider` adapter** — tied to **Provider.call** and to the workflow's associated `Input`/`Output` types. Needs two host seams the proposal doesn't have: `baml.llm.tool_args<T>(prompt)` (decode model args) and `baml.cast.checked<T>` (the existential `Output -> T` downcast).
- **`StepRecord<T>` + `CostMeter` + `MeteredContext`** — tied to **ExecutionContext's emit surface** (proposal §7's flagged-but-undefined event channel). The rollup is the concrete consumer the proposal hand-waved.
- **`json_encode/decode` (canonical)** — tied to the journal serialization boundary; deterministic encoding is required for replay-stable bytes.

## (c) Where it is awkward, leaky, or unresolved

- **Determinism is enforced by host convention, not the type system.** Nothing in the proposal stops a workflow author from calling a model OUTSIDE a `Durable` step (a bare `client().call`), which would re-sample on replay and corrupt the journal. The model has no way to say "every model call inside a `Workflow.run` must be fenced." This is the background §6 "easy to get subtly wrong" hazard, and the proposal cannot make it a compile-time guarantee — it can only offer the combinator and hope it's used. **Open Question 1** (does every capability `requires Provider`?) bites here: because `Durable` deliberately does NOT implement `Streaming`/`Realtime` (you cannot replay a live duplex), a durable step silently loses those capabilities, and the loss is only discovered at the call's `_` arm — never at compile time.

- **`fresh`/replay attribution is a hack.** `durable_is_live(ctx)` reads the engine's `info.is_replaying` bit to decide whether tokens were really spent. That bit is genuinely host state, but threading it through `StepRecord.fresh` means cost rollup is correct only if every consumer remembers to check it. The proposal's clean `Usage` record has no place to say "this cost is a replayed echo, not a fresh charge", so we bolt it on. **Open Question 5** (capability `match` over an existential) is adjacent: we also rely on runtime reflection to assert `Tools`, and a `Fallback` of agents would claim `Tools` statically but could route to a non-Tools member — a durable step over such a fallback would journal a confusing failure.

- **The two-nondeterminism boundary leaks at the adapter cast.** `WorkflowProvider.call` must `baml.cast.checked<T>(out)` because the agent's tool dispatch unifies the tool result type `T` with the workflow's `Output` existentially — the compiler cannot see through `Workflow.Output` at the dispatch site. So a workflow-as-tool whose `Output` doesn't match what the agent expects fails at runtime, not compile time. This is the same existential-erasure the proposal accepts everywhere `client` returns the opaque `Provider`, now showing up at a graph boundary.

- **Nested durability scoping is asserted, not proven.** `ctx.child(key)` gives a workflow-as-tool its own journal under the parent agent-step's activity. Whether a child workflow correctly resumes when the PARENT step replays (does the engine replay the child too, or treat the parent activity's recorded output as terminal?) is engine-specific (background §6 "whether the inner agent is itself durable"). The proposal has no opinion; we punt to `DurableCtx` semantics. If the parent step is one activity, the child workflow's per-step checkpoints are *invisible* to the outer engine — which is correct for replay but means the inner workflow's partial progress is lost on outer-step retry. That tradeoff is unresolvable in this model; it is a property of where you draw the activity boundary, and the proposal gives no vocabulary to draw it.

- **`emit`/`MeteredContext` is still vapor in the proposal.** §7 only *flags* that `ExecutionContext` needs an event-emit surface. The cost rollup depends on it concretely (every inner turn must emit a `UsageEvent`). If `emit` doesn't exist, there is no portable way to intercept per-turn usage from inside an opaque `run_tools` loop — you'd have to override `run_tools` per provider, defeating the shared default.

## (d) Verdict: **Workable-with-additions**

Direction B (workflow-as-tool) is genuinely clean and is the proposal's model paying off: a workflow is a function, a function is a provider, a provider is a tool. Direction A (agent-as-step) is expressible but only by adding a real host primitive — the durable engine (`DurableCtx`/`durable_activity`) — that the proposal does not contain and arguably should not, since it is the province of Temporal/DBOS, not the LLM client layer. The model absorbs the boundary by making the whole agent loop one `.call` and wrapping it in a combinator, which is elegant; but determinism-on-replay, fresh-vs-replayed cost attribution, and nested-journal scoping are all enforced by host convention and runtime checks, never by the type system. The proposal cannot give a compile-time guarantee that a workflow's model calls are all fenced, nor that an agent-as-tool's `Output` matches — both are the same existential-erasure tax `client`-as-sugar accepts elsewhere. Net: the spine holds and composes in both directions, but a production durable-nesting story requires net-new combinators, a net-new engine seam, and the still-unspecified `emit` surface to be made real.
