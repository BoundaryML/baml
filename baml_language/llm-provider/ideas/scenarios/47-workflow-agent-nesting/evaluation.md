# Evaluation — Agents inside workflows, workflows inside agents

Adversarial read of whether the proposed Provider/capability/`client`-is-sugar model expresses two-directional nesting: an agent loop as a durable workflow step, and a whole durable workflow as a single agent tool.

## (a) What the proposal reuses unchanged

- **"A workflow IS a Provider" is the whole direction-B payoff, and it is free.** The proposal's load-bearing claim is `client = function -> Provider`, where `Provider` is now a bare composable *marker* (`../provider-as-marker.md`) and `call<T>(prompt) -> T` is the **`HttpProvider`** capability that owns the request/response shape. A workflow is also a function with a request/response shape, so `WorkflowProvider implements HttpProvider` (its `call`/`call_with`) adapts one to the other with no new interface — the workflow then composes anywhere a provider does (member of a `Fallback`, wrapped in `Durable`). This is the cleanest part of the scenario, and the marker framing makes it *more* honest: the workflow claims exactly the one capability it has (request/response), not a universal `call` it would have had to fake for a non-request/response shape.
- **`Tools` is reused verbatim for the inner agent.** The triage agent is just a `Tools` provider; `run_tools` (the default loop) drives it. The four structured-output encodings and the id-vs-name / positional `tool_result` correlation stay below the `ToolCall`/`ToolResult` seam inside `Anthropic`'s and `OpenAI`'s `Tools` impls. `usage.baml` never branches on which provider — portability holds because `Tool`/`ToolCall`/`ToolResult` are the neutral vocabulary the proposal already standardizes (proposal §7).
- **Combinator shape reused for `Durable`.** `Durable` is a plain non-generic class wrapping a `Provider` (the marker) and `implements HttpProvider` to forward `.call`/`.call_with`, exactly like `Fallback`/`Retry`/`Cache` (proposal §6, and the `../provider-as-marker.md` §3 combinator pattern: a combinator `requires Provider` for the factories and `implements` each capability it forwards). It matches its inner provider for `HttpProvider` at call time. An entire agent loop becomes one `.call`, so one combinator fences the entire multi-turn nondeterminism.
- **Observability records reused.** `Usage`, `Cost`, `Price`, `obs_start/finish`, `UsageReporting` come straight from scenario 32; the rollup only sums and re-attaches them.
- **Capability negotiation = a runtime `match`** (proposal §5). Asserting "this client is actually a Tools agent" is `match (ClaudeAgent()) { let t: Tools => ... }`.
- **The product sidecars ride the canonical `call_with` + `ResponseMeta`, not a bespoke wrapper (P1 resolved-with-mechanism).** The agent/step boundary's `usage` and replayed-echo bit are projected off a `DurableMeta` (a `ResponseMeta`) through `HttpProvider.call_with<T,U> -> (T, U)`, reusing the exact interface/concrete/`Supported`/delegation shape of `../value-sidecar-model.md` and `_conventions.md` ("Value + sidecar model"). No `StepRecord<T>` companion, no parallel `call_metered`-style method, and — because `call_with` is the `HttpProvider` capability `Durable` forwards (it matches its inner provider for `HttpProvider` and re-emits `call_with`) — no silent sidecar drop through the `Durable` combinator. The honest residuals are the value+sidecar model's own (below in (c) and §8 of the resolution doc): the Fallback aggregate is the winner's view only, per-field absence is a runtime promise (P2), and the engine-`match` escape hatch rides OQ5 wrapper-transparency. The durable *engine* round-trip (record/replay, the journal, `WorkflowError`) is deliberately **not** put through `call_with` — it is a stateful round-trip / sum, not a product sidecar, so it stays on the engine seam and the `throws` channel where the earlier work left it.

## (b) Net-new surface it must add (each tied to a primitive)

- **`DurableCtx` + `durable_activity` host seam** — tied to **`HttpProvider.call`** and the **combinator layer**. The single-shot `HttpProvider.call` has *nowhere* to express record-and-replay; that is engine state (Temporal history, DBOS step log). New host primitive: an opaque journal with a memoized `activity(ctx, key, () -> string)`. This is the irreducible addition — the proposal models the LLM call but not the durable engine.
- **`Durable` / `DurableAgentStep` combinators** — tied to **Provider** (the marker) as the thing wrapped, and to **`HttpProvider`** as the capability `Durable` forwards. New, but shaped exactly like existing combinators.
- **`Workflow` interface (`run` + `as_tool`)** — tied to the **`type` primitive** (`as_tool` reflects `Input` to a `Tool.parameters`) and to **`Tool`**. Net-new because the proposal has no notion of a durable graph; it is additive, not a change to the spine.
- **`WorkflowProvider` adapter** — `implements HttpProvider` (the capability that owns `call`/`call_with`) and is tied to the workflow's associated `Input`/`Output` types. Needs two host seams the proposal doesn't have: `baml.llm.tool_args<T>(prompt)` (decode model args) and `baml.cast.checked<T>` (the existential `Output -> T` downcast).
- **`CostMeter` + `MeteredContext`** — tied to **ExecutionContext's emit surface** (proposal §7's flagged-but-undefined event channel). The rollup is the concrete consumer the proposal hand-waved.
- **Value+sidecar boundary: `call_with` + `DurableMeta` (a `ResponseMeta`), NOT a bespoke `StepRecord<T>` companion (RESOLVED-WITH-MECHANISM).** The agent/step boundary's product sidecars — the rolled-up `usage` and the replayed-echo bit — used to ride a bespoke `StepRecord<T> { value, usage, fresh }` wrapper returned from `DurableAgentStep.run`. That is exactly the `Metered<T>`/`Warned<T>`-style parallel companion the value+sidecar model (`../value-sidecar-model.md`, *P1*) retires. The rewrite puts them on `HttpProvider.call_with<T,U>(prompt, project) -> (T, U)` (the capability that owns the value+sidecar method — `../provider-as-marker.md`): `DurableAgentStep.run_with` and `Durable.call_with` return a **tuple**, and the sidecars are a `DurableMeta` — a `ResponseMeta` implementation sourced from the journal, with usage off the recorded payload and `replayed` (a `Replayable` framework dimension, the §3 FrameworkMeta-style delegation) off the engine's live bit. `Durable` now forwards `call_with`, so an inner agent's usage is **not silently dropped** through the combinator — the P1 win. The journal still has to *serialize* the cost, but that is a **private** `Journaled<T> { value, usage }` payload, not the public return shape; the boundary hands back `(T, U)`. Provider dimensions `DurableMeta` cannot reconstruct off the recorded bytes (logprobs/citations/reasoning) report `Unsupported`, not null — "can't" stays typed (`Supported<T>`).
- **Tuples `(T, U)` + destructuring — REQUIRED net-new language surface.** The value+sidecar boundary returns a **tuple**: `DurableAgentStep.run_with` and `Durable.call_with` are `-> (T, U)`, the inner usage capture is `let (value, used): (T, Usage) = …`, and the app destructures `let (rolled_usage, was_replayed) = meta`. This is the same first-class-tuple-types-and-destructuring dependency the streaming folds need (`../value-sidecar-model.md` §6), shared, not bespoke to this scenario. (A named `Output<T,U> { value, extra }` struct is the fallback if tuples are rejected, at an ergonomic cost — and would re-introduce exactly the kind of companion wrapper this rewrite removed.) Closures-as-method-params (`project: (ResponseMeta) -> U`) and the `Supported<T>` std type ride in with it.
- **Journal serialization is the REAL stdlib JSON surface — NOT net-new.** The journal serialization boundary uses `baml.json.to_string<T>` / `baml.json.from_string<T>` (canonical typed encode/decode), which already exist; deterministic encoding is required for replay-stable bytes and the canonical form provides it. It serializes the **private** `Journaled<T> { value, usage }` payload (not a public companion). The earlier draft invented a `json_encode/decode` host seam for this — there is no such gap; it is ordinary stdlib JSON.
- **`baml.errors.WorkflowError` capability error interface — NET-NEW.** The durable engine is a capability beyond call/stream/realtime/tools, so its failures get their own channel. `Workflow.run` and `DurableAgentStep.run` declare `baml.ExtendUnknownError<baml.errors.WorkflowError>`; `WorkflowError`'s classifiers (`is_replay_mismatch` / `is_decode_error`) are the triage a durable engine actually performs — a non-deterministic replay is unrecoverable by retry, unlike a `CallError`'s network blip. Concrete members: `DurableDecodeError` (a journaled value no longer decodes to its recorded schema — implements **both** `WorkflowError` and `CallError`, since the same failure surfaces on `Durable.call_with`'s single-answer decode *and* on a step's `Journaled<T>` decode) and `WorkflowOutputMismatch` (the existential `Output -> T` cast failed). `UnknownToolError` (a new `ToolError`) handles the agent asking for an unserved tool. Per the error model, `baml.errors.Unsupported` is a class implementing the four core interfaces, so the Tools-negotiation `_` arm throws it directly on the `ToolError` channel — no `LlmClient`-style single channel survives. The new `WorkflowError` channel is net-new, so canonical `Unsupported` does not implement it out of the box — but `implements` is a Rust-like trait relation that admits external impls, so the `WorkflowError` author writes one row, `implements baml.errors.WorkflowError for baml.errors.Unsupported`, declared alongside the channel (local trait, foreign type — coherent), and the negotiation `_` arm inside `SupportWorkflow.run` typechecks on the `WorkflowError` channel. That row is the same coverage convention every net-new channel follows; the only residual is that nothing *forces* it, so a forgotten row is a type error at the first `_` arm, not a silent gap. See (c).

## (c) Where it is awkward, leaky, or unresolved

- **Determinism is enforced by host convention, not the type system.** Nothing in the proposal stops a workflow author from calling a model OUTSIDE a `Durable` step (a bare `client().call`), which would re-sample on replay and corrupt the journal. The model has no way to say "every model call inside a `Workflow.run` must be fenced." This is the background §6 "easy to get subtly wrong" hazard, and the proposal cannot make it a compile-time guarantee — it can only offer the combinator and hope it's used. The capability-loss residual is now framed correctly by the marker model (`../provider-as-marker.md`): **OQ1 is resolved** — `Provider` is a bare marker, so `Durable` simply implements the *one* capability it can honestly serve (`HttpProvider`) and does NOT implement `Streaming`/`Realtime` (you cannot replay a live duplex). There is no degenerate `call`/`stream` to fake. The residual is purely **P2** (capability = runtime promise): a durable step over a streaming-capable inner provider silently loses streaming, and the loss is discovered only at the companion's `_` arm — never at compile time. That is the same runtime-promise property every combinator has, not an OQ1 base-`call` problem.

- **The replayed-echo bit now has a home, but it is still a runtime-projected dimension.** `durable_is_live(ctx)` reads the engine's `info.is_replaying` bit to decide whether tokens were really spent. The value+sidecar rewrite gives that bit a *named* home — `DurableMeta.replayed()` via the `Replayable` `ResponseMeta` dimension, projected off `call_with` — instead of a bespoke `StepRecord.fresh` field every consumer must remember to read. But it is still answered at **runtime**: a caller learns "this was a replayed echo, not a fresh charge" only by projecting it and matching `Replayable` in the `project` closure (`match (m) { let r: Replayable => r.replayed(), _ => false }`), never from the static type of the boundary. That is **P2** localized to the replayed dimension — the same per-field-absence-is-a-runtime-promise residual the value+sidecar model owns (`../value-sidecar-model.md` §8.3): `Supported<T>` and the `Replayable` `match` make absence/presence *typed and honest*, but *which* dimensions a boundary carries is still a runtime answer. **Open Question 5** (capability `match` over an existential) is adjacent in two ways: the `Replayable` probe inside `project` *is* an OQ5 wrapper-transparent `match`, and we also rely on runtime reflection to assert `Tools`, so a `Fallback` of agents would claim `Tools` statically but could route to a non-Tools member — a durable step over such a fallback would journal a confusing failure.

- **The two-nondeterminism boundary leaks at the adapter cast.** `WorkflowProvider.call` must `baml.cast.checked<T>(out)` because the agent's tool dispatch unifies the tool result type `T` with the workflow's `Output` existentially — the compiler cannot see through `Workflow.Output` at the dispatch site. So a workflow-as-tool whose `Output` doesn't match what the agent expects fails at runtime, not compile time. This is the same existential-erasure the proposal accepts everywhere `client` returns the opaque `Provider`, now showing up at a graph boundary.

- **Nested durability scoping is asserted, not proven.** `ctx.child(key)` gives a workflow-as-tool its own journal under the parent agent-step's activity. Whether a child workflow correctly resumes when the PARENT step replays (does the engine replay the child too, or treat the parent activity's recorded output as terminal?) is engine-specific (background §6 "whether the inner agent is itself durable"). The proposal has no opinion; we punt to `DurableCtx` semantics. If the parent step is one activity, the child workflow's per-step checkpoints are *invisible* to the outer engine — which is correct for replay but means the inner workflow's partial progress is lost on outer-step retry. That tradeoff is unresolvable in this model; it is a property of where you draw the activity boundary, and the proposal gives no vocabulary to draw it.

- **`emit`/`MeteredContext` is still vapor in the proposal.** §7 only *flags* that `ExecutionContext` needs an event-emit surface. The cost rollup depends on it concretely (every inner turn must emit a `UsageEvent`). If `emit` doesn't exist, there is no portable way to intercept per-turn usage from inside an opaque `run_tools` loop — you'd have to override `run_tools` per provider, defeating the shared default.

- **Across the nesting's channel crossings, keeping errors typed is a coverage convention — supply the `implements` rows or the crossing boxes (recoverably) (NEW).** This scenario stacks four capability channels: the inner agent throws `ToolError` (and its providers' `CallError`s); `DurableAgentStep.run` presents `WorkflowError`; `WorkflowProvider.call` presents `CallError` again (because a workflow-as-tool IS an `HttpProvider.call`); and `Durable.call` re-wraps to `CallError`. Whether a down-stack error stays typed across a boundary is *not* fixed by the model — it is a matter of whether the receiving channel admits that error type. Because `implements` is a Rust-like trait relation with external impls in both directions, the channel author can make upstream errors ride through typed: the `WorkflowError` author writes `implements baml.errors.WorkflowError for baml.errors.Refused` (and for the rate-limit class) alongside its channel, so a down-stack `Refused`/rate-limit crosses into `DurableAgentStep.run`'s channel as its *typed self*, caught concretely with no box and `is_rate_limit()` intact at every layer. The core-channel crossings are already covered: stdlib errors and the well-behaved bespoke errors (`Refused`, `OpenAiRateLimitError`) implement all four common interfaces, so a `CallError` raised in the inner agent flows up `WorkflowProvider.call`'s and `Durable.call`'s `CallError` channels unboxed. Where a row is *missing*, the crossing boxes via `baml.UnknownError.with_message` per rule 3 — but this does **not** destroy the error: `with_message` annotates the existing `UnknownError` *in place* (its third arm), so `.data` always holds the original `OpenAiRateLimitError` untouched, and a single `baml.UnknownError.from<ai.CallError>(e)` at the outer `ResolveTicketSafe` consumer pulls the *same* concrete error back out. When boxing does happen, recovery is **explicit, never transparent (settled)**: a `catch (e) { let c: ai.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on the box — the author must explicitly `baml.UnknownError.from<ai.CallError>(e)` inside the `UnknownError` arm. That residual case is exactly **P2** (capability = runtime promise) applied to the error channel: where a coverage row is absent, precision is recoverable at runtime but not statically advertised, and reachable only by code that already knows to probe for it. So the honest residuals are two and small: (a) the coverage is unenforced — nothing *forces* the channel author to write the row, so a forgotten row is a silent box (data intact, recover via `from<T>`); and (b) a *genuinely foreign* value (a host panic in the engine, an unmapped JSON failure) has no inner typed error to admit, so the `baml.UnknownError` escape hatch is doing exactly its job there. Neither is a structural wall: the typed-provenance is expressible across the entire nesting the moment the channel authors add their rows.

- **`DurableDecodeError` implementing two interfaces is convenient but hides WHERE it failed (NEW).** Because the same decode failure can arise on `Durable.call` (a `CallError` site) and on `DurableAgentStep.run` (a `WorkflowError` site), `DurableDecodeError` implements both. But that means a consumer catching `baml.errors.CallError` and a consumer catching `baml.errors.WorkflowError` can BOTH match the same instance, and neither can tell from the type alone whether the corrupt journal entry was a single answer or a whole agent step — only `step_id` distinguishes them, and that is a field, not a type. The multi-interface error is the model's way of saying "this failure is meaningful on several channels," but it quietly gives up the ability to use the *channel* as evidence of *which* operation broke. For a replay-corruption bug — where you most want to know exactly which activity's bytes drifted — that is the wrong thing to blur.

- **`Unsupported` on the `WorkflowError` channel is one external `implements` row away — but is semantically odd here once legal.** The Tools-negotiation `_` arm throws `baml.errors.Unsupported` on a `WorkflowError` channel. The canonical `baml.errors.Unsupported` implements only the FOUR CORE capability interfaces (Call/Stream/Tool/Realtime); it predates this scenario's net-new `WorkflowError` channel and does **not** implement it out of the box. Because `implements` is a Rust-like trait relation with external impls, this is not a wall: the `WorkflowError` author writes `implements baml.errors.WorkflowError for baml.errors.Unsupported` (local trait, foreign type — coherent) declared alongside the channel in `implement.baml`, and the throw typechecks. This is the same one-row coverage convention every net-new channel follows — *not* a "reach back and widen a core class" tax, and *not* a re-opened gap per capability: the row lives next to the new channel, the author who owns the channel writes it, and a forgotten row is a type error at the first `_` arm (rule 2 rejects the throw), never a silent gap. (A blanket `implements <Cap>Error for baml.errors.Unsupported` per new channel is the standing recommendation.) Where the genuine tension lies is *semantic*, not structural: even once legal, a "the provider can't do Tools" failure surfacing as a *workflow* error conflates a static-capability-negotiation miss with a durable-engine fault. A consumer triaging `WorkflowError.is_replay_mismatch()` will see `false` for an `Unsupported` (classifiers all false) and may wrongly conclude the engine is healthy. The universal-Unsupported design buys "legal on any channel" at the cost of channel-as-meaning: on the `WorkflowError` channel, `Unsupported` is a category error wearing the right type.

## (d) Verdict: **Workable-with-additions**

Direction B (workflow-as-tool) is genuinely clean and is the proposal's model paying off: a workflow is a function, a request/response function `implements HttpProvider` (hence IS a `Provider` marker — `../provider-as-marker.md`), and a provider is a tool. Direction A (agent-as-step) is expressible but only by adding a real host primitive — the durable engine (`DurableCtx`/`durable_activity`) — that the proposal does not contain and arguably should not, since it is the province of Temporal/DBOS, not the LLM client layer. The model absorbs the boundary by making the whole agent loop one `.call` and wrapping it in a combinator, which is elegant; but determinism-on-replay, fresh-vs-replayed cost attribution, and nested-journal scoping are all enforced by host convention and runtime checks, never by the type system. The proposal cannot give a compile-time guarantee that a workflow's model calls are all fenced, nor that an agent-as-tool's `Output` matches — both are the same existential-erasure tax `client`-as-sugar accepts elsewhere. Net: the spine holds and composes in both directions, but a production durable-nesting story requires net-new combinators, a net-new engine seam (now with its own `baml.errors.WorkflowError` channel), and the still-unspecified `emit` surface to be made real. The per-capability error model is the right call — durable failures genuinely need different classifiers than call failures — and it does *not* impose a structural boxing wall on the nesting. A concrete provider error raised deep in an inner agent loop stays typed across the four channel crossings when the receiving channel admits its type, which `implements` (a Rust-like trait relation with external impls in both directions) lets the channel author arrange: stdlib and well-behaved bespoke errors already implement the four common interfaces, so core-channel crossings stay typed for free, and a net-new channel like `WorkflowError` admits an upstream `Refused`/rate-limit by writing one `implements WorkflowError for <UpstreamErr>` row alongside itself. So keeping cross-capability provenance typed is a *coverage convention*, not a wall. The honest residuals are two and small: (1) the coverage is unenforced — nothing forces the channel author to write the row, so a forgotten row boxes the crossing into `baml.UnknownError` (the data survives untouched in `.data`, recoverable by an explicit `from<InnerErr>(e)` probe at the outer consumer; recovery is settled as explicit, never transparent, since `catch` is a runtime is-a test on the box, which is a `baml.UnknownError` and never matches a `let c: CallError =>` arm); and (2) a genuinely foreign value (a host panic in the durable engine, an unmapped JSON failure) has no inner typed error, so the `baml.UnknownError` escape hatch is doing exactly its job. The standing recommendation is conventional, not a shape change: ship every error implementing the common capability-error interfaces, and add a blanket `implements <Cap>Error for baml.errors.Unsupported` (and for the upstream errors you forward) with each new channel. The remaining error-model frictions in this scenario are independent of boxing: the classifier-vocabulary mismatch (`is_replay_mismatch` is meaningless on a `CallError`, `is_network_error` meaningless on a `WorkflowError`), the multi-interface `DurableDecodeError` blurring *which* operation broke, and `Unsupported`-as-`WorkflowError` being a category error wearing the right type.
