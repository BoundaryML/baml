# Evaluation — Enriched outputs: logprobs, citations, grounding

Adversarial read of whether the proposed model expresses enriched, provider-bound output without lying. The defining stress here is **binary, provider-bound capability with no honest fallback**, and **no shared type** across the three "sourced answer" mechanisms.

## (a) What the proposal reuses unchanged

- **Capabilities as `interface … requires Provider`.** `Scored`, `Citable`, `Grounded`, `Annotated` are exactly the `Streaming`/`Realtime` shape from §1. Nothing new in the mechanism — a provider implements the ones it can, omits the rest. `Anthropic` simply has no `implements Scored` block; `OpenAI` has no `implements Citable`. The type *is* the capability set, verbatim from idea (2).
- **Capability negotiation = runtime `match`** (§5). Every companion (`.logprobs`, `.cited`, `.grounded`, `.annotated`) is a `match (p)` against its interface with a `_` arm. The proposal's "delivery refinement vs different interaction shape" split maps cleanly: these are all **no-honest-fallback** capabilities, so every `_` arm *errors* (like `Realtime`, unlike `Streaming`).
- **`client` is config-only sugar** (§3). The enriched knobs (`top_logprobs`, `citations.enabled`, the search/grounding tool) are NOT client fields and NOT provider fields — they are private to the capability method body (`openai_add_logprobs`, `anthropic_enable_citations`). The client stays `OpenAI { model, api_key }`. This is the rule from §4 working as intended.
- **`parse<T>` generic + provider-private wire code** (§2). The four structured encodings (response_format / responseSchema / forced-tool / SAP-text) live inside each `build_request`, and the enriched readers (`*_read_logprobs`, `*_read_citations`) sit beside them. One interface, divergent bodies.
- **`Fallback` forwards a capability by runtime delegation** (§6). `Fallback`'s `implements Scored` re-uses the for-in/`match`/`continue` loop and errors when no member is `Scored` — structurally identical to the proposal's `Realtime` arm.

## (b) Net-new surface it must add (each tied to a primitive)

- **Four capability interfaces** — `Scored`, `Citable`, `Grounded`, `Annotated` (primitive: `interface … requires Provider`). These are new std-lib interfaces, but they cost nothing beyond declaration; they ride the existing capability machinery.
- **Paired result types** — `Scored$Result<T>`, `Citable$Result<T>`, `Grounded$Result<T>`, `Annotated$Result<T>` (primitive: generic `class`). Needed because each capability returns *value + sidecar* in one call; the base `call<T> -> T` has nowhere to put the sidecar. This is the real shape cost: an enriched call cannot be `call<T>`, it needs its own return type.
- **Wire value types** — `Logprobs`/`TokenLogprob`/`TopAlternative`, `DocCitation`/`CitedBlock`, `GroundingChunk`/`GroundingSupport`/`GroundingMetadata`, `Annotation` (primitive: plain `class`). Deliberately NOT unified — four provider-shaped records, no `Citation` supertype.
- **`baml.errors.Unsupported`** as the no-fallback sentinel (primitive: the `throws` channel). Already used by the proposal's `.live` arm; reused here.
- **Host boundaries** — `openai_add_logprobs`, `gemini_read_grounding`, `anthropic_read_citations`, etc. (primitive: `$rust_io_function`). Genuine transport/codec boundaries, exactly like `PrimitiveClient` today.

## (c) Where it is awkward, leaky, or unresolved

- **OQ#1 ("does every capability `requires Provider`?") bites hardest here.** `requires Provider` forces every enriched capability to also be a single-turn `call`. That is fine — but it also implies the *richer* method should be reachable. It is not: `Scored.logprobs<T>` is a SEPARATE method from `call<T>`, so the enriched value and the plain value are produced by different calls with no shared default. There is no "call, and also give me scores if you can" primitive; you must commit to `.logprobs` up front and eat an `Unsupported` throw if the provider can't. The base `call<T> -> T` genuinely cannot carry a sidecar, so enrichment is bolted on beside it, not folded into it.

- **OQ#5 (runtime membership over an existential) is the leak the app feels.** `client GptScored()` returns the existential `Provider`, so "can this client give me logprobs?" is answered by a runtime `match`, never the type checker. Swap `GptScored()` for `Claude()` in `Classify` and nothing fails to compile — `ConfidentClassify` throws `Unsupported` only when called. For a feature whose whole premise is "Anthropic has no path," compile-time refusal would be the honest contract, and the sugar cannot give it. The proposal's escape hatch (drop `client`, write `function … -> OpenAI`) recovers it, but then you lose provider-swap and combinators — the very portability this set is meant to show. This is the sharpest tension in the scenario: **binary provider-bound capability wants a static guarantee, and the existential return denies it.**

- **No shared citation type is a NON-leak — and the model is honest about it.** The proposal does not force a `Citation` supertype, so `Citable`/`Grounded`/ `Annotated` stay three separate companions returning three types. That is correct (the background says these are different objects), but it means there is **no portable `.sourced()` companion**: an app that wants "sourced regardless of provider" writes `SourcedAnimal`-style normalization itself (`SourcedAnswer` in usage.baml, matching each capability in turn). The std lib declines to lie; the cost lands on the app, visibly. Acceptable, but worth stating plainly: the model does not *help* you unify what providers refuse to unify.

- **`Scored` looks portable but isn't semantically.** OpenAI and Gemini both `implements Scored`, yet OpenAI leaves `avg` null while Gemini fills it, and the token boundaries are tokenizer-bound per model. The interface types make them look interchangeable; they are not. The model expresses the *shape* portability and silently passes through the *semantic* divergence — a real footgun the type system does not catch.

- **`Fallback`'s `Scored` claim is a static lie that always could fail.** §6 already accepts this: `Resilient()` statically claims `Scored`, then throws at call time if every member (e.g. an all-Anthropic fallback) lacks logprobs. For delivery refinements that degrade, the lie is cheap; for a no-fallback capability it means the combinator can never *guarantee* the capability it advertises. Consistent with the proposal, but the consequence is starker here.

## (d) Verdict: **Workable-with-additions**

The capability-interface machinery absorbs enriched outputs with almost no new mechanism: four interfaces, their result types, and four record shapes, all on existing primitives. The honest modeling of Anthropic's missing logprobs (omit the `implements` block; companion errors with no fallback) is exactly what the proposal's "different interaction shape" arm prescribes, and the refusal to invent a shared citation type is the right call. The "additions" are real but small — the paired `*$Result<T>` types exist only because `call<T> -> T` cannot carry a sidecar, which is a structural limit, not a bug. The genuine unresolved weakness is OQ#5: a capability that is *binary and provider-bound* is precisely the case where you want a compile-time guarantee, and the existential `client` return can only offer a runtime `match` + `Unsupported` throw. The proposal names the escape hatch (longhand concrete return type) but at the cost of the portability the rest of the model sells. Workable, and honest about its seams — not Clean, because the one thing this scenario most wants (static "this client can score") is the one thing the sugar structurally cannot express.
