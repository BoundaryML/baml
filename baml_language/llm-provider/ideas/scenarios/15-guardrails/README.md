# Scenario 15 — Guardrails (input/output tripwires)

Input/output guardrails are modeled as a `Guarded` **combinator** that wraps any `Provider`: output guards run sequentially after `.call`, input guards run *concurrently* with the agent and cancel it on a trip, and a tripwire is just a typed `throw` (`InputTripwire` / `OutputTripwire`) the app catches by type. The guardrail is itself a `Provider` (a `ModelGuard` whose `.call` delegates to a judge model), so detectors retry/fallback/cache like any other provider, and `.guarded([...], [...])` attaches the same reusable checks to divergent inner providers (an Anthropic chat model and a `ClaudeCode` subprocess harness) with identical call sites — replacing copy-pasted per-agent wrappers. The hard edges: concurrent input guarding needs a net-new `race_cancel` host primitive, and the stop/resume asymmetry means an output-guard rejection can only throw-and-restart, not resume the finished loop.
