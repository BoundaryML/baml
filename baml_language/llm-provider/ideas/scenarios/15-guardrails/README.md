# Scenario 15 — Guardrails (input/output tripwires)

Input/output guardrails are modeled as a `Guarded` **combinator** that wraps any `Provider` (the marker) and `implements HttpProvider` to forward the inner request/response surface: output guards run sequentially after `.call`, input guards run *concurrently* with the agent and cancel it on a trip, and a tripwire is just a typed `throw` (`InputTripwire` / `OutputTripwire`) the app catches by type. A model guard is itself a provider that `implements HttpProvider` (a `ModelGuard` whose `call`/`call_with` delegate to a judge model), so detectors retry/fallback/cache like any other provider; a deterministic `CodeGuard` `implements Guardrail` only — it is a `Provider` (marker) without any request/response `call` to fake (the old Open Question 1, now resolved). `.guarded([...], [...])` attaches the same reusable checks to divergent inner providers (an Anthropic chat model and a `ClaudeCode` subprocess harness) with identical call sites — replacing copy-pasted per-agent wrappers. Concurrent input guarding is plain BEP-034 structured concurrency (`spawn` the agent + each guard, `baml.future.race` them, and a `baml.spawn.CancelToken` so a tripping guard cancels the inner call) — a shipped language feature, not a net-new host primitive. The one real hard edge: the stop/resume asymmetry means an output-guard rejection can only throw-and-restart, not resume the finished loop.
