# Evaluation — Guardrails (input/output tripwires)

Adversarial read of whether the proposed Provider model expresses content guardrails cleanly. Background: `background/02-tools-and-agents.md → ## 6. ◆ Guardrails`.

## (a) What the proposal reuses unchanged

- **The combinator pattern, verbatim.** `Guarded { inner: Provider, ... }` is the exact `Fallback`/`Retry`/`Cache` shape from §6 of the proposal: a plain non-generic class that wraps a `Provider`, forwards `Provider.call`, and forwards capabilities (`Tools`) by runtime delegation. Nothing new about the wrapping mechanism — guardrails *are* a combinator, which is the cleanest part of the fit.
- **"The guardrail is itself a model" falls out for free.** Because the base is `Provider`, `ModelGuard` is just another provider whose `.call` delegates to a judge. The detector composes with the rest of the toolbox with zero new surface: `judge: Anthropic{...}.with_retry(2)` retries the guardrail's own model call, and a guardrail could be `.fallback_to`'d to a cheaper model. This directly answers the background's "the guardrail is another model — with its own failure modes, costs": those failure modes are handled by the *same* combinators as any provider.
- **Typed tripwire = typed throw.** The proposal's `throws Error` channel plus interface-membership `catch` gives the SDK's two-distinct-exception-classes story (`InputTripwire` vs `OutputTripwire`) with no new machinery — the app `catch`es by type, exactly like `InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered`.
- **Reuse over copy-paste.** The background's headline pain ("ten agents that need the same checks means ten wrappers") is dissolved by `.guarded([...], [...])` being a default method on `Provider`: define `PiiGuard()`/`ToxicityGuard()` once, attach to any provider. `usage.baml` attaches the identical guard set to an Anthropic chat model and a `ClaudeCode` subprocess harness with byte-identical call sites — the combinator never sees the inner provider's transport, so it is genuinely portable.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Guardrail` capability interface** (`requires Provider`, adds `name` + `inspect<V>`). Tied to: the capability-interface primitive. Clean — this is precisely the intended extension point. `inspect<V>` is generic over the inspected value (string input vs typed output `T`), reusing the `parse<T>`-style generic threading.
- **`baml.sys.race_cancel<T>(agent, guards, value)` host primitive.** Tied to: a *missing* host primitive. The concurrent-input-guardrail requirement ("run the input guardrail concurrently with the agent and cancel the agent if the guardrail trips") needs task-spawn + cooperative cancellation, which BAML has **no** native surface for. Today's combinators (`Fallback`, `Retry`) are strictly sequential; this is the first combinator that needs concurrency. It is declared as `$rust_io_function` and is the single biggest net-new cost of this scenario. The `agent: () -> T` thunk also assumes first-class thunks/closures survive to the host boundary — itself unproven.
- **Tagged-union outcome types** (`AgentValue<T> | InputTrip`). Tied to: union returns + `match`. Reused machinery, but only exists to thread `race_cancel`'s "who won" out of the host.
- **`GuardVerdict` / `GuardDecision` / tripwire classes.** Plain data classes — trivial, no new primitive.
- **`.guarded(...)` default method on `Provider`.** Tied to: the default-method primitive (the `with_retry` shape). Clean, but note it must be merged into the canonical `Provider` interface to be inherited everywhere — std-lib churn, not app churn.

## (c) Where it is awkward, leaky, or unresolved

- **Stop/resume asymmetry is genuinely UNSUPPORTED (background "compose poorly").** The background's sharpest pain: a `stopWhen` predicate finalizes the result *inside* the loop; an output guardrail runs *after*. If the output guard rejects, there is "no clean way to tell the already-finished loop to try again." Our `Guarded.Tools` impl runs the output guard at the terminal-value branch of `step` — but on a trip it can only **throw**. It cannot say "continue the loop with corrective feedback," because the `Tools` seam (`step -> T | ToolCalls`, `submit(results)`) has no "the value was rejected, re-open the turn" move. The provider-owned opaque `Transcript` is exactly what blocks us: we can't synthesize a follow-up assistant turn without reaching inside it. So output-guard-then-retry is expressible only as throw-and-restart-from-scratch, losing all loop state. This is the asymmetry the background names, and the proposal does not close it.

- **Open Question 1 (does every capability `requires Provider`?) bites here.** `Guardrail requires Provider` forces `CodeGuard` (a regex check) to implement `Provider.call` — which has no meaningful generative behavior, so it `throw`s. We pay a fake method to get a deterministic checker into the same list as a model guard. The alternative (a `Guardrail` that does NOT require `Provider`) would make `ModelGuard` unable to reuse retry/cache on its judge without re-wrapping. The proposal's "best- effort single turn or stand-alone?" question has no good answer for guardrails: model guards *want* `requires Provider`; code guards are punished by it.

- **`race_cancel` cancellation is host-authoritative, not BAML-authoritative.** "Cancel the agent" means cancelling an in-flight HTTP request or killing a subprocess turn. The proposal's model has no notion of cancellation tokens; the agent thunk can't observe "you've been cancelled" to clean up. For the `ClaudeCode` harness, cancelling a subprocess mid-tool-call has real side effects (a half-written file) the BAML layer can't reason about. We can *start* the race in BAML but the semantics of cancel live entirely below the `$rust_io_function` line — server/host-authoritative state the model cannot express. This is the same class of gap as Open Question 7 (host-backed bodies as the bridge boundary): fine for "do IO", silent about "cancel IO."

- **Open Question 5 (capability `match` over an existential) is load-bearing twice.** `Guarded.Tools` must `match (self.inner) { let t: Tools => ... }` and re-thread the opaque transcript. If runtime interface-membership testing does NOT survive (OQ5 is unconfirmed), the whole "forward Tools through a wrapper" pattern collapses and guardrails can only wrap plain `.call`, never an agentic loop.

- **Input guard inspects "user text" via a host helper.** `prompt_user_text(prompt)` digs the user-authored span out of an opaque `PromptAst`. The proposal keeps `PromptAst` opaque on purpose; a guardrail that wants to inspect *only the user turn* (not system scaffolding) must reach through a host accessor. Minor, but it leaks the fact that "what the guardrail should inspect" is under-specified at the BAML layer.

## (d) Verdict: **Workable-with-additions**

The wrapping story is clean and the reuse win is real: guardrails-as-combinators and guardrail-as-a-Provider are exactly what the model is good at, and `.guarded([...],[...])` genuinely deletes the ten-copy-pasted-wrappers pain. Sequential output guards and typed tripwires need nothing new. But two additions are non-trivial and one gap is unclosed: the concurrent-input-guardrail demands a brand-new `race_cancel` host primitive with cooperative cancellation that the model has no vocabulary for (cancellation is purely host-authoritative), and the stop/resume asymmetry the background calls out is genuinely **unsupported** — an output-guard rejection can only throw-and-restart, never resume the finished loop, because the provider-owned opaque `Transcript` gives the wrapper no re-open move. Guardrails ship, but the "concurrent + resumable" refinements sit on host primitives outside the proposal's expressive core.
