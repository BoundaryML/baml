# Evaluation — Guardrails (input/output tripwires)

Adversarial read of whether the proposed Provider model expresses content guardrails cleanly. Background: `background/02-tools-and-agents.md → ## 6. ◆ Guardrails`.

## (a) What the proposal reuses unchanged

- **The combinator pattern, verbatim.** `Guarded { inner: Provider, ... }` is the exact `Fallback`/`Retry`/`Cache` shape from §6 of the proposal: a plain non-generic class that wraps a `Provider` (the marker), `implements HttpProvider` to forward `call`/`call_with` to the inner request/response provider, and forwards capabilities (`Tools`) by runtime delegation. `Guarded.call_with` threads the caller's `project` straight through to the inner's `call_with`, so the inner agent/detector's usage/cost sidecar is **not dropped** by the guard wrapper. Nothing new about the wrapping mechanism — guardrails *are* a combinator, which is the cleanest part of the fit.
- **"The guardrail is itself a model" falls out for free.** Because `Provider` is the composable marker, `ModelGuard` is just another provider: it `requires Provider` (via `Guardrail`) and `implements HttpProvider` to forward `call`/`call_with` to its judge. The detector composes with the rest of the toolbox with zero new surface: `judge: Anthropic{...}.with_retry(2)` retries the guardrail's own model call, and a guardrail could be `.fallback_to`'d to a cheaper model. This directly answers the background's "the guardrail is another model — with its own failure modes, costs": those failure modes are handled by the *same* combinators as any provider.
- **Typed tripwire = typed throw.** The per-capability `baml.ExtendUnknownError<CapErr>` channel plus runtime-match `catch` gives the SDK's two-distinct-exception-classes story (`InputTripwire` vs `OutputTripwire`) with no new machinery — the app `catch`es by type, exactly like `InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered`. A tripwire is a deliberate guardrail DOMAIN failure, so each tripwire class `implements baml.errors.CallError` (it surfaces on `Guarded.call`) *and* `baml.errors.ToolError` (it surfaces mid tool-loop in `Guarded.step`); like the canonical `Refused`, all its classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) return false, so a triage handler that only inspects classifiers correctly treats it as a non-transport, non-parse decline.
- **Reuse over copy-paste.** The background's headline pain ("ten agents that need the same checks means ten wrappers") is dissolved by `.guarded([...], [...])` being a default method on `Provider`: define `PiiGuard()`/`ToxicityGuard()` once, attach to any provider. `usage.baml` attaches the identical guard set to an Anthropic chat model and a `ClaudeCode` subprocess harness with byte-identical call sites — the combinator never sees the inner provider's transport, so it is genuinely portable.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Guardrail` capability interface** (`requires Provider`, adds `name` + `inspect<V>`). Tied to: the capability-interface primitive. Clean — this is precisely the intended extension point. `inspect<V>` is generic over the inspected value (string input vs typed output `T`), reusing the `parse<T>`-style generic threading.
- **The concurrent input phase is NOT net-new — it is shipped structured concurrency (BEP-034).** The requirement ("run the input guardrail concurrently with the agent and cancel the agent if the guardrail trips") is expressed entirely in shipped language features: `spawn { ... }` starts the agent and each guard concurrently (each yielding a `baml.future.Future`), a `baml.spawn.CancelToken` linked via `spawn with baml.spawn.options(cancel = ...)` lets a tripping guard cancel the in-flight agent call (its next `await` throws `baml.panics.Cancelled`), and `baml.future.race` settles on the first task to finish and cancels the losers. There is no `$rust_io_function` host primitive and no missing surface. Earlier combinators (`Fallback`, `Retry`) happen to be sequential, but concurrency was never the obstacle — fan-out is just a list of `spawn`s and the join is a `baml.future.*` combinator. The closures handed to `spawn` are ordinary BAML closures evaluated by the runtime, not values smuggled across a host boundary.
- **`GuardVerdict` / `GuardDecision` / tripwire classes.** Plain data classes — trivial, no new primitive. (The old `AgentValue<T>` / `InputTrip` tagged-union outcome types are gone: with real `spawn`/`race`, the agent's `(T, U)` is just the future's value and a guard trip is a typed `throw InputTripwire` re-thrown by `await`.)
- **`.guarded(...)` default method on `Provider`.** Tied to: the default-method primitive (the `with_retry` shape). Clean, but note it must be merged into the canonical `Provider` interface to be inherited everywhere — std-lib churn, not app churn.

## (c) Where it is awkward, leaky, or unresolved

- **Stop/resume asymmetry is genuinely UNSUPPORTED (background "compose poorly").** The background's sharpest pain: a `stopWhen` predicate finalizes the result *inside* the loop; an output guardrail runs *after*. If the output guard rejects, there is "no clean way to tell the already-finished loop to try again." Our `Guarded.Tools` impl runs the output guard at the terminal-value branch of `step` — but on a trip it can only **throw**. It cannot say "continue the loop with corrective feedback," because the `Tools` seam (`step -> T | ToolCalls`, `submit(results)`) has no "the value was rejected, re-open the turn" move. The provider-owned opaque `Transcript` is exactly what blocks us: we can't synthesize a follow-up assistant turn without reaching inside it. So output-guard-then-retry is expressible only as throw-and-restart-from-scratch, losing all loop state. This is the asymmetry the background names, and the proposal does not close it.

- **Open Question 1 is RESOLVED here by the marker model.** Under the old "`Provider` *is* the thing that can `call`" framing, `Guardrail requires Provider` forced `CodeGuard` (a regex check) to implement a degenerate `Provider.call` that just `throw`s `NotGenerativeError` — a fake method paid to get a deterministic checker into the same list as a model guard. The marker revision (`../provider-as-marker.md`) dissolves this: `Provider` is a bare marker with **no** `call`, and `call`/`call_with` live on `HttpProvider`. So `CodeGuard` now `implements Guardrail` **only** — it is still a `Provider` (because `Guardrail requires Provider` the marker), composes in the same guard list, and carries **no** fabricated `call`. The whole `NotGenerativeError` class is gone. Meanwhile `ModelGuard` *does* want request/response, so it `implements HttpProvider` and forwards `call`/`call_with` to its judge. Both cases are now honest: a code guard simply does not claim the request/response surface, and the type system reflects that rather than forcing a throwing stub. The old "best-effort single turn or stand-alone?" tension does not arise — capability is per-shape, and a deterministic checker just doesn't have the request/response shape.

- **Cancellation IS BAML-authoritative now — the remaining gap is cooperative-cancel cleanup, not vocabulary.** "Cancel the agent" is a first-class operation: `baml.spawn.CancelToken` (and `Future.cancel()`) fire a cooperative one-shot cancel, and the agent's next `await` throws `baml.panics.Cancelled` — so the BAML layer *can* express and observe cancellation directly (a guard fires the token; the agent can `catch (baml.panics.Cancelled) { ... }` to clean up). The honest residual gap is the same one any cooperative-cancel system has: cancellation is *cooperative*, so the in-flight effect only stops at the next `await` point. For the `ClaudeCode` harness, a subprocess mid-tool-call may already have a half-written file when the cancel lands — that side effect is real and below the `$rust_io_function` transport line. But that is a property of the I/O, not a missing concurrency surface: the start, the race, the cancel signal, and the `Cancelled`-throw are all expressible in BAML (BEP-034). What the model still cannot fully reason about is the *external* state a cancelled subprocess leaves behind — a narrower, IO-cleanup concern, not "BAML has no cancellation."

- **Open Question 5 (capability `match` over an existential) is load-bearing twice.** `Guarded.Tools` must `match (self.inner) { let t: Tools => ... }` and re-thread the opaque transcript. If runtime interface-membership testing does NOT survive (OQ5 is unconfirmed), the whole "forward Tools through a wrapper" pattern collapses and guardrails can only wrap plain `.call`, never an agentic loop.

- **Input guard inspects "user text" via a host helper.** `prompt_user_text(prompt)` digs the user-authored span out of an opaque `PromptAst`. The proposal keeps `PromptAst` opaque on purpose; a guardrail that wants to inspect *only the user turn* (not system scaffolding) must reach through a host accessor. Minor, but it leaks the fact that "what the guardrail should inspect" is under-specified at the BAML layer.

- **A guard's failure changes channel as it crosses the call→tool seam, and loses its *static* classifier signal (NEW, error-model).** `Guardrail.inspect` is on the call path, so its channel is `baml.errors.CallError` — a `ModelGuard` whose judge is rate-limited throws an `OpenAiRateLimitError`/concrete `CallError` with `is_rate_limit() -> true`. On the plain `Guarded.call` path that error stays a `CallError` and the app's triage still works statically. But `Guarded.step`/`begin` forward the **`Tools`** capability, whose channel is `baml.errors.ToolError`. A `CallError` from a guard is *not* a `ToolError`, so the only channel-correct move is the trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.ToolError>(e, ...) }` we added — which boxes the judge's rate-limit into a `baml.UnknownError`. This does **not** destroy it: `with_message` annotates the box in place, so `UnknownError.data` still holds the original `OpenAiRateLimitError` untouched, and an app that re-asserts `from<baml.errors.CallError>(e)` on the tool-loop channel pulls the *same* concrete error back out, `is_rate_limit()` intact. What is actually lost is the **static** signal: the tool-loop channel is `baml.errors.ToolError | baml.UnknownError`, which does not advertise that a recoverable rate-limit can be sitting in the box, so recovery is by *speculative* `from<CallError>` probing rather than type-directed — the compiler can't tell the author "a guard's rate-limit can reach you here." This is exactly **P2** (capability = runtime promise) applied to the error channel: precision is recoverable at runtime but not statically guaranteed. And recovery is **explicit, never transparent (settled)**: a `catch (e) { let c: baml.errors.CallError => … }` arm is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `CallError`), so that arm never fires on it — a plain `catch` across this seam only ever sees `baml.errors.ToolError` or `baml.UnknownError`. To pull the rate-limit back the author must `baml.UnknownError.from<baml.errors.CallError>(e)` explicitly inside the `UnknownError` arm; the cost is firm, not conditional. The error model makes this legal but un-advertised: the same failure is *statically* richer through `.call` than through `.run_tools` even though its data is recoverable on both, an asymmetry the single-`type Error` model hid (it hid it by being uniformly imprecise). Making the tripwires `implements` BOTH `CallError` and `ToolError` makes the *tripwire* case statically discoverable on the tool channel; a guard's genuine *transport* error still arrives boxed, recoverable but not advertised.

- **The race composes the `CallError` channel cleanly — `await` re-throws, no host escape hatch (NEW, error-model).** Both the agent (`call_with<T, U>` matched for `HttpProvider`) and each guard (`.inspect`) raise on the `CallError` channel, and `InputTripwire` `implements baml.errors.CallError`, so the spawned futures share a homogeneous `Future<(T, U), baml.errors.CallError>` type and `await baml.future.race(...)` re-throws whichever typed error settles first — a guard's `InputTripwire`, or a genuine transport `CallError` from agent or guard — *unboxed*, caught concretely at the call site. There is no `$rust_io_function` whose foreign faults must be normalized: the scheduler is the shipped BEP-034 runtime, and a cancelled future is observable in BAML (`Future.is_cancelled()`, or a `catch (baml.panics.Cancelled)`), not an opaque host outcome. "The agent was cancelled" is a *success* of the guard (the guard's `InputTripwire` wins the race), exactly as intended — the only thing the agent observes on its own future is the cooperative `baml.panics.Cancelled` at its next `await`, which it may catch to clean up. So the concurrent combinator is no more reliant on the escape hatch than the sequential ones.

## (d) Verdict: **Workable-with-additions**

The wrapping story is clean and the reuse win is real: guardrails-as-combinators and guardrail-as-a-Provider are exactly what the model is good at, and `.guarded([...],[...])` genuinely deletes the ten-copy-pasted-wrappers pain. Sequential output guards and typed tripwires need nothing new — and the concurrent-input-guardrail, once thought to need a brand-new host primitive, is just **shipped structured concurrency (BEP-034)**: `spawn` the agent and each guard, `baml.future.race` them, and a `baml.spawn.CancelToken` cancels the inner call when a guard trips. Cancellation is first-class and BAML-authoritative, not a host escape hatch. The one gap that remains genuinely **unsupported** is the stop/resume asymmetry the background calls out — an output-guard rejection can only throw-and-restart, never resume the finished loop, because the provider-owned opaque `Transcript` gives the wrapper no re-open move. Guardrails ship; the only refinement still outside the proposal's expressive core is *resumable* output guarding, and that is a transcript-reopen problem, not a concurrency one.
