# Evaluation — Function / tool calling basics (the `Tools` capability seam)

Adversarial read of whether the proposed model ([`../../01-providers-clients-capabilities.md`](../../01-providers-clients-capabilities.md)) actually absorbs the four-beat tool loop and its provider divergences, or merely relocates them.

## (a) What the proposal reuses unchanged

- **`interface Tools requires Provider`** with `type Transcript`, `begin`/`step`/ `submit`, and the default `run_tools` loop — taken verbatim from §7 / the conventions cheat-sheet. We wrote three real providers against it and did not have to alter the seam.
- **`step<T>(t) -> T | ToolCalls`** as the exact shape of `Iterator.next -> Item | Done`. The `match` in the loop body is the same interface-membership / union-discrimination machinery (BEP-044/057) already shipping. No new control flow.
- **Opaque, provider-owned `type Transcript`.** This is the load-bearing reuse: OpenAI keeps a `messages[]`, Anthropic additionally keeps `pending_ids[]` for positional re-assembly, Gemini keeps an `id_map[]` because the wire has no ids. Three different transcript shapes, one associated type, and the loop sees none of it.
- **`ToolCall { id, name, args }` / `ToolResult { id, output }` with an opaque `id`.** The loop threads `id` through `dispatch` without interpreting it; each provider gives `id` whatever meaning it needs (echo for OpenAI/Anthropic, synthesized name+position key for Gemini).
- **`client` sugar + capability `match`.** `Weather.run_tools(...)` is a companion that `match`es the provider for `Tools` and errors on the `_` arm — identical to the `.live` pattern in §5. No tool-specific negotiation machinery.
- **Combinator-by-delegation.** `ToolFallback` is the §6 `Fallback` pattern, forwarding `Tools` instead of `Streaming`.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`Tool { name, description, parameters: type }`** — there is no `Tool` type today (proposal flags this in §7). Ties to the first-class `type` primitive + `reflect.type_of<T>()`. Without it the app author would hand-write JSON Schema.
2. **`ExecutionContext.dispatch(calls) -> ToolResult[]`** and a **`deps: unknown` slot** — net-new on the existing `ExecutionContext` (`ns_llm/llm.baml:6`, today `{ jinja_string, args, function_name }`). `dispatch` is what makes the default `run_tools` loop runnable; `deps` is the Pydantic-AI `RunContext[Deps]` injection point. Ties to the `ExecutionContext` primitive.
3. **Schema-reflection host functions:** `baml.reflect.type_to_json_schema(type)` **and** `baml.reflect.type_to_gemini_openapi(type)`. Ties to the `type` + `reflect` primitives but is genuinely new host surface — the one-schema / three-dialect problem is solved by *two distinct reflection codecs*, not one. This is the cleanest place the divergence could land, but it IS new code the host must ship and keep correct.
4. **A pile of `baml.llm.*` wire helpers** (`openai_tool_message`, `anthropic_tool_result_block`, `gemini_function_response`, `openai_extract_tool_calls`, …). These are `$rust_io_function` host boundaries. They are not "new language surface" but they ARE new std-lib breadth — the proposal's claim that "threading stays inside the provider" cashes out as *a lot* of per-provider host code. Honest accounting: the model doesn't shrink the work, it relocates it below the seam.

5. **`baml.errors.ToolError` as the tool-loop's capability channel.** Every loop method (`begin`/`step`/`submit`/`run_tools`, plus `ExecutionContext.dispatch`/`invoke_one`) declares `throws baml.ExtendUnknownError<baml.errors.ToolError>`; the HTTP codec methods (`build_request`/`send`/`parse`) on the same providers declare `<baml.errors.CallError>`. There is no longer a single `baml.errors.LlmClient` blanket — the channel is per-*capability*, so the very same `OpenAI` provider speaks `CallError` on its plain-`call` path and `ToolError` on its loop path. The concrete domain failures this scenario raises on purpose become small typed classes: `NoToolProvider` and `ToolCallDenied` (`implements baml.errors.ToolError`) and `AllProvidersFailed` (`implements baml.errors.CallError`). Foreign transport failures (the host `post_chat`/`post_messages`/`post_generate` boundaries, `baml.http.send`, SAP) are NOT typed — each loop method ends in `} catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.ToolError>(e, "<provider> step failed"); }`, exactly mirroring the CallError normalization in the codec. This is net-new versus the old single-error model and is the right shape, but see (c) for where it strains.

## (c) Where it is awkward, leaky, or unresolved

- **OQ #1 — RESOLVED ("no — `Provider` is a bare marker").** Under the marker revision ([`../../provider-as-marker.md`](../../provider-as-marker.md)), `Tools requires Provider` no longer drags a `call` along: `call`/`call_with` live on `HttpProvider`, not on the marker. A chat model that does tools `implements HttpProvider` (so it has `call`) *and* `implements Tools` — two independent capabilities. A provider that *only* makes sense as a loop (a pure tool-router) `implements Tools` and simply does **not** implement `HttpProvider`; it owes no degenerate best-effort `call`. The old "every tool-capable provider must fake a `call`" complaint disappears — `call` is just a capability the basic-call companion `match`es for, present iff the provider is request/response.

- **OQ #5 (capability `match` over an interface-existential) — load-bearing and unresolved.** `Weather.run_tools` and `ToolFallback.begin` both do `match (p) { let tp: Tools => ... }` on the existential `Provider`. This is a *runtime* membership test against a value whose concrete type must survive to runtime. The whole scenario's portability rests on OQ#5 being answered "yes"; the proposal lists it as open. If value-level reflection can't discriminate `Tools` membership, the entire companion mechanism collapses to "always error or always assume."

- **The combinator + opaque-Transcript interaction leaks.** `ToolFallback` cannot expose `Tools.Transcript` as a clean associated type, because a transcript is *owned by the member that produced it* — you can `begin` on GPT but you must not `submit` to Claude. We had to introduce `BoundTranscript { owner: Tools, inner: unknown }` to carry the owner alongside an `unknown`-typed inner transcript. That `inner: unknown` is a hole: the associated `type Transcript` is existentially erased through the combinator. It works, but it's the first place the type system gives up and we lean on `unknown`. Worse, fallback is only honest at `begin`: if GPT succeeds at `begin`/`step` and then fails mid-loop at `submit`, ToolFallback cannot transparently re-route to Claude — the conversation state is non-portable. So "fallback" for `Tools` means "pick a provider up front," not "fail over mid-conversation." The proposal's §6 fallback story silently weakens for stateful capabilities, and nothing in the model flags that.

- **Compile-time capability guarantee is absent (by design, but it bites here).** Because `client` returns the existential `Provider`, "this client can run tools" is a runtime promise. An app that wires `client: Flash()` into a `.run_tools` function only learns at call time whether Gemini-via-this-provider implements `Tools`. The escape hatch (write `function … -> SomeToolProvider` longhand) exists but throws away the `client` ergonomics the scenario is selling. Stated plainly: **the proposal cannot give a compile-time guarantee that a given client supports tool-calling** without dropping the sugar.

- **Argument validation lives nowhere canonical.** The background calls out that the model emits JSON-shaped args that may not match the schema. We put validation inside `ExecutionContext.invoke_one` (SAP-validate against the tool's `type`, return an error `ToolResult` on failure). That's a reasonable home, but the proposal never specifies it — whether a bad-args call errors the loop or feeds an error back to the model is an unlegislated policy decision sitting in net-new host code.

- **`ToolError` vs `CallError` on ONE provider — and the combinator forwards BOTH channels.** This scenario is the first where a single concrete provider straddles two capability error channels: `OpenAI.send` throws on the `CallError` channel, `OpenAI.step` throws on the `ToolError` channel, and there is no relationship between the two interfaces (they are independent, not a hierarchy). That is mostly fine, but it surfaces a real combinator problem the old single-error model hid. `ToolFallback` forwards BOTH capabilities: it `implements HttpProvider` (so `call`/`call_with ... <CallError>`, now that those live on `HttpProvider` not the marker — [`../../provider-as-marker.md`](../../provider-as-marker.md)) AND `implements Tools` (`begin/step/submit ... <ToolError>`). When `ToolFallback.call` swallows a member's failure with `catch (e) { _ => continue; }` and ultimately throws `AllProvidersFailed`, the *original* `CallError`s (a rate-limit, a refusal) are discarded — the consumer can no longer triage `is_rate_limit()`, because the combinator collapsed N typed failures into one untyped "all failed." The error model gives us per-capability channels but no canonical way for a combinator to *aggregate* the typed errors it forwards; `AllProvidersFailed` is a deliberately lossy stand-in. Worse, on the `ToolError` side there is no aggregation at all: `begin` only tries members until one is tool-capable, so a mid-loop `submit` failure on the bound owner propagates raw with no fallback — meaning the SAME `ToolFallback` is lossy-but-resilient on `call` and faithful-but-non-resilient on `step`/`submit`. The two channels behave differently, and nothing in the error model flags that asymmetry.

- **A `Refused` mid-loop has no obvious home.** The canonical `Refused` (conventions) `implements CallError` and `StreamError`. In a tool loop, a model that declines *inside* `step` (Anthropic `stop_reason: "refusal"` between tool turns) is a `ToolError`-channel event — but `Refused` doesn't implement `ToolError`. So either the provider must re-declare `Refused implements baml.errors.ToolError` (a third interface on the same class), or it must box the refusal into an `UnknownError` on the tool channel. Boxing does *not* destroy the refusal — `UnknownError.data` holds the original `Refused` untouched, and the app can pull it back out with `from<Refused>(e)`, classifiers intact. What it loses is the *static* branch: the tool channel is `ToolError | baml.UnknownError`, which does not advertise that a `Refused` can reach the consumer there, so recovery is by speculatively probing `from<Refused>` rather than a type-directed catch arm (the P2-analog — precision recoverable at runtime, not statically guaranteed). And the catch does *not* auto-unwrap (settled): a plain `catch (e) { let r: Refused => … }` arm is a runtime is-a test on `e` itself, and the boxed value *is* a `baml.UnknownError` (which does not implement `Refused`), so that arm never fires on it — the consumer only sees `ToolError` or `UnknownError`, and pulling the refusal back is *always* the explicit `from<Refused>(e)` probe inside the `UnknownError` arm. So the cost is firm: the inner classifier is reachable, but only by code that already knows to probe for it. This scenario doesn't raise a mid-loop refusal today, but the error model's "one concrete class implements whichever interfaces apply" rule means refusal-bearing classes will accrete interface lists (`CallError` + `StreamError` + `ToolError` + `RealtimeError`) as they appear in more capabilities — the classifier set is uniform, but the *interface membership* is not, and there is no shared base to lean on.

- **Gemini's id synthesis is correct but invisible.** The opaque-`id` contract lets us synthesize `name#index` ids below the seam so the loop's id-correlation works even though Gemini has no ids. This is the model working *well*. The leak is only that the synthesis quality (does name+position actually disambiguate two concurrent same-function calls?) is entirely on the provider author, with no language-level help — exactly the case the background flags as ambiguous.

## (d) Verdict: **Workable-with-additions**

The `Tools` seam is the strongest part of the proposal: `begin`/`step`/`submit` over an opaque, provider-owned `Transcript`, with `step -> T | ToolCalls` mirroring `Iterator.next`, genuinely absorbs the four-beat dance and keeps all three divergences (schema dialect, id-vs-name correlation, result threading + ordering) below the seam without the app author seeing them. Portability across OpenAI, Anthropic, and Gemini is real in `usage.baml`: the app code is byte-identical across providers. But it is not *Clean*, for two concrete reasons the model does not resolve: (1) the combinator layer cannot keep the `Transcript` associated type honest — `ToolFallback` falls back to `inner: unknown` and can only choose a provider at `begin`, not fail over mid-conversation, so stateful fallback silently degrades; and (2) tool-capability is a runtime promise (OQ#5 must be answered, and even when it is, there's no compile-time "this client runs tools" without dropping the `client` sugar). Plus the one-schema/three-dialect win is real but paid for in net-new host surface — two reflection codecs and a per-provider pile of wire helpers. The work doesn't disappear; it moves under the seam, which is the right place for it.
