# Evaluation — Fork / branch a conversation

Adversarial read of how the `Provider` + capabilities model in [`../../01-providers-clients-capabilities.md`](../../01-providers-clients-capabilities.md) holds up against branching, the way background §3 actually varies it (copy vs pointer vs emergent-from-ids; tail vs anywhere; bytes-you-own vs server-stored).

## (a) What the proposal reuses unchanged

- **The opaque-associated-`type` move.** `Session.Session` and the `Cursor` payload are exactly `Tools.Transcript`: the wire discipline (a copied prefix array, a DAG node id, a server `previous_response_id`) stays *inside* the provider behind `$rust_type`. The three encodings in `implement.baml` differ wildly and the app never sees it. This is the proposal's central bet and it pays off here unchanged.
- **Capabilities as `requires` interfaces + `match` negotiation.** `Branching requires Session requires Provider` is a clean three-level chain. "Can this conversation fork?" is the `match (p) { let b: Branching => … }` in `Fork`, the same negotiation the proposal uses for `Streaming`/`Realtime` (§5). The "some sessions can't fork" case (OpenAI Agents `Session`, Vercel) is modeled for free: those would implement `Session` but not `Branching`, and land in the `_` arm.
- **`client` as config-only sugar.** `Brancher()`, `Tree()`, `ServerChain()` are zero-logic config blocks; the `store: NodeStore{…}` field for the DAG is "just a bound field, like `model`" (§4). No fork API leaks into the client.
- **Typed-throws as the failure channel (§1 `type Error`).** `CannotForkHere` and `ForkNotOwned` are refinements the call site `catch`es, exactly like the `Fallback` loop reasons about failures in §6.

## (b) Net-new surface it must add (each tied to a primitive)

- **A `Session` capability interface** (`open`/`turn`/`latest`/`head`/ `cursor_at`/`transcript`, `type Session`). Tied to: the capability-interface primitive (§1). Multi-turn sessions are not in `_conventions.md`; branching presupposes them, so this scenario must introduce the base it branches over.
- **A `Branching` capability** (`fork`/`copy_out`) `requires Session`. Tied to: `requires` subtyping (§1). Kept separate precisely so non-forkable sessions type-check.
- **`Cursor` (opaque position)** — `class Cursor { _data: $rust_type }`. Tied to: the same `$rust_type` opaque-payload primitive as `PromptAst`. There is no "position inside a conversation" type today; copy/pointer/id each encode it differently, so it must be opaque.
- **A read-only `Transcript` view with a `complete: bool`.** Tied to: the read-projection pattern (the `History` view in scenario 10). The `complete` flag is net-new *and load-bearing* — it is the only place the model can tell the truth about server-stored bytes.
- **`NodeStore` (a tree/DAG host handle)** with `put_node`/`walk_ancestry`/ `find_ancestor_with_turn`/`gc`. Tied to: host-backed `$rust_type` + methods (Open Question 7). This is genuinely *more* than the proposal's `KV` (§6 `cached(store: KV)`): KV is flat key→value and cannot express parent pointers or ancestry walks. Pointer-based fork forces a richer store primitive than caching ever needed — and that store has to do GC of dead leaves.
- **`ForkNotOwned` / `CannotForkHere` error variants.** Tied to: the `type Error` channel (§1). New failure modes the base `LlmClient` error doesn't name.

## (c) Where it is awkward, leaky, or unresolved

- **Fork-at-tail vs fork-anywhere is a runtime promise, not a type (OQ 5, OQ 1).** `fork(s, at: Cursor?)` is one signature for both. A tail-only provider *still implements `Branching`* — it just throws `CannotForkHere` when handed a non-head cursor. So "this client can branch from any point" is exactly as unprovable as "this client is `Realtime`": it is answered by a runtime `match`/`catch`, never the checker. Worse than the §5 streaming case, because here the capability is *present* and only the *argument* is rejected — the `match` can't even gate it; you must `catch`. The escape hatch ("drop the sugar, return a concrete type") doesn't help: the divergence is a value (the cursor), not a type, so no return type can encode "forks anywhere."

- **Server-authoritative state breaks the read seam — the model is honest but not clean (OQ 4, OQ 3).** `Responses.transcript` returns `{ turns: [], complete: false }` and `copy_out` *throws* `ForkNotOwned`. The proposal's `parse`/`Body` seam (§2, OQ 4) assumes the bytes come back to the client; here the bytes never leave the provider. We surface this with a `complete` flag and a typed throw rather than pretending — which is the right call — but it means **a whole capability (`copy_out`, `transcript`) is a runtime coin-flip across providers implementing the same interface.** Two providers satisfy `Branching`; one can export branches and one cannot, and the type system says they are identical. The proposal genuinely *cannot* express "this branch is yours to own." That is a real expressiveness gap, not a stylistic one.

- **`fork` returning a `Session` value, immutability, and OQ 1.** Sessions are modeled as immutable values (`turn` returns a *new* `Session`). For copy-prefix this is natural; for the DAG it is a lie of convenience — the `PiNode` value is a cheap handle but the *store* it points at is shared, mutable, and needs GC. So "immutable session value" is true at the BAML layer and false at the host layer, and the proposal has no vocabulary for that split. OQ 1 ("does every capability `requires Provider`?") bites here too: `Session.call` is a best-effort single turn that *discards* the session — semantically odd, since the whole point of a `Session` provider is that turns accumulate.

- **Combinators don't compose with stateful sessions (§6).** A `Fallback` is a `Provider` and the sugar happily wraps it, but you cannot fail a *forked Claude session value* over to a *Responses chain* mid-conversation — the opaque state belongs to one member. `usage.baml` has to **pin** to a single member (`PinnedSession`) and deliberately *not* route `Session`/`Branching` through the combinator. The proposal claims (§6) a combinator "forwards all capabilities at once"; for stateful capabilities that claim is false, and nothing in the model stops an app from writing `ResilientChat().session(…)` and getting an un-failoverable session. This is a footgun the type system permits.

- **Retrofitting ancestry, exactly as background §3 warns.** The DAG provider's `turn` and `transcript` both have to `walk_ancestry` — every store op is ancestry-aware, not "the latest array." The proposal doesn't *cause* this, but it doesn't *help* either: there is no shared session-store abstraction, so each branching provider re-implements ancestry walks and GC by hand. The copy-provider and the pointer-provider share zero code below the seam.

## (d) Verdict: **Workable-with-additions**

The opaque-associated-`type` + `requires`-capability + `match`-negotiation machinery absorbs the three branching encodings cleanly at the *app* surface: `DraftWithAlternative` runs unmodified against copy-prefix, pointer-DAG, and emergent-id providers, which is the portability the proposal promises. But it gets there only by adding a real stack of net-new surface — a `Session` base, a `Branching` capability, an opaque `Cursor`, and crucially a tree-shaped `NodeStore` that is strictly richer than the proposal's `KV`. And two stresses expose hard limits rather than rough edges: fork-anywhere-vs-tail is an un-typeable runtime promise (you must `catch`, not just `match`), and server-authoritative branches (Responses) cannot be owned, inspected, or exported — `copy_out` and `transcript` become honest-but-unreliable across providers wearing the same interface. The model can *describe* every provider in background §3 and run portable code over them; it cannot *guarantee* the two properties an app most wants from branching — "I can fork from any point" and "the branch is mine." Those stay runtime promises, which is consistent with the proposal's stated philosophy (capability is a runtime promise, §5) but is a genuine ceiling, not a polish item.
