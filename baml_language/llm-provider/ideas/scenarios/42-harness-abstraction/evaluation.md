# Evaluation — Wrapping harnesses behind one abstraction

Adversarial read of whether the proposed model expresses the AI-SDK-v7 `HarnessAgent` move: ONE agent interface over MANY runtimes (Claude Code / Codex / Pi), whose output flows into the SAME streaming/UI surfaces as a plain model call. The background names three hard things — **lossy normalization** (`rewindFiles`/`steer` with no common method), **session lifecycle across server boundaries** (`detach`/`stop`/`destroy`), and **keeping two abstractions (providers + harnesses) compatible** (a `HarnessAgent` stream indistinguishable from a `streamText` stream). The proposal is *literally* this scenario — §8 says "a harness is a Provider" — so the first hard thing is nearly free and the other two are where it strains.

## (a) What the proposal reuses unchanged

- **"A harness is a `Provider`" is the whole abstraction, verbatim.** §8 already models `ClaudeCode` as `Provider + Realtime`. `HarnessAgent` adds nothing to that claim — it is a `Provider` that *wraps* a `Harness` provider and forwards by runtime delegation, the exact `Fallback` template from §6. So "one agent interface over many runtimes" is "a combinator over many providers," with zero new machinery for the wrapping itself.
- **`client` = `function -> Provider` covers the facade with no special case.** `CodeAgent()` and `PiAgentClient()` are ordinary clients; swapping the runtime is editing one `inner:` field. `Coder(runtime)` does per-tenant runtime selection as a plain `if` — the §3 "clients are functions" rule, reused.
- **Harness output into the same UI surface is the companion `match`, intact.** `SummarizeStream.stream(...)` desugars to the canonical companion: `match (p) { let s: Streaming => s.stream(...), let h: HttpProvider => buffer_as_stream(h, ...), _ => throw Unsupported }`. Because `HarnessAgent implements Streaming`, the heavy Claude Code runtime takes the `Streaming` arm and returns the *same* `baml.llm.Stream<TStream, TFinal>` a chat model emits. The "indistinguishable from `streamText` at the UI" requirement is satisfied by the type, not by new surface — the only cost is one host projector (`project_text_stream`).
- **A harness has no honest `call`, and under the marker `Provider` that is no longer a problem (OQ1 resolved).** `Provider` is now a bare *marker* (`../provider-as-marker.md`): `call`/`call_with` belong to `HttpProvider`, and a harness drives a subprocess, not a request/response codec. So `ClaudeCodeHarness`/`PiHarness`/`HarnessAgent` carry NO `implements Provider { call }` — the earlier degenerate "run the whole subprocess and hope" body is deleted, not faked. They are still `Provider`s because their real capabilities (`Realtime`, `Harness`, `Streaming`) all `requires Provider`. The basic-value function `Summarize(task) -> Patch` is served by the §2 call↔stream *degrade* (no `HttpProvider`, so drain the `Streaming` provider), which is honest: the value is a fully-drained session stream. The old "this harness `call` is dishonest" complaint is gone.
- **Runtime divergence stays *inside* the provider bodies, as §7 prescribes.** Claude's JSONL-keyed-by-cwd vs Pi's session-tree-node lives entirely in each `create_session`/`attach` host body; the `SessionHandle._ref` is opaque to the BAML layer, exactly as `ToolCall.id` is opaque to the tool loop. The abstraction does not have to *understand* the divergence to carry it.
- **`ControlPlane.supported_verbs()` (from 37) is reused as the lossy-normalization honesty layer.** It is how the facade advertises that Claude-in-Container backs `RewindFiles` and Pi doesn't, without growing a method per feature.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Harness requires Realtime` (create/attach/detach/stop/destroy).** Tied to the capability-as-`requires Provider`-interface rule (§1). This is the load- bearing addition. The proposal's `Realtime.run(self, prompt, io) -> Transcript` is a *single in-process duplex call*: `io` exists only within one request, so it has **no vocabulary for parking a session and resuming it in a different request**. `Harness` adds the handle-keyed lifecycle that `Realtime` lacks. Open Question 2 (how the live `io` surfaces) is about *one* call; this scenario needs lifecycle *between* calls, which OQ-2 does not contemplate.
- **`SessionHandle { id, runtime, _ref: $rust_type }`.** Tied to the host-boundary `$rust_type` primitive. The opaque `_ref` is the coordinates to re-find a parked runtime; `runtime` is stamped so a stored handle routes back to the right adapter on resume (the background's "cwd-keyed storage orphans transcripts" problem, made explicit). Net-new type.
- **A net-new capability-error channel: `baml.errors.HarnessError`.** Tied to the error model's "any NEW capability gets a NEW `baml.errors.<Cap>Error` interface, same shape" rule. The `Harness` lifecycle (create/attach/detach/stop/destroy) is a capability beyond call/stream/realtime/tools, so its methods declare `baml.ExtendUnknownError<baml.errors.HarnessError>`, not the `CallError` channel. The interface's classifiers are chosen for what a cross-request session layer actually triages — `is_session_expired()` (the runtime was reclaimed) and `is_runtime_error()` (the sandbox/process leg failed) — rather than the call-path triad (`is_network_error`/`is_rate_limit`/`is_parse_error`), which is the first sign this capability does not fit the existing classifiers.
- **`SessionService` + `HandleStore` + `SessionExpired`.** Tied to the `interface`/`implements` + `throws` channel. The store of *handles* mirrors 17's `SessionStore`. `SessionExpired` is the genuinely new thing, and under the new error model it is now a **concrete class `implements baml.errors.HarnessError`** with `is_session_expired() -> true` — so the app branches on the typed bit instead of string-matching a message. It encodes that the live runtime behind a stored handle is **server-authoritative and may be reclaimed out from under the store**. Because it is a *concrete* HarnessError rather than the old undifferentiated `LlmClient`, a resume can distinguish "handle gone, start fresh" from a transient runtime leg (`HarnessRuntimeError`, `is_runtime_error -> true`) and from a foreign blip normalized into `baml.UnknownError` — three outcomes the single-channel model collapsed into one.
- **`AgentStreaming requires Streaming` + `project_text_stream`.** Tied to `baml.llm.Stream` and the `$rust_io_function` boundary. `Streaming` gives the plain-UI projection; `AgentStreaming.events` exposes the *lossless* InEvent log for rich agent UIs (tool cards, permission asks). The projector is the host function that makes a harness stream type-identical to a chat stream — net-new, but it is the concrete answer to "keep the two abstractions compatible."
- **`HarnessAgent.raw() -> Harness` — the escape hatch.** No new primitive (just a method returning the inner provider), but it is net-new *surface*. It is the proposal's only honest answer to lossy normalization: features with no common method (`rewindFiles`) are reached by dropping through the facade to the concrete runtime and `match`ing down. The §5 capability `match` is the mechanism; `raw()` is the door.
- **`ServerSession` combinator.** Net-new library class, no new primitive — `create`/`attach`/`detach` + `SessionService` glue. It is what turns the lifecycle primitives into the two-handler dance an app actually writes.

## (c) Where it is awkward, leaky, or unresolved

- **OQ-2, exceeded — the channel is per-request but the session is per-user.** OQ-2 asks how the live `io` rides onto the realtime companion *within one call*. This scenario breaks the assumption that there *is* one call: the session outlives the channel. I had to mint a handle (`create_session`) **with no `io` at all**, then hand a *fresh* `io` at each `attach`. So `Realtime.run`'s "the channel is a parameter of the capability method" answer is right but insufficient — the *session* is the durable thing, the *channel* is ephemeral, and the proposal models only the channel. The handle is net-new precisely because OQ-2's framing has no place to put durable session identity.

- **Server-authoritative state is *representable* but not *ownable* — and that is the honest limit.** `HandleStore.get(id)` can return a handle whose runtime was already GC'd; only the subsequent `attach()` discovers `SessionExpired`. The store and the runtime can disagree, and **the runtime is authoritative**. The proposal is a pure declarative/host-boundary model; it has no concept of a durable instance the host reclaims on its own clock. I can *encode* the failure (two `catch` sites in `ServerSession.resume`) but I cannot make the BAML layer *prevent* it — sandbox eviction, TTL, orphan GC all live below `$rust_io_function`. **Stated plainly: durable, server-reclaimed session state is outside the model; the model can only react to it.** This is the §6 durable-instance problem the background flags, and the proposal does not solve it — it relocates it into host bodies and a new error variant.

- **Lossy normalization leaks through `raw()`, and `raw()` is untyped per-runtime.** The escape hatch returns `Harness` — the *intersection* type — so even after `raw()` the app must `match` on `ControlPlane.supported_verbs()` and send a `RewindFiles` *OutEvent over the channel*, because there is no `rewindFiles(...)` method anywhere in the type system. A developer who wants "Claude Code's rewind, statically" has no type to ask for it: the concrete classes (`ClaudeCodeHarness`) expose rewind only as a runtime-honored verb, not a method. The escape hatch is therefore **a runtime negotiation, not a static capability** — `RewindIfPossible` is a function that can throw "this runtime cannot rewind" at runtime, never a compile error. The proposal's existential return (§5) guarantees this: a `client` yields `Provider`, so even the escape hatch can only recover capability by `match`, not by type.

- **`stop()` means different things on different runtimes — a silent semantic downgrade.** Claude Code's `stop` SIGINTs the in-flight turn at a boundary; Pi has **no interrupt verb**, so `PiHarness.stop` can only stop subscribing and let the turn settle server-side. Both satisfy the `Harness.stop(self, h) -> null` signature, so the type system says they are interchangeable — but they are not. This is the background's "lossy normalization" / "support is not binary" tension reappearing at the *lifecycle* layer, and the proposal has no place to record "this method is best-effort on this runtime." `supported_verbs` covers the *control plane* verbs but not the *lifecycle* methods, which are real methods on `Harness`, not OutEvents. A second `supported_lifecycle()` negotiation, or a per-method capability split, would be needed — net-new, unaddressed.

- **Combinators forward `Harness` but cannot honor it across members (OQ unrelated, but a real hole).** `ResilientCoder()` is `Fallback`, which §6 says claims every capability it forwards — so it claims `Harness`. But a `SessionHandle` minted by member A (Claude) is meaningless to member B (Pi): `attach(h, io)` must go to the SAME runtime that created `h`. A `Fallback.attach` that "tries each member in order" would hand a Claude handle to Pi. So `Harness` is the one capability a `Fallback` **must not** transparently forward — the combinator's claim is a lie for session-keyed methods. The usage file flags this ("hold a single HarnessAgent, not a Fallback, for lifecycle"), but the proposal's "a combinator statically claims every capability it forwards" rule (§6) is *wrong* here, and nothing in the type system stops the footgun. The error model **sharpens** this: per rule 4 a `Fallback.attach` would also have to declare `baml.ExtendUnknownError<baml.errors.HarnessError>` — i.e. it statically advertises that it can raise a *session-keyed* error for a runtime it has no business attaching to. The channel makes the combinator's false claim type-check cleanly, so the new error model does nothing to flag the footgun and arguably legitimizes it.

- **The new HarnessError channel surfaces one genuine tension and one that the error model can express cleanly.** (1) The genuine one: `baml.errors.HarnessError` had to invent its *own* classifiers (`is_session_expired`/`is_runtime_error`) because the call-path triad is meaningless for a parked subprocess — confirming that "one interface per capability, same shape" is a *shape* convention, not a *vocabulary* one; every genuinely new capability re-opens the question of what its classifiers even are, and a generic harness consumer that only knows `is_network_error` learns nothing. This is independent of boxing and stands. (2) The `Unsupported` distinction, by contrast, *is* expressible — it is a coverage choice, not a forced flattening. Today both "this client isn't a harness" and "this runtime can't rewind" are thrown as `baml.errors.Unsupported` (legal on the `HarnessError` channel because `Unsupported` implements every common interface), which collapses "wrong capability" and "right capability, missing verb" into one type. But the harness package can keep them distinct: mint a concrete `RewindUnsupported` for the runtime-verb miss and declare, in the harness package, `implements baml.errors.HarnessError for RewindUnsupported` (local trait, local type) — leaving canonical `Unsupported` to mean only "wrong capability." Because `implements` admits external impls, the channel author owns this distinction; the model *does* prescribe the mechanism (an `implements` row), so distinguishing *why* a verb was refused from *whether* the provider is a harness is one concrete subtype away, not a wall. The lossy-normalization escape hatch (`raw()` + `RewindFiles` OutEvent) remains a runtime negotiation rather than a static guarantee — the *type* still cannot promise rewind at compile time — but the *error* it raises is as fine-grained as the harness author cares to make it.

- **`SessionExpired` is a concrete error reached through an *existential* provider — reflection through the facade is lossy at the catch, too.** `HarnessAgent` hides the concrete runtime; `ServerSession.resume` rethrows `SessionExpired` (a concrete `baml.errors.HarnessError`) up through the facade. At the consumer (`HandleContinue`) the catch can still match the concrete `SessionExpired` arm *even though the static channel is `baml.errors.HarnessError | baml.UnknownError`* — exactly the "concrete arms are runtime refinements" promise. That works. What does **not** survive the facade is the runtime *identity*: a `SessionExpired` thrown by Claude and one thrown by Pi are the same type, so the app cannot type-discriminate which runtime's session died — it must read `SessionHandle.runtime` off the handle it stored. The error carries the *fact* of expiry but not the *provenance*, and the existential `Provider` return guarantees that provenance can never be recovered from the error type alone.

- **OQ-7, relied on heavily and confirmed-by-assumption.** Every adapter body (`create_session`/`attach`/`detach`/`events`) is `$rust_io_function` inside an `implements` block — subprocess lifecycle, JSONL replay, session-tree forks. This scenario *is* the stress test for OQ-7 ("is an `implements` block with native bodies the supported bridge boundary?"). If the answer is no — if native bodies can't hold long-lived, parkable child-process state across calls — the entire lifecycle layer is unimplementable. The proposal assumes yes; this scenario bets the whole abstraction on it.

## (d) Verdict: **Workable-with-additions**

The proposal's headline claim for this scenario — "a harness is a Provider, so the facade is just a combinator and its output drops into the same streaming UI" — is *true and clean*. Under the marker `Provider` (`../provider-as-marker.md`) it is also *more* honest than before: a harness no longer fakes a request/response `call` to satisfy a base contract (OQ1 resolved) — it `requires Provider` and exposes only its real `Realtime`/`Harness`/`Streaming` surface. One-shot, plain stream, rich event log, and runtime swap are all expressed with reused machinery (the companion `match` — with the one-shot value now riding the §2 call↔stream *drain* degrade rather than a harness `call`, the §6 delegation template, the `client` sugar) plus one honest host projector. That is the genuinely strong half, and it is exactly the half the background calls the newest, hardest move. But the *session* half — the part the background spends most of its "what's hard" on — needs a net-new `Harness` capability on a net-new `baml.errors.HarnessError` channel, with a durable `SessionHandle`, a `SessionService` whose server-authoritative `SessionExpired` is now a concrete typed HarnessError, and a cross-request driver, none of which the proposal anticipates: `Realtime.run`'s in-process channel models only one request, and OQ-2 does not reach durable session identity. The per-capability error model pays off here — `is_session_expired()` vs `is_runtime_error()` vs `baml.UnknownError` give the resume path three distinguishable outcomes the old single channel collapsed — but it also exposes that a brand-new capability must mint its *own* classifiers (the call-path triad is meaningless for a parked subprocess), so the error model fits this scenario only after the scenario teaches it new classifier vocabulary. (Distinguishing a runtime-verb miss from "wrong capability" is *not* part of that cost: the harness package can declare `implements baml.errors.HarnessError for RewindUnsupported` and keep the two facts as separate typed errors — a coverage row the channel author writes, not a forced overload of `Unsupported`.) Two things are *plainly unsupported* rather than merely net-new: (1) **server-reclaimed durable state** — the model can react to `SessionExpired` but cannot own the runtime's reclaim clock; and (2) a **static handle on lossy-normalized features** — `rewindFiles`/`steer` are runtime verbs negotiated at call time, never types, so "give me a harness that can rewrite history" is unprovable at compile time, and `Fallback` actively lies when it claims to forward session-keyed `Harness` methods. The additions all sit *on* the spine (a new `requires`-interface, an opaque handle type, a store, an error variant) rather than amending it — so it is Workable, not Awkward — but "workable" here means the proposal hands you the Provider abstraction for free and leaves you to build the entire durable-session and lossy-feature-escape layer yourself, with two corners (server-authoritative reclaim, compile-time feature guarantees) it cannot reach at all.
