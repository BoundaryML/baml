# Evaluation — Embedding & deployment of a harness

Adversarial read of whether the proposed Provider/capability model expresses *how a host drives and deploys an agent*. Background: `background/06-harnesses.md → ## 6. ◆ Embedding & deployment`.

## (a) What the proposal reuses unchanged

- **Harness-as-`Provider`.** `ClaudeCode`, `Pi`, and `AgentsRunner` are providers whose `call<T>` flattens a whole agent run into one typed answer. This is §8 of the proposal verbatim — a provider with no `HttpProvider`, transport is a subprocess/generator, not `baml.http`. The `client → function … -> Provider` rewrite covers all three with no special case (`CodeAgent()`, `RpcAgent()`).
- **`Realtime` for the steerable duplex.** The live control/event channel is the `io: Channel` parameter of `Realtime.run`, handed in at `Fix.live(task, io)` — not a client field. Pure canonical reuse; the proposal's §3/§5 channel-pass-in story applies unchanged.
- **Capability negotiation as a runtime `match`.** `DeployedAgent.handle` `match`es its `inner` against `Durable`; `SubprocessSupervisor.run` `match`es against `Realtime`. The companion-falls-back-or-errors rule (§5) is exactly the mechanism for "this Pi instance has no durable identity."
- **Combinators wrap, don't configure.** `SubprocessSupervisor` is a plain non-generic class that wraps a `Provider` and adds respawn-on-crash, chained as `.supervised(3)` — the `with_retry`/`Fallback` pattern (§6) applied to the background's "subprocess lifecycle is hard."
- **SAP at the final seam.** Every harness ends in `baml.sap.parse<T>(final_blob)` (OQ #6's public `baml.sap.parse`).

## (b) Net-new surface it must add (each tied to a primitive)

- **`Drivable` capability + `type Drive` + `HostMsg`/`AgentMsg`** — ties to the proposal's *capability-is-an-interface* primitive and the *associated-`type`* primitive (same shape as `Tools.Transcript`). This is the load-bearing addition: the background's central divergence is the *drive channel* (subprocess+JSONL vs JSON-RPC vs in-process generator), and `Provider.call` alone hides it. `Drive` being provider-owned and opaque is what lets one host vocabulary (`HostMsg`/`AgentMsg`) sit over three framings — the JSONL-vs-RPC divergence lives entirely inside `pump`, exactly where the proposal says per-provider wire threading belongs (§7).
- **`Durable` capability + `Instance` + `lease_acquire`** — ties to the capability primitive *and* to a new host boundary. Durable instance identity ("same `<id>` continues the same agent under single-writer semantics") has no expression in the base model; it is a genuinely new capability interface plus a `$rust_io` lease/persistence seam.
- **`register_provider` / `Registry`** — ties to nothing in the proposal; it is an *anti-`client`* surface. The proposal's whole §3/§4 thesis is "config is a declarative provider field." registerProvider is the opposite: a process-global mutable table read late at `open()` time. We add it as host primitives and show the harness body reading it, but it sits *outside* the provider-field model.
- **`Trigger` + `DeployedAgent`** — ties loosely to "a `client` is a value." We make the deployable unit a class carrying a `Provider` + declarative triggers. Triggers themselves (webhook/cron framing) are pure net-new data the substrate interprets; the proposal has no notion of deployment or scheduling.
- **`Subprocess`/`Generator`/`rpc_call`/`gen_next`** — ties to OQ #7 (`$rust_io_function` bodies inside `implements`). These are the non-HTTP transport bridges the base model explicitly leaves open.

## (c) Where it is awkward, leaky, or unresolved

- **OQ #3 (the request side is HTTP-specific) is the deepest hit here.** The proposal asks whether non-HTTP transports want an associated request type. This scenario answers *yes, emphatically*: a harness has three mutually unlike transports and `build_request -> baml.http.Request` fits none of them. Our `Drivable` with `type Drive` is precisely the "associated type for non-HTTP transports" OQ #3 floats — so the proposal's base model is *insufficient as written* and needs this capability to be real. The base `Provider.call` is honest but lossy: it can only express "drive to completion," which is why every `call` here is a hand-rolled `open`/`pump`/`close` loop duplicated across three providers (a default method on `Drivable` could DRY it, but then `Drivable` is doing the base model's job).

- **OQ #1 (does every capability `requires Provider`?) leaks for `AgentsRunner`.** `Realtime requires Provider` forces a best-effort single turn. `AgentsRunner`'s realtime is *read-only* (events stream out; `io.on` never fires) and its `pump` *throws* on any host input. So `AgentsRunner` claims `Realtime` but silently degrades duplex to simplex — a capability the type system says it has and the runtime only half-delivers. The proposal's "capability is a runtime promise" covers this, but it means a host wiring `io.on(...)` against a `.live` companion gets *no signal* that steering is a no-op. That is a real leak: simplex-vs-duplex is a different interaction shape, not a delivery refinement, yet it rides the same `Realtime` interface.

- **Server-authoritative / durable state is only partially expressible.** We can model `Durable.attach` and a single-writer lease, but the *guarantee* — that concurrent triggers on the same `<id>` serialize correctly — lives entirely in the `$rust_io` substrate (Durable Object / DB row). BAML can declare the capability and throw on lease contention; it cannot *enforce* single-writer semantics in the language. The model surfaces the seam honestly but offers no more safety than a comment. This is a plain "the proposal cannot express it" for the part that actually matters operationally.

- **registerProvider fights the whole design.** §4 says "options dissolve into provider fields." Deployment says "provider config is *runtime* config you mutate at boot, applying to every harness." These are contradictory philosophies and we had to model *both*: a `client CodeAgent()` block AND a `register_provider(...)` call, with the harness `open()` reading the registry late so the imperative path can override the declarative one. The proposal has no opinion on which wins, and the precedence (constructed field vs late registry read) is something we *invented* here. This is unresolved surface, not just awkward.

- **No compile-time capability guarantee for deployment.** Because `client` returns the existential `Provider`, `translator_agent()`'s `inner` is typed `Provider`; whether it is `Durable` is discovered by `match` at request time. A deployment platform genuinely wants to *reject at deploy time* an agent declared with `triggers: [webhook]` whose provider can't persist instances. The proposal's escape hatch (drop the sugar, write `-> ConcreteDurable`) works but forfeits the polymorphism that made `DeployedAgent` reusable across harnesses. You cannot have both "any harness" and "statically durable."

## (d) Verdict: **Workable-with-additions**

The base-`Provider` model carries the *coarse* shape of a harness cleanly: `call` flattens a run, `Realtime` gives the duplex, combinators supervise the subprocess, and the `client` rewrite makes a harness indistinguishable from a chat model at the call site — that portability across ClaudeCode/Pi/AgentsRunner is real and is the proposal's strongest showing here. But the scenario's *actual content* — the three drive channels, durable instance identity, triggers, and runtime provider config — is all net-new surface the base model does not contain, and two of those additions (`Drivable`, registerProvider) sit in unresolved tension with the proposal's own theses (OQ #3 says the request side may need a non-HTTP associated type; §4 says config is a field, yet deployment demands a runtime registry). The model never *blocks* the scenario, but it also does not *give* you the hard parts — durable single-writer state and a compile-time durability guarantee remain outside the language. Workable, provided the proposal adopts `Drivable` (resolving OQ #3 affirmatively) and accepts an out-of-band deployment/trigger/registry layer as explicitly not-the-provider-model.
