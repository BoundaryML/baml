# Evaluation — Embedding & deployment of a harness

Adversarial read of whether the proposed Provider/capability model expresses *how a host drives and deploys an agent*. Background: `background/06-harnesses.md → ## 6. ◆ Embedding & deployment`.

## (a) What the proposal reuses unchanged

- **Harness-as-`Provider` (the bare marker).** `ClaudeCode`, `Pi`, and `AgentsRunner` are providers in the only sense provider-as-marker keeps: *composable*. They carry NO `HttpProvider.call` — a harness is not request/response — and the old "flatten the run into a `call<T>`" was exactly the degenerate base method the marker revision retires. Each is a `Provider` because every capability it implements (`Drivable`, `Realtime`, `Durable`) `requires Provider`; the marker is implicit, no `implements Provider` block to fake. Transport is a subprocess/generator, not `baml.http`. The `client → function … -> Provider` rewrite covers all three with no special case (`CodeAgent()`, `RpcAgent()`).
- **`Realtime` for the steerable duplex.** The live control/event channel is the `io: Channel` parameter of `Realtime.run`, handed in at `Fix.live(task, io)` — not a client field. Pure canonical reuse; the proposal's §3/§5 channel-pass-in story applies unchanged.
- **Capability negotiation as a runtime `match`.** `DeployedAgent.handle` `match`es its `inner` against `Durable`; `SubprocessSupervisor.run` `match`es against `Realtime` and throws `baml.errors.Unsupported` on the `_` arm (legal on any capability channel because `Unsupported` implements all of them). The companion-falls-back-or-errors rule (§5) is exactly the mechanism for "this Pi instance has no durable identity."
- **Combinators wrap, don't configure.** `SubprocessSupervisor` is a plain non-generic class that wraps a `Provider` and adds respawn-on-crash, chained as `.supervised(3)` — the `with_retry`/`Fallback` pattern (§6) applied to the background's "subprocess lifecycle is hard."
- **SAP at the final seam.** The drive-to-value path ends in `baml.sap.parse<T>(final_blob)` (OQ #6's public `baml.sap.parse`) — once, on `Drivable.drive_to_value`, not re-hand-rolled per harness.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Drivable` capability + `type Drive` + `HostMsg`/`AgentMsg`** — ties to the proposal's *capability-is-an-interface* primitive and the *associated-`type`* primitive (same shape as `Tools.Transcript`). This is the load-bearing addition: the background's central divergence is the *drive channel* (subprocess+JSONL vs JSON-RPC vs in-process generator), and a single flatten-to-a-value method alone hides it — which is exactly why, under provider-as-marker, drive-to-completion (`drive_to_value`) lives ON `Drivable` rather than as a faked base `call`. `Drive` being provider-owned and opaque is what lets one host vocabulary (`HostMsg`/`AgentMsg`) sit over three framings — the JSONL-vs-RPC divergence lives entirely inside `pump`, exactly where the proposal says per-provider wire threading belongs (§7).
- **`Durable` capability + `Instance` + `lease_acquire`** — ties to the capability primitive *and* to a new host boundary. Durable instance identity ("same `<id>` continues the same agent under single-writer semantics") has no expression in the base model; it is a genuinely new capability interface plus a `$rust_io` lease/persistence seam.
- **`register_provider` / `Registry`** — ties to nothing in the proposal; it is an *anti-`client`* surface. The proposal's whole §3/§4 thesis is "config is a declarative provider field." registerProvider is the opposite: a process-global mutable table read late at `open()` time. We add it as host primitives and show the harness body reading it, but it sits *outside* the provider-field model.
- **`Trigger` + `DeployedAgent`** — ties loosely to "a `client` is a value." We make the deployable unit a class carrying a `Provider` + declarative triggers. Triggers themselves (webhook/cron framing) are pure net-new data the substrate interprets; the proposal has no notion of deployment or scheduling.
- **`Subprocess`/`Generator`/`rpc_call`/`gen_next`** — ties to OQ #7 (`$rust_io_function` bodies inside `implements`). These are the non-HTTP transport bridges the base model explicitly leaves open.

- **Three net-new capability-error interfaces: `baml.errors.DriveError`, `baml.errors.DurableError`, `baml.errors.DeployError`.** The base error model ships exactly four — `CallError`/`StreamError`/`ToolError`/`RealtimeError` — and the rule is that any capability *beyond* those gets its own interface with classifier methods. This scenario's three additions each need one: `Drivable.{open,pump,close_drive}` declare `baml.ExtendUnknownError<baml.errors.DriveError>` (classifiers `is_transport_error`/`is_unsteerable`), `Durable.attach` declares `…<DurableError>` (`is_lease_contention`), and `DeployedAgent.handle` declares `…<DeployError>` (`is_run_failure`). The concrete errors map cleanly: the agent-emitted `"error"` AgentMsg becomes `HarnessRunError` (it implements `DriveError` + `RealtimeError`, because that one decline surfaces inside `pump`/`drive_to_value` and mid-`Realtime`; it additionally implements `CallError` so it rides a combinator-over-harness value path — `SubprocessSupervisor.call` — as its concrete self); a held lease becomes `InstanceBusyError`; an unsteerable pull-only generator becomes `UnsteerableDriveError`. This is the same per-capability-channel shape the core four use — it generalizes without ceremony, which is the error model's best showing here.

## (c) Where it is awkward, leaky, or unresolved

- **OQ #3 (the request side is HTTP-specific) is the deepest hit here — and provider-as-marker is what makes the fix clean.** The proposal asks whether non-HTTP transports want an associated request type. This scenario answers *yes, emphatically*: a harness has three mutually unlike transports and `build_request -> baml.http.Request` fits none of them. Our `Drivable` with `type Drive` is precisely the "associated type for non-HTTP transports" OQ #3 floats. Under the OLD base-`Provider.call` thesis this created a tension: each harness had to fake a degenerate `call` that was *only* "drive to completion," and DRYing the duplicated `open`/`pump`/`close` loop into a `Drivable` default felt like `Drivable` usurping the base model's job. **The marker revision dissolves that tension entirely:** there is no base `call` for `Drivable` to usurp — the value path *belongs* on the capability that owns the transport. We put `drive_to_value<T>` as a DEFAULT method on `Drivable` (one loop, shared by all three harnesses), and that is exactly *right*, not a workaround. The basic `Fix(task)` companion gains one degrade arm (`let d: Drivable => d.drive_to_value<T>(prompt)`) alongside the canonical `HttpProvider`/`Streaming` arms — the §2 universal-`match` story, with `Drivable` slotting in as just another value source.

- **OQ #1 is now RESOLVED — but `Realtime`'s simplex/duplex leak survives it.** OQ #1 ("does every capability `requires Provider` — i.e. must everything carry a `call`?") is closed by provider-as-marker as *no*: `Drivable`, `Durable`, and `Realtime` each `requires Provider` (the bare marker) and add only their own interaction, so no harness fakes a degenerate `call`. The old complaint that "`call` is dishonest on a harness" is gone. What does NOT go away is a *different* leak, internal to `Realtime`: `AgentsRunner`'s realtime is *read-only* (events stream out; `io.on` never fires) and its `pump` *throws* on any host input, yet it still `implements Realtime`. So `AgentsRunner` claims `Realtime` but silently degrades duplex to simplex — a capability the type system says it has and the runtime only half-delivers. The proposal's "capability is a runtime promise" (now applied to `call` too) covers this, but a host wiring `io.on(...)` against a `.live` companion still gets *no signal* that steering is a no-op. That is a real leak: simplex-vs-duplex is a different interaction shape, not a delivery refinement, yet it rides the same `Realtime` interface — orthogonal to, and unhelped by, the marker revision.

- **Server-authoritative / durable state is only partially expressible.** We can model `Durable.attach` and a single-writer lease, and lease contention now has a *typed* shape — `InstanceBusyError` (a concrete `DurableError` with `is_lease_contention() -> true`) the host branches on instead of the old model's stringly `baml.errors.LlmClient`. But the *guarantee* — that concurrent triggers on the same `<id>` serialize correctly — lives entirely in the `$rust_io` substrate (Durable Object / DB row). BAML can declare the capability and throw a typed contention error; it cannot *enforce* single-writer semantics in the language. The model surfaces the seam honestly but offers no more safety than a comment. This is a plain "the proposal cannot express it" for the part that actually matters operationally.

- **registerProvider fights the whole design.** §4 says "options dissolve into provider fields." Deployment says "provider config is *runtime* config you mutate at boot, applying to every harness." These are contradictory philosophies and we had to model *both*: a `client CodeAgent()` block AND a `register_provider(...)` call, with the harness `open()` reading the registry late so the imperative path can override the declarative one. The proposal has no opinion on which wins, and the precedence (constructed field vs late registry read) is something we *invented* here. This is unresolved surface, not just awkward.

- **The deployment channel can keep cross-capability errors typed; the only residual is the unenforced coverage convention.** `DeployedAgent.handle` is the choke point where THREE underlying capability channels converge: `Durable.attach` (`DurableError`), the inner harness's value path `Drivable.drive_to_value` (`DriveError`, carrying `HarnessRunError`; a request/response inner would instead surface `HttpProvider.call`'s `CallError`), and `handle`'s own declared channel (`DeployError`). The error model's normalizer — `baml.UnknownError.with_message<baml.errors.DeployError>(e, …)` — passes a thrown value through *as a concrete type* whenever it `implements DeployError`; otherwise it boxes into `baml.UnknownError`. The decisive point is that *which* errors implement `DeployError` is not fixed at the moment those errors were written: because BAML `implements` is a Rust-like trait relation admitting **external impls in both directions**, the **`DeployedAgent` package** — the one that owns `DeployError` — can declare, alongside its channel, `implements baml.errors.DeployError for InstanceBusyError` and `implements baml.errors.DeployError for HarnessRunError` (local trait, foreign type; coherent because the trait is local). Now an upstream `InstanceBusyError` or `HarnessRunError` rides the `DeployError` channel as its TYPED self, caught concretely at the webhook by `let b: InstanceBusyError =>`, with **no box** — `is_lease_contention()` and all. There is no forward-reference wall: a downstream channel retro-admits the upstream error types it wants to carry, and it is one external `implements` row per type (or a blanket impl), not a re-derivation of variance. So minimizing boxing here is a **coverage convention**, not a structural cost: either side of the boundary can supply the rows, and we in fact close every advertised crossing this way. The honest residuals are two and small. (1) Nothing *forces* the row — coverage is unenforced, so a forgotten `implements DeployError for <upstream error>` leaves that one crossing boxing; but then the error still survives untouched in `.data` (`with_message`'s third arm annotates the existing `UnknownError` in place), recoverable by re-asserting `from<InstanceBusyError>(e)` inside the `UnknownError` arm — and a forgotten row shows up as a type error at the first `_` arm, not a silent loss. (2) A *genuinely foreign* value reaching `handle` (a host panic in the lease substrate, an unmapped JSON failure) has no inner typed error to admit, so boxing into `baml.UnknownError` is correct there — that is the escape hatch doing its job, not a gap. **Recovery, when a crossing does box, is explicit, because `catch` is settled as no-auto-unwrap:** `handle(...) catch (e) { let b: InstanceBusyError => … }` is a runtime is-a test on `e` *itself*, and a boxed error *is* a `baml.UnknownError` (which does not implement `InstanceBusyError`), so that arm never fires on the box; you re-assert `baml.UnknownError.from<InstanceBusyError>(e)` inside the `UnknownError` arm. This is the error-channel form of P2's "capability = runtime promise" only for the *un-covered* crossings — and the model gives you the trait-impl tool to cover them, so it is not the variance pressure the combinator layer claims to have dissolved reappearing structurally, just a convention to follow.

- **No compile-time capability guarantee for deployment.** Because `client` returns the existential `Provider`, `translator_agent()`'s `inner` is typed `Provider`; whether it is `Durable` is discovered by `match` at request time. A deployment platform genuinely wants to *reject at deploy time* an agent declared with `triggers: [webhook]` whose provider can't persist instances. The proposal's escape hatch (drop the sugar, write `-> ConcreteDurable`) works but forfeits the polymorphism that made `DeployedAgent` reusable across harnesses. You cannot have both "any harness" and "statically durable."

## (d) Verdict: **Workable-with-additions**

The marker-`Provider` model carries the *coarse* shape of a harness cleanly: `Drivable.drive_to_value` flattens a run (one shared default, not a degenerate per-harness `call`), `Realtime` gives the duplex, combinators supervise the subprocess, and the `client` rewrite makes a harness indistinguishable from a chat model at the call site — `Fix(task)` is the same companion either way, just resolving to the `Drivable` degrade arm instead of `HttpProvider.call`. That portability across ClaudeCode/Pi/AgentsRunner is real and is the proposal's strongest showing here. Provider-as-marker *improves* this showing: the old "every harness fakes a `call`" awkwardness (OQ1) is gone — the harnesses expose only their real interaction, and the value path sits where it belongs. But the scenario's *actual content* — the three drive channels, durable instance identity, triggers, and runtime provider config — is all net-new surface the base model does not contain, and two of those additions (`Drivable`, registerProvider) sit in unresolved tension with the proposal's own theses (OQ #3 says the request side may need a non-HTTP associated type; §4 says config is a field, yet deployment demands a runtime registry). The model never *blocks* the scenario, but it also does not *give* you the hard parts — durable single-writer state and a compile-time durability guarantee remain outside the language. Workable, provided the proposal adopts `Drivable` (resolving OQ #3 affirmatively) and accepts an out-of-band deployment/trigger/registry layer as explicitly not-the-provider-model.
