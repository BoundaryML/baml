# Scenario 22 — Realtime / voice: a persistent bidirectional connection

This scenario stresses the `Realtime` capability against a real voice session, where the model holds a phone-call-style spoken conversation over one long-lived duplex socket. The payoff to look for: the connection **is** the session (no request/response, no session id), so the client block is pure config (`voice`, `instructions`, `manual_turn` for server-VAD vs push-to-talk) and the live `Channel` is handed in at the `.live` call — never a client field, because the duplex does not exist until you connect. Audio is **not a result**: PCM chunks ride the `Channel` as a side channel while `run` returns only the durable `Transcript` of typed *items* (not chat messages). `implement.baml` holds the OpenAI-items and Gemini-turn providers behind one interface plus the net-new duplex/concurrency host primitives; `usage.baml` shows config-only clients, the mic-pump + handler wiring, barge-in, and a fallback chain; `evaluation.md` argues **Workable-with-additions** and flags the two things the proposal cannot express — server-authoritative non-retryable state, and a compile-time realtime guarantee (Open Questions 1, 2, 3).
