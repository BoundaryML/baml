# Evaluation — Realtime / voice

Adversarial read of the proposal against a persistent bidirectional voice connection. The question is not "can you write some BAML" but "does the *proposed model* — Provider base, capabilities as `requires Provider`, client = config-only function, io as a call-time pass-in — fit the shape of a realtime session, or does the session shape leak through it?"

## (a) What the proposal reuses unchanged

- **`interface Realtime requires Provider`** — used verbatim. The capability's single method `run(self, prompt, io) -> Transcript` is exactly the right shape: a long-lived call that returns a *record* (not the audio) when the session ends. No new interface was needed at the capability level.
- **The pass-in `io: Channel`** — the proposal's central realtime claim (§3, Open Question 2) holds cleanly here. A voice channel genuinely does not exist until you connect, so making it a parameter of the capability method rather than a client field is not just acceptable, it is *correct*: `PhoneAssistant()` is pure config, and `VoiceChat.live(system, io)` is where the live duplex enters. The split the prompt asked us to justify — config-only client + a call-time io — falls directly out of the model with zero strain.
- **`.live` as a capability companion that `match`es and errors** — reused exactly as §5 specifies. Realtime is the canonical "different interaction shape, no honest fallback" case: the `_` arm `throw`s `Unsupported`, because a one-shot `.call` cannot fake a duplex session. This is the cleanest instance in the whole scenario set of "delivery refinement vs interaction-shape change."
- **`Realtime requires Provider` ⇒ a degenerate `call`** — reused as the proposal intends. `OpenAIRealtime.call<T>` is a real, if lossy, single turn (connect, one text item, one response, parse the caption). It satisfies the `requires` obligation without being a lie.
- **Combinators forward `.live` by runtime delegation** — `Fallback.run` from the conventions routes to the first `Realtime` member with no new code.
- **`server VAD vs push-to-talk` is one boolean field** — `manual_turn` is a provider field, exactly the "options dissolve into fields" rule (§4). The most divergent realtime behavior (who initiates a turn) reshapes the *body* of `run`/`forward_out`, never the interface. The app flips one field (`PhoneAssistant` vs `PushToTalk`) and the client shape is identical.

## (b) Net-new surface it must add (each tied to a primitive)

1. **A concrete event vocabulary: `InEvent`/`OutEvent` + `InKind`/`OutKind`.** The conventions' `Channel` is generic over abstract `InEvent`/`OutEvent` *associated* types. A voice session has to *pin* them to a real union (audio chunk, caption delta, input transcript, speech-started, tool-call, turn-done, error / append-audio, commit, cancel, truncate, …). Tied to: the `Channel` interface's associated `InEvent`/`OutEvent`. This is unavoidable and large — it is the realtime wire grammar, and it has no analogue in the request/response providers.

2. **A `Channel.send_in` (down-delivery) method.** The conventions' `Channel` has `on` / `send` / `close`. But `on` registers a handler and `send` pushes *up* the wire; nothing lets the provider's down-pump deliver a *decoded* `InEvent` to the app's handlers. The provider does the wire→`InEvent` decode, so it needs a "fan this to the registered handlers" call. We added `send_in`. Tied to: the `Channel` interface. This is a real gap in the canonical `Channel` — `on`+`send` alone is half-duplex from the provider's point of view.

3. **`baml.realtime.open(url, headers) -> WireSocket` (full-duplex socket).** `baml.http.fetch_sse` is read-only; a realtime provider must push and pull on one connection. Tied to: the host transport boundary (Open Question 3 — "the request side is HTTP-specific"). This is the answer to OQ3 for realtime: the provider sidesteps `HttpProvider` entirely and talks a duplex socket primitive.

4. **`baml.sys.spawn(() -> null) -> Task` (host concurrency).** The background's #1 "what's hard" — pump mic up AND drain events down simultaneously, forever, or deadlock — is **not expressible in straight-line BAML**. `run` is single-threaded; it cannot run two unbounded loops. We had to add a host spawn. Tied to: nothing in the proposal — it is a genuinely new host primitive the realtime model forces. (Tools/streaming never needed it because they are pull-based and turn-bounded.)

5. **`Transcript` as a typed item list; `Item` with `itype`.** The conventions leave `Transcript` opaque. Realtime needs it concrete to model items-not- messages (a `function_call` and its output are separate ordered items, not a chat turn). Tied to: `Realtime.run`'s return type. Modest, but real.

6. **Media/JSON host helpers** (`baml.media.b64_encode/decode`, `baml.json.object/get/has`, `baml.audio.play/open_channel`). Ambient host surface; small, but the audio side channel (`play` returns ms-enqueued for truncation) is load-bearing for barge-in.

## (c) Where it is awkward, leaky, or unresolved

- **Open Question 2 (how does `io` surface) — resolved well, with one wrinkle.** `io` riding only on the `.live` companion is exactly right and the scenario proves it. The wrinkle: the companion's signature is `VoiceChat.live(system, io)`, but the app must *also* register `io.on_kind(...)` handlers and start a mic pump *before* calling `.live`, because `.live` blocks for the whole session. So the `io` is not a simple "pass it in and get a result" — it is a live object the app wires up first, then hands over. The proposal's framing ("the channel arrives at the realtime call") undersells that the app and the provider *share* a mutable `io` concurrently. It works, but it is the least "functional" corner of an otherwise functional model.

- **Open Question 1 (does every capability `requires Provider`) — the degenerate `call` is nearly useless here.** `OpenAIRealtime.call<T>` exists and is honest, but a realtime model with no audio output, no streaming, and a full socket setup/teardown per call is something *no one will ever call*. So `requires Provider` is satisfied by a method that exists only to satisfy it. The scenario is mild evidence for the OQ1 alternative ("some capabilities should stand alone rather than refine `call`"): Realtime arguably wants to NOT require Provider. The proposal's uniformity has a small cost here.

- **Open Question 3 (the request side is HTTP-specific) — confirmed and pushed further.** A realtime provider implements neither `HttpProvider` nor a `build_request` over `baml.http.Request`; it opens a raw `WireSocket`. So "HTTP is a capability, not the base" is necessary but *not the whole story* — the base `Provider` also can't assume `baml.http` for the *transport*. The realtime provider is the second non-HTTP transport (after the harness, §8), and it needs its own host opener. The proposal accommodates this (sidestep `HttpProvider`), but it confirms there is no shared "transport" abstraction — each non-HTTP transport invents its own host primitive.

- **Server-authoritative state cannot be expressed as a guarantee.** The background's "the connection IS the session" is the deepest mismatch. The proposal's combinators assume a call is a *retryable value*: `Fallback`/`Retry` re-invoke `.call`/`.run` on failure. But a realtime session has externally visible side effects (audio already played, server-side conversation already mutated) that a retry cannot undo. `ResilientVoice()` *compiles* and the `.live` fallback to Gemini *runs*, but any audio that streamed from the failed OpenAI attempt is gone, and there is no session id to resume. The model has no way to *say* "this provider is non-retryable / its effects are external." The combinator layer silently does the wrong, dangerous thing. This is unresolved by the proposal and is the single sharpest leak.

- **Portability leaks through the config fields, not the interface.** The interface and `Channel` vocabulary are genuinely portable — `run_phone_call`'s handler code is byte-for-byte identical across OpenAI and Gemini. But: (1) `voice: "alloy"` is meaningful for `OpenAIRealtime` and a lie for `GeminiLive` (different catalogs), so `GeminiPhone` simply omits it — the *config* is not portable even though the *capability* is. (2) Under Gemini auto-VAD, `Commit` and `RequestResponse` `OutEvent`s are **silently dropped** (no wire frame exists), so the exact `run_push_to_talk` app code is a no-op against Gemini. The normalized event union hides this: the app emits events the target provider ignores. That is a real semantic divergence the type system does not catch — the price of one `Channel` vocabulary over two genuinely different turn models.

- **`tool_call` id-vs-name correlation leaks into the shared `ToolCall`.** OpenAI has real `call_id`s; Gemini correlates tool results by function *name*. We hid this by stuffing the name into `ToolCall.id` for Gemini, so `submit`- style correlation works opaquely. It is the same trick the conventions use for the Tools capability, and it holds — but only because the id is opaque to the app. If an app ever inspected the id, the abstraction would break.

## (d) Verdict: **Workable-with-additions**

The proposal's core realtime bet — config-only client, pass-in `io`, `.live` companion that errors with no fallback — is not just workable, it is the *most natural fit* in the scenario set; the config/io split the prompt asked us to justify is genuinely the right one and needs no defending. But "realtime" forces more net-new host surface than any prior scenario: a full duplex socket opener, a host concurrency primitive (`spawn`) with no analogue anywhere else, and a concrete down-delivery method (`send_in`) the canonical `Channel` is missing. Two things remain genuinely unresolved and the proposal cannot currently express them: (1) server-authoritative, non-retryable session state — combinators will silently retry effects that already escaped over the wire; and (2) a compile-time guarantee that a given client *is* realtime — it is a runtime `match`, so `VoiceChat.live` against a non-realtime client fails at call time, not build time. Neither is fatal; both are flagged. Workable-with-additions, with the additions being substantial host primitives, not just types.
