# Evaluation — Realtime / voice

Adversarial read of the proposal against a persistent bidirectional voice connection. The question is not "can you write some BAML" but "does the *proposed model* — Provider *marker*, capabilities as `requires Provider`, client = config-only function, io as a call-time pass-in — fit the shape of a realtime session, or does the session shape leak through it?"

This scenario is read against the **marker** spine ([`../provider-as-marker.md`](../provider-as-marker.md)): `Provider` carries NO interaction method; `call`/`call_with` belong to `HttpProvider`, `run` to `Realtime`. So a realtime provider is *not* forced to fake a `call` — it `requires Provider` (the marker) through `Realtime` and exposes only `run`. The old "degenerate `call`" complaint (OQ1) is therefore **resolved**, and the friction it caused below is recast accordingly.

## (a) What the proposal reuses unchanged

- **`interface Realtime requires Provider`** — used verbatim. The capability's single method `run(self, prompt, io) -> Transcript` is exactly the right shape: a long-lived call that returns a *record* (not the audio) when the session ends. No new interface was needed at the capability level.
- **The pass-in `io: Channel`** — the proposal's central realtime claim (§3, Open Question 2) holds cleanly here. A voice channel genuinely does not exist until you connect, so making it a parameter of the capability method rather than a client field is not just acceptable, it is *correct*: `PhoneAssistant()` is pure config, and `VoiceChat.live(system, io)` is where the live duplex enters. The split the prompt asked us to justify — config-only client + a call-time io — falls directly out of the model with zero strain.
- **`.live` as a capability companion that `match`es and errors** — reused exactly as §5 specifies. Realtime is the canonical "different interaction shape, no honest fallback" case: the `_` arm `throw`s `Unsupported`, because a one-shot `.call` cannot fake a duplex session. This is the cleanest instance in the whole scenario set of "delivery refinement vs interaction-shape change."
- **`Realtime requires Provider` (marker) ⇒ NO `call` to fake** — the marker model's cleanest payoff in this scenario. `OpenAIRealtime` and `GeminiLive` implement *only* `Realtime { run }`; because `Realtime requires Provider`, they still ARE providers (composable, fallback-able) without an `implements Provider { call }` block at all. The earlier draft wrote a degenerate single-turn `call` (connect, one text item, one response, parse the caption) to satisfy a base contract; under the marker that contract is gone, so the lossy fake is *deleted*, not merely tolerated. `Provider` being a bare marker is exactly what makes a pure-realtime provider honest.
- **Combinators forward `.live` by runtime delegation** — `Fallback.run` from the conventions routes to the first `Realtime` member with no new code.
- **`server VAD vs push-to-talk` is one boolean field** — `manual_turn` is a provider field, exactly the "options dissolve into fields" rule (§4). The most divergent realtime behavior (who initiates a turn) reshapes the *body* of `run`/`forward_out`, never the interface. The app flips one field (`PhoneAssistant` vs `PushToTalk`) and the client shape is identical.

## (b) Net-new surface it must add (each tied to a primitive)

1. **A concrete event vocabulary: `InEvent`/`OutEvent` + `InKind`/`OutKind`.** The conventions' `Channel` is generic over abstract `InEvent`/`OutEvent` *associated* types. A voice session has to *pin* them to a real union (audio chunk, caption delta, input transcript, speech-started, tool-call, turn-done, error / append-audio, commit, cancel, truncate, …). Tied to: the `Channel` interface's associated `InEvent`/`OutEvent`. This is unavoidable and large — it is the realtime wire grammar, and it has no analogue in the request/response providers.

2. **A `Channel.send_in` (down-delivery) method.** The conventions' `Channel` has `on` / `send` / `close`. But `on` registers a handler and `send` pushes *up* the wire; nothing lets the provider's down-pump deliver a *decoded* `InEvent` to the app's handlers. The provider does the wire→`InEvent` decode, so it needs a "fan this to the registered handlers" call. We added `send_in`. Tied to: the `Channel` interface. This is a real gap in the canonical `Channel` — `on`+`send` alone is half-duplex from the provider's point of view.

3. **`baml.realtime.open(url, headers) -> WireSocket` (full-duplex socket).** `baml.http.fetch_sse` is read-only; a realtime provider must push and pull on one connection. Tied to: the host transport boundary (Open Question 3 — "the request side is HTTP-specific"). This is the answer to OQ3 for realtime: the provider sidesteps `HttpProvider` entirely and talks a duplex socket primitive.

4. **Concurrency (the two pumps) — NOT net-new; it uses the shipped `spawn`/`await`/`Future`.** The background's #1 "what's hard" — pump mic up AND drain events down simultaneously, forever, or deadlock — *is* expressible in BAML: structured concurrency is a first-class, SHIPPED language feature (BEP-034, `baml_std/baml/ns_spawn` + `ns_future`). `run` is not stuck single-threaded — `spawn { drain_loop() }` runs the down-pump concurrently and returns a `baml.future.Future<null, E>` immediately; `await pump` blocks on it for the whole session and re-throws its error; the app's up-pump rides its own `spawn` (usage.baml). So the realtime model forces **no** new concurrency primitive — it just exercises one the language already has. (Tools/streaming never needed `spawn` because they are pull-based and turn-bounded; realtime needs the fan-out, and the language already provides it.)

5. **`Transcript` as a typed item list; `Item` with `itype`.** The conventions leave `Transcript` opaque. Realtime needs it concrete to model items-not- messages (a `function_call` and its output are separate ordered items, not a chat turn). Tied to: `Realtime.run`'s return type. Modest, but real.

6. **The audio side channel: `baml.audio.open_channel/play`.** This is the one genuinely net-new host helper in this group — `play` returns ms-enqueued for truncation, which is load-bearing for barge-in, and `open_channel` mints the host-backed `AudioChannel`. (The JSON/base64 work it sits next to is *not* net-new: wire frames are built as native `map<string, json>` literals + `baml.json.stringify`, read back with `baml.json.parse` + map/array navigation, and PCM is base64'd with the real `uint8array.to_base64()` / `uint8array.from_base64()` — all already in `baml_std`.)

## (c) Where it is awkward, leaky, or unresolved

- **Open Question 2 (how does `io` surface) — resolved well, with one wrinkle.** `io` riding only on the `.live` companion is exactly right and the scenario proves it. The wrinkle: the companion's signature is `VoiceChat.live(system, io)`, but the app must *also* register `io.on_kind(...)` handlers and start a mic pump *before* calling `.live`, because `.live` blocks for the whole session. So the `io` is not a simple "pass it in and get a result" — it is a live object the app wires up first, then hands over. The proposal's framing ("the channel arrives at the realtime call") undersells that the app and the provider *share* a mutable `io` concurrently. It works, but it is the least "functional" corner of an otherwise functional model.

- **Open Question 1 (must every capability carry a `call`) — RESOLVED by the marker.** The earlier draft had `OpenAIRealtime.call<T>` exist only to satisfy a base contract — a full socket setup/teardown per call, no audio, no streaming, something *no one would ever call*. Under the marker model that base contract does not exist: `call`/`call_with` live on `HttpProvider`, and a realtime provider `requires Provider` (the marker) through `Realtime` while exposing only `run`. So the degenerate `call` is *gone*, not merely tolerated — Realtime stands alone, and the class is still a Provider (composable, fallback-able) purely by virtue of the marker. This was the scenario's sharpest argument *for* the marker revision, and the revision adopts exactly that conclusion. No residual cost here.

- **Open Question 3 (the request side is HTTP-specific) — confirmed and pushed further.** A realtime provider implements neither `HttpProvider` nor a `build_request` over `baml.http.Request`; it opens a raw `WireSocket`. So "HTTP is a capability, not the base" is necessary but *not the whole story* — the base `Provider` also can't assume `baml.http` for the *transport*. The realtime provider is the second non-HTTP transport (after the harness, §8), and it needs its own host opener. The proposal accommodates this (sidestep `HttpProvider`), but it confirms there is no shared "transport" abstraction — each non-HTTP transport invents its own host primitive.

- **Server-authoritative state cannot be expressed as a guarantee.** The background's "the connection IS the session" is the deepest mismatch. The proposal's combinators assume a call is a *retryable value*: `Fallback`/`Retry` re-invoke `.call`/`.run` on failure. But a realtime session has externally visible side effects (audio already played, server-side conversation already mutated) that a retry cannot undo. `ResilientVoice()` *compiles* and the `.live` fallback to Gemini *runs*, but any audio that streamed from the failed OpenAI attempt is gone, and there is no session id to resume. The model has no way to *say* "this provider is non-retryable / its effects are external." The combinator layer silently does the wrong, dangerous thing. This is unresolved by the proposal and is the single sharpest leak.

- **Portability leaks through the config fields, not the interface.** The interface and `Channel` vocabulary are genuinely portable — `run_phone_call`'s handler code is byte-for-byte identical across OpenAI and Gemini. But: (1) `voice: "alloy"` is meaningful for `OpenAIRealtime` and a lie for `GeminiLive` (different catalogs), so `GeminiPhone` simply omits it — the *config* is not portable even though the *capability* is. (2) Under Gemini auto-VAD, `Commit` and `RequestResponse` `OutEvent`s are **silently dropped** (no wire frame exists), so the exact `run_push_to_talk` app code is a no-op against Gemini. The normalized event union hides this: the app emits events the target provider ignores. That is a real semantic divergence the type system does not catch — the price of one `Channel` vocabulary over two genuinely different turn models.

- **`tool_call` id-vs-name correlation leaks into the shared `ToolCall`.** OpenAI has real `call_id`s; Gemini correlates tool results by function *name*. We hid this by stuffing the name into `ToolCall.id` for Gemini, so `submit`- style correlation works opaquely. It is the same trick the conventions use for the Tools capability, and it holds — but only because the id is opaque to the app. If an app ever inspected the id, the abstraction would break.

## (c′) The error model under realtime

The old `type Error = baml.errors.LlmClient` single channel is gone; every fallible method now declares `baml.ExtendUnknownError<CapErr>`. Realtime maps onto this with two specific frictions.

- **Refusal-as-typed-channel survives, but the realtime decline is *mid-session*, and now there is only the in-band form.** A request/response provider raises a `Refused` once, at parse time, and the app branches on it. Realtime's structured decline arrives as an `InKind.Error` *frame* during a session that has already been running for minutes — it flows over `io` to the app's `on_kind(InKind.Error, …)` handler, as data, not as a throw. Under the marker model there is no degenerate `call` path, so the *throwable* form of this decline disappears entirely: `RealtimeServerError` now implements only `baml.errors.RealtimeError`, is reserved for a *session-fatal* error the provider chooses to raise on the realtime channel, and the routine mid-session decline is purely an `InEvent`. So the seam the earlier draft flagged — "the same condition is a throwable typed value on `call` but a Channel data event on `.live`" — is *narrowed*: there is no longer a competing call-path form to reconcile. What remains is the honest realtime fact that a long-lived session's errors are mostly **in-band** on `io`, and only the rare session-fatal one rides the `throws` channel. The per-capability channel does not (and need not) unify in-band events with thrown errors.

- **The combinator forwards the `RealtimeError` channel, which makes the non-retryable-state leak (above) *type-check as safe*.** `Fallback.run` declares `throws baml.ExtendUnknownError<baml.errors.RealtimeError>` — the same channel its member declares. So when OpenAI's `run` throws (e.g. a normalized socket `UnknownError`), `Fallback` is statically *entitled* to catch it and re-drive Gemini. The error model says this is correct and uniform; the realtime semantics say it is dangerous (audio already played, server state already mutated, no session id to resume). The flat `CapErr | UnknownError` channel gives the combinator *permission* to retry precisely the errors it must NOT transparently retry. The classifiers (`is_network_error`) don't help: a dropped socket IS a network error by every honest definition, yet it is exactly the case where a silent reconnect-as-retry replays external effects. The error model's "concreteness recovered at the catch" virtue here recovers the wrong affordance — nothing in the channel marks an error as *non-retryable*, and `RealtimeError` has no classifier for it.

- **Is `RealtimeError` even the right interface for a duplex transport?** `CallError`'s three classifiers (`is_network_error`/`is_rate_limit`/`is_parse_error`) are request/response-shaped. A realtime session's failure modes are different: socket half-closed, server VAD desync, audio buffer overrun, barge-in truncation rejected. We gave `RealtimeError` only `is_network_error`, because the others don't obviously apply — but that means the interface under-describes its own capability. A novel capability getting its own `baml.errors.<Cap>Error` interface is the right escape valve, yet here the *content* of that interface is the open question: realtime's errors don't factor into the same classifier vocabulary, so the app's interface-typed `catch` arm can triage almost nothing and falls back to the concrete type or `UnknownError` more often than for `call`.

## (d) Verdict: **Workable-with-additions**

The proposal's core realtime bet — config-only client, pass-in `io`, `.live` companion that errors with no fallback — is not just workable, it is the *most natural fit* in the scenario set; the config/io split the prompt asked us to justify is genuinely the right one and needs no defending. The marker revision strengthens this further: with `Provider` a bare marker and `call` an `HttpProvider` capability, the realtime providers drop their degenerate `call` entirely and `requires Provider` through `Realtime` alone — so **OQ1 ("must a realtime provider fake a `call`?") is resolved as "no,"** and this scenario was the sharpest evidence for that revision. But "realtime" still forces more net-new host surface than any prior scenario: a full duplex socket opener and a concrete down-delivery method (`send_in`) the canonical `Channel` is missing. (Concurrency itself is *not* net-new — the two pumps use the SHIPPED `spawn`/`await`/`Future` from BEP-034; realtime is just the first scenario that exercises it.) Two things remain genuinely unresolved and the proposal cannot currently express them: (1) server-authoritative, non-retryable session state — combinators will silently retry effects that already escaped over the wire; and (2) a compile-time guarantee that a given client *is* realtime — it is a runtime `match` (the same runtime-promise property the marker makes universal), so `VoiceChat.live` against a non-realtime client fails at call time, not build time. Neither is fatal; both are flagged. The new per-capability error model (`baml.ExtendUnknownError<baml.errors.RealtimeError>` in place of the old single `LlmClient` channel) is a clean fit for the *throwable* failures — a concrete session-fatal `RealtimeServerError` implements `RealtimeError` (no longer a dual `CallError`/`RealtimeError`, since the marker model leaves no call path to surface on), and `Unsupported` rides the realtime channel for the no-fallback `.live` negotiation — but it sharpens rather than solves the non-retryable-state leak: the combinator now *statically* shares the member's `RealtimeError` channel, so it is entitled to retry exactly the socket-drop errors it must not transparently replay, and no classifier marks an error as non-retryable. Workable-with-additions, with the additions being substantial host primitives, not just types.
