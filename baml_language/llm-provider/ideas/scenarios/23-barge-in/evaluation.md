# Evaluation — Barge-in, interruption & mid-session mutation

Adversarial read of whether the proposed Provider/capability model expresses **cancel + truncate-at-played-position + live `session.update`**, the races between them, and cancel-vs-close.

## (a) What the proposal reuses unchanged

- **`Realtime requires Provider` + `run(prompt, io)` (pass-in `io`).** The whole duplex loop — feed user audio, accumulate, drive responses — sits inside `OpenAIRealtime.run` / `GeminiLive.run` exactly as §3/§8 describe. The control plane (cancel/truncate) and the data plane (audio) share the one handed-in `Channel`; no second handle is invented, matching OQ#2's resolution.
- **Capability negotiation = runtime `match`.** Every app-driven steering helper (`PushToTalkInterrupt`, `SwapVoice`, `StopThisResponse`) is a `match (p) { let lc: LiveControl => …, _ => throw }`. This is the proposal's §5 pattern verbatim, with the `_` arm erroring because barge-in has **no honest fallback** (you cannot fake interruption on a non-steerable provider) — the same split as `Realtime`.
- **`client` as config-only sugar.** `VoiceOpenAI()` / `VoiceGemini()` carry voice
  + instructions as fields; the live channel never appears in the client. The `.live(args, io)` companion supplies `io`. No new client machinery.
- **Combinator opt-OUT is reuse, not addition.** `Fallback`/`Retry` simply do not implement `LiveControl`, so they degrade-or-error like any capability they don't forward. The model already says a combinator only claims what it forwards.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`LiveControl requires Realtime` interface** (`implement.baml` §1). The canonical `Realtime` has only `run`; cancel/truncate/update have nowhere to live. This is the irreducible addition: a typed seam where the provider owns the wire encoding and the *meaning* of truncate. Tied to: **capabilities are interfaces that `requires Provider`** — `LiveControl` is one more in the lattice (`Provider <- Realtime <- LiveControl`).
2. **A pinned `InEvent`/`OutEvent` event algebra** (`implement.baml` §0). The canonical `Channel` declares `on(handler: (InEvent)->void)` / `send(OutEvent)` but leaves the event types abstract. Barge-in is the first scenario that must pin them: `OutKind.{Cancel,Truncate,SessionUpdate,…}` and `InKind.{SpeechStarted,Audio,ResponseDone,Interrupted}`. Tied to: the **`Channel` primitive** — its events were a hole the proposal deferred.
3. **`PlaybackCursor`** (`implement.baml` §2) — played-position bookkeeping plus the generation counter that drops late `audio.delta`. Nothing in the canonical set tracks playback, because no HTTP provider ever needed it. It's a plain value the app threads (like `ClientHeldSession` / `ChainHandle` in scenario 20), not a provider. Tied to: nothing — it is genuinely outside the provider model, which is itself a finding (see c).
4. **`baml.audio.play_and_measure` host primitive.** The played-ms truncate argument can only come from the audio device. Tied to: the `$rust_io_function` host-boundary rule (OQ#7) — this is a new genuine seam.
5. **`baml.realtime.await_transcript(io)` host primitive** — blocks until the session ends and materializes the provider-owned `Transcript`. Tied to: the opaque associated `Transcript` of `Realtime`.

## (c) Where it is awkward, leaky, or unresolved

- **Played-position bookkeeping lives OUTSIDE the provider, but truncate's correctness depends on it.** `PlaybackCursor` is app-owned (only the app's speaker knows the true played-ms), yet `LiveControl.truncate(io, item_id, heard_ms)` is a provider method. So the provider owns the *encoding* of truncate but the *number* is fed in from app land. If the app miscounts (forgets the playback buffer, double-counts across items), the provider faithfully encodes a wrong truncate and the model's memory silently desyncs from what was heard. The capability cannot guarantee the one thing that makes truncate correct. This is the scenario's sharpest leak.
- **`truncate` is a no-op on Gemini — a thin abstraction, not a portable one.** `barge_in()` is portable at the *call site* (identical lines for both providers), but `heard_ms` is load-bearing for OpenAI and meaningless for Gemini (server-authoritative: it already discarded its unheard tail). The capability hides the *encoding* difference; it cannot hide that the two backends have **different notions of what the model remembers it said**. An app that relies on truncate to keep memory honest will be correct on OpenAI and merely-lucky on Gemini. The type system says both are `LiveControl`; the type system is lying about the semantics.
- **Server-authoritative state is unrepresentable.** Gemini decides what was kept; the client has no say. The proposal's model is client-drives-provider (`run` calls `io.send`), with no way to express "the server owns this fact and may overrule you." `GeminiLive.truncate` returning `null` is the only honest encoding, and it is indistinguishable at the type level from a truncate that *did* something. Same shortcoming scenario 20 hit with server-stored chains.
- **Races are correct but the safety is by-convention, not by-type.** The cancel/late-`audio.delta` race is handled inside `PlaybackCursor` (the `interrupting` window + `generation` bump). This works, but nothing in the type system forces a provider author to consult the cursor before playing a frame; a naive `run` that plays every `InKind.Audio` unconditionally compiles fine and ships the race. The proposal gives no place to encode "frames after a cancel are stale" as a checked invariant.
- **OQ#1 (does every capability `requires Provider`?) bites here.** `OpenAIRealtime` must implement `Provider.call` as a "best-effort single turn," but for a barge-in-centric voice model a single buffered turn is nearly meaningless — it exists only to satisfy the `requires Provider` chain. The `call` impl is dead weight the model forces. This is concrete evidence for OQ#1's "should some capabilities stand alone rather than refine `call`?"
- **OQ#2 (how does `io` surface?) is fine for `run`, strained for `LiveControl`.** `LiveControl.cancel(self, io)` re-takes the *same* `io` the session is already running on. There's no compile-time link tying "this `io`" to "the `io` `run` is driving"; an app could call `lc.cancel(io_b)` against the wrong channel and it would type-check. The pass-in model has no notion of "the channel this session is bound to."
- **No compile-time capability guarantee (§5, OQ#5).** Because `client` returns the existential `Provider`, "is this voice client steerable?" is a runtime `match`. An app that wires push-to-talk to a non-steerable backend discovers it only when the user presses the button. The escape hatch (drop sugar, write `function … -> OpenAIRealtime`) recovers the guarantee but loses dynamic selection — and `Voice(backend)` in usage.baml is *exactly* a case where you want dynamic selection AND a steerability guarantee, and you can't have both.

## (d) Verdict: **Workable-with-additions**

The interaction *shape* fits: barge-in is "more methods on the live capability," and a `LiveControl requires Realtime` interface drops cleanly into the lattice, reusing the runtime-`match` negotiation and the pass-in `io` wholesale. Cancel-vs- close even comes out *better* than the SDKs — they're distinct methods on distinct interfaces (`LiveControl.cancel` vs `Channel.close`), so the background's "conflate them and end the call by accident" hazard is removed by typing. But the additions are not free and one of them is structural: the **played-position bookkeeping that makes truncate correct lives in app land, outside any provider**, and the model has no way to make the provider *or* the type system responsible for it. Combined with truncate being a semantic no-op on server-authoritative backends like Gemini, the capability ends up portable in *encoding* but not in *meaning* — it abstracts the wire frame while leaking the memory model underneath. That's expressible, and honestly so (the no-op is visible in the provider body), but it is not clean: the proposal cannot state "this provider's truncate actually rewrites memory" as a checkable fact, and cannot bind a control call to the session it belongs to.
