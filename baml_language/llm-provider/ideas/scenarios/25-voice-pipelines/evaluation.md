# Evaluation — Cascaded voice pipelines + unified voice abstraction

Adversarial read: does "Provider base + capability interfaces + client-as-sugar" actually express a Pipecat-style cascaded voice agent *and* a Mastra-style unified voice object? Where does it hold, where does it leak?

## (a) What the proposal reuses unchanged

- **`Realtime` as the face of a voice session.** `CascadedVoice` and `NovaSonic` both `implements Realtime { run(prompt, io: Channel) -> Transcript }` — the exact pass-in `Channel` model from §3/§5. The app's `VoiceChat.live(system, io)` companion `match`es `Realtime` and routes to `run` with **no knowledge** of whether the implementation is a three-hop cascade or a one-hop STS. The cascaded↔STS architecture fork (the central voice decision) collapses to a one-line client swap. This is the proposal's best moment.

- **Combinators as plain classes that present a richer interface than their members.** `CascadedVoice` is exactly the `Fallback` pattern from §6: a plain non-generic class whose members are `Provider`s, which itself `implements` `Realtime`. STT/LLM/TTS go in as fields; one `Realtime` comes out. The "stages are providers, the wiring is a combinator" framing is native, not bolted on.

- **`requires Provider` (the marker) makes single-capability stages first-class.** An STT box (`Deepgram`) is a `Provider` whose REAL interaction is `listen`; a TTS box's is `speak`. Neither is forced to carry a `call` — under the marker revision `Provider` has no interaction method, so `SttProvider`/`TtsProvider` own their own verbs and nothing degenerate is forged. (Deepgram *additionally* `implements HttpProvider` for its genuine one-shot transcribe; Whisper/ElevenLabs/Cartesia do too — but that is a real HTTP path each chose, not a base obligation.) They drop into the combinator as `SttProvider` / `TtsProvider`-typed fields, and `llm: HttpProvider` accepts *any* chat model — so Deepgram × Llama × Cartesia type-checks with no per-combination glue declared in BAML.

- **Swap = field swap.** `PhoneAgent` → `PhoneAgentBudget` swaps all three stages and the combinator body is untouched, because it only ever sees the capability interfaces. Portability is real here.

- **Runtime capability `match` + degrade-or-error.** `Announce(text)` over a `CompositeVoice` errors (no `HttpProvider` to match — the `.call` companion's `_` arm throws `Unsupported`); `Whisper.listen` degrades streaming to a single buffered final frame. Both are the §5 split — delivery refinement degrades, missing interaction shape errors — applied to audio without new mechanism. Note the hole now lives in the *companion match*, not in a forged `CompositeVoice.call`.

## (b) Net-new surface it must add (each tied to a primitive)

- **`SttProvider` / `TtsProvider` capability interfaces** (the unified `listen`/ `speak` verbs). These are *new capabilities* in the §1 sense — `requires Provider`, single method each. Cheap and on-pattern, but they ARE additions: the proposal ships `Streaming`/`Realtime`/`Tools`/`Inspectable` and nothing audio.

- **`baml.errors.SttError` / `baml.errors.TtsError` capability-error interfaces.** Because STT and TTS are net-new capabilities, the error model adds two net-new *error* channels too: `listen` declares `baml.ExtendUnknownError<baml.errors.SttError>` and `speak` declares `baml.ExtendUnknownError<baml.errors.TtsError>`. Each gets the same classifier shape (`is_network_error`/`is_rate_limit`, plus `is_parse_error` on STT where transcript decoding can fail). A concrete `DeepgramHttpError` implements *both* `CallError` (its one-shot HTTP path) and `SttError` (its websocket `listen` path) — the canonical "one error, several capability faces" pattern, now spanning a core channel and a net-new one. The cost is *not* boxing — the channel author keeps upstream errors typed with one external `implements` row per error (e.g. `implements baml.errors.SttError for baml.errors.Refused` declared alongside `SttError`, and likewise for `Unsupported`) — it is the classifier *vocabulary*: each new verb drags a new error interface, and the classifier menu (`is_rate_limit` is meaningful for both; `is_parse_error` is meaningless for TTS) has to be decided per capability rather than inherited.

- **Audio media primitives at the host boundary:** `AudioChunk`, `AudioStream` (the audio analogue of `baml.http.SseStream`), `Transcription`, `VoiceTranscript` /`VoiceTurn`. These are `$rust_type`-backed opaque values, mirroring `baml.llm.PromptAst`. Needed because the spine only models text/JSON bodies.

- **`baml.llm.Stream<Transcription, string>` as the STT return.** Reuses the existing `Stream<TStream, TFinal>` shape (partials + final) — no new type, but a new *use* of it (the stream item is `Transcription`, not an output token).

- **A turn-detection host primitive: `VadDetector` + `silero_vad()`**, plus the cancel/queue helpers (`baml.voice.cancel_token`, `block_until_closed`). Nothing in the proposal models VAD/barge-in; it is genuinely new and lives inside the combinator body.

- **Audio members on the realtime event unions:** `InEventAudio`, `OutEventAudio`, `OutEventFlush`. The canonical `Channel` references `InEvent`/`OutEvent` but leaves them abstract; voice needs concrete audio/flush frames. Ties to OQ2 (how the channel surfaces) and to the `Channel` interface itself.

## (c) Where it is awkward, leaky, or unresolved

- **OQ1 (must every capability refine a base `call`?) — RESOLVED by the marker revision.** Previously two of the three combinators here had a `call` that was a lie or a stub: `CascadedVoice` forged a `call<T>` that silently dropped STT and TTS down to the LLM stage, and `CompositeVoice` (no model at all) had a forced `call<T>` that could only `throw`. Under [`../provider-as-marker.md`](../provider-as-marker.md), `Provider` is a bare marker with no interaction method, so `call` is an `HttpProvider` capability matched by the companion — not a base obligation. Both forged `call`s are now **deleted**: `CascadedVoice` exposes only `Realtime.run`, `CompositeVoice` exposes only `listen`/`speak`, and `NovaSonic` only `run`. Each still IS a `Provider` (via its capability's `requires Provider`) without faking anything. The capability hole at `Announce(text)` over a `CompositeVoice` did not disappear — it relocated honestly to the companion `match`, whose `_` arm throws a typed `Unsupported` when no `HttpProvider` is present. This scenario was direct evidence for the revision (pure-I/O and cascade capabilities want to stand alone); the revision adopts exactly that. There is no longer any "best-effort single turn" to strain over.

- **OQ2 (how the live `io` surfaces) + the audio-frame typing gap.** `Channel` is one interface with abstract `InEvent`/`OutEvent`. A telephony G.711 transport, a WebRTC transport, and a raw-WS transport all carry *different* concrete frame types, but `CascadedVoice.run` `match`es `InEventAudio` against a single `Channel`. There is no compile-time guarantee the handed-in channel actually speaks audio — a text `Channel` would simply never match `InEventAudio` and the agent would sit mute. The proposal gives no typed-channel mechanism; transport capability is unchecked.

- **No compile-time guarantee that a client is voice-capable.** Because `client` returns the existential `Provider`, `VoiceChat.live` only discovers at runtime whether the provider is `Realtime`. For `PhoneAgent` it is; but nothing stops an app author wiring a non-realtime client into `VoiceChat` and getting a runtime `Unsupported`. The escape hatch (drop the sugar, write `-> SomeRealtimeProvider`) works but forfeits the `client` ergonomics the scenario is selling.

- **Barge-in / latency budget live entirely in one combinator body, untyped.** The hard parts the background calls out — VAD firing, cancelling in-flight TTS, flushing the speaker queue, stitching STT+TTS text onto one LLM clock — are all imperative code inside `CascadedVoice.run` (`speaking.cancel()`, `OutEventFlush`, `context.append_*`). The model neither helps nor hinders here; it's "just BAML", which means the <300ms budget and echo handling are entirely the author's, with no abstraction the proposal contributes. Honest, but it shows the model stops at the combinator boundary.

- **Server-authoritative STS state is invisible.** For `NovaSonic`, turn-taking, interruption, and conversation state live *on the model's server*. The BAML `run` body is a single `$rust_io_function`; none of that state is expressible or inspectable in the model. The proposal can *invoke* an STS provider but cannot *describe* its session semantics — fine for a one-hop call, but it means the cascaded and STS paths are only superficially interchangeable (the cascade exposes per-turn hooks the STS path cannot).

- **`TtsProvider`-level fallback doesn't compose cleanly — and the new error channel rides along.** `with_retry`/ `fallback_to` are `Provider` default methods returning `Retry`/`Fallback`, which forward `call`/`stream`/`run` — but **not** `speak`/`listen`. A `Fallback` of two TTS providers would not forward `TtsProvider.speak` unless `Fallback` is extended to `implements TtsProvider`. So the new capabilities don't get combinator forwarding for free; every combinator must be taught each new verb (the §6 "statically claims every capability it forwards" cost, now multiplied by audio). The error model deepens this: a `speak`-forwarding combinator must *also* declare the matching `baml.ExtendUnknownError<baml.errors.TtsError>` channel and route its members' failures through it — `Retry`'s back-off logic has no `TtsError` classifier to consult for "is this retryable" unless `TtsError` happens to carry the right method, so generic retry over a brand-new capability is not actually generic.

- **NEW tension — which interface faces ride the `listen` channel is a coverage choice, not automatic.** `DeepgramHttpError` implements both `CallError` and `SttError`. Held as the existential `SttProvider` (all `CompositeVoice.input` and `CascadedVoice.stt` ever see), it raises on the `listen` channel, whose static type is `SttError | UnknownError`. By default an app that catches `let e: baml.errors.CallError` around a `listen` misses it: `CallError` is not in that channel's static type, so the value rides as its `SttError` face (the concrete `DeepgramHttpError` arm still recovers it via runtime match-most-specific). This is *not* erasure and *not* a forward-reference wall — the `SttError` author can put `CallError` on the `listen` channel by declaring `implements baml.errors.SttError for <those CallError types>` (or, if uniform call-vs-listen triage is wanted, by having the channel admit `CallError` directly), so "the same transport failure caught the same way regardless of verb" is one external `implements` row away. The honest residual is only that nothing *forces* those rows: absent them, the same transport failure is triaged under whichever interface the raising verb advertises, and the data is still recoverable via an explicit `from<baml.errors.CallError>` probe inside the `UnknownError` arm.

- **NEW tension — the swallowing catches inside `CascadedVoice.run` discard typed capability errors by choice, not by erasure.** The combinator body deliberately continues the session when a stage fails: `self.stt.listen(mic) catch (e) { _ => { return; } }`, same for `llm.call` and `tts.speak`. Under the new model those `_` arms now receive *typed* `SttError`/`CallError`/`TtsError` values (a Deepgram rate-limit, a Refused brain), not an opaque `LlmClient` — richer than before. Nothing in the model forces these errors to die: the cascade can re-raise a swallowed stage error onto its own `RealtimeError` channel *typed*, because `RealtimeError`'s author can declare `implements baml.errors.RealtimeError for baml.errors.SttError` (and for `CallError`/`TtsError`) — local trait, foreign type — so a mid-turn STT rate-limit reaches the `Realtime` caller as its concrete self, classifiable. The bridge exists; the *coverage* is the cascade author's to write. The honest residual is the classifier-vocabulary mismatch underneath it: even routed onto `RealtimeError`, a session-level caller's predicates (`is_barge_in`, retryability of a *turn*) are not the same questions a stage's `is_rate_limit` answers, so deciding what `RealtimeError` should synthesize from a stage failure is a per-capability vocabulary choice, not something inherited.

## (d) Verdict: **Workable-with-additions**

The core claim survives the voice scenario well: STT/LLM/TTS as composable single-capability providers wired by a `Realtime`-implementing combinator is a *natural* fit for "Provider marker + capability interfaces + combinators," and the cascaded↔STS fork genuinely reduces to a one-line client swap behind one `.live(args, io)` companion — the strongest possible endorsement of the unified `Realtime` face. But it is not Clean: it requires a real net-new layer (two voice capability interfaces, two matching net-new *error* interfaces `baml.errors.SttError`/`baml.errors.TtsError`, audio media primitives, a VAD host primitive, audio event frames), and it exposes two structural seams the proposal already flagged. The per-capability error model tracks the per-capability *value* model exactly — each new verb drags a new `baml.ExtendUnknownError<…>` channel — which is consistent but means novel capabilities never inherit triage. **OQ1 — the sharpest seam in the old draft — is now resolved by the marker revision:** because `Provider` carries no `call`, the forged `CascadedVoice.call` (a half-truth dropping STT/TTS) and the throwing `CompositeVoice.call` are both deleted; `call` is an `HttpProvider` capability the companion `match`es for. The capability hole survives in the *right* place — `Announce(text)` over a model-less `CompositeVoice` throws a typed `baml.errors.Unsupported` from the companion's `_` arm (legal on the CallError channel because `Unsupported` implements every capability interface), caught by its concrete class, not a stringly `LlmClient`. This scenario was concrete evidence that pure-I/O and cascade capabilities want to stand alone; the marker `Provider` lets them. The residual costs are unchanged: the absence of typed channels / compile-time realtime guarantees means transport-audio compatibility and "is this client even voice?" are both runtime gambles, and the model *expresses* cascaded voice but does not *help* with the budget, barge-in, or correctness that make voice hard — that all falls into one untyped combinator body. Workable, with the additions above; OQ1's degenerate-`call` complaint is now retired.
