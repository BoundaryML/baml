# Evaluation — Harness extensibility (tools, MCP, sub-agents, skills, hooks, A2A)

Adversarial read of whether the base-`Provider` + capabilities model actually expresses the five extension surfaces from `background/06-harnesses.md` §4.

## (a) What the proposal reuses unchanged

- **The `Tools` capability and its `ToolCall`/`ToolResult`/`ToolCalls` seam** carry the whole tool loop. In-process tools and MCP tools collapse into one dispatch path because the loop only ever speaks `(id, name, args) -> (id, output)` and never interprets the id — so "this tool is a local closure" vs "this tool is a remote MCP server" is a runtime branch inside `dispatch`, invisible to the loop. That is exactly the §4 requirement that "my function" and "a remote MCP server" be configured uniformly.
- **`client` = `function -> Provider` sugar** gives sub-agent registries for free: a sub-agent is a *named Provider*, so `agents: map<string, Provider>` is an ordinary field. No new "AgentDefinition" concept — `Reviewer()` is a client like any other.
- **Combinators inherited on the `Provider` marker** apply to A2A peers with no special-casing: `RemoteSummarizer()` chains `.with_retry(2).fallback_to(...)` on an `A2aProvider` identically to a chat model (`usage.baml` §7). This is the cleanest win — a request/response peer agent you don't own is portable behind one function. (The harness is excluded from this particular chain *honestly*: under the marker spine it is not request/response, so it never pretends to be a `call` fallback — see (d).)
- **`HttpProvider` defaults** absorb A2A wholesale: A2A is "JSON-RPC 2.0 over HTTP(S) + SSE", which is precisely `build_request`/`send`/`parse` with an inherited `call`/`call_with`. No net-new transport. `A2aProvider` already `implements HttpProvider`, so the marker revision touches it not at all.
- **Options-as-fields** means `tools`, `agents`, `hooks` are just `ClaudeCode` fields. No options blob, no `@providers:` map.
- **`Realtime.run(prompt, io)`** is reused verbatim for the steerable `.live` session (`Pair.live`).

## (b) Net-new surface it must add (each tied to a primitive)

- **`HarnessTool` extends the canonical `Tool`** with a `source: ToolSource?` (in-process handler vs MCP connection + wire name). The canonical `Tool` has no dispatch source, because in the base model dispatch is the app's `ctx.dispatch` closure. Carrying both kinds behind one `Tool[]` field forces this. *Tied to:* the `Tool` type and `ExecutionContext.dispatch`.
- **`ToolHandler` / `McpConnection` / `HarnessSession` host primitives** (`$rust_type`). Genuine boundaries — a captured host closure, a live MCP socket, a subprocess. *Tied to:* §7's "host-backed providers" (Open Q7).
- **`ExecutionContext.emit` + a `Hook` interface + `HookEvent`/`HookVerdict`.** The proposal flags `emit` as needed ("an event-emit surface") but never defines the event vocabulary or the *veto/rewrite* semantics. Hooks that **block or mutate** a tool call are net-new: they require `dispatch` to be hook-gated, which the canonical `dispatch` is not. *Tied to:* `ExecutionContext` (§7 net-new flag).
- **A `Skills` capability** (`skill<T>` + `commands`). Skills/slash-commands are a distinct interaction shape (named typed procedure, not a prompt), so they earn their own `requires Provider` interface alongside `Tools`. *Tied to:* the capability-interface pattern.
- **A net-new `baml.errors.SkillError` capability-error interface.** Because `Skills` is a capability beyond call/stream/realtime/tools, the error model says it must carry its own error channel: `skill<T>`/`commands` declare `baml.ExtendUnknownError<baml.errors.SkillError>`, mirroring how the core capabilities each declare their own. We gave it two classifiers — `is_network_error` (the control plane is unreachable) and `is_unknown_skill` (the harness has no such named procedure) — but see (c.7): those classifiers are a guess, because a *slash command that simply isn't defined* is the kind of failure neither `is_network_error` nor a parse-error captures. *Tied to:* the per-capability error-channel rule.
- **A `SubAgent` combinator** to enforce the §4 composition rules structurally (fresh conversation, final-only, no nested sub-agents). It `implements HttpProvider` and forwards *only* `call`/`call_with` to its inner provider's `HttpProvider` (routing the sidecar projection through so usage/cost is not dropped — the P1 fix), deliberately withholding `Tools`/`Skills` — that withholding *is* the "cannot spawn its own sub-agents" rule. Under the marker spine, "expose only request/response to the parent" is now stated precisely as "implement `HttpProvider` and nothing else," rather than "implement the base `Provider.call`." *Tied to:* combinator pattern.
- **`A2aProvider` + `AgentCard` + discovery factory.** Discovery (`/.well-known/agent-card.json`) is a static factory returning a configured provider; net-new but small. *Tied to:* static-factory pattern + `HttpProvider`.

## (c) Where it is awkward, leaky, or unresolved

1. **The `Tools.begin(prompt, tools: Tool[])` signature fights the field model.** The canonical loop hands `begin` a `Tool[]` (schemas only). But our real dispatch needs `HarnessTool[]` (handlers + MCP sources), which we carry as a *provider field* (`self.tools`), not as the loop's argument. So `ClaudeCode.begin` **ignores its `tools` parameter** and reads `self.tools` instead (see the inline note in `implement.baml`). The canonical seam assumes tools arrive *at the call*; the harness world assumes tools are *configured on the provider*. These two sources of truth don't reconcile, and the signature lies about which one wins. This is a genuine seam mismatch, not cosmetic.

2. **Tool *output* typing is loose everywhere — and the model can't fix it (§4 "What's hard").** `ToolResult.output` is `unknown`; `HarnessTool` has no `output: type`; MCP/handler results come back `unknown`. The first-class `type` primitive types tool *inputs* beautifully (`parameters: reflect.type_of<TArgs>()`) but the proposal offers nothing to type outputs, and we deliberately left `output` off `HarnessTool` to avoid pretending otherwise. This is honest, but it means the one place SAP could help (parsing a tool result into a typed shape) is left to the app. The model neither solves nor worsens the industry-wide gap.

3. **Hooks that *block* expose the runtime-only nature of capabilities (Open Q5).** A `Hook` blocking a tool depends on `match`ing `HookVerdict.replace`/membership at runtime, and the whole hook pipeline is value-level. There is no way to state "this agent has a lint hook" in a type; a misconfigured `hooks: []` silently disables policy. The proposal's runtime-membership `match` (Open Q5) is fine for *capability presence*, but hooks want *guaranteed* invocation, which the model cannot promise statically. Server-authoritative hook state (a hook that lives on the harness binary, not in BAML) is entirely outside the model — we can only dispatch hooks we own in-process.

4. **OQ1 RESOLVED by the marker spine — Skills no longer forces a fake `call`.** The old worry here was that "every capability `requires Provider`" meant a pure skill-runner had to implement `call<T>` as a "best-effort single turn." Under `../provider-as-marker.md` that is gone: `Provider` is a bare marker with *no* `call`, `Skills requires Provider` (the marker), and a skills-only service implements only `Skills`. It is a Provider by being composable, not by faking request/response. `ClaudeCode` itself now implements only its real surfaces (`Tools` + `Realtime` + `Skills`) and has *no* `implements Provider { call }` block at all — exactly the standalone interaction shape we wanted. The cost (named in `provider-as-marker.md` §5) lands instead at the call site: a function written as a plain value function over a skills-only/harness client `throw`s `Unsupported` rather than being caught by the type system — visible in `usage.baml` §7, where the harness can no longer stand in as a request/response fallback.

5. **Sub-agent indirection leaks through `flat_tool_names`.** The model surfaces sub-agents to the binary as a single built-in `"Agent"` tool name, and the binary resolves the registry. But our BAML-side `HookedExecutionContext.invoke` has no closure for built-in `"Agent"` — it `throw`s "provider-resolved". So sub-agent dispatch and tool dispatch live on **two different planes** (one in the binary, one in BAML), and the seam between them is the stringly-typed `flat_tool_names`. The §4 "wire-name leakage" problem reappears here as a `null`-source `HarnessTool`.

6. **Open Q3 (request side is HTTP-specific).** `A2aProvider` fits `HttpProvider` cleanly, but A2A's **async push-notification** path for long-running tasks is a callback the peer makes back to *us* — there is no place for an inbound webhook in the `build_request`/`send`/`parse` codec. We can model A2A's request/SSE path but not its push path without a `Realtime`-style inbound channel, which A2A-as-an- `HttpProvider` doesn't have.

7. **A novel capability's error interface forces us to guess the classifiers — and the harness's most-distinctive failure doesn't fit them.** The error model says any capability beyond the four core ones gets a new `baml.errors.<Cap>Error` interface with "sensible classifier methods." For `Skills` we invented `is_network_error` + `is_unknown_skill`. But the core interfaces are built around `is_network_error`/`is_rate_limit`/`is_parse_error` — a *transport-and-parse* taxonomy — and a skill that simply isn't defined (`commands()` doesn't list it) is neither. So either every new capability re-litigates what "classification" even means, or we bolt on capability-specific predicates (`is_unknown_skill`) that no shared caller can rely on. The uniform-triage promise ("callers triage without the concrete class") weakens precisely at the capability boundary the model is supposed to make extensible: a caller holding `baml.errors.SkillError` can ask `is_unknown_skill`, but a caller holding the *core* `baml.errors.CallError` for the same harness's `.call` cannot — the two channels for one provider don't share a vocabulary.

8. **The hook/dispatch plane throws `baml.errors.Io`, which the error model never sees — and `dispatch_one` *eats* it into a tool-result instead of routing it to `ToolError`.** `HookedExecutionContext.dispatch`/`invoke`/`Hook.on_event` still declare `throws baml.errors.Io` (a foreign transport error, deliberately left as-is). But `dispatch_one` catches a failed `invoke` and turns it into `ToolResult { output: { "error": ... } }` — a value, not a thrown `baml.errors.ToolError`. So an in-process tool blowing up never reaches the `baml.ExtendUnknownError<baml.errors.ToolError>` channel that `step`/`submit` advertise; it is laundered into the transcript as ordinary tool output. That is arguably correct (the model *should* see a tool failure and decide what to do), but it means the typed `ToolError` channel describes only *harness-protocol* failures (spawn/pump/submit), never *tool-execution* failures — a real asymmetry the per-capability channel hides. And because hooks themselves can `throw baml.errors.Io`, a blocking hook that fails is swallowed by `run_hooks`' `catch (_) { continue; }` rather than ever becoming a `ToolError`: a policy hook can silently no-op, and the error model cannot express "this failure was a hook failure" at all.

## (d) Verdict: **Workable-with-additions**

The model's spine carries the load surprisingly well: sub-agents-as-Providers, A2A-peers-as-Providers, and the in-process/MCP tool merge all fall out of the base `Provider` + `Tools` seam with no new core concept, and combinator portability over a peer agent is genuinely elegant. The per-capability error model rides along cleanly — `ClaudeCode`'s real surfaces declare their own channels (`begin`/`step`/`submit` the `ToolError` channel, `run` the `RealtimeError` channel, `skill`/`commands` the net-new `SkillError` channel), and the `A2aProvider` HTTP codec declares `CallError` and normalizes foreign `baml.errors.Io` into `baml.UnknownError` exactly like a chat provider. The harness carries NO `CallError` channel because it carries no `call`: the marker spine aligns each error channel with a capability the provider actually has, rather than forcing a degenerate `call`/`CallError` pair onto a subprocess. But it is not Clean. Five real additions are required (`Skills`, a net-new `baml.errors.SkillError` channel for it, the hook pipeline with block/mutate semantics, `HarnessTool`'s dispatch source, the `SubAgent` combinator), and three seams are awkward rather than merely new: `Tools.begin`'s `tools` parameter is dead weight once tools are provider fields; hook/sub-agent dispatch splits across the BAML and binary planes with the wire-name leakage the background calls out; and the error model itself splits — the typed `ToolError` channel only ever carries harness-*protocol* failures while actual tool-execution and hook failures are laundered into `ToolResult` values or swallowed by `run_hooks` (c.8), and a novel capability like `Skills` forces classifier predicates the shared triage vocabulary can't support (c.7). The model also cannot express two things §4 implies — a compile-time guarantee that a hook *will* run, and server-authoritative state on a peer or on the harness binary. None of these sink the design, and the marker spine actually *removes* one prior complaint outright — the harness no longer fakes a degenerate `call`, so OQ1 is resolved here (c.4). But "extensibility" is still where the runtime-promise nature of capabilities (Q3, Q5, and now the call-site `Unsupported` for a value function over a non-request/response client) is most visible, so the honest grade is Workable-with-additions.
