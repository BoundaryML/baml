# 39 — Harness extensibility: tools, skills, sub-agents, hooks, MCP, A2A

How the proposed base-`Provider` + capabilities model absorbs the five ways you teach an agent new tricks. In-process tools and external MCP servers ride one `Tool[]` field; sub-agents are named `Provider`s with restricted tools (and a `SubAgent` combinator enforcing the "no nested sub-agents" rule by withholding capabilities); skills/slash-commands are a `Skills` capability; lifecycle hooks ride `ExecutionContext.emit` plus a hook-gated `dispatch`; and A2A peer agents you don't own are an `A2aProvider` that `implements HttpProvider` over JSON-RPC 2.0 — so request/response peers over the wire are portable behind one function. Under the marker spine (`../provider-as-marker.md`) a subprocess harness is NOT request/response: `Provider` is a bare marker, `call` belongs to `HttpProvider`, and `ClaudeCode` is a Provider only through the capabilities it really has (`Tools`/`Realtime`/`Skills`) — it never fakes a one-shot `call`. Read `implement.baml` (library) then `usage.baml` (app), then `evaluation.md` for where it leaks (tool-output typing, the `begin(tools)` parameter fighting field-configured tools, and the binary-vs-BAML dispatch split).
