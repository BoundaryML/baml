# Evaluation — Capability negotiation

Adversarial read of whether the proposed model expresses capability negotiation cleanly. This is the proposal's *central* scenario — §5 ("companions `match`, and fall back to `.call`") is the whole thesis of how a client discovers what a provider can do. So the bar is high and the failure modes are the interesting part. The background names four discovery mechanisms (runtime 400, declarative flags, static table, live query) and one hard truth: **"supported" is not binary.** The proposal answers exactly *one* of those mechanisms natively; the other three and the gradient are net-new.

**P1 update (value + sidecar):** the silent-downgrade `warnings` channel is a **product sidecar** (you got a `T` *and* a note about how it was made), so it is now **resolved-with-a-named-mechanism**: `call_with` + a `warnings()` dimension on `ResponseMeta` (../value-sidecar-model.md, _conventions.md "Value + sidecar model"), *not* the bespoke `Warned<T>` companion this scenario originally invented. Because `call_with` is the `HttpProvider` value+sidecar method that combinators forward (Negotiated routes it to a member's `call_with`), the downgrade warning survives `Negotiated`/`Retry`/`Fallback` — the silent-drop this scenario's old out-of-band `baml.sys.warn` sink risked is gone. Honest residuals stay (below): a Fallback aggregate projects only the **winner's** meta; per-field absence (`Warnings` present or not) is a **runtime** promise (P2); and the request-time downscale warning rides a small `(image, Warning[])` tuple because `guard` runs *before* any ResponseMeta exists.

## (a) What the proposal reuses unchanged

- **The §5 behavioral `match` is the runtime-400 + interaction-shape story, intact.** "Can this provider stream / run tools / go realtime *at all*" is answered by `match (p) { let s: Streaming => …, _ => … }` with the `_` arm deciding degrade-vs-error. `Summarize$stream` (usage §3) is the proposal's own §5 example verbatim — Streaming degrades to a buffered `.call`, Gemini (no `implements Streaming`) takes the fallback arm. Zero new machinery; this half of negotiation is genuinely free.
- **The typed `throws`/`catch` channel is the runtime-400 absorber.** A schema rejection is a `catch (e) { let r: SchemaRejected => … }` — the exact shape of the Python `except openai.BadRequestError` pattern, but as a typed error arm. `Negotiated.call_with` (implement §6) is built entirely from `match` + `catch`, both pre-existing.
- **Combinators wrap a Provider, so negotiation composes with orchestration.** `Negotiated` is a plain non-generic class that `implements HttpProvider` by routing `call_with` to a member (matching the bare-marker member to `HttpProvider` first, per [`../provider-as-marker.md`](../provider-as-marker.md) §6; `call` is inherited), identical to the `Fallback`/`Retry` template. `Production` (usage §5) chains `Negotiated(...).with_retry(2).fallback_to(...)` with no special-casing — the combinator factories live on the `Provider` marker, so negotiation is "just another combinator."
- **`client` = `function -> Provider` lets the degraded twin be an ordinary sibling client.** `OpenAIPromptJson()` and `SmartExtractor()` are both clients; passing one as the `degraded` field of the other is the §3 "client: takes any Provider expression" rule, reused.
- **The existential return is, again, the mechanism *and* the limit.** Because a client returns `Provider`, `CanThisModelDoStructuredOutput` (usage §2) *must* `match` down to `Capabilities` at runtime — there is no static `.structured_output`. That is the proposal's stated §5 posture, applied honestly here.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Capabilities` interface + the `Support` lattice (`Yes`/`No`/`Maybe`).** Tied to the capability-as-`requires Provider`-interface rule (§1). This is the proposal's missing third leg. §5 gives "match on the *behavioral* capability"; it has **no answer for declarative, data-shaped capability** (Vercel `supportedUrls`, LiteLLM `supports_vision`). I model it as a behavior-free capability interface whose methods are pure reads — which is idiomatic, but it is *new surface the proposal does not mention*. The `Support` enum is the load- bearing addition: a `bool` would reproduce the background's named failure ("a flag can't capture the gradient"). The `Maybe` arm is what makes the declarative layer defer to the runtime probe instead of lying.
- **`baml.schema.depth/uses_unions/uses_refs` + `baml.media.image_dims`.** Host functions tied to the `$rust_io_function` boundary. These are what let a *declarative* answer be computed *for the specific `T`/image* rather than for the model in the abstract — i.e. they are how the gradient is made checkable before the call. Without them, `Capabilities` could only return per-model constants (the stale-table failure mode).
- **`Warning` + a `warnings()` dimension on `ResponseMeta` (the PRODUCT-sidecar path).** Tied to the value+sidecar model: `call_with<T,U>` + `ResponseMeta` (`Warnings requires ResponseMeta`), **not** a bespoke `Warned<T>` companion or an out-of-band `baml.sys.warn` sink. The background: "silent downgrades are worse than errors," and the AI SDK returns a `warnings` array. `call<T>` still returns a bare `T` (the 90% path, zero tax) and *ignores* warnings — but the author who cares projects them off `call_with` (`m => match (m) { let w: Warnings => w.warnings(), _ => [] }`), the same path as usage/logprobs. The win over the old sink: `call_with` is the `HttpProvider` value+sidecar method that combinators forward, so `Negotiated` wraps the inner meta in a `DowngradeMeta` (forwarding every provider dimension, answering `warnings()` itself — the §3 delegation shape) and the downgrade note **survives Retry/Fallback** instead of vanishing into an ambient sink the next combinator drops. The residual concession is now P2-shaped, not carrier-shaped: a caller *can* still ignore the warning (it's in `U`, not forced), and which providers expose `Warnings` is a runtime `match`, not a static guarantee.

- **Tuples `(T, U)` — REQUIRED net-new surface.** `call_with` returns `(T, U)` and `ExtractChecked`/`DescribeImage` destructure it; `ResolutionGate.guard` returns `(image, Warning[])` because it runs *before* any `ResponseMeta` exists. First-class tuple types + tuple destructuring (`let (safe, pre): (image, Warning[]) = …`) are a shared dependency with the streaming folds and the rest of the value+sidecar model — flagged here as load-bearing for this scenario, not bespoke to it. (A named `Output<T,U>` struct is the fallback if tuples are rejected, at an ergonomic cost.)
- **`SchemaRejected` error — a concrete class on the `baml.errors.CallError` channel.** Under the new error model there is no single `LlmClient` type; every fallible method declares `baml.ExtendUnknownError<baml.errors.CallError>` (or `StreamError`/`ToolError`/`RealtimeError`). `SchemaRejected` is a concrete class that `implements baml.errors.CallError` (and `StreamError`, since a streamed structured output can be rejected mid-stream) with `is_parse_error() -> true`. That classifier is exactly what lets `Negotiated` distinguish "the *schema* was the problem" (downgrade-able) from "the network was the problem" (not) — a transport `Io`/`Timeout` (which the stdlib makes a `CallError`, so it rides this channel as its typed self, not boxed) is simply not a `SchemaRejected`, so `let r: SchemaRejected` never matches it and the downgrade never fires on a timeout. The per-provider non-2xx transport face is a separate concrete class (`OpenAiHttpError { status }`, `GeminiHttpError { status }`) that also implements `CallError` (with `is_rate_limit() -> status == 429`). New error classes, built on the per-capability channel rather than a single provider error type.
- **`Negotiated` + `ResolutionGate` combinators.** Net-new *library* classes, no new primitive — `match` + `catch` + a `DowngradeMeta`/`PreflightMeta` wrapper that records the warning into the projected `ResponseMeta`. They are the glue that turns Yes/No/Maybe into "send / refuse / probe-then-fall-back," which is the actual negotiation the proposal hand-waves as "the `_` arm decides."

## (c) Where it is awkward, leaky, or unresolved

- **OQ-5, head-on — the *graded* match needs more than membership reflection.** OQ-5 asks only whether `match (p) { let s: Streaming => … }` (interface membership) is supported. But this scenario needs strictly *more*: `cap.structured_output<T>()` is a **generic method on a runtime-existential provider**, dispatched on a `T` that itself must be reflected (`reflect.type_of<T>()`) *inside* the matched capability. The §5 `match` recovers the concrete type; does the runtime then support calling a *type-parameterized* method on it and re-reflecting `T`? If OQ-5 only guarantees membership (a `bool` test), the entire `Capabilities` layer is unsound — it depends on dispatching real generic behavior through the existential, not just testing the tag. **This scenario silently raises the bar OQ-5 sets, and the proposal does not confirm it can clear it.**

- **OQ-1 — RESOLVED by the marker model. `Capabilities requires Provider` no longer forces a `call`.** OQ-1 asked whether every capability should `requires Provider` and whether that forced a degenerate `call` onto read-only capabilities. Under [`../provider-as-marker.md`](../provider-as-marker.md) `Provider` is a bare **marker** carrying only the combinator factories — it has NO `call`. So `Capabilities` (pure data, no behavior) `requires Provider` to ride the existential and be `match`-able, and that is now **honest**: being a Provider means "composable + matchable", not "can run a completion." `call`/`call_with` live on `HttpProvider`; a metadata-only provider simply does not implement `HttpProvider`, and nothing forces it to pretend it can run a completion. LiteLLM's dict-like table maps cleanly to a `Capabilities`-only provider. The old "every capability refines `call`" framing — which fit Streaming/Realtime but actively misfit a read-only capability — is gone; this scenario's worst-case for OQ-1 is exactly the case the marker revision fixes.

- **The gradient is *expressible* but the proposal's native answer is *binary*, so the whole declarative layer is bolted on.** §5's `match` returns "is-a Streaming: y/n." The background's central finding — JSON schema but only shallow, images but not at resolution, tools but not parallel — has **no native home** in the proposal. I had to invent `Support`/`Capabilities`/the gradient host probes wholesale. The proposal does not merely under-specify this; its one negotiation mechanism (`match`) is the wrong *shape* for graded support. This is the scenario the proposal is named for, and it answers ~40% of it out of the box.

- **Warnings now have a typed home (`call_with` + `ResponseMeta`), but the caller can still skip it.** The old `baml.sys.warn` sink is gone: a downgrade is recorded into the meta layer (`DowngradeMeta`/`PreflightMeta`) and projected as a real `(T, U)` product via `call_with`, surviving combinators. What does *not* fully resolve: the value+sidecar model deliberately keeps `call<T> -> T` as the zero-tax 90% path, so an author who calls `.call` (or the `client` sugar) still gets no warning — the model can now *carry* the downgrade in a typed channel but cannot *force* the caller to read it without abandoning the bare-`T` path. That is the same residual the model accepts everywhere (warnings are in `U`, opt-in), reduced from "worse than errors, no typed home at all" to "typed home, opt-in projection." A pervasive `Warned<T>`-everywhere signature change is explicitly *not* needed — that was the bespoke companion this rewrite removed.

- **No compile-time capability guarantee — and here it actively hurts.** As in provider-diversity, `client` returns the existential, so "this client supports structured output for `Resume`" is unprovable statically; `CanThisModelDoStructuredOutput` is a runtime function returning a *string*. The escape hatch (`function … -> ConcreteProvider`) recovers a static capability but only for *one named provider* — you cannot say "any provider, but it must structured-output this `T`." Capability negotiation is precisely the place a developer wants a build-time guarantee ("don't ship a config that can't do what this function needs"), and the model can only offer a runtime probe. **Stated plainly: a compile-time capability contract is unsupported.**

- **Live-query discovery (Claude Agent SDK `q.supportedModels()`) is unmodeled.** The fourth mechanism — asking the *running runtime* what it supports — is an out-of-band, stateful, async query against a live session. `Capabilities` methods are pure/synchronous reads of static knowledge; a live query is an IO call against server-authoritative state. It would have to be a separate `throws`-ing method (`function probe_models(self) -> ModelInfo[] throws baml.ExtendUnknownError<baml.errors.CallError>`), which collides with `Capabilities` being a pure, *infallible* read interface — and forces a choice of capability channel for a method that is really a control-plane query, not a `call`. The proposal has no story for server-authoritative capability state; this scenario does not invent one.

- **NEW (error model): `Negotiated` does not just *forward* the `CallError` channel — it *narrows* the observable error set by design.** Rule 4 says a combinator declares the SAME `baml.ExtendUnknownError<baml.errors.CallError>` channel as its inner provider, with "no narrow / widen / forward." `Negotiated` honors that *statically* — its `call_with<T,U>` channel is identical to `inner.call_with<T,U>`'s (and `call` derives from it) — but it deliberately *consumes* one concrete inhabitant of that channel: a `SchemaRejected` thrown by `inner` is caught and turned into a successful (degraded) result plus a projected warning, so the caller of `Negotiated` will **never** observe `SchemaRejected` even though the type system still lists it as reachable. That is a real and intended divergence between the static channel and the runtime behavior. The honest tension: the new model gives combinators a uniform channel precisely so they don't do error-type gymnastics, but it has **no way to express "I handle `SchemaRejected` and re-emit everything else"** — the narrowing is invisible at the type level, and a `ResolutionGate`-style combinator that introduces `ImageInputUnsupported` (a *new* concrete `CallError` the inner provider never throws) likewise *widens* the runtime error set with zero static signal. Forwarding-as-identity is clean; selective-catch and inject-new-error are exactly where "same channel" stops telling the caller the truth.

- **NEW (error model): the `Maybe`-probe relies on matching a concrete `CallError` through the existential — and the trailing normalizer must not eat it.** `Negotiated` holds `inner: Provider` (the bare marker), so under [`../provider-as-marker.md`](../provider-as-marker.md) it must first `match (self.inner) { let h: HttpProvider => h.call_with<T,U>(…) }` (the `inner_call_with` helper) — the marker has no `call_with`. Through that `HttpProvider` handle, `h.call_with<T,U>(prompt, project)` is statically typed to throw `baml.errors.CallError | baml.UnknownError`. The probe's correctness depends on the runtime refining that existential channel back to the *concrete* `SchemaRejected` in `catch (e) { let r: SchemaRejected => … }` — the same "concrete-through-interface" recovery the model promises at the consumer's catch, but here happening *inside a library combinator* across a `requires Provider` existential. It works only if (a) the concrete class survives `inner`'s own trailing `with_message<baml.errors.CallError>` normalizer unchanged — which it does, since `with_message` passes a known `CallError` through untouched — and (b) the runtime match dispatches on the concrete tag, not the static `CallError` handle. If a future provider routed its schema-rejection through `UnknownError` instead of throwing the concrete `SchemaRejected`, the `Maybe` branch would silently stop downgrading (it would re-throw via the `_ => throw e` arm) — so the whole graded layer is load-bearing on *every* provider choosing the concrete-error discipline over the escape hatch for this one failure.

## (d) Verdict: **Workable-with-additions**

The proposal nails the half of capability negotiation it was designed for: the behavioral, binary, "can it do this *kind* of thing at all" gate is a §5 `match` plus typed `catch`, and it composes with orchestration for free. That is real and clean. But this is the scenario the proposal is *named after*, and its single native mechanism — `match` on interface membership — is the wrong shape for the background's headline finding that **support is not binary.** Everything that matters about real-world negotiation (declarative pre-flight à la `supportedUrls`/LiteLLM, the Yes/Maybe/No gradient, the silent-downgrade `warnings` channel, a typed schema-rejection so a downgrade doesn't fire on a timeout) is net-new surface the proposal does not mention — though one of these, the `warnings` channel, is now *resolved-with-a-named-mechanism*: it is a product sidecar carried by `call_with` + a `ResponseMeta.warnings()` dimension (REQUIRES first-class tuples `(T, U)` + destructuring), replacing this scenario's original bespoke `Warned<T>` companion and surviving combinators instead of leaking into an out-of-band sink. One remaining addition still stresses the proposal's open questions: the declarative `Capabilities` layer needs generic-method dispatch through the existential (more than OQ-5 promises). The other pressure here — OQ-1 — is now **resolved** by the marker revision: under [`../provider-as-marker.md`](../provider-as-marker.md) `Provider` is a bare marker with no `call`, so a read-only metadata capability `requires Provider` honestly (composable + matchable) and is no longer forced to carry a degenerate `call` it can never run; `call`/`call_with` live on `HttpProvider`, which a `Capabilities`-only provider simply does not implement. Compile-time capability guarantees and live-runtime capability queries are plainly unsupported. The additions are all built *on* the spine (a new interface, a lattice enum, host probes, and concrete `CallError`-implementing error classes — `SchemaRejected`, `OpenAiHttpError`, `ImageInputUnsupported` — on the per-capability channel) rather than amending it — so the verdict is Workable, not Awkward — but "workable" here means "the proposal supplies the runtime escape hatch and you build the entire declarative-and-graded layer yourself," which is a generous read of a scenario that bears the proposal's own name.
