# Evaluation — Capability negotiation

Adversarial read of whether the proposed model expresses capability negotiation cleanly. This is the proposal's *central* scenario — §5 ("companions `match`, and fall back to `.call`") is the whole thesis of how a client discovers what a provider can do. So the bar is high and the failure modes are the interesting part. The background names four discovery mechanisms (runtime 400, declarative flags, static table, live query) and one hard truth: **"supported" is not binary.** The proposal answers exactly *one* of those mechanisms natively; the other three and the gradient are net-new.

## (a) What the proposal reuses unchanged

- **The §5 behavioral `match` is the runtime-400 + interaction-shape story, intact.** "Can this provider stream / run tools / go realtime *at all*" is answered by `match (p) { let s: Streaming => …, _ => … }` with the `_` arm deciding degrade-vs-error. `Summarize$stream` (usage §3) is the proposal's own §5 example verbatim — Streaming degrades to a buffered `.call`, Gemini (no `implements Streaming`) takes the fallback arm. Zero new machinery; this half of negotiation is genuinely free.
- **The typed `throws`/`catch` channel is the runtime-400 absorber.** A schema rejection is a `catch (e) { let r: SchemaRejected => … }` — the exact shape of the Python `except openai.BadRequestError` pattern, but as a typed error arm. `Negotiated.call` (implement §6) is built entirely from `match` + `catch`, both pre-existing.
- **Combinators wrap a Provider, so negotiation composes with orchestration.** `Negotiated` is a plain non-generic class forwarding `.call`, identical to the `Fallback`/`Retry` template (proposal §6). `Production` (usage §5) chains `Negotiated(...).with_retry(2).fallback_to(...)` with no special-casing — negotiation is "just another combinator."
- **`client` = `function -> Provider` lets the degraded twin be an ordinary sibling client.** `OpenAIPromptJson()` and `SmartExtractor()` are both clients; passing one as the `degraded` field of the other is the §3 "client: takes any Provider expression" rule, reused.
- **The existential return is, again, the mechanism *and* the limit.** Because a client returns `Provider`, `CanThisModelDoStructuredOutput` (usage §2) *must* `match` down to `Capabilities` at runtime — there is no static `.structured_output`. That is the proposal's stated §5 posture, applied honestly here.

## (b) Net-new surface it must add (each tied to a primitive)

- **`Capabilities` interface + the `Support` lattice (`Yes`/`No`/`Maybe`).** Tied to the capability-as-`requires Provider`-interface rule (§1). This is the proposal's missing third leg. §5 gives "match on the *behavioral* capability"; it has **no answer for declarative, data-shaped capability** (Vercel `supportedUrls`, LiteLLM `supports_vision`). I model it as a behavior-free capability interface whose methods are pure reads — which is idiomatic, but it is *new surface the proposal does not mention*. The `Support` enum is the load- bearing addition: a `bool` would reproduce the background's named failure ("a flag can't capture the gradient"). The `Maybe` arm is what makes the declarative layer defer to the runtime probe instead of lying.
- **`baml.schema.depth/uses_unions/uses_refs` + `baml.media.image_dims`.** Host functions tied to the `$rust_io_function` boundary. These are what let a *declarative* answer be computed *for the specific `T`/image* rather than for the model in the abstract — i.e. they are how the gradient is made checkable before the call. Without them, `Capabilities` could only return per-model constants (the stale-table failure mode).
- **`Warning` + `baml.sys.warn` (a warnings sink).** Tied to the `ExecutionContext` net-new note (§7) and to `call<T>(prompt) -> T`'s signature. The background: "silent downgrades are worse than errors," and the AI SDK returns a `warnings` array. **The proposal's `call<T>` returns a bare `T` with no room for warnings.** I thread them out-of-band through `baml.sys.warn`, which is a real concession: the warnings are not in the return type, so a caller can ignore them exactly as the background warns ("only if the caller reads them"). `Warned<T>` is sketched for a future widened path but the plain `.call` path can't use it.
- **`SchemaRejected` error.** Tied to the `type Error` channel (§1). Distinguishes "the *schema* was the problem" (downgrade-able) from "the network was the problem" (not). The proposal's single `LlmClient` error can't carry this branch, so `Negotiated` would otherwise downgrade on a timeout — a correctness bug. New error class, built on the existing channel.
- **`Negotiated` + `ResolutionGate` combinators.** Net-new *library* classes, no new primitive — `match` + `catch` + `warn`. They are the glue that turns Yes/No/Maybe into "send / refuse / probe-then-fall-back," which is the actual negotiation the proposal hand-waves as "the `_` arm decides."

## (c) Where it is awkward, leaky, or unresolved

- **OQ-5, head-on — the *graded* match needs more than membership reflection.** OQ-5 asks only whether `match (p) { let s: Streaming => … }` (interface membership) is supported. But this scenario needs strictly *more*: `cap.structured_output<T>()` is a **generic method on a runtime-existential provider**, dispatched on a `T` that itself must be reflected (`reflect.type_of<T>()`) *inside* the matched capability. The §5 `match` recovers the concrete type; does the runtime then support calling a *type-parameterized* method on it and re-reflecting `T`? If OQ-5 only guarantees membership (a `bool` test), the entire `Capabilities` layer is unsound — it depends on dispatching real generic behavior through the existential, not just testing the tag. **This scenario silently raises the bar OQ-5 sets, and the proposal does not confirm it can clear it.**

- **OQ-1, head-on — `Capabilities requires Provider` forces a meaningless `call`.** OQ-1 asks whether every capability should `requires Provider`. `Capabilities` is the case that breaks the assumption: it is **pure data, no behavior**, yet to ride the existential and be `match`-able it must `requires Provider` and therefore *is-a* Provider with a `call`. A bare capability-metadata object (LiteLLM's table is literally a dict, not a client) is forced to pretend it can run a completion. Either `Capabilities` is allowed to *not* `requires Provider` (then how does a held `client` expose it?), or every metadata record drags a `call` it will never implement. The proposal's "every capability refines `call`" framing fits Streaming/Realtime and actively misfits a read-only capability.

- **The gradient is *expressible* but the proposal's native answer is *binary*, so the whole declarative layer is bolted on.** §5's `match` returns "is-a Streaming: y/n." The background's central finding — JSON schema but only shallow, images but not at resolution, tools but not parallel — has **no native home** in the proposal. I had to invent `Support`/`Capabilities`/the gradient host probes wholesale. The proposal does not merely under-specify this; its one negotiation mechanism (`match`) is the wrong *shape* for graded support. This is the scenario the proposal is named for, and it answers ~40% of it out of the box.

- **Warnings have nowhere typed to go — the silent-downgrade failure persists.** Because `call<T> -> T` can't carry warnings, my `baml.sys.warn` sink is exactly the "array the caller might not read." The model can *record* a downgrade but cannot *make the caller acknowledge* it — the background's "worse than errors" problem is reproduced, not solved. A type-system answer (`call` returning `Warned<T>` everywhere) would ripple through every provider, every combinator, and the `client` sugar, so the proposal effectively can't adopt it without a pervasive signature change.

- **No compile-time capability guarantee — and here it actively hurts.** As in provider-diversity, `client` returns the existential, so "this client supports structured output for `Resume`" is unprovable statically; `CanThisModelDoStructuredOutput` is a runtime function returning a *string*. The escape hatch (`function … -> ConcreteProvider`) recovers a static capability but only for *one named provider* — you cannot say "any provider, but it must structured-output this `T`." Capability negotiation is precisely the place a developer wants a build-time guarantee ("don't ship a config that can't do what this function needs"), and the model can only offer a runtime probe. **Stated plainly: a compile-time capability contract is unsupported.**

- **Live-query discovery (Claude Agent SDK `q.supportedModels()`) is unmodeled.** The fourth mechanism — asking the *running runtime* what it supports — is an out-of-band, stateful, async query against a live session. `Capabilities` methods are pure/synchronous reads of static knowledge; a live query is an IO call against server-authoritative state. It would have to be a separate `throws`-ing method (`function probe_models(self) -> ModelInfo[] throws Io`), which collides with `Capabilities` being a pure read interface. The proposal has no story for server-authoritative capability state; this scenario does not invent one.

## (d) Verdict: **Workable-with-additions**

The proposal nails the half of capability negotiation it was designed for: the behavioral, binary, "can it do this *kind* of thing at all" gate is a §5 `match` plus typed `catch`, and it composes with orchestration for free. That is real and clean. But this is the scenario the proposal is *named after*, and its single native mechanism — `match` on interface membership — is the wrong shape for the background's headline finding that **support is not binary.** Everything that matters about real-world negotiation (declarative pre-flight à la `supportedUrls`/LiteLLM, the Yes/Maybe/No gradient, the silent-downgrade `warnings` channel, a typed schema-rejection so a downgrade doesn't fire on a timeout) is net-new surface the proposal does not mention, and two of those additions stress its own open questions: the declarative `Capabilities` layer needs generic-method dispatch through the existential (more than OQ-5 promises), and it is the case that makes `requires Provider` (OQ-1) actively wrong, since a read-only metadata capability is forced to carry a `call` it can never run. Compile-time capability guarantees and live-runtime capability queries are plainly unsupported. The additions are all built *on* the spine (a new interface, a lattice enum, host probes, an error variant) rather than amending it — so the verdict is Workable, not Awkward — but "workable" here means "the proposal supplies the runtime escape hatch and you build the entire declarative-and-graded layer yourself," which is a generous read of a scenario that bears the proposal's own name.
