# Capability negotiation

"Will this model accept my JSON schema / my image at this resolution / parallel tools — before I find out via a 400?" The proposal's native answer is the runtime `match` on the existential `Provider` (now a bare *marker*; interaction lives on the capabilities — `call`/`call_with` on `HttpProvider`, see [`../provider-as-marker.md`](../provider-as-marker.md)): a companion tests interface membership and either degrades (a `.stream` companion buffers an `HttpProvider.call`) or errors. That cleanly handles the *behavioral, binary* question ("can it stream/run-tools at all"), but the background's core finding is that **support is not binary** — a model takes JSON schema but only shallow, images but not at a resolution, tools but not in parallel. So this scenario shows the §5 `match` reused unchanged, then the net-new surface a graded answer forces: a declarative `Capabilities` read- interface returning a `Yes`/`No`/`Maybe` `Support` lattice (the `supportedUrls`/LiteLLM pattern), a `Negotiated` combinator that sends-on-Yes / refuses-on-No / probes-on-Maybe, a `warnings` sidecar for silent downgrades carried on the canonical `call_with` + `ResponseMeta` path (a product sidecar — not a bespoke `Warned<T>` companion), and a typed `SchemaRejected` so a downgrade doesn't fire on a network blip. `usage.baml` runs the same `Extract` function over OpenAI and Gemini, whose declarative answers diverge on the very same union type.
