# Evaluation — Scaling the catalog: deferred & searchable tools

Adversarial read of whether the proposed model ([`../../01-providers-clients-capabilities.md`](../../01-providers-clients-capabilities.md)) absorbs deferred/searchable tool catalogs, or merely relocates the cost. This is the first scenario where a provider divergence is not just *wire encoding* — it is a **capability one provider has and another structurally lacks**, and where the hard part (prompt-cache stability) cannot be made portable by hiding it under a seam.

## (a) What the proposal reuses unchanged

- **`interface Tools requires Provider`** — `begin`/`step`/`submit` and the default `run_tools` loop are reused verbatim. `SearchableTools requires Tools` is a clean refinement: it keeps the same `type Transcript` and the same four-beat loop. The dispatch seam (`ToolCall`/`ToolResult`, opaque `id`) is untouched.
- **The `step<T>(t) -> T | ToolCalls` union.** The synthetic `tool_search` call surfaces as an ordinary `ToolCall` named `"tool_search"`; the loop's existing `match` discriminates it with one extra `if`. No new control flow, no search-specific return type — search results ride back as a normal `ToolResult`.
- **Opaque, provider-owned `type Transcript`.** Load-bearing again: OpenAI's transcript carries `defer_loading`-flagged wire tools the provider pages in; Anthropic's transcript carries `loaded_names[]` + a mutated `wire_tools` it grows as searches resolve. Two completely different deferral strategies, one associated type, invisible above the seam.
- **Combinator-by-delegation.** `McpProvider` is the §6 delegation pattern applied to discovery: it wraps an `inner: Provider`, forwards `HttpProvider` (plain `call`/`call_with`) and `Tools`/`SearchableTools` by `match`ing the inner provider for each capability, and binds the transcript to the owner — exactly the `ToolFallback`/`BoundTranscript` shape from scenario 09. Per [`../../provider-as-marker.md`](../../provider-as-marker.md), `McpProvider`'s plain delegating call is now an `HttpProvider` capability (it `match`es `self.inner` for `HttpProvider` and forwards `call_with`'s projection so usage/sidecar isn't dropped), not a method on a base `Provider` — the marker carries no `call`.
- **`client` sugar + capability `match`.** `Support.search_tools(...)` is a companion that `match`es for `SearchableTools`, and crucially has a *real* degrade arm (`let tp: Tools => run_tools(flatten_catalog(...))`) — unlike `Realtime`, an honest fallback exists: ship the whole catalog. That fallback is the §5 "delivery refinement degrades to `.call`" rule, here "searchable degrades to flat tools."
- **Options-dissolve.** `defer` and `namespace` are fields on `CatalogTool`, not an options blob; `max_tokens` is still just an `Anthropic` field. No `@providers:` map needed to express "OpenAI supports defer_loading, Anthropic doesn't" — that fact is encoded by *which capability the class implements and how*.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`interface SearchableTools requires Tools`** with `begin_searchable` + default `search_tools`. Net-new capability interface. The plain `Tools.begin` takes a flat `Tool[]` and structurally assumes the whole list ships; deferral needs a different entry shape (`Catalog` + `SearchResolver`). This is the cleanest possible add — it `requires Tools`, reuses the transcript, and the default loop is a near-copy of `run_tools` with a search/dispatch split. Ties to the `requires` + default-method machinery (BEP-044/057).
2. **`class CatalogTool { tool: Tool, defer: bool, namespace: string }`, `class Namespace`, `class Catalog`.** Net-new types. The canonical `Tool` is deliberately left untouched (so every plain-`Tools` provider still works); deferral policy + namespacing discipline are *wrapped around* it. Ties to the first-class `type` primitive (the inner `Tool.parameters: type` is reused as-is).
3. **`interface SearchResolver { resolve(query) -> CatalogTool[] }`.** Net-new. This is the host primitive for *client-executed* search — the hook the model's query is dispatched through when the provider can't (or shouldn't) index the catalog itself. There is no analog in the base proposal; it is the server-vs-client search seam made explicit. **Error-model note:** `resolve` sits *on the tool loop* (the default `search_tools` calls it between `step` and `submit`), so it declares the same channel as the loop, `baml.ExtendUnknownError<baml.errors.ToolError>`. We did NOT mint a new `SearchError` interface — a resolver failure is a tool-loop failure, and reusing `ToolError` keeps the loop's `throws` uniform. The cost of that choice is below in (c).
4. **The synthetic `tool_search` `Tool` + its reserved name.** Net-new convention (`SearchableToolsOps.search_tool()`), with `parameters: reflect.type_of<SearchQuery>()`. This reuses the `type` primitive but introduces a *reserved tool name* the loop must special-case — a small but real piece of protocol the proposal didn't have.
5. **`reflect.type_to_json_schema` / `type_to_gemini_openapi`** are reused from scenario 09, but searchable mode needs them invoked *lazily* (only on loaded tools), which the host bridges (`splice_loaded_schemas`, `search_result_payload`) now own. No new reflection primitive, but a new *call site discipline*.

## (c) Where it is awkward, leaky, or unresolved

**The big one: cache-prefix stability is not portable, and the model can't say so.** On OpenAI the deferred schemas are on the wire but never enter the cacheable prefix until searched, so a turn that doesn't page anything in keeps a byte-stable prefix and hits cache. On Anthropic the library *emulates* deferral by withholding schemas and **splicing them into `wire_tools` when a search resolves** — which mutates the leading tool block and **invalidates the prompt cache on exactly the turns that load tools**. Both providers implement `SearchableTools`, both type-check identically, and the app code is byte-for-byte the same — but the *cost profile diverges sharply* and **nothing in the type system or the capability set expresses that divergence.** The proposal's "capability is a runtime promise" (§5) degrades here into "capability is present but its cost is silently provider-dependent." An app author who tuned `defer` flags for OpenAI's cache behavior gets a different bill on Anthropic with zero compile-time or runtime signal. The seam hides the mechanism *and* the economics, and only the economics matter for this feature.

**Open Question 3 (the request side is HTTP-specific) bites directly.** `tool_search`
+ `defer_loading` are *request-construction* features: they live in how `build_request` / `begin` lays out the `tools` array, and there is no first-class place to express "this part of the request is deferrable." We smuggled it in as a `CatalogTool.defer` field that the provider *interprets*, but the proposal has no notion of a deferrable request fragment — so OpenAI's native deferral and Anthropic's emulated deferral are two unrelated code paths that happen to share an interface. OQ3 asks whether the request side wants its own associated type; this scenario is concrete evidence that it wants *more than that* — it wants a way to mark request content as load-on-demand, which neither `baml.http.Request` nor `PromptAst` models.

**Open Question 5 (capability `match` over an existential) is fine but load-bearing twice.** `McpProvider.begin_searchable` does `match (self.inner) { let st: SearchableTools => ... }` to decide between native page-in and emulated discovery, and `inner_as_tools` does a second `match` to recover the `Tools` view for transcript binding. This is exactly the runtime membership test OQ5 needs confirmed — and the double `match` (once for `SearchableTools`, once for `Tools`) is mildly awkward: a `SearchableTools` value *is-a* `Tools` by `requires`, but we still re-`match` to get a `Tools`-typed binding for `McpTranscript.owner`. If `requires` gave us upcasting without a re-`match`, this would be one line shorter.

**Server-authoritative state is unrepresentable — and that's the heart of MCP.** MCP's catalog lives on a *remote server*; `tools/list` can change between turns (a server adds/revokes a tool), and the model may have a stale view. The proposal's `Transcript` is provider-owned and opaque, which is the right home — but there is **no way to express "this capability's source of truth is external and may drift."** `McpResolver.resolve` reconciles two registries (remote `tools/list` + the app's local `RegistryResolver`) by `dedup`, but that reconciliation is hand-rolled host code, not anything the model gives us. The background's "client-side search must reconcile two registries" hazard is real and the proposal offers **no primitive** for it — drift surfaces as an empty search or a phantom call, exactly as warned, and we can only paper over it in `$rust_io_function` bodies.

**Namespacing is a convention, not a guarantee.** We fold the namespace into the wire tool name (`"billing.process_refund"`) via `qualify`, and put discriminative descriptions on `Namespace`. But nothing *enforces* the "<~10 tools per namespace, discriminative descriptions" discipline that the background says search quality lives or dies on. The proposal can carry the metadata; it cannot lint it. That's arguably out of scope — but it means the one thing that determines whether search *works* is unmodeled.

**The degrade arm quietly defeats the feature.** `Support.search_tools`'s fallback arm is `run_tools(flatten_catalog(catalog))` — i.e. if the provider isn't `SearchableTools`, ship every schema. That's an *honest* fallback (the tools still work) but it silently throws away the entire point (token + cache savings). Compared to `Realtime`'s fallback (which errors loudly), this one *succeeds while doing the expensive thing*, which is arguably worse: the app author gets correct results and a surprise bill, with no signal that deferral didn't happen. Capability-as-runtime- promise has no way to say "I'll do this, but not cheaply."

**The error model: client-executed search collapses an app failure and a provider failure onto one channel — NEW.** The per-capability `baml.ExtendUnknownError<CapErr>` model (which replaces the old single `baml.errors.LlmClient`/`type Error` channel) is a clean fit for the *plumbing* of this scenario: every method on the tool loop — `begin_searchable`, `step`, `submit`, the default `search_tools`, and the provider statics under them — declares `baml.ExtendUnknownError<baml.errors.ToolError>`, foreign transport/JSON failures funnel through one trailing `catch (e) { _ => throw baml.UnknownError.with_message<baml.errors.ToolError>(e, "…") }`, and the "inner provider is not tool-capable" arms in `McpProvider` throw the canonical `baml.errors.Unsupported` (legal on the `ToolError` channel because it implements all four capability interfaces). But searchable tools force a *new* error-model awkwardness the plain tool loop never had: **`SearchResolver.resolve` is APP code that throws on a LIBRARY capability channel.** `RegistryResolver` and `McpResolver` are written by the application, yet because the default loop calls `resolve` between `step` and `submit`, their failures are typed `baml.errors.ToolError` — the *same* interface a provider raises for a wire-side tool failure. At the consumer `catch`, `let e: baml.errors.ToolError => …` cannot tell "the model's search query hit my registry and my ranking host-function panicked" from "Anthropic returned a malformed tool_use block." The classifiers (`is_network_error` / `is_rate_limit`) are provider-shaped vocabulary that mean nothing for an in-process registry lookup, so an app-side resolver failure either masquerades as a provider error or falls through to `baml.UnknownError` — and there is no `is_resolver_error()` to branch on. The old single-channel model hid this by having *one* error type for everything; the new model promised precise triage, and here the precision stops exactly at the app/library boundary the resolver straddles.

**`McpResolver` swallows the one classifiable error this scenario actually has.** A dead MCP server is the canonical `is_network_error() -> true` case — but `McpResolver.resolve` catches `search_servers`' failure with `_ => { []; }` so "a dead server must not abort the whole search." That suppression is correct for availability, but it means the *one* failure mode that the `baml.errors.ToolError` classifiers were designed to surface (a network-down remote catalog) never reaches the channel at all: drift degrades to an empty search, exactly as the background warns, and the typed-error machinery is bypassed below the seam. So the error model is simultaneously too coarse (resolver failures collapse onto `ToolError`) and unused (the network failure that *would* classify cleanly is swallowed). Neither is a model bug — both are honest consequences of client-executed search living on a provider-shaped error channel.

## (d) Verdict: **Workable-with-additions**

The interaction *shape* is a clean fit: `SearchableTools requires Tools` reuses the transcript, the loop, the dispatch seam, and the combinator-by-delegation pattern with almost no friction, and the synthetic-`tool_search`-as-ordinary-`ToolCall` trick lets one default loop serve both hosted and client-executed search. The net-new surface (`SearchableTools`, `Catalog`/`Namespace`/`CatalogTool`, `SearchResolver`) is additive and idiomatic — it `requires` its way onto the existing stack rather than forking it. The per-capability error model rides along cleanly for the plumbing (everything on the loop declares `baml.ExtendUnknownError<baml.errors.ToolError>`; foreign errors normalize through `baml.UnknownError`; capability-negotiation uses `baml.errors.Unsupported`) and needs NO net-new error interface — but it exposes a fresh seam: `SearchResolver` is app code throwing on a library capability channel, so resolver failures and provider failures are indistinguishable at the `baml.errors.ToolError` interface, and the one cleanly-classifiable failure (a dead MCP server) is deliberately swallowed below the seam. **But** the proposal genuinely cannot express the two things that make this feature worth shipping: (1) **prompt-cache cost is provider-divergent and invisible** — OpenAI's native deferral and Anthropic's emulated deferral are the same type with wildly different economics, and there is no compile-time or runtime channel to surface that (OQ3 territory, and worse than OQ3 frames it); and (2) **server-authoritative, drifting catalog state** (MCP's whole premise) has no primitive — reconciliation is hand-rolled host code. The model absorbs the *plumbing* of deferred tools cleanly and fails to absorb their *reason for existing* (cost) and their *hardest case* (remote, mutable registries). Workable, because everything compiles and runs and an app can use it portably; with-additions, because portability here is a trap unless the model grows a way to talk about the cost a capability incurs.
