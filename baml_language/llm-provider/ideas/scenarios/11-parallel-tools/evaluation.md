# Evaluation — Parallel tool calls

Adversarial read of whether the proposed model expresses "run the tool calls a turn emitted concurrently and feed all results back together."

## (a) What the proposal reuses unchanged

The big claim of §7 is that *dispatch policy lives above the `ToolCall`/`ToolResult` seam, and wire threading lives below it.* Parallel tool calls is the cleanest possible confirmation:

- **`Tools` (begin/step/submit) is untouched.** The providers in `implement.baml` are copied from scenario 09 with no change to their tool loop. Anthropic still re-orders by `pending_ids`; Gemini still synthesizes ids for same-function fan-out. Parallelism happens entirely between `step` returning `ToolCalls` and `submit` receiving `ToolResult[]`. The provider is a spectator.
- **`run_tools` (the default loop in `_conventions.md`) is untouched.** It still calls `ctx.dispatch(calls.calls)` verbatim. We never override `run_tools` for this scenario — unlike scenario 10 (bounded loops), which had to. Parallelism is *below* `run_tools`, inside the one method it already delegated to.
- **The `ToolCall.id` correlation contract carries the determinism.** Because the loop never interprets `id`, the dispatcher can run calls in any order and stamp results with the original id; the provider re-keys (OpenAI/Anthropic by id, Anthropic additionally by recorded position, Gemini by synthetic id→name). The proposal's "id is OPAQUE to the loop" line is exactly what lets the writer emit in call order while work runs out of order.
- **Combinators compose orthogonally.** `ResilientTools()` (fallback) and `parallel_ctx()` (dispatch) coexist with zero coupling — client returns a `Provider`, ctx carries dispatch policy. Two independent axes, as the proposal's §6 combinator story predicts.

## (b) Net-new surface it must add (each tied to a primitive)

1. **`Tool.effect: ToolEffect` annotation** — tied to the `Tool` primitive (proposal §7 "Net-new flags"). The background is explicit: *"there is no standard tool metadata that marks a tool read-only,"* so no dispatcher can decide what is safe to fan out. We add the missing metadata as a field on `Tool`, defaulting to `Write` (safe). This is genuinely new surface on a type the proposal already flagged as new.

2. **`Dispatcher` interface + `ExecutionContext.dispatch` delegating to it** — tied to `ExecutionContext.dispatch` (proposal §7: "ExecutionContext needs a `dispatch`"). The proposal gave `dispatch` as a *fixed method*. To make parallel/sequential/effect-aware/limited pluggable without touching providers, `dispatch` must become a strategy object. This is a small generalization of an already-net-new method, not a new concept — but it IS new surface.

3. **The slot-array helpers** (`ParallelHelpers.empty_slots`/`unwrap_slots`) — small `$rust_io_function` utilities for the effect-aware scatter/gather. Tied to the host boundary (`$rust_io_function`, like `PrimitiveClient`). These are array plumbing, not concurrency.

   **Concurrency is NOT net-new.** Structured concurrency is a SHIPPED first-class language feature (BEP-034 — `baml_std/baml/ns_spawn`, `ns_future`): `spawn { body }` returns a `baml.future.Future<T,E>` immediately, `await` yields the value or re-throws, and the combinators `baml.future.all` (Promise.all — cancels losers on first failure) / `all_complete` (losers finish) join them. So fan-out is "a list of spawns" and the join is `baml.future.all`; there is no `baml.async.gather`/`gather_until_error` to invent. The earlier draft's claim that "BAML has no concurrency surface today at all / this is the largest net-new ask" was simply **wrong** — the surface exists and these strategies use it directly. The mapping in this scenario:
   - run-all (order-preserving, per-call failure capture) → `settle_all`: each call runs in its own `spawn` that **catches its own failure inside the spawn body** (so the future is infallible), and `baml.future.all` joins them in input order. No "allSettled" combinator is needed because the catch-inside-spawn turns every future into a guaranteed `Settled<T>`.
   - stop-on-first-error → `baml.future.all` directly: on the first failing call it cancels the in-flight siblings and re-throws the original `ToolError` unchanged. No host primitive, no error-channel fudging — `await` surfaces the failing `invoke_one`'s concrete `ToolError` on this method's declared channel.
   - rate-limit cap → `baml.spawn.TaskGroup.new(limit)` (the real "Semaphore"): every call's `spawn` is enrolled in the group via `spawn with baml.spawn.options(group = g)`; at most `limit` run concurrently and the rest queue FIFO, each `spawn` still returning its Future immediately.

4. **`Settled<T>`** — a plain data record (`ok: T?`, `failure: string?`) for the run-all per-task ok/failure union. NOT a host primitive and NOT tied to any invented `gather`: it is just the value a `spawn`'s catch arm produces so the future is infallible and `baml.future.all` never throws. Run-all wants a per-task union rather than a throwing call because the whole point is *not* to propagate one failure.

## (c) Where it is awkward, leaky, or unresolved

- **Run-all returns; stop-on-first-error THROWS — asymmetric seam.** A `Dispatcher` returns `ToolResult[]`. Run-all always can (a failure is just an error result). Stop-on-first-error *cannot* produce a per-call result array when it aborts — so `StopOnFirstErrorDispatch.dispatch` throws instead. That means the two policies have visibly different control-flow contracts through the same interface method, and the app's call site needs a `catch` for one but not the other (see `run_strict_pipeline` vs `run_research_parallel` in `usage.baml`). The interface type doesn't capture this; it's a runtime convention. Mildly leaky. Under the error model the asymmetry is *also* invisible in the channel: every `dispatch` declares `baml.ExtendUnknownError<baml.errors.ToolError>` whether it can throw a tool failure (stop-on-error) or never does (run-all). The channel says "this *might* throw a `ToolError`"; it cannot say "this *will/won't*." So the type still doesn't distinguish the two policies. Note this asymmetry is a property of the `Dispatcher` *interface*, not of concurrency: the stop-on-error body is a clean `await baml.future.all(...)` that re-throws the failing `invoke_one`'s **concrete** `ToolError` unchanged — `await` re-throws the future's error verbatim, so the typed channel survives the fan-out untouched. There is no concurrency primitive in the middle to launder or re-wrap the error, so the earlier draft's "a generic concurrency primitive is forced to name a specific capability's error interface" leak **does not exist**: `baml.future.all` is generic over `Future<T,E>` and propagates `E` as-is. The only honest thing the channel cannot encode is "this strategy will always succeed" vs "this one may throw" — a `Dispatcher`-interface limitation, identical to any interface method that some implementors never throw on.

- **Effect-gating is sequencing, not a real gate — the proposal cannot express the actual requirement.** The background asks for *"charge only if the email succeeds."* `EffectAwareDispatch` can only *sequence* writes in relative order; it has no cross-call transactionality, no rollback, no "commit B iff A succeeded." Expressing a true gate would need the model to NOT emit both calls in one turn (a model-side control), or a dispatcher that can abort-and-undo — neither of which the `ToolCall`/`ToolResult` seam can represent, because a result must be produced for every call the model emitted or the wire protocol breaks. **This is a plain limitation: the seam guarantees one result per call, which is structurally incompatible with "don't run the second call."** Honest verdict: unsupported at the dispatch layer; it belongs to a different control (turn-shaping / approval), out of scope here.

- **No compile-time guarantee that a fanned-out tool is actually read-only.** `Tool.effect` is an author assertion. Nothing checks that the `search_web` handler is pure. This is the same runtime-promise posture the proposal accepts everywhere (capability is a runtime `match`, not a static type), so it is consistent — but a reviewer should note the safety property is unenforced.

- **Open Question #5 (capability `match` over an interface-existential) is load- bearing here.** `EffectAwareDispatch` doesn't match on capabilities, but the whole scenario assumes `match (reg.effect_of(c)) { ToolEffect::ReadOnly => ...}` and the combinator forwarding from scenario 09 (`let tp: Tools => ...`) work at runtime. If value-level reflection can't test interface membership at runtime, the `Fallback`-over-`Tools` composition in `run_resilient` doesn't hold. We depend on #5 resolving "yes."

- **Concurrency needs NO host-body escape hatch (Open Question #7 is not stressed here).** The earlier draft worried that the concurrency primitives were `$rust_io_function` bodies taking BAML closures and scheduling them on the host — "the sharpest unresolved dependency." That worry is moot: fan-out is expressed in the *language* (`spawn`/`await`/`baml.future.all`/`baml.spawn.TaskGroup`, all BEP-034), not through a native body that drives BAML callbacks. The runtime already schedules `spawn`-ed bodies under its async executor; no closure crosses a `$rust_io_function` boundary to be run concurrently. The only `$rust_io_function`s left in this scenario are leaf I/O and array plumbing (`Registry.invoke_one`, `ParallelHelpers.*`, the wire encoders), exactly the OQ7 shape the rest of the model already relies on — nothing stronger.

- **Cache stability is defended by convention, not by the type.** The "single writer emits in input order" discipline lives inside each `dispatch` body and inside Anthropic's `submit` re-order. Nothing in the `Dispatcher` interface *forces* a strategy to preserve order; a careless third-party dispatcher that pushed results as they resolved would silently defeat prompt caching and break Anthropic positional matching. The proposal gives no place to encode "must be order-preserving" as a contract.

## (d) Verdict

**Workable-with-additions.**

The proposal's central bet — that dispatch policy is separable from wire threading at the `ToolCall`/`ToolResult` seam — pays off almost perfectly for parallelism: not one line of provider or `run_tools` code changes, and the four strategies plus the rate limiter all slot in as `Dispatcher` implementations behind the single `ctx.dispatch` call the proposal already specified. That is a strong result. The additions are real but bounded and well-localized: a `Tool.effect` field (filling a gap the background itself names) and a `Dispatcher` strategy generalization of an already-net-new method. **Concurrency is NOT among the additions** — structured concurrency (`spawn`/`await`/`Future`, `baml.future.all`/`all_complete`, `baml.spawn.TaskGroup`, `CancelToken`) is a shipped first-class language feature (BEP-034), so fan-out is a list of spawns, the join is `baml.future.all`, the rate-limit cap is a `TaskGroup`, and stop-on-error is `baml.future.all`'s built-in loser-cancellation — none of it is a host primitive the proposal must add, and none of it depends on Open Question #7. The model still cannot express the genuinely cross-call requirement ("charge only if email succeeds"): the seam's "one result per emitted call" invariant is structurally incompatible with it, so that requirement is honestly out of scope rather than awkwardly forced. Net: the interface model absorbs parallel dispatch cleanly using language-level concurrency that already exists; the only new surface is one `Tool.effect` annotation (unenforceable) and the `Dispatcher` strategy generalization.
