# BEP-044 Interfaces - Implementation v2

Written 2026-05-20 after rereading the updated `README.md` and the prior
`IMPLEMENTATION_PLAN.md`. This document supersedes the old implementation plan.

The old plan assumed that interface fields are redeclared inside each
`implements` block and become qualified runtime fields such as
`Serializable.id`. The updated README changes that model substantially:
interface fields are satisfied by ordinary class fields, optional `as` links
map interface field names to class field names, and `.as<T>` is the explicit
upcast/disambiguation mechanism.

## Executive Summary

The current branch has a useful amount of interface machinery, but much of it
implements the older qualified-field design. The main implementation job is to
replace the "interface fields become extra class fields" model with a flat class
field model plus an interface-field link table.

Keep and refine:

- The lexer/parser entry points for `interface`, `implements`, top-level
  `implements I for T`, and `requires`.
- The rough HIR/TIR split, interface registry, method dispatch lowering, and
  default method support.
- Existing diagnostics for duplicate interfaces, missing required methods,
  field type mismatch, ambiguous interface methods, and invalid `default`.

Replace or significantly change:

- Fields inside `implements` blocks. They should become invalid syntax or a
  lowering diagnostic, depending on the parser recovery strategy.
- Qualified construction and runtime fields such as `Foo.(I.bar)` or
  `Interface.field`.
- Bare aliases for interface fields generated by TIR/MIR/emitter.
- `obj.Interface.method` / `obj.Interface.field` as the primary projection
  syntax. The README now specifies `.as<Interface>`-style upcasts via
  `.as<T>`.
- Runtime-ish `Self` substitution. `Self` is a type-level alias with special
  static call rules, not a runtime interface mechanism.
- Interface closure in `class_implements`. Implementors must explicitly
  implement required parent interfaces.

## Current Branch Snapshot

Already present:

- Lexer/parser tokens and CST nodes for `interface`, `implements`, top-level
  `implements I for T`, `requires`, and old `extends` aliasing.
- AST/HIR structures for interfaces and implements blocks.
- LSP checks for duplicate implements, missing required methods, missing fields,
  field type mismatch, conflicting interface fields, duplicate method
  signatures, and `default` misuse.
- TIR registry and subtype checks for interface `requires`.
- Interface method resolution and MIR lowering through type-tag based dispatch.
- Emitter support for interface fields and methods under the old qualified-slot
  representation.
- Broad tests in `crates/baml_tests/tests/interfaces.rs` and LSP syntax fixtures.

Known stale behavior:

- `ImplementsBlockDef.fields` stores field declarations inside `implements`
  blocks. The README now forbids implementing field-bearing interfaces by adding
  fields inside the block.
- Top-level `implements I for T` is merged into a local class when `T` names a
  class, but primitive/external field-free implementations are not preserved as
  first-class impl records.
- TIR/MIR/emitter include interface fields as extra runtime slots with qualified
  names, then add bare aliases when unambiguous.
- Construction accepts or expects interface-qualified field names in places where
  the README now requires ordinary class field names.
- `requires` is stored in fields named `extends`, which invites continued
  confusion between interface requirements and generic bounds.
- `Self` is substituted to the enclosing type name during lowering. That loses
  the information needed for the README's interface-receiver restrictions.
- The registry currently records a transitive closure of class implements. This
  hides the README rule that a class must explicitly implement every required
  interface.
- `int <: float` still appears in structural subtyping. The README says this is
  not implicit; `int <: bigint` is the intended widening once `bigint` exists.

## Target Semantic Model

### Interface Fields

Interface fields declare the shape an implementor must expose through that
interface:

```baml
interface Named {
  name string
}

class Person {
  name string

  implements Named {}
}
```

The class owns the storage. The interface owns a view over that storage.

Validation rules:

- Every interface field must resolve to exactly one class field.
- An empty `implements I {}` auto-links by exact name when the class has a field
  with the same name and exact type expression.
- An explicit link inside an implements block uses
  `interface_field as class_field`.
- The linked class field type must exactly match the interface field type after
  normal type-name resolution. Do not allow field covariance.
- A class field may satisfy multiple interface fields if each link is exact.
- Concrete class construction uses class field names only.
- Access on a concrete-typed value uses class field names.
- Access through an interface-typed value uses interface field names and resolves
  through that value's implementation link.

Invalid:

```baml
class Person {
  implements Named {
    name string
  }
}
```

The old syntax above must report a targeted diagnostic explaining that interface
fields are implemented by class fields or `field as class_field` links.

### Out-of-Body Implementations

Top-level implementations remain useful for primitives and external nameable
types:

```baml
interface ToJson {
  to_json() string
}

implements ToJson for int {
  to_json() string { ... }
}
```

Rules:

- Only concrete, nameable target types can be implemented out-of-body.
- Interfaces with required fields cannot be implemented out-of-body.
- Out-of-body impls should not merge into local class declarations. They should
  be represented as implementation records and registered during TIR package
  construction.
- In-body and out-of-body duplicate implementations for the same concrete type
  and interface are errors.
- Orphan/coherence rules need one diagnostic code. The current branch already
  uses E0126 for "out-of-body implements field interface", while the README also
  references E0126 for orphan rules. Pick one allocation before updating
  snapshots.

### Requires

`requires` is the interface relationship. `extends` should be reserved for
generic bounds.

```baml
interface Dog requires Animal {
  bark() string
}

class Poodle {
  implements Animal {}
  implements Dog {}
}
```

Rules:

- `Dog <: Animal` when `Dog requires Animal`.
- Values typed as `Dog` expose `Animal` fields and methods.
- A concrete implementor must explicitly implement every required parent
  interface. Do not silently add parent implementations through registry closure.
- Duplicate or conflicting required methods should be caught on the interface
  definition.
- `requires` cycles are invalid.
- Consider continuing to parse `extends` temporarily only as a compatibility
  alias with a diagnostic, then remove it when fixtures have moved.

### Upcasting and `.as<T>`

`.as<T>` is an explicit type projection, primarily for interface upcasts and
method disambiguation:

```baml
let animal = dog.as<Animal>
let sound = pet.as<Dog>.speak()
```

Rules:

- `.as<I>` is valid when the receiver's static type is a concrete type that
  implements `I`, or an interface type that is a subtype of `I`.
- `.as<I>` must not downcast from a supertype interface to a subtype interface.
  Use `match` / `is` style refinement for that.
- `.as<Concrete>` must not downcast an interface value to a concrete type.
- `.as<T>` should produce a value with the projected static type. Runtime
  representation can be erased to the same value plus static type information in
  MIR.
- Method ambiguity should be resolved by `.as<I>.method()`, not by
  `value.I.method()`.
- Field access after upcast uses the projected interface field names.

### Subtyping Safety

Subtyping should be nominal for interfaces and conservative for mutable or
object-bearing values.

Rules:

- Concrete type `C` is a subtype of interface `I` only when `C` explicitly
  implements `I`.
- Interface `A` is a subtype of interface `B` only when `A == B` or
  `A requires B` transitively.
- Do not infer `A <: B` because some concrete class implements both.
- Do not accept a supertype and downcast it to another type in a way that permits
  mutation through an unsafe alias.
- Interface field types are exact. `class.field: Sub` does not satisfy
  `interface.field: Super`.
- Revisit generic/list/map variance. The README's safety note implies that
  mutable or object-containing containers should be invariant unless a specific
  immutable/read-only model is proven.
- Remove implicit `int <: float`. Add or preserve only the README-approved
  widening behavior (`int <: bigint`) once `bigint` is represented in the type
  system.

### Self

`Self` is compile-time, not runtime.

Rules:

- `Self` is valid only inside an interface or class declaration.
- In an interface method, `Self` denotes the eventual implementing concrete type.
- The receiver `self` counts as a `Self` parameter.
- A method with only the receiver as `Self` may be called on an interface-typed
  value.
- A method with additional `Self` parameters may be called only when the receiver
  is concrete-typed, because the compiler must know the other `Self` arguments
  are the same concrete type.
- A method returning `Self` returns the concrete type when called on a
  concrete-typed receiver and the interface type when called on an
  interface-typed receiver.
- Do not lower `Self` by eagerly replacing it with the enclosing interface name.
  Keep enough information in TIR method signatures to apply call-site rules.

## Implementation Phases

### Phase 0 - Lock the Spec With Failing Tests

Add tests first for the updated README model. It is fine for these to fail until
later phases land.

Focus on:

- Class fields auto-satisfy interface fields.
- `field as class_field` links.
- Field declarations inside `implements` are errors.
- Out-of-body field-bearing interfaces are errors.
- Field-free out-of-body primitive impls are accepted.
- `.as<I>` upcasts work and downcasts fail.
- `Self` static call rules are enforced.
- Required parent interfaces must be implemented explicitly.
- Old qualified construction and member syntax no longer passes.

### Phase 1 - Parser and Syntax Model

Files:

- `crates/baml_compiler_lexer/src/tokens.rs`
- `crates/baml_compiler_parser/src/parser.rs`
- `crates/baml_compiler_syntax/src/syntax_kind.rs`
- `crates/baml_compiler_syntax/src/ast.rs`

Work:

- Add `as` as a contextual keyword or token where needed.
- Extend `implements` block parsing to recognize field links:
  `interface_field as class_field`.
- Stop treating field declarations inside `implements` as valid declarations.
  Either parse them into an error node with recovery or lower them into a

- Add parser support for member-style generic projection `.as<T>`.
- Decide whether `.as<T>` is a property-like expression (`x.as<I>`) or requires
  call parens (`x.as<I>()`). The README uses `.as<T>` syntax, so prefer no
  required parens.
- Keep existing generic-call parsing intact for normal methods.

### Phase 4 - TIR Type System and Member Resolution

Work:

- Change the interface registry to track direct implementations separately from
  required-interface relationships.
- Register top-level primitive/external implementations.
- Build an implementation field-link table:
  `(concrete_type, interface_type, interface_field) -> class_field`.
- For in-body impls, derive auto-links from the target class fields.
- For out-of-body impls, reject field-bearing interfaces before registering
  field links.
- Update `lookup_class_fields` and `class_all_fields_ordered` so they return
  only actual class fields.
- Update interface member resolution so interface field access consults the
  field-link table instead of qualified class fields.
- Remove qualified construction support from
  `qualified_interface_field_for_construction` or make it diagnostic-only during
  migration.
- Add an expression/type form for `.as<T>` and enforce valid upcast rules.
- Replace `Self` eager substitution with an explicit type form or method
  signature flag.
- At call sites, specialize `Self` based on concrete receivers and collapse
  return `Self` to the interface type for interface receivers.
- Revisit `is_subtype` and `is_subtype_structural`:

### Phase 5 - MIR and Emitter

Files:

- `crates/baml_compiler2_mir/src/lower.rs`
- `crates/baml_compiler2_emit/src/lib.rs`

Work:

- Stop emitting interface fields as separate qualified runtime fields.
- Preserve only class-owned fields in class layouts and generated schemas.
- Lower interface field access by resolving to the linked class field at the
  call/member site.
- Lower `.as<I>` as a static type projection. It should not allocate, copy, or
  mutate the runtime value.
- Keep interface method dispatch through type tags, but update ambiguity
  resolution to flow through `.as<I>`.
- Ensure default method calls still dispatch correctly after the projection
  change.
- Remove emitter aliases for unambiguous interface field names. Concrete class
  schema should not grow interface-owned fields.

### Phase 6 - Cleanup and Compatibility Removal

Work:

- Remove old `implements`-block field fixtures once replacement diagnostics are
  snapshot-tested.
- Remove or deprecate `obj.Interface.member` syntax after `.as<I>` tests pass.
- Rename internal `extends` fields/comments to `requires`.
- Delete dead helper paths that only existed for qualified field construction.
- Update README examples or comments if any test-driven wording reveals

## Diagnostics Plan

Update existing diagnostics:

- E0113 MissingRequiredInterfaceMethod: keep, but include required interface
  chain when the method comes from a parent.
- E0116 InterfaceFieldTypeMismatch: keep, but report interface field span and
  linked class field span.
- E0124 MissingInterfaceField: keep or repurpose for missing class field/link.
  Message should suggest adding a class field or `field as class_field` link.
- E0125 AmbiguousInterfaceMethod: keep for methods only.
- E0126: resolve ID conflict between orphan/coherence and out-of-body
  field-bearing interface.

Add or split diagnostics:

- InterfaceFieldDeclaredInImplementsBlock: old field syntax inside an
  `implements` body.
- UnknownInterfaceFieldInLink: left-hand name in `field as class_field` is not
  declared by the interface.
- UnknownClassFieldInLink: right-hand name does not exist on the class.
- DuplicateInterfaceFieldLink: same interface field linked multiple times.
- OutOfBodyImplementsFieldInterface: top-level implementation targets an
  interface with fields.
- InvalidOutOfBodyImplTarget: target is not a concrete, nameable type.
- MissingRequiredParentInterface: class implements child but not required
  parent.
- InvalidInterfaceUpcast: `.as<T>` target is not a valid supertype projection.
- InvalidInterfaceDowncast: `.as<T>` attempts a runtime-refinement/downcast.
- AmbiguousInterfaceProjection: generic or duplicate implementation makes
  `.as<T>` non-unique.
- SelfOutsideType: `Self` appears outside class/interface.
- InvalidSelfCallThroughInterface: additional `Self` parameters require a
  concrete receiver.
- AmbiguousInterfaceField: field ambiguity should not be reported as method
  ambiguity.

Message improvements:

- Prefer wording that names both sides of a field link:
  "`Named.name` is linked to `Person.display_name`, but the types differ".
- For missing fields, avoid telling users to redeclare fields inside
  `implements`.
- For `.as<T>`, say whether the problem is non-implementation, downcast, or
  invalid target.
- For required parents, point to the `requires` clause and the class impl block.

## Open Decisions

- Should `extends` on interfaces remain a temporary alias with a diagnostic, or
  become an immediate parse/lower error?
- Which diagnostic ID should own orphan/coherence errors versus field-bearing
  out-of-body implementations?
- Is `.as<T>` a first-class expression that can be assigned to variables, or is
  it only legal before member access? The implementation should prefer
  first-class expression typing because it matches normal upcasts and keeps the
  model simple.
- Should `obj.Interface.member` remain as a compatibility fallback for one
  release, or fail immediately once `.as<I>` is implemented?
- `bigint` is not currently represented in the obvious type code paths. Is
  adding `bigint` part of BEP-044, or should this plan only remove
  `int <: float` and leave `int <: bigint` to a numeric-types change?
- Container variance needs a final policy. The safety text argues for
  invariance unless the compiler can prove immutable/read-only usage.
