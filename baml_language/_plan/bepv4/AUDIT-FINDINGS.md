# BEPv4 design audit — 2026-07-30

Multi-agent audit of the BEPv4 design (`_plan/bepv4/`), the `baml_std/ai` stdlib, and the
`ns_ai_scenarios` corpus. 10 dimension auditors (two hands-on: build a custom provider from
scratch; hand-roll a custom runner loop), 87 raw findings, triaged to 24, each adversarially
verified with `target/debug/baml-cli` (verifiers had to *attempt* every "not doable" claim
before confirming). Result: **22 confirmed, 2 refuted**. Full per-finding evidence with
file:line cites and repro commands is in the appendix below.

Note on timing: this ran against the working tree of `aaron/custom-llm-providers-v4` on the
evening of Jul 30; two findings were partially fixed *mid-audit* (`ai.output_fingerprint<T>()`
appeared in `execution/task.baml`, and `bridges.baml`'s unqualified `AgentProvider` was
corrected + CLI rebuilt). Verifiers re-tested against the fixed binary; severities reflect the
post-fix state.

## The headline question: can users escape the framework?

| Escape hatch | Verdict |
| --- | --- |
| **Custom provider** (`AgentProvider`) | **Yes, as of tonight** — a from-scratch provider with zero `ns_internal` refs passes end-to-end using the new `ai.output_fingerprint<T>()`. But it's a trap-lined path: the `Conversation` interface's documented `null` fingerprint default *guarantees* a runtime failure (F0), `render_shorthand` panics unclassified on malformed strings (F0), delegating wrappers hit the instance-ownership wall (F8), and there is no "implement a provider" page or conformance suite (F7, F9). |
| **Custom runner** (`ai.Runner`, hand-rolled loop) | **Yes** — an auditor built and ran a full custom `begin`/`step`/`submit` loop with interleaved app logic on public primitives. But every piece of the stock Agent's correctness scaffolding (batch validation, correlation, usage arithmetic, HTTP classification, render recipe) is `ns_internal`, so custom runners must copy-and-drift (F7). |
| **Custom retry/routing policy** | **Partially** — `retry_if` exists but the gate overrules it: transport/5xx failures are categorically un-retryable through `ai.retry` (F3); custom policy means writing your own wrapper provider (workaround verified, F3/F8). |
| **Custom streaming provider** | **No.** The one genuine *critical*: `StreamingProvider` must return the closed concrete `baml.llm.Stream` whose fields are Rust-side handles; no fake exists; reliability wrappers strip streaming; OpenAI (the docs' default) doesn't even implement it (F4, F16). |
| **MCP-style dynamic tools** | **Yes** — the "one static function per remote tool" claim was **refuted**: per-tool closures over `tool_from_json_schema` work. |
| **Own application/session logic** | Mostly, with three real walls for conversational apps: append is user-role-plain-text only (F19), there's no way to read back what the model said/did per turn (F20), and observer events can't support real telemetry (F21). |

## Priority clusters

**P0 — safety limits that silently don't work**
- F2: `ai.Budget.max_cost_usd` never trips — no adapter reports `cost_usd`, so the check compares `0.0` forever. Unbounded real-money spend behind a documented cap. (Token-priced workaround via `prepare_step` verified.)
- F14+F3+F15: the reliability story is inverted end-to-end — default `ai.retry` replays exactly the failures the docs say never to replay (Refused/InvalidRequest/ParseFailed) while never replaying the one class that usually helps (transport/5xx); no backoff and `retry_after_ms` is consumed nowhere; and the legacy `baml.llm` retry/fallback/round-robin stack still runs *underneath* `ai.retry` with no effects gate (5×3 = 15 requests per step is expressible by accident).

**P1 — core-loop foot-guns**
- F6: direct calls don't implement the documented `IncompleteRun` contract (bare `UnknownError`, conversation lost, unresumable); and `IncompleteRun implements ai.Failure` means generic catch arms silently absorb routine budget stops.
- F10+F11: four tool-supply points with silent replace precedence — diverging rosters flip `Handoff` to `Done` with no diagnostic; `Agent` permanently mutates the caller's `ToolRegistry` across runs.
- F13: tool handlers are pinned to `Throws = ai.Failure`, making ordinary fallible functions and agent-as-tool composition compile errors; thrown typed failures are erased to debug strings at the tool boundary.
- F12: `ModelStep.outcome: T | ToolCalls` untagged union — `T = ToolCalls` silently burns the whole step budget.
- F5+F18: mutation semantics inconsistency (`Conversation.append_*` mutates behind a value-returning signature; `MessageHistory.append` is copy-on-write) and `AgentSession`'s invariants are bypassable by open literal construction (`busy` is a public mutable field).

**P2 — the conversational-app gap** (aligns with the message-first session recommendation)
- F19: mid-conversation injection = user-role plain text only; media/system/assistant appends rejected by every provider; compaction forces lossy export→import whose fidelity report `AgentSession.import` silently discards.
- F20: no assistant-text/reasoning channel (`TextDeltaEvent`/`ReasoningBlock` are defined and constructed nowhere for mainstream providers — the memory agent smuggles narration through a fake `summary` tool arg); no per-turn readback; no session-first entry point (dual first/later-turn code paths).
- F21: no timestamps on events, no step-completed event, intermediate request IDs unrecoverable, no outbound request capture — OTEL/audit integration is not buildable.

**P3 — coherence and publication**
- F0+F7+F9: publish the provider-author kit (fingerprint stamping post-`begin`, `Usage.add`, `classify_http`, correlation validators), fix the contradictory `null`-fingerprint docstring, write the "implement a provider" page, ship a conformance suite (reference adapters currently violate their own contract: `pending_calls` guards are inert on every real adapter).
- F1: cross-namespace spelling incoherence — doc examples (`openai.OpenAIProvider`) don't resolve in ns_* files; `describe` prints `root.`-relative paths that are wrong to paste.
- F16: streaming escapes the error model (pre-BEPv4 `Io|LlmClient`, provably unreachable `ai.Failure` catch arms).
- F17: `ai.sessions`/`ai.run.InSession` is an undocumented second execution surface on an underscore-private protocol method, contradicting the "one lifecycle" doctrine.

## Refuted (so you don't have to re-litigate)
- "MCP escape hatch broken / one static function per remote tool" — refuted; runtime per-tool closures work, `before_tool_call` covers interception.
- "No public metadata-preserving completion verb" — stale; `Done<T>.response()` is public and the corpus was already migrated.

# Appendix: full findings with evidence

### F0. Custom AgentProvider is unimplementable on public API: mandatory output-fingerprint invariant is only satisfiable via ns_internal, and the Conversation interface's documented null default is a guaranteed runtime failure

**Severity:** major · **Category:** not-doable · **Found by:** tasks-providers, custom-provider, tools-agents, testing-observability, cross-cutting-coherence, reliability-approvals


Five independent auditors hit the same wall hands-on: a provider adapter written strictly against the public interfaces (the design's headline escape hatch) compiles cleanly but is rejected by the Agent loop, because Conversation.output_type_fingerprint() must byte-match ai.internal._output_type_fingerprint<T>()'s versioned 'baml-output/v1;nominal=...;schema=...' string, which no public API produces. Worse, the ai.Conversation interface ships a default returning null with a doc comment saying 'Application-defined conversations may return null' — while the runtime unconditionally throws ai.InvalidRequest on null, so implementing exactly what the interface declares produces a provider that type-checks and fails on first run. A second undocumented hurdle: render_shorthand() panics unless it returns a parsable vendor string, and the only non-vendor escape value is the magic 'baml-fallback/fake' hidden in ns_testing. Every provider in the corpus — OpenAI, Anthropic, Google, and the stdlib's own fakes — reaches into ai.internal to satisfy the contract. One auditor noted a public ai.output_fingerprint<T>() wrapper appeared mid-audit (execution/task.baml:115, mtime 21:52), which fixes the constructor half but leaves the contradictory docstring and internal-only step-side validators.


**Evidence:** Enforcement: crates/baml_builtins2/baml_std/ai/ns_run/agent.baml:94-101,127 calls ai.internal._require_conversation_invariants on every start mode; ns_internal/agent.baml:379-428 defines the fingerprint format and rejects null ('no versioned output fingerprint') or mismatched values. Contradiction: messages/conversation.baml:7-10 ('Application-defined conversations may return null.' / `function output_type_fingerprint(self) -> string? throws never { null }`) vs ns_internal/agent.baml:419-425. Hands-on (custom-provider): built minimal AcmeProvider using only public interfaces; `baml-cli check` passed; `baml-cli test -i "*acme*"` failed: `ai.InvalidRequest { provider: "acme", ... detail: "AgentProvider conversation has no versioned output fingerprint" }`; after adding `declared_output_type: ai.internal._output_type_fingerprint<T>()` (copied from stdlib FakeProvider) the same tests PASS. Hands-on (tools-agents): public-only provider => run 1: panic 'ai: invalid provider render shorthand'; after magic shorthand => fingerprint rejection; after ai.internal call => PASS. Magic shorthand: ns_testing/fakes.baml:10-12 ('baml-fallback/fake'); panic default: provider/protocol.baml:11-15. Corpus dependence: ns_testing/fakes.baml:51,60,66, fake_tools.baml:44,110,201, ns_anthropic/messages/tool_calling.baml:29,46, ns_openai/responses/tool_calling.baml:12,39. Doc mandate contradicting interface: _plan/bepv4/pages/conversations-and-resuming.md:113-117. Privacy disclaimer being violated: ns_internal/http.baml:1-3 ('Nothing in ai.internal is part of the public surface'). Mid-audit fix noted: execution/task.baml:115-118 (public ai.output_fingerprint<T>, 'For PROVIDER AUTHORS').


**Adversarial verification:** Partially confirmed with the headline corrected. The "unimplementable on public API" half is now false: I built a from-scratch AgentProvider with zero ai.internal references using the new public ai.output_fingerprint<T>() (execution/task.baml:115-118, an uncommitted working-tree change present in the built CLI) and it passed end-to-end (baml-cli test: PASS). The "magic baml-fallback/fake" sub-claim is also refuted — render_shorthand returning any vendor/model-shaped string ("acme/acme-1") works; only a malformed string triggers the reproduced unclassified panic "ai: invalid provider render shorthand" (provider/protocol.baml:11-15). However, the second half is fully confirmed by direct reproduction: implementing ai.Conversation exactly as its docstring says ("Application-defined conversations may return null", messages/conversation.baml:7-10) compiles cleanly and then fails on first Agent run with ai.InvalidRequest "AgentProvider conversation has no versioned output fingerprint" (thrown from ns_internal/agent.baml:420 via ns_run/agent.baml:94-101,127), and the design page conversations-and-resuming.md:113-117 mandates exactly this rejection — a live doc/runtime contradiction and foot-gun. Since a working strictly-public path exists, this is no longer a critical not-doable; it is a major design-inconsistency/foot-gun (contradictory interface default that guarantees runtime failure, plus an unclassified panic path, plus a corpus that still models ns_internal usage).


**Workaround today:** Fully public custom AgentProvider (verified passing with `baml-cli test`): in begin<T>, store the public fingerprint and have the conversation return it — `class AcmeConversation { owner: AcmeProvider, history: ai.MessageHistory, fingerprint: string, implements ai.Conversation { function provider(self) -> ai.Provider throws never { self.owner } function messages(self) -> ai.Messages throws never { self.history } function output_type_fingerprint(self) -> string? throws never { self.fingerprint } } }` with `begin<T>` returning `AcmeConversation { owner: self, history: task.messages().to_history(), fingerprint: ai.output_fingerprint<T>() }`; `render_shorthand` may return any "vendor/model"-shaped string (e.g. "acme/acme-1" — no magic ns_testing string needed, but it must parse or the runtime panics). Do NOT rely on the interface's documented null default for output_type_fingerprint — it always fails Agent runs.


**Suggested fix:** Promote the fingerprint machinery fully into public API (the new ai.output_fingerprint<T>() is a start): have the Agent/runtime stamp the fingerprint onto conversations after begin() so provider authors never construct it, or honor the documented null case by skipping the check (matching pending_calls' 'null means unreported' convention). Delete or fix the 'may return null' comment. Give render_shorthand a documented grammar and a public non-vendor fallback family, and change the panic to a classified ai.Failure. Make ns_internal access from user packages a compiler warning.

### F1. Freshly built stdlib fails to compile ANY project (bridges.baml:79 unqualified sibling-namespace reference), and cross-namespace spelling is incoherent between docs, corpus, and tooling

**Severity:** major · **Category:** inconsistency · **Found by:** custom-runner, cross-cutting-coherence


The current WIP CLI ships a builtin that itself violates BAML's root.-absolute cross-namespace rule: ns_internal/bridges.baml:79 references AgentProvider unqualified, so a brand-new minimal project gets 'error[E0002]: unresolved type: AgentProvider' and baml-cli test runs zero tests — and the compiler's suggested fix ('Did you mean root.AgentProvider?') points into the user's package and does not work. The same resolution story bites everywhere: doc examples spell `openai.OpenAIProvider` which will not resolve in any ns_* file (the corpus writes `root.openai.OpenAIProvider`), and `baml-cli describe` renders ai types with package-internal `root.` paths (root.jobs.BatchOptions, root.harness.Harness) that are wrong to paste into user code. If the stdlib author trips on this in the AI package's own plumbing, application authors will constantly.


**Evidence:** Bug: crates/baml_builtins2/baml_std/ai/ns_internal/bridges.baml:78-79 (`let capability: AgentProvider =>` inside _fallback_member; needs ai.AgentProvider). Reproduced in a fresh minimal project (baml.toml + 2 files): `baml-cli check` → 'bridges.baml:79:25-79:38 error[E0002]: unresolved type: AgentProvider. Did you mean `root.AgentProvider`?'; `baml-cli test` refuses to run any test; following the suggestion (adding `type AgentProvider = ai.AgentProvider;` at user root) does not fix it. Docs vs corpus: conversations-and-resuming.md:328-330 (`openai.OpenAIProvider { ...openai.responses(), ... }`) vs ns_ai_scenarios/00_shared/models.baml:50 (`root.openai.OpenAIProvider`). describe leakage: `baml-cli describe ai.run.Batch` prints `options: root.jobs.BatchOptions`; `describe ai.run.Harness` prints `harness: root.harness.Harness`. (Binary rebuilt mid-audit at 21:53; probes had run green under the previous build, confirming this landed in current WIP.)


**Adversarial verification:** The headline symptom is stale: bridges.baml now reads `ai.AgentProvider` (line 75, file untracked, mtime 22:00; binary rebuilt 22:08 after the auditor's 21:53 observation), and I verified a fresh minimal project passes `baml-cli check` and runs tests, and the full 174-file corpus compiles — so 'fails to compile ANY project' no longer holds and was transient WIP churn. However, the underlying cross-namespace spelling incoherence is fully confirmed by my own repros: (a) the doc example at conversations-and-resuming.md:328-330 (`openai.OpenAIProvider { ...openai.responses() }`) fails E0002/E0003 inside any ns_* file, and even at root the value call `openai.responses()` fails E0003 while the type position resolves — a type-vs-value resolution asymmetry that makes the doc snippet uncompilable anywhere; (b) `baml-cli describe ai.run.Batch`/`ai.run.Harness` render package-internal paths (`root.jobs.BatchOptions`, `root.harness.Harness`, `root.observe.AgentEvent`) which produce E0002 when pasted into user code, whereas the public spelling `ai.jobs.BatchOptions` resolves. With the compile-break gone, severity drops from critical to major: the confirmed residue is docs that don't compile, tooling that prints unpasteable type paths, and an inconsistent resolution model — a real coherence flaw, not a total outage.


**Workaround today:** In any ns_* file, always use root.-absolute paths exactly as the corpus does: `root.openai.OpenAIProvider { ...root.openai.responses(), model: "...", api_key: baml.env.get_or_panic("OPENAI_API_KEY") }` (verified compiling in the corpus copy). When pasting types from `baml-cli describe` output, mentally rewrite `root.X` to `ai.X` for stdlib types — e.g. describe prints `root.jobs.BatchOptions` but the spelling that resolves in user code is `ai.jobs.BatchOptions` (verified: root.* gives E0002, ai.* resolves). The bridges.baml compile break needs no workaround — it is already fixed in the current working tree/binary.


**Suggested fix:** Fix bridges.baml:79 to ai.AgentProvider and add a CI gate that compiles an empty user project against the embedded stdlib. Make unresolved-name suggestions search enclosing/parent namespaces first. Longer-term: either allow sibling/ancestor namespace resolution (so doc spellings are real code) or make describe and diagnostics render package-qualified public names (ai.AgentProvider, ai.jobs.BatchOptions) instead of package-internal root.* paths, and audit every doc example for the spelling that actually compiles.

### F2. ai.Budget.max_cost_usd is a silently failing safety limit: no provider ever reports cost, so the documented spend cap never trips

**Severity:** major · **Category:** not-doable · **Found by:** reliability-approvals


The approvals/limits page sells ai.Budget { max_steps, max_cost_usd } as a working spend limit, but nothing in the stack ever populates Usage.cost_usd: the ClientProvider bridge (every declarative provider function) reports usage: null outright and the reference OpenAI adapter hardcodes cost_usd: null. The Agent's check `(usage.cost_usd ?? 0.0) >= max` therefore compares 0.0 against the cap forever — a production cost cap yields unbounded spend until max_steps. There is also no max_tokens budget dimension even though token counts ARE reported by real adapters. A safety limit that silently does nothing is a state-corrupting foot-gun (unbounded real-money spend).


**Evidence:** Doc claims: _plan/bepv4/pages/approvals-limits-and-handoffs.md:14 ('ai.Budget { max_steps, max_cost_usd } | Stops work between provider steps') and :216-217. Check: baml_std/ai/ns_run/agent.baml:241-251. No producer: baml_std/ai/ns_internal/client_provider.baml:163 (`usage: null`), baml_src_temp2/ns_openai/ns_internal/responses/structured_output.baml:330 (`cost_usd: null`); `grep -rn cost_usd` shows only fakes set it (to 0.0) and every scenario passes `max_cost_usd: null`. CLI proof: test 'audit: cost budget is inert' — agent run with `budget = ai.Budget { max_steps: null, max_cost_usd: 0.0000001 }` returns Done (PASS), never BudgetReached.


**Adversarial verification:** Reproduced the core claim: with a provider that reports tokens but cost_usd: null — exactly what every shipped HTTP adapter does (ns_openai .../responses/structured_output.baml:330, ns_anthropic/ns_internal/structured_output.baml:184, ns_google/ns_internal/wire.baml:233 all hardcode `cost_usd: null`; the declarative-client bridge reports `usage: null` at baml_std/ai/ns_internal/client_provider.baml:163) — an agent run with `max_cost_usd: 0.0000001` and 1M tokens/step completed as Done, never BudgetReached (test 'verify 2a', PASS, agent check at ns_run/agent.baml:242 `(usage.cost_usd ?? 0.0) >= max`). So out-of-the-box the documented spend cap (approvals-limits-and-handoffs.md:14, :216-217) is silently inert with every stock provider. However, three overstatements downgrade severity from critical/not-doable: (1) the enforcement path itself works and is tested — scenarios' LiveCostedToolProvider wrapper and ScriptedToolProvider.usage_per_step trip it with reason "max_cost_usd" (02_tools_and_agents/tests/handoffs_and_budgets.baml:179-186); (2) "no provider ever reports cost" is false — ns_claude_code/provider.baml:322 populates cost_usd from the CLI's total_cost_usd; (3) a ~15-line fully public workaround exists (verified test 'verify 2b', PASS): prepare_step + ai.observe.estimated_cost + StepPlan.stop yields the same ai.BudgetReached, and the default budget's max_steps: 32 (agent.baml:25) bounds spend unless the user explicitly nulls it. Net: a real silently-inert safety knob and doc-vs-reality gap (docs never say cost must be provider-supplied), but doable publicly — bad-ergonomics/foot-gun, not not-doable.


**Workaround today:** Token-priced cost cap via the public prepare_step callback (verified PASS as test 'verify 2b'):

let price = ai.observe.TokenPrice { input_per_million: 1.0, output_per_million: 2.0 };
let runner = ai.run.Agent<Resolution>.new(
    tools = [search_knowledge],
    prepare_step = (context) -> {
        let spent = ai.observe.estimated_cost(context.usage, price);
        ai.tools.StepPlan {
            provider: null,
            tools: null,
            stop: if (spent >= 0.01) { ai.tools.AgentStop { reason: "max_cost_usd_estimated" } } else { null },
        }
    },
);
// Returns ai.BudgetReached { reason: "max_cost_usd_estimated", ... } exactly like a native budget trip (agent.baml:276-284).

Alternative (heavier, also verified working in-tree): wrap any provider to inject usage.cost_usd per step, as ns_ai_scenarios/02_tools_and_agents/08_handoffs_and_budgets/utilities.baml's LiveCostedToolProvider does — then the native max_cost_usd trips.


**Suggested fix:** Either wire cost in (accept an ai.observe.TokenPrice table on Budget/Agent and compute from token usage between steps) or remove max_cost_usd until providers report cost. At minimum, fail loudly when max_cost_usd is set but the provider never reports cost, and add a max_total_tokens dimension that works with what adapters already report.

### F3. ai.retry can never replay transport/5xx failures — the single most common retryable class — even when retry_if says yes

**Severity:** major · **Category:** not-doable · **Found by:** errors-failures


NetworkFailure hardcodes effects()=Effects.Unknown, and the retry gate fails closed on Unknown BEFORE consulting the caller's retry_if predicate, so the stdlib retry wrapper categorically refuses to replay connection resets and HTTP 500/502/503/408 (all mapped to NetworkFailure by the shared classifier). There is no override, no idempotency-key hook, no other knob: 'retry a 503 on a pure inference call' is inexpressible with ai.retry, and reimplementing the ~170-line Retry wrapper itself requires ai.internal helpers. The classifier's own doc comment asserts 'Effects.None is correct for pure inference calls' while returning a type whose effects() is Unknown, and the errors page says NetworkFailure 'Retry usually helps? often'.


**Evidence:** defaults.baml:24-26 (NetworkFailure -> Effects.Unknown); ns_internal/replay.baml:15-23 (_may_retry_model_step returns false on Effects.Unknown before retry_if is consulted); ns_internal/http.baml:7-9,20-22 (comment '`Effects.None` is correct for pure inference calls' yet 5xx/408 -> NetworkFailure). Demonstrated: custom AgentProvider throws ai.NetworkFailure once, wrapped in ai.retry(flaky, 3, retry_if = (_) -> true); `baml-cli test -i "*audit*" --logs info` output: 'audit A label=network:connection reset calls=1' — one attempt, run failed despite an always-yes predicate and 3 allowed attempts. Docs contradict: pages/errors-and-error-handling.md:61.


**Adversarial verification:** Reproduced live: a custom AgentProvider throwing ai.NetworkFailure once, wrapped in ai.retry(flaky, 3, retry_if = (_) -> true), failed after exactly 1 call ("audit A label=network:connection reset calls=1", baml-cli test PASS on the assertion calls==1) — the stdlib retry never replays transport/5xx failures because NetworkFailure.effects() is Effects.Unknown (defaults.baml:24-26) and ai.internal._may_retry_model_step returns false on Unknown before retry_if is consulted (replay.baml:15-23), while _classify_http maps all 5xx/408 to NetworkFailure under a doc comment claiming "Effects.None is correct for pure inference calls" (http.baml:7-21) and pages/errors-and-error-handling.md:61 tells users retry "often" helps for NetworkFailure via retry_if. However, one sub-claim is overstated: I built a working user-space retry wrapper (~90 lines) using ONLY public APIs — no ai.internal — that successfully replayed the NetworkFailure (test "audit c3 B" PASS, calls==2), so the behavior is a policy gap plus a doc contradiction, not strictly "not doable"; the workaround does require reimplementing the whole wrapper, deliberately discarding the effect-safety guard, and discovering via an opaque runtime InvalidRequest that the Agent runner's hidden ownership invariant (ns_internal/agent.baml:275-287) forces a wrapper Conversation class. Severity corrected to major: the flagship retry combinator silently no-ops on the most common retryable failure class and the docs actively misdirect, but a public-API escape hatch exists.


**Workaround today:** Write your own AgentProvider wrapper — public API only, verified working (test passed, retried a NetworkFailure and completed): class UserRetry { inner: ai.Provider, max_attempts: int, retry_if: ((ai.Failure) -> bool throws never)? } implementing ai.Provider and ai.AgentProvider. begin<T> casts self.inner to ai.AgentProvider via match and returns UserRetryConversation { owner: self, inner: provider.begin<T>(task.with_provider(self.inner)) } — the wrapper conversation class (implements ai.Conversation with provider() returning self.owner, delegating messages()/output_type_fingerprint() to inner) is MANDATORY because the Agent runner rejects a directly-delegated inner conversation with InvalidRequest "AgentProvider returned a conversation owned by another provider instance". step<T> loops: `let result = provider.step<T>(state.inner, tools) catch (e) { let failure: ai.Failure => { if (attempt >= self.max_attempts || !judge(failure)) { throw e; } attempt = attempt + 1; continue; }, _ => throw ... }; return result;` — applying only the caller's retry_if and deliberately ignoring failure.effects(). submit delegates and reassigns state.inner. Full working file: /private/tmp/claude-501/-Users-aaron-projects-baml-baml-language/aad98799-44ad-41b3-88db-a6fb1e698bc2/scratchpad/verify3/proj/ns_ai_scenarios/03_routing_and_reliability/tests/verify_claim3.baml (test "audit c3 B" PASS, flaky.calls == 2).


**Suggested fix:** Split fact from policy: keep Effects.Unknown as the fact, but let the caller opt in (e.g. replay_unknown_effects = true, or an idempotency-key hook on AgentProvider.step), since a pure conversation step is replay-safe by the plan's own transactional-step contract. Alternatively classify pure-inference transport failures as Effects.None, as http.baml's comment already claims.

### F4. StreamingProvider is unimplementable and untestable: it must return the closed concrete baml.llm.Stream class, no fake exists, and the default OpenAI provider doesn't implement it

**Severity:** critical · **Category:** not-doable · **Found by:** media-realtime-voice, custom-provider, tasks-providers


ai.StreamingProvider's one method must return the concrete class baml.llm.Stream, whose fields (_client: PrimitiveClient, _sse: SseStream, _acc, _cache) are private native handles user code cannot even name, hardwired to a Rust-side accumulator that only understands built-in vendor SSE dialects. So a custom provider (local model, websocket, proxy, in-house gateway) can never add streaming, and — uniquely among capabilities — no offline fake is possible: ai.testing has fakes for agent, tools, sessions, background, batch, transcription, and realtime, but none for streaming; the only streaming tests in the corpus are live-key integ tests. Even the Anthropic reference adapter must write Stream's private fields and call the dunder baml.llm.__new_stream_cache. Compounding it, OpenAI — the docs' default 'fast_model()' — does not implement StreamingProvider at all (only Anthropic does), so streaming the flagship examples' own default provider throws Unsupported. Realtime shows the right pattern (LiveSession is an interface, so FakeRealtimeProvider exists); streaming is the lone capability whose output type is a closed concrete class.


**Evidence:** Interface returns concrete class: baml_std/ai/provider/protocol.baml:99-102; Stream internals: baml_std/baml/ns_llm/llm_types.baml:657-720 (fields _client/_acc/_sse/_cache; next() hardwired to self._sse/self._acc/__sap_parse_partial). Hands-on: wrote MyFakeStreamingProvider constructing baml.llm.Stream; `baml-cli check` → "error[E0002]: unresolved type: root.http.SseStream" plus cannot-infer errors. Reference ritual: ns_anthropic/ns_internal/client.baml:301-306 constructs `baml.llm.Stream { _client:..., _acc:..., _sse:..., _cache: baml.llm.__new_stream_cache<TPartial, T>() }`. Only impl: ns_anthropic/messages/provider.baml:45; `grep -rln "StreamingProvider" ns_openai` → no matches; no fake: `grep -rn "stream" baml_std/ai/ns_testing/*.baml` → only transcription audio. ### F8. Provider instance identity and conversation ownership have no public primitive, and the invariant is enforced inconsistently — thin delegating wrappers fail or pass depending on nesting depth

**Severity:** major · **Category:** not-doable · **Found by:** custom-provider, reliability-approvals


The protocol obligates providers to 'reject conversations owned by another provider instance', but BAML class equality is structural — two identically-configured provider values compare equal — so user code cannot express 'same instance' at all. The stdlib's answer is a bound-method-equality trick hidden in ai.internal._same_provider_instance (14+ call sites); the docs' ClaudeCodeCli example instead tells users to hand-add `_instance_id: baml.id.new()` fields. Worse, the invariant is checked only against the outermost provider: the natural middleware pattern — delegate begin/step/submit to an inner provider, exactly what the stdlib's own FlakyOnceLiveAgent helper does — is rejected with 'conversation owned by another provider instance' when used directly as the task's provider, but works fine when nested inside ai.retry (which never re-checks inner ownership). **Evidence:** Obligation: provider/protocol.baml:75-77. Trick + rationale: ns_internal/agent.baml:265-273 ('Class == is structural in BAML. Bound-method equality includes receiver identity...'). Doc workaround: harnesses-and-custom-extensions.md:112-115 ('// Class equality is structural; conversation ownership needs a per-instance identity. _instance_id: baml.id.new(),'). Hands-on probe: `structural a==b: true`, `same_instance(a,b): false`, `same_instance(a,a): true` for two identically-configured providers. Depth inconsistency (both tests PASS): 'audit: thin delegating wrapper used directly' logs 'REJECTED: AgentProvider returned a conversation owned by another provider instance' while 'audit: same thin wrapper works under ai.retry' completes — same class copied from ns_ai_scenarios/03_routing_and_reliability/tests/retry_safe_calls.baml:33-71. Check site: ns_run/agent.baml:126-127 + ns_internal/agent.baml:275-287; boilerplate: reliability/retry.baml:55-67,103-115,133-145 (three identical guards).


**Adversarial verification:** Every cited fact reproduced: protocol.baml:75-77 obligation, ns_internal/agent.baml:265-273 bound-method trick (17 uses, 6 files, all internal), harnesses-and-custom-extensions.md:112-115 contradictory _instance_id doc pattern, and retry.baml's triplicated guard. Given the stdlib's own example is broken-by-pattern and middleware is a first-class advertised use case, I judge it major in ergonomic impact but with workaround; corrected_severity: major kept.


**Workaround today:** Public-API compliant delegating wrapper (verified working directly as a task provider): give the wrapper its own Conversation class that re-owns the inner conversation, mirroring stdlib RetryConversation.

```baml
class OwnedConversation {
  owner: MyWrapper,
  inner: ai.Conversation,
  implements ai.Conversation {
    function provider(self) -> ai.Provider throws never { self.owner }
    function messages(self) -> ai.Messages throws never { self.inner.messages() }
    function output_type_fingerprint(self) -> string? throws never { self.inner.output_type_fingerprint() }
  }
}
class MyWrapper {
  inner: ai.testing.FakeProvider, // or any AgentProvider
  implements ai.Provider { /* name, render_shorthand delegate */ }
  implements ai.AgentProvider {
    function begin<T>(self, task: ai.Task<T>) -> ai.Conversation throws ai.Failure | baml.errors.UnknownError {
      OwnedConversation { owner: self, inner: self.inner.begin<T>(task.with_provider(self.inner)) }
    }
    function step<T>(self, conversation: ai.Conversation, tools: ai.tools.Tool[]) -> ai.ModelStep<T> throws ai.Failure | baml.errors.UnknownError {
      let state = match (conversation) { let v: OwnedConversation => v, _ => throw baml.errors.UnknownError.with_message<never>(null, "foreign conversation") };
      self.inner.step<T>(state.inner, tools)
    }
    function submit(self, conversation: ai.Conversation, results: ai.tools.ToolResult[]) -> ai.Conversation throws ai.Failure | baml.errors.UnknownError {
      let state = match (conversation) { let v: OwnedConversation => v, _ => throw baml.errors.UnknownError.with_message<never>(null, "foreign conversation") };
      state.inner = self.inner.as<ai.AgentProvider>.submit(state.inner, results); state
    }
  }
}
```

Instance identity in pure user code (no ns_internal): bound-method equality — `a.name == b.name` returns true only for the same provider object (verified: false for two identically-configured providers, true for the same one). Both work today; neither is documented as the public idiom.


**Suggested fix:** Expose identity as first-class public API (ai.same_provider_instance(a,b) or an auto-generated identity handle on Provider), and make the ownership invariant structural: walk a provider's delegation chain via an optional unwrap()/delegate() method so thin wrappers are legal at any depth — or enforce uniformly and ship a public ai.DelegatingProvider/WrapConversation base supplying the boilerplate.

Closures are AnyFunctions and can be built per-remote-tool in a runtime loop capturing the tool name, and the public `before_tool_call` hook on ai.run.Agent.new (ns_run/agent.baml:33-35) is explicitly allowed to rewrite call arguments (ns_internal/agent.baml:136-137), so wrapping model args as {"args": original} makes dispatch succeed while the model still sees the faithful remote schema. I demonstrated this end-to-end through the full public Agent loop with a fake provider: N runtime-discovered tools, proxy received `remote_lookup <- {"order_id":"O-42"}`, zero ToolErrors (test PASS, scratchpad verify4/proj/ns_ai_scenarios/02_tools_and_agents/tests/verify_mcp_e2e.baml). What survives is a real but lesser finding: the documented escape hatch fails in its advertised naive use, the workaround couples tool construction to a distant runner hook (forget it and you get a silent model-facing ToolError), and the 'received never' message is genuinely baffling — that residue is bad-ergonomics/doc-gap severity, not a critical not-doable.


### No public metadata-preserving completion verb: the observability docs' own examples and 13+ scenario files run on ai.internal._response_from_done

**Why refuted:** The claim's load-bearing evidence no longer exists: grep for `ai.internal._response_from_done` across baml_src_temp2 returns 0 hits (claimed 13+), and the only remaining reference in the entire repo is the now-dead definition at baml_std/ai/ns_internal/agent.baml:346 with zero callers.
