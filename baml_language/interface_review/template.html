    How to read this model, language cleanup, and the limits of “no leaks”
    This is an executable design model, not an implementation or a proof of the new BAML ABI. Green checks validate the model’s accounting and selected expected states. Evidence links say what was actually probed. “Policy to review” marks a recommendation or unresolved protocol detail.
    • Reference versus authority: a live lease keeps state safe to access. An open scope grants permission to start operations. Closing a wrapper releases local ownership; closing a scope revokes operations and drains admitted work.
    • One receiver, many views: every view keeps concrete identity, interface metadata, exact type pins and the original scope. Function, interface and storage handles use the same ownership principles.
    • Collection is simplified: the model removes objects when no modeled owners remain, then removes their outgoing edges. Real VM and host collectors may delay collection and trace internal cycles. The cross-runtime cycle case specifically represents roots that neither collector can trace through.
    • No universal prompt cleanup: application-retained references remain live; separate collectors do not automatically collect cross-runtime cycles; JS finalization may never run; an uncooperative worker can keep a closing runtime alive indefinitely. Scope teardown releases eligible bridge roots after actual drain, not arbitrary native resources on a deadline.
    • Mutations: scalar reads are values, mutable child reads are storage references, and explicit supported data export is a copy. Parent-field replacement detaches old aliases. Cancellation after commit does not undo the write.
    • Coverage: these finite cases organize the review. Their runtime gates also need adversarial scheduling, fault injection, recursive containers, iterators/streams, generic witnesses, inherited/default methods and every supported bridge. Passing the browser model cannot establish leak freedom.
