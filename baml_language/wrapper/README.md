This is the standalone BAML implementation of the `baml` toolchain wrapper. It resolves environment, nearest project, user default and fallback selectors; installs absent managed toolchains; manages shared channels; and launches the selected CLI with inherited stdin/stdout/stderr and its exit status. Selection and installation decisions are BAML code. Generic native stdlib operations provide process supervision, filesystem operations, TOML edits and validated archive extraction.

The wrapper uses the process APIs adopted in #5456 and the filesystem, path, archive, atomic-write, locking, and typed TOML implementations adopted in #5457. Host telemetry metadata and strict archive preflight are included in #5457. Subprocess execution retains normal platform signal delivery without automatic parent-to-child signal forwarding.

BCS records canonical command context and sanitized operational-error metadata. Full input snapshots and argument-bearing return snapshots are not requested. The existing `http_bodies=false` policy suppresses all error payloads, including requested errors; this wrapper preserves that policy.

| Boundary | Captured values |
| --- | --- |
| `dispatch`, `WrapperInvocation.parse`, `management_command`, `selection_impl`, management `preflight` / `execute`, acquisition, version reporting, passive checks and self-update | Outcomes only; no input, returned-value or error snapshots. |
| `run_toolchain` | Only returned `baml.sys.ProcessExit { exit_code, signal }`. No selected binary, arguments or stdout/stderr buffers. |
| `user.wrapper_error` | A parameterless marker adding only the three allowlisted metadata fields below; no input, output or error values. |

Child stdout/stderr remain inherited and uncaptured. A delegated CLI/project keeps its own recording policy. `sys.exit` has no returned output; cancellation records only its status. A nonzero child exit or signal is retained in ProcessExit and does not itself emit a wrapper-error marker. VM panics retain their runtime panic status and bypass error handlers, so they do not produce these catch-handler markers. HTTP bodies remain excluded, and no runtime policy, identity, destination or PostHog usage property is changed.

The error marker schema is closed:

| Metadata key | Allowed values |
| --- | --- |
| `wrapper.error.stage` | `dispatch`, `parse`, `management_command`, `preflight`, `execute`, `selection`, `acquisition`, `status_acquisition`, `freshness`, `refresh`, `version`, `self_update`, `child_launch` |
| `wrapper.error.category` | `usage`, `invalid_selection`, `project_not_found`, `configuration`, `io`, `timeout`, `invalid_argument`, `other` |
| `wrapper.error.disposition` | `propagated`, `recovered`, `terminal` |

Classification inspects only known error types through a hidden call; unrecognized types become `other`. It never reads error fields, stringifies exceptions, or derives labels from messages, class names, argv/flags/values, paths, credentials, response bodies or user-defined data. The marker adds these three fields to existing trace context; it does not copy the exception into context or snapshots. Internal telemetry sender objects and payloads are not captured.

`propagated` means that boundary rethrows; `recovered` means its handler continues; `terminal` identifies the dispatch catch that reports the command failure. A single error can have several markers. Recovered version, status-acquisition and passive-check failures remain visible even if the process succeeds. Use process status for the invocation's final outcome. The existing stderr diagnostic and exit behavior are preserved. This instruments selected operational boundaries, not every utility or errors consumed inside unrelated untraced utilities. Help bypasses management and self-update handlers; internal telemetry/replacement helpers bypass parsing.

The foreground `user.dispatch` span carries `context_metadata['command']`, computed by the same `WrapperCli.command_name(args)` normalization as PostHog before argument parsing. Parser/operational spans and error markers inherit that bounded label independently of PostHog. The terminal marker restores the bounded label after dispatch context unwinds, preserving other parent context. Labels include `baml check`, `baml local`, `baml self update` and `baml toolchain use`; flags, argument values and unknown command names do not enter this field. `baml` can mean empty argv, root help, version, an unknown command or `--` termination. Helpers remove an inherited foreground command label.

These are span fields, not process launch metadata. Join the single dispatch span to `processes` by process_id when counting invocations; inherited descendants or multiple error markers otherwise duplicate counts. Cloud OS argv omission is unchanged. For isolated local recording, use `DO_NOT_TRACK=1 BOUNDARY_API_KEY=local BAML_TELEMETRY=medium BAML_HOME=/tmp/wrapper-command-home/.baml /path/to/baml toolchain list`, then query:

```sh
DO_NOT_TRACK=1 BOUNDARY_API_KEY=local BAML_TELEMETRY=off /path/to/baml-cli local recordings query --project-dir /tmp/wrapper-command-home --output-format json \
  "SELECT s.context_metadata['command'] AS command, p.status, COUNT(*) AS invocations
   FROM spans s JOIN processes p ON s.process_id = p.process_id
   WHERE s.span_name = 'user.dispatch'
   GROUP BY s.context_metadata['command'], p.status"
```

For diagnostics, query `user.wrapper_error` spans and their `wrapper.error.stage`, `wrapper.error.category` and `wrapper.error.disposition` metadata, joining processes for the final outcome. `BAML_TELEMETRY=off` disables markers and local sinks too. `DO_NOT_TRACK` controls PostHog separately. `high` adds automatic spans without requesting input/output capture; packed `on` retains the baked level (normally medium). No errors or cancellation payloads are restored through these markers.

The command line is declared once in `cli.baml` with the parser in `ns_clap`, a port of clap to BAML laid out like clap (lexer, `Arg`, `Command`, parser, validator, `ArgMatches`, `Error`, help). `crates/baml_cli/tests/clap_conformance_e2e.rs` parses generated command lines with both and requires the same outcome; the one setting beyond clap, `external_subcommand_passthrough`, is tested next to the parser. In the wrapper: `toolchain` and `self` are the wrapper's commands, `--project-dir` and `--output-format` are global options accepted before or after them, and every other command is an external subcommand forwarded to the selected CLI with its tokens untouched. The CLI's other value-taking global options are declared there too, so the wrapper can find the command that follows them.

The code is organized around the data each operation owns: `WrapperInvocation` parses arguments and coordinates selection/management; version, channel, and path selectors implement their own behavior through `ToolchainSelector`; command classes carry only their applicable options. Configuration constructors validate documents before writes, and `ReleaseStore` keeps a validated release source with its cache. `WrapperTelemetry` owns a session and `TelemetryQueue` distinguishes delivered, rejected, and unavailable outcomes. Recoverable I/O/configuration failures are handled at the operation that can recover; the entry point renders remaining errors. Shared wrapper tests use descriptive `test` blocks with their setup and assertions in one place.

Build with `python3 baml_language/wrapper/build --cli /absolute/path/to/baml-cli --output /absolute/path/to/baml`. The compiler and adjacent pack host must come from this checkout. `--no-self-update` produces a package-manager variant. The wrapper version comes from `wrapper/release.toml`. Builds prepare a temporary project with those constants and invoke `baml pack`; no source files are rewritten. For cross-target packaging, pass `--target <triple> --pack-host /path/to/the/matching/baml-pack-host` to embed the host built from the same commit without fetching a released runtime.

Release builds pass bare `--embed-telemetry` to this build helper, using `pack.build.embed_telemetry_api_key_from_env_var = "BAML_WRAPPER_BOUNDARY_API_KEY"` from the wrapper manifest. The flag accepts no value; the environment-variable name must be configured in `baml.toml`. Packing embeds that environment variable's value directly as the BCS telemetry API key, after a read-only `POST /v1/auth/verify` request with `{"fullResponse":true}` checks its owning organization/project and exclusive write access to the expected environment. The complete 200 JSON response must include the environment name and parent IDs. A missing, empty, or invalid key, an unsupported verification response, an unavailable verification service, or an ownership or permission mismatch fails the build. Local and test builds omit `--embed-telemetry` and remain usable without BCS credentials. The packed wrapper uses identity bindings for `BAML_TELEMETRY`, `BOUNDARY_API_KEY`, and `BOUNDARY_PROJECT`: `BAML_TELEMETRY=off` disables BCS recording, and the other two variables select caller-owned ingestion instead of the embedded key. `BOUNDARY_API_URL` also overrides the baked endpoint. The wrapper excludes HTTP bodies from network spans. This recording is separate from the wrapper-owned PostHog pipeline described below. The wrapper uses the existing packed-runtime BCS dispatch and shutdown policy, including its normal bounded delivery drain. It sets `on_initial_telemetry_failure = "ignore"` using the existing artifact policy. PostHog delivery retains its independent durable queue and detached helper.

The release workflow reads `BAML_WRAPPER_BOUNDARY_API_KEY`, `BAML_WRAPPER_BCS_PROJECT`, and `BAML_WRAPPER_BCS_ENVIRONMENT` as GitHub secrets from the `infisical-github-baml-language-release` environment and exposes the same names to the builder. Configure all three in Infisical and sync them to that GitHub environment before running wrapper release packaging. The builder writes those destination names into `boundary.project` and `pack.build.embed_telemetry_env` in the temporary `baml.toml`; packing checks the key against both assertions. Runtime destination inference uses the key’s ordinary ingestion permission. Both self-update variants and every target embed the supplied key. The packed BAML implementation owns the canonical `baml-wrapper[-no-self-update]-<version>-<target>` release assets in the `wrapper-baml` Actions artifact. Rust builds remain reference artifacts outside the publishing download patterns. Shared release tests exercise both implementations and every shipped variant before publishing. Wrapper test fixtures set `BAML_TELEMETRY=off` when exercising uploaded release binaries.

`toolchain use <selector>` updates the closest existing `baml.toml`; `toolchain use --global <selector>` (or `-g`) sets the user default in `$BAML_HOME/config.toml`. Output identifies the new selection and the previous selection, including recorded concrete channel versions. The project always wins over the user default, and `BAML_TOOLCHAIN` takes precedence over both. Relative project paths use the manifest directory; environment and user-default paths use the invocation directory. `toolchain pin` is removed. Updates follow the resolved shared channel and preserve selectors. Damaged installations require an explicit `toolchain install <version> --force`.

Root help and wrapper-command help work without a toolchain. Version reporting prints the wrapper version, attempts to install an absent managed CLI, and invokes its original version flag. Selection, installation, verification, or launch failure produces a warning and a successful wrapper-only version report; when the CLI runs, its exit code is preserved. All other CLI commands, including `update`, `upgrade`, unknown commands, and command help, are forwarded unchanged to the selected CLI. The selected CLI provides independent wrapper/toolchain update guidance for `update` and `upgrade`.

The wrapper interprets `--project-dir PATH` and `--project-dir=PATH` when selecting the toolchain and forwards the original arguments to `baml-cli`. Relative `--project-dir` paths use the shell working directory. Change the working directory with ordinary `cd`; `--directory` is removed from the wrapper and CLI. The wrapper leaves its actual cwd unchanged so the CLI applies forwarded filesystem flags once. Flags after `--` belong to the target program. `baml cloud ... --project` names a cloud project; the wrapper never reads it.

`toolchain install` without a selector installs the active environment/project/user/fallback selection. For a recorded channel it installs that recorded concrete version, preserving the mapping; `toolchain update` is the explicit operation that advances a channel. A local-path selection has nothing to install. Explicit `toolchain install <selector>` and `toolchain use <selector>` acquire only the requested target, without first installing the previous active selection. `toolchain list` reads local selectors, channel mappings, and installation directories without acquiring or validating an executable. No toolchain management command installs the active selection as preflight. `toolchain update` installs the selected channel’s release directly, and `toolchain uninstall` only removes the specified version. Omitting the selector from `toolchain install` resolves its target through normal selection precedence and then uses the same installation operation as an explicit target.

`toolchain status [--install]` reports the active selection and available releases. With `--output-format json` it writes one versioned resolution object with available releases to stdout; `toolchain list --output-format json` writes the local inventory the same way. Plain status attempts to install an absent selected executable once, warns if acquisition fails, and continues reporting selection and available-release metadata. `--install` makes installation failure fatal instead. Recorded channels retain their concrete version; an unrecorded channel is initialized when installation succeeds. If initialization fails, the missing channel mapping remains a resolution error; metadata, configuration, and verification errors also remain fatal. A validated local-path toolchain returns `version: null` and is never executed to discover its version. Detected installation damage remains an error.

```json
{
  "schema_version": 1,
  "selector": "nightly",
  "version": "0.23.1-nightly.20261026.a",
  "source": "/work/project/baml.toml",
  "wrapper_path": "/home/user/.baml/bin/baml",
  "toolchain_path": "/home/user/.baml/toolchains/0.23.1-nightly.20261026.a/bin/baml-cli",
  "managed": true,
  "installed": true,
  "available_releases": { "nightly": "0.23.1-nightly.20261026.a" }
}
```

`source` identifies the manifest, user config, `$BAML_TOOLCHAIN`, or fallback that selected the toolchain. Exact managed versions can be resolved while absent, in which case `installed` is false and `toolchain_path` is the expected installation path. Consumers should accept additional JSON fields in future schema-compatible updates.

Normal channel launches warn when cached metadata identifies a different available release. A passive refresh runs alongside the child CLI, has a five-second network deadline, and is retried at most once per 24 hours, including failures. `[update] auto_check = false` disables refreshes while preserving notices justified by existing cached metadata. Exact versions and local paths do not perform passive checks. `toolchain status` explicitly refreshes metadata and never advances a recorded channel.

Builds with `baml self update` disabled print concrete package-manager commands; successful wrapper updates point to the separate toolchain update check. Wrapper-owned errors use the CLI's human-readable `error:` convention, and management commands produce no entry-point return-value output.

Run `python3 baml_language/wrapper_tests/run` to test both self-update variants. Release workflows pack the published BAML wrapper for every wrapper platform from the same run's compiler and pack-host artifacts, verify its embedded release fingerprint, and gate the release on wrapper tests.

The wrapper has its own telemetry pipeline. Each invocation emits a canonical command event (`baml`, `baml toolchain status`, `baml toolchain update`, and so on), discarding all flags and argument values. Every event has `client: baml-in-baml`. Auxiliary events include `wrapper_resolution`, `wrapper_install`, `wrapper_selection`, `wrapper_update`, `wrapper_self_update`, and `wrapper_unhandled_error`. Unhandled errors include parse and handoff failures, excluding recovered errors and delegated CLI exit codes. It uses `$BAML_HOME/wrapper-telemetry.toml` and `$BAML_HOME/wrapper-telemetry/`; `DO_NOT_TRACK`, a disabled wrapper preference, or the disabled global CLI telemetry preference suppress collection and delivery. Events contain coarse wrapper metadata and bounded decisions/outcomes, without raw selectors, paths, arguments, or errors. Delivery occurs only in a detached `__flush-wrapper-telemetry` helper. During Windows self-update, the wrapper runs that helper from the updater copy so telemetry delivery does not keep the replacement target open. The build takes the ingestion constants from `wrapper/release.toml`. See [TELEMETRY.md](../../TELEMETRY.md) for fields and opt-out behavior.
