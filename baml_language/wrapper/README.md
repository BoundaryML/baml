This is the standalone BAML implementation of the `baml` toolchain wrapper. It resolves environment, nearest project, user default and fallback selectors; installs absent managed toolchains; manages shared channels; and launches the selected CLI with inherited stdin/stdout/stderr and its exit status. Selection and installation decisions are BAML code. Generic native stdlib operations provide process supervision, filesystem operations, TOML edits and validated archive extraction.

The wrapper uses the process APIs adopted in #5456 and the filesystem, path, archive, atomic-write, locking, and typed TOML implementations adopted in #5457. Host telemetry metadata and strict archive preflight are included in #5457. Subprocess execution retains normal platform signal delivery without automatic parent-to-child signal forwarding.

BCS retains explicit spans for dispatch, argument parsing, management command preflight/execution, and self-update. These spans capture no arguments, outputs, or error payloads. Counting argument-parser spans excludes detached telemetry/replacement helpers; update handler spans exclude command help. An error escaping dispatch is a wrapper failure, while recovered internal errors and delegated CLI exit codes are excluded. These boundaries remain queryable independently of completed aggregate profiles.

The code is organized around the data each operation owns: `WrapperInvocation` parses arguments and coordinates selection/management; version, channel, and path selectors implement their own behavior through `ToolchainSelector`; command classes carry only their applicable options. Configuration constructors validate documents before writes, and `ReleaseStore` keeps a validated release source with its cache. `WrapperTelemetry` owns a session and `TelemetryQueue` distinguishes delivered, rejected, and unavailable outcomes. Recoverable I/O/configuration failures are handled at the operation that can recover; the entry point renders remaining errors. Shared wrapper tests use descriptive `test` blocks with their setup and assertions in one place.

Build with `python3 baml_language/wrapper/build --cli /absolute/path/to/baml-cli --output /absolute/path/to/baml`. The compiler and adjacent pack host must come from this checkout. `--no-self-update` produces a package-manager variant. The wrapper version comes from the Rust wrapper's Cargo manifest. Builds prepare a temporary project with those constants and invoke `baml pack`; no source files are rewritten. For cross-target packaging, pass `--target <triple> --pack-host /path/to/the/matching/baml-pack-host` to embed the host built from the same commit without fetching a released runtime.

Release builds pass `--embed-telemetry --telemetry-environment <environment>` to this build helper. Set `BOUNDARY_PROJECT=org/project` and authenticate the builder with a mint-capable `BOUNDARY_API_KEY` or saved administrator login. Packing provisions and embeds a public BCS ingestion credential; the builder’s private credential is not included. Minting failure fails the build. Local and test builds omit `--embed-telemetry` and remain usable without BCS credentials. The packed wrapper accepts `BAML_WRAPPER_BCS_TELEMETRY=off` to disable BCS recording, and excludes HTTP bodies from network spans. This recording is separate from the wrapper-owned PostHog pipeline described below. The wrapper uses the existing packed-runtime BCS dispatch and shutdown policy, including its normal bounded delivery drain. It sets `on_initial_telemetry_failure = "ignore"` using the existing artifact policy. PostHog delivery retains its independent durable queue and detached helper. The Rust wrapper emits PostHog events only and does not initialize BCS recording.

The release workflow reads `BAML_WRAPPER_BCS_PROJECT` (`org/project`) and `BAML_WRAPPER_BCS_ENVIRONMENT` (an existing environment) from GitHub variables, and `BAML_WRAPPER_BOUNDARY_API_KEY` from the `infisical-github-baml-language-release` environment. The caller passes that secret by name to the reusable workflow, whose environment-bound packing job exposes it to the builder as `BOUNDARY_API_KEY`. Configure those values before running wrapper release packaging; missing configuration and rejected minting fail the job before publishing candidate archives. Both self-update variants and every target receive their own embedded credential. Wrapper test fixtures set `BAML_WRAPPER_BCS_TELEMETRY=off` when exercising uploaded release binaries.

`toolchain use <selector>` updates the closest existing `baml.toml`; `toolchain use --global <selector>` (or `-g`) sets the user default in `$BAML_HOME/config.toml`. Output identifies the new selection and the previous selection, including recorded concrete channel versions. The project always wins over the user default, and `BAML_TOOLCHAIN` takes precedence over both. Relative project paths use the manifest directory; environment and user-default paths use the invocation directory. `toolchain pin` is removed. Updates follow the resolved shared channel and preserve selectors. Damaged installations require an explicit `toolchain install <version> --force`.

Root help and wrapper-command help work without a toolchain. Version reporting installs an absent managed CLI, invokes its original version flag, and propagates failures. All other CLI commands, including `update`, `upgrade`, unknown commands, and command help, are forwarded unchanged to the selected CLI. The selected CLI provides independent wrapper/toolchain update guidance for `update` and `upgrade`.

Both wrappers interpret `--project PATH` and `--project=PATH` when selecting the toolchain and forward the original arguments to `baml-cli`. Relative `--project` paths use the shell working directory. Change the working directory with ordinary `cd`; `--directory` is removed from the wrapper and CLI. The wrapper leaves its actual cwd unchanged so the CLI applies forwarded filesystem flags once. Flags after `--` belong to the target program. After the `query` command, `--project` names a cloud project and does not change filesystem toolchain selection; a root-level `--project` before `query` still selects the source project.

`toolchain install` without a selector installs the active environment/project/user/fallback selection. For a recorded channel it installs that recorded concrete version, preserving the mapping; `toolchain update` is the explicit operation that advances a channel. A local-path selection has nothing to install.

`toolchain status [--install] [--json]` reports the active selection and available releases. `--json` writes one versioned resolution object with available releases to stdout. Every non-help toolchain command first attempts to install the active selection; failures are reported on stderr and the requested operation continues. `--install` requires installation to succeed. Recorded channels retain their concrete version; unrecorded channels establish their first mapping. A validated local-path toolchain returns `version: null` and is never executed to discover its version. Detected installation damage remains an error.

```json
{
  "schema_version": 1,
  "selector": "nightly",
  "version": "0.23.1-nightly.20261026.a",
  "source": "/work/project/baml.toml",
  "wrapper_path": "/home/user/.baml/bin/baml",
  "toolchain_path": "/home/user/.baml/toolchains/0.23.1-nightly.20261026.a/bin/baml-cli",
  "managed": true,
  "installed": true,
  "available_releases": { "nightly": "0.23.1-nightly.20261026.a" }
}
```

`source` identifies the manifest, user config, `$BAML_TOOLCHAIN`, or fallback that selected the toolchain. Exact managed versions can be resolved while absent, in which case `installed` is false and `toolchain_path` is the expected installation path. Consumers should accept additional JSON fields in future schema-compatible updates.

Normal channel launches warn when cached metadata identifies a different available release. A passive refresh runs alongside the child CLI, has a five-second network deadline, and is retried at most once per 24 hours, including failures. `[update] auto_check = false` disables refreshes while preserving notices justified by existing cached metadata. Exact versions and local paths do not perform passive checks. `toolchain status` explicitly refreshes metadata after the best-effort installation attempt and never advances a recorded channel.

`baml update` and `baml upgrade` resolve and install the selected CLI, then delegate to it for guidance about independent wrapper and channel updates. Disabled self-update builds print concrete package-manager commands; successful wrapper updates point to the separate toolchain update check. Wrapper-owned errors use the CLI's human-readable `error:` convention, and management commands produce no entry-point return-value output.

Run `python3 baml_language/wrapper_tests/run` to compare both implementations and both self-update variants. Release workflows pack candidates for every wrapper platform from the same run's compiler and pack-host artifacts, verify their embedded release fingerprint, and gate the release on wrapper tests. Candidate archives remain separate from the shipping Rust wrapper archives until promotion. The wrapper version is intentionally unchanged; this work does not publish a release.

Both wrappers implement a separate wrapper telemetry pipeline, with `wrapper_invocation`, `wrapper_resolution`, `wrapper_install`, `wrapper_selection`, `wrapper_update`, and `wrapper_self_update` events. They share `$BAML_HOME/wrapper-telemetry.toml` and `$BAML_HOME/wrapper-telemetry/`; `DO_NOT_TRACK`, a disabled wrapper preference, or the disabled global CLI telemetry preference suppress collection and delivery. Events contain coarse wrapper metadata and bounded decisions/outcomes, without raw selectors, paths, arguments, or errors. Delivery occurs only in a detached `__flush-wrapper-telemetry` helper; Rust seals and spawns it before `exec()`. The BAML build derives ingestion constants from the independent Rust wrapper module. See [TELEMETRY.md](../../TELEMETRY.md) for fields and opt-out behavior.
