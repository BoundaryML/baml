# Multiple runtime registrations

## Requirements

A host process loads one CFFI bridge library and may register several BAML programs. Loading a generated SDK must preserve every previously loaded program. Each runtime-bound operation, including asynchronous calls, callbacks, closures, streams, and function specifications, must preserve its origin. Keys are unsigned 64-bit values throughout Rust, C, WASM, and host bindings. Java uses the bits of a `long`; JavaScript uses `bigint`, never `number`.

Identical generated contents may reuse an engine. Distinct generated programs must coexist, including programs that declare different host classes under the same BAML FQN. Conflicting registrations must fail without changing the existing registration. Dynamic instances must remain independent even when their source contents match. Registration and lookup must be thread-safe, and removing a registration must not invalidate calls that already acquired their runtime.

## Design

`bridge_cffi::runtime_registry` owns a process-wide `RwLock` around a map from `u64` to an `Arc<dyn Bex>` and the registration's canonical program bytes. Generated registration compares the complete canonical bytes under the same write lock that constructs and inserts the engine. Repeated identical registration returns the existing engine; a collision produces an explicit error. Construction failure leaves the registry unchanged. A constructor panic is caught before it can poison the registry lock.

`baml_program_identity` defines a versioned SHA-256 identity over the decoded executable program serialized with Borsh's deterministic map ordering. It excludes the artifact envelope and diagnostic file identities, source paths, debug locals, line tables, and debug metadata. It retains executable contents and program declarations. The first eight digest bytes, interpreted in big-endian order with bit 63 set, are the generated key. This reserves the upper half for generated programs and the lower half for monotonically allocated dynamic registrations. A 63-bit digest collision is possible and is detected by the full canonical-content comparison; it never silently replaces another program. Regeneration after a compiler change may produce a different key because executable bytecode is part of program identity.

Generated SDK roots embed this key and register their bytecode. Python, Node, Web, Go, Rust, C++, C#, Java, and Swift generated calls bind to that registration. The legacy Python source-emitting generator hashes a versioned, length-delimited list of sorted program-relative filenames and their contents and registers those canonical source bytes. Absolute paths and parent traversal are rejected. Ruby's current initialization-only bridge obtains the same canonical identity through the C ABI. Generated registrations are process-owned: unloading one imported module cannot unregister an engine shared by another import. Distinct Python imports and Java class loaders retain independent host type maps even when they share the same native program. TypeScript factories capture their SDK's map. Callback dispatch captures the originating map, including deferred result/error encoding, instead of depending on whichever SDK loaded last.

Program identity is separate from configured-instance identity. Generated registration represents the shared default instance of that program. Callers that need independent state or different system operations must use dynamic creation without a generated key. Dynamic construction always allocates a fresh lower-half key, including for identical bytecode. Python and JavaScript runtime handles expose their key and `close`; the C ABI exposes `create_runtime` and `unregister_runtime`. Rust, Go, and Swift also provide dynamic bytecode constructors. Closing a dynamic registration prevents new calls by that key. Explicit close is required; abandoning a host runtime handle alone does not unregister it. Keys are never reassigned during the process lifetime.

Dispatch resolves and retains an `Arc` before consuming arguments. Native capability-table entries retain their runtime and key, and clones preserve that ownership. This allows legacy capability calls to infer their engine; named and capability call dispatch rejects arguments carrying handles from a different runtime. Host-callable and host-opaque keys have a separate namespace and are excluded from native capability lookup. In-flight calls and capability handles keep the engine alive after unregistration; the final dynamic owner schedules shutdown and drains host-value releases after its remaining calls and handles finish. The process shutdown path also visits still-live unregistered engines through weak identities and waits for spawned work. Existing process-wide shutdown remains a final teardown operation, not a way to unload one SDK. Node callback registrations retain their JavaScript functions without pinning the event loop: pending native-call promises keep active calls alive, and the `beforeExit` shutdown hook drains background work and generated registrations.

Function-call identifiers and callback transport remain process-wide and unique. The active-call map retains each call's runtime for cancellation; duplicate active call IDs fail explicitly. Handle cloning/releasing and media operations remain process-wide because their handles already identify owned values. Legacy named-call entry points work only when runtime selection is unambiguous; they report an error when multiple programs are registered.

The C ABI revision-2 table grows append-only with `register_program`, `create_runtime`, `unregister_runtime`, `call_function_for_runtime`, and `program_key`. Existing slots retain their offsets. Updated consumers check the table extent before accessing the new slots. SDKs using new routing require an updated bridge library. Checked-in C headers and JavaScript declarations/build artifacts must be regenerated with their normal repository scripts.

## Regression checks

`../sdk_tests/multi_program/run.py` generates programs A and B with overlapping function and class names, then loads both within one Python process and within one Node process. It checks typed results, instance methods, closures, concurrent async callbacks, streaming, repeated generated imports, rejected conflicts, dynamic-instance separation, explicit close, and keys above JavaScript's safe-integer range through `2**64 - 1`. It also generates an identical program in a different directory and asserts equal generated identities. The native registry tests exercise concurrent registration, collision safety, diagnostic-path canonicalization, and capability ownership after removal. Web runtime tests exercise independent dynamic registrations with an in-flight callback.

To reproduce from `baml_language`, build `baml_cli`, build the Python bridge with `maturin develop` in its virtual environment, and build the Node bridge using its package scripts. Then run `python3 sdk_tests/multi_program/run.py`. The runner uses `sdks/python/.venv/bin/python`, the Node bridge workspace dependencies, and `target/debug/baml-cli`; it does not download or use a published bridge. Generated regression SDKs are ignored build artifacts.

## Review follow-up

Call IDs have explicit reservation ownership. Allocation reserves an ID so cancellation before dispatch remains attached to its eventual originating runtime. Native preparation claims that reservation, and the in-flight call owns its route until completion. Encoding failures and abandoned preparations release their reservations; callers using the raw ABI can release an undispatched ID with the appended `release_function_call` slot. Releasing a caller reservation after dispatch does not cancel or discard the dispatched call. Cancelling an unknown, released, or completed ID returns false and allocates no state. Dynamic runtime IDs are monotonic and need no retirement tombstones. Generated registration compilation uses a separate lock so existing runtime lookups remain available during a slow import.

Generated registrations remain process-owned in every binding, including Web. Calling `close()` on a generated registration fails explicitly; one import cannot invalidate another import of the same program. Dynamic runtime handles support explicit close. Java inspects nested argument containers, registered class fields, and union records before encoding, selects the originating program for raw helper calls, and rejects mixed runtime capabilities. Source-mode Python fixtures exercise actual generated package imports alongside bytecode SDKs.

The review follow-up passed seven Python multi-program tests, the TypeScript multi-program executable, eleven Chromium/Web tests, 45 native CFFI unit/registry tests, 208 Python/Go generator tests, two Java routing unit tests, the Go bridge suite, and the C++ bridge smoke. The updated C# bridge and Swift source module compile. The preceding PR commit passed the complete Linux/Windows SDK CI matrix; the review changes are verified again by PR CI.

Python raw helpers preserve the type map attached to a specific generated SDK runtime wrapper, even when another import shares the same native program key. A wrapper holds a weak reference to that map to avoid an ownership cycle. A fresh key-only runtime lookup has no SDK import identity and falls back to the first registered map for the key; generated call factories continue to capture their own SDK map.
